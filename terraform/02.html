Terraform テラフォーム

設計図（コード）を書くと、その通りにクラウド上に建物（サーバなど）を建ててくれる道具。

AWS エーダブリューエス

世界一大きな「貸し土地屋さん」。クラウド上の土地を貸してくれる。この本ではずっとここを使う。

プロバイダ provider

建物を建てる土地を貸す業者の指定。「AWSの、この地域に建てる」と宣言する部分。

リソース resource

建てる建物そのもの。サーバ・門・門番など、Terraformが作る物のこと。

EC2インスタンス aws_instance

クラウド上に建てる仮想のサーバ1台。この章でいう「小屋」。

AMI Amazon Machine Image

サーバの土台になるOSや初期状態の型。建物の「完成見本の型紙」。

IAM アイアム

誰が何をできるかを管理する仕組み。権限を絞った作業員アカウントを作るのに使う。

VPC 仮想プライベートクラウド

AWSの広い土地の中に持つ、自分専用のフェンスで囲った敷地。建物はこの中に建つ。

セキュリティグループ security group

建物の出入りを管理する門（ファイアウォール）。どのポートに誰が入れるかを決める。

入力変数 variable

設計図に外から値を渡せる差し込み口。同じ値を1か所で管理するのに使う。

出力変数 output

設計図の外に値（サーバの住所など）を返す出口。

データソース data source

AWSから読み取り専用で情報を取り寄せる仕組み。建物は作らず、既存の情報を取得するだけ。

ASG Auto Scalingグループ

サーバの長屋を自動管理する大家。戸の起動・監視・建て替え・戸数調整を全部やってくれる。

ロードバランサ ELB / ALB

客を複数のサーバに公平に振り分ける「門番」。入り口を1つにまとめる。

DRY原則 Don't Repeat Yourself

同じ情報を繰り返し書くな、という原則。重複は直し忘れ事故のもと。

Infrastructure as Code IaC

インフラ（建物）をコード（設計図）として管理する考え方。コードがあれば何度でも再現できる。

2.0

なぜAWSという土地で学ぶのか

どこの土地を借りて練習するか

要するに：Terraformはいろんなクラウドに使えるが、この本では一番人気で機能が豊富、しかも無料枠で練習できるAWSという土地を使う。

棟梁
棟梁ハル、ここが今日の現場だ。見てごらん。何もない更地だろう。お前が「設計図」を1枚書くだけで、この更地に勝手に小屋が建つ。道具の名前はTerraformだ。
ハル
ハル設計図を書くだけで建つ？魔法ですか？そもそもこの「更地」って、誰の土地なんですか？
棟梁
棟梁魔法じゃない、仕組みだ。土地はAWSという世界一大きな「貸し土地屋さん」の区画だよ。TerraformはAzureやGoogle Cloud、自前の土地にも建てられるが、この本ではずっとAWSを使う。
ハル
ハルなんでAWSなんですか？
棟梁
棟梁理由は3つだ。①シェア32%で一番人気、②建てられる建物の種類が豊富、③最初の1年は無料枠があってほぼタダで練習できる。
ハル
ハル人気で・道具が揃ってて・しかもタダ同然で練習できる土地だから、ってことですね！

🏗️ たとえ話

家を建てる練習をするなら、まずどこの土地を借りるか決める。AWSは「日本一お客が多くて、建築資材も道具も何でも揃っていて、しかも最初の1年は地代タダ」という、練習にうってつけの貸し土地屋さん。だからこの本では、ずっとこの土地で建築の練習をする。

2.1

AWSアカウントのセットアップ

更地を借りる手続き

要するに：大家さんの鍵（ルートユーザ）は最初の1回だけ。すぐに権限を絞った作業員（IAMユーザ）を作り、その名札番号と合言葉（アクセスキー）を安全に保管する。建物は自分専用の敷地（デフォルトVPC）に建つ。

ハル
ハル土地を借りるには、まず何をすればいいんですか？
棟梁
棟梁AWSの登録ページで申し込む。登録直後のお前は「ルートユーザ（土地の大家さん本人）」だ。これは土地のほぼ全部に手を出せる強い権限を持っている。
ハル
ハル強いなら、ずっとそれを使えばいいじゃないですか。
棟梁
棟梁そこが落とし穴だ。強すぎる鍵を毎日持ち歩くのは危ない。落としたら土地を全部乗っ取られる。だから大家さんの鍵を使う目的はただ1つ、「権限の限られた作業員アカウントを作ること」だけ。作ったらすぐ乗り換える。
ハル
ハル作業員アカウントってどうやって作るんですか？
棟梁
棟梁IAMというサービスを使う。IAMの画面 → ユーザー → ユーザーを追加 → 名前を入れて「プログラムによるアクセス」を選ぶ。これで新しい作業員ができる。
棟梁
棟梁ただし作りたての作業員は何の権限もない。仕事をさせるにはIAMポリシーという許可証を渡す。練習用ならAdministratorAccessという既製品を1枚付けるのが一番楽だ。
ハル
ハル許可証を付けたら完成ですか？
棟梁
棟梁「ユーザーの作成」を押すと身分証が2枚出る。アクセスキーIDとシークレットアクセスキーだ。画面を閉じると二度と表示されない。すぐ安全な場所に保管して、絶対に他人に見せるな。

🏗️ たとえ話

土地を借りた直後、お前の手には「敷地の何もかもを開けられるマスターキー（大家さんの鍵）」が握らされている。でもこの鍵を毎日工事に持って出るのは危険だ。落とせば敷地ごと乗っ取られる。だからこのマスターキーで最初にやるのは、「特定の工事だけできる作業員用の鍵を1本作ること」だけ。普段はその作業員の鍵で工事をする。作業員には「これとこれをしてよい」という許可証（IAMポリシー）を持たせ、その作業員の名札番号と合言葉は金庫にしまう。

このコードは、AWSの管理画面で行う「画面操作」の流れをメモしたものです（実際に打つコマンドではありません）。

画面操作の流れ（参考）
# AWSの管理画面でやる作業（コマンドではなく画面操作）の流れ
# 1. ルートユーザでログイン
# 2. IAM画面を開く → ユーザーを追加
# 3. AdministratorAccess の許可証を付ける
# 4. アクセスキーID と シークレットアクセスキー を保存する（二度と表示されない！）
棟梁
棟梁もう1つ覚えておくこと。この本の例はすべて、お前のアカウントの「デフォルトVPC」という区画の中に建つ。
ハル
ハルVPCって何ですか？
棟梁
棟梁VPCだ。AWSの広い土地の中に、自分専用のフェンスで囲った敷地を持つようなもの。2013年以降のアカウントには最初から「デフォルトVPC（既定の敷地）」がある。指定しなければ建物は自動でそこに建つ。うっかり消したら、別のリージョンを使うか、管理画面で作り直せばいい。

💡 なぜこれが必要か

  • 強すぎる鍵を日常使いしないことで、乗っ取り被害を最小限にできる。
  • アクセスキーを用意しておくと、後でTerraformがAWSの土地に建物を建てられる。

📌 この項のまとめ

  • ルートユーザ＝大家さん本人。作業員を作る目的だけに使う。
  • IAMユーザ＝権限を絞った作業員。IAMポリシー（許可証）を付けて初めて仕事ができる。
  • 練習用ならAdministratorAccessを付けるのが一番簡単。
  • アクセスキーID／シークレットアクセスキーは二度と表示されないので即保管・他人に見せない。
  • 建物はデフォルトVPC（自分専用の敷地）の中に建つ。
2.2

Terraformのインストール

道具を手に入れる

要するに：Terraform本体を入れてterraformで動作確認する。AWSの名札番号と合言葉を環境変数（一時的な付箋）としてターミナルに貼ると、道具がAWSの土地を操作できるようになる。

ハル
ハル土地は借りました。次は道具ですね。Terraform本体はどう手に入れるんですか？
棟梁
棟梁お前のパソコンの「道具の宅配屋さん（パッケージマネージャ）」を使うのが一番楽だ。MacならHomebrew、WindowsならChocolatey、Linuxは公式ドキュメントか手動ダウンロードだ。
ハル
ハルちゃんと使えるか、どう確かめるんですか？
棟梁
棟梁ただterraformと打ってみろ。使い方の一覧が出れば成功だ。

🏗️ たとえ話

土地は借りた。次は工具一式（Terraform本体）を手に入れる番だ。一番楽なのは「道具の宅配屋さん」に頼むこと。手に入れたら、まず工具を握って空振りしてみて、ちゃんと動くか確かめる。さらに、この工具で借りた土地に入るには「作業員の名札番号と合言葉」を工具に教えておく必要がある。これは作業現場の入り口に貼る付箋のようなもので、現場（ターミナル）を閉じると剥がれてしまう。

このコードは、MacのHomebrewでTerraform本体を取り寄せます。

Macでインストール
# MacのHomebrewでTerraformを取り寄せる
$ brew tap hashicorp/tap
$ brew install hashicorp/tap/terraform

このコードは、WindowsのChocolateyでTerraform本体を取り寄せます。

Windowsでインストール
# WindowsのChocolateyでTerraformを取り寄せる
$ choco install terraform
棟梁
棟梁手動でも入れられる。公式サイトからOSに合ったZIPを落として展開するとterraformという1個の道具が出る。それをPATHという「どこからでも呼び出せる道具棚」に置く。

このコードは、道具がちゃんと使えるか確認します。使い方の一覧が出ればOKです。

動作確認と主なコマンド一覧
# 道具が使えるか確認する。使い方の一覧が出ればOK
$ terraform
Usage: terraform [global options] <subcommand> [args]

Main commands:
  init          作業フォルダを他のコマンドが使えるよう準備する
  validate      設定が正しいか検査する
  plan          今の設定で必要になる変更を表示する
  apply         インフラを作成・更新する
  destroy       前に作ったインフラを取り壊す
(...)
ハル
ハル道具は使えました。でもこの道具、どうやって私のAWSの土地に入るんですか？合言葉とか要りますよね。
棟梁
棟梁いいところに気づいた。さっき保存したアクセスキーIDとシークレットアクセスキーを「環境変数」という形で道具に渡す。環境変数は、ターミナルに一時的に貼っておく付箋みたいなものだ。

このコードは、AWSの名札番号と合言葉を、道具に渡すための付箋としてターミナルに貼ります（Mac・Linux）。

認証情報を環境変数で渡す（Mac・Linux）
# AWSの名札番号と合言葉を、道具に渡すための付箋として貼る
$ export AWS_ACCESS_KEY_ID=(あなたのアクセスキーID)
$ export AWS_SECRET_ACCESS_KEY=(あなたのシークレットアクセスキー)

このコードは、同じことをWindowsのコマンドプロンプトで行います。

認証情報を環境変数で渡す（Windows）
# Windowsの場合
$ set AWS_ACCESS_KEY_ID=(あなたのアクセスキーID)
$ set AWS_SECRET_ACCESS_KEY=(あなたのシークレットアクセスキー)
ハル
ハルこれ、パソコンを再起動したら消えちゃいませんか？他の渡し方もあるんですか？
棟梁
棟梁そのとおり。この付箋は今開いているターミナルだけのもの。再起動したら貼り直す。他にもaws configureで$HOME/.aws/に保存する方法や、IAMロールで認証する方法もある。詳しくは6章だ。今は環境変数で十分。

💡 なぜこれが必要か

  • 道具がないと設計図を実行できない。
  • 認証情報を渡すことで、はじめて自分のAWSに建物を建てられる。

📌 この項のまとめ

  • インストールはパッケージマネージャ（Homebrew/Chocolatey）か手動ダウンロードで行う。
  • terraformと打って使い方が出れば成功。
  • アクセスキーはAWS_ACCESS_KEY_IDとAWS_SECRET_ACCESS_KEYという環境変数で渡す。
  • 環境変数は今のターミナル限り。再起動したら貼り直す。
  • 他にも~/.aws/の認証情報やIAMロールでの認証もできる（6章で詳説）。
2.3

サーバ1台のデプロイ

更地に最初の小屋を1軒建てる

要するに：.tfファイルに「欲しい建物」を宣言型で書き、initで準備、planで予習、applyで建築する。Terraformは建てたものを覚えているので、設計図を変えると差分だけを反映する。

ハル
ハルいよいよ建てるんですね！設計図ってどう書くんですか？
棟梁
棟梁設計図は拡張子.tfのファイルに、HCLという言葉で書く。HCLは「宣言型言語」だ。
ハル
ハル宣言型？
棟梁
棟梁「どう建てるか」じゃなく「どんな建物が欲しいか」だけ書けばいい言語だ。「小屋が1軒欲しい」と書けば、釘を打つ順番はTerraformが勝手に考える。手順を一つ一つ書く「手続き型」とは逆だ。書くエディタはメモ帳でもいいが、VS Codeなど多くが色付けに対応している（検索は「HCL」で）。

🏗️ たとえ話

普通の設計図は「まず基礎を打って、次に柱を立てて…」と手順を細かく書く（手続き型）。Terraformの設計図はそうじゃない。「ここに小屋を1軒、大きさはこれくらい」と完成形の希望だけを書く（宣言型）。すると棟梁（Terraform）が、釘を打つ順番から何から全部考えて建ててくれる。お前は「欲しい家の姿」だけ伝えればいい。

このコードは、設計図の冒頭で「どの貸し土地屋（AWS）の、どの地域に建てるか」を宣言します。

provider（業者と地域の宣言）
# provider（プロバイダ）＝建物を建てる土地を貸す業者の指定
provider "aws" {
  region = "us-east-2"   # ① 建てる地域。us-east-2 はアメリカ・オハイオ
}
ハル
ハルregionって何ですか？
棟梁
棟梁リージョン（地域）だ。さらに各リージョンの中にアベイラビリティゾーンという別々の建物群がある。この本は原文どおりus-east-2を使う（日本には東京・大阪リージョンもある）。

このコードは、建てたい建物（リソース）を書くときの一般的な型です。

リソースの書き方（型）
# 建物（リソース）を書くときの一般的な型
resource "<プロバイダ>_<タイプ>" "<名前>" {
  [設定 ...]
}

このコードは、更地に仮想サーバ（小屋）を1台建てる設計図です。

サーバ1台を建てる設計図
# 更地に仮想サーバ（EC2インスタンス）を1台建てる設計図
resource "aws_instance" "example" {
  ami           = "ami-0fb653ca2d3203ac1"   # ① 設計テンプレート。中身はUbuntu 20.04
  instance_type = "t2.micro"                # ② 建物の大きさ。一番小さい無料枠サイズ
}
ハル
ハルamiとinstance_typeって何ですか？
棟梁
棟梁amiはAMI。建物でいう「内装まで決まった完成見本の型紙」だ。注意点としてAMI IDは地域ごとに違う。regionを変えるなら自分で探して書き換える（自動取得は7章）。instance_typeはサーバの大きさ。t2.microはCPU1個・メモリ1GBの無料枠だ。
ハル
ハル引数って全部覚えなきゃダメですか？
棟梁
棟梁無理だよ。膨大にある。全部暗記する人間はいない。その都度公式ドキュメントを見る。わしも何年もやってるが、いまだに1日に何度も見るよ。

ワークフロー: init → plan → apply

設計図ができたら、この3ステップで実行します。

init

準備する

設計図を読んで「AWSを使うんだな」と判断し、AWS用のコードをネットから取り寄せて.terraformフォルダに置く。最初の1回。冪等なので何度実行してもOK。

plan

予習する

「設計図どおりに建てたら何が起きるか」を、建てる前に差分で見せる。+は追加、-は削除、~は変更。

apply

実行する

本当に建てる。同じ差分を見せて「本当にやっていいか？」と聞き、yesで建築開始。

🏗️ たとえ話

Webサーバ1台のデプロイ

小屋を人が住める家にする

要するに：素のサーバにユーザーデータで「初回起動時にWebサーバを立てる仕込み」を渡し、セキュリティグループという門でポート8080を開け、参照でそれを小屋に取り付ける。仕込みを変えると小屋は丸ごと建て替えになる。

ハル
ハル小屋は建ちましたが、ただの箱ですよね。中で何か動かしたいです。
棟梁
棟梁次はこの小屋でWebサーバを動かす。目標は「HTTPリクエストに応答する、できるだけシンプルなWeb」だ。例を単純にするため、いつでも「Hello, World」だけ返す超簡単なサーバを動かす。

🏗️ たとえ話

更地に建てた小屋は、まだ電気も水道も通っていない「ただの箱」だ。これを人が住める家にするには、引っ越し直後に呼び鈴が鳴ったら「いらっしゃい（Hello, World）」と応対できる住人を住まわせる必要がある。さらに、小屋には外との出入り口を管理する「門」を付けて、決まった入り口（ポート）だけ客を通すようにする。

このコードは、index.htmlに文字を書き、ポート8080で簡易Webサーバを立ち上げる仕込みスクリプトです。

仕込みスクリプト（Hello, World を返す）
# index.htmlに文字を書き、ポート8080で簡易Webサーバを立ち上げるスクリプト
#!/bin/bash
echo "Hello, World" > index.html
nohup busybox httpd -f -p 8080 &
ハル
ハルこの呪文、何をしてるんですか？
棟梁
棟梁1行目でindex.htmlに「Hello, World」と書き込む。2行目でbusybox（Ubuntuに最初から入る万能ツール）を起動し、ポート8080でWebサーバを立て、それを配る。nohupと末尾の&は、スクリプトが終わってもサーバが裏で動き続けるためだ。
ハル
ハルなんでポート80じゃなくて8080なんですか？普通のWebは80ですよね。
棟梁
棟梁鋭い。1024以下のポート（80もそう）で待ち受けるにはroot（管理者）権限が要る。侵入されたら侵入者もroot権限を得て危険だ。だからWebサーバは権限の限られた一般ユーザで動かすのがベストプラクティスで、結果1024より大きい8080などを使う。後半では門番でポート80を受けてサーバに流す方法も見る。
ハル
ハルこのスクリプト、どうやってサーバの中で実行するんですか？
棟梁
棟梁普通はPackerでAMIを焼くが、今回は1行スクリプトだけなので、素のUbuntu AMIのまま、EC2の「ユーザーデータ（初回起動時に自動実行する仕込みスクリプト）」として渡す。設計図にuser_data引数を足す。

このコードは、小屋を建てると同時に「初回起動でWebサーバを立ち上げる仕込み」を渡します。

user_data を渡す設計図
# 小屋を建てると同時に「初回起動でWebサーバを立ち上げる仕込み」を渡す
resource "aws_instance" "example" {
  ami           = "ami-0fb653ca2d3203ac1"
  instance_type = "t2.micro"

  user_data = <<-EOF
              #!/bin/bash
              echo "Hello, World" > index.html
              nohup busybox httpd -f -p 8080 &
              EOF

  user_data_replace_on_change = true   # ① 仕込みを変えたら古い小屋を壊して新築し直す

  tags = {
    Name = "terraform-example"
  }
}
ハル
ハル<<-EOFって何ですか？user_data_replace_on_change = trueは？
棟梁
棟梁<<-EOFはヒアドキュメント。間を1つの長い文字列として渡せる。user_data_replace_on_changeは、仕込みスクリプトが「初回起動時しか実行されない」ため必要だ。すでに動く小屋は起動済みなので仕込みを書き換えても反映されない。だからtrueにして「仕込みを変えたら古い小屋を壊して新築しろ」と指示する。

このコードは、ポート8080への外からのアクセスを許可する門（セキュリティグループ）を作ります。

セキュリティグループ（門）
# ポート8080への外からのアクセスを許可する門（セキュリティグループ）
resource "aws_security_group" "instance" {
  name = "terraform-example-instance"

  ingress {
    from_port   = 8080            # ① 受け付け開始ポート
    to_port     = 8080            # ② 受け付け終了ポート（8080だけ許可）
    protocol    = "tcp"           # ③ 通信の種類はTCP
    cidr_blocks = ["0.0.0.0/0"]   # ④ どのIPからのアクセスも許可
  }
}
ハル
ハルingressと0.0.0.0/0って何ですか？
棟梁
棟梁ingressは「内向き」の許可ルールだ。0.0.0.0/0はCIDRブロックの一種で「あり得るすべてのIP」を意味する。つまりこの門は、どこの誰でもポート8080に来てよい、という設定だ。
ハル
ハル門は作りました。でもこの門と小屋、どうつなぐんですか？
棟梁
棟梁門のIDを小屋のvpc_security_group_idsに渡す。そのために「式」を学ぶ。これまでの"ami-..."や5は、一番単純な「リテラル」という式だ。
ハル
ハル他の建物の情報を引っぱってくることもできるんですか？
棟梁
棟梁できる。それが「参照」だ。書き方は<PROVIDER>_<TYPE>.<NAME>.<ATTRIBUTE>。セキュリティグループはid属性を公開するのでaws_security_group.instance.idと書く。

このコードは、属性を参照する書き方の一般的な型と、さっき作った門のIDを指し示す参照です。

参照の書き方
# 参照の書き方
<PROVIDER>_<TYPE>.<NAME>.<ATTRIBUTE>

# さっき作った門のIDを指し示す参照
aws_security_group.instance.id

このコードは、小屋に「この門を使え」と指示します。

門を小屋に取り付ける設計図
# 小屋に「この門を使え」と指示した設計図
resource "aws_instance" "example" {
  ami                    = "ami-0fb653ca2d3203ac1"
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.instance.id]   # ① 門を小屋に取り付ける

  user_data = <<-EOF
              #!/bin/bash
              echo "Hello, World" > index.html
              nohup busybox httpd -f -p 8080 &
              EOF
  user_data_replace_on_change = true

  tags = {
    Name = "terraform-example"
  }
}
ハル
ハル順番とか大丈夫なんですか？門より小屋が先にできちゃったら困りませんか？
棟梁
棟梁心配ない。建物Aが建物Bを参照すると「暗黙的依存」ができる。Terraformはこれを読み取って依存グラフ（依存の地図）を作り、正しい順番を自分で決める。今回は小屋が門のIDを参照してるので「門が先、小屋が後」。terraform graphで地図を見られる。

🏗️ たとえ話

「小屋に門を取り付ける」と設計図に書けば、棟梁（Terraform）は自然と「じゃあ門を先に作らないとな」と気づく。これが暗黙的依存だ。誰かに「先に門を作れ」と指示しなくても、設計図の中で小屋が門を指さしている（参照している）から、棟梁が建てる順番を自動で決めてくれる。しかも前後関係のない建物は同時に建てるから工事が早い。

このコードは、建物どうしの前後関係（依存グラフ）を表示します。出力はDOTというグラフ記述言語です。

terraform graph（依存グラフ）

    "[root] aws_instance.example"

棟梁
棟梁これはDOTというグラフ記述言語だ。GraphvizやGraphvizOnlineに貼ると絵になる。Terraformはこの地図をたどり、前後関係のない建物は同時並行で建てる。「欲しい物を書けば、最も効率のよい建て方をTerraformが判断する」、これが宣言型の素晴らしさだ。ではapplyだ。

このコードは、門を新設し、既存の小屋を新しい仕込み入りの小屋で置き換える様子です。

apply（置き換えの差分）

$ terraform apply

        ami                    = "ami-0fb653ca2d3203ac1"

ハル
ハル-/+って記号が出てます。さっきの~（その場更新）とは違いますね。
棟梁
棟梁-/+は「置き換え」だ。原因は# forces replacementという注記で分かる。今回はuser_dataを変えたので、古い小屋を取り壊して完全に新築する。これは「イミュータブルインフラ」の一例だ。注意点として、置き換えの間はWebが使えない時間（ダウンタイム）が出る。停止時間なしの方法は5章だ。

このコードは、建てたWebサーバに「ページちょうだい」とリクエストして動作を確認します。

curl で動作確認

ハル
ハル「Hello, World」が返ってきました！本当に動いてますね！
棟梁
棟梁最後にネットワークの注意を1つ。この本ではシンプルさのため、すべての建物をデフォルトVPCの「デフォルトサブネット」に置いている。
ハル
ハルサブネットって何ですか？
棟梁
棟梁VPC（敷地）は別々のIPアドレス帯を持つ複数のサブネットに分かれている。デフォルトVPCの小区画はすべてパブリックサブネットで、外からアクセスできる住所がつく。練習ならいいが本番では危険だ。本番ではサーバを外から届かないプライベートサブネットに置き、道路に面した区画には門番だけを置く。

💡 なぜこれが必要か

  • ユーザーデータを使えば、AMIを作らなくてもサーバ起動時に好きな初期設定ができる。
  • セキュリティグループで、誰がどのポートに入れるかを制御できる。
  • 参照を使うと、建物どうしを結び付け、正しい建築順序を自動化できる。

📌 この項のまとめ

  • user_data＝初回起動時に走る仕込みスクリプト。変更時はuser_data_replace_on_change = trueで建て替え。
  • <<-EOF ... EOF＝複数行文字列を書くヒアドキュメント。
  • セキュリティグループ＝出入りを管理する門。ingressで内向き許可、0.0.0.0/0で全IP許可、CIDRはIP範囲の表記。
  • 式＝値を返す書き方。リテラル（値そのもの）と参照（他の場所の値を指す）がある。
  • 参照<種類>.<名前>.<属性>で暗黙的依存ができ、Terraformが建築順を自動決定（terraform graphで確認）。
  • -/+は置き換え（イミュータブルインフラ）、~はその場更新。置き換え中はダウンタイムが出る。
  • 練習はパブリックサブネットでOKだが、本番はサーバをプライベートサブネットへ。

設定変更可能なWebサーバのデプロイ

同じ寸法を1か所で管理する

要するに：同じ値の重複（DRY違反）は入力変数でまとめる。変数にはdescription/default/type/validation/sensitiveが付けられる。var.名前で参照、文字列内なら${...}で補間。出力変数で結果を外に取り出せる。

ハル
ハル棟梁、気づいたんですけど「8080」って、門の設定とユーザーデータの2か所に書いてますよね。
棟梁
棟梁よく気づいた。それはDRY原則に反している。同じ寸法を2か所に書くと、片方だけ直してもう片方を直し忘れる事故が起きる。
ハル
ハルどうすれば1か所にまとめられるんですか？
棟梁
棟梁「入力変数」を使う。設計図に外から値を渡せる差し込み口だ。variable "NAME" { ... }と書く。

🏗️ たとえ話

「窓の高さは120cm」という寸法を、玄関の図面と居間の図面の2か所に手書きすると、後で「やっぱり130cmに」と直すとき片方を直し忘れる。これがDRY違反だ。賢い大工は、寸法を「寸法表」に1つだけ書いて、各図面からはその寸法表を見るようにする。これが入力変数。直すときは寸法表の1か所を変えるだけで、全部の図面に反映される。

入力変数のパラメータ

パラメータ役割
descriptionこの変数が何に使われるかの説明。plan/apply時にも表示されるので常に書くのがよい。
default値が渡されなかったときの既定値。渡し方は-var・-var-file・環境変数TF_VAR_<名前>の3つ。どれもなければ対話的に聞かれる。
type渡せる値の種類を縛る。string・number・bool・list・map・set・object・tuple・any。書かないとany扱い。常に付けるのがよい。
validation型チェック以上の独自検査（最大・最小値など）。詳しくは8章。
sensitivetrueでその値をログに出さない。パスワードやAPIキーなどに付ける。詳しくは6章。

入力変数の書き方

型の例（number / list / list(number)）

variable "object_example" {

ハル
ハル毎回聞かれるのは面倒です。聞かれないようにできますか？
棟梁
棟梁3つやり方がある。①コマンドラインで-var、②環境変数TF_VAR_<名前>、③default値を書く。③が一番楽だ。

このコードは、値の3つの渡し方（コマンドライン・環境変数・default）です。

値の3つの渡し方
# ① コマンドラインで値を渡す

}

棟梁変数の値を設計図で使うときは「変数参照」を使う。書き方はvar.<変数名>だ。門のfrom_portとto_portをserver_portにしてみよう。

このコードは、門のポート番号を、ハードコードではなく変数で指定します。

門のポートを変数参照に

  name = "terraform-example-instance"
  ingress {
    from_port   = var.server_port   # ① 変数の値を参照
    to_port     = var.server_port   # ② 同じ変数を参照（1か所で管理）
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
ハル
ハルユーザーデータの中の「8080」も同じ変数にしたいです。でも文字列の途中ですよね？
棟梁
棟梁そういうときは「補間」を使う。書き方は"${...}"。波括弧の中に参照を書けば、Terraformがそれを文字列に変換して埋め込む。

このコードは、文字列の中に変数を埋め込みます（補間）。

補間 ${...}
# 文字列の中に変数を埋め込む（補間）
  user_data = <<-EOF
              #!/bin/bash
              echo "Hello, World" > index.html
              nohup busybox httpd -f -p ${var.server_port} &
              EOF

出力変数

棟梁
棟梁入力変数の逆もある。「出力変数」だ。設計図の外に値を返す出口だ。output "<NAME>" { value = <VALUE> }と書く。CONFIGにはdescription、sensitive、depends_onが書ける。
CONFIG役割
descriptionどんなデータが出るかの説明。常に書く。
sensitivetrueでplan/applyの最後に表示しない。秘密情報を含むとき。入力変数や機密属性を参照するなら出力にも必要。
depends_on普段は参照から依存を自動判断するが、まれに手動でヒントを与える明示的な依存指定。

このコードは、出力変数の書き方の型と、WebサーバのパブリックIPを実行後に表示する例です。

出力変数の書き方
# 出力変数の書き方
output "<NAME>" {
  value = <VALUE>
  [CONFIG ...]
}

# WebサーバのパブリックIPを実行後に表示する出力変数
output "public_ip" {
  value       = aws_instance.example.public_ip   # ① 小屋のパブリックIP属性を参照
  description = "Webサーバのパブリックなアドレス"
}

このコードは、何も建物を変えていないので作成は0件ですが、最後に出力が表示される様子です。

apply の出力表示
# 何も変えていないので作成は0件。だが最後に出力が表示される
$ terraform apply
(...)
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.

Outputs:
public_ip = "54.174.13.5"

このコードは、変更を加えずに出力だけを一覧表示・取り出します。

terraform output
# 出力だけを一覧表示する
$ terraform output
public_ip = "54.174.13.5"

# 特定の出力だけ取り出す
$ terraform output public_ip
"54.174.13.5"
棟梁
棟梁これはスクリプトで便利だ。applyでデプロイ → output public_ipでIP取得 → curlで叩いて成功確認、という簡単な動作確認（スモークテスト）が組める。入力変数と出力変数は、設定可能で再利用可能なインフラコードを作る重要な機能だ（4章で詳説）。

💡 なぜこれが必要か

  • 同じ値を1か所で管理でき、直し忘れ事故を防げる。
  • 型制約で、間違った種類の値を実行前に弾ける。
  • 出力変数で、IPなどの結果をすぐ取り出せて自動化に使える。

📌 この項のまとめ

  • DRY原則＝同じ情報を繰り返さない。重複は入力変数で解消する。
  • 入力変数のパラメータ: description/default/type/validation/sensitive。
  • 型: string・number・bool・list・map・set・object・tuple・any。型違反は実行前にエラー。
  • 値の渡し方: -var、-var-file、TF_VAR_<名前>、default、対話入力。
  • 参照はvar.<名前>、文字列内は${...}の補間。
  • 出力変数はoutputで定義。terraform outputで表示。sensitive/depends_onも指定可。
2.6

Webサーバのクラスタのデプロイ

1軒を何戸もの長屋にする

要するに：1台は単一障害点。ASG（自動管理される長屋）で2〜10戸を維持する。各戸の仕様は起動設定で定義し、create_before_destroyで置き換えの行き詰まりを防ぐ。建てる小区画はデータソースで動的に取得する。

ハル
ハル1軒のWebサーバが動きました。でも、この小屋が壊れたらサービス全滅ですよね？
棟梁
棟梁そのとおり。1台のサーバは「単一障害点」だ。故障や過負荷で誰もサイトを見られなくなる。解決策は、複数の小屋を「長屋（クラスタ）」にして、壊れた小屋を避けて客を流し、混み具合に応じて戸数を増減することだ。
ハル
ハル長屋を手で管理するの、大変そうです。
棟梁
棟梁だからAWSの「Auto Scalingグループ（ASG）」に任せる。ASGは各戸の起動、健康監視、壊れた戸の建て替え、混み具合に応じた戸数調整まで全部自動でやる。

🏗️ たとえ話

住める家が1軒だけだと、その家が火事になればおしまい（単一障害点）。そこで同じ間取りの戸をいくつも並べた「長屋」を建てる。長屋には腕利きの大家（ASG）を雇い、空き巣に入られた戸を建て替えたり、客が増えれば戸を増やし、減れば畳む、といった面倒を全部任せる。1戸が壊れても残りの戸が客を迎えられる。

1台 → 長屋への変化

⚠️

変更前: 小屋1軒

[客] → [小屋1軒]。壊れたら終わり。単一障害点。

脆い
🏘️

変更後: 長屋（ASG管理）

[客] → [ASGが管理する長屋: 2〜10戸]。1戸壊れても残りが対応、自動で建て替え。

止まらない
棟梁
棟梁ASGを作る第一歩は「起動設定」だ。aws_launch_configurationはaws_instanceとほぼ同じだが、タグは使えず、user_data_replace_on_changeも不要、2つの引数名が違う（ami→image_id、vpc_security_group_ids→security_groups）。

このコードは、長屋の各戸の共通仕様書（起動設定）です。

起動設定（各戸の共通仕様書）
# 長屋の各戸の共通仕様書（起動設定）
resource "aws_launch_configuration" "example" {
  image_id        = "ami-0fb653ca2d3203ac1"           # ① aws_instanceのamiに相当
  instance_type   = "t2.micro"
  security_groups = [aws_security_group.instance.id]      # ② vpc_security_group_idsに相当

  user_data = <<-EOF
              #!/bin/bash
              echo "Hello, World" > index.html
              nohup busybox httpd -f -p ${var.server_port} &
              EOF
}

このコードは、長屋を管理する大家（ASG）本体です。2〜10戸を維持します。

ASG本体
# 長屋を管理する大家（ASG）。2〜10戸を維持する
resource "aws_autoscaling_group" "example" {
  launch_configuration = aws_launch_configuration.example.name   # ① どの仕様書で建てるか
  min_size = 2    # ② 最低でも2戸
  max_size = 10   # ③ 最大10戸まで

  tag {
    key                 = "Name"
    value               = "terraform-asg-example"
    propagate_at_launch = true   # ④ このタグを各戸にも引き継ぐ
  }
}
ハル
ハルこれで完成じゃないんですか？
棟梁
棟梁1つ問題がある。ASGは起動設定の「名前」を参照している。起動設定はイミュータブル（変更不可）なので、仕様書を変えるとTerraformは作り替えようとする。普通は「古いものを削除→新しいものを作成」の順だが、ASGが古い仕様書をまだ参照してるので削除できず、行き詰まる。
ハル
ハルどうやって解決するんですか？
棟梁
棟梁「ライフサイクル」を使う。create_before_destroyをtrueにすると置き換えの順番が逆になり、「新しい仕様書を先に作る→古いものを削除」になって行き詰まりが解消する。

このコードは、起動設定にライフサイクル設定を足して、置き換え順を「先に作ってから壊す」にします。

create_before_destroy
# 起動設定に置き換え順「先に作ってから壊す」を足す
resource "aws_launch_configuration" "example" {
  image_id        = "ami-0fb653ca2d3203ac1"
  instance_type   = "t2.micro"
  security_groups = [aws_security_group.instance.id]
  user_data = <<-EOF
              #!/bin/bash
              echo "Hello, World" > index.html
              nohup busybox httpd -f -p ${var.server_port} &
              EOF

  # Autoscaling Groupがある起動設定を使った場合に必須
  lifecycle {
    create_before_destroy = true   # ① 先に新しいものを作ってから古いものを壊す
  }
}

データソースでサブネットを取り寄せる

棟梁
棟梁もう1つ足すパラメータがある。vpc_zone_identifierだ。長屋の各戸をどのサブネット（小区画）に建てるかをASGに指示する。各サブネットは別々のAZ（別々のデータセンタ）にあるので、複数にまたがって建てれば、いくつかのデータセンタが障害を起こしてもサービスを続けられる。
ハル
ハルサブネットの一覧を直接書けばいいんですか？
棟梁
棟梁それもできるが、メンテナンス性とポータビリティに欠ける。代わりに「データソース」を使う。これは実行のたびにAWSから取り寄せる読み取り専用の情報だ。何かを作るわけではなく、AWSのAPIに問い合わせて情報を取り、設計図で使えるようにするだけ。書き方はdata "<PROVIDER>_<TYPE>" "<NAME>" { ... }。

🏗️ たとえ話

長屋の戸をどの区画に建てるか。区画番号を1つ1つ図面に手書きすると、別の現場に図面を持っていったとき番号が合わない。そこで現場ごとに役所（AWS）の窓口へ行き「この敷地に使える区画を全部教えて」とその場で問い合わせる。これがデータソース。何も建てず、ただ最新の情報を読み取ってくるだけ。だから図面はどの現場でもそのまま使える。

このコードは、データソースの書き方の型と、デフォルトの敷地（VPC）情報を取り寄せる例です。

データソース（VPC情報を取り寄せる）
# データソースの書き方
data "<PROVIDER>_<TYPE>" "<NAME>" {
  [CONFIG ...]
}

# デフォルトの敷地（デフォルトVPC）の情報を取り寄せる
data "aws_vpc" "default" {
  default = true   # ① 「デフォルトVPCを探せ」という検索条件
}

このコードは、データソースから値を取り出す書き方の型と、取り寄せたVPCのIDを取り出す例です。

データソースから値を取り出す
# データソースから値を取り出す書き方
data.<PROVIDER>_<TYPE>.<NAME>.<ATTRIBUTE>

# 取り寄せたVPCのIDを取り出す
data.aws_vpc.default.id

このコードは、そのVPC内のサブネット（小区画）一覧を取り寄せます。

サブネット一覧を取り寄せる
# デフォルトVPCの中にある小区画（サブネット）一覧を取り寄せる
data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"                    # ① 「vpc-idで絞り込む」
    values = [data.aws_vpc.default.id]   # ② そのVPCのIDを条件にする
  }
}

このコードは、取り寄せたサブネット一覧をASGに渡し、複数のデータセンタに戸を建てさせます。

ASGにサブネットを渡す
# 取り寄せたサブネット一覧をASGに渡し、複数のデータセンタに戸を建てさせる
resource "aws_autoscaling_group" "example" {
  launch_configuration = aws_launch_configuration.example.name
  vpc_zone_identifier  = data.aws_subnets.default.ids   # ① どの小区画に建てるか
  min_size = 2
  max_size = 10

  tag {
    key                 = "Name"
    value               = "terraform-asg-example"
    propagate_at_launch = true
  }
}

💡 なぜこれが必要か

  • 1台故障してもサービスが止まらない（可用性が上がる）。
  • 混み具合に応じて戸数が自動で増減する（スケーラビリティ）。
  • データソースで環境に合わせた値を自動取得でき、ハードコードを避けられる。

📌 この項のまとめ

  • 1台のサーバは単一障害点。クラスタ（長屋）で冗長化する。
  • ASG＝起動・監視・建て替え・戸数調整を自動でやる長屋の大家。
  • 起動設定＝各戸の共通仕様書。ami→image_id、vpc_security_group_ids→security_groupsに名前が変わる。
  • 起動設定はイミュータブル。lifecycle { create_before_destroy = true }で「先に作ってから壊す」に。
  • 複数サブネット（複数AZ）に分散すればデータセンタ障害に耐える。
  • データソースは読み取り専用の情報取得。data.<種類>.<名前>.<属性>で値を使う。
2.7

ロードバランサのデプロイ

入り口に1人の門番を置く

要するに：各サーバに別々の住所があると不便なので、入り口に門番（ALB）を置き、客を健康な戸に振り分ける。ALBはリスナ・リスナルール・ターゲットグループから成る。ASGと連携させ、健康診断をELB方式にすると、不調な戸を自動で建て替えられる。

ハル
ハル長屋はできました。でも各戸にそれぞれ住所（IP）がありますよね。お客さんに「どの戸に行けばいい」って伝えればいいんですか？
棟梁
棟梁そこが問題だ。エンドユーザには1つの入り口だけ知らせたい。解決策は、客を各戸に振り分ける「ロードバランサ（門番）」を置き、ユーザにはその門番の住所（DNS名）だけアクセスさせること。これもAWSがやってくれる。ELBというサービスだ。
ハル
ハル門番にも種類があるんですか？
棟梁
棟梁3種類ある。今回のWebサーバは特別な性能要件のないHTTPアプリなので、ALBが最適だ。

🏗️ たとえ話

長屋の各戸にバラバラの住所を客に教えるのは不親切だし、戸は増えたり減ったりする。そこで長屋の入り口に1人の門番（ロードバランサ）を立たせる。客は門番の場所だけ覚えればよく、門番が「今いちばん空いている健康な戸」へ案内する。具合の悪い戸には客を通さない。門番自身も複数人で交代制（複数台）なので、1人が休んでも入り口が閉まることはない。

3種類のロードバランサ

ALBの部品の流れ

①

リスナ（受付窓口）

特定のポート（例: 80）とプロトコル（例: HTTP）で客を待ち受ける。

②

リスナルール（振り分け規則）

来た客のパス（/fooなど）やホスト名を見て、合えば指定のターゲットグループに送る。

③

ターゲットグループ（受け取るサーバ群）

門番から客を受け取るサーバの集まり。健康診断を行い、合格したサーバだけに客を送る。

このコードは、門番本体（ALB）を作ります。

ALB本体
# 門番本体（ALB）を作る
resource "aws_lb" "example" {
  name               = "terraform-asg-example"
  load_balancer_type = "application"                  # ① 種類はアプリケーション(ALB)
  subnets            = data.aws_subnet_ids.default.ids # ② どの小区画で動くか
}
棟梁
棟梁subnetsはデフォルトVPCの全サブネットを使う。AWSの門番は1台でなく、別々のサブネット（別々のデータセンタ）で動く複数台で構成される。トラフィックに応じて台数を増減し、1台ダウンしてもフェイルオーバする。だから難しい設定なしにスケーラビリティと高可用性が手に入る（本番ではEC2はプライベート、ALBはパブリックに分けることが多い）。

このコードは、門番の受付窓口（リスナ）です。ポート80でHTTPを待ち受けます。

リスナ（受付窓口）
# 門番の受付窓口（リスナ）。ポート80でHTTPを待ち受ける
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.example.arn   # ① どの門番の窓口か
  port              = 80                   # ② 待ち受けるポート
  protocol          = "HTTP"               # ③ 待ち受けるプロトコル

  # デフォルトではシンプルな404ページを返す
  default_action {
    type = "fixed-response"
    fixed_response {
      content_type = "text/plain"
      message_body = "404: page not found"
      status_code  = 404
    }
  }
}
棟梁
棟梁この窓口はポート80でHTTPを待ち受け、どのルールにも合わない客には素っ気ない404を返す。ところでALBもデフォルトでは出入りを許さないので、門番用の門（セキュリティグループ）が要る。

このコードは、門番(ALB)用の門です。客からのポート80を受け、健康診断のため全ポートへ出ていけます。

ALB用のセキュリティグループ（門）
# 門番(ALB)用の門。客からのポート80を受け、健康診断のため全ポートへ出ていける
resource "aws_security_group" "alb" {
  name = "terraform-example-alb"

  # インバウンドHTTPリクエストを許可
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]   # ① どのIPからのポート80も許可
  }

  # アウトバウンドリクエストをすべて許可
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"            # ② -1 はすべてのプロトコルの意味
    cidr_blocks = ["0.0.0.0/0"]   # ③ どこへでも出ていける（健康診断のため）
  }
}
ハル
ハルegressって何ですか？さっきはingressでしたよね。
棟梁
棟梁ingressが「内向き」ならegressは「外向き」だ。門番は各戸に健康診断のリクエストを送る必要があるので、全ポートへ出ていける許可を与える。この門をALBに取り付ける。

このコードは、作った門を門番(ALB)に取り付けます。

門をALBに取り付ける
# 作った門を門番(ALB)に取り付ける
resource "aws_lb" "example" {
  name               = "terraform-asg-example"
  load_balancer_type = "application"
  subnets            = data.aws_subnets.default.ids
  security_groups    = [aws_security_group.alb.id]   # ① ALB用の門を取り付ける
}

このコードは、客を受け取るサーバ群(ターゲットグループ)と、その健康診断ルールです。

ターゲットグループ（受け取るサーバ群＋健康診断）
# 客を受け取るサーバ群(ターゲットグループ)と、その健康診断ルール
resource "aws_lb_target_group" "asg" {
  name     = "terraform-asg-example"
  port     = var.server_port            # ① 戸に送るポート（変数で指定）
  protocol = "HTTP"
  vpc_id   = data.aws_vpc.default.id     # ② どの敷地のサーバか

  health_check {
    path                = "/"      # ③ 「/」に診断リクエストを送る
    protocol            = "HTTP"
    matcher             = "200"    # ④ 200が返れば健康とみなす
    interval            = 15       # ⑤ 15秒ごとに診断
    timeout             = 3        # ⑥ 3秒以内に返事がなければ失敗
    healthy_threshold   = 2        # ⑦ 2回連続成功で「健康」
    unhealthy_threshold = 2        # ⑧ 2回連続失敗で「不調」
  }
}
棟梁
棟梁このターゲットグループは、定期的に各戸へHTTPリクエストを送り、matcher（200 OK）に合う戸だけhealthyとみなす。返事がおかしい戸はunhealthyとされ、自動で客を送らなくなる。
ハル
ハル門番は、どの戸に客を送ればいいって、どうやって知るんですか？長屋の戸は増えたり減ったりしますよね。
棟梁
棟梁いい質問だ。aws_lb_target_group_attachmentで静的リストを貼ることもできるが、ASGの戸はいつでも増減するので静的リストではダメだ。代わりにASGとALBの連携を使う。ASGに戻ってtarget_group_arnsでターゲットグループを指定する。

このコードは、ASGの戸を自動的にターゲットグループに登録させる連携設定です。

ASGとALBの連携
# ASGの戸を、自動的にターゲットグループに登録させる連携設定
resource "aws_autoscaling_group" "example" {
  launch_configuration = aws_launch_configuration.example.name
  vpc_zone_identifier  = data.aws_subnets.default.ids

  target_group_arns = [aws_lb_target_group.asg.arn]   # ① 戸を自動でこの群に登録
  health_check_type = "ELB"                          # ② 健康診断はELB方式を使う

  min_size = 2
  max_size = 10

  tag {
    key                 = "Name"
    value               = "terraform-asg-example"
    propagate_at_launch = true
  }
}
ハル
ハルhealth_check_type = "ELB"って何ですか？
棟梁
棟梁健康診断のやり方の指定だ。デフォルトのEC2は最小限で、「VMがダウンか疎通不能」のときだけ不調とみなす。ELBに変えると、ターゲットグループの診断結果を使い、不調な戸を自動で建て替えるよう大家(ASG)に指示する。「動いてはいるが返事ができない」戸も建て替えられる。

このコードは、振り分け規則(リスナルール)です。来た客をすべてターゲットグループに転送します。

リスナルール（振り分け規則）
# 振り分け規則(リスナルール)。来た客をすべてターゲットグループに転送する
resource "aws_lb_listener_rule" "asg" {
  listener_arn = aws_lb_listener.http.arn   # ① どの受付窓口の規則か
  priority     = 100                       # ② 規則の優先順位

  condition {
    path_pattern {
      values = ["*"]   # ③ どんなパスでも合致（すべて受ける）
    }
  }
  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.asg.arn   # ④ ターゲットグループへ転送
  }
}

このコードは、表示する出力を、個別サーバのIPではなく門番のDNS名に置き換えます。

出力をALBのDNS名に
# 表示するのは個別サーバのIPではなく、門番のDNS名にする
output "alb_dns_name" {
  value       = aws_lb.example.dns_name   # ① 門番の入り口アドレス
  description = "ロードバランサのドメイン名"
}

このコードは、applyが完了すると門番の入り口アドレスが表示される様子と、そのアドレスを叩いた結果です。

apply後の出力と動作確認
# applyが完了すると門番の入り口アドレスが表示される
Outputs:

# 門番のアドレスを叩くと、長屋のどれかの戸が応答する
$ curl http://<alb_dns_name>
Hello, World
棟梁
棟梁戸が起動してALBに健康と認識されるまで数分かかる。管理画面で2戸起動・ALB・ターゲットグループが見え、両方の戸がHealthyになるのを待つ（通常1〜2分）。
ハル
ハル「Hello, World」が出ました！しかも棟梁、アクセスするたびに違う戸が応答してるんですか？
棟梁
棟梁そうだ。ALBが客を順に振り分けている。試しに1戸を「終了」させても、ALBのURLは200 OKを返し続ける。ALBが故障を検知してその戸への振り分けを止めるからだ。さらに戸が減ったのをASGが検知して新しい戸を建て直す（自己回復）。desired_capacity（希望戸数）を足してapplyすればサイズも変えられる。

💡 なぜこれが必要か

  • ユーザに知らせる入り口を1つにできる。
  • 故障した戸を自動で避け、自動で建て替えるので、止まらないサービスになる。
  • 客を均等に振り分け、混雑に強くなる。

📌 この項のまとめ

  • ロードバランサ＝客を複数サーバに振り分ける門番。AWSではELBサービス。
  • 3種類: ALB（HTTP/HTTPS・L7）、NLB（TCP/UDP/TLS・L4・超高速）、CLB（旧型）。HTTPアプリにはALB。
  • ALBの部品: リスナ（受付窓口）・リスナルール（振り分け規則）・ターゲットグループ（受け取るサーバ群＋健康診断）。
  • ALB用のセキュリティグループはingressでポート80、egressで全ポート（健康診断用）を許可。
  • ASGのtarget_group_arnsで戸を自動登録、health_check_type = "ELB"で診断結果に基づき建て替え。
  • リスナルールで条件に合う客をターゲットグループへforward。出力はALBのDNS名にする。

章末の理解度チェック

自分の言葉で答えてみよう（全5問）
第1問init・plan・applyの役割

Terraformで設計図を実行するとき使うinit・plan・applyの3つは、それぞれ何をするコマンドですか。

✅ 解答例を見る
initは作業フォルダを準備するコマンドで、設計図を読んで必要なプロバイダ（AWSなど）のコードを取り寄せる。新しく始めるときに使い、何度実行しても結果は同じ。planは「この設計図を適用すると何が起きるか」を実際に変える前に予習で見せる。applyは本当に変更を実行する。実行前に同じ差分を見せてyesの確認を求める。
📝 採点ポイント
・init＝準備・プロバイダのコード取り寄せ、と説明できている
・plan＝変更前の予習・差分の表示、と説明できている
・apply＝実際に変更を実行・確認を求める、と説明できている
第2問変数を使う理由（DRY原則）

ポート番号などの値を入力変数にまとめるのはなぜですか。まとめないとどんな問題が起きますか。

✅ 解答例を見る
同じ値を複数の場所に直接書くと、片方だけ直してもう片方を直し忘れる事故が起きるから。これはDRY原則（同じ情報を繰り返さない）に反する。入力変数で1か所にまとめれば、変えるときも1か所だけ直せばよく、矛盾やミスを防げる。型制約を付ければ間違った種類の値も実行前に弾ける。
📝 採点ポイント
・値の重複が直し忘れ・矛盾を生むと説明できている
・DRY原則（繰り返さない）に触れている
・1か所で管理できる利点を述べている
第3問単一障害点とASG・ALB

サーバ1台だけで運用する危険性と、それをASGとALBでどう解決するかを説明してください。

✅ 解答例を見る
サーバ1台は単一障害点で、それが故障したり過負荷になると、サービス全体が止まってしまう。ASG（Auto Scalingグループ）を使えば複数のサーバを長屋のように束ねて自動管理し、壊れた戸を自動で建て替え、混み具合に応じて戸数を増減できる。ALB（ロードバランサ）を入り口に置けば、ユーザは1つのアドレスにアクセスするだけでよく、ALBが健康なサーバだけに客を振り分ける。
📝 採点ポイント
・1台＝単一障害点で全体が止まるリスクを説明できている
・ASGが冗長化・自動建て替え・戸数調整をする点に触れている
・ALBが入り口を1つにし、健康なサーバに振り分ける点に触れている
第4問データソースとは何か

Terraformの「データソース」とは何ですか。リソースとの違いも含めて説明してください。

✅ 解答例を見る
データソースは、実行のたびにプロバイダ（AWSなど）から取り寄せる読み取り専用の情報のこと。dataブロックで書く。リソースが建物を「作る」のに対し、データソースは何も作らず、既存の情報（VPCのIDやサブネット一覧など）を取得して設計図の中で使えるようにするだけ。これを使うと、サブネット一覧などを直接書かずに環境に合わせて自動取得でき、メンテナンスしやすくなる。
📝 採点ポイント
・読み取り専用の情報取得であると説明できている
・リソース（作成する）との違いに触れている
・ハードコードを避けられる利点に触れている
第5問destroyとコードの関係

terraform destroyで全部のリソースを消しても、設計図（コード）を残しておけば困らないのはなぜですか。

✅ 解答例を見る
Infrastructure as Code（インフラをコードとして管理すること）の考え方のおかげで、すべてのインフラの情報が設計図に書かれているから。リソースをdestroyで消しても、terraform applyを実行すれば設計図どおりに全部再現できる。だから練習で課金を止めたいときは安心してdestroyしてよく、コードさえ残してGitにコミットしておけば、いつでも同じ環境を作り直せる。
📝 採点ポイント
・コードにすべての情報が書かれている点を説明できている
・applyで再現できる点に触れている
・IaCの利点として述べられている
