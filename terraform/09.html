9.1

手動テスト（自分の目と手で行う検査）検査員が現場に行って、自分の手でドアを開けて確かめる

要するに：手動テストとは、検査員が現場に行って自分の目と手で「ちゃんと動くか」を確かめること。ふつうのプログラムなら自分の機械の中で動かして確認できる。

ハル
弟子・ハルテストって何ですか？ よく聞くけどピンと来ません。
棟梁
師匠・棟梁工房でいえば「検査（inspection）」だ。建物を建てたら、人が住む前に「安全に建ったか」「水道は出るか」「ドアは開くか」を確かめるだろう。あれと同じ。手動テストは、検査員が自分の足で現場に行き、自分の目で見て、手でドアを開けて確かめる検査だ。

↓ まず「ふつうのプログラム」（Rubyの小さなWebサーバ）の例。どのドアを叩かれたらどう返事するかを決めた応対マニュアル。読まなくてOK。

応対マニュアル（WebServer）と、手元で動かして curl で叩く例を見る
# どのドアを叩かれたら、どう返事するかを決めた応対マニュアル
class WebServer < WEBrick::HTTPServlet::AbstractServlet
  def do_GET(request, response)
    case request.path
    when "/"      # ① 玄関には 200(成功)+「Hello, World」
      response.status = 200; response.body = 'Hello, World'
    when "/api"   # ② 裏口には 201 + JSON
      response.status = 201; response.body = '{"foo":"bar"}'
    else           # ③ それ以外は 404(見つかりません)
      response.status = 404; response.body = 'Not Found'
    end
  end
end

# 自分の機械の中(localhost)で動かして curl で叩けば手で確認できる
$ ruby web-server.rb        # 8000番で待機開始
$ curl localhost:8000/
Hello, World

✅ この項のまとめ（なぜ必要か含む）

  • 手動テスト＝検査員が現場で自分の目と手で確かめること。
  • ふつうのプログラムは自分の機械の中（ローカルホスト）で動かして叩けば確認できる。
  • まず「人が手で確かめる」基本を知ると、自動検査が何を自動化しているのか腑に落ちる。
9.1.1

手動テストの基礎（Terraformでは現場でしか検査できない）

要するに：Terraformの手動検査は「本物の土地に建てて、適切な道具で叩いて確かめる」しかない。確認の道具は建てる物（受付ロビー・データベース・VPN等）によって変わる。

ハル
弟子・ハルじゃあTerraformも、自分の機械の中で動かして検査すれば？
棟梁
師匠・棟梁そこが大きな落とし穴。受付ロビー（ALB）のような建物は、自分のパソコンの中には建たない。本物のAWSという土地の上にしか建たないんだ。

⚠️ 検査に関する重要事項 その1

Terraformコードを検査するとき、自分の機械（ローカルホスト）は使えない。唯一の現実的な方法は、本物の土地（AWSなど）に実際に建ててみること。あなたが手で打っていた terraform apply／terraform destroy こそが、手で建てて手で壊す「手動検査」だった。

↓ examplesフォルダの「お試しサンプル」を本物の土地に建て、住所をcurlで叩いて404が返るか確かめる流れ。読まなくてOK。

サンプルを apply して curl で叩く手動検査を見る
# alb モジュールをお試しで一棟建てるサンプル設計図
module "alb" {
  source     = "../../modules/networking/alb"
  alb_name   = "terraform-up-and-running"
  subnet_ids = data.aws_subnets.default.ids
}

# 建てると受付ロビーが5つの建材で完成し、住所(DNS名)が出る
$ terraform apply
Apply complete! Resources: 5 added, 0 changed, 0 destroyed.
Outputs:
alb_dns_name = "hello-world-stage-477699288.us-east-2.elb.amazonaws.com"

# 住所を叩き、どのドアにも当たらない来訪者が「404」を返すか確認
$ curl -s -o /dev/null -w "%{http_code}" hello-world-stage-...elb.amazonaws.com
404

🏗️ たとえ話：模型では耐震は測れない

受付ロビーは机の上の模型では検査できません。本物の土地に実際に建ててこそ、地震に耐えるか・ドアが開くかを確かめられます。しかも確認の道具は対象しだい――受付ロビー（HTTP）ならcurl、データベースならMySQLクライアント、VPNならVPNクライアント、何も受けないサーバならSSHでログインして中で確かめる、と変わります。

✅ この項のまとめ

  • 重要事項その1：Terraformの検査にローカルホストは使えない。本物の土地に建てるしかない。
  • 手動検査＝サンプルをterraform applyで建て、適切な道具で叩いて確認し、terraform destroyで壊す。
  • 確認の道具（curl/MySQLクライアント/SSH等）は対象によって変える。
  • 開発者には他環境から完全に分離したサンドボックス環境を持たせる。衝突を防ぐため開発者ごとに別アカウントが理想（AWSはアカウント追加に費用がかからず、Organizationsで請求をまとめられる）。
9.1.2

テスト後の後片付け（建てた仮設物を放置しない）

要するに：検査のために建てた仮設物は放置すると土地代（コスト）が膨らむ。terraform destroyで片付ける文化を作り、cloud-nuke 等で古い物を自動で取り壊す。

棟梁
師匠・棟梁検査のために建てたものを放置するとどうなる？
ハル
弟子・ハル砂場のあちこちに建てっぱなしの仮設小屋が散らかって……土地代がどんどんかかる！
棟梁
師匠・棟梁そうだ。壊し忘れにも備えて、自動の掃除屋を雇うといい。cloud-nuke や aws-nuke が、古くなった建材を自動で取り壊してくれる。

⚠️ 検査に関する重要事項 その2

サンドボックス環境を定期的に片付けよう。最低限、検査後にterraform destroyする文化を作る。

cloud-nuke で48時間より古い仮設物を取り壊す例を見る
# 48時間より古いリソースを取り壊す(検査用の仮設物はもう不要だろう、という推測)
$ cloud-nuke aws --older-than 48h

✅ この項のまとめ

  • 重要事項その2：サンドボックスを定期的に片付ける。
  • terraform destroyを習慣にする。
  • cloud-nuke / aws-nuke を cron（定期実行）で回し、古い建材を自動取り壊し。
  • （本の警告）ここから先は本書で最も難しい部分。本気で学ぶならGoのコードを書いて動かす覚悟を。Rubyのコードは頭の整理用なので動かさなくてよい。
9.2

自動テスト（自動でくり返せる検査機）検査手順をコードにして、機械にくり返させる

要するに：自動テストは検査手順をコード化してくり返せるようにすること。ユニット（部品単体）・統合（組み合わせ）・E2E（端から端まで）の3種類があり、見つかる不具合が違うので組み合わせて使う。

🚪

ユニットテスト

建材1個・部屋1個を単独で検査（「このドアは単体で開閉するか」）。外の依存先はモック（模型）に差し替える。

🚰

統合テスト

複数の設備を組み合わせて協調するか検査（「キッチンと水道管を繋いで本当に水が出るか」）。本物と模型を混ぜる。

🏠

E2Eテスト

建物・設備すべてをそろえ、住人目線で端から端まで使う検査。本番そっくりの建物で本物だけを使う。

🏗️ たとえ話：3つの別々の保険

ドア単体が無事でも、組み合わせると不具合が出ることがある（だから統合検査）。各部屋が無事でも、実際に住むと問題が出ることがある（だからE2E検査）。3種は見つかる不具合が違う、別々の保険なので組み合わせて使います。

✅ この項のまとめ

  • ユニットテスト：1つの単位（Terraformでは1モジュール）を単独で検査。依存先はモックに差し替え。
  • 統合テスト：複数の単位を組み合わせて検査。本物とモックを混ぜる。
  • E2Eテスト：本番そっくりの全体を、住人目線で本物だけで検査。
  • 3種は別々の不具合を見つけるので組み合わせる。
9.2.1

ユニットテスト（部品1個の検査）

要するに：ユニットテストは部品単体を高速で検査すること。検査しやすくするには「入力も出力もシンプルな独立部品」に切り出すのがコツ。

棟梁
師匠・棟梁さっきの応対マニュアルは、検査しようとすると訪問者役・返事役・サーバ役を全部用意せねばならず面倒だった。検査が書きにくいときは「コードが臭う（直すべきサイン）」と言う。応対の判断だけを取り出して、ドア名を渡すと状態・形式・本文を返すだけの独立部品Handlersにすると、検査がとても簡単になる。
独立部品 Handlers と、それを直接叩くユニットテストを見る
# 入力(ドア名)も出力(素直な値)もシンプルな独立部品 → 検査しやすい
class Handlers
  def handle(path)
    case path
    when "/"    then [200, 'text/plain', 'Hello, World']
    when "/api" then [201, 'application/json', '{"foo":"bar"}']
    else            [404, 'text/plain', 'Not Found']
    end
  end
end

# 検査:ドア名を渡して返事が正しいか確かめるだけ
def test_unit_hello
  status, type, body = @handlers.handle("/")
  assert_equal(200, status); assert_equal('Hello, World', body)
end

# 実行すると3件全部合格、所要0.0006秒(一瞬！)
$ ruby web-server-test.rb
3 tests, 9 assertions, 0 failures, 0 errors / 100% passed

✅ この項のまとめ

  • ユニットテスト＝1つの単位を単独で検査する。
  • 検査しにくい＝設計のにおい（直すべき合図）。
  • シンプルな入力・出力の部品にすると検査しやすい。
  • ユニットテストは超高速（0.0006秒）で自信を与えてくれる。
9.2.1.1

Terraformコードのユニットテスト（受付ロビーの耐震試験）

要するに：Terraformのユニットテストは、1モジュールを本物の土地に建てて叩いて確かめ、必ず取り壊す検査。Terratest（Go）で apply→確認→destroy を自動化する。

ハル
弟子・ハルTerraformの「単位」は何ですか？ Rubyみたいに依存先を全部模型にすれば？
棟梁
師匠・棟梁「単位」は8章で作ったalbのような再利用モジュール。だがTerraformコードは99%が「AWSに建ててもらう注文」。注文先を全部模型にしたら検査するコードがほとんど残らないし、本当に建つ自信にもならない。

⚠️ 検査に関する重要事項 その3

Terraformコードに純粋なユニットテストはできない。本物の土地に建てる以上、実態は統合テスト。だが「できるだけ早くフィードバックを得るため1モジュールだけ検査する」狙いから、あえてユニットテストと呼ぶ。（LocalStack等の模型業者で一部は差し替え可能だが、全部模型化は非現実的。）

1

小さく独立したモジュールを作る

2

建てやすいサンプルを作る

3

terraform apply で本物の土地に建てる

4

建てた物が期待どおり動くか確認（ALBならHTTPで叩く）

5

terraform destroy で片付ける

これは手動検査とまったく同じ手順をコードにしただけ。検査コードはGoで書き、Terratestを使う。↓ albの検査コード。読まなくてOK。

alb_example_test.go（Terratestでの apply→確認→destroy）を見る
func TestAlbExample(t *testing.T) {
    opts := &terraform.Options{
        TerraformDir: "../examples/alb",   # 検査する設計図の場所
    }

    # ★ destroy を apply より前に「予約」する(理由は下の吹き出し)
    defer terraform.Destroy(t, opts)

    terraform.InitAndApply(t, opts)            # init+apply=建てる

    # 受付ロビーの住所を取り出してURLを組み立てる
    albDnsName := terraform.OutputRequired(t, opts, "alb_dns_name")
    url := fmt.Sprintf("http://%s", albDnsName)

    # 何も当てはまらないドアが「404」を返すか、最大10回・10秒間隔で叩き直して確認
    http_helper.HttpGetWithRetry(t, url, nil, 404,
        "404: page not found", 10, 10*time.Second)
}

# 実行(打ち切り防止に -timeout 30m)。約5分で完了
$ go test -v -timeout 30m
Apply complete! ... Destroy complete! ... PASS  (229s)
ハル
弟子・ハルなぜdefer terraform.Destroyが一番上に？ 片付けは最後では？ あとmaxRetriesって何で何回も叩くんですか？
棟梁
師匠・棟梁片付けを最後の行に書くと、手前で検査が失敗したとき片付けにたどり着けず、建てた物が放置される。deferは「どう終わっても必ず実行」する予約だから、建てるより先に「終わったら必ず取り壊して」と予約しておくんだ。リトライは、建物はapply直後すぐ使えるとは限らない（電気が通り住所が広まるまで時間がかかる）から、うまくいくまで叩き直すのが最適なんだ。
ハル
弟子・ハル-timeout 30mは？
棟梁
師匠・棟梁Goは標準だと10分で検査を打ち切る。打ち切られると片付けコードも動かず放置される。本物のインフラ検査では長めに（30分など）設定して打ち切りを防ぐんだ。検査は必ず分離した専用の土地（アカウント）で。

🏗️ たとえ話：先に「解体予約」を入れてから建てる

検査用の仮設展示場は、建てる前に「検査が済んだら、結果がどうあれ必ず解体してください」と解体業者に予約を入れます（defer）。途中で耐震試験に落ちても、予約済みなので確実に解体されます。建物は完成直後すぐ入れるとは限らないので、検査員は「使えるようになるまで」何度もドアを叩き直します（リトライ）。

✅ この項のまとめ

  • 重要事項その3：Terraformに純粋なユニットテストはできない（実態は統合テスト）。
  • 手順：小モジュール→サンプル→apply→確認→destroy。
  • TerratestのInitAndApply／OutputRequired／HttpGetWithRetry／Destroyを使う。
  • defer terraform.Destroyをapplyの前に置き、失敗しても必ず片付ける。
  • リトライは「立ち上がりに時間がかかる」ため必須。-timeout 30mで打ち切りを防ぐ。検査は専用アカウントで。
9.2.1.2

依存性の注入（外の業者を差し替えられるようにする）

要するに：依存性の注入とは、外部依存をコードに直書きせず入力変数で外から差し込めるようにすること。検査では模型を注入し、外部依存を最小化して身軽に検査する。

📌 外部業者に頼った検査の4つの困りごと

  • 業者が休業すると、こちらに問題が無くても検査が失敗する。
  • 業者が返事を変えると検査も失敗し、実装が正しくても直し続ける羽目に。
  • 業者が遅いと検査も遅くなり、ユニットテストの高速さが消える。
  • 業者の挙動に依存する細かい場合（エッジケース）を試したくても、業者を操れない。

↓ Rubyの例：外部業者を別部品に切り出し、応対係に「外から差し込む」。本番は本物、検査では模型を差し込む。読まなくてOK。

依存性の注入（Ruby）と模型業者を見る
# 応対係は業者部品を外から受け取って使う(直書きしない)
class Handlers
  def initialize(web_service)
    @web_service = web_service        # 外から渡された業者を覚える
  end
  def handle(path)
    when "/web-service" then @web_service.proxy  # 渡された業者に中継
  end
end

# 検査用の模型業者:いつも決まった返事を返すだけの偽物
class MockWebService
  def proxy; @response; end
end
# → 模型を差し込めば、外部業者が休業中でも検査できる
棟梁
師匠・棟梁Terraformでの「注入口」は何だと思う？
ハル
弟子・ハル……入力変数（variable）ですか？
棟梁
師匠・棟梁正解だ。まず外部依存をdependencies.tfに集めて一目で分かるようにし、各依存にdefault = nullの入力変数を足す。指定しなければデータソースで自動取得、指定すれば模型を差し込める。mysql_configをmysqlモジュールの出力と同じ型にそろえれば、mysql_config = module.mysqlと1行で注入でき、型がずれればTerraformが即エラーで教えてくれる（型安全な合成）。
入力変数化 ＋ count とローカル変数での切り替えを見る
# 外から差し込める入力変数(未指定なら null)
variable "mysql_config" {
  type = object({ address = string, port = number })  # mysqlの出力と同じ型
  default = null
}

# 未指定(null)のときだけ、対応するデータソースを1個作る
data "terraform_remote_state" "db" {
  count = var.mysql_config == null ? 1 : 0   # 未指定→1個、指定済み→0個
}

# 未指定ならデータソース、指定済みなら入力を採用(count付きは配列なので[0])
locals {
  mysql_config = var.mysql_config == null
    ? data.terraform_remote_state.db[0].outputs
    : var.mysql_config
}

↓ 検査側はVarsで模型を注入し、「状態200で本文にHello, Worldを含む」を判定する。読まなくてOK。

hello-world-app の検査コード（模型注入＋含む判定）を見る
func TestHelloWorldAppExample(t *testing.T) {
    opts := &terraform.Options{
        TerraformDir: "../examples/hello-world-app/standalone",
        Vars: map[string]interface{}{          # 変数を検査側から設定
            "mysql_config": map[string]interface{}{
                "address": "mock-value-for-test",   # 模型の住所
                "port":    3306,
            },
        },
    }
    defer terraform.Destroy(t, opts)
    terraform.InitAndApply(t, opts)
    # 完全一致でなく「含む」で判定(HTMLの中に挨拶が埋まっているため)
    http_helper.HttpGetWithRetryWithCustomValidation(t, url, nil, 10,
        10*time.Second, func(status int, body string) bool {
            return status == 200 && strings.Contains(body, "Hello, World")
        })
}

🏗️ たとえ話：水道を仮設タンクに切り替える

キッチン（アプリ）を検査するのに本物の水道局（データベース）に繋ぐと、断水したら検査できません。だから水道の口を「外から差し込める接続口（入力変数）」にしておき、検査では決まった水を出す仮設タンク（模型）を繋ぎます。接続口の形（型）を本物とそろえておけば、本物の水道もそのまま1本で繋げ、形が合わなければすぐ分かります。

✅ この項のまとめ

  • 依存性の注入＝依存を外から差し込めるようにする設計。
  • 外部依存はdependencies.tfに集約。
  • 各依存にdefault = nullの入力変数を足し、countとローカル変数で「注入 or データソース」を切り替える。
  • countを付けたデータソースは配列になるので[0]で参照。
  • 検査ではVarsで模型を注入し、HttpGetWithRetryWithCustomValidationで「含む」判定。
9.2.1.3

テストを並列に実行する（複数の検査員を同時に走らせる）

要するに：検査を速くするには t.Parallel() で並列実行する。ただし名前がぶつかるので、random.UniqueId() で各リソースに一意な名前空間を与える。

棟梁
師匠・棟梁Goは標準だと検査を一列（直列）に走らせる。各検査の先頭にt.Parallel()を書けば並列になる。だが落とし穴がある。両方の検査がALBやセキュリティグループを同じ名前で建てようとすると、名前がぶつかって失敗するんだ。
ハル
弟子・ハル同じ住所表示の建物を2つ建てようとして喧嘩する感じですね。

⚠️ 検査に関する重要事項 その4

あらゆるリソースに名前空間を持たせよう。名前空間＝各リソースの名前を自由に設定できるよう設計すること。名前を入力変数化し、検査ではrandom.UniqueId()でぶつからない名前をランダムに付ける。

名前を変数化し random.UniqueId() で衝突回避する例を見る
# モジュール側:ALBの名前を外から設定できるようにする
variable "alb_name" { type = string; default = "terraform-up-and-running" }

# 検査側:test- のあとにランダムな一意IDを付け、衝突を避ける
func TestAlbExample(t *testing.T) {
    t.Parallel()                            # この検査を並列対象に
    opts := &terraform.Options{
        TerraformDir: "../examples/alb",
        Vars: map[string]interface{}{
            "alb_name": fmt.Sprintf("test-%s", random.UniqueId()),
        },
    }
}

# 両方同時に走り、全体時間は「合計」でなく「一番遅い検査ぶん」に近づく
$ go test -v -timeout 30m         # 216s で両方完了
$ go test -v -timeout 30m -parallel 2   # 同時実行数を2に指定
ハル
弟子・ハルrandom.UniqueId()って？
棟梁
師匠・棟梁ランダムな6文字を返す係。短いから名前の文字数制限に引っかかりにくく、62の6乗＝560億通り以上あるからまず衝突しない。並列数は標準だとCPU数。-parallelやGOMAXPROCSで変えられる。なお同じフォルダに対して同時に走らせると.terraformや状態ファイルを上書きしあって失敗するから、test_structure.CopyTerraformFolderToTempで各検査を別の一時フォルダにコピーして回避する。

✅ この項のまとめ

  • 各検査の先頭にt.Parallel()で並列化。
  • 重要事項その4：あらゆるリソースに名前空間を。
  • random.UniqueId()（6文字・560億通り超）で一意な名前を付ける。
  • 並列数はCPU数が既定。-parallel／GOMAXPROCSで変更可。
  • 同じフォルダの並列はCopyTerraformFolderToTempで一時フォルダにコピーして回避。
9.2.2

統合テスト（複数の設備を組み合わせた検査）

要するに：統合テストは複数モジュール（本物のmysqlとアプリ）を組み合わせて建て、協調して動くか確かめる検査。ユニットテストより遅い。状態ファイルは部分設定で検査用に切り替える。

棟梁
師匠・棟梁Rubyの統合テストは、応対係を本物のサーバとして自分の機械で立て、HTTPで叩く（ユニットの0.0006秒が0.22秒に＝約387倍遅い）。大事なのは絶対値でなく傾向――統合はユニットより遅い。Terraformでは、前は模型にしたMySQLを今度は本物建て、アプリと組み合わせる。
ハル
弟子・ハル状態ファイルの保存先が直書きですけど、検査で上書きしたら本物のステージングが壊れません？
棟梁
師匠・棟梁鋭い。だから3.3で出た部分設定を使う。backend設定をbackend.hclに切り出し、本番は-backend-config=backend.hcl、検査はTerratestのBackendConfigで渡す。keyにuniqueIdを入れれば検査ごとに別の保存場所になり、本物の状態を壊さない。
統合テストの骨組み（mysql→アプリ→確認→片付け）と部分設定を見る
func TestHelloWorldAppStage(t *testing.T) {
    t.Parallel()
    # ① MySQLを建てる(最後に取り壊す予約)
    dbOpts := createDbOpts(t, dbDirStage)
    defer terraform.Destroy(t, dbOpts)
    terraform.InitAndApply(t, dbOpts)
    # ② アプリを建てる(最後に取り壊す予約)
    helloOpts := createHelloOpts(dbOpts, appDirStage)
    defer terraform.Destroy(t, helloOpts)
    terraform.InitAndApply(t, helloOpts)
    # ③ アプリが動くか確認
    validateHelloApp(t, helloOpts)
}

# 検査用の保存先を渡す(key に uniqueId が入るので検査ごとに別の場所)
BackendConfig: map[string]interface{}{
    "bucket": bucketForTesting, "key": dbStateKey, "encrypt": true,
}

# アプリには mysql と同じ保存先を渡し、状態を読ませる
$ go test -v -timeout 30m -run "TestHelloWorldAppStage"
PASS (795s ≒ 13分。ユニットより倍以上)

🏗️ たとえ話：キッチンと水道を本物で繋ぐ

ユニット検査では仮設タンクで済ませたキッチン検査を、今度は本物の水道管（MySQL）に繋いで「本当に水が出るか」を確かめます。ただし検査用の水道メーターは本番のメーター（状態ファイル）と別にしておかないと、本番の検針記録を壊してしまう――だから検査専用の別メーター（部分設定）を使います。本物を繋ぐぶん、検査は時間がかかります。

✅ この項のまとめ

  • 統合テスト＝複数モジュールを組み合わせて検査。ユニットテストより遅い。
  • ハードコードした値（db_name等）は入力変数化。
  • backendはbackend.hclに切り出し、本番は-backend-config、検査はBackendConfigで渡す。
  • keyにuniqueIdを入れて検査ごとに保存先を分離。
  • アプリにはmysqlと同じ保存先を渡し、状態を読ませる。
9.2.2.1

テストステージ（検査を段階に分けて飛ばせるようにする）

要するに：テストステージは検査を名前付きの段階に分け、SKIP_<名前>=true で不要な段階を飛ばす仕組み。開発中の内側ループを爆速にする。

棟梁
師匠・棟梁統合テストは5段階だ――①mysqlをapply ②アプリをapply ③確認 ④アプリをdestroy ⑤mysqlをdestroy。CIでは毎回全部やりたいが、開発中アプリだけ直すのに毎回mysqlを建て壊すのは無駄だろう？ 理想は、最初に両方建てたら、あとはアプリだけ直す→apply→確認の内側ループをぐるぐる回し、OKになったら最後に両方壊す。

↓ Terratestのtest_structureで各段階を名前付き関数に包み、データはディスクに保存（別プロセスでも引き継げる）。SKIP_foo=trueでfoo段階を飛ばす。読まなくてOK。

テストステージのコードと SKIP の使い方を見る
func TestHelloWorldAppStageWithStages(t *testing.T) {
    stage := test_structure.RunTestStage
    defer stage(t, "teardown_db",  func() { teardownDb(t, dbDirStage) })
    stage(t, "deploy_db",        func() { deployDb(t, dbDirStage) })
    defer stage(t, "teardown_app", func() { teardownApp(t, appDirStage) })
    stage(t, "deploy_app",       func() { deployApp(t, dbDirStage, appDirStage) })
    stage(t, "validate_app",     func() { validateApp(t, appDirStage) })
}
# deployは設定をディスクに保存(SaveTerraformOptions)、teardownは読み出す(Load...)

# ① 取り壊しを飛ばして建てたまま残す(423s)
$ SKIP_teardown_db=true SKIP_teardown_app=true go test -run '...'
# ② mysqlデプロイも飛ばし、アプリのデプロイ+確認だけ → わずか13.8s！
$ SKIP_teardown_db=true SKIP_teardown_app=true SKIP_deploy_db=true go test ...
# ③ 仕上げ:デプロイと確認を飛ばし、取り壊しだけ(340s)
$ SKIP_deploy_db=true SKIP_deploy_app=true SKIP_validate_app=true go test ...
ハル
弟子・ハル13秒！ さっきの423秒から激減ですね。なんでメモリじゃなくディスク経由なんですか？
棟梁
師匠・棟梁各段階を別々の実行（別プロセス）で走らせるからだ。1回目はdeployだけ・別の回はteardownだけ、と分けて走らせても同じデータベースを使えるよう、情報をディスクに残す。これで変更のたびに10〜15分待つ代わりに10〜60秒で試せる。開発中は何百回も回すから節約は巨大だ。

🏗️ たとえ話：足場を組んだまま内装だけ直す

毎回、土台から足場まで全部解体して建て直していては日が暮れます。土台（mysql）と足場は組んだまま残し、内装（アプリ）だけ直して見せる――この内側のループを速く回すのが、職人の腕の見せどころ。仕上がったら最後にまとめて解体します。

✅ この項のまとめ

  • test_structure.RunTestStageで各段階を名前付き関数に包む。
  • SaveTerraformOptions／LoadTerraformOptionsでステージ間データをディスク経由で受け渡す（別プロセス対応）。
  • SKIP_<ステージ名>=trueで飛ばす。
  • CIでは全段階、開発中は必要な段階だけ走らせて高速化（13分→13秒）。
9.2.2.2

リトライ（一時的な失敗をやり直す）

要するに：インフラ検査では一時的な失敗（不安定なテスト）が起きる。RetryableTerraformErrors などで既知のエラーを自動でやり直すと、検査が安定する。

棟梁
師匠・棟梁検査がたまに理由もなく失敗することがある。これを不安定なテストと呼ぶ。EC2が起動しそこねたり、通信エラーだったり。「既知のエラーなら自動でやり直す」設定を入れると強くなる。
RetryableTerraformErrors で自動リトライする例を見る
# 既知のエラーに対し、5秒間隔で最大3回までやり直す
MaxRetries:         3,
TimeBetweenRetries: 5 * time.Second,
RetryableTerraformErrors: map[string]string{
    # キー=やり直すエラー文(正規表現可)、値=ログに出す補足メモ
    "RequestError: send request failed": "通信制限の問題か?",
},
# → 既知のエラーに当たると「想定内・要リトライ」とログを残して再実行される

✅ この項のまとめ

  • 不安定なテスト＝一時的な理由でたまに失敗する検査。
  • MaxRetries（回数）・TimeBetweenRetries（間隔）・RetryableTerraformErrors（やり直すエラーのマップ）でリトライを有効化。
  • キーはエラー文（正規表現可）、値はログ用の補足。
9.2.3

E2Eテスト（住人目線で端から端まで検査）

要するに：E2Eテストはピラミッドの頂点で少数だけ。全部ゼロから建てると遅く・不安定すぎるので、本番そっくりの永続環境に「変更分だけ」適用して住人目線で確認するのが現実的。

テストピラミッド

▲ E2Eテスト（少数・頂点）

書くコスト・不安定さ・実行時間がすべて最大。だから少なく。

▲▲▲ 統合テスト（中くらい・中間）

複数モジュールの組み合わせ。リトライで実用に。

▲▲▲▲▲ ユニットテスト（多数・底辺）

速くて安定。たくさん書く。

⚠️ 検査に関する重要事項 その5

小さなモジュールはテストが簡単で高速。シンプルなアプリの検査でさえ名前空間・依存性の注入・リトライ・テストステージとかなりの手間がかかった。だから可能な限りピラミッドの低いところで検査する。

📌 ゼロから全部建てるE2Eが破綻する2つの理由

  • 遅すぎる：全部ゼロから建てて壊すと数時間。夜だけ走らせ→朝失敗報告→調査→翌日確認、で1日1バグしか直せず、やがて失敗が無視される。
  • 不安定すぎる：リソース1個が一時ダウンする確率を0.1%とすると、無事な確率は99.9%。N個なら99.9%のN乗。ユニット(20個)98.0%、統合(60個)94.1%まではリトライで救えるが、E2E(600個)は54.9%＝半分近く失敗！
棟梁
師匠・棟梁現実的な戦略はこうだ。①「test」という本番そっくりの環境を1回だけ作り動かしっぱなしにする。②誰かがコードを変えるたびに、その変更だけをtest環境に適用し、Selenium等で住人目線で確認する。デプロイするリソースが数百から数個に減り、速く安定する。しかも本番のデプロイの仕方そっくりだから、「インフラが動くか」だけでなく「デプロイ手順が動くか」も検査できるんだ。

🏗️ たとえ話：モデルルームに変更分だけ反映する

住人目線の最終確認のたびに街を丸ごと建て直すのは無謀です。本番そっくりのモデルルームを一度だけ建てて常設し、変更があるたびに「その変更箇所だけ」を反映して、住人になったつもりで隅々まで使ってみます。これは本番の改修のやり方と同じなので、改修手順そのものの検査にもなります。

✅ この項のまとめ

  • テストピラミッド：ユニット（多）＞統合（中）＞E2E（少）。上ほど高コスト・不安定・遅い。
  • 重要事項その5：小さなモジュールは検査が簡単で速い。
  • ゼロから全部建てるE2Eは遅すぎ・不安定すぎ（99.9%のN乗で確率が激減）。
  • 現実策：永続的なtest環境に変更分だけ適用して住人目線で確認。デプロイ手順も検査できる。
9.2.4

要するに：apply/destroy 以外にも、静的解析・プランテスト・サーバテストという3つの検査手法があり、それぞれ別のバグを見つける。組み合わせると効果が高い。

建てたサーバの中を竣工検査する。

9.2.4.1

静的解析（建てる前に図面を書類審査する）

要するに：静的解析はコードを実行せずに読み解いて調べる書類審査。速くて手軽だが、見つかるのは静的に分かる限られたエラーだけ。

terraform validatetfsectflintTerrascan
説明Terraform組み込みセキュリティ検知プラガブルなリンタ規則・セキュリティ検知
組み込みチェック文法のみAWS/Azure/GCP/K8s等AWS/Azure/GCPAWS/Azure/GCP/K8s等
カスタムチェックなしYAML/JSONGoプラグインRegoで定義
terraform validate が必須引数の欠落を見つける例を見る
# alb_name の指定を忘れると、必須の引数が無いと教えてくれる
$ terraform validate
│ Error: Missing required argument
│ The argument "alb_name" is required, but no definition was found.
棟梁
師匠・棟梁validateは文法だけ。tfsecやtflintはもっと踏み込んだ規則を強制できる。「セキュリティグループが開放的すぎないか（全IP0.0.0.0/0を許す禁止）」「全EC2がタグ規則に従うか」など。これがポリシーをコードで定義する考えだ。

📌 強みと弱み

  • 強み：速い・簡単・安定・本物の業者(AWS)に認証不要・本物を建てたり壊したりしなくていい。
  • 弱み：見つかるのは静的に分かる限られたエラー（文法・型・一部のロジック）だけ。0.0.0.0/0を直書きした違反は検知できても、変数から動的に読む値の違反は検知できない。機能は確かめないので、全合格でも動かないことがある。

🏗️ たとえ話：着工前の図面の書類審査

現場に行く前に、役所が図面だけを机上で審査します。記入漏れや明らかな違反は速く・無料で弾けますが、図面を見るだけでは「実際に建てたら水が出るか」までは分かりません。

✅ この項のまとめ

  • 静的解析＝実行せずコードを読んで調べる。
  • terraform validate（文法）／ tfsec / tflint / Terrascan。
  • 強み：速い・簡単・安定・認証不要・建てる必要なし。
  • 弱み：静的に分かるエラーだけ・動的な値の違反は不可・機能は未確認。
9.2.4.2

プランを使ったテスト（建てずに「建てる計画書」を審査する）

要するに：プランテストは terraform plan の「建てる計画書」を調べる検査。建てないので速め・安定。Terratest（自由）やOPA/Rego（宣言的に規則を書く）で行う。

planは読み取り（状態取得・データソース実行）だけして書き込みはしないので、ユニット/統合より手前。道具はTerratest / OPA / Sentinel / Checkov / terraform-compliance など。

Terratest で計画書の中身（建てる数・特定の値）を調べる例を見る
# init+plan を実行し、計画書を文字列で受け取る
planString := terraform.InitAndPlan(t, opts)

# 「5個建てる予定か」を確かめる
resourceCounts := terraform.GetResourceCount(t, planString)
require.Equal(t, 5, resourceCounts.Add)

# 計画書を構造体にして、特定リソースの name が期待どおりか確かめる
planStruct := terraform.InitAndPlanAndShowWithStructNoLogTempPlanFile(t, opts)
alb := planStruct.ResourcePlannedValuesMap["module.alb.aws_lb.example"]
require.Equal(t, albName, alb.AttributeValues["name"])
棟梁
師匠・棟梁Terratestは任意のGoコードで何でも調べられるが、取りかかりが難しい。もっと宣言的に書きたいなら近年人気のOPAがある。Regoという宣言型言語で「全リソースにManagedBy = terraformタグを付ける」といった規則を書き、毎コミットで自動審査できる。
OPA/Rego での規則と審査の流れを見る
# enforce_tagging.rego:ManagedBy タグがあれば許可(allow)
package terraform
allow {
   resource_change := input.resource_changes[_]
   resource_change.change.after.tags["ManagedBy"]
}

# 計画をJSONに変換して審査する
$ terraform plan -out tfplan.binary
$ terraform show -json tfplan.binary > tfplan.json
$ opa eval --data enforce_tagging.rego --input tfplan.json data.terraform.allow
undefined   # タグ無し→未定義(不許可)。タグを付けると true(許可)

📌 強みと弱み

  • 強み：速い（静的解析ほどではないがユニット/統合より速い）・そこそこ簡単・安定・建てる必要なし。
  • 弱み：見つかるエラーは限られる（静的解析よりは多いがユニット/統合に及ばない）・planには本物の業者(AWS)への認証が必要・機能は確認しない。

🏗️ たとえ話：施工計画書を審査する

図面の書類審査より一歩進んで、「いつ何をいくつ建てるか」を書いた施工計画書を読みます。実際に建てはしないので速くて安定。「街の全建物に管理プレートを付ける」といった会社の決まりも、計画書の段階で機械的に確かめられます。

✅ この項のまとめ

  • プランテスト＝terraform planの出力を調べる。読み取りはするが書き込みはしない。
  • Terratest：InitAndPlan／GetResourceCount／...ShowWithStruct...。
  • OPA(Rego)：plan -out→show -json→opa evalで審査。allowがtrue/undefined。
  • 強み：速め・そこそこ簡単・安定・建てる不要。弱み：エラーは限定的・planに認証必要・機能は未確認。
9.2.4.3

サーバテスト（建てたサーバの中を竣工検査する）

要するに：サーバテストは建てたサーバの中身（権限・依存・ポート等）をDSLで竣工検査する手法。多くのエラーを見つけられるが、本物を建てるので遅く・不安定・お金がかかる。

サーバが正しく設定されているかに絞って確かめる道具群。決まった名前がないので本書では「サーバテスト」と呼ぶ。InSpec / Serverspec / Goss。DSLで「サーバが仕様どおりか」を簡単に書ける。

InSpec でファイル権限・ポート待ち受けを確かめる例を見る
# 設定ファイルが存在し、権限が0644か確かめる
describe file('/etc/myapp.conf') do
  it { should exist }
  its('mode') { should cmp 0644 }
end

# 8080番ポートが実際に待ち受けているか確かめる
describe port(8080) do
  it { should be_listening }
end

📌 強みと弱み

  • 強み：サーバの属性確認が簡単（DSLのおかげ）・ポリシーチェックのライブラリを作れる（PCI・HIPAA等の法令順守確認に便利）・多くの種類のエラーを発見（実際に建てて動くサーバを見るので静的解析やプランテストよりずっと多い）。
  • 弱み：速くない（apply＋たぶんdestroyの完全サイクル）・不安定・AWS認証＋対象サーバへのSSH等の別認証が要る・建てる金と時間がかかる・サーバ以外のインフラは見ない・機能は確認しない。

🏗️ たとえ話：完成した家の中の竣工検査

建物そのものではなく「室内」を点検します。鍵のかかり具合（ファイル権限）、必要な設備が入っているか（依存のインストール）、指定の窓口が開いているか（ポートの待ち受け）。実際に建てた中に入って見るぶん多くを見つけられますが、毎回本物を建てるので時間もお金もかかります。

✅ この項のまとめ

  • サーバテスト＝建てたサーバの設定が仕様どおりか確かめる。InSpec / Serverspec / Goss。
  • DSLで簡単に書け、ポリシーチェックのライブラリ化・法令順守確認に便利。
  • 実際に建てて中を見るので多くのエラーを発見。
  • 弱み：遅い・不安定・AWS認証＋SSH認証・建てる金と時間・サーバ以外は見ない・機能は未確認。

章末の理解度チェック

読み終わったら、自分の言葉で答えてみてください。

第1問ローカルホストが使えない理由

なぜTerraformコードの手動テストでは「自分のパソコンの中（ローカルホスト）」が使えないのですか。検査員が現場に行く、というたとえを使って説明してください。

✅ 解答例
Terraformのコードはほぼ全部が「AWSなどの本物の土地にロビーや警備員を建ててもらう注文」だからです。受付ロビーのような建物は自分のパソコンの中には建たず、本物の土地の上にしか建ちません。だから検査員は現場（本物のクラウド環境）に行って、実際に建てて確かめるしかないのです。これが重要事項その1です。
📝 採点ポイント
□ コードのほとんどが本物のクラウドへの注文だと述べている ／ □ 自分の機械には建てられないと述べている ／ □ だから本物の環境にデプロイして手動テストするしかないと結論づけている
第2問defer を apply の前に置く理由

Terratestの検査で defer terraform.Destroy を、建てる InitAndApply よりも前に書くのはなぜですか。

✅ 解答例
deferは「関数が成功でも失敗でも終わるときに必ず実行する」予約です。片付けをコードの最後に普通に書くと、その手前で検査が失敗したとき片付けにたどり着けず、建てた物が放置されます。deferをapplyの前に置けば、建てる前に「終わったら必ず取り壊す」予約が登録されるので、途中で失敗しても確実に片付けられます。
📝 採点ポイント
□ deferは終了時に必ず実行される仕組みだと説明している ／ □ 途中で失敗すると後ろの片付けに到達できないと述べている ／ □ 先に予約しておけば失敗しても片付くと結論づけている
第3問名前空間とランダムID

複数の検査を並列に走らせると失敗することがあります。その原因と、random.UniqueId() を使った対策を説明してください。

✅ 解答例
原因は、各検査が同じ名前でALBやセキュリティグループなどを建てようとして名前がぶつかる（同じ住所表示の建物を2つ建てようとする）からです。対策は、リソースの名前を入力変数で設定できるようにし、random.UniqueId()が返すランダムな6文字を名前に付けて一意にすること（名前空間化）です。560億通り以上あるのでまず衝突せず、安心して並列実行できます。
📝 採点ポイント
□ 同じ名前で建てようとして衝突するのが原因だと述べている ／ □ 名前を変数化して一意な名前を付ける（名前空間化）と述べている ／ □ random.UniqueId()でランダムな一意IDを付けると述べている
第4問テストステージの効果

テストステージ（SKIP_<名前>=true で段階を飛ばす）は、何のために使い、開発中にどんな効果がありますか。

✅ 解答例
統合テストはmysqlとアプリを建てて確認して壊す5段階ですが、アプリだけ直したいときに毎回mysqlを建て直すのは時間とお金の無駄です。テストステージで段階を名前付きに分け、不要な段階（mysqlのデプロイや取り壊し）を飛ばせば、アプリのデプロイと確認だけを回せます。これで1回10〜15分かかっていたループが10〜60秒になり、開発中のくり返しが爆速になります。
📝 採点ポイント
□ 検査を段階に分けて飛ばせる仕組みだと述べている ／ □ 不要な段階（mysqlの建て直し等）を省けると述べている ／ □ 開発中のループが大幅に速くなると述べている
第5問テストピラミッドとE2Eの現実的戦略

テストピラミッドの考え方を説明し、E2Eテストを「ゼロから全部建てる」のではなく現実にはどうするのかを述べてください。

✅ 解答例
テストピラミッドは、ユニットテストをたくさん（底辺）、統合テストを中くらい、E2Eテストを少しだけ（頂点）にする考え方です。上に行くほどコスト・不安定さ・時間が増えるからです。E2Eを全部ゼロから建てると数時間かかって遅すぎ、リソースが多いほど一時的失敗の確率が上がって不安定すぎます。だから現実には、本番そっくりの永続的なtest環境を1回作って動かしっぱなしにし、変更があるたびに「その変更分だけ」適用して住人目線で確認します。これは本番のデプロイの仕方にも似ているので、デプロイ手順自体も検査できます。
📝 採点ポイント
□ ユニット多・統合中・E2E少という配分を述べている ／ □ 上ほどコスト・不安定・遅いと述べている ／ □ E2Eは永続環境に変更分だけ適用するのが現実的だと述べている
