宣言型言語 declarative

「どう作るか（手順）」ではなく「どんな状態になっていてほしいか（完成図）」だけを書く書き方。Terraformはこの仲間。

リソース resource

Terraformが作る1つ1つの部品（サーバ・利用者・ロードバランサなど）。この章では「建物」にたとえます。

count カウント

「この設計図の建物を何棟作るか」を数で指定する道具。番号で建物を並べて管理する。

for_each フォーイーチ

一覧（集合・マップ）を回して建物・小部屋・モジュールを作る道具。番号でなく名前で管理する。

for 式 フォーしき

一覧を別の一覧に「変換」する道具（大文字化・絞り込みなど）。for_eachとは別物。

三項演算子 ? :

「条件 ? 真のとき : 偽のとき」と書く分岐の式。条件が当たれば左、外れれば右の値になる。

インラインブロック 小部屋

建物（リソース）の中に書く小さな設定のかたまり。タグの設定などがこれ。

dynamic ブロック 動的

小部屋（インラインブロック）を一覧の数だけ自動で量産する書き方。

マップ map

「名前→値」の対応表。たとえば Owner→team-foo のように、キーと値の組で覚える。

集合 set

重複のない要素の集まり。リソースのfor_eachに渡せる形。

ASG Auto Scaling Group

自動で台数を増減するサーバの群れ。この章では「同じ規格の棟が並んだ住宅団地」のイメージ。

ALB ロードバランサ

アクセスを複数のサーバに振り分ける受付係。団地の入口の管理人さん。

ゼロダウンタイムデプロイ

ユーザを一瞬も止めずに、新しい中身へ建て替えること。住みながらの無停止リフォーム。

create_before_destroy

「壊す前に作る」という印。古い棟を壊す前に新しい棟を建てる順番にする設定。

ステートファイル state

Terraformが「自分が何を作ったか」を記録する管理台帳。これに載っていないものは知らない。

plan / apply

plan＝建てる前の見積もり、apply＝実際に建てる作業。

import 取り込み

Terraformを使う前から建っていたものを、台帳に登録して管理下に入れるコマンド。

moved ブロック

「この識別子はあっちに移した」とコードに書いて、台帳を自動更新させる仕組み。リネームでの作り直しを防ぐ。

イミュータブル immutable

「変更不可」の性質。変えようとすると古いものを壊して作り直すパラメータのこと。

instance refresh インスタンスの更新

AWS純正の無停止入れ替え機能。1台ずつ順に新しくしてくれる。

スプラット式 [*]

「全部ちょうだい」の合図。配列から全要素の属性を一気に取り出す書き方。

序

はじめに：宣言型言語という建て方

なぜ Terraform はループや条件分岐が苦手なのか

要するに：Terraformは完成形だけを書く宣言型言語なので繰り返しや条件分岐が苦手。でも count・for_each・for・三項演算子・lifecycle などの道具で補える。

🏗️ たとえ話：完成図を渡す工務店

グラウンドワークス工房は「同じ規格の建物を量産する工務店」。棟梁は職人に「まず基礎を掘って、次に柱を……」と手順を全部指示するのではなく、完成図を渡して「これと同じ状態にしておいて」と頼みます。これが宣言型。意図は分かりやすく設計図も小さく保てますが、その代わり「同じ家を3回くり返し建てろ」「お客さんを困らせず建て替えろ」といった手順が大事な作業は、完成図だけでは表しにくいのです。

ハル
ハル（弟子）棟梁、Terraformって「宣言型言語」っていうんですよね。なんでしたっけ？
棟梁
棟梁（師匠）「どう作業するか」じゃなくて「最終的にどんな建物が建っていてほしいか」だけを書く言い方だ。職人に手順を全部指示するんじゃなく、完成図を渡して「これと同じ状態にして」と頼むようなものさ。
ハル
ハル手順を書かなくていいから楽そうですね。
棟梁
棟梁意図が分かりやすいし設計図も小さく保てる。でも苦手もある。完成図しか書けないから「同じことを3回くり返せ（forループ）」や「もしこうなら作れ（if文）」が言語そのものに無いんだ。無停止の建て替えみたいに本来は手順が大事な作業も、完成図だけで表さないといけない。
ハル
ハルえっ、じゃあ同じ家を3棟建てたいときは、設計図を3枚コピペするしか？
棟梁
棟梁いや、Terraformはちゃんと道具を用意してる。count、for_each と for、三項演算子、lifecycle ブロックの create_before_destroy、それに便利な関数。組み合わせればループもif文も無停止の建て替えもできる。
ハル
ハルつまり「宣言型でできない作業を、専用の道具で補う」のがこの章ですね！

  • 宣言型の強み（意図が明確・コードが小さい）を活かしつつ、弱点（繰り返し・条件・手順）を道具で埋められる。
  • この章で扱う4テーマ（ループ／条件分岐／ゼロダウンタイムデプロイ／つまずきポイント）の地図を最初に持てる。

  • 補う道具：count、for_each、for、三項演算子、lifecycle、各種関数。

5.1

ループ

用途別に4種類のループ道具がある

要するに：Terraformのループは用途別に4種類（count／for_each／for式／for文字列命令）あり、それぞれ得意な場面が違う。

🏗️ たとえ話：用途別の型枠

工房でも、家まるごとを量産する大きな型枠と、家の中の棚だけを量産する小さな型枠は別物。Terraformのループも、量産したいものが「建物まるごと」か「家の中の小部屋」か「一覧の中身の加工」かで、使う道具が変わります。

ハルループの道具がいくつもあるって。なんで1つじゃダメなんですか？

棟梁場面が少しずつ違うからだよ。①建物まるごとを繰り返す count、②建物や小部屋（インラインブロック）を繰り返す for_each、③一覧を変換する for 式、④文字列の中で一覧を流し込む for 文字列命令。順番に見ていこう。

5.1.1

count パラメータによるループ

型枠の枚数を指定して建物を量産する

要するに：countは「建物を何棟作るか」と「番号で区別」する一番古くて単純な道具。便利だが、小部屋には使えず、列の途中を削ると後ろが全部作り直しになる。

🏗️ たとえ話：型枠の枚数指定

count は「この設計図の建物を何棟作るか」を決める型枠の枚数指定。ただし素朴に「3棟」とだけ頼むと、表札（名前）まで全部同じになって、同じ表札の家が3軒並んでしまいエラーに。そこで count.index（何番目かの番号）を表札に混ぜ、さらに本当の名前の一覧から番号で引っ張り出します。

ハル
ハルまず count からですね。これは何ですか？
棟梁
棟梁一番古くて単純な「型枠の枚数指定」だ。count = 3 と書けば3棟作る。でも素朴にやると、利用者の名前が全員同じになってエラーになる落とし穴がある。
ハル
ハルあー、同じ表札の家が3軒並んじゃう感じですね。
棟梁
棟梁そこで count.index を使う。0,1,2…と番号をくれるから名前に混ぜれば別々になる。でも neo.0 はダサいから、本当の名前の一覧を変数に入れて、番号で引っ張り出すんだ。長さは length 関数で数えられる。

まず、利用者（IAMユーザ）を1人だけ作る素朴な設計図です。

このコードは AWS の利用者アカウントを1人「neo」という名前で作ります。

HCL コードを見る（1人だけ作る）
# AWSの利用者アカウントを1人「neo」という名前で作る
provider "aws" {
  region = "us-east-2"             # ① どの地域に作るか
}

resource "aws_iam_user" "example" {
  name = "neo"                     # ② 利用者の名前。今は1人だけ
}

普通の言語ならforループを書きたくなりますが、Terraformには無いので動きません。代わりに count を使います。3棟作れますが、名前が全部同じでエラーになります。

HCL コードを見る（forループは疑似コード／count=3 は名前重複でエラー）
# これは疑似コード。Terraformでは動作しない（forループ自体が無い）
for (i = 0; i < 3; i++) {
  resource "aws_iam_user" "example" {
    name = "neo"
  }
}

# 同じ設計図を3棟作る（ただし名前が全部同じでエラーになる）
resource "aws_iam_user" "example" {
  count = 3                        # ① この設計図を3棟ぶん作れ
  name  = "neo"                    # ② 3人とも「neo」で重複エラー
}

番号を振り分けるには count.index（0,1,2…という何番目かの番号）を名前に混ぜます。

HCL コードを見る（count.index で別々の名前）
# 0,1,2の番号を名前に混ぜて、別々の名前の利用者を3人作る
resource "aws_iam_user" "example" {
  count = 3                        # ① 3棟ぶん作る
  name  = "neo.${count.index}"     # ② count.index は0,1,2…の番号
}
terraform plan の結果を見る
# neo.0 / neo.1 / neo.2 という名前で作ろうとする
  # aws_iam_user.example[0] will be created
      + name = "neo.0"
  # aws_iam_user.example[1] will be created
      + name = "neo.1"
  # aws_iam_user.example[2] will be created
      + name = "neo.2"

Plan: 3 to add, 0 to change, 0 to destroy.

neo.0 では使いにくいので、名前の一覧を変数に入れます。一覧の○番目は 配列[番号] で取り出し、長さは length() で数えます。

HCL コードを見る（名前一覧の変数＋length で量産）
# IAMユーザに付けたい名前の一覧（リスト）を持つ変数
variable "user_names" {
  description = "これらの名前でIAMユーザを作成する"
  type        = list(string)       # ① 文字列の一覧という型
  default     = ["neo", "trinity", "morpheus"]  # ② 3人ぶん
}

# 配列の○番目を取り出す書き方： ARRAY[<インデックス>]
var.user_names[1]                 # 0から数えて2人めを取り出す

# length関数：一覧の要素数を返す
length(<配列>)

# 名前一覧の数だけ利用者を作り、各人に一覧の名前を割り当てる
resource "aws_iam_user" "example" {
  count = length(var.user_names)        # ① 一覧の長さ（=3）ぶん作る
  name  = var.user_names[count.index]   # ② count.index番目の名前
}
terraform plan の結果を見る（読みやすい名前で3人）
  # aws_iam_user.example[0] + name = "neo"
  # aws_iam_user.example[1] + name = "trinity"
  # aws_iam_user.example[2] + name = "morpheus"

Plan: 3 to add, 0 to change, 0 to destroy.

作った値を別の場所から使う（スプラット式）

ハル
ハルできた名前を別の場所から使いたいときは？ 普通は「リソース名.属性」で取れますよね。
棟梁
棟梁count 付きは「1棟」じゃなく「建物の配列（並んだ列）」になる。だから <名前>[番号].属性 と番号を指定する。全部まとめて欲しいときは *（スプラット式）を使うと一気に取れる。

1人めのARNだけ取り出すには番号 [0] を、全員ぶんなら [*] を使います。

HCL コードを見る（[0] と [*] で属性を取り出す）
# 1人めの住所ID（ARN）だけを取り出す
output "first_arn" {
  value = aws_iam_user.example[0].arn   # ① [0]で1人めを指定
}

# 全利用者の住所IDをまとめて取り出す
output "all_arns" {
  value = aws_iam_user.example[*].arn    # ① [*]で全員ぶんを一気に取得
}
terraform apply の結果を見る
Apply complete! Resources: 3 added, 0 changed, 0 destroyed.

first_arn = "arn:aws:iam::123456789012:user/neo"
all_arns = [
  "arn:aws:iam::123456789012:user/neo",
  "arn:aws:iam::123456789012:user/trinity",
  "arn:aws:iam::123456789012:user/morpheus",
]

モジュールにも count が使える

ハル
ハルcount って、家まるごとを作る「モジュール」にも使えるんですか？
棟梁
棟梁Terraform 0.13以降ならモジュール（一棟分の設計図セット）にも使える。count で囲めばモジュールの配列になる。考え方は同じだよ。

利用者を1人作るモジュールを count で3人ぶん呼び出します。

HCL コードを見る（モジュールを count で量産）
# 利用者を1人作り、その住所ID（ARN）を返す小さな設計図セット
resource "aws_iam_user" "example" { name = var.user_name }
variable "user_name" { type = string }
output "user_arn" { value = aws_iam_user.example.arn }

# モジュールを名前の数だけ呼び出し、3人作る
module "users" {
  source    = "../../../modules/landing-zone/iam-user"
  count     = length(var.user_names)        # ① 名前の数だけ作る
  user_name = var.user_names[count.index]   # ② count.index番目の名前
}
output "user_arns" {
  value = module.users[*].user_arn          # ③ 全モジュールの戻り値をまとめて取る
}

count の制限その1：小部屋には使えない

ハル
ハルcount 便利じゃないですか。落とし穴なんてあるんですか？
棟梁
棟梁大きいのが2つある。1つめは「建物の中の小部屋（インラインブロック）は count で繰り返せない」。たとえば ASG に付ける tag という小部屋を動的に何個も作りたくても、count は小部屋の中では使えない。

ASGのタグは「小部屋（インラインブロック）」で書きますが、これを count で量産することはできません。

HCL コードを見る（tag という小部屋）
# サーバの群れ（ASG）に「Name」という名札（タグ）を1つ付ける
resource "aws_autoscaling_group" "example" {
  # (...)
  tag {                            # ① これが「小部屋（インラインブロック）」
    key                 = "Name"
    value               = var.cluster_name
    propagate_at_launch = true
  }
}

count の制限その2：途中を消すと後ろが作り直しになる

ハル
ハル制限の2つめは？
棟梁
棟梁「途中の要素を消すと、後ろが全部ずれて作り直しになる」ことだ。count は建物を「番号で並んだ列」として管理してる。真ん中を抜くと後ろが繰り上がるだろう？ Terraformは番号で見分けてるから、繰り上がりを「中身の入れ替え」と勘違いするんだ。
ハル
ハルえっ、消したい1棟だけじゃなくて、後ろも巻き込まれる？
棟梁
棟梁そう。3人の真ん中 trinity を消すとこうなる。

🏗️ たとえ話：1号棟・2号棟…と番号だけで管理する団地

建物を「1号棟・2号棟・3号棟」と番号だけで管理していると、2号棟を取り壊した瞬間、3号棟が「新しい2号棟」に繰り上がります。台帳上は「2号棟（中身が trinity→morpheus に変わった）」「3号棟（消滅）」と読めてしまう。結果は合っていても、途中で本当に建物を壊して建て直すので、その間お客さんは使えなくなります。

terraform plan の結果を見る（trinity を消すだけのつもりが…）
  # aws_iam_user.example[1] will be updated in-place
  ~ name = "trinity" -> "morpheus"   # 1番を改名

  # aws_iam_user.example[2] will be destroyed
  - name = "morpheus" -> null            # 2番を削除

Plan: 0 to add, 1 to change, 1 to destroy.

💡 なぜこれが必要か / これを知ると何ができるか

  • 設計図1枚で同じ建物を何棟でも作れる（コピペ不要）。
  • count.index と一覧・length を組み合わせれば、各棟に固有の名前や設定を与えられる。
  • 2つの制限（小部屋NG・途中削除で作り直し）を知れば、事故を避けられる。

📌 この項のまとめ

  • count = 数でリソース／モジュールをその数だけ作る。
  • count.indexで繰り返し番号（0始まり）を取得。
  • count付きは配列になり、[番号]や[*]（スプラット式）で取り出す。
  • 制限1：インラインブロック（小部屋）には使えない。
  • 制限2：途中の要素を削除すると、それ以降が作り直しになる。
5.1.2

for_each 式によるループ

番号でなく名前で管理する、より安全なループ

要するに：for_eachは集合・マップを回して建物・小部屋・モジュールを作り、名前で管理するので途中削除でも巻き込まれない。dynamicブロックで小部屋も動的に量産でき、共通の名札はdefault_tagsで一括設定できる。

🏗️ たとえ話：番号でなく表札で管理する団地

count が「1号棟・2号棟…」と番号で管理するのに対し、for_each は表札（名前）で管理します。「neo邸・trinity邸・morpheus邸」と呼んでいれば、trinity邸を取り壊しても neo邸・morpheus邸はそのまま。番号の繰り上がりが起きないので、巻き添えの建て直しが起きません。

ハル
ハルその2つの制限、なんとかならないんですか？
棟梁
棟梁なるよ。Terraform 0.12で for_each が登場して両方解決した。リスト・集合・マップを回して、建物・小部屋・モジュールのどれでもコピーできる。
ハル
ハルcount との一番の違いは？
棟梁
棟梁建物を「番号の列」じゃなく「名前付きの集まり（マップ）」で管理することだ。名前で見分けるから、途中の1つを消しても後ろがずれない。これが決定的に大きい。

同じ3人を for_each で作ります。各要素には each.key・each.value でアクセス。リソースには集合かマップしか渡せないので toset で変換します。

HCL コードを見る（for_each で利用者を作る）
# for_each の一般形：COLLECTION を回して CONFIG を作る
resource "<TYPE>" "<NAME>" {
  for_each = <COLLECTION>
  [CONFIG ...]
}

# 名前一覧を「集合」に変えて、それぞれの名前で利用者を作る
resource "aws_iam_user" "example" {
  for_each = toset(var.user_names)   # ① toset で一覧を集合に変換
  name     = each.value              # ② each.value で今回の名前
}

結果は「名前付きの対応表（マップ）」になります。ARNだけ欲しいときは values 関数とスプラット式を組み合わせます。

HCL コードと apply 結果を見る
# 作った利用者をマップとして丸ごと表示
output "all_users" { value = aws_iam_user.example }

# 結果（キーが名前、値が利用者の情報）
all_users = {
  "morpheus" = { "arn" = "...:user/morpheus", "name" = "morpheus", ... }
  "neo"      = { "arn" = "...:user/neo", "name" = "neo", ... }
  "trinity"  = { "arn" = "...:user/trinity", "name" = "trinity", ... }
}

# マップから値だけ取り出し、全員のARNの一覧にする
output "all_arns" {
  value = values(aws_iam_user.example)[*].arn   # values で値を取り、[*]でARNを集める
}

途中削除しても巻き込まれない

ハル
ハルここで trinity を消したら？ count のときみたいに巻き込まれます？
棟梁
棟梁試してごらん。名前で見分けてるから、trinity だけがきれいに消える。これが count より for_each を選ぶべき理由だ。モジュールでもほぼ理想的に動くよ。
terraform plan の結果を見る（trinity だけ消える）
  # aws_iam_user.example["trinity"] will be destroyed
  - name = "trinity" -> null

Plan: 0 to add, 0 to change, 1 to destroy.

# モジュールでも for_each で同じことができる
module "users" {
  source    = "../../../modules/landing-zone/iam-user"
  for_each  = toset(var.user_names)   # ① 名前の集合を回す
  user_name = each.value              # ② 今回の名前を渡す
}
output "user_arns" {
  value = values(module.users)[*].user_arn   # ③ 戻り値を集める
}

dynamic ブロックで小部屋を動的に量産

ハル
ハルもう1つの制限「小部屋が繰り返せない」も for_each で解決？
棟梁
棟梁そう。dynamic ブロックという書き方で、小部屋（インラインブロック）を一覧の数だけ動的に作れる。さっきのASGのタグを、お客さんが自由に増やせるようにしてみよう。

🏗️ たとえ話：お客さん指定の名札を必要な数だけ貼る

固定の「Name」表札は必ず1枚貼る。それに加えて、お客さんが「うちは Owner と DeployedBy の名札も付けて」と指定した分だけ、dynamic という名札職人が一覧を見ながら必要な枚数だけ自動で貼ってくれます。

お客さんがカスタムタグを指定できるマップ型の変数を追加し、本番環境で担当チームとデプロイ方法の名札を付けます。

HCL コードを見る（custom_tags 変数と本番設定）
# サーバ群に付ける「お客さん指定の名札」の対応表
variable "custom_tags" {
  type    = map(string)        # ① キーも値も文字列の対応表（マップ）
  default = {}                 # ② 既定は空（何も付けない）
}

# 本番のWebサーバ群に担当チームとデプロイ方法の名札を付ける
module "webserver_cluster" {
  source       = "../../../../modules/services/webserver-cluster"
  cluster_name = "webservers-prod"
  # (...)
  custom_tags = {
    Owner      = "team-foo"        # ① 誰が担当か
    DeployedBy = "terraform"       # ② Terraform管理（手で触るなの印）
  }
}

疑似コードのforループは動かないので、dynamic ブロックを使います。content が各回で作る中身です。

HCL コードを見る（dynamic ブロックで tag を量産）
# dynamic の一般形：COLLECTION を回して content 内の小部屋を量産
dynamic "<VAR_NAME>" {
  for_each = <COLLECTION>
  content { [CONFIG...] }
}

# お客さん指定の名札の数だけ、tag という小部屋を自動で量産
resource "aws_autoscaling_group" "example" {
  # (...)
  tag {                            # ① 固定で付ける名札
    key = "Name"; value = var.cluster_name; propagate_at_launch = true
  }
  dynamic "tag" {                  # ② ここから小部屋を動的に量産
    for_each = var.custom_tags     # ③ お客さん指定の名札一覧を回す
    content {
      key                 = tag.key    # ④ 今回のキー
      value               = tag.value  # ⑤ 今回の値
      propagate_at_launch = true
    }
  }
}

タグに関するルールを強制する（default_tags）

ハル
ハルタグって、リソースごとに手で付けるんですか？ 数が多いと付け忘れそう。
棟梁
棟梁すべてのリソースに同じ名札を付けたいなら、aws プロバイダ（AWSとの窓口設定）に default_tags を置くのが確実だ。工房の入口に「全棟にこの表札を付けること」と貼り出すようなものさ。

このモジュールで作る全AWSリソースに、共通の名札を自動で付けます。

HCL コードを見る（default_tags で一括設定）
# このモジュールで作る全AWSリソースに、共通の名札を自動で付ける
provider "aws" {
  region = "us-east-2"
  default_tags {
    tags = {
      Owner     = "team-foo"       # ① 担当チーム
      ManagedBy = "Terraform"      # ② Terraform管理であること
    }
  }
}

ただし例外があり、タグ非対応のリソースや、タグは対応するが default_tags に対応しない aws_autoscaling_group は対象外です（前節でASGのタグを手で設定したのはこのため）。default_tags は共通の基準を与えつつ、リソースごとの上書きも許します。9章ではOPAのようなツールで「全リソースに ManagedBy を付ける」ポリシーを強制する方法を扱います。

💡 なぜこれが必要か / これを知ると何ができるか

  • count の2大制限（小部屋NG・途中削除で作り直し）を両方解決できる。
  • ユーザが自由にタグを増やせる、柔軟で安全なモジュールが作れる。
  • default_tags でタグ付けのルールをコードとして全社的に強制できる。

📌 この項のまとめ

  • for_eachは集合（set）・マップを回す（リソースではリスト不可、tosetで変換）。
  • each.key／each.valueで要素にアクセス。
  • 結果はマップになり、values()＋[*]で値を集める。
  • 名前で管理するため、途中削除でも他がずれない。
  • dynamicブロックでインラインブロック（小部屋）を動的生成。
  • 共通タグはdefault_tagsで一括設定（ただしASG等の例外あり）。
5.1.3

for 式によるループ

一覧を別の一覧に「変換」する道具

要するに：for式は「一覧（リスト・マップ）を加工して別の一覧・マップに変換する」道具。ifでフィルタもできる。for_eachとは別物。

🏗️ たとえ話：資材リストの一括加工

for_each が「建物を量産する型枠」なら、for 式は資材リストを一括で加工する道具。「全部の表札を大文字に塗り直す」「5文字未満の名前だけ残す」のように、一覧の中身をまとめて変換します。建物を増やすのではなく、リストそのものを作り変えるのが役目です。

ハル
ハル「いくつ作るか」のループは分かりました。でも、1つの値を作るために一覧を加工したいときは？ 名前を全部大文字にしたいとか。
棟梁
棟梁それが for 式だ。さっきの for_each とは別物だぞ。「一覧を別の一覧に変換する」道具で、Pythonでいうリスト内包表記と同じ働きをする。
ハル
ハルリスト内包……？ 何ですかそれ。
棟梁
棟梁「一覧の各要素を加工して新しい一覧を作る」を1行で書く書き方さ。まずPythonで見せよう。

参考までにPythonのリスト内包表記。普通のforループを1行にでき、if でフィルタもできます。

Python コードを見る（参考：リスト内包表記）
# 普通のforループで名前を1つずつ大文字に変換する
names = ["neo", "trinity", "morpheus"]
upper_case_names = []
for name in names:
    upper_case_names.append(name.upper())
# 出力: ['NEO', 'TRINITY', 'MORPHEUS']

# 同じことを1行で（リスト内包表記）
upper_case_names = [name.upper() for name in names]

# 5文字未満の名前だけ大文字にして残す（if でフィルタ）
short = [name.upper() for name in names if len(name) < 5]
# 出力: ['NEO']

Terraformの for 式も同じ。名前を全部大文字に変換し、if でフィルタもできます。

HCL コードを見る（リストの変換とフィルタ）
# for式の一般形：LIST を回し、各 ITEM を OUTPUT に変換
[for <ITEM> in <LIST> : <OUTPUT>]

# 名前一覧を全部大文字に変換した一覧にする
output "upper_names" {
  value = [for name in var.names : upper(name)]
}
# 結果: ["NEO", "TRINITY", "MORPHEUS"]

# 5文字未満の名前だけを大文字にして残す（if でフィルタ）
output "short_upper_names" {
  value = [for name in var.names : upper(name) if length(name) < 5]
}
# 結果: ["NEO"]

マップに対してもループでき、出力をリスト（角括弧）にもマップ（波括弧）にもできます。

HCL コードを見る（マップのループと出力）
# マップに対する for式：KEY と VALUE を取り出して変換
[for <KEY>, <VALUE> in <MAP> : <OUTPUT>]

# 名前と役どころの対応表
variable "hero_thousand_faces" {
  type = map(string)
  default = { neo = "hero", trinity = "love interest", morpheus = "mentor" }
}
# 「名前 is the 役どころ」という文を一覧で作る
output "bios" {
  value = [for name, role in var.hero_thousand_faces : "${name} is the ${role}"]
}
# 結果: ["morpheus is the mentor", "neo is the hero", "trinity is the love interest"]

# 出力をマップにする（波括弧、キー => 値）。キーも値も大文字に
output "upper_roles" {
  value = {for name, role in var.hero_thousand_faces : upper(name) => upper(role)}
}
# 結果: { "MORPHEUS" = "MENTOR", "NEO" = "HERO", "TRINITY" = "LOVE INTEREST" }

💡 なぜこれが必要か / これを知ると何ができるか

  • 1つの変数や設定値を、一覧から加工して組み立てられる。
  • 大文字変換・フィルタ・名前と役の合成など、データの整形を1行で書ける。
  • 角括弧→リスト、波括弧→マップ、と出力の形も選べる。

📌 この項のまとめ

  • [for x in list : 式]でリストを変換。
  • if 条件でフィルタ。
  • [for k, v in map : 式]でマップを回す。
  • {for ... : キー => 値}でマップを出力。
  • for_each（コピー作成）とは役割が違う（こちらは値の変換）。
5.1.4

for の文字列ディレクティブを使ったループ

文字列の中で一覧を繰り返し展開する

要するに：%{ for ... }...%{ endfor }で文字列の中で一覧を繰り返し展開できる。番号も取れるが、最後に余計なコンマが残る課題があり、ifで解決する（次節）。

🏗️ たとえ話：看板に住人名簿を流し込む

団地の入口の看板に「neo, trinity, morpheus」と住人名を並べたい。%{ for ... } は、一覧を見ながら看板の文字列に名前を1人ずつ流し込む道具です。ただし機械的に区切りを付けるので、最後の名前の後ろにも余計なコンマが残ってしまうのが目下の悩みどころ。

ハル
ハル文字列の中でループ……って、どういうことですか？
棟梁
棟梁前に "Hello, ${var.name}" みたいに ${...} で値を差し込む「文字列補間」を習ったね。その仲間で、文字列の中でループやif文を回せる「文字列ディレクティブ」がある。記号がドル記号じゃなく、パーセント記号と波括弧 %{...} になるのが目印だ。

名前の一覧を1本の文字列に展開します。番号も取り出せます。

HCL コードを見る（for 文字列ディレクティブ）
# 一般形：COLLECTION を回し、各回で BODY を展開
%{ for <ITEM> in <COLLECTION> }<BODY>%{ endfor }

# 名前の後ろにコンマとスペースを付けながら一覧を1本の文字列に展開
output "for_directive" {
  value = "%{ for name in var.names }${name}, %{ endfor }"
}
# 結果: "neo, trinity, morpheus, "

# 番号も取り出す： (番号) 名前 という形で展開
output "for_directive_index" {
  value = "%{ for i, name in var.names }(${i}) ${name}, %{ endfor }"
}
# 結果: "(0) neo, (1) trinity, (2) morpheus, "
ハル
ハルあれ、最後の名前の後ろにもコンマとスペースが付いてて、ちょっと変ですね。
棟梁
棟梁そう、そこが課題だ。これを直すには、次の節で説明する if 文字列ディレクティブを使うんだ。お楽しみに取っておこう。

💡 なぜこれが必要か / これを知ると何ができるか

  • 設定ファイルやメッセージ文字列の中に一覧を流し込んで生成できる。
  • ${...}（補間）と%{...}（ディレクティブ）の違いを区別できる。

📌 この項のまとめ

  • 文字列ディレクティブは%{...}（補間の${...}とは別記号）。
  • %{ for x in 集合 }本体%{ endfor }でループ。
  • %{ for i, x in 集合 }で番号も取得。
  • 末尾に余計な区切りが残る問題はifで解決（次節）。
5.2

条件分岐

「もし○○なら作る」も用途別に3系統

要するに：条件分岐（もし〜なら作る）も用途別にcount・for_each／for式・if文字列ディレクティブの3系統がある。

🏗️ たとえ話：お客さんごとに付けるオプション設備

「本番のお宅にはオートスケール（時間で台数を増減する仕組み）を付ける、開発のお宅には付けない」——これが条件分岐。お客さんごとに設備を付ける／付けないを選ぶオプション工事のようなものです。

ハル
ハル次は条件分岐ですね。「もし○○なら作る」ってやつ。これも道具が複数あるんですか？
棟梁
棟梁そう。①条件付きでリソースを作る count、②条件付きでリソースや小部屋を作る for_each と for 式、③文字列の中の分岐に使う if 文字列ディレクティブ。順番に見ていこう。

📌 この項のまとめ

  • count：条件付きでリソースを作る／作らない。
  • for_eachとfor式：条件付きでリソースや小部屋を作る。
  • if文字列ディレクティブ：文字列の中の分岐。
5.2.1

count パラメータを使った条件分岐（if / if-else）

count を 1 か 0 に切り替えて分岐する

要するに：countを? 1 : 0（と逆向きの? 0 : 1）で切り替えれば、if文・if-else文を再現できる。結果のARNは三項演算子よりconcat＋oneで取り出すほうが安全。

🏗️ たとえ話：オプション工事を「1棟」か「0棟」かで切り替える

「設備を付ける＝その設備を1棟ぶん建てる」「付けない＝0棟」と考えれば、count の数を1か0かで切り替えるだけで「付ける／付けない」のオプション工事になります。さらに「読み取り専用と読み書き両方は、どちらか一方だけ」のような排他の選択も、片方を 1:0、もう片方を 0:1 と逆にすれば表せます。

ハル
ハルcount って数を数える道具でしたよね。それで条件分岐？
棟梁
棟梁ちょっと頭を使う。count に1を入れれば1棟、0を入れれば1棟もできない。つまり「1か0か」で切り替えれば「作る／作らない」のif文になるんだ。

5.2.1.1 count を使った if 文

4章ではWebサーバクラスタのモジュールを作り、スケジュール（時間で台数を増減する設定）は本番だけに直接書きました。これをモジュール側に入れ、ユーザが「使う／使わない」を選べるようにします。

真偽値の切り替えスイッチ変数を追加し、三項演算子 条件 ? 1 : 0 と組み合わせます。

HCL コードを見る（enable_autoscaling スイッチで if 文）
# オートスケールを使うかどうかの切り替えスイッチ
variable "enable_autoscaling" {
  type = bool                      # ① true か false かの真偽値
}

# スイッチがtrueのときだけ、朝に台数を増やすスケジュールを作る
resource "aws_autoscaling_schedule" "scale_out_during_business_hours" {
  count = var.enable_autoscaling ? 1 : 0   # ① trueなら1（作る）、falseなら0
  recurrence = "0 9 * * *"                  # ② 毎朝9時に発動
  # (...)
}

# スイッチがtrueのときだけ、夜に台数を減らすスケジュールを作る
resource "aws_autoscaling_schedule" "scale_in_at_night" {
  count = var.enable_autoscaling ? 1 : 0
  recurrence = "0 17 * * *"                 # 毎夕17時に発動
  # (...)
}

ステージング環境では false（OFF）、本番環境では true（ON）にして呼び出します（4章で本番に直接書いた aws_autoscaling_schedule は削除します）。

HCL コードを見る（環境ごとにスイッチを切り替える）
# ステージング：オートスケール無し
module "webserver_cluster" {
  cluster_name       = "webservers-stage"
  enable_autoscaling = false     # ① スイッチOFF
}

# 本番：オートスケール有り
module "webserver_cluster" {
  cluster_name       = "webservers-prod"
  enable_autoscaling = true      # ① スイッチON
  custom_tags = { Owner = "team-foo", ManagedBy = "terraform" }
}

5.2.1.2 count を使った if-else 文

ハル
ハルif（作る／作らない）は分かりました。じゃあif-else（こっちかあっちか）は？
棟梁
棟梁同じ三項演算子を使う。片方を ? 1 : 0、もう片方を ? 0 : 1 と逆にすればいい。trueなら最初だけ、falseなら2つめだけ作られる。

利用者 neo に CloudWatch への「読み取りのみ」か「読み書き両方」のどちらかの権限を与えます。スイッチ変数の真偽で、付ける権限を逆向きの三項演算子で切り替えます。

HCL コードを見る（if-else をまねる）
# CloudWatchを「見るだけ」できる権限（読み取り専用ポリシー）
resource "aws_iam_policy" "cloudwatch_read_only" { # Describe*/Get*/List* のみ許可 }
# CloudWatchを「何でもできる」権限（フルアクセス）
resource "aws_iam_policy" "cloudwatch_full_access" { # cloudwatch:* を許可 }

# neoにフルアクセスを与えるかの切り替えスイッチ
variable "give_neo_cloudwatch_full_access" { type = bool }

# trueならフルアクセスの紐付けだけ作る（if句）
resource "aws_iam_user_policy_attachment" "neo_cloudwatch_full_access" {
  count = var.give_neo_cloudwatch_full_access ? 1 : 0   # trueなら1
  policy_arn = aws_iam_policy.cloudwatch_full_access.arn
}
# falseなら読み取りのみの紐付けだけ作る（else句）
resource "aws_iam_user_policy_attachment" "neo_cloudwatch_read_only" {
  count = var.give_neo_cloudwatch_full_access ? 0 : 1   # 真逆の0:1
  policy_arn = aws_iam_policy.cloudwatch_read_only.arn
}

作られたリソースの属性を安全に取り出す（concat ＋ one）

ハル
ハルでも、実際に付いたポリシーのARNを出力したいときは？ どっちが作られたか分からないのに。
棟梁
棟梁一番素朴なのは三項演算子で同じ条件をもう一度書く方法だが、これは少し危うい。将来 count の条件を変えると、出力の条件式も直し忘れて、存在しない番号の建物を見ようとしてエラーになる恐れがある。
ハル
ハルじゃあ、もっと安全な方法は？
棟梁
棟梁concat（連結）と one（1つ取り出し）を使う。if-elseだと片方が空・片方が1個になるから、つなげると必ず1個の一覧になり、one がその中身を返してくれる。条件分岐を変えても壊れない。

2つの紐付けを連結し、1つだけある要素を取り出します（one は0個ならnull、1個ならその要素、複数ならエラー）。

HCL コードを見る（三項演算子版と concat+one 版）
# 素朴な方法：三項演算子で同じ条件を再度書く（条件変更に弱い）
output "neo_cloudwatch_policy_arn" {
  value = (
    var.give_neo_cloudwatch_full_access
    ? aws_iam_user_policy_attachment.neo_cloudwatch_full_access[0].policy_arn
    : aws_iam_user_policy_attachment.neo_cloudwatch_read_only[0].policy_arn
  )
}

# 安全な方法：連結して1つだけある要素を取り出す（条件変更に強い）
output "neo_cloudwatch_policy_arn" {
  value = one(concat(
    aws_iam_user_policy_attachment.neo_cloudwatch_full_access[*].policy_arn,
    aws_iam_user_policy_attachment.neo_cloudwatch_read_only[*].policy_arn
  ))
}

count とビルトイン関数でif-elseをまねるのはハックですが、ほぼ問題なく動き、複雑さをユーザから隠してクリーンなAPIを提供できます。

💡 なぜこれが必要か / これを知ると何ができるか

  • 環境ごとに「この設備を付ける／付けない」を1枚の設計図で切り替えられる。
  • if-elseで「読み取りのみ／読み書き」のような排他的な選択を表現できる。
  • concat＋oneで、条件変更に強い安全な出力が書ける。

📌 この項のまとめ

  • count = 条件 ? 1 : 0でif文。
  • もう片方を? 0 : 1にすればif-else。
  • 三項演算子の出力は条件変更に弱い（直し忘れリスク）。
  • concat（連結）＋one（1つ取り出し）で安全に属性を取得。
  • oneは0個→null、1個→その要素、複数→エラー。
5.2.2

for_each と for を使った条件分岐

空集合なら作らない＋for式のifでフィルタ

要するに：for_eachに空集合を渡すと作られず、中身があると作られる。for式のifでフィルタして条件分岐できる。ただし単純な作る／作らないはcountのほうが簡単。

🏗️ たとえ話：注文書が空なら工事しない

for_each は「注文書（一覧）」を見て工事する道具。注文書が空っぽなら何も作らず、中身があればその分だけ作る。さらに for 式の if で「Nameの名札は既に付いてるから注文書から除外」と注文を絞り込んでから渡せます。

ハル
ハルfor_each でも条件分岐できるんですか？
棟梁
棟梁できる。for_each に空の集合を渡せば何も作られない。空じゃなければ作られる。問題は「どうやって集合を空にするか」だが、ここで for 式と組み合わせるんだ。

タグ設定の dynamic ブロックは、var.custom_tags が空なら何も作りません（=すでに条件分岐）。さらに for 式の if で「Name」キーを除外し、値を大文字化してから渡します。

HCL コードを見る（for式のifでフィルタ）
# 空なら何も作られない（=すでに条件分岐になっている）
dynamic "tag" {
  for_each = var.custom_tags
  content { ... }
}

# 値を大文字化しつつ、キーが「Name」の要素を取り除いてからタグを作る
dynamic "tag" {
  for_each = {
    for key, value in var.custom_tags:
    key => upper(value)            # ① 値を大文字に変換
    if key != "Name"               # ② キーが Name のものは除外
  }
  content {
    key   = tag.key
    value = tag.value
    propagate_at_launch = true
  }
}

for 式の if でフィルタすることで任意の条件分岐ができます（ここではモジュールが既に Name タグを設定しているため重複を防いでいます）。

ハル
ハル結局、count と for_each、条件分岐ではどっちを使えば？
棟梁
棟梁コピーを複数作るならほぼ常に for_each。でも「作るか作らないか」の単純な条件分岐は、count を0か1にするほうが単純だ。だから僕のおすすめは「条件付きで作るかどうかは count、それ以外のループや条件分岐は for_each」だよ。
やりたいことおすすめの道具
作る／作らないの単純な条件分岐count（? 1 : 0）
コピーを複数作るfor_each
小部屋を条件付きで作る・絞り込むfor_each ＋ for 式の if

💡 なぜこれが必要か / これを知ると何ができるか

  • for_each＋forのifで、複雑な条件付きのリソース・小部屋生成ができる。
  • countとfor_eachの使い分け方針を持てる（作る/作らない＝count、それ以外＝for_each）。

📌 この項のまとめ

  • for_eachに空集合→何も作らない、非空→作る。
  • for式のifでフィルタして条件分岐。
  • 値の加工（大文字化など）も同時にできる。
  • 使い分け：条件付き作成はcount、その他のループ・条件分岐はfor_each。
5.2.3

if 文字列ディレクティブを使った条件分岐

末尾の余計なコンマを消す＋チルダで空白除去

要するに：%{ if ... }...%{ endif }で文字列内の分岐ができ、forの末尾コンマ問題を解決できる。チルダ~で余計な空白を除き、elseで偽のときの表示も指定できる。

🏗️ たとえ話：看板の最後だけ区切りを変える

前節の住人名簿の看板は、最後の名前の後ろにも余計なコンマが残っていました。%{ if ... } を使うと「最後の住人じゃなければコンマを付ける」と指示でき、末尾のコンマが消えます。さらにチルダ ~ で改行の余白を削り、else で「最後だけはコンマでなくピリオド」のような仕上げもできます。

ハル
ハルさっき後回しにした、文字列の余計なコンマ問題！ if 文字列ディレクティブで直すんですよね。
棟梁
棟梁そう。%{ if 条件 }真のとき表示%{ endif } だ。「最後の要素じゃなければコンマを付ける」とすれば、末尾の余計なコンマが消える。

最後の名前以外にだけコンマを付けます。読みやすくするためコードをヒアドキュメントに入れますが、今度は余計な空白と改行が増えます。

HCL コードと結果を見る（if で末尾コンマを消す／空白が増える）
# 一般形：CONDITIONがtrueのときだけTRUEVALを表示
%{ if <CONDITION> }<TRUEVAL>%{ endif }

# 最後の名前以外にだけコンマとスペースを付ける
output "for_directive_index_if" {
  value = <<EOF
%{ for i, name in var.names }
  ${name}%{ if i < length(var.names) - 1 }, %{ endif }
%{ endfor }
EOF
}
# 結果：コンマは消えたが、余計な空白と改行が増えてしまった
ハル
ハルあれ、コンマは消えたけど、今度は変な空白と改行だらけです！
棟梁
棟梁ヒアドキュメントの中の空白は全部出力される。そこでチルダ（~）をディレクティブに付ける。チルダの前後の空白が削られるよ。
ハル
ハルifだけじゃなく、elseも付けられますか？
棟梁
棟梁付けられる。%{ if 条件 }真%{ else }偽%{ endif } だ。たとえば最後の要素だけコンマじゃなくピリオドを付けられる。

チルダで空白を削ってきれいに1行にし、else で「途中はコンマ、最後だけピリオド」にします。

HCL コードと結果を見る（チルダ＋else で仕上げる）
# チルダ（~）で前後の余計な空白を削り、きれいに1行にする
output "for_directive_index_if_strip" {
  value = <<EOF
%{~ for i, name in var.names ~}
${name}%{ if i < length(var.names) - 1 }, %{ endif }
%{~ endfor ~}
EOF
}
# 結果: "neo, trinity, morpheus"

# else付き一般形：CONDITIONがfalseのときはFALSEVALを表示
%{ if <CONDITION> }<TRUEVAL>%{ else }<FALSEVAL>%{ endif }

# 途中はコンマ、最後だけピリオドにする
output "for_directive_index_if_else_strip" {
  value = <<EOF
%{~ for i, name in var.names ~}
${name}%{ if i < length(var.names) - 1 }, %{ else }.%{ endif }
%{~ endfor ~}
EOF
}
# 結果: "neo, trinity, morpheus."

💡 なぜこれが必要か / これを知ると何ができるか

  • 一覧から「きれいに整形された文字列」（区切りや末尾記号を正しく付けた文）を生成できる。
  • ヒアドキュメントとチルダで、読みやすさと出力の整形を両立できる。

📌 この項のまとめ

  • %{ if 条件 }真%{ endif }で文字列内分岐。
  • 末尾の余計なコンマを除去できる。
  • ヒアドキュメント（<<EOF ... EOF）で複数行を読みやすく。
  • チルダ~で前後の空白を除去。
  • %{ else }で偽のときの表示を指定。

ゼロダウンタイムデプロイ

お客さんを困らせず、住みながら建て替える

要するに：nameを起動設定に依存させ、create_before_destroy＋min_elb_capacityを使うと、新ASGを先に建てて合格を待ってから旧ASGを壊すので、無停止で建て替えられる。失敗時は自動で巻き戻る。

🏗️ たとえ話：住みながらの無停止リフォーム

普通は古い棟を壊してから新しい棟を建てますが、それだと壊してから建つまでの間、お客さんが住む家がなくなります。そこで先に新しい棟を建て、入居の準備（ヘルスチェック合格）が整ってから、古い棟を取り壊す。これが「壊す前に作る」=create_before_destroy。受付係（ALB）は常に住める棟へお客さんを案内できるので、一瞬も止まりません。

ハル
ハルいよいよ「お客さんを困らせずに建て替える」ですね。住みながらのリフォームってことですか？
棟梁
棟梁まさにそう。鍵は「先に新しい棟を建ててから、古い棟を壊す」順番だ。それを実現するのが create_before_destroy ライフサイクルだよ。

AMIと表示テキストを変数で受け取れるようにし、起動設定に「壊す前に作る」印を付けます。

HCL コードを見る（変数と起動設定の create_before_destroy）
# サーバの元になるイメージ（AMI）と表示テキストの変数
variable "ami"         { type = string; default = "ami-0fb653ca2d3203ac1" }
variable "server_text" { type = string; default = "Hello, World" }

# サーバの起動設定。イメージと表示テキストを変数から受け取る
resource "aws_launch_configuration" "example" {
  image_id        = var.ami                          # ① 元イメージ
  instance_type   = var.instance_type
  user_data = templatefile("${path.module}/user-data.sh", {
    server_port = var.server_port
    server_text = var.server_text                    # ② 表示テキストを埋め込む
  })
  lifecycle {
    create_before_destroy = true                     # ③ 削除より先に作成する印
  }
}

ASG が新インスタンスを起動しない問題と3つの設定

ハル
ハル起動設定が新しくなって、ASGもそれを参照し直すんですよね。これで完了？
棟梁
棟梁それがね、ASGは参照を変えただけでは新しいサーバを起動しない。古いサーバが動いたまま。新インスタンスをデプロイさせるには、ASG自体を「置き換え」させる必要がある。そこで3つの設定を使う。Paul Hinzeさんから教わったテクニックだ。
1

ASGの name を起動設定の名前に依存させる

起動設定が変わると名前が変わり、ASGの名前も変わるので、ASGの置き換えが強制される。

2

ASGに create_before_destroy = true

古いASGを消す前に、新しいASGを先に作る。

3

min_elb_capacity を min_size に設定

新ASGで最低その台数がヘルスチェックを通るまで、古いASGの削除開始を待たせる。

「先に新棟を建て、ヘルスチェック合格を待ってから旧棟を壊す」設定にしたASGです。

HCL コードを見る（無停止デプロイ用のASG）
resource "aws_autoscaling_group" "example" {
  # 起動設定の名前に依存させ、置き換えられたらASGも置き換える
  name = "${var.cluster_name}-${aws_launch_configuration.example.name}"  # ① 名前を依存
  launch_configuration = aws_launch_configuration.example.name
  health_check_type    = "ELB"
  min_size = var.min_size
  max_size = var.max_size

  # 最低この数がヘルスチェックをパスするまで待つ
  min_elb_capacity = var.min_size                  # ② 合格台数を待つ

  lifecycle {
    create_before_destroy = true                   # ③ 削除より先に作成
  }
  tag { key = "Name"; value = var.cluster_name; propagate_at_launch = true }
  dynamic "tag" { # custom_tags を大文字化・Name除外して付与 }
}

5.4.1

ハル

ハル
ハルなんで plan で数が分からないとダメなんですか？
棟梁
棟梁plan は見積もりだろう？ 建てる前に棟数が決まってないと見積もれない。使えるのはハードコード値・変数・データソース・長さがplan時に分かるリストまで。「作ってみないと分からない計算結果」は使えないんだ。

固定の数（ハードコード）やデータソース（既存情報の参照）は問題なし。しかし別リソースの出力（ランダムな数など）に依存するとエラーになります。

HCL コードとエラーを見る
# OK：数が固定なのでplan時に分かる
resource "aws_instance" "example_1" {
  count = 3                # ① 固定の数
}

# OK：データソース（AZの数）。plan時に分かる
resource "aws_instance" "example_2" {
  count = length(data.aws_availability_zones.all.names)   # AZの数ぶん
}

# NG：別リソースの計算結果（plan時に未確定）に依存
resource "random_integer" "num_instances" { min = 1; max = 3 }
resource "aws_instance" "example_3" {
  count = random_integer.num_instances.result   # ① applyしないと分からない
}

# エラー：
# Error: Invalid count argument
# The "count" value depends on resource attributes that cannot be
# determined until apply, ...

💡 なぜこれが必要か / これを知ると何ができるか

  • 設計時に「なぜこのエラーが出るか」を理解し、構成を組み直せる。
  • 動的な数が必要なときは、依存元を先にapplyする（-target）等の回避策を選べる。

📌 この項のまとめ

  • count/for_eachはplan段階で計算できる必要がある。
  • 使える：ハードコード値・変数・データソース・長さがplan時に確定するリスト。
  • 使えない：他リソースの出力（apply後に決まる計算結果）。
  • 違反するとInvalid count argumentエラー。
5.4.2

ゼロダウンタイムデプロイの制限事項

小細工よりネイティブ機能を使う

要するに：create_before_destroy方式はAuto Scalingポリシーと相性が悪く、その場しのぎになりがち。AWSならinstance_refresh、ECSやKubernetesにもネイティブな無停止デプロイ機能があるので、あればそちらを使う。

🏗️ たとえ話：手作りの仮設足場より、純正の専用設備を使う

「壊す前に作る」方式は、いわば手作りの仮設足場。新棟を建て直すたびに台数が初期サイズ（min_size）にリセットされてしまうなど、相性問題が残ります。重要で複雑な工事は、メーカー（AWS）が用意した純正の専用設備（instance refresh）を使うほうが安定する、という教えです。

ハル
ハル無停止デプロイにも落とし穴が？
棟梁
棟梁2つある。1つめは「Auto Scalingポリシーと相性が悪い」こと。create_before_destroy で新ASGを建てると、サイズが min_size にリセットされてしまう。朝9時に2台→10台にするスケジュールがあっても、午前11時にデプロイすると新ASGは2台で起動し、翌朝9時までそのままになる。回避策は recurrence の調整や、現在の台数を取得して desired_capacity を設定するカスタムスクリプトなどだ。
ハル
ハル2つめは？
棟梁
棟梁もっと大きい。「重要で複雑な作業は、その場しのぎの組み合わせ技じゃなく、専用のネイティブ機能を使うべき」。実はAWSは今、インスタンスの更新（instance refresh）というネイティブな仕組みを提供してる。これを使えば create_before_destroy の小細工は要らない。

無停止デプロイ用の変更を元に戻し（name を普通に、create_before_destroy と min_elb_capacity を削除）、AWS純正の instance_refresh ブロックを使います。

HCL コードを見る（instance_refresh）
# AWSネイティブの「インスタンスの更新」で無停止デプロイするASG
resource "aws_autoscaling_group" "example" {
  name = var.cluster_name      # ① 起動設定に依存しない普通の名前
  health_check_type = "ELB"
  min_size = var.min_size
  max_size = var.max_size

  # ASGに変更を展開するのにインスタンスの更新を使用
  instance_refresh {
    strategy = "Rolling"                       # ② 1台ずつ順に入れ替える方式
    preferences {
      min_healthy_percentage = 50              # ③ 最低50%は健全に保つ
    }
  }
}
terraform plan の結果を見る（ASGは作り直されない）
  # aws_autoscaling_group.ex will be updated in-place（作り直さない）
  ~ launch_configuration = ... -> (known after apply)

  # aws_launch_configuration.ex must be replaced（起動設定だけ作り直し）
  ~ user_data = "bd7c0a6" -> "4919a13" # forces replacement

Plan: 1 to add, 1 to change, 1 to destroy.

apply はすぐ終わり、裏でAWSが1台ずつ入れ替えます（新を起動→ヘルスチェック→古いのを停止、を繰り返す）。流れの言葉スケッチです。

言葉スケッチを見る（図5-7 / 図5-8）
# 図5-7 インスタンスの更新が進行中（AWSが裏で1台ずつ入れ替える）
  [旧][旧] → [新][旧] → [新][新]（順次）

# 図5-8 インスタンスの更新が完了
  [新][新]
ハル
ハルインスタンスの更新、いいことばかりですか？
棟梁
棟梁ほぼね。AWSが全部管理し、設定もでき、エラー処理もしっかり、回避策もいらない。唯一の欠点は遅いことがある（2台で20分かかることも）くらい。それでもほとんどの無停止デプロイにはこっちのほうがずっと安定だ。
ハル
ハル他のサービスにもこういうネイティブ機能はあるんですか？
棟梁
棟梁あるよ。ECS（Dockerコンテナの管理サービス）なら deployment_maximum_percent と deployment_minimum_healthy_percent、Kubernetesなら strategy = "RollingUpdate" と rolling_update ブロック。使うリソースのドキュメントを確認して、ネイティブ機能があるならそれを使うのが鉄則だ。

💡 なぜこれが必要か / これを知ると何ができるか

  • 自前の組み合わせ技より、安定したネイティブ機能を選べる。
  • Auto Scalingポリシー併用時のサイズリセット問題を回避できる。
  • ECS・Kubernetesなど他サービスでも適切なデプロイ機能を選べる。

📌 この項のまとめ

  • 制限1：create_before_destroyはサイズをmin_sizeにリセットし、Auto Scalingポリシーと衝突。
  • 制限2：複雑な作業は専用のネイティブ機能を使うべき。
  • AWS ASGにはinstance_refresh（Rolling＋min_healthy_percentage）がある。
  • 欠点は速度（遅いことがある）だけで、安定性は高い。
  • ECSはdeployment_*_percent、KubernetesはRollingUpdateをネイティブ提供。
5.4.3

有効なプランも失敗することがある

plan はステートに載るものしか見ない

要するに：planはステートに載るものだけを見るので、手動で作った既存リソースと名前が衝突すると、有効に見えるプランがapplyで失敗する。Terraform管理に統一し、既存物はimportで取り込む。

🏗️ たとえ話：自分の台帳にない建物は「無い」ものと思ってしまう

Terraformは自分の管理台帳（ステート）に載っている建物しか把握していません。誰かが台帳に載せずに勝手に建てた家があると、Terraformは「その区画は空いてる」と見積もって（plan成功）、いざ建てに行くと「もう建ってますよ」と役所に弾かれて失敗します（apply失敗）。

ハル
ハルplan がOKだったのに apply で失敗するなんてこと、あるんですか？
棟梁
棟梁あるんだ。2章で手動で作ったのと同じ名前のIAMユーザを、コードで追加しようとするとどうなるか見てみよう。
ハル
ハルなんで plan では気づけなかったんですか？
棟梁
棟梁plan は「ステートファイル（管理台帳）に載っているものだけ」を見るからだ。手動で作ったユーザは台帳に載ってないから存在を知らない。「新しく作れる」と判断して、実際にAWSへ作りに行くと「もうあるよ」と弾かれるわけだ。

既存の利用者と同じ名前で追加しようとすると、plan は問題なさそうに見えますが、apply で「既に存在する」と失敗します。

HCL コードと plan/apply 結果を見る
# 既存の利用者と同じ名前で利用者を追加しようとする（衝突の元）
resource "aws_iam_user" "existing_user" {
  name = "yevgeniy.brikman"    # 自分のユーザ名に置き換える
}

# plan：一見、何も問題なさそう
  + name = "yevgeniy.brikman"
Plan: 1 to add, 0 to change, 0 to destroy.

# apply：同じ名前の利用者が既に存在するため失敗
Error: Error creating IAM User yevgeniy.brikman: EntityAlreadyExists:
User with name yevgeniy.brikman already exists.

2つの学び

棟梁
棟梁学びの1つめは「Terraformを使い始めたら、Terraformだけを使う」こと。手で変更すると、おかしなエラーの原因になるだけでなく、コードがインフラを正しく表さなくなって、Infrastructure as Code（IaC）の利点が消える。
ハル
ハルなるほど、設計図と実物がズレちゃうんですね。
棟梁
棟梁学びの2つめは「既存のインフラがあるなら import コマンドを使う」こと。Terraformを使う前から建っていた建物を、台帳に登録して管理下に入れる仕組みだ。
🔒

学び1：Terraformだけを使う

手動変更は避ける。コードが実物を正確に表さなくなり、IaCの利点を失う。

📥

学び2：既存物は import

terraform import で既存リソースをステートに追加する。

terraform import は2つの引数（設定内のアドレスと、リソース固有のID）を取ります。各リソースのドキュメント末尾にインポート方法が載っています。

シェルコマンドを見る（terraform import）
# 既存のIAMユーザをステートに取り込み、Terraform管理下に入れる
$ terraform import aws_iam_user.existing_user yevgeniy.brikman

これでTerraformはユーザの存在を認識し、以降の plan で作ろうとしなくなります。大量にある場合は terraformer や terracognita が便利。訳注：2023年6月のTerraform 1.5では、コマンドではなくコード内でインポートする import ブロックが導入されました。

💡 なぜこれが必要か / これを知ると何ができるか

  • 初心者が陥りがちな「planはOKなのにapplyで失敗」の正体を理解できる。
  • Terraform管理に統一することで、コードと実物のズレを防げる。
  • 既存インフラをimportで安全に管理下へ取り込める。

📌 この項のまとめ

  • planはステートファイルに載るものしか見ない。
  • 手動／CLIで作った管理外リソースと識別子が衝突するとapplyで失敗。
  • 学び1：使い始めたらTerraformだけで管理する。
  • 学び2：既存物はterraform import（または1.5のimportブロック）で取り込む。
  • 大量なら terraformer / terracognita を活用。
5.4.4

リファクタリングは難しい

「ただの名前変え」がシステム停止を招く

要するに：名前や識別子の変更は作り直し＝ダウンタイムを招く。常にplanで確認し、削除前に作成し、識別子変更はterraform state mvかmovedブロックでステートを更新する。イミュータブルなパラメータにも注意する。

🏗️ たとえ話：図面のラベルを書き換えただけで建物が取り壊される

図面上で建物のラベルを「instance」から「cluster_instance」に書き換えただけなのに、Terraformは「古い建物を取り壊して、まったく別の新しい建物を建てた」と解釈してしまいます。受付（ALB）やガードマン（セキュリティグループ）の建物が一瞬消えると、その間お客さんは入れず、全通信が拒否されます。台帳の付け替え（moved）を一緒にやれば、現物はそのままで済みます。

ハル
ハルリファクタリングって、動きを変えずに中身をきれいに整理することですよね。それが難しいんですか？
棟梁
棟梁普通のプログラミングなら気軽にできる。でもTerraformでは「外から見た振る舞い」が何かに細心の注意がいる。怠るとシステム停止を招くんだ。
棟梁
棟梁例えば cluster_name という変数の値を foo から bar に変えるとしよう。この値はセキュリティグループやALBの name で使われてる。name を変えると、Terraformは古いリソースを消して新しいのを作る。ALBなら新ALBが立つまで行き先がなくなり、セキュリティグループなら新しいのができるまでサーバが全通信を拒否する。
ハル
ハルじゃあ、リソースの識別子（名前ラベル）を分かりやすく変えるのは？ instance を cluster_instance にするとか。
棟梁
棟梁それも危険だ。ご想像のとおりダウンタイムが起きる。識別子変更・モジュール分割・既存リソースへの count/for_each の後付けでも同じ問題が起きる。

ALBやセキュリティグループの name や識別子を変えると作り直しになります。Terraformは識別子をクラウド側のIDに関連付けているためです。

HCL コードを見る（name と識別子の変更が作り直しを招く）
# ロードバランサ。name に cluster_name を使っている
resource "aws_lb" "example" {
  name = var.cluster_name   # ① ここを変えると作り直しになる
}

# 変更前：識別子は instance
resource "aws_security_group" "instance" { ... }
# 変更後：識別子を cluster_instance に（これがダウンタイムの原因）
resource "aws_security_group" "cluster_instance" { ... }

4つの学び

棟梁
棟梁学び1は「いつも plan を使う」。出力を見て、消すつもりのないリソースが消されようとしてたら事前に気づける。学び2は「削除する前に作成」。create_before_destroy が使えるかもしれないし、追加して apply→古いのを消して再 apply の2段階でもいい。
ハル
ハルでも、識別子を変えたいときはどうしても作り直しになっちゃうんですか？
棟梁
棟梁いや、ステート（台帳）のほうも一緒に更新すればいい。ただし台帳を手で書き換えるのは絶対ダメ。2つの正しい方法がある。terraform state mv コマンドと、コードに書く moved ブロックだ。

terraform state mv は台帳の関連付けを古い参照から新しい参照へ移します。識別子を更新してからこれを実行すると、plan が「変更なし」と表示します。

シェルコマンドを見る（terraform state mv）
# 一般形：台帳の関連付けを古い参照から新しい参照へ移す
terraform state mv <ORIGINAL_REFERENCE> <NEW_REFERENCE>

# identifier を instance から cluster_instance へ移す
$ terraform state mv \
  aws_security_group.instance \
  aws_security_group.cluster_instance
棟梁
棟梁ただ、手でCLIを実行する仕組みは問題を起こしやすい。多くのチームが使うモジュールをリファクタするとき、全チームに「state mv を忘れずに」と頼むのは危険だろう。
ハル
ハル全員が忘れずやるなんて無理ですよ……。
棟梁
棟梁そこでTerraform 1.1の moved ブロックだ。コードに書いておけば、apply 時にTerraformが自動でステートを更新する。リファクタするたびに書いておけばいい。

moved ブロックに from（元）と to（新）を書くと、apply 時に「移動」として検知し、作り直しはしません。

HCL コードと apply 結果を見る（moved ブロック）
# 「instance は cluster_instance に移した」と台帳更新を自動指示
moved {
  from = aws_security_group.instance         # ① 元の識別子
  to   = aws_security_group.cluster_instance # ② 新しい識別子
}

# apply 出力：移動として検知し、作り直しはしない
  # aws_security_group.instance has moved to
  # aws_security_group.cluster_instance
Plan: 0 to add, 0 to change, 0 to destroy.

yes を入力するとステートが自動更新され、リソースの追加・変更・削除は起きません。

ハル
ハル名前以外で、変えると作り直しになるものってありますか？
棟梁
棟梁あるよ。多くのパラメータはイミュータブルだ。変えようとすると古いリソースを消して作り直す。各リソースのドキュメントに書いてあるから、確認する癖をつけよう。やっぱり常に plan、そして create_before_destroy を使うべきか考えること。
1

いつも plan を使う

出力を確認し、意図しない削除に気づく。

2

削除する前に作成する

create_before_destroy、または「追加してapply→削除してapply」の2段階で。

3

ステートの変更は state mv か moved で

ステートファイルは手で更新せず、terraform state mv か moved ブロックを使う。

4

イミュータブルなパラメータに注意

変更不可のパラメータは変えると作り直し。ドキュメントを確認する。

💡 なぜこれが必要か / これを知ると何ができるか

  • 「ただの名前変え」がシステム停止を招く理由を理解できる。
  • movedブロックで、チーム全体のリファクタを安全・自動に行える。
  • イミュータブルなパラメータを見分け、事前に事故を防げる。

📌 この項のまとめ

  • nameや識別子の変更は古いリソースの削除＋新規作成＝ダウンタイム。
  • 学び1：いつもplanで意図しない削除に気づく。
  • 学び2：削除する前に作成する（create_before_destroyや2段階apply）。
  • 学び3：ステートは手で触らずterraform state mvかmovedブロックで更新。
  • 学び4：イミュータブルなパラメータは変更で作り直し。ドキュメント確認を習慣に。

読み終わったあと、自分の言葉で答えてみよう
第1問count と for_each の違い

同じリソースを複数コピーで作るとき、countよりfor_eachが好まれるのはなぜですか? 「途中の要素を削除したとき」に注目して説明してください。

✅ 解答例
countはリソースを番号（インデックス）で並べて管理するため、列の途中を削除すると後ろの要素が繰り上がり、Terraformはそれを「中身の入れ替え＋末尾削除」と誤解して、削除した要素以降を全部作り直してしまいます。一方for_eachは名前（キー）で管理するので、途中の1つを消しても他はずれず、その要素だけがきれいに削除されます。
📝 採点ポイント
・countは番号（インデックス）で管理する点に触れている
・途中削除で後ろがずれて作り直しになると説明している
・for_eachは名前（キー）で管理し、対象だけ削除できると説明している
第2問count で if 文を作る方法

Terraformにはif文がありませんが、countを使って「条件が真のときだけリソースを作る」にはどう書きますか? 使う仕組みの名前も挙げてください。

✅ 解答例
三項演算子（条件式）を使い、count = 条件 ? 1 : 0と書きます。条件が真ならcountが1になってリソースが1つ作られ、偽なら0になって何も作られません。if-elseにしたいときは、もう一方のリソースにcount = 条件 ? 0 : 1と逆向きに書きます。
📝 採点ポイント
・三項演算子（? :）を使うと述べている
・count = 条件 ? 1 : 0の形を示している
・1なら作る・0なら作らない、を説明している
第3問ゼロダウンタイムデプロイの仕組み

create_before_destroyを使ったゼロダウンタイムデプロイで、ユーザにダウンタイムが起きないのはなぜですか? 流れを簡単に説明してください。

✅ 解答例
古いASGを壊す前に、新しいASGを先に作るからです。新ASGのサーバが起動してヘルスチェックに通り（min_elb_capacity台ぶん）、ロードバランサに登録されるまで待ってから、古いASGをロードバランサから外して停止します。この間つねにトラフィックをさばけるサーバが存在するので、ユーザから見て止まる瞬間がありません。
📝 採点ポイント
・古いものを壊す前に新しいものを作る（順序）に触れている
・ヘルスチェック通過やmin_elb_capacityでの待機に触れている
・常に稼働サーバがあるためダウンタイムが無い、と結論づけている
第4問有効なプランが失敗する理由

terraform planは成功したのにapplyで失敗することがあります。なぜそんなことが起きるのですか? また、それを防ぐにはどうすればよいですか?

✅ 解答例
planはステートファイルに載っているリソースしか見ないため、手動やCLIで作った管理外のリソースを知りません。そのため同じ名前のリソースを作ろうとするプランが有効に見えても、実際にクラウドへ作りに行くと名前が衝突して失敗します。防ぐには、使い始めたらTerraformだけで管理し、既存リソースはterraform import（またはimportブロック）でステートに取り込みます。
📝 採点ポイント
・planはステートに載るものしか見ないと説明している
・管理外リソースとの識別子の衝突が原因と述べている
・importでの取り込みやTerraform一本化を対策に挙げている
第5問moved ブロックの役割

リソースの識別子（例：instance→cluster_instance）をリネームするときにmovedブロックを使うと、なぜダウンタイムを防げるのですか?

✅ 解答例
識別子をただ変えるだけだと、Terraformは古いリソースを削除して新しいリソースを作ろうとし、その間サービスが止まります。movedブロックにfrom（元の識別子）とto（新しい識別子）を書いておくと、Terraformは「同じリソースを別名に移しただけ」と理解してステートの関連付けを更新するだけになり、実際のリソースは作り直されません。terraform state mvを手で実行するのと同じことをコードで自動化でき、チーム全員の実行忘れも防げます。
📝 採点ポイント
・識別子変更は本来、削除＋新規作成になると説明している
・movedブロックがステートの関連付けを更新するだけだと述べている
・from/toやstate mvとの関係、実行忘れ防止に触れている
