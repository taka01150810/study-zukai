インフラ infrastructure

サーバ・データベース・ネットワークなど、ソフトを動かす土台のこと。街でいう道路・水道・土地。

IaC Infrastructure as Code

インフラを手作業ではなく「設計図（コード）」として書いて建てる考え方。手の勘を図面に落とす。

DevOps デブオプス

作る人（Dev）と土台を守る人（Ops）が協力し、ソフトを効率よく届けるための考え方の集まり。

プロビジョニング provisioning

土地を造成してサーバそのものや設備を用意すること。Terraformの担当。街の不動産デベロッパー。

設定管理 configuration管理

すでに建ったサーバの中身を整える道具。Chef/Puppet/Ansible。建った家の内装職人。

サーバテンプレート server templating

全部入りの「型（イメージ）」を作って量産する道具。Docker/Packer/Vagrant。モデルハウスの型。

オーケストレーション orchestration

たくさんのサーバ/コンテナを束ねて指揮する道具。Kubernetes。大勢の職人を束ねる総監督。

クラウド cloud

AWS・Azure・GCPなど、土地（サーバ）を貸してくれる大地主。自前で機械を持たずに借りる。

プロバイダ provider

AWSなどクラウドの提供業者。Terraformはその「入口（API）」を代わりに呼ぶ。

冪等性 idempotence

何度実行しても結果が同じになる性質。何度押しても安全なボタン。

設定ドリフト configuration drift

サーバの設定が一台ずつ少しずつズレていくこと。改築を重ねて家がバラバラになる。

イミュータブル immutable

一度建てたら変えない方式。更新は新しい型で建て直す。改築せず建て替え。

宣言型 declarative

「完成形」だけを書き、やり方は道具に任せる。完成写真を渡す。Terraform流。

手続き型 procedural

「一手一手の手順」を書く。料理レシピのように手順を並べる。Chef/Ansible流。

マスタ／エージェント master / agent

全体を仕切る親方サーバと、各サーバに常駐する代理人。Terraformはどちらも要らない（マスタレス・エージェントレス）。

API エーピーアイ

クラウドへの「注文の入口」。Terraformはここに発注して土台を建ててもらう。

📦

ソフトウェアは「届けて」はじめて完成建てて終わりではなく、住む人に引き渡すまでが仕事

要するに：ソフトウェアは作るだけでなく、お客さんが使える状態にして「届ける」までが仕事。Terraformはその「届ける」工程で土台を作る道具。

ハル
弟子・ハル棟梁、僕、家を建てる勉強をしに来たんですけど、ここってコンピュータの会社なんですよね。なんで建築のたとえばっかりなんですか？
棟梁
師匠・棟梁ハハ、いい入りだね。コンピュータの土台づくりは街づくりや建築にそっくりなんだ。家は「設計して終わり」でも「組み上げて終わり」でもない。住む人が安心して暮らせるよう引き渡してはじめて完成だ。
ハル
弟子・ハルえっ、建ったら完成じゃないんですか？
棟梁
師匠・棟梁そこが落とし穴だ。ソフトでいうと、コードが自分のパソコンで動いても、テストが通っても、上司が「出していいよ」と言っても、まだ完成じゃない。お客さんが実際に使える状態にして「届ける」までが仕事。これをソフトウェアデリバリと言う。
棟梁
師匠・棟梁本番のサーバで動かしたり、人が殺到しても倒れないよう補強したり、攻撃者から守ったり。その"全部の作業"がデリバリ。Terraformはその中の「土台や街そのものを作る部分」を受け持つんだ。

🏗️ たとえ話：引き渡しまでが大工の仕事

家は柱を組んだ瞬間が完成ではありません。雨漏りしないか、地震に耐えるか、泥棒に入られないかを整え、住む人が安心して暮らせる状態にして鍵を渡してはじめて仕事が終わります。Terraformは、その家を建てる土地の造成や基礎工事を引き受ける道具です。

✅ この項のまとめ

  • コードが手元で動いても、テストが通っても完成ではない。
  • お客さんが使える状態にして届けて、はじめて完成。
  • 届ける作業＝本番で動かす・障害に強くする・攻撃から守る、など全部。
  • Terraformは届ける工程の中で土台（インフラ）を建てる道具。
1.1

DevOpsとは何か作る職人と土台を守る職人が、協力するようになった話

要するに：DevOpsは「DevとOpsが協力してソフトを届けるのを効率化する考え方の集まり」。その柱の一つ「自動化」が、コードで土台を管理するという発想につながる。

昔の現場：DevとOpsを分けたら、成長すると壊れた

ハル
弟子・ハル「DevOps」って言葉、全然わかりません！
棟梁
師匠・棟梁昔はコンピュータの会社を作るのに、自分でハードウェア（物理の機械）も用意した。棚を組んで機械を置き、ケーブルを繋ぎ、空調や予備電源まで作る。土地を買って基礎を打つ土木作業さ。
棟梁
師匠・棟梁そこで人を二手に分けた。中身を作る開発者（Dev）と、機械や土台を見る運用者（Ops）だ。家具職人と、土地と基礎を守る土方さんを分けたようなものだ。
ハル
弟子・ハル役割を分けたら、うまくいきそうですけど？
棟梁
師匠・棟梁しばらくは回るが、会社が大きくなると壊れる。Devが作ったものを「壁の向こうに投げる」ようにOpsへ渡し、Opsが手作業で据え付ける。手作業だからサーバが増えるほど遅く、苦しく、結果が読めない。人だからミスもする。
棟梁
師匠・棟梁すると一台ごとに少しずつ違う機械が生まれる。雪の結晶になぞらえてスノーフレークサーバ、そのズレを設定ドリフトと呼ぶ。
ハル
弟子・ハル一軒ずつ微妙に違う家ができちゃう、みたいな？
棟梁
師匠・棟梁その通り。不具合が増え、開発者は「俺の作業場では動いたんだけどなあ」と肩をすくめる。障害や止まる時間が増え、疲れたOpsは引き渡しを週1、月1、半年に1回と減らす。半年ぶりの引き渡しでは図面がぶつかり合う大混乱（マージコンフリクト）になり、組織がタコツボ（サイロ化）になる。

🏗️ たとえ話：投げ渡しの現場

設計職人が図面を「壁の向こうに放り投げ」、土方さんが手作業で基礎を打つ。サーバが増えるほど手が回らず、一軒ごとに微妙に違う家（スノーフレークサーバ）が建ち、改修を重ねるほどズレ（設定ドリフト）が広がる。やがて誰も全体を把握できなくなり、現場は崩壊します。

弟子・ハルじゃあDevとOpsの区別もあいまいに？
棟梁

弟子・ハルDevOpsって、結局どういう意味？役職？技術の名前？
棟梁
師匠・棟梁どれでもない。進め方・考え方・技の集まりだ。この本ではこう言う――「DevOpsの目的は、ソフトを届けるのを今までよりずっと効率的にすること」。図面を絶えず少しずつ合わせ続け、1日に何度でも引き渡せるようにし、自分で立ち直る丈夫な建物を作る。

1.2

Infrastructure as Codeとは何か手の勘を、誰でも同じに建てられる設計図に

要するに：IaC（アイエーシー）は「インフラを手作業ではなくコード（設計図）として書いて建てる」考え方。その道具は5つの仲間に分かれる。

ハル
弟子・ハルインフラストラクチャ アズ コード、長いです。要するに何ですか？
棟梁
師匠・棟梁インフラを定義し・建て・更新し・取り壊すために、コードを書いて実行する考え方だ。相手が物理の機械でも、全作業を「ソフトとして扱う」と頭を切り替える。サーバ・DB・ネットワーク・設定・説明書・テスト・手順まで、ほぼ全部をコードにできる。
ハル
弟子・ハル大工さんが、家を建てる手順を全部"設計図"に落とし込むみたいな？
棟梁
師匠・棟梁まさに。手の勘を、誰が見ても同じに建てられる図面にする。その図面を書く道具は、大きく5つの仲間に分かれる。一つずつ見ていこう。

🏗️ たとえ話：勘の棟梁から、図面の工房へ

昔の名棟梁は頭の中の勘で家を建てました。でもその人が休めば工事は止まり、弟子は同じ家を建てられません。図面（コード）にしておけば、誰が見ても同じ家を、何度でも、間違いなく建てられます。IaCとは「工房のすべてを図面化する」ことです。

IaCツールの5つの仲間

1

アドホックなスクリプト

その場限りの口頭メモを命令文にしたもの（Bash等）。

2

設定管理ツール

建った家の中を整える内装職人（Chef/Puppet/Ansible）。

3

サーバテンプレーティングツール

モデルハウスの型を作って量産（Docker/Packer/Vagrant）。

4

オーケストレーションツール

大勢の職人を束ねる総監督（Kubernetes等）。

5

プロビジョニングツール

土地を造成して土台を作る不動産デベロッパー（Terraform/CloudFormation/Heat）。

✅ この項のまとめ

  • IaCはインフラを定義・構築・更新・削除するためのコードを書く考え方。
  • サーバからテスト・手順書までほぼ全部をコードにできる。
  • 道具は5カテゴリ：アドホックなスクリプト／設定管理／サーバテンプレーティング／オーケストレーション／プロビジョニング。
1.2.1

アドホックなスクリプトその場限りの口頭メモを、命令文にしただけ

要するに：アドホックなスクリプトは汎用言語で書く"その場限りの台本"。小さな一回きりには最適だが、インフラ全体の管理には不向きで荒れやすい。

ハル
弟子・ハル「アドホック」って何ですか？
棟梁
師匠・棟梁アドホック＝その場限り、間に合わせ。今まで手でやった作業を細かい手順に分け、好きな言語（Bash・Ruby・Python等）で書いて実行するだけ。手書きの作業メモをそのまま命令文にしたものだ。
棟梁
師匠・棟梁いいところは、広く使われる自由な言語でどうとでも書けること。悪いところも同じで、どうとでも書けてしまうこと。8行なら良いが、土台全部をこの台本で管理し始めると、ほどけないスパゲッティになる。

↓ このコードは、Webサーバを手順そのままに自動化した「間に合わせの台本」（PHPとApacheを入れて起動するだけ）。読まなくてOK。

setup-webserver.sh（Bash）を見る
# Web サーバを手作業の手順そのままに自動化した間に合わせの台本
#!/bin/bash
set -e
# ① 入れられるソフトの一覧を最新にする
sudo apt-get update
# ② PHP と Apache（Webサーバのソフト）を入れる
sudo apt-get install -y php apache2
# ③ Git の保管庫からアプリのコードを取ってくる
sudo git clone https://github.com/brikis98/php-app.git /var/www/html/app
# ④ Apache を起動する
sudo service apache2 start

🏗️ たとえ話：付箋に書いた作業メモ

「板を切る→釘を打つ→ニスを塗る」と付箋に書いた即席メモ。一回きりの小さな修理には最高です。でも家全体の建築をぜんぶ付箋でやろうとすると、付箋が山のように増え、誰も全体を追えなくなります。

✅ この項のまとめ

  • アドホックなスクリプトは汎用言語（Bash等）で手順を書くその場限りの台本。
  • 長所も短所も「どうとでも書けてしまう」点にある。
  • 専用ツールは分かりやすい入口と一定の型を提供する。
  • 小規模な一回きりには最適、インフラ全体の管理には不向き。
1.2.2

設定管理ツール建った家の中を整える、規律ある内装職人

要するに：設定管理ツール（Chef/Puppet/Ansible）は、既存サーバにソフトを入れて整える内装職人。書き方の規約・冪等性・多数サーバへの配布という利点を持つ。

ハル
弟子・ハルChef、Puppet、Ansible。何をする道具ですか？
棟梁
師匠・棟梁もう建っている家の中に、家具や設備を据え付けて整える内装職人だ。さっきのBashと同じApacheの設定を、もっと規律正しく書ける。

↓ このYAMLはAnsibleに「Webサーバをこう整えてね」と頼む内装の指示書。読まなくてOK。

web-server.yml（Ansibleロール）を見る
# Ansible に Web サーバの整え方を頼む内装の指示書（ロール）
- name: apt-getのキャッシュを最新にする
  apt:
    update_cache: yes
- name: PHP を入れる
  apt:
    name: php
- name: Apache を入れる
  apt:
    name: apache2
- name: 保管庫からコードを取ってくる

イメージの2種類：仮想マシン と コンテナ

🏠

仮想マシン（VM）

ハイパーバイザでCPU・メモリ・ディスク・ネットワークまで丸ごと真似る。独立した一軒家。完全に切り離せて安全だが、丸ごと作るぶん重い（起動も遅い）。Packer/Vagrantで定義。

VMware / VirtualBox
🚪

コンテナ

OSのユーザスペースだけを真似た軽い小部屋。建物の中を壁で仕切った貸し部屋。ミリ秒で起動・無駄が少ないが、カーネルを共有するので切り離しは弱い。Dockerで定義。

Docker

📌 補足：カーネルスペースとユーザスペース

  • 普通はコンテナの切り離しで十分だが、悪意あるかもしれない他人のコードを動かす場合は、VM並みの強い切り離しが要ることもある。（補足：CoreOS rktは2020年に終了）

✅ この項のまとめ

  • TerraformはHashiCorp製・Go言語・オープンソースの一個の実行ファイル。
  • Terraform設定（設計図）を読み、プロバイダのAPIを代理で呼んで建てる。
  • 既存のAPIキーを使え、PC以外の設備は不要。
  • terraform applyで反映、変更も設定の書き換え＋applyで行う。
  • 透過的ポータビリティ（別クラウドへ丸ごと移植）は現実には不可、プロバイダ固有コードを書く方針。
1.5

Terraformと他のIaCツールとはどう違うのか道具選びは、機能一覧ではなく「兼ね合い」で決める

要するに：道具選びは機能一覧では決められない。トレードオフ（あちらを立てればこちらが立たず）と優先順位で、複数の観点を比べて選ぶ。

ハル
弟子・ハルIaCが素晴らしいのは分かりました。でも道具がたくさんあって、どれを選べば…。
棟梁
師匠・棟梁そこが一番難しい。世間の比較はただの機能一覧で「どれでも成功できそう」に見える。「PHPでもCでもWebは作れる」と言うようなもので、技術的には正しくても判断材料が抜けている。これからTerraform・Chef・Puppet・Ansible・Pulumi・CloudFormation・Heatをトレードオフで比べる（Docker/Packer/Kubernetesは組み合わせ用途なので除外）。

🏗️ たとえ話：道具箱から一本を選ぶ

カタログの「機能一覧」だけ見れば、どの工具でも家は建ちます。でも実際の選択は「軽さか頑丈さか」「手に馴染むか最新か」「仲間が使い慣れているか」といった兼ね合いと優先順位で決まります。棟梁は10個のものさしで、自分の工房（Gruntwork）がなぜTerraformを選んだかを語っていきます。

✅ この項のまとめ

  • IaCツールは役割が重なり、機能一覧だけでは選べない。
  • 選択はトレードオフと優先順位の問題。
  • 比較対象はTerraform/Chef/Puppet/Ansible/Pulumi/CloudFormation/Heat（Docker等は除外）。
  • 観点は全10項目（このあと一つずつ）。
1.5.1

設定管理ツールか、プロビジョニングツールか

要するに：境界はあいまい。用途で選び、サーバテンプレートを使うならプロビジョニング、使わないなら両者の組み合わせも有効。

ハル
弟子・ハル設定管理とプロビジョニング、きっちり分かれるんですか？
棟梁
師匠・棟梁境界はあいまいだ。Ansibleでもサーバを建てられるし、Terraformからサーバ内の設定スクリプトも走らせられる。サーバテンプレートを使っているなら設定の仕事は済んでいるので、造成するプロビジョニングが最適。使っていないなら、造成はTerraform・中の設定はAnsible、という組み合わせもよく使う。

✅ この項のまとめ

  • Chef/Puppet/Ansibleは設定管理、CloudFormation/Terraform/Heatはプロビジョニング。
  • 境界はあいまいで、互いに相手の領分も少しはこなせる。
  • サーバテンプレートを使うならプロビジョニングが最適。
  • 使わないなら設定管理＋プロビジョニング（例：Terraform＋Ansible）の併用も有効。
1.5.2

ミュータブルなインフラか、イミュータブルなインフラか

要するに：設定管理ツールはその場で改築するミュータブルが基本、Terraform＋テンプレートは建て直すイミュータブルが基本。イミュータブルは設定ドリフトに強いが、毎回イメージを作る時間などの欠点もある。

🔨

ミュータブル（その場で改築）

Chef/Puppet/Ansibleの基本。既存サーバを更新し続けると改築履歴がバラバラになり、設定ドリフト・原因不明バグ・「テストでは動くのに本番で違う」が起きる＝スノーフレークサーバ。

🏚️➡️🏠

イミュータブル（建て直し）

Terraform＋テンプレートの基本。変更＝新イメージで新サーバを建て古いのを止める。ドリフトに強く、中身を把握しやすく、過去に戻しやすい。テストも効きやすい。

📌 公平に：イミュータブルの欠点

  • 小さな変更ごとにイメージを作って全サーバに配るのは時間がかかりすぎることがある。
  • 稼働後はディスク書き込みで多少のドリフトは出る（頻繁にデプロイしていれば問題にならない）。

✅ この項のまとめ

  • ミュータブル＝その場で改築（設定管理ツールの基本）、イミュータブル＝建て直し（Terraform＋テンプレートの基本）。
  • ミュータブルは改築履歴の差から設定ドリフト・再現性の低下を招く。
  • イミュータブルは把握・戻し・テストがしやすい。
  • イミュータブルの欠点はイメージ作成の時間と、稼働後のわずかなドリフト。
1.5.3

手続き型言語か、宣言型言語かこの章の山場。「10台→15台」で違いが効く

要するに：手続き型は手順を、宣言型は望む完成形を書く。宣言型は差分を道具が計算するので、状態の把握・再利用がしやすく、コードが小さく保てる。

棟梁
師匠・棟梁手続き型（Chef/Ansible）は「ある状態に至る一手一手の手順」を書く。宣言型（Terraform/CloudFormation/Puppet/Heat/Pulumi）は「最終的にこうあってほしい」状態だけを書く。料理でいえば、手続き型はレシピ、宣言型は完成写真だ。
📋

手続き型（Ansible）で10台

「ami の型でサーバを10台建てよ」と手順を書く。

Ansible（10台）を見る
- ec2:
    count: 10
    image: ami-0fb653ca2d3203ac1
    instance_type: t2.micro
🖼️

宣言型（Terraform）で10台

「amiの型のサーバが10台ある状態」を完成形として宣言。

Terraform（10台）を見る
resource "aws_instance" "example" {
  count         = 10
  ami           = "ami-0fb653ca2d3203ac1"
  instance_type = "t2.micro"
}

面白いのは「15台に増やしたいとき」

😵

手続き型は書き直し地獄

数を15で再実行すると新たに15台建ち、合計25台に！ だから今いくつあるか自分で把握し「あと5台だけ」と書き直す必要がある。

あと5台だけ建てる手順を見る
# 現状を踏まえて書き直す羽目に
- ec2:
    count: 5
    image: ami-0fb653ca2d3203ac1
    instance_type: t2.micro
😊

宣言型は数字を変えるだけ

countを10→15にするだけ。Terraformが「あと5台必要」と自分で気づく。

count を 15 にするだけ ＋ plan を見る
resource "aws_instance" "example" {
  count         = 15
  ami           = "ami-0fb653ca2d3203ac1"
  instance_type = "t2.micro"
}

# terraform plan で、変更前に「何が変わるか」を見られる
$ terraform plan
+ aws_instance.example[11..14] will be created ...
# 「5台を追加、変更0、削除0」
Plan: 5 to add, 0 to change, 0 to destroy.

バージョン変更（amiの差し替え）も、宣言型ならamiを書き換えるだけ。差分はTerraformが計算する。（補足：Ansibleにもタグで既存EC2を探す機能はあるが、履歴を考えて手作業でロジックを組むのは複雑。）

📌 手続き型の2つの弱点

  • 状態を完全に把握できない：テンプレを読むだけでは何が建ったか分からず、適用順まで知る必要がある（順番が違えば結果も違う）。
  • 再利用しにくい：現在の状態を考えに入れねばならず、状態は刻々と変わる。1週間前のコードはもう使えない＝肥大化・複雑化する。

🏗️ たとえ話：レシピ vs 完成写真

手続き型は「鍋に湯を沸かし、塩を入れ…」のレシピ。今すでに何皿できているかを自分で数えて手順を書き直さねばなりません。宣言型は「完成形はこの一皿」という写真を渡すだけ。今が何皿でも、料理人（Terraform）が差分を計算して完成形に揃えてくれます。

✅ この項のまとめ

  • 手続き型（Chef/Ansible）は手順を、宣言型（Terraform等）は望む状態を書く。
  • 手続き型は再実行で重複建設が起き、現状把握＋書き直しが必要。
  • 宣言型はcountやamiを書き換えるだけで差分を道具が計算する。
  • 手続き型の弱点は①状態を完全に把握できない②再利用しにくい＝肥大化。
  • 宣言型はコードが常に最新の完成形を表し、小さく再利用しやすい。
1.5.4

汎用言語かドメイン特化言語か

要するに：汎用言語はいろいろ使えて強力だが学ぶ量が多い。DSLは学びやすく簡潔で書き方が揃うが、できることは限られる。

棟梁
師匠・棟梁汎用言語（GPL）派はChef=Ruby、Pulumi=JS/TS/Python/Go/C#/Java。ドメイン特化言語（DSL）派はTerraform=HCL、Puppet=Puppet言語、Ansible/CloudFormation/Heat=YAML。万能工具と専用工具の違いだ。
🛠️

DSLの利点

①学習が容易（小さくシンプル）②明快で簡潔（同じことが短く書ける）③記述が揃いやすい（書き方が実質1通り）。

🧰

汎用言語の利点

①既知の言語を使える（新言語不要）②エコシステムが大きく成熟（IDE・ライブラリ・テスト道具）③強力（制御・テスト・抽象化・連携が得意）。

✅ この項のまとめ

  • 汎用言語（GPL）はChef=Ruby、Pulumi=JS/Python等。DSLはTerraform=HCL、Ansible等=YAML。
  • 境界は厳密でなく考えを助ける見取り図。
  • DSLの利点：学習が容易・明快で簡潔・記述が揃いやすい。
  • 汎用言語の利点：既知の言語を使える・エコシステムが大きい・強力。
1.5.5

マスタか、マスタレスか

要するに：ChefやPuppetは中央の親方（マスタサーバ）が基本で、便利だが余計な設備・保守・セキュリティの負担が増える。Terraform等はマスタレスで、既存のAPIキーやSSHキーで済む。

👑

マスタの利点

①状態を確認・管理する唯一の中央拠点（Web画面で現状が見やすい）②裏で動き続け設定を強制（手で変えてもドリフトを巻き戻す）。

💸

マスタの欠点

①余計なインフラ（マスタ用サーバ、時にクラスタ）②メンテナンス（保守・更新・バックアップ・監視・拡張）③セキュリティ（通信路・ポート・認証で攻撃面が増える）。

ChefやPuppetのマスタレス対応はまちまち（cronで定期的に最新を引き取る等）。Ansible/CloudFormation/Heat/Terraform/Pulumiは初期設定でマスタレス。TerraformはクラウドのAPIサーバがマスタとも言えるが追加管理は不要（既存APIキー）、AnsibleはSSHで直接つなぐ（既存SSHキー）。

✅ この項のまとめ

  • Chef/Puppetは初期設定でマスタサーバが必要。
  • マスタの利点：状態確認の中央拠点・設定の強制（ドリフトの巻き戻し）。
  • マスタの欠点：余計なインフラ・メンテナンス・セキュリティ面の拡大。
  • Ansible/CloudFormation/Heat/Terraform/Pulumiはマスタレスで追加設備不要。
1.5.6

エージェントか、エージェントレスか

要するに：ChefやPuppetは各サーバに代理人（エージェント）を常駐させるのが基本で、立ち上げ・保守・セキュリティの負担と故障モードが増える。Terraform等はクラウド既存の仕組みを使い、追加エージェント不要。

📌 エージェントの3つの負担

  • ブートストラップ：そもそも最初にサーバを用意してエージェントを入れるには？という鶏と卵の問題。
  • メンテナンス：定期更新・監視・再起動が要る。
  • セキュリティ：送信/受信ポートを開け、認証も要り、攻撃面が広がる。
ハル
弟子・ハル部品が増えると何が困るんですか？
棟梁
師匠・棟梁故障モード（故障の起き方）が増える。深夜3時の障害報告で、原因がアプリか、IaCコードか、クライアントか、マスタか、その間の通信か…と切り分けねばならない。Ansible/CloudFormation/Heat/Terraform/Pulumiは追加エージェント不要。クラウドが各サーバに入れている既存のエージェントやSSHデーモンを使うんだ。

✅ この項のまとめ

  • Chef/Puppetは各サーバにエージェントを常駐させる必要がある。
  • 欠点：ブートストラップ・メンテナンス・セキュリティ（ポートと認証）。
  • 部品が増えると故障モードが増え、障害の切り分けが難しくなる。
  • Terraform等はクラウド既存のエージェントやSSHを使い、追加エージェント不要。
1.5.7

有償か、無償か

要するに：CloudFormation/Heatは完全無償、他は無償版＋有償版。Terraform等の無償版は本番で十分使えるが、Pulumiは状態管理の都合で実質有償サービスが必要。有償サービスは自分の制御外という点に注意。

棟梁
師匠・棟梁CloudFormationとHeatは完全無償。Terraform/Chef/Puppet/Ansible/Pulumiは無償版と有償版がある。問いたいのは「無償版が絞られすぎて実質有償を使わざるを得ないか？」だ。有償は調べる価値があるが、自分でコントロールできない――倒産・買収（Chef/Puppet/Ansibleは経験済み）・値上げ（Pulumiは2021年に最大10倍も）・終了のリスクがある。
ハル
弟子・ハルなんでPulumiだけ実質有償なんですか？
棟梁
師匠・棟梁鍵は状態の管理だ。Pulumiは初期設定だと状態保管にPulumi Serviceを使う。障害復旧の節目記録・チームで使う時の並列ロック・暗号化が、Pulumi Serviceでしか使えないとされる。これ無しで複数人の本番運用は現実的でない。

✅ この項のまとめ

  • CloudFormation/Heatは完全無償、Terraform/Chef/Puppet/Ansible/Pulumiは無償＋有償。
  • Terraform等の無償版は本番運用に十分。
  • 有償サービスは制御外（倒産・買収・値上げ・終了のリスク）。
  • Pulumiは状態管理（チェックポイント・並列ロック・暗号化）の都合で実質Pulumi Serviceが必要。

1.5.10

複数のツールの組み合わせ一つに絞らず、適材適所で組む

要するに：一つに絞る必要はなく、強み弱みを見て複数を組み合わせるのが現実的。代表的な組み合わせが三つある。

1.5.10.1 プロビジョニング＋設定管理（Terraform＋Ansible）

土台すべて（VPC・サブネット・DB・ロードバランサ・サーバ）をTerraformで造成し、サーバ上のアプリをAnsibleで据え付ける。

言葉スケッチを見る
[Terraform] --造成--> [VPC / サブネット / DB / ロードバランサ / サーバ]
                                                          |
[Ansible]   --設定--> [サーバ上にアプリをデプロイ] <-------+
👍

利点

追加インフラ不要・組み合わせ方が豊富（タグで連携）・最初に取り組みやすい。

👎

欠点

Ansibleはミュータブル＋手続き型コードを大量に書くので、規模が大きくなると保守が難しい。

1.5.10.2 プロビジョニング＋サーバテンプレーティング（Terraform＋Packer）

PackerでアプリをVMイメージに固め、Terraformでそのサーバと土台を建てる。

言葉スケッチを見る
[Packer]    --型を作る--> [アプリ入り VM イメージ]
                                |
[Terraform] --建てる--> [この VM のサーバ + VPC / サブネット / DB / ロードバランサ]
👍

利点

追加インフラ不要・イミュータブルで保守しやすい・本書で多く扱う。

👎

欠点

①VMのビルド/デプロイが遅く試行錯誤が遅い②Terraform単体はデプロイ戦略に限界（ネイティブなブルーグリーン不可）。

1.5.10.3 プロビジョニング＋サーバテンプレーティング＋オーケストレーション（Terraform＋Packer＋Docker＋Kubernetes）

PackerでDocker＋Kubernetes入りVMイメージを作り、Terraformでクラスタと土台を造成し、Kubernetesでアプリを束ねて運用する。

言葉スケッチを見る
[Packer]     --型を作る--> [Docker + Kubernetes 入り VM イメージ]
                                |
[Terraform]  --建てる--> [VM のクラスタ + VPC / サブネット / DB / ロードバランサ]
                                |
[Kubernetes] --指揮--> [VM 群を束ねて Docker 化アプリを運用]
👍

利点

Dockerは速くテストしやすい・Kubernetesの内蔵機能（各種デプロイ・オートヒーリング・オートスケーリング）を全部使える。

👎

欠点

複雑さが増す（Kubernetesクラスタの運用負担・抽象化の層の増加）。具体例は7章。

🏗️ たとえ話：適材適所で街を建てる

型はPacker、土地の造成はTerraform、職人の指揮はKubernetes、建物の内装はAnsible。一本の万能工具で全部やろうとせず、それぞれの得意な道具を組み合わせて、一つの街を建てます。

✅ この項のまとめ

  • 現実は複数ツールの組み合わせが普通。各ツールの強み弱みを見て適材適所で選ぶ。
  • ①Terraform＋Ansible：始めやすいが規模拡大で保守困難。
  • ②Terraform＋Packer：イミュータブルで保守しやすいがビルドが遅くデプロイ戦略に限界。
  • ③Terraform＋Packer＋Docker＋Kubernetes：機能豊富だが複雑（7章で具体例）。

章末の理解度チェック

読み終わったら、自分の言葉で答えてみてください。

第1問DevOpsとIaC

DevOpsとは何で、その中の「自動化」がなぜInfrastructure as Code（IaC）につながるのか、自分の言葉で説明してください。

✅ 解答例
DevOpsは、開発する人（Dev）と土台を運用する人（Ops）が協力して、ソフトを今までよりずっと効率的に届けるための考え方の集まりです（役職や特定の技術ではない）。その柱の一つが「自動化」で、手作業でクリックやコマンドを打つ代わりにコードで土台を管理しようという発想になり、それがインフラをコードとして書くIaCにつながります。
📝 採点ポイント
□ DevOpsは役職や技術ではなく考え方の集まりだと言えている ／ □ 目的が「ソフトを効率的に届けること」だと触れている ／ □ 自動化＝コードで管理、がIaCにつながると説明できている
第2問5つの道具カテゴリ

IaCツールの5つのカテゴリを挙げ、Terraformがどれに当たるかを説明してください。設定管理とプロビジョニングの違いにも触れてください。

✅ 解答例
5つは、アドホックなスクリプト・設定管理・サーバテンプレーティング・オーケストレーション・プロビジョニングです。Terraformはプロビジョニングに当たります。設定管理（Chef/Puppet/Ansible）は既にあるサーバの中身を整える道具、プロビジョニング（Terraform等）はサーバそのものや土台の設備を作り出す道具です。
📝 採点ポイント
□ 5カテゴリをすべて挙げられている ／ □ Terraformがプロビジョニングだと言えている ／ □ 設定管理＝中身を整える、プロビジョニング＝土台を作る、の違いを説明できている
第3問手続き型と宣言型

「サーバを10台から15台に増やす」場面を例に、手続き型と宣言型の違いを説明してください。

✅ 解答例
手続き型（Ansible等）は手順を書くので、すでに10台あることを自分で把握し、「あと5台建てる」手順に書き直す必要があります（数を15で再実行すると合計25台になってしまう）。宣言型（Terraform）は望む完成形を書くので、countを10から15にするだけ。差分（あと5台）はTerraformが自分で計算します。
📝 採点ポイント
□ 手続き型は現状把握＋書き直しが必要 ／ □ 手続き型で再実行すると重複して建つ点に触れている ／ □ 宣言型は望む状態を書くだけで差分は道具が計算する
第4問ミュータブルとイミュータブル

ミュータブルなインフラとイミュータブルなインフラの違いを、「設定ドリフト」という言葉を使って説明してください。

✅ 解答例
ミュータブルは既存サーバをその場で改築していく方式（設定管理ツールの基本）。改築履歴がサーバごとに違ってくるため設定ドリフトが起きやすい。イミュータブルは変更のたびに新しいイメージから新サーバを建て古いのを捨てる方式（Terraform＋テンプレートの基本）。後からいじらないので設定ドリフトが起きにくく、中身を把握しやすく、過去のバージョンにも戻しやすい。
📝 採点ポイント
□ ミュータブル＝その場で改築、イミュータブル＝建て直し ／ □ 設定ドリフトがミュータブルで起きやすい理由（改築履歴の差）に触れている ／ □ イミュータブルの利点を挙げている
第5問マスタレス・エージェントレス

Terraformが「マスタレス・エージェントレス」と言われるのはなぜか、ChefやPuppetと対比して説明してください。

✅ 解答例
ChefやPuppetは、初期設定では全体を仕切る親方サーバ（マスタ）と、各サーバに常駐する代理人（エージェント）が必要で、余計な設備・保守・セキュリティの負担が増えます。TerraformはクラウドのAPIを使うので追加のマスタを建てる必要がなく（既存APIキーを使う）、各サーバに自前のエージェントを入れる必要もありません（クラウド側の既存の仕組みを使う）。だからマスタレス・エージェントレスと言われます。
📝 採点ポイント
□ Chef/Puppetはマスタとエージェントが基本 ／ □ マスタ/エージェントの負担（設備・保守・セキュリティ）に触れている ／ □ Terraformは既存のAPIキーやクラウドの仕組みで済むと説明できている
