プロバイダ provider

AWS・Azure・Google Cloud など、実際に建物を建ててくれる施工会社のこと。Terraform に差し込む「窓口担当（プラグイン）」。

コア core / 本体

Terraform の本体プログラム。コマンド受付・設計図の読み取り・段取りを担う「本部」。

リージョン region / 地域

工事する土地（地域）。例：us-east-2＝アメリカ東部。この章では東日本支社・西日本支社にたとえる。

エイリアス alias / 名札

同じ会社の担当を複数置くとき、見分けるために付ける名札。

required_providers

「どの担当を・どこから・どのバージョンで連れてくるか」を明記する依頼書。

アカウント account / 契約口座

クラウドの契約口座。Google Cloud では「プロジェクト」と呼ぶ。

assume_role ロールの引き受け

別の口座に入るため、その口座の権限（役割）を借りる仕組み。

モジュール module / 組み立てキット

建材をまとめて再利用できる部品。再利用可能モジュールとルートモジュールの2種。

configuration_aliases 設定エイリアス

モジュールが「外から担当を受け取る」と宣言する名札。自分では担当を作らない。

RDS / レプリケーション 複製

マネージドなデータベース置き場。本体（プライマリ）から控え（レプリカ）へ自動で写しを作る仕組み。

Docker / コンテナ 型紙 / 箱

イメージ＝OSやソフトを焼き付けた型紙。コンテナ＝隔離された箱の中でその型紙を動かしたもの。

Kubernetes K8s

多数のコンテナ（箱）を束ねて指揮するオーケストレーション（指揮）ツール。

EKS マネージド K8s

AWS が司令塔と実働サーバを代わりに動かしてくれる Kubernetes サービス。

ARN

AWS 上の住所のような、世界で1つの一意な識別子。

try 関数

引数を順に試し、エラーにならなかった最初の値を返す安全装置。

AMI

サーバの中身を丸ごと焼き付けた型紙の品番。地域ごとに番号が違う。

ハル棟梁、今までの設計図には、いつも最初にこんな一文がありましたよね。これって何を言ってるんですか？

7.1

1つのプロバイダを使うまずは基本の1社から

7.1.1 プロバイダとは何か

要するに： Terraform は「本部（コア）」と「各社の窓口担当（プロバイダ）」でできている。プロバイダは会社ごとのプラグインで、aws_ のような接頭辞でどの会社の建材かが分かる。

ハル
ハルそもそもプロバイダって何ですか？ なんとなく「おまじない」として書いてました。
棟梁
棟梁Terraform Provider と言ってね。AWS、Azure、Google Cloud、DigitalOcean みたいな「実際に建物を建ててくれる相手」のことだよ。Terraform は内部で「本部」と「各社の窓口担当」の2つに分かれているんだ。
ハル
ハル本部と窓口担当は、どうやって話すんですか？
棟梁
棟梁コアは RPC という方法で窓口担当に指示を出す。窓口担当はそれを受けて、ネットワーク（HTTP）で本物の AWS や Azure に連絡を取る。
🏛️

コア（本体・本部）

terraform 本体。コマンド受付（plan/apply）、設計図(HCL)の読み取り、依存関係の整理、状態ファイルの読み書きなど共通の段取りを担う。Go 製で HashiCorp が管理。

🧑‍💼

プロバイダ（窓口担当）

コアに差し込むプラグイン。AWS 担当、Azure 担当のように各社ごとに1人ずついる。

本部と各社・本物のクラウドのつながりを一本道で表すとこうなります。

つながりの図（テキスト）を見る
[Terraform コア(本部)] --RPC(社内連絡)--> [プロバイダ(窓口担当)] --HTTP(外線電話)--> [AWS/Azure/GCP(実際の建設会社)]
ハル
ハル窓口担当ごとに、扱う建材の名前って違うんですか？
棟梁
棟梁そう。各プロバイダは自分専用の接頭辞を持っていてね。AWS 担当の建材は全部 aws_ で始まる（aws_instance、aws_ami など）。Azure 担当は azurerm_ だ。名前の頭を見れば、どの会社の建材か一目で分かる。
ハル
ハルなるほど、頭文字が「どの会社の担当か」の名札みたいなものなんですね！

🏗️ たとえ話

工房の「本部」が段取り全般を仕切り、各建設会社の「窓口担当」が現場とやり取りします。窓口担当が本部に持ってくる建材には会社の刻印（aws_ など）が押してあって、どの会社の納品物か一目で分かるわけです。

🤔 なぜこれが必要か

  • プロバイダの正体を知ると「なぜ会社ごとに別々の設定が要るか」が腑に落ちるから。
  • 接頭辞を見れば、設計図のどの行がどの会社の仕事か判別できるようになる。

📌 この項のまとめ

  • Terraform はコア（本部）とプロバイダ（窓口担当プラグイン）の2部構成。
  • コアはコマンド処理・依存解決・状態管理など共通機能を担う。
  • プロバイダはコアに RPC でつながり、各クラウドに HTTP でアクセスする。
  • 各プロバイダは aws_・azurerm_ のような接頭辞を持つ。
  • 近年は各社が自社担当を整備している（AWS の社員が AWS プロバイダを、など）。

7.1.2 プロバイダをどのようにインストールするのか

要するに： provider ブロックを書けば公式の担当は自動で入る。だが本番では required_providers で「あだ名・配布元・バージョン」を明記して、誰をどこから連れてくるかを自分で制御すべき。

ハル
ハル窓口担当って、どうやって雇うんですか？
棟梁
棟梁公式の会社なら、設計図に provider ブロックを書くだけでいい。実は aws_instance のように aws_ で始まる建材を1つ置くだけでも、Terraform は接頭辞から「AWS 担当が必要だ」と判断してくれるんだ。

このコードは「AWS の窓口担当を雇い、アメリカ東部で工事させる」という依頼です。

HCL コードを見る
# 「AWS の窓口担当を雇い、アメリカ東部で工事させる」という依頼
provider "aws" {
  region = "us-east-2"  # ① 工事する地域
}

このコマンドを打つと、必要な窓口担当（プロバイダ）の中身を自動でダウンロードしてきます。

ターミナルの実行例を見る
# terraform init を実行すると、必要な窓口担当（プロバイダ）を自動で連れてくる
$ terraform init

Initializing provider plugins...
- Finding hashicorp/aws versions matching "4.19.0"...
- Installing hashicorp/aws v4.19.0...
- Installed hashicorp/aws v4.19.0 (signed by HashiCorp)
ハル
ハルでもこれ、魔法すぎませんか？ どの会社の・どのバージョンの担当を・どこから連れてくるか、なんで分かるんですか？
棟梁
棟梁鋭い。本番ではもっと自分で手綱を握りたい。そのために required_providers を書くんだ。3つの部分を指定する。

このコードは「どの担当を・どこから・どのバージョンで連れてくるか」を細かく指定する雛形です。

HCL コード（雛形）を見る
# 「どの窓口担当を・どこから・どのバージョンで連れてくるか」を細かく指定する依頼書
terraform {
  required_providers {
    <LOCAL_NAME> = {           # ① 設計図の中で担当を呼ぶときの「あだ名」
      source  = "<URL>"        # ② どこから連れてくるか（配布元の住所）
      version = "<VERSION>"    # ③ どのバージョンか
    }
  }
}
🏷️

LOCAL_NAME（あだ名）

設計図の中だけの呼び名。AWS の推奨名は aws。同じ推奨名の会社が2つある時の区別にも使う。

📮

source（配布元の住所）

[HOSTNAME/]NAMESPACE/TYPE の形。AWS なら hashicorp/aws。HOSTNAME 省略で公開レジストリを見に行く。

🔢

version（版の縛り）

4.19.0 で固定も、~> 4.0 のように範囲指定も可。詳しくは8章。

このコードは「AWS の窓口担当をバージョン4系で公式レジストリから連れてくる」指定です。

HCL コードを見る
# AWS の窓口担当をバージョン 4 系で公式レジストリから連れてくる指定
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"  # ① 公開レジストリの hashicorp 配下の aws
      version = "~> 4.0"         # ② 4 系（4.0 以上 5.0 未満）に縛る
    }
  }
}
ハル
ハルじゃあ hashicorp 以外の会社（Datadog や自作の担当）を使いたい時は？
棟梁
棟梁その時は required_providers を書く必要がある。バージョンを自分で制御したい時も同じだ。大事な心得を1つ。常に required_providers を書くことを勧めるよ。

🏗️ たとえ話

init だけだと「適当に評判の良い AWS建設を、最新版で呼んどいて」と任せきりにする状態。required_providers は「AWS建設の、住所はここ、契約バージョンは4系で」と発注書に明記すること。明記しておけば、別の作業員が同じ発注書を使っても、毎回まったく同じ会社・同じ版が来てくれます。

🤔 なぜこれが必要か

  • バージョンを固定しないと、ある日突然新版が入って街が壊れることがあるから。
  • 公式以外（Datadog 等）や自作の担当を使うには明記が必須だから。
  • 配布元と版を明記すると、他の人が同じ設計図を使っても同じ担当が入る。

📌 この項のまとめ

  • provider ブロックだけでも公式担当は init で自動ダウンロードされる。
  • required_providers で LOCAL_NAME・source(URL)・version を指定できる。
  • URL は [HOSTNAME/]NAMESPACE/TYPE。HOSTNAME 省略で公開レジストリ。
  • version は固定も範囲も可。
  • 心得: required_providers は常に書く。

7.1.3 プロバイダをどのように使うのか

要するに： 使う流れは「required_providers で宣言 → provider で設定 → その会社の建材は自動でその設定に従う」。地域や口座を変えたいなら、担当を複数置く必要がある。

1

宣言する

required_providers で「どの担当を使うか」を宣言。

2

設定する

provider ブロックでその担当の設定（地域など）を書く。設定項目は region 以外にも多数あるので必ずドキュメントを見る。

3

建材が自動追従

いったん設定すると、その会社の建材（aws_ で始まるもの）はすべて自動でその設定を使う。地域を us-east-2 にしたら aws_ のリソースは全部アメリカ東部に建つ。

このコードは「AWS の4系の担当を使う」と宣言し、その担当を「アメリカ東部で工事する」と設定する2段です。

HCL コードを見る
# まず「AWS の 4 系の担当を使う」と宣言
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 4.0"
    }
  }
}

# 次に「その担当はアメリカ東部で工事する」と設定
provider "aws" {
  region = "us-east-2"  # ① 今は地域しか設定していないが、設定項目は他にもたくさんある
}
ハル
ハルえっ、じゃあ一部を東部、一部を西部に建てたい時は？ 別の口座に建てたい時は？
棟梁
棟梁それがまさに次の節のテーマだ。「同じ会社の窓口担当を複数置く」方法を学ぶ必要がある。

🏗️ たとえ話

「AWS建設を雇う」と発注書に書く（宣言）→「東日本支社の土地で工事してね」と現場を指定する（設定）。すると、その後に届く AWS建設の建材は全部、何も言わなくても東日本支社の現場に運ばれます。東でも西でも建てたいなら、東担当と西担当の2人を雇う必要があるわけです。

🤔 なぜこれが必要か

  • 設定の流れを掴むと、設計図のどこを直せば工事先が変わるか分かるから。
  • 「1担当=1設定」と分かると、複数地域に分けたい動機が明確になる。

📌 この項のまとめ

  • 使う流れ: 宣言（required_providers）→ 設定（provider）→ 建材が自動追従。
  • 設定項目は region 以外にも多数。ドキュメントを確認する。
  • 同じ会社で複数地域・複数口座に分けたいなら次節の手法が要る。
7.2

同じプロバイダのコピーを複数使うAWS建設の担当を「東日本支社用」「西日本支社用」に増やす

棟梁
棟梁ここからは、同じ会社（AWS）の窓口担当を「東日本支社用」「西日本支社用」と複数置く話だ。よくある場面を3つ見ていこう。複数の地域、複数の口座、そして複数の担当を扱えるモジュール作りだ。

7.2.1 複数のAWSリージョンを使う

要するに： 同じ会社の担当を複数置くには provider に alias（名札）を付け、建材には provider、モジュールには providers（複数形マップ）で割り当てる。ただし複数地域を1モジュールにまとめるのは原則アンチパターン。

ハル
ハル一部を東部 us-east-2、一部を西部 us-west-1 に建てたいとします。担当を2つ書けばいいんですか？
棟梁
棟梁惜しい。書くだけならできるが、問題がある。これだと、各建材が「どっちの担当を使うのか」を指定できないんだ。

このコードは同じ会社の担当を2つ書いた例（このままだと区別できず問題あり）です。

HCL コードを見る
# 同じ会社の担当を2つ書いてみたが…これだけでは問題がある
provider "aws" {
  region = "us-east-2"
}

provider "aws" {
  region = "us-west-1"
}

このコードは「今の地域名を教えて」というデータソースを2つ置いた例ですが、どちらの担当を使うか不明です。

HCL コードを見る
# 「今の地域名を教えて」というデータソースを2つ置いたが、どちらの担当を使うか不明
data "aws_region" "region_1" {
}

data "aws_region" "region_2" {
}
ハル
ハルたしかに、どっちが東部でどっちが西部か見分けがつきません。どうするんですか？
棟梁
棟梁そこで エイリアスを付けるんだ。担当ごとに alias で名札を付け、それを建材に provider パラメータで渡して「この担当を使え」と指定する。

このコードは各担当に名札（エイリアス）を付け、各データソースにどの名札の担当を使うか明示するものです。確認用に地域名も出力します。

HCL コードを見る
# 各担当に「名札（エイリアス）」を付けて区別できるようにする
provider "aws" {
  region = "us-east-2"
  alias  = "region_1"   # ① 東部の担当に「region_1」という名札
}

provider "aws" {
  region = "us-west-1"
  alias  = "region_2"   # ② 西部の担当に「region_2」という名札
}

# 各データソースに「どの名札の担当を使うか」を明示
data "aws_region" "region_1" {
  provider = aws.region_1   # ① 東部の担当を使う
}

data "aws_region" "region_2" {
  provider = aws.region_2   # ② 西部の担当を使う
}

# 確認用：それぞれが本当に違う地域を見ているかを出力する
output "region_1" {
  value       = data.aws_region.region_1.name
  description = "1つめの地域の名前"
}

output "region_2" {
  value       = data.aws_region.region_2.name
  description = "2つめの地域の名前"
}

apply するとそれぞれ別の地域名が表示されます。

ターミナルの実行例を見る
$ terraform apply
(...)
Outputs:
region_1 = "us-east-2"
region_2 = "us-west-1"
ハル
ハルおお、ちゃんと東部と西部に分かれてる！ これ、建物（リソース）にも使えますか？
棟梁
棟梁同じ provider パラメータが使える。ただし AMI ID（型紙の品番）は地域ごとに違うから注意だ。手で調べるのは退屈でミスも起きやすい。だから aws_ami データソースで自動的に探させるのが賢い。
ハル
ハルなんで地域ごとに品番が違うんですか？
棟梁
棟梁東部の Ubuntu 20.04 と西部の Ubuntu 20.04 では品番が別物なんだ。だから各地域で aws_ami を使って最新の品番を自動取得し、サーバの ami をその結果から引くように直すんだよ。

このコードは、各地域で最新のUbuntu 20.04の型紙の品番を自動で探し、その結果を使って2台のサーバを別々の地域に建て、建った区画を出力するものです。

HCL コードを見る
# 各地域で「最新の Ubuntu 20.04 の型紙の品番」を自動で探す
data "aws_ami" "ubuntu_region_1" {
  provider = aws.region_1   # ① 東部の担当で探す
  most_recent = true
  owners      = ["099720109477"] # Canonical（Ubuntu の発行元）
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
}

data "aws_ami" "ubuntu_region_2" {
  provider = aws.region_2   # ② 西部の担当で探す
  most_recent = true
  owners      = ["099720109477"] # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
}

# 型紙の品番を「自動で探した結果」から引いて、2台のサーバを別々の地域に建てる
resource "aws_instance" "region_1" {
  provider      = aws.region_1
  ami           = data.aws_ami.ubuntu_region_1.id   # ① 東部で探した品番
  instance_type = "t2.micro"
}

resource "aws_instance" "region_2" {
  provider      = aws.region_2
  ami           = data.aws_ami.ubuntu_region_2.id   # ② 西部で探した品番
  instance_type = "t2.micro"
}

# 各サーバが地域内のどの区画に建ったかを出力
output "instance_region_1_az" {
  value       = aws_instance.region_1.availability_zone
  description = "1つめの地域でサーバが建った区画"
}
output "instance_region_2_az" {
  value       = aws_instance.region_2.availability_zone
  description = "2つめの地域でサーバが建った区画"
}

apply すると、別々の地域のアベイラビリティゾーンに建っているのが分かります。

ターミナルの実行例を見る
$ terraform apply
(...)
Outputs:
instance_region_1_az = "us-east-2a"
instance_region_2_az = "us-west-1b"

モジュールを複数地域に使う（RDS のクロスリージョンレプリケーション）

ハル
ハル建材は分かりました。でもモジュール（部品をまとめた組み立てキット）の場合はどうするんですか？
棟梁
棟梁3章で Amazon RDS でテスト用にデータベースを1台建てたね。だが本番でDBが1台だと単一障害点になる。RDS はレプリケーションを標準で持っていて、本体（プライマリ）から控え（レプリカ）へ自動でデータを写してくれる。
ハル
ハル控えを別の地域に置けるんですか？
棟梁
棟梁そう。控えを西部に置けば、東部で大災害が起きても西部に切り替えられる。これをクロスリージョンレプリケーションと言う。テスト用コードを、複製対応の再利用可能モジュール mysql に作り替えよう。

このコードは、複製を有効にするための2つの新しい入力変数（バックアップ保持日数と、控えになる場合の複製元DBの住所）です。

HCL コードを見る
# 複製を有効にするための2つの新しい入力変数
variable "backup_retention_period" {
  description = "バックアップを保持する日数。複製を有効にするには 0 より大きい値が必要。"
  type        = number
  default     = null
}
variable "replicate_source_db" {
  description = "指定すると、その ARN の RDS データベースの控え（レプリカ）になる。"
  type        = string
  default     = null
}
棟梁
棟梁ポイントは2つ。①この2つの変数を使う。②控えの場合、本体から引き継がれる engine・db_name・username・password は設定できないので、replicate_source_db が設定されている時はこれらを設定しないよう条件分岐する。

このコードは、本体にも控えにもなれる汎用のデータベース設計です。控えのときは本体から引き継ぐ項目を null にします。

HCL コードを見る
# 本体にもなれるし控えにもなれる、汎用のデータベース設計
resource "aws_db_instance" "example" {
  identifier_prefix   = "terraform-up-and-running"
  allocated_storage   = 10
  instance_class      = "db.t2.micro"
  skip_final_snapshot = true

  backup_retention_period = var.backup_retention_period  # ① バックアップ有効化（複製の前提）
  replicate_source_db     = var.replicate_source_db      # ② 設定時はこのDBは控えになる

  # ③ replicate_source_db が未設定の時だけ設定（控えは本体から引き継ぐため）
  engine   = var.replicate_source_db == null ? "mysql" : null
  db_name  = var.replicate_source_db == null ? var.db_name : null
  username = var.replicate_source_db == null ? var.db_username : null
  password = var.replicate_source_db == null ? var.db_password : null
}

このコードは、控えのとき省略できるようDB名・ユーザー名・パスワードの初期値を null にし、控えを作るとき渡すための住所（ARN）を出力し、このモジュールが使うAWS担当の版を宣言するものです。

HCL コードを見る
# 控えのときは省略できるよう、初期値を null（未指定）にしておく
variable "db_name" {
  description = "データベースの名前。"
  type        = string
  default     = null
}
variable "db_username" {
  description = "データベースのユーザー名。"
  type        = string
  sensitive   = true
  default     = null
}
variable "db_password" {
  description = "データベースのパスワード。"
  type        = string
  sensitive   = true
  default     = null
}

# このデータベースの住所（ARN）を出力。控えを作るときに渡すため
output "arn" {
  value       = aws_db_instance.example.arn
  description = "データベースの ARN"
}

# このモジュールは AWS の 4 系の担当を使う、と宣言
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 4.0"
    }
  }
}
棟梁
棟梁さて、本番環境で本体と控えを建てよう。まず機密（ユーザー名・パスワード）の変数を定義し、本体（プライマリ）を mysql モジュールで作り、控え（レプリカ）を2つめのモジュールで作る。控えには本体の ARN を渡すだけだ。

このコードは、本番DBの機密変数を定義し、本体を作り、本体のARNを渡して控えを作るものです。

HCL コードを見る
# 本番のデータベースのユーザー名とパスワード（機密なので sensitive にする）
variable "db_username" {
  description = "データベースのユーザー名"
  type        = string
  sensitive   = true
}
variable "db_password" {
  description = "データベースのパスワード"
  type        = string
  sensitive   = true
}

# 本体（プライマリ）のデータベースを建てる
module "mysql_primary" {
  source = "../../../../modules/data-stores/mysql"
  db_name     = "prod_db"
  db_username = var.db_username
  db_password = var.db_password
  backup_retention_period = 1  # 複製を支えるため、バックアップ有効化（1日分保持）
}

# 控え（レプリカ）を建てる。本体の ARN を渡すだけ
module "mysql_replica" {
  source = "../../../../modules/data-stores/mysql"
  replicate_source_db = module.mysql_primary.arn  # 本体の控えとして設定
}
ハル
ハルシンプルですね。でも本体を東部、控えを西部にするにはどうするんですか？
棟梁
棟梁担当を2つ作り名札を付ける。そしてモジュールに「どの担当を使え」と伝えるには providers（複数形）パラメータを使うんだ。
ハル
ハル建材のときは provider（単数）、モジュールのときは providers（複数）。なんで違うんですか？
棟梁
棟梁建材1つは必ず1社の担当にしか頼まないから単数。でもモジュールは中に複数の建材を持ち複数の担当を使うことがあるから複数形のマップになっている。providers マップの鍵は、モジュール内の required_providers のあだ名と一致させる必要がある。これも、どのモジュールにも required_providers を書くべき理由だよ。

このコードは、本体用（東部 primary）と控え用（西部 replica）の担当を名札付きで用意し、各モジュールに providers マップでどの担当を使うか割り当て、最後に本体と控えの接続先・ポート・住所を出力するものです。

HCL コードを見る
# 本体用（東部）と控え用（西部）の2つの担当を、名札付きで用意
provider "aws" {
  region = "us-east-2"
  alias  = "primary"   # ① 本体用＝東部
}
provider "aws" {
  region = "us-west-1"
  alias  = "replica"   # ② 控え用＝西部
}

# 本体モジュールに「primary（東部）の担当を使え」と指示
module "mysql_primary" {
  source = "../../../../modules/data-stores/mysql"
  providers = {
    aws = aws.primary   # ① モジュール内の「aws」に東部の担当を割り当てる
  }
  db_name     = "prod_db"
  db_username = var.db_username
  db_password = var.db_password
  backup_retention_period = 1
}

# 控えモジュールに「replica（西部）の担当を使え」と指示
module "mysql_replica" {
  source = "../../../../modules/data-stores/mysql"
  providers = {
    aws = aws.replica   # ① モジュール内の「aws」に西部の担当を割り当てる
  }
  replicate_source_db = module.mysql_primary.arn
}

# 本体と控えの接続先・ポート・住所を出力
output "primary_address" { value = module.mysql_primary.address }
output "primary_port"    { value = module.mysql_primary.port }
output "primary_arn"     { value = module.mysql_primary.arn }
output "replica_address" { value = module.mysql_replica.address }
output "replica_port"    { value = module.mysql_replica.port }
output "replica_arn"     { value = module.mysql_replica.arn }

apply には20〜30分かかります。完了すると、本体は us-east-2（東部）、控えは us-west-1（西部）の住所になります。

棟梁
棟梁地域をまたいだ複製ができた。テスト環境もこの mysql モジュールを使うようにするのは君への練習課題だ。ただしテストでは複製なしで設定してごらん。

🏗️ たとえ話

本体の街を東日本支社に、控えの街を西日本支社に建てます。本体担当（東）と控え担当（西）の2人を名札付きで雇い、組み立てキット（モジュール）には「君はこの担当（東）と組め」と割り当てます。東で大地震が起きても、西日本支社の控えの街がそっくり生きているので、街は止まりません。

注意1：複数リージョンは難しい

棟梁
棟梁釘を刺しておく。世界中の複数地域でインフラを動かすのは本当は難しい。特にアクティブ・アクティブでは。
ハル
ハルどんな難しさが？
棟梁
棟梁地域間の通信の遅れ（レイテンシ）、書き込みを1地域に限るか複数でやるか（結果整合性やシャーディング＝データ分割が必要）、一意なIDの作り方、データを国内に置けという法律への対応など。どれも本書の範囲を超える。「現実の複数地域展開は、設計図に名札をちょっと渡せば済む話ではない」とは強く言っておきたい。

注意2：エイリアスは慎重に使おう

ハル
ハルエイリアス、便利なのに使いすぎ注意なんですか？
棟梁
棟梁複数地域にする主目的は「1地域が倒れても別地域が生き残る」ことだろう。ところがエイリアスで両地域を同じモジュールで管理していると、片方の地域が倒れた時、モジュールはその地域につなげないから plan も apply も失敗する。大災害のさなかに変更を出せない、という最悪の事態になる。
ハル
ハルじゃあどうすれば？
棟梁
棟梁各環境は完全に分離すべきだ。地域ごとに別々のモジュールで管理する。そうすれば作業ミスも外部障害も影響範囲を閉じ込められる。
ハル
ハルじゃあエイリアスはいつ使うんですか？
棟梁
棟梁複数の担当にまたがるインフラが「完全に一体で、まとめてデプロイしたい」場合だ。例を2つ。①CloudFront（CDN）の TLS 証明書を ACM で発行する場合、証明書は必ず us-east-1 で作る必要があるので「CloudFront 用」と「証明書用 us-east-1」の2つを持つ。②GuardDuty のように全地域に置くよう AWS が推奨するサービス。こういう特別な場合を除けば、複数地域のためのエイリアスはまれだ。もっと一般的な用途は、次に話す「別々の口座に別々に認証する」時だよ。

🤔 なぜこれが必要か

  • AMI など地域差のある値を自動で正しく引けるようになるから。
  • 災害に強いクロスリージョンレプリケーションを組めるようになるから。
  • エイリアスの正しい使いどころ（一体不可分なインフラ）を判断できるから。

📌 この項のまとめ

  • 同じ会社の担当を複数置くには alias（名札）を付ける。
  • 建材は provider = aws.名札、モジュールは providers = { aws = aws.名札 }。
  • AMI ID は地域ごとに違うので aws_ami データソースで自動取得する。
  • RDS は本体→控えの複製を地域をまたいで組める。
  • 原則として地域ごとにモジュールを分離。エイリアスは一体不可分なインフラのみ。

7.2.2 複数のAWSアカウントを使う

要するに： 複数口座を使うのは分離・認証認可・監査のため。Terraform では alias 付き provider に assume_role を足してロールを引き受け、複数口座に認証する。引き受けには両口座での許可が必要。

ハル
ハル今度は「複数の口座（アカウント）」ですね。なんで口座を分けるんですか？
棟梁
棟梁アカウントを分ける理由は主に3つある。順に説明しよう。
🚧

① 分離（隔離）

環境ごとに口座を分けて被害範囲を閉じ込める。テスト口座が攻撃されても本番には手が出せない。うっかり本番を壊すことも起きにくい。

🔐

② 認証と認可

「テストには権限を、本番には与えない」が制御しやすい。口座ごとに認証手順が別なので「テストのつもりで本番を消した」事故も防げる。

🧾

③ 監査とレポーティング

変更の証跡をたどり、法令順守を確認、逸脱を検知できる。一括請求で口座・サービス・タグごとに費用を分解できる。

ハル
ハル口座が増えたら、開発者は口座ごとにユーザーを作るんですか？
棟梁
棟梁いや、それはアンチパターンだ。普通は開発者1人につきプロフィールを1つだけ持ち、それでアクセス権のあるどの口座にも認証できるようにする。AWS では IAM ロールを引き受けることで複数口座に認証する。

子アカウントを作る（AWS Organizations）

棟梁
棟梁テスト用に新しい子アカウントを作るには AWS Organizations を使う。全子口座の請求を親口座にまとめ、管理用ダッシュボードも提供してくれる。
1

「AWS アカウントを追加」を押す

初回は「組織を作成する」画面が出ることがあるので押す。メール認証を求められたら従う。

2

情報を入力

「AWS アカウント名」（例：staging）、「所有者のメール」（口座ごとに重複不可。最初の口座と同じメールは使えない）、「IAM ロール名」（デフォルトの OrganizationAccountAccessRole 推奨）。

3

作成して ID をメモ

数分待つと子口座ができる。12桁の口座 ID をメモ。以降、親=111111111111、子=222222222222 と仮定。コンソール右上の「ロールの切り替え」で子口座に入れる。

🏗️ たとえ話

本社（親口座）の下に、テスト専用の別会社（子口座）を1つ設立するイメージ。設立すると、本社の社員証で入れる「管理者用の合鍵」（OrganizationAccountAccessRole）が子会社に自動で用意されます。請求は全部本社にまとめて届きます。

💡 コラム：1つのメールで複数の別名を使う

  • Gmail はアドレスの「+」記号の後ろが無視される。example@gmail.com なら example+stage@gmail.com も全部 example@gmail.com に届く。
  • 口座ごとに別々のメールが要る時、example+dev@、example+stage@ と作り分けられる。AWS には別アドレスに見えて、実は全部同じ受信箱。

Terraform で複数アカウントに認証する

ハル
ハルTerraform ではどう書くんですか？
棟梁
棟梁複数地域の時と同じく名札付きの provider を2つ書く。そして子口座の provider に assume_role ブロックを足して、子口座のロールを引き受けるんだ。

このコードは、親口座用・子口座用の担当を名札付きで用意し、子口座には assume_role でその口座のロールを引き受ける設定を加えるものです。

HCL コードを見る
# 親口座用の担当（名札 parent）
provider "aws" {
  region = "us-east-2"
  alias  = "parent"
}

# 子口座（222222222222）のロールを引き受ける実際の設定
provider "aws" {
  region = "us-east-2"
  alias  = "child"
  assume_role {
    role_arn = "arn:aws:iam::222222222222:role/OrganizationAccountAccessRole"  # 引き受けるロールの住所
  }
}

このコードは「今、自分はどの口座の誰か？」を親・子それぞれの担当で問い合わせ、口座IDを出力して認証できているか確認するものです。

HCL コードを見る
# 「今、自分はどの口座の誰か？」を、親・子それぞれの担当で問い合わせる
data "aws_caller_identity" "parent" {
  provider = aws.parent   # ① 親口座として
}
data "aws_caller_identity" "child" {
  provider = aws.child    # ② 子口座として
}

# 親口座と子口座のIDを出力して確認
output "parent_account_id" {
  value       = data.aws_caller_identity.parent.account_id
  description = "親 AWS アカウントの ID"
}
output "child_account_id" {
  value       = data.aws_caller_identity.child.account_id
  description = "子 AWS アカウントの ID"
}

apply すると、別々の口座IDが返ります＝両方に認証できている証拠です。

ターミナルの実行例を見る
$ terraform apply
(...)
Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
Outputs:
parent_account_id = "111111111111"
child_account_id = "222222222222"
ハル
ハルちゃんと親 111... と子 222... に分かれてる！ エイリアスと assume_role で複数口座を扱えるんですね。

注意1：クロスアカウントのIAMロールは2段階の設定が必要

棟梁
棟梁口座 111... から 222... のロールを引き受けるには、両方の口座で許可が要る。
ハル
ハル両方ですか？
棟梁
棟梁そう。①ロールがある側（子 222...）で「親 111... を信頼して引き受けを許す」ポリシーを設定。OrganizationAccountAccessRole なら Organizations が自動でやる。自作ロールでは明示的に sts:AssumeRole を設定する必要がある。②引き受ける側（親 111...）でも同様に引き受け権限が要る。今回は2章で君に AdministratorAccess を付けたので知らないうちに通っている。だが現実では管理者権限は使わないことが多いので、明示的に sts:AssumeRole を付ける必要がある。

注意2：エイリアスは慎重に使おう

棟梁
棟梁マルチアカウントでもエイリアスの使いすぎは禁物だ。複数口座にする目的は「分離して、ある口座の問題が他に波及しないようにする」こと。複数口座にまたがってデプロイするモジュールは、その方針そのものに反する。複数口座をエイリアスで扱うのは、リソースを意図的に一体化して同時にデプロイしたい場合だけにしよう。

🤔 なぜこれが必要か

  • テストと本番を口座ごと分けて事故・攻撃を閉じ込められるから。
  • 開発者1人1プロフィールで複数口座に安全に入れる仕組みを組めるから。
  • 全口座の費用をまとめて見える化し、チーム単位で予算管理できるから。

📌 この項のまとめ

  • 口座を分ける理由は分離・認証認可・監査の3つ。
  • 子口座は AWS Organizations で作り、親が請求と管理を束ねる。
  • Terraform では assume_role ブロックでロールを引き受けて子口座に認証。
  • クロスアカウントの引き受けは「ロール側」と「引き受ける側」の両方で許可が必要。
  • 複数口座をまたぐモジュールは原則アンチパターン。意図的な一体化時のみ。

7.2.3 複数のプロバイダを使えるモジュールを作る

要するに： 再利用可能モジュールに provider を書くのは設定・重複・性能の3つの理由でアンチパターン。代わりに required_providers 内で configuration_aliases を宣言し、利用者がルートで作った担当を providers マップで渡す。

🧩

再利用可能モジュール

直接デプロイせず、他のモジュールや建材と組み合わせて使う低レベル部品。

🏗️

ルートモジュール

複数の再利用可能モジュールを組み合わせ、apply を直接実行する高レベルの組み立て体。定義は「apply を直接打つ対象かどうか」。

棟梁
棟梁これまでの例では provider は全部ルートモジュールに書いていた。複数口座コードを再利用可能モジュールにすると、provider の設定が全部モジュールの中に隠れてしまう。これはアンチパターンなんだ。理由は3つある。
⚙️

① 設定上の問題

モジュールが担当の全設定を握る。AWS プロバイダの設定項目は50個前後。全部変えられる変数を50個も足したら保守も利用も地獄。

📋

② 重複の問題

複数モジュールを組み合わせるのが普通だから、各モジュールに設定群を毎回コピペして渡す羽目になる。退屈でミスも起きやすい。

🐢

③ パフォーマンスの問題

provider ごとに新プロセスが起動し RPC でやり取り。数が増えると深刻に遅く・失敗しやすくなる。

棟梁
棟梁私の実話だ。5サービスを全25地域に置くつもりで、各モジュールに25個の provider を入れ、5サービス分まとめた。計算してごらん。
ハル
ハル25 × 5 で…125個ですか！
棟梁
棟梁そう、125個。apply すると125プロセスが起動し、数百の API/RPC コールが殺到。CPU が応答しなくなり、1回の plan に20分、ネットワーク過負荷で apply がエラーで落ちることもあった。だから再利用可能モジュールには provider を書くな、が鉄則だ。

🏗️ たとえ話

組み立てキット（部品）の中に「どの建設会社をどう雇うか」の契約まで埋め込んでしまうと、キットを使うたびに会社を雇い直す羽目に。125個もキットを並べたら、現場に125社の窓口担当が一斉に押しかけ、電話が鳴りやまず工事が完全に止まります。契約は元締め（ルート）が1か所でまとめ、部品は「担当を1人貸して」と名札で受け取るだけにすべきです。

設定エイリアス（configuration_aliases）

棟梁
棟梁その答えが設定エイリアスだ。普通のエイリアスとよく似ているが、provider ブロックではなく required_providers の中で定義する。
ハル
ハル普通のエイリアスと一番違うところは？
棟梁
棟梁設定エイリアスは「それ自体では担当を作らない」点だ。代わりに、利用者に「providers マップで担当を必ず渡しなさい」と強制する。

このコードは、モジュール側が「parent と child という2つの担当を外から受け取る」と宣言し、その名札を各データソースに割り当てるものです。

HCL コード（モジュール側）を見る
# モジュールが「parent と child という2つの担当を外から受け取る」と宣言する
terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = "~> 4.0"
      configuration_aliases = [aws.parent, aws.child]  # ① 外から受け取る担当の名札を宣言
    }
  }
}

# 受け取った名札を、各データソースに割り当てる
data "aws_caller_identity" "parent" {
  provider = aws.parent
}
data "aws_caller_identity" "child" {
  provider = aws.child
}

このコードは利用者側（ルート）で本物の担当を2つ用意し、モジュール呼び出しで providers マップを設定エイリアスに対応付けて渡すものです。

HCL コード（利用者側）を見る
# 利用者側（ルート）で、本物の担当を2つ用意する
provider "aws" {
  region = "us-east-2"
  alias  = "parent"
}
provider "aws" {
  region = "us-east-2"
  alias  = "child"
  assume_role {
    role_arn = "arn:aws:iam::222222222222:role/OrganizationAccountAccessRole"
  }
}

# 用意した担当を、モジュールの設定エイリアスに対応付けて渡す
module "multi_account_example" {
  source = "../../modules/multi-account"
  providers = {
    aws.parent = aws.parent   # ① モジュールの parent に本物の parent を割り当て
    aws.child  = aws.child    # ② モジュールの child に本物の child を割り当て
  }
}
ハル
ハルなるほど、つまり「担当の実体はルートで作り、部品（モジュール）は名札だけ宣言して外から受け取る」ってことですね！

🤔 なぜこれが必要か

  • 再利用可能モジュールを、認証や地域に縛られない汎用部品にできるから。
  • provider の乱立による plan/apply の遅延・失敗を避けられるから。
  • Terraform に「必要な担当を必ず渡させる」安全装置を効かせられるから。

📌 この項のまとめ

  • モジュールは再利用可能モジュールとルートモジュールの2種。
  • 再利用可能モジュール内の provider 定義は3つの理由でアンチパターン（設定・重複・性能）。
  • 代わりに configuration_aliases を required_providers 内で宣言する。
  • 設定エイリアスは担当を作らず、利用者に providers マップでの提供を強制する。
  • 担当の実体はルートで作り、部品は名札を外から受け取る。
