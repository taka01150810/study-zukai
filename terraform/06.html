この章のあらすじ・要するに・なぜ必要か

要するに： 大切な鍵（パスワードやアクセスキー）を、設計図にそのまま書き込んではいけない。鍵には専用の金庫があって、目的に合った金庫を選び、鍵を渡す相手や置き場所をきちんと管理しよう、という話です。

棟梁
棟梁ハル、その設計図、すぐ消しなさい。
ハル
ハルえっ、なんでですか！？ ちゃんと動きますけど。
棟梁
棟梁動くことと安全なことは別なんだよ。それはな、建物のマスターキーを、誰でも見られる設計図の表紙に油性ペンで書いたのと同じことだ。今日はその「鍵」と「金庫」の話をじっくりやろう。

この章で扱う設計図の例は、データベースという「大事な書類を保管する部屋」を建てるものだ。username と password は、この部屋と中の書類すべてを自由にできる「管理人の鍵」。これが悪い人の手に渡ったら書類は全部抜かれる。

このコードは MySQL という種類のデータベース（書類保管室）を1部屋建てる設計図です。最後の名前とパスワードを安全に入れたいのがテーマです。

設計図の例（aws_db_instance） 
# MySQLという種類のデータベース（書類保管室）を1部屋建てる設計図
resource "aws_db_instance" "example" {
  identifier_prefix   = "terraform-up-and-running"  # 部屋の名前の頭につける文字
  engine              = "mysql"       # 書類保管室の種類（MySQL製）
  allocated_storage   = 10            # 棚の広さ（10ギガ分）
  instance_class      = "db.t2.micro" # 部屋のグレード（一番小さい安いやつ）
  skip_final_snapshot = true          # 取り壊すとき最後の写真を撮らない
  db_name             = var.db_name        # 中に作る書類フォルダの名前

  # ここに「部屋の管理人の名前とパスワード」を安全に入れたいが、どうする？
  username = "???"
  password = "???"
}

シークレット管理の基本

鍵の扱いの大原則

要するに： 鍵を設計図にそのまま書いてはいけない。一度漏れると回収も監査もできず、被害が無限に広がる。

ハル
ハル鍵を扱う基本ルールって、何個くらいあるんですか？
棟梁
棟梁まず第1ルール。「鍵をプレーンテキストで保存するな」。
ハル
ハルで、第2ルールは？
棟梁
棟梁「鍵をプレーンテキストで保存するな」。……同じだ。冗談抜きで、それくらい大事だから2回言ったんだよ。設計図に直接パスワードを書いてバージョン管理に保存する、あれは絶対ダメだ。

絶対にやってはいけないのがこれ。鍵を設計図に丸書きしている見本です。

  # ...（中略）...

  # 絶対ダメ！
  username = "admin"      # 管理人の名前を丸書き
  password = "password"   # パスワードを丸書き
  # 絶対ダメ！
}

なぜダメか — 4つの理由

👥

理由1：全員が鍵を入手

設計図を見られる工房の職人全員が、建物の管理人鍵を手に入れられる。社内の全開発者がDBの認証情報を見られてしまう。

💾

理由2：全パソコンにコピー

設計図をチェックアウトしたあらゆるパソコンに鍵が残る。職人のPC、CIサーバ、Gitサーバ、デプロイ先、バックアップ装置…全部に散らばる。

🐛

理由3：全ソフトが読める

鍵がそのままディスクに転がっているから、そのパソコン上で動くどんなソフトも鍵を盗み見できる。

🚫

理由4：監査も無効化も不可

あちこちにコピーされていると、誰がいつ触ったかの記録もないし、「この鍵はもう使えなくする」と取り消す手段もない。

ハル
ハルうわあ……つまり一度ばらまいたら、回収不能なんですね。
棟梁
棟梁そうだ。悪い人（ハッカー、競合他社、不満を持って辞めた元社員）に無数の侵入経路をプレゼントすることになる。しかも侵入されたことにすら気づけない。だから鍵は専用の金庫＝シークレット管理ツールに入れるのが必須なんだよ。

🔑 たとえ話

設計図の表紙に油性ペンでマスターキーの番号を書くようなものだ。設計図は工房中でコピーされ、職人のカバン、コピー機、倉庫、町の印刷屋にまで散らばる。番号を書いた紙は回収できないし、誰がそれを写したかも分からない。一度書いたら、その建物はもう「誰でも入れる建物」になってしまう。

📌 なぜこれが必要か / できること

  • 設計図への丸書きが、なぜ「最悪の選択」なのかを4つの理由で説明できるようになる。
  • 鍵を専用の金庫に入れる、という次の話への動機がはっきりする。

📝 この項のまとめ

  • 第1も第2のルールも「鍵をプレーンテキストで保存するな」。
  • 理由は「全員が見られる」「全パソコンにコピーが残る」「全ソフトが読める」「監査も無効化もできない」の4つ。
  • 鍵は専用のシークレット管理ツールに入れる。

ハル
ハルどの鍵も同じ金庫に入れちゃダメなんですか？
棟梁
棟梁ダメだ。ほとんどの金庫はこの3種のどれか1つ専用に作られている。「設備の鍵としてのパスワード」と「お客さんのログイン用パスワード」では、しまい方が根本的に違うんだ。
ハル
ハルどう違うんですか？

ハル
ハルなるほど、「後で元に戻したいか」で金庫の仕組みが変わるんですね。

🔑 たとえ話

設備の鍵は、また使うために「合鍵を作り直せる原型」として金庫にしまう。お客さんのログインパスワードは、本人確認さえできればよく原型を残す必要がないので、「形だけ照合できる溶かした型」にしてしまう。同じ金庫に両方しまうと、片方には不便で片方には危険だ。だから目的に合った金庫を使う。

📌 なぜこれが必要か / できること

  • 金庫を選ぶ前に「自分が扱う鍵はどの種類か」を見分けられるようになる。
  • 暗号化（元に戻せる）とハッシュ（戻せない）の違いを使い分けられるようになる。

📝 この項のまとめ

  • 鍵は個人・顧客・インフラの3種類。
  • 設備の鍵は元に戻せる暗号化（AES等）、顧客のパスワードは戻せないハッシュ（bcrypt等）。
  • 種類に合った金庫を使う。この章はインフラの鍵が中心。

6.2.2 鍵（シークレット）の保存方法

要するに： しまい方は「暗号化ファイルをバージョン管理に置く方式」と「金庫番の窓口に預ける方式」の2つ。どちらも暗号化キーの守り方が肝です。

ハル
ハル鍵のしまい方って、何パターンあるんですか？
棟梁
棟梁よく使うのは2つ。「ファイル型の金庫」と「集中管理型の金庫」だ。
🗄

ファイルベースの金庫

鍵を暗号化してファイルに入れ、そのファイルをバージョン管理に置く方式。

ファイル型
🏦

集中型の金庫

ネットワーク越しに使う「金庫番のいる窓口（Webサービス）」。鍵を暗号化してMySQL等のデータ置き場に保存。

集中型
ハル
ハルでもファイルを暗号化するには暗号化キーが要りますよね。それ自体が鍵じゃないですか。どこにしまうんですか？
棟梁
棟梁いいところに気づいた。それがこの方式の難しさで、暗号化キーをどう守るかが残る。設計図に置いたら意味がないし、別のキーで暗号化しても問題が先送りになるだけだ。
ハル
ハルじゃあどうするんですか？
棟梁
棟梁解決策は2つ。1つはKMS（キーマネジメントサービス）に暗号化キーを預けて、業者に鍵守りを任せる。もう1つは各職人がPGPキー（公開鍵と秘密鍵のペア）を持ち、公開鍵で暗号化して、対応する秘密鍵を持つ職人だけが開けられるようにする。
棟梁
棟梁集中型でも暗号化キーは要るが、それはサービス自身が管理するか、クラウドのKMSに任せる。

🔑 たとえ話

鍵を金庫に入れても、その金庫を開ける「金庫の鍵」が要る。それを設計図に書いたら金庫の意味がない。そこで、金庫の鍵を「街の信頼できる鍵預かり所（KMS）」に丸ごと預けるか、職人それぞれが自分だけ開けられる個人ロッカー（PGP）に金庫の鍵をしまう、というわけだ。

📌 なぜこれが必要か / できること

  • 「ファイル型」と「集中型」の違いを理解し、後の節の選択につなげられる。
  • 暗号化キー自体をどう守るか（KMSやPGP）という核心の問題を理解できる。

📝 この項のまとめ

  • ファイル型：暗号化ファイルをバージョン管理に置く。暗号化キーはKMSやPGPで守る。
  • 集中型：金庫番の窓口に預ける。暗号化キーはサービス自身かKMSが守る。
  • どちらも「暗号化キーの守り方」が課題。

6.2.3 鍵（シークレット）にアクセスするインタフェイス

要するに： 金庫の窓口にはAPI（プログラム向け）、CLI（コマンド向け）、UI（画面向け）の3つがあります。

ハル
ハル金庫から鍵を出し入れする方法も決まってるんですか？
棟梁
棟梁たいていの金庫は3つの窓口を持っている。API、CLI、UIだ。
🔌

API

HTTP経由のネットワーク越し呼び出し窓口。プログラムから取り出すのに便利。アプリ起動時にDBパスワードを取りに行く、など。

⌨️

CLI

コマンドで操作する窓口。ファイル型の金庫はだいたいこれ。職人が手で扱ったりスクリプトを書いたりするのに便利。

🖥

UI

画面で操作する窓口。Web・デスクトップ・スマホから使える。チームの誰でも鍵を扱える。

📌 なぜこれが必要か / できること

  • 自動化したいならAPI/CLI、人が手で扱うならUI、と用途で窓口を選べるようになる。

📝 この項のまとめ

  • API：プログラムから取りに行く窓口。
  • CLI：コマンドやスクリプトで使う窓口。
  • UI：画面で操作する窓口。

6.3.1

プロバイダ

入場ゲートの鍵をどう渡すか

要するに： terraform apply ではまずクラウドの入場ゲートで身元確認される。その鍵を「人のユーザ」と「マシンユーザ」で分けて考えます。

ハル
ハルプロバイダって何でしたっけ？
棟梁
棟梁terraform apply を実行するとき、まずAWSという街の入場ゲートで「あなたは誰ですか」と聞かれる。それに答えるのがアクセスキー、つまり鍵だ。これをどこにしまい、どう渡すかが最初の問題だな。

絶対にやってはいけないのが、入場ゲートの鍵を設計図に丸書きすることです。

絶対NG例：ゲートの鍵を丸書き 
# これは「絶対にやってはいけない」見本
provider "aws" {
  region = "us-east-2"   # 使う地域（オハイオ）

  # 絶対ダメ！
  access_key = "(ACCESS_KEY)"   # アクセスキー（鍵のID）を丸書き
  secret_key = "(SECRET_KEY)"   # シークレットキー（鍵の本体）を丸書き
  # 絶対ダメ！
}
棟梁
棟梁ダメな理由はもう分かるな。安全じゃないし、そもそも人や環境ごとに違う鍵を使うのが普通だから、1つの鍵を全員に使わせるのは実用的でもない。
ハル
ハルじゃあ、誰がTerraformを動かすかで分けるんですね。
棟梁
棟梁そうだ。「人のユーザ」＝自分のパソコンで動かす職人と、「マシンユーザ」＝人が介さず自動で動かす仕組み（CIサーバなど）、この2つに分けて考える。

6.3.1.1 人のユーザ

要するに： 自分のパソコンで動かすなら、鍵は個人用金庫にしまい、環境変数でTerraformに渡す。aws-vaultなら使い捨ての一時鍵を渡せて安全。

ハル
ハルまず自分のパソコンで動かす場合ですね。鍵を設計図に書かないとなると、どこに渡すんですか？
棟梁
棟梁よくあるのは環境変数を使う方法だ。AWSならこうする。

AWSの鍵を環境変数にセットします。行頭にスペースを入れているのは履歴に残さないためです。

環境変数に鍵をセット 
# 行頭スペースで履歴に残さない
 export AWS_ACCESS_KEY_ID=(YOUR_ACCESS_KEY_ID)
 export AWS_SECRET_ACCESS_KEY=(YOUR_SECRET_ACCESS_KEY)
ハル
ハルなんでコマンドの先頭にスペースが入ってるんですか？
棟梁
棟梁いい目のつけどころだ。多くのシェルは打ったコマンドを履歴ファイル（~/.bash_historyなど）に残す。だが行頭をスペースで始めると履歴に書かれない。鍵をうっかり履歴に残さない工夫だ。効かないシェルなら HISTCONTROL を ignoreboth にするといい。
棟梁
棟梁環境変数の利点は3つ。(1)設計図に鍵を書かずに済む、(2)動かす人が自分の鍵を使える、(3)鍵がディスクではなくメモリ（電源を切れば消える一時記憶）だけに乗る。
ハル
ハルでも、そのアクセスキー自体はどこに保管するんですか？ 覚えるには長すぎますよね。
棟梁
棟梁そこだ。人のユーザは個人向けの金庫（1Password、LastPassなど）に鍵をしまう。そこからコピーして export に貼ればいい。よく使うならCLI付きの金庫が便利だ。1Passwordには op というCLIがある。

1Passwordにコマンドでログインします。

opでログイン 
# 1Passwordにコマンドでログイン
eval $(op signin my)

「aws-dev」という項目に保存したIDとシークレットを取り出して環境変数にセットします。

1Passwordから鍵を取り出す 
export AWS_ACCESS_KEY_ID=$(op get item 'aws-dev' --fields 'id')
export AWS_SECRET_ACCESS_KEY=$(op get item 'aws-dev' --fields 'secret')
ハル
ハルAWS専用のもっと簡単なやつとかないんですか？
棟梁
棟梁あるよ。aws-vault というツールだ。dev というプロファイルに鍵を保存するにはこうする。

aws-vaultに「dev」という名札で鍵を登録します（入力を求められます）。

aws-vault add 
aws-vault add dev
Enter Access Key Id: (YOUR_ACCESS_KEY_ID)
Enter Secret Key: (YOUR_SECRET_ACCESS_KEY)

中ではOS標準の金庫（macOSキーチェーン、Windows資格情報マネージャ）に安全にしまわれます。一度しまえば、こうしてAWSに認証してコマンドを実行できます。

aws-vault exec で一時鍵を使う 
# 一時的な鍵を使ってterraform applyを実行
aws-vault exec dev -- terraform apply
棟梁
棟梁exec は内部でAWS STSを使って、その場限りの一時鍵を取り出し、環境変数として渡す。だから永続的な鍵は金庫にしまったまま、実行プロセスには使い捨ての鍵しか渡さない。漏れたときの被害が最小になるんだ。IAMロールの引き受け、多要素認証（MFA）、Webコンソールログインにも対応している。
ハル
ハルなるほど。金庫から本物の鍵を出さずに、使い捨ての合鍵だけ渡すんですね！

🔑 たとえ話

本物のマスターキーは個人の頑丈な金庫にしまったまま渡さない。代わりに、その日だけ使えて夜になると自動で使えなくなる「使い捨ての合鍵」を作ってもらい、職人にはそれを渡す。たとえ合鍵を落としても、翌日にはただの鉄くずだ。aws-vaultはこの「使い捨て合鍵屋」の役目をしてくれる。

📌 なぜこれが必要か / できること

  • 設計図に鍵を書かずに、自分の鍵で安全にapplyできるようになる。
  • 一時鍵（使い捨て合鍵）の考え方が分かり、漏洩リスクを減らせる。

📝 この項のまとめ

  • 環境変数で鍵を渡せば、設計図に書かずメモリだけに乗せられる。
  • 行頭スペースで履歴に鍵を残さない工夫がある。
  • 鍵は個人用金庫（1Password等）に保管。op や aws-vault のCLIが便利。
  • aws-vault はSTSで一時鍵を渡すので最も安全。

6.3.1.2 マシンユーザ

要するに： 自動で動くCIサーバは金庫のパスワードを覚えられない。「どのマシンから、どのマシンへ」認証するかで答えが変わります。CircleCI・EC2上のJenkins・GitHub Actionsの3例を見ます。

ハル
ハル人なら金庫のパスワードを覚えられますけど、自動で動くCIサーバは覚えられませんよね。どうするんですか？
棟梁
棟梁そこがマシンユーザの問題だ。「どのマシンから、どのマシンへ」認証するかで答えが大きく変わる。3つの例を見よう。CircleCI、EC2上のJenkins、GitHub Actionsだ。
棟梁
棟梁先に言っておく。これから出すCI/CDの例は「どう認証するか」だけを示した単純化したものだ。本番で使える完全なCI/CDの作り方は9章で扱う。

例1：CIサーバとしてのCircleCI（鍵を保存する方式）

ハル
ハルCircleCIはどうやるんですか？
棟梁
棟梁CircleCIはマネージドなCI/CDだ。terraform apply を動かすジョブを設定ファイルに書く。

このファイル(.circleci/config.yml)はCircleCIにterraform applyの手順を教える設定です。

.circleci/config.yml 
version: '2.1'
orbs:
  # 再利用できる設定部品(Orb)でTerraformをインストール
  terraform: circleci/terraform@1.1.0

  # terraform applyを実行するジョブ
  terraform_apply:
    executor: terraform/default
    steps:
      - checkout         # コードをgit cloneで取得
      - terraform/init   # 'terraform init'を実行
      - terraform/apply  # 'terraform apply'を実行
workflows:
  deploy:
    jobs:
      - terraform_apply
    # mainブランチにコミットされた時だけ実行
    filters:
      branches:
        only:
          - main
棟梁
棟梁CircleCIでは専用のマシンユーザ（人ではなく自動化用のIAMユーザ）を作り、その鍵をCircleCIコンテキストに手でコピーして保存する。ビルドが走ると、CircleCIがその鍵を環境変数としてワークフローに渡してくれる。

ハル
ハル便利そうですけど、欠点はありますか？
棟梁
棟梁2つある。(a)鍵を手で管理しないといけない、(b)そのせいで一度保存したらほぼ変えない「ずっと使える永続鍵」を使わざるを得ない。実際、CircleCIに保存していた鍵が漏れた事故もある。次の2例でもっと良いやり方を見よう。

🔑 たとえ話

CircleCIという外部の業者の受付に、本物の合鍵を1本あずけっぱなしにする方式だ。受付は鍵を職人ロボットに渡してくれるが、合鍵は人が手で持ち込み、めったに作り直さない。受付が泥棒に入られたら、その合鍵がそのまま盗まれてしまう。

📝 この項のまとめ

  • CircleCIコンテキストに鍵を手でコピーして保存。
  • ビルド時に環境変数として自動で渡る。
  • 欠点は「手動管理が必要」「永続鍵になりがち」の2つ。

例2：JenkinsをCIサーバとして動かすEC2インスタンス（IAMロールを使用）

ハル
ハルAWSの中で動いてるCIサーバなら、もっと楽になるんですか？
棟梁
棟梁ぐっと楽になる。EC2インスタンスの上でJenkinsを動かしているなら、そのEC2にIAMロールを付けるのがおすすめだ。
ハル
ハルIAMロールって、IAMユーザと何が違うんですか？
棟梁
棟梁IAMロールは権限を付けられる点はIAMユーザと似ているが、人に紐づかず、パスワードもアクセスキーも持たない。代わりに他のもの（EC2など）がそのロールを「引き受ける」ことで、その場限りの権限を得る。建物で言えば「夜間警備員という役割の制服と一時鍵」で、当番になった人がその場で借りるんだ。

まず、いつものEC2インスタンス（クラウド上の仮想サーバ）を1台建てる設計図があるとします。

EC2インスタンス 
resource "aws_instance" "example" {
  ami           = "ami-0fb653ca2d3203ac1"  # 使うOSイメージのID
  instance_type = "t2.micro"               # サーバのグレード
}

まず「誰がこの役割を引き受けられるか」を決める許可書を作ります。EC2サービスに引き受けを許す例です。

引き受け許可書（assume_role） 
# 「EC2サービスがこのロールを引き受けてよい」という許可書
data "aws_iam_policy_document" "assume_role" {
  statement {
    effect  = "Allow"                  # 許可する
    actions = ["sts:AssumeRole"]       # ロールの引き受けという行為を

    principals {
      type        = "Service"          # 相手はAWSのサービス
      identifiers = ["ec2.amazonaws.com"]  # そのうちEC2サービスに
    }
  }
}

その許可書を使ってIAMロール本体（権限の役割）を作ります。

IAMロール本体 
resource "aws_iam_role" "instance" {
  name_prefix        = var.name                              # ロール名の頭につける文字
  assume_role_policy = data.aws_iam_policy_document.assume_role.json  # 上の許可書
}

このままでは何の権限もないので、「このロールで何ができるか」を決める権限の許可書（EC2の管理者権限）を作ります。

権限の許可書（ec2_admin） 
# 「EC2に対して何でもしてよい」という権限の許可書
data "aws_iam_policy_document" "ec2_admin_permissions" {
  statement {
    effect    = "Allow"        # 許可する
    actions   = ["ec2:*"]      # EC2に対するすべての操作を
    resources = ["*"]          # すべての対象に
  }
}

その権限の許可書をロールに貼り付けます。

権限をロールに貼り付け 
resource "aws_iam_role_policy" "example" {
  role   = aws_iam_role.instance.id                              # 貼り付け先のロール
  policy = data.aws_iam_policy_document.ec2_admin_permissions.json  # 貼り付ける権限
}

EC2が自動でロールを引き受けられるよう、EC2とロールを結びつける入れ物（インスタンスプロファイル）を作ります。

インスタンスプロファイル 
resource "aws_iam_instance_profile" "instance" {
  role = aws_iam_role.instance.name   # 結びつけるロールの名前
}

そしてEC2にそのプロファイルを取り付けます。

EC2にプロファイルをアタッチ 
resource "aws_instance" "example" {
  ami           = "ami-0fb653ca2d3203ac1"
  instance_type = "t2.micro"

  # インスタンスプロファイルをアタッチ（取り付ける）
  iam_instance_profile = aws_iam_instance_profile.instance.name
}
ハル
ハルこれでEC2が勝手に鍵を手に入れるんですか？ 魔法みたいです。
棟梁
棟梁仕組みがあるんだ。AWSは各EC2の中にインスタンスメタデータのエンドポイントとして http://169.254.169.254 という入口を用意している。これはそのインスタンスの中からしか触れない。SSHでログインして curl で覗くとこうなる。

EC2にSSHでログインして、メタデータの窓口を覗いてみた例です。

メタデータ窓口を覗く 
ssh ubuntu@<IP_OF_INSTANCE>
Welcome to Ubuntu 20.04.3 LTS (GNU/Linux 5.11.0-1022-aws x86_64)
(...)

curl http://169.254.169.254/latest/meta-data/
ami-id
ami-launch-index
ami-manifest-path
block-device-mapping/
events/
hibernation/
hostname
identity-credentials/
(...)
棟梁
棟梁ロールが（インスタンスプロファイル経由で）付いていると、このメタデータの中にAWS認証用の一時鍵が入る。TerraformのようにAWS SDKを使うツールは、この窓口から自動で鍵を取りに行くことを知っている。だからこのEC2上で terraform apply を実行すると、勝手にロールを引き受けて認証し、EC2管理者権限で動けるんだ。
棟梁
棟梁注意点が2つ。1つ目。この窓口は標準ではEC2上の全OSユーザが触れてしまう。だから iptables や nftables で、アプリを動かすユーザ（例：app）だけが触れるよう閉じる。起動時にしか鍵が要らないなら、起動後に窓口を完全に無効化してしまう手もある。2つ目。2019年に、先にトークン（一時的な合言葉）を取らないと情報を取れないIMDSv2が出た。
棟梁
棟梁IAMロールの利点は、(a)鍵を手で管理しなくていい、(b)窓口から渡される鍵は常に一時的で自動でローテートされる、ことだ。
ハル
ハルAWSの中で動いてるからこそ、AWSが自動で合鍵を配ってくれるんですね。

🔑 たとえ話

EC2はAWSという街の中に建てた建物だ。街の管理人は、その建物の壁に「ロール（夜間警備員）の制服と一時鍵を渡す小窓」を埋め込んでくれる。建物の中の人が小窓から手を出せば、その日の一時鍵が自動で配られ、夜が明けると鍵は無効になる。手で合鍵を持ち込む必要がない。ただし小窓に誰でも手を伸ばせると危ないので、信頼した職人だけが届くように囲っておく。

📌 なぜこれが必要か / できること

  • 永続鍵を手で管理する手間と漏洩リスクをなくせる。
  • IAMロール・インスタンスプロファイル・メタデータ窓口の関係を理解できる。

📝 この項のまとめ

  • IAMロールは人に紐づかず永続鍵も持たない「役割」。
  • EC2はインスタンスプロファイル経由でロールを引き受ける。
  • メタデータ窓口（169.254.169.254）から一時鍵が自動配布される。
  • 利点は手動管理不要・一時鍵の自動ローテート。窓口はアクセス制限すべき。

例3：CIサーバとしてのGitHub Actions（OIDC使用）

ハル
ハルGitHub Actionsは、AWSの外で動きますよね。CircleCIみたいに手動コピーするしかないんですか？
棟梁
棟梁昔はそうだった。でも2021年からGitHub ActionsはOIDCという良いやり方に対応した。CIシステムとクラウド業者の間に「信頼関係」を結んでおくと、手で鍵を管理しなくてもCIが業者に認証できる。AWS・Azure・Google Cloudに対応。CircleCIも2022年3月にOIDC対応したよ。

GitHub Actionsのワークフロー(.github/workflows/terraform.yml)はこう書きます。mainブランチのコミットにだけ実行します。

terraform.yml（ワークフロー） 
name: Terraform Apply
# mainブランチのコミットに対してだけ実行
on:
  push:
    branches:
      - 'main'
jobs:
  TerraformApply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2

      # Hashicorpのsetup-terraformアクションでTerraformを実行
      - uses: hashicorp/setup-terraform@v1
          with:
            terraform_version: 1.1.0
            terraform_wrapper: false
        run: |
          terraform init
          terraform apply -auto-approve
棟梁
棟梁最初のステップは、AWSアカウントの中にIAM OIDC IDプロバイダを作り、GitHub Actionsのサムプリントを信頼するよう設定することだ。サムプリントは tls_certificate データソースで取る。

「GitHubを信頼する」という身元確認の窓口をAWSアカウント内に作り、GitHubの証明書の指紋を取得します。

OIDC IDプロバイダ + 指紋取得 
resource "aws_iam_openid_connect_provider" "github_actions" {
  url             = "https://token.actions.githubusercontent.com"  # GitHubの身元証明の発行元
  client_id_list  = ["sts.amazonaws.com"]                          # 受け取る相手
  thumbprint_list = [
    data.tls_certificate.github.certificates[0].sha1_fingerprint   # GitHubの証明書の指紋
  ]
}

# GitHubのOIDCサムプリント（指紋）を取得
data "tls_certificate" "github" {
  url = "https://token.actions.githubusercontent.com"
}
棟梁
棟梁補足だが、2023年7月からはAWSにサムプリントを渡す必要がなくなった。ただしAPI側がまだ追いついておらず、文字列自体は渡す必要がある。仕様が変わるので、動かないときは使うActionのドキュメントを確認してくれ。次に、前と同じくEC2管理者権限のIAMロールを作るが、「引き受けるためのポリシー」はこう変わる。

「GitHubのOIDC窓口経由でこのロールを引き受けてよい」という許可書を作ります。条件で許可するリポジトリ・ブランチを絞ります。

OIDC用 引き受け許可書 
data "aws_iam_policy_document" "assume_role_policy" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]  # Web身元証明での引き受けを許す
    effect  = "Allow"

    principals {
      identifiers = [aws_iam_openid_connect_provider.github_actions.arn]  # 上のOIDC窓口
      type        = "Federated"                                       # 外部の身元連携
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      # 指定したリポジトリとブランチだけが引き受けられる
      values = [
        for a in var.allowed_repos_branches :
        "repo:${a["org"]}/${a["repo"]}:ref:refs/heads/${a["branch"]}"
      ]
    }
  }
}
棟梁
棟梁この condition（条件）ブロックが超大事だ。これがないと、世界中のあらゆるGitHubリポジトリがお前のAWSに認証できてしまう。だから許可するリポジトリとブランチを変数で絞る。

「このIAMロールを引き受けてよいGitHubのリポジトリとブランチ」の一覧を受け取る変数です。

allowed_repos_branches 変数 
variable "allowed_repos_branches" {
  description = "GitHub repos/branches allowed to assume the IAM role."
  type = list(object({
    org    = string   # 組織名
    repo   = string   # リポジトリ名
    branch = string   # ブランチ名
  }))
  # 使用例:
  # allowed_repos_branches = [
  #   { org = "brikis98", repo = "terraform-up-and-running-code", branch = "main" }
  # ]
}

ワークフローの先頭で、ビルドに身元証明トークンを発行する権限を与えます。

id-token: write 権限 
# このビルドが身元証明トークンを発行する権限
permissions:

OIDCでAWSに認証

棟梁
棟梁補足だが、configure-aws-credentials も setup-terraform も、原著ではv1指定だが2023年7月時点ではv2が最新だ。
ハル
ハルつまり、許可したリポジトリ・ブランチでビルドが走ったときだけ、GitHubが一時鍵で勝手にロールを引き受けてくれるんですね。鍵の手動管理ゼロ！
棟梁
棟梁その通り。AWSの外で動くのに、永続鍵も手動管理も要らない。これがOIDCの強みだ。

🔑 たとえ話

GitHubは別の街で働くロボット職人だ。AWSの街の門番に「token.actions… という工房の、しかも『この組織・このリポジトリ・このブランチ』の職人だけは身分証を見せれば一時鍵を渡してよい」と事前に約束（信頼関係）を結んでおく。すると合鍵を郵送しなくても、本人が身分証を見せるだけで門番がその場限りの鍵を発行してくれる。約束に「この職人だけ」という条件を必ず付けないと、世界中の誰でも入れてしまうので注意だ。

📌 なぜこれが必要か / できること

  • AWS外のCIでも、永続鍵を持たずに安全に認証できるようになる。
  • OIDC IDプロバイダ・引き受けポリシー・条件の絞り込みの役割を理解できる。

📝 この項のまとめ

  • OIDCはCIと業者の間に信頼関係を結ぶ仕組み。
  • AWS内にIAM OIDC IDプロバイダを作り、GitHubを信頼させる。
  • 引き受けポリシーの condition で許可リポジトリ・ブランチを必ず限定。
  • 手動管理不要・永続鍵不要・AWS外でも動く。

6.3.2.1 環境変数

要するに： 鍵を設計図から切り離せて安価・柔軟。ただしTerraformの外で管理するため標準化しづらく、設定漏れも起きやすい。

棟梁
棟梁1つ目は環境変数。Terraformは環境変数を読む機能を持っているから、設計図に鍵を書かずに済む。まず変数を宣言する。

データベースの管理人の名前とパスワードを受け取る箱（変数）を宣言します。sensitive = true で画面に値を出さなくします。

variable "db_username" {
  description = "The username for the database"
  type        = string
  sensitive   = true   # 秘密扱い。plan/applyの画面に値を表示しない
}

variable "db_password" {

  type        = string
  sensitive   = true   # 秘密扱い
}
ハル
ハルsensitive = true って何ですか？
棟梁
棟梁sensitiveパラメータだ。これを付けると plan や apply の表示でこの値を伏せ字にしてくれる。鍵がうっかり画面やログに出るのを防ぐ。あと、鍵を設計図に置かないから default（初期値）は付けない。

宣言した変数をリソースに渡します。

変数をリソースに渡す 
resource "aws_db_instance" "example" {
  # ...（中略）...

  # シークレットをリソースに渡す

  password = var.db_password   # 変数からパスワード
}

  • 既存のどんな金庫とも組み合わせて鍵を渡せるようになる。

  • 標準化しづらく設定漏れが起きやすいのが欠点。

6.3.2.2 暗号化されたファイル

要するに： 鍵を暗号化ファイルにしてバージョン管理に置く方式。コードで管理でき設定漏れを減らせるが、扱いが面倒でローテーションが難しく、費用もかかる。sopsで手間を軽減できます。

ハル
ハル2つ目は暗号化ファイルですね。鍵を暗号化してファイルに入れて、バージョン管理に置く、と。
棟梁
棟梁そうだ。ただ暗号化には暗号化キーが要る。これ自体が鍵だから、KMSかPGPで守る。ここではAWS KMSを使う例を見よう。まずAWSが管理する暗号化キー、KMSキー（CMK）を作る。誰がこのキーを使えるかを決めるキーポリシーが要る。

AWSへの入場ゲートを開き、今ログインしている自分自身の情報を取得します。

自分の情報を取得 
provider "aws" {
  region = "us-east-2"
}

data "aws_caller_identity" "self" {}

「今の自分にこの暗号化キーの全権限を与える」というキーポリシーを作ります。

キーポリシー 
data "aws_iam_policy_document" "cmk_admin_policy" {
  statement {
    effect    = "Allow"        # 許可する
    resources = ["*"]          # すべての対象に
    actions   = ["kms:*"]      # KMSのすべての操作を
    principals {
      type        = "AWS"
      identifiers = [data.aws_caller_identity.self.arn]  # 相手は「今の自分」
    }
  }
}

そのポリシーを使ってCMK（暗号化キー）を作ります。

CMKを作成 
resource "aws_kms_key" "cmk" {
  policy = data.aws_iam_policy_document.cmk_admin_policy.json   # 上のキーポリシー
}

CMKは長い数字でしか呼べないので、人間が読みやすい別名（エイリアス）を付けます。

エイリアス（別名）を付ける 
resource "aws_kms_alias" "cmk" {
  name          = "alias/kms-cmk-example"   # 付ける別名
  target_key_id = aws_kms_key.cmk.id        # 別名を付ける対象のキー
}
ハル
ハルこの暗号化キーの中身（本物の鍵）は見られるんですか？
棟梁
棟梁見られない。設計上、中の暗号化キーは取り出せないから、うっかり漏らすこともない。キーに触れるのはAWSだけ。我々はAWSのAPI/CLI越しに「暗号化して」「復号して」と頼むだけだ。

まず、鍵を入れたファイルを作ります。まだ暗号化していないので、これはバージョン管理に入れてはいけません。

db-creds.yml（暗号化前） 
# まだ暗号化していない。バージョン管理に入れるな
username: admin
password: password

ファイルの中身をKMSで暗号化し、結果を別ファイルに書き出す小さなスクリプト(encrypt.sh)です。

encrypt.sh 
#!/bin/bash
# ファイルの中身をKMSで暗号化し、結果を別ファイルに書き出す

CMK_ID="$1"
AWS_REGION="$2"
INPUT_FILE="$3"
OUTPUT_FILE="$4"

echo "CMK $CMK_ID を使って $INPUT_FILE の中身を暗号化します..."
ciphertext=$(aws kms encrypt \
  --key-id "$CMK_ID" \
  --region "$AWS_REGION" \
  --plaintext "fileb://$INPUT_FILE" \
  --output text \
  --query CiphertextBlob)

echo "結果を $OUTPUT_FILE に書き出します..."
echo "$ciphertext" > "$OUTPUT_FILE"

echo "完了！"

encrypt.shを使ってdb-creds.ymlを暗号化し、db-creds.yml.encryptedに保存します。

実行例 
./encrypt.sh \
  alias/kms-cmk-example \
  us-east-2 \
  db-creds.yml \
  db-creds.yml.encrypted

CMK alias/kms-cmk-example を使って db-creds.yml の中身を暗号化します...
結果を db-creds.yml.encrypted に書き出します...
完了！
棟梁
棟梁これで元のプレーンテキスト db-creds.yml は消し、暗号化済みの db-creds.yml.encrypted だけをバージョン管理に安全に入れられる。Terraformで使うには、まず aws_kms_secrets データソースで復号する。

暗号化ファイルを読み込み、KMSのキーで中身を復号します。

復号（aws_kms_secrets） 
data "aws_kms_secrets" "creds" {
  secret {
    name    = "db"
    payload = file("${path.module}/db-creds.yml.encrypted")  # 暗号化ファイルを読む
  }
}

復号した中身（YAML）を読み解いて、db_credsという入れ物に保存します。

YAMLを読み解く 
locals {
  db_creds = yamldecode(data.aws_kms_secrets.creds.plaintext["db"])
}

復号した鍵をデータベースに渡します。

リソースに渡す 
resource "aws_db_instance" "example" {
  # ...（中略）...
  username = local.db_creds.username   # 復号した管理人名
  password = local.db_creds.password   # 復号したパスワード
}
ハル
ハルでも編集するたびに毎回あの長いコマンドで復号して、直して、また暗号化するんですか？ 面倒すぎませんか？
棟梁
棟梁その通り、扱いにくい。しかも編集中はプレーンテキストがパソコンに残るから、うっかりバージョン管理に入れない注意も要る。そこでsopsが便利だ。sops <FILE> と打つと、自動で復号してエディタで開き、保存して閉じると自動で再暗号化してくれる。2022年時点でAWS KMS・GCP KMS・Azure Key Vault・PGPに対応。
ハル
ハルTerraformはsopsのファイルをそのまま読めるんですか？
棟梁
棟梁そこは注意だ。Terraformはsopsの暗号化ファイルのネイティブ復号にまだ対応していない。だからcarlpett/sopsのようなサードパーティプロバイダを使うか、Terragruntユーザなら組み込みの sops_decrypt_file 関数を使う。
✅

利点

・プレーンテキストの鍵を設計図に置かずに済む
・暗号化された形でバージョン管理に入り、パッケージ化・テストができ設定漏れを減らせる
・対応形式なら取り出しが簡単
・AWS KMS・GCP KMS・PGPなど色々な暗号化に対応
・すべてコードに書ける（sops統合にはサードパーティが要る）

⚠️

欠点

・保存が難しい（多くのコマンドかsops等の外部ツールと学習が要る）
・暗号化キーとテストデータ準備が要り自動テスト統合が難しい
・暗号化されてもバージョン管理に残るのでローテーション・無効化が難しい。暗号化キーを盗まれると全部復号される
・マネージドキーは費用（AWS KMSはキー1つ月1ドル、暗号/復号API1万回0.03ドル、一般に月1〜10ドル、大規模で月10〜50ドル）
・標準化が難しく、誤ってプレーンテキストをチェックインするミスも比較的多い

🔑 たとえ話

鍵を頑丈な箱（暗号化ファイル）に入れて、その箱ごと設計図と一緒に倉庫（バージョン管理）にしまう方式だ。箱を開ける鍵は街の鍵預かり所（KMS）にあずける。箱は設計図と一緒に運べて履歴も残るので便利だが、開け閉めの作業がいちいち面倒で、預かり所の鍵を盗まれると過去にしまった箱が全部開けられてしまう。sopsは「箱を自動で開け閉めしてくれる職人」だ。

📌 なぜこれが必要か / できること

  • 鍵をコードと一緒にバージョン管理・テストできるようになる。
  • KMSで暗号化キーを安全に預け、Terraformから復号して使えるようになる。

📝 この項のまとめ

  • KMSでCMK（暗号化キー）を作り、エイリアスで呼びやすくする。
  • aws kms encrypt で暗号化、aws_kms_secrets ＋ yamldecode で復号して使う。
  • sopsで暗号化・復号を透過的にできる（Terraformはサードパーティ経由）。
  • 設定漏れは減るが、面倒・ローテーション困難・有料が欠点。

・バージョン管理・パッケージ化・テストができず環境間の設定漏れが起きやすい
・マネージドな金庫は費用（AWS KMSキー1つ月1ドル、API1万回0.03ドル、一般に月10〜25ドル、大規模で月数百ドルも）
・HashiCorp Vault等のセルフマネージドは運用費＋開発者の時間がかかり月数千ドルになることも
・取り出しが難しい（複数マシン間の安全な認証が必要）
・外部システムに依存し自動テスト統合が難しい（モックかテストデータが要る）

🔑 たとえ話

街の中心に建つ大きな金庫ビル（集中型サービス）に鍵をあずける方式だ。受付（Web UI）から鍵を入れるのは簡単で、金庫番が「誰がいつどの鍵を借りたか」を帳簿（監査ログ）に必ず記録し、古い鍵は定期的に新品に交換（ローテーション）してくれる。ただし金庫ビルの利用料は高めで、遠くの建物から鍵を借りに来るたびに「あなたは誰か」を確認する手間がかかる。

📌 なぜこれが必要か / できること

  • Web UIで鍵を管理し、コードで安全に読み出せるようになる。
  • ローテーション・監査ログという「漏れたときに効く」機能を使えるようになる。

📝 この項のまとめ

  • aws_secretsmanager_secret_version で読み出し、jsondecode で読み解く。
  • 保存が楽、ローテーション・監査・標準化に強い。
  • 費用が高め、取り出し・テストが難しいのが欠点。
6.3.3

ステートファイルとプランファイル

渡した鍵が台帳に残る落とし穴

要するに： どのテクニックで渡しても、鍵はステートファイルにもプランファイルにもプレーンテキストで残る。だから両ファイルを暗号化バックエンドに置き、アクセスを鍵と同等に厳しく管理します。

ハル
ハルこれで鍵の渡し方はバッチリですね！
棟梁
棟梁まだ落とし穴がある。あと2箇所、鍵が漏れる場所があるんだ。ステートファイルとプランファイルだ。

6.3.3.1 ステートファイル

棟梁
棟梁不意打ちなんだが、どのテクニックを使おうと、リソースやデータソースに渡した鍵は、Terraformのステートファイル（terraform.tfstate）にプレーンテキストで保存されてしまうんだ。
ハル
ハルええっ！？ せっかく暗号化したのに、台帳に丸書きされちゃうんですか？
棟梁
棟梁そうなんだ。環境変数でも暗号化ファイルでも集中金庫でも、aws_db_instance に渡した時点でステートに丸書きされる。2014年から指摘されている問題で、きれいな解決の予定はまだない。ステートから鍵を消す回避策もあるが、不安定でリリースごとに壊れやすいから、おすすめしない。台帳そのものを金庫にしまうんだ。2つやることがある。
🔒

やること1：暗号化対応バックエンドに保存

ローカルの terraform.tfstate をバージョン管理に置くのではなく、S3・GCS・Azure Blob Storage のような暗号化できるバックエンドを使う。通信時（TLS）もディスク上（AES-256）も暗号化される。

🚧

やること2：触れる人を厳しく絞る

ステートには鍵が入りうるから、最低でも鍵そのものと同じくらい厳しくアクセスを管理する。S3なら本番バケットへのアクセスは信頼できる少数の職人か本番デプロイ用CIだけに絞る。

6.3.3.2 プランファイル

ハル
ハルプランファイルって何ですか？
棟梁
棟梁terraform plan の結果はファイルに保存できる。

planの結果をexample.planというファイルに保存します。

plan -out で保存 
terraform plan -out=example.plan

保存したプランに対してapplyすると、planで確認したのと寸分違わぬ変更が適用されます。

保存したプランをapply 
terraform apply example.plan
棟梁
棟梁便利な機能だが、重要な注意がある。ステートと同じで、リソースやデータソースに渡した鍵は、プランファイルにもプレーンテキストで保存されてしまう。aws_db_instance にplanすれば、プランファイルにDBの名前とパスワードが丸書きで入る。
ハル
ハルステートと同じ落とし穴ですね。じゃあ対策も同じ？
棟梁
棟梁ほぼ同じだ。2つある。
🔒

やること1：プランファイルを暗号化する

保存するなら通信時（TLS）も保存時（AES-256）も暗号化する。両方を暗号化できるS3バケットに置く、など。

🚧

やること2：触れる人を厳しく絞る

プランファイルにも鍵が入りうるから、最低でも鍵そのものと同じくらい厳しくアクセスを管理する。S3なら本番バケットは信頼できる少数の職人か本番デプロイ用CIだけ。

🔑 たとえ話

鍵をどんなに上手に手渡ししても、工房は作業のたびに「この建物の現状」を台帳（ステート）と作業予定書（プラン）に書き写す。そこに鍵の番号がそのまま転記されてしまうのだ。だから台帳と予定書そのものを、頑丈な金庫（暗号化バックエンド）にしまい、その金庫を開けられる職人を本物の鍵と同じくらい厳しく絞る必要がある。

📌 なぜこれが必要か / できること

  • 「鍵を暗号化しても台帳経由で漏れる」という盲点を防げるようになる。
  • ステート・プランの暗号化とアクセス制御という仕上げの守りができるようになる。

📝 この項のまとめ

  • 渡した鍵はステートファイル・プランファイルにプレーンテキストで残る。
  • 解決のきれいな予定はなく、消す回避策は不安定で非推奨。
  • ステートは暗号化対応バックエンド（S3等）に保存し、アクセスを厳しく絞る。
  • プランファイルも暗号化し、アクセスを鍵と同等に厳しく絞る。

章末の理解度チェック（全5問）

自分の言葉で答えてみよう

この章を読み終わったあと、自分の言葉で答えてみてください。答えは折りたたみの中にあります。

第1問鍵を丸書きしてはいけない理由

パスワードを設計図（Terraformコード）に直接書いてバージョン管理に入れると、なぜ危険でしょうか。理由を2つ以上、自分の言葉で説明してください。

✅ 解答例を見る
設計図を見られる人全員がパスワードを手に入れてしまううえ、設計図をコピーしたあらゆるパソコン（職人のPC、CIサーバ、バックアップ装置など）に鍵のコピーが残ってしまうから。さらに、誰が見たかの記録が取れず、後から鍵を無効化することもできず、一度漏れると被害を止められない。
📝 採点ポイント
・アクセス権がある全員に鍵が渡ってしまう点
・多数のパソコンにコピーが残る点
・監査や無効化ができない点
第2問IAMロールとOIDCの使いどころ

CIサーバがAWSに認証するとき、「AWSの中で動いている場合」と「AWSの外で動いている場合」で、それぞれおすすめの方法を1つずつ挙げ、共通する利点を説明してください。

✅ 解答例を見る
AWSの中（EC2上のJenkinsなど）で動くならIAMロール、AWSの外（GitHub Actionsなど）で動くならOIDCがおすすめ。どちらも鍵を手で管理する必要がなく、ずっと使える永続鍵ではなく、その場限りの一時鍵を使うので、漏れたときの被害が小さくて済む。
📝 採点ポイント
・AWS内＝IAMロールを挙げている
・AWS外＝OIDCを挙げている
・手動管理不要・一時鍵という共通利点に触れている
第3問リソースに鍵を渡す3方式の違い

リソースやデータソースに鍵を渡す3つの方法（環境変数・暗号化ファイル・シークレットストア）のうち、「ローテーションや無効化、監査ログに最も強いのはどれか」を答え、その代わりの欠点も1つ挙げてください。

✅ 解答例を見る
最も強いのは集中型のシークレットストア（AWS Secrets ManagerやHashiCorp Vaultなど）。鍵の入れ替えや取り消し、誰が触れたかの記録に対応している。ただし費用が高めで、複数マシン間の認証や自動テストとの組み合わせが難しいのが欠点。
📝 採点ポイント
・シークレットストアを選んでいる
・ローテーション・無効化・監査の強みに触れている
・費用やテスト・取り出しの難しさなど欠点を1つ挙げている
第4問ステートファイルの落とし穴

鍵を暗号化ファイルやシークレットストアから安全に読み込んだのに、それでも鍵が漏れる可能性が残るのはなぜですか。どう対策すればよいかも答えてください。

✅ 解答例を見る
リソースやデータソースに渡した鍵は、どんな方法で読み込んでもTerraformのステートファイル（とプランファイル）にプレーンテキストで保存されてしまうから。対策として、S3など暗号化に対応したバックエンドにステートを保存し、通信時も保存時も暗号化したうえで、バックエンドに触れる人を鍵そのものと同じくらい厳しく絞る。
📝 採点ポイント
・ステート（とプラン）に鍵がプレーンテキストで残る点
・暗号化対応バックエンド（S3等）の利用
・アクセス制御を厳しくする点
第5問sensitive パラメータの役割

変数に sensitive = true を付けると何が起きますか。なぜそれが鍵の管理で役立つのか説明してください。

✅ 解答例を見る
sensitive = true を付けると、Terraformが plan や apply の画面でその値を伏せ字にして表示しなくなる。鍵がうっかり画面やログに出力されて、見られたり記録に残ったりするのを防げるので、鍵の漏洩リスクを下げられる。
📝 採点ポイント
・planやapplyで値が表示されなくなる点
・画面やログへの漏洩を防ぐ目的
・鍵（機密情報）に使うものだと理解している
