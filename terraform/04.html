モジュール module / モジュール

再利用できる「部品のかたまり」。あるフォルダの中にあるTerraform設定ファイルの集まり。工場で量産する間取りユニットにあたる。

ルートモジュール root module

一番上で直接実行する入り口のモジュール。現場に直接組み立てる建物そのもの。

再利用可能なモジュール reusable module

他のモジュールから呼び出して使う部品。工場で量産して各現場に運ぶユニット。

ステージング staging

社内テスト用の練習現場。本番にそっくりだが、こっそり試せる。

本番 production

実際のお客さんが使う現場。失敗が許されない場所。

入力変数 variable

モジュールに外から値を渡す窓口。間取りユニットの「オプション注文表」。

ローカルな値 local values

モジュール内だけで使う名前付きの値。外から上書きできない。部品に貼る用途ラベル。

出力変数 output

モジュールが外に返す値。ユニットの管理番号を現場に教えるイメージ。

ハードコード hardcode

値を直接コードに書き込んで固定すること。型番が決め打ちの表札。

マジックナンバー magic number

意味の説明なしに直接書かれた謎の数値。80 や -1 など。

init terraform init

準備コマンド。プロバイダのインストール・バックエンド設定・モジュールのダウンロードの3役をこなす。

DRY Don't Repeat Yourself

同じことを繰り返し書かない、という考え方。コピペを避ける。

templatefile ビルトイン関数

外部ファイルを読み込んで変数を埋め込む関数。設計図に部材を貼り込む。

path.module パス参照

「このモジュールがあるフォルダ」を指す書き方。ユニット内の部材の場所を示す。

インラインブロック inline block

リソースの中に直接書き込む設定のかたまり。壁に作り付けの窓。

VPC Virtual Private Cloud

クラウド上の自分専用の仮想ネットワーク。建物を建てる敷地と塀。

Gitタグ tag

あるコミット（保存時点）に付ける目印の名前。ユニットの「型番」。

セマンティックバージョニング semantic versioning

MAJOR.MINOR.PATCH という意味のあるバージョン付けルール。

この章で作る2つの現場（導入）あらすじ / 要するに / なぜ必要か

要するに：同じ構成を2つ以上の現場で作るなら、コピペではなく1つのモジュール（再利用部品）にまとめて使い回す。

🏭 たとえ話：工房に届いた「同じ建物を2つ」の注文

グラウンドワークス工房に新しい依頼が来ました。「テスト用の現場（ステージング）と、お客さん向けの本番の現場、ほぼ同じ建物を2つ建ててほしい」。ハルは「同じ設計図をまるごとコピーすればいい」と言いますが、棟梁は首を横に振ります。今回学ぶのは「規格化された間取りユニットを工場で1回作って、いろんな現場で使い回す」という工房の知恵です。

ハル
ハル棟梁、前の章でロードバランサとサーバ群とデータベースのある建物を1つ建てましたよね。今度の依頼は何ですか？
棟梁
棟梁今度は同じような建物を「2つ」建てる依頼だよ。1つはステージング、もう1つは本番だ。
ハル
ハルステージングって何ですか？
棟梁
棟梁ステージングは社内テスト用の練習現場。本番と違ってこっそり試せる。コスト削減でサーバを少なくしたり安いサーバを使ったりするけど、理想は本番とほぼ同じ作りにすることだ。
ハル
ハルなら簡単。ステージングのフォルダをまるごとコピーして本番フォルダにすればいいんでしょ？
棟梁
棟梁それが一番やっちゃいけないことだ。Ruby でも同じ処理をあちこちコピペするかい？
ハル
ハルいえ、関数にまとめて呼び出します。

このコードは「あいさつ」という作業を1か所にまとめて、何度でも呼べるようにする例です。

Ruby: 処理を関数にまとめて使い回す 
# 関数（処理のかたまり）をある1か所で定義する
def example_function()
  puts "Hello, World"
end

# まったく別の場所から、その作業を呼び出して使い回す
example_function()
棟梁
棟梁それと同じ発想だ。Terraform でその「処理のかたまり」にあたるのが モジュール。コピペではなく1つのモジュールを両方の現場で使い回す。
ハル
ハルプレハブ工場で間取りユニットを1個作っておいて、トラックでいろんな現場に運んで設置する、みたいな感じですか？
棟梁
棟梁まさにそれだ。モジュールは「再利用できて、手入れしやすくて、テストもできる」コードの要。やがて何もかもをモジュールにして、会社の中で部品ライブラリを共有するようになるよ。

💡 なぜこれが必要か / これを知るとできること

  • コピペは「直すとき全部直す」羽目になるが、モジュールなら1か所直せば全現場に反映できる。
  • ステージングと本番のような「ほぼ同じ環境」をブレなくそろえられる。
  • 新しい現場を数行のコードで立ち上げられ、人が作った部品を取り込むこともできる。
  • テスト環境だけ新しい部品を試して、本番に影響を出さない安全な進め方ができる。

📌 この項のまとめ

  • ステージング = テスト用の現場、本番 = お客さん向けの現場。理想は両者をほぼ同じ構成に。
  • コピペではなくモジュールで使い回すのが正解。
  • この章で学ぶのは「基礎・入力・ローカル値・出力・注意点・バージョン管理」の6本柱。
  • 本のサンプルコードは GitHub（github.com/brikis98/terraform-up-and-running-code）から入手できる。
4.1

モジュールの基本フォルダの集まり / source / init / ハードコードの危険

要するに：モジュールはフォルダ内の設定ファイルの集まり。再利用するには module ブロックで source を指定して呼び出し、init で取り込む。ただし名前がハードコードのままだと衝突する。

ハル
ハルモジュールって、すごく難しい仕組みなんですか？
棟梁
棟梁拍子抜けするほど単純だよ。「あるフォルダの中にある設定ファイルの集まり」、それがもうモジュールだ。
ハル
ハルえっ、じゃあ今まで僕が書いてきたファイルも全部モジュールだった？
棟梁
棟梁そのとおり。直接 apply した設定ファイルも立派なモジュールだ。ただしそれはルートモジュールと呼ぶ。
ハル
ハルじゃあ「使い回せる部品」としてのモジュールは別ですか？
棟梁
棟梁そう。本当の力を見るには再利用可能なモジュールを作る必要がある。

🏭 たとえ話：現場の建物 vs 工場のユニット

現場に直接組み立てる建物そのものが「ルートモジュール」。工場で量産して各現場にトラックで運ぶ間取りユニットが「再利用可能なモジュール」です。これから、前の章で建てた建物を、工場で量産できるユニットに作り変えます。

工場（modules フォルダ）を作る手順

1

更地にする

stage/services/webserver-cluster で terraform destroy を実行し、前の章で建てたものを撤去する。

2

工場フォルダを作る

工房のトップレベルに modules という新しいフォルダ（=工場）を作る。

3

ファイルを移す

stage/services/webserver-cluster の中のファイルを全部 modules/services/webserver-cluster に移動する。

このフォルダの言葉スケッチは「工場(modules)」と「各現場(stage/prod)」を分けた様子を表します。

フォルダ構成（工場と現場の分離） 
modules/
└── services/
    └── webserver-cluster/   ← 量産する間取りユニット（再利用部品）の置き場
        ├── main.tf
        ├── variables.tf
        ├── outputs.tf
        └── user-data.sh
stage/
└── services/
    └── webserver-cluster/   ← ステージング現場（ユニットを呼び出すだけ）
prod/
└── services/
    └── webserver-cluster/   ← 本番現場（ユニットを呼び出すだけ）
ハル
ハル移動したら、何か直すことはありますか？
棟梁
棟梁ある。main.tf の provider（プロバイダ）の定義を削除してくれ。
ハル
ハルえっ、なんで消すんですか？ないと動かないんじゃ？
棟梁
棟梁プロバイダは「部品を使う側（現場）」が設定すべきもので、部品自身が決めるべきじゃない。工場のユニットは「どの電力会社と契約するか」までは決めない。それは設置する現場が決めることだろう？（詳しくは7章で。）

モジュール（部品）を現場に呼び出すときの基本の書き方です。

HCL: module ブロックの基本構文 
module "<NAME>" {
  source = "<SOURCE>"

  [CONFIG ...]
}

NAME=このコード内での部品の呼び名、source=部品の設計図の場所、CONFIG=部品ごとの設定。

ステージング現場で工場のユニットを呼び出して設置する設計図です。

HCL: stage/services/webserver-cluster/main.tf 
# provider は「使う側」が設定する。AWSのリージョン(地域)を us-east-2 に指定
provider "aws" {
  region = "us-east-2"
}

# ① webserver_cluster という呼び名で、工場のユニットを1つ設置する
module "webserver_cluster" {
  # ② source = ユニットの設計図がある場所。../ は「1つ上のフォルダ」を表す相対パス
  source = "../../../modules/services/webserver-cluster"
}

本番現場も、まったく同じユニットを使い回せます（中身はステージングと同じ）。

HCL: prod/services/webserver-cluster/main.tf 
provider "aws" {
  region = "us-east-2"
}

module "webserver_cluster" {
  source = "../../../modules/services/webserver-cluster"
}
ハル
ハルすごい！巨大な設計図じゃなく、たった数行で同じ建物が建つ。書いたら plan や apply すればいいんですか？
棟梁
棟梁その前に大事な手順がある。モジュールを追加したり source を変えたら、必ず init を実行する必要があるんだ。

モジュールを使い始めたら、まず init で部品を取り込みます。

bash: terraform init の実行と出力 
# モジュールを使い始めたら、まず init で部品を取り込む
$ terraform init
Initializing modules...
- webserver_cluster in ../../../modules/services/webserver-cluster

Initializing the backend...

Initializing provider plugins...

Terraform has been successfully initialized!
ハル
ハルあれ、init ってバックエンドの設定とプロバイダのインストールをするコマンドだと思ってました。
棟梁
棟梁ここで init の秘密が分かる。init は「プロバイダをインストールし、バックエンドを設定し、そしてモジュールをダウンロードする」、この3役をこなす。
ハル
ハルじゃあ、もう apply していいですか？
棟梁
棟梁待った。このモジュールには問題がある。すべての名前がハードコードされているんだ。
ハル
ハル名前がハードコードされていると、何が困るんですか？
棟梁
棟梁リソース名が全部決め打ちだろう？同じAWSアカウントでこのモジュールを2回以上使うと「名前がかぶってますよ」というエラーが出る。本番とステージングは同じユニットだから名前が完全に同じでぶつかる。
ハル
ハルあっ、同じ型番の表札を2つの家に付けたら、郵便屋さんが混乱しちゃう。
棟梁
棟梁さらに terraform_remote_state がステージング用のデータベースを見るようにハードコードされている。本番現場でもステージングのDBを見にいってしまう。
ハル
ハルそれは困る。本番なのにテスト用のDBにつながっちゃう。
棟梁
棟梁これを直すには、現場ごとに違う動きができるよう、モジュールに「入力」を設定できるようにする。それが次の話だ。

💡 なぜこれが必要か / これを知るとできること

  • 数行のコードで同じ構成を複数現場に展開できる。
  • init の本当の役割（プロバイダ・バックエンド・モジュールの取り込み）が分かる。
  • ハードコードの危険（名前衝突・参照ミス）に気づけるようになる。

📌 この項のまとめ

  • フォルダ内の設定ファイルの集まり = モジュール。直接実行する入り口がルートモジュール。
  • 再利用は module "<NAME>" { source = "<SOURCE>" ... } で呼ぶ。
  • モジュール内では provider を定義せず、使う側が設定する。
  • モジュールを追加・変更したら init が必要。init はモジュールのダウンロードもする。
  • 名前がハードコードだと同一アカウント内で衝突する → 入力変数で解決する。
4.2

モジュールの入力入力変数 = API（注文表）/ 名前・参照先・サーバの大きさ

要するに：モジュールに入力変数を持たせれば、同じ部品を現場ごとに「名前・参照先・サーバの大きさ・台数」を変えて使い回せる。入力変数はモジュールの窓口（API）。

ハル
ハル「入力」って、さっきの Ruby の関数でいうと何にあたるんですか？
棟梁
棟梁関数に渡す「引数（パラメータ）」だよ。外から値を渡せるようにするだろう？

「相手の名前を変えてあいさつできる」ように引数を受け取る関数の例です。

Ruby: 引数を2つ受け取る関数 
# 入力(引数)が2つある関数
def example_function(param1, param2)
  puts "Hello, #{param1} #{param2}"
end

# 関数に入力を2つ渡して呼び出す
example_function("foo", "bar")

🏭 たとえ話：間取りユニットの「オプション注文表」

入力変数は「この間取りユニット、壁の色は何色にしますか？ドアの向きは？」と現場ごとに選べるオプション注文表です。ユニットそのものは共通だけど、注文表で現場ごとに微調整する——ステージングは小さく安く、本番は大きく強く、と同じ部品で作り分けられます。

まず3つの入力変数を追加（名前と参照先）

「ユニットの注文表」に3つの選択項目を追加する設計図です。現場ごとに違う値を入れて使い回します。

HCL: modules/.../variables.tf（名前と参照先） 
# ① 全リソースに付ける名前（現場ごとに変えて名前衝突を防ぐ）
variable "cluster_name" {
  description = "クラスタの全リソースに使う名前"
  type        = string
}

# ② データベースの状態が入っている S3 バケットの名前
variable "db_remote_state_bucket" {
  description = "データベースのリモートステートが入った S3 バケット名"
  type        = string
}

# ③ S3 の中で、データベースの状態ファイルがどこに置かれているかのパス
variable "db_remote_state_key" {
  description = "S3 内のデータベースのリモートステートのパス"
  type        = string
}

ALB（ロードバランサ）のセキュリティグループ。ハードコードしていた名前を、注文表の値で組み立てます。

HCL: 名前を ${var.cluster_name}-alb にする 
resource "aws_security_group" "alb" {
  # ① 「現場名-alb」にする。var.cluster_name が変わるので衝突しない
  name = "${var.cluster_name}-alb"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
ハル
ハル${var.cluster_name}-alb って、現場名のうしろに -alb をくっつけてるんですね。
棟梁
棟梁そう。同じように aws_security_group（-instance）、aws_alb の各リソース、aws_autoscaling_group の tag にも同じ変更を加える。さらに terraform_remote_state も直して、正しい現場のDBを読むようにする。

「データベースの状態を読み出す」設定。どの現場のDBを見るかを注文表で切り替えます。

HCL: terraform_remote_state を変数化 
data "terraform_remote_state" "db" {
  backend = "s3"

  config = {
    # ① どのバケットを見るかを注文表(入力変数)から受け取る
    bucket = var.db_remote_state_bucket
    # ② バケット内のどのパスを見るかも注文表から受け取る
    key    = var.db_remote_state_key
    region = "us-east-2"
  }
}

ステージング現場で、ユニットの注文表に値を入れて設置する設計図です。

HCL: stage/.../main.tf（注文表に値を入れる） 
module "webserver_cluster" {
  source = "../../../modules/services/webserver-cluster"

  # ① 現場名は「webservers-stage」(ステージング用)
  cluster_name           = "webservers-stage"
  # ② データベースの状態が入ったバケット名(自分のものに置き換える)
  db_remote_state_bucket = "(YOUR_BUCKET_NAME)"
  # ③ ステージング用のデータベース状態のパス
  db_remote_state_key    = "stage/data-stores/mysql/terraform.tfstate"
}

本番現場でも同じ変数を使いますが、本番に合った値にします。

HCL: prod/.../main.tf（注文表の値だけ変える） 
module "webserver_cluster" {
  source = "../../../modules/services/webserver-cluster"

  cluster_name           = "webservers-prod"          # ① 本番用の名前
  db_remote_state_bucket = "(YOUR_BUCKET_NAME)"
  db_remote_state_key    = "prod/data-stores/mysql/terraform.tfstate"  # ② 本番用DB
}
ハル
ハルあれ、本番用のデータベースってもう作ってあるんでしたっけ？
棟梁
棟梁いや、まだ無い。ステージングと同じ要領で本番のDBを作るのは、君への宿題だ。自分でやってみてごらん。
ハル
ハルモジュールへの値の渡し方って、リソースの引数を書くのと全く同じ書き方ですね。
棟梁
棟梁そのとおり。入力変数はモジュールに対する API（窓口）なんだ。現場ごとの振る舞いをこの窓口で制御する。
ハル
ハル名前とDBだけじゃなく、サーバの大きさも現場で変えたいですよね。ステージングは小さく、本番は大きく。
棟梁
棟梁まさにそれをやろう。variables.tf にさらに3つの入力変数を追加だ。

さらに3つの入力変数（サーバの大きさと台数）

「サーバの大きさと台数」を現場ごとに選べるようにする注文表の追加項目です。

HCL: variables.tf（サイズと台数）

4.3

モジュールのローカルな値locals / マジックナンバーに名前を付ける / DRY

要するに：モジュール内だけで使い、外から変えられたくない値は locals ブロックで名前を付け、local.<名前> で参照する。マジックナンバーが減って読みやすくなる。

ハル
ハル入力変数って便利だけど、何でもかんでも入力変数にしちゃダメなんですか？
棟梁
棟梁いい質問だ。中間的な計算や、同じ値を1か所にまとめたい（DRY に保つ）一方で、「外から変更されたくない」値もある。
ハル
ハルDRY って何ですか？
棟梁
棟梁同じ値をあちこちにコピペしない、ってことだ。例を見せよう。ロードバランサは「ポート80」を使うが、この 80 があちこちにコピペされている。まずリスナだ。

ロードバランサの受付窓口（リスナ）。ポート80（HTTPの標準ポート）を待ち受けます。

HCL: リスナにハードコードされた 80 
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.example.arn
  port              = 80
  protocol          = "HTTP"

  # 行き先が決まらない場合は「404 ページが見つかりません」を返す
  default_action {
    type = "fixed-response"

    fixed_response {
      content_type = "text/plain"
      message_body = "404: page not found"
      status_code  = 404
    }
  }
}

ロードバランサのセキュリティグループにも 80 や 0 や -1 が散らばっています。

HCL: セキュリティグループにも散らばる謎の数字 
resource "aws_security_group" "alb" {
  name = "${var.cluster_name}-alb"

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
ハル
ハル0.0.0.0/0 とか -1 とか、暗号みたいな数字がたくさんありますね……。
棟梁
棟梁0.0.0.0/0は「すべてのIPアドレス」、0は「あらゆるポート」、-1は「あらゆるプロトコル」。こういう意味の分かりにくい数字を マジックナンバーと呼ぶ。何か所もハードコードされていると読みにくいしメンテもしにくい。
ハル
ハルじゃあ入力変数にすればいいんじゃ？
棟梁
棟梁それも手だが、入力変数にすると使う人が間違って上書きしてしまう。「すべてのIPを許可」を勝手に変えられたら困るだろう。そういう時は locals ブロックでローカルな値を使うんだ。

🏭 たとえ話：ネジに「玄関ドア用」とラベルを貼る

謎の番号「80番ネジ」のままだと、現場の職人は何のネジか分かりません。そこで「玄関ドア用ネジ」とラベルを貼っておく——それがローカルな値です。local.http_port と書けば「あ、これはHTTPのポートのことね」とひと目で分かります。しかもこのラベルは工場の中だけのもので、現場が勝手に貼り替えることはできません。

「モジュール内だけで使う名前付きの値」をまとめて定義する場所です。

HCL: locals ブロック 
locals {
  http_port    = 80              # ① HTTP の標準ポート
  any_port     = 0               # ② あらゆるポートを表す値
  any_protocol = "-1"            # ③ あらゆるプロトコルを表す値
  tcp_protocol = "tcp"           # ④ TCP というプロトコル名
  all_ips      = ["0.0.0.0/0"]   # ⑤ すべての IP アドレスを表す値
}

読み出すには ローカル参照 local.<NAME> を使います。

リスナ。ハードコードの 80 を、意味の分かる名前 local.http_port に置き換えました。

HCL: リスナの port を local.http_port に 
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.example.arn
  port              = local.http_port   # ① 80 ではなく「http_port」という名前で読む
  protocol          = "HTTP"

  default_action {
    type = "fixed-response"

    fixed_response {
      content_type = "text/plain"
      message_body = "404: page not found"
      status_code  = 404
    }
  }
}

セキュリティグループも全部、謎の数字を意味の分かる名前に置き換えます。

HCL: セキュリティグループを名前付きの値に 
resource "aws_security_group" "alb" {
  name = "${var.cluster_name}-alb"

  ingress {
    from_port   = local.http_port    # ① 80 → http_port
    to_port     = local.http_port
    protocol    = local.tcp_protocol # ② "tcp" → tcp_protocol
    cidr_blocks = local.all_ips       # ③ ["0.0.0.0/0"] → all_ips
  }

  egress {
    from_port   = local.any_port      # ④ 0 → any_port
    to_port     = local.any_port
    protocol    = local.any_protocol  # ⑤ "-1" → any_protocol
    cidr_blocks = local.all_ips
  }
}
ハル
ハルlocal.http_port って書いてあれば「HTTPのポートのことね」ってひと目で分かる。ネジに「玄関ドア用ネジ」ってラベルを貼った感じ。
棟梁
棟梁まさにそれだ。ローカルな値を使うとコードが読みやすく、手入れもしやすくなる。どんどん使っていこう。

💡 なぜこれが必要か / これを知るとできること

  • 同じ値のコピペ（マジックナンバー）を1か所にまとめて DRY にできる。
  • 入力変数と違い外から上書きされないので、勝手に変えられたくない値を守れる。
  • local.http_port のように名前が意味を語るので、読みやすくなる。

📌 この項のまとめ

  • locals { ... } でローカルな値を定義、local.<NAME> で読み出す。
  • ローカルな値はモジュール内限定で、他モジュールに影響せず、外から上書き不可。
  • 入力変数 = 外から設定させたい値、ローカル値 = 内部だけの中間的な値・固定値。
  • マジックナンバーに名前を付けると可読性と保守性が上がる。
4.4

モジュールの出力output = 返り値 / スケジュール / バケツリレー

要するに：モジュールの内部情報を外で使うには出力変数（output）で「返す」。読むときは module.<モジュール名>.<出力名>。さらに現場側で再出力して画面に表示できる。

ハル
ハルAuto Scaling グループって、決まった時間に台数を変えることもできますか？
棟梁
棟梁できるよ。スケジュールされたアクションというものでね。営業時間中だけ多いなら、午前9時から午後5時までサーバを増やす、なんてことができる。
ハル
ハルそれ、モジュールに入れちゃえばステージングも本番も両方できますね！
棟梁
棟梁そこが落とし穴だ。モジュールに入れると両方に適用される。でもステージングにこんなスケーリングは要らない。だから今は本番現場にだけ書こう。（5章で条件付きの定義を学んだら、モジュールへ移すよ。）

本番現場に「朝サーバを増やし、夜減らす」スケジュールを追加する設計図です。

HCL: aws_autoscaling_schedule を2つ（対象未指定） 
# ① 朝(9時)にサーバを10台に増やす設定
resource "aws_autoscaling_schedule" "scale_out_during_business_hours" {
  scheduled_action_name = "scale-out-during-business-hours"
  min_size              = 2
  max_size              = 10
  desired_capacity      = 10
  recurrence            = "0 9 * * *"   # cron式で「毎日午前9時」
}

# ② 夜(17時)にサーバを2台に減らす設定
resource "aws_autoscaling_schedule" "scale_in_at_night" {
  scheduled_action_name = "scale-in-at-night"
  min_size              = 2
  max_size              = 10
  desired_capacity      = 2
  recurrence            = "0 17 * * *"  # cron式で「毎日午後5時」
}
ハル
ハル0 9 * * * って何ですか？暗号ですか？
棟梁
棟梁cron式だよ。0 9 * * *は「毎日午前9時」、0 17 * * *は「毎日午後5時」。朝に台数を10に増やし、夜に2に減らす。（タイムゾーンはデフォルトでUTC。日本時間JSTなどにするには timezone パラメータを使う。）
ハル
ハルでも、このスケジュールってどのサーバ群に効かせるんですか？「どのクラスタか」を書いてないですよね。
棟梁
棟梁鋭い！autoscaling_group_name が必要なのにまだ書いていない。でもASG自体はモジュールの中で定義されている。さて、その名前を外からどう参照する？
ハル
ハルうーん……モジュールの中の情報を、外から知る方法が要りますね。
棟梁
棟梁そう。Ruby の関数でいうと「返り値」だ。

「計算結果を呼び出し元に返す」関数の例です。

Ruby: 値を返す関数 
# 値を1つ返す関数
def example_function(param1, param2)
  return "Hello, #{param1} #{param2}"
end

# 返り値を受け取るために関数を呼び出す
return_value = example_function("foo", "bar")

🏭 たとえ話：ユニットに「設置したら管理番号を教えてね」

工場のユニットに「設置したらユニットの管理番号を教えてね」と頼んでおき、現場でその番号を使う——それが出力変数です。さらに、現場で受け取った番号を看板に書いて表に出すこともできます。モジュールの中の出力を、現場でもう一回出力する「バケツリレー」です。

モジュールの「返り値」を定義します。Auto Scaling グループの名前を外に渡します。

HCL: modules/.../outputs.tf（ASG名を出力） 
output "asg_name" {
  value       = aws_autoscaling_group.example.name   # ① 返す中身: ASGの名前
  description = "Auto Scaling グループの名前"
}

各スケジュールに「どのASGに効かせるか」を、モジュールの出力から受け取らせます。

HCL: prod/.../main.tf（スケジュールに対象を指定）

  min_size              = 2
  max_size              = 10
  desired_capacity      = 10
  recurrence            = "0 9 * * *"

}

resource "aws_autoscaling_schedule" "scale_in_at_night" {

  max_size              = 10

ハル
ハル工場のユニットに「設置したら管理番号を教えてね」って言っておいて、現場でその番号を使う感じですね。
棟梁
棟梁そのとおり。もう1つ出力したいものがある。ALBのDNS名だ。これを出せば、どのURLでテストすればいいか分かる。

ALB（ロードバランサ）のアクセス先アドレス（DNS名）を返す出力変数です。

HCL: modules/.../outputs.tf（ALBのDNS名を出力）

  • モジュール内のリソース（ASGの名前やALBのDNS名など）を外から参照できる。

4.5

モジュールの注意点ファイルパス と インラインブロック の2つ

要するに：モジュールを作る時に気をつける点が2つ——「ファイルパス」と「インラインブロック」。

ハル
ハルもうデプロイできるって言ってましたけど、注意点って何ですか？
棟梁
棟梁気をつけるべき点が2つある。「ファイルパス」と「インラインブロック」だ。順番に見ていこう。

4.5.1 ファイルパス

要するに：モジュール内で外部ファイルを読むときは path.module を付けて「このモジュールのフォルダからの相対」にする。さもないと別フォルダで実行されたときに迷子になる。

ハル
ハルファイルパスの何に気をつけるんですか？
棟梁
棟梁3章で起動スクリプトを user-data.sh という外部ファイルに書いて、templatefile で読み込んだのを覚えているかい？
ハル
ハルはい。templatefile("user-data.sh", ...) って書いたやつですね。
棟梁
棟梁ファイルの場所は相対パスで書く。絶対パスは書きたくない。君のコードは配置が違う別のコンピュータで実行されるかもしれないからだ。
ハル
ハルでも相対パスって、「どこから見た」相対なんですか？
棟梁
棟梁そこが落とし穴。Terraform はデフォルトで「カレントディレクトリ（今いるフォルダ）からの相対」と判断する。apply を実行するフォルダに設定ファイルがあるルートモジュールなら問題ない。
ハル
ハルでも今は、別フォルダにある工場のユニット（モジュール）から読んでますよね？
棟梁
棟梁そう。それだとうまくいかない。解決するのがパス参照で、path.<TYPE> という書式を使う。

🏭 たとえ話：「このユニットのフォルダから見て」と指定する

ユニットの中の部材（user-data.sh）を読むなら「このユニットの設計図フォルダから見て」と指定すれば、どこの現場で組み立てても部材を迷子になりません。それが path.module です。

Terraform が用意しているパスのタイプ

書き方意味
path.moduleその定義が書かれているモジュールがあるフォルダのパスを返す（=このユニットのフォルダ）。
path.rootルートモジュール（一番上）のフォルダのパスを返す。
path.cwdカレントディレクトリのパス。普通は path.root と同じ。特別な使い方では異なる。

起動スクリプトの場所を「このモジュールのフォルダからの相対」で正しく指定します。

HCL: templatefile に path.module を付ける 
  user_data = templatefile("${path.module}/user-data.sh", {
    # ① path.module = このユニットの設計図フォルダ。そこの user-data.sh を読む
    server_port = var.server_port
    db_address  = data.terraform_remote_state.db.outputs.address
    db_port     = data.terraform_remote_state.db.outputs.port
  })
ハル
ハルユニットの中の部品を読むなら「このユニットのフォルダから見て」って指定すれば、どこの現場でも迷子にならないんですね。

💡 なぜこれが必要か / これを知るとできること

  • 再利用モジュールが、どの現場（フォルダ）から呼ばれてもファイルを正しく読めるようになる。
  • path.module / path.root / path.cwd の違いを理解して使い分けられる。

📌 この項のまとめ

  • 相対パスはデフォルトで「カレントディレクトリ基準」と判断される。
  • ルートモジュールならそれでよいが、再利用モジュールでは破綻する。
  • 解決は path.module（モジュールのフォルダ基準）を使うこと。
  • path.root はルート、path.cwd は通常 root と同じ。

4.5.2 インラインブロック

要するに：インラインブロックと別リソースは混ぜると壊れる。再利用モジュールでは別リソースを使うと、あとから外でルールを足せて柔軟になる。

ハル
ハルもう1つの注意点、インラインブロックって何ですか？
棟梁
棟梁インラインブロックはこういう書き方だ。

インラインブロックの形。リソースの中に NAME { ... } が直接埋め込まれています。

HCL: インラインブロックの形 
resource "xxx" "yyy" {
  <NAME> {
    [CONFIG...]
  }
}

NAME=ブロックの名前（ingress など）、CONFIG=その中の引数（from_port など）。aws_security_group では受信(ingress)・送信(egress)を、インラインブロックでも別リソース aws_security_group_rule でも書けます。

ハル
ハル両方使えるなら、両方混ぜて書いてもいいんですか？
棟梁
棟梁それが一番やってはいけないことだ。両方を混ぜると、設定がぶつかってお互いに上書きし合う。必ずどちらか一方にする。私のアドバイスは「モジュールを作る時は常に別リソースを使え」だ。
ハル
ハルなんで別リソースの方がいいんですか？
棟梁
棟梁別リソースは「どこにでも追記できる」。インラインブロックはそのリソースを作るモジュールの中にしか書けないが、別リソースならモジュールの外からでもルールを追加できる。柔軟性が上がるんだ。

🏭 たとえ話：窓は「作り付け」より「後付けできる規格」に

最初から壁に窓を作り付けにしちゃうと、現場で窓を増やせません。でも「窓は後付けできる規格」にしておけば、現場ごとに必要な窓を足せます。インラインブロック=作り付けの窓、別リソース=後付けできる窓、というわけです。

ingress/egress を「インラインブロック」で書いた例（柔軟性が低い）です。

HCL: インラインブロック版（柔軟性が低い） 
resource "aws_security_group" "alb" {
  name = "${var.cluster_name}-alb"

  ingress {
    from_port   = local.http_port
    to_port     = local.http_port
    protocol    = local.tcp_protocol
    cidr_blocks = local.all_ips
  }

  egress {
    from_port   = local.any_port
    to_port     = local.any_port
    protocol    = local.any_protocol
    cidr_blocks = local.all_ips
  }
}

同じルールを aws_security_group_rule という別リソースに書き換えます（あとから外でルールを足せる）。

HCL: 別リソース版（柔軟） 
# ① 空のセキュリティグループ。ルールは別リソースで足していく
resource "aws_security_group" "alb" {
  name = "${var.cluster_name}-alb"
}

# ② HTTP の受信を許可するルール(別リソース)
resource "aws_security_group_rule" "allow_http_inbound" {
  type              = "ingress"
  security_group_id = aws_security_group.alb.id   # どのグループに付けるか

  from_port   = local.http_port
  to_port     = local.http_port
  protocol    = local.tcp_protocol
  cidr_blocks = local.all_ips
}

# ③ すべての送信を許可するルール(別リソース)
resource "aws_security_group_rule" "allow_all_outbound" {
  type              = "egress"
  security_group_id = aws_security_group.alb.id

  from_port   = local.any_port
  to_port     = local.any_port
  protocol    = local.any_protocol
  cidr_blocks = local.all_ips
}

外からルールを足せるように、セキュリティグループの ID を出力変数として出します。

HCL: modules/.../outputs.tf（SGのIDを出力） 
output "alb_security_group_id" {
  value       = aws_security_group.alb.id
  description = "ロードバランサに付いたセキュリティグループの ID"
}

これで、ステージングだけテスト用にポート12345を追加で開けられます。

HCL: 現場側で外からルールを1本足す 
module "webserver_cluster" {
  source = "../../../modules/services/webserver-cluster"

  # (わかりやすくするためパラメータは省略)
}

# ① モジュールの外から、出力されたID を使ってルールを1本足す
resource "aws_security_group_rule" "allow_testing_inbound" {
  type              = "ingress"
  security_group_id = module.webserver_cluster.alb_security_group_id

  from_port   = 12345
  to_port     = 12345
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
}
ハル
ハルもしモジュールの中でルールを1本でもインラインブロックで書いてたら、このコードは動かないんですよね？
棟梁
棟梁そのとおり。混ぜたら破綻する。同じ問題は多くの Terraform リソースで起きる。代表的なのはこの組み合わせだ。
本体リソースルール用の別リソース
aws_security_groupaws_security_group_rule
aws_route_tableaws_route
aws_network_aclaws_network_acl_rule
ハル
ハル工場のユニットでいうと、最初から壁に窓を作り付けにしちゃうと現場で窓を増やせないけど、「窓は後付けできる規格」にしておけば現場ごとに足せる、って感じですね。
棟梁
棟梁いい例えだ。これでステージングと本番の両方をデプロイする準備が整った。terraform apply で2つの別々の現場を完成させよう。

💡 なぜこれが必要か / これを知るとできること

  • 別リソースにしておくと、モジュールの外から後付けでルールを追加できる柔軟なモジュールになる。
  • インラインと別リソースを混ぜると上書き合戦で壊れる、という落とし穴を避けられる。

コラム：ネットワークの分離

要するに：環境は理想的にはネットワーク（VPC）レベルでも分離すべき。例ではシンプルさのため同一VPCを使っているが、実運用ではVPCやアカウントで分ける。

ハル
ハルこれでステージングと本番、ちゃんと分かれた2つの環境ができましたよね？
棟梁
棟梁コードの上では分かれている。でも実は、ネットワークのレベルでは分かれていないんだ。
ハル
ハルえっ、どういうことですか？
棟梁
棟梁例をシンプルにするため、すべてのリソースを同じ VPC に置いている。つまりステージングのサーバから本番のサーバにアクセスできるし、逆もできる状態なんだ。
ハル
ハルそれって危なくないですか？
棟梁
棟梁2つのリスクがある。1つめは片方のミスがもう片方に波及すること。2つめは攻撃者が片方に侵入したらもう片方にも入れてしまうこと。
ハル
ハルそれは怖い……。じゃあ実際にはどうするんですか？
棟梁
棟梁単純な例を除けば、環境ごとに別のVPCを使うべきだ。念には念を入れて別のAWSアカウントで動かすこともある。

🏭 たとえ話：隣り合わせより、別の塀で囲った別の敷地に

プレハブの2つの建物を、同じ敷地の中に隣り合わせで建てるんじゃなく、別々の塀で囲った別の敷地に建てるイメージです。こうすれば片方の事故やトラブルがもう片方に飛び火しません。

💡 なぜこれが必要か / これを知るとできること

  • 環境を同一VPCに置くリスク（波及・侵入の連鎖）を理解できる。
  • 本来はVPCやアカウントで分離すべきと判断できる。

📌 4.5 のまとめ

  • インラインブロック = リソース内に直接書く設定。別リソース = 独立したリソースとして書く設定。
  • 両者を混ぜると上書きし合って壊れる。モジュールでは別リソース推奨。
  • 別リソースなら外から追記でき、SGのIDを出力すれば現場ごとにルールを足せる。
  • 同じ問題は aws_route_table/aws_route、aws_network_acl/aws_network_acl_rule でも起きる。
  • 例ではシンプルさのため同一VPCを使うが、実運用では環境ごとにVPCやアカウントを分けるべき。
4.6

モジュールのバージョン管理Gitタグ / ?ref= / セマンティックバージョニング

要するに：モジュールを別の Git リポジトリに置き、source に ?ref=タグ名 を付けてバージョンを指定すれば、環境ごとに違うバージョンを使え、本番に影響を出さずステージングで安全に試せる。

ハル
ハルいまステージングも本番も同じモジュールのフォルダを指してますよね。モジュールを直したら……？
棟梁
棟梁いいところに気づいた。同じフォルダを両方が指していると、モジュールを変えると次のデプロイで両方の環境に一気に反映されてしまう。
ハル
ハルそれじゃ「本番に影響を出さずにステージングだけで試す」ができないですね。
棟梁
棟梁そのとおり。解決策がモジュールのバージョン管理だ。バージョンを付ければ、ステージングは新しいv0.0.2、本番は安定版v0.0.1、と使い分けられる。
ハル
ハルユニットに「2024年モデル」「2023年モデル」みたいに型番を付けて、現場ごとに好きな型番を発注する感じですか？
棟梁
棟梁まさにそれだ。source にはローカルパスのほか、GitのURL・MercurialのURL・任意のHTTP URL なども指定できる。

🏭 たとえ話：ユニットに「型番」を付けて発注する

工場のユニットに「2024年モデル(v0.0.2)」「2023年モデル(v0.0.1)」のように型番を付けておけば、テスト現場では新型を試し、本番現場では安定した旧型を使い続けられます。新型に欠陥があっても本番には影響しません。安全だと分かってから本番現場に新型を納品します。

工場リポジトリ(modules)と現場リポジトリ(live)に分ける

🏭

modules リポジトリ

再利用可能なモジュール（バージョン付き）を定義する。各モジュールは「インフラの一部分の設計図」。これが工場。

部品の置き場
🏗️

live リポジトリ

各環境（stage / prod / mgmt など）で実際に動くインフラを定義する。modules の設計図を元に作ったものが入る。これが現場。

実際に動く環境

「工場リポジトリ(modules)」と「現場リポジトリ(live)」に分けた言葉スケッチです。

フォルダ構造（2リポジトリ） 
modules リポジトリ/           ← 再利用部品(バージョン付き)の置き場 = 工場
└── services/
    └── webserver-cluster/

live リポジトリ/              ← 実際に動く各環境 = 現場
├── stage/
├── prod/
└── global/

modules フォルダを Git リポジトリにして、リモートに送る一連の操作です。

bash: modules を Git リポジトリにする 
$ cd modules
$ git init
$ git add .
$ git commit -m "modules リポジトリの最初のコミット"
$ git remote add origin "(リモートGitリポジトリのURL)"
$ git push origin main
ハル
ハルバージョン番号ってどうやって付けるんですか？
棟梁
棟梁Git のタグを使う。タグをバージョン番号として使うんだ。GitHub なら「リリース管理」画面からも付けられる。

v0.0.1 というタグ（バージョン名）を付けて、リモートに送ります。

bash: タグを付けてプッシュ 
$ git tag -a "v0.0.1" -m "webserver-cluster モジュールの最初のリリース"
$ git push --follow-tags

Git 上のバージョン v0.0.1 のユニットを呼び出すステージング現場の設計図です。URL の // は必要なので注意。

HCL: source に Git URL + ?ref=v0.0.1 
module "webserver_cluster" {
  # ① source = GitのURL。// はリポジトリとサブフォルダの境目。?ref=v0.0.1 でバージョン指定
  source = "github.com/foo/modules//services/webserver-cluster?ref=v0.0.1"

  cluster_name           = "webservers-stage"
  db_remote_state_bucket = "(YOUR_BUCKET_NAME)"
  db_remote_state_key    = "stage/data-stores/mysql/terraform.tfstate"

  instance_type = "t2.micro"
  min_size      = 2
  max_size      = 2
}
ハル
ハル// ってなんで2本もスラッシュがあるんですか？打ち間違いかと思いました。
棟梁
棟梁二重スラッシュは「ここまでがリポジトリ名、ここからがその中のサブフォルダ」という境目を表すんだ。だから必要なんだよ。

Git をいじりたくないなら、本のサンプルリポジトリのモジュールも使えます（実際は改行せず1行で書く）。

HCL: サンプルリポジトリのモジュールを使う例 
source = "github.com/brikis98/terraform-up-and-running-code//code/terraform/04-terraform-module/module-example/modules/services/webserver-cluster?ref=v0.3.0"
ハル
ハル?ref= のところって、バージョン名以外も書けるんですか？
棟梁
棟梁書ける。ref には sha1ハッシュ（コミットの固有ID）、ブランチ名、Gitタグ名を渡せる。でもバージョンには Gitタグがお勧めだ。理由はこうだ。
refの種類評価
ブランチ名不安定：init のたびに最新コミットが変わる可能性がある。
sha1ハッシュ難解：人間に優しくない（長くて意味が分からない）。
Gitタグ推奨：コミットと同じように扱えるうえ、分かりやすい名前を付けられる。
ハル
ハルタグの名前って、v0.0.1 とか v0.0.2 ってどう決めるんですか？
棟梁
棟梁セマンティックバージョニングが便利だ。MAJOR.MINOR.PATCH（例: 1.0.4）という形式で、各数字をいつ上げるかにルールがある。
数字いつ上げるか
MAJOR（メジャー）APIの互換性がなくなる時（使う側がコードを直す必要がある変更）。
MINOR（マイナー）後方互換性のある機能追加（前のままでも動く新機能）。
PATCH（パッチ）後方互換性のあるバグ修正。
ハル
ハルバージョン番号を見ただけで「あ、これは互換性が壊れる大きな変更だな」って分かるんですね。
棟梁
棟梁そういうことだ。バージョン番号を通して「どんな変更で、なぜ上げたか」を使う人に伝えられる。さて、Git URL に変えたら init でモジュールをダウンロードさせる必要がある。

Git からモジュールのコードをダウンロードします。今度はローカルではなく Git から読んでいるのが分かります。

bash: terraform init（Gitからダウンロード） 
$ terraform init

for webserver_cluster...

(...)
ハル
ハルもしモジュールが非公開のGitリポジトリにある場合はどうするんですか？
棟梁
棟梁Terraform に認証方法を教える必要がある。お勧めは SSH認証だ。認証情報をコードに書かなくて済む。各開発者がSSHキーを作り、Gitユーザに紐づけ、ssh-agent に登録すれば、Terraform が自動でその鍵を使ってくれる。

bash: SSH URL の形式と具体例

# 具体例

bash: git clone で URL を検証

  • 同じフォルダを共有すると変更が全環境に即反映され、本番への波及を防げない。
  • バージョンを付ければ、ステージングで新版を検証し、安定後に本番を上げる安全な運用ができる。

章末の理解度チェック自分の言葉で答えてみよう（全5問）

第1問モジュールとは何か

「Terraform モジュール」とは何か、そしてなぜステージングと本番で設計図をコピペするより良いのかを、自分の言葉で説明してください。

✅ 解答例を見る
モジュールは「あるフォルダ内のTerraform設定ファイルの集まり」で、再利用できる部品のかたまりです。コピペだと同じ構成が複数の場所に重複し、1か所の修正のために全コピー先を手作業で直す必要があり、ミスも増えます。モジュールなら部品を1つだけ持ち、各環境から呼び出すので、修正が1か所で済みます。
📝 採点ポイント
・モジュール = フォルダ内の設定ファイルの集まり（再利用部品）だと言えている
・コピペは重複・保守が大変というデメリットに触れている
・モジュールは1か所の修正で全環境に反映できる利点に触れている
第2問入力変数とローカルな値の使い分け

モジュールの「入力変数（variable）」と「ローカルな値（locals）」は、どう使い分けるべきですか。

✅ 解答例を見る
入力変数は「使う側に外から設定させたい値」に使います（例: 現場名やサーバの大きさ）。ローカルな値は「モジュール内だけで使う中間的な値や固定値で、外から勝手に変えられたくないもの」に使います（例: HTTPのポート80や、すべてのIPを表す値）。ローカルな値はモジュール外から上書きできず、他モジュールにも影響しません。
📝 採点ポイント
・入力変数 = 外から設定させる窓口だと言えている
・ローカルな値 = 内部専用・外から上書き不可だと言えている
・マジックナンバーに名前を付けて読みやすくする目的に触れている
第3問モジュール内のファイルパス

再利用可能なモジュールの中で templatefile を使って外部ファイルを読むとき、なぜ path.module を付ける必要があるのですか。

✅ 解答例を見る
Terraform の相対パスはデフォルトで「カレントディレクトリ（apply を実行するフォルダ）」を基準にします。再利用モジュールは呼び出す現場フォルダと別の場所にあるため、ただファイル名だけ書くとファイルを見つけられません。path.module は「そのモジュールがあるフォルダ」を指すので、どの現場から呼ばれてもファイルを正しく読めます。
📝 採点ポイント
・デフォルトの相対パスはカレントディレクトリ基準だと説明している
・モジュールは別フォルダにあるため破綻する点に触れている
・path.module = モジュールのフォルダ基準で解決できると言えている
第4問インラインブロックと別リソース

セキュリティグループのルールを「インラインブロック」ではなく「別リソース（aws_security_group_rule）」で書くと、どんな利点がありますか。混ぜて使うとどうなりますか。

✅ 解答例を見る
別リソースにすると、モジュールの外からでもルールを後付けで追加できるので、モジュールが柔軟になります（例: ステージングだけテスト用ポートを開ける）。一方インラインブロックはリソースを作るモジュール内にしか書けません。インラインブロックと別リソースを混ぜると設定がぶつかって上書きし合い、Terraform が壊れるので、どちらか一方に統一する必要があります。
📝 採点ポイント
・別リソースは外から追記でき柔軟になると言えている
・インラインは作成モジュール内にしか書けないと言えている
・混ぜると上書き合戦で壊れるので統一すべきと言えている
第5問モジュールのバージョン管理

モジュールを Git タグでバージョン管理すると、ステージングと本番の運用がどう安全になりますか。ref にブランチ名ではなくタグを使うのが推奨される理由も添えてください。

✅ 解答例を見る
バージョンを付けると、ステージングは新版（例: v0.0.2）、本番は安定版（例: v0.0.1）と使い分けられます。ステージングで新版を十分テストし、安全だと確認してから本番を上げられるので、本番の実ユーザに影響を出さずに変更を試せます。ブランチ名は init のたびに最新コミットが変わって不安定で、sha1 は分かりにくいのに対し、タグは特定コミットを指す分かりやすい固定名なので推奨されます。
📝 採点ポイント
・環境ごとに違うバージョンを使い分けられると言えている
・ステージングで検証してから本番を上げる安全運用に触れている
・タグが安定・分かりやすい（ブランチは不安定、sha1は難解）と言えている
