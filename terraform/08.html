8.0

本番レベルのインフラとは何か会社の運命を任せられる「本物の建物」

要するに： 本番レベルとは「会社の運命を任せられる」品質の設備。負荷・障害・攻撃に耐えるものを指す。模型（試作）と本物（本番）では必要な手間がまるで違う。

ハル
ハル棟梁、「本番レベルのインフラ」って、ふつうのインフラと何が違うんですか？
棟梁
棟梁良い出発点だね。本番レベルというのは「会社の運命を預けられる建物」のことだよ。
ハル
ハル運命を、ですか。おおげさじゃないですか？
棟梁
棟梁本気だよ。お客がどっと押し寄せても倒れない。地震（障害）が来ても家財（データ）が壊れない。泥棒（ハッカー）が入ろうとしても押し入られない。そういう建物に会社は商売を賭ける。外れたら会社は潰れる。模型の家とはまるで重みが違う。
ハル
ハル建てるのにどれくらいかかるんですか？
棟梁
棟梁著者が多くの現場を見て出した目安があるんだ。表にするとこうなる。

🏗️ たとえ話：模型の家 vs 本物の建物

段ボールで作る模型の家なら一晩で完成する。でも、人が安心して住み続け、地震や台風や火事に耐え、防犯もできる本物の建物は、基礎工事・耐震・配線・防火・検査…と工程が山ほどある。だから何ヶ月もかかる。「数分で建つ」と思っていると、見積もりを大きく外して施主の信用を失う。

8.1

本番レベルのインフラ構築に時間がかかる理由遅れには3つの理由がある

要するに： インフラ工事が遅れるのには3つの理由がある。①分野が未熟、②ヤクの毛刈り、③そもそも本質的にやることが多い。

ハル
ハルそもそも、なんでそんなに時間がかかるんですか？
棟梁
棟梁「5分」の直しが丸1日、「1日」の新機能が2週間、「2週間」のアプリが半年。これを言い表した格言がある。ホフスタッターの法則だ。「いつでも予測以上の時間がかかる――この法則を計算に入れても」。理由は3つある。

8.1.1 理由その1: DevOpsはまだ石器時代

ハル
ハル1つめの理由は何ですか？
棟梁
棟梁DevOpsという分野が、まだ石器時代だからだよ。悪口じゃない、生まれたてだという意味だ。
ハル
ハルそんなに新しいんですか？
棟梁
棟梁クラウド、Infrastructure as Code、DevOpsという言葉は2000年代半ば〜終わり。Terraform、Docker、Packer、Kubernetesは2010年代半ば〜終わりに出たばかり。どれも新しくて急速に変わり続けている。
ハル
ハルつまり、まだ枯れた工法じゃないってことですね。
棟梁
棟梁そのとおり。成熟しておらず、深い経験を持つ職人も少ない。予定より長引くのが当たり前なんだ。

🏗️ たとえ話：まだ確立していない工法

新しい建材や工法が出たばかりの建築現場を想像してほしい。施工マニュアルも標準もまだ整っていない。熟練した大工も少ない。そんな現場で予定どおり建つわけがない。これがDevOpsの今だ。

📝 この項のまとめ

  • 道具も手法も生まれたてで、急速に変化している。
  • 熟練者が少ないため、工期が延びるのは構造的に当たり前。

8.1.2 理由その2: ヤクの毛刈り（Yak shaving）

ハル
ハル2つめの「ヤクの毛刈り」って、何ですか？動物の毛？
棟梁
棟梁有名なたとえがある。「車にワックスをかけたい」→「ホースが壊れてる、買いに行こう」→「橋の料金が高い、隣のETCカードを借りよう」→「枕を返さないと貸してくれない」→「枕の詰め物が出た、ヤクの毛を刈って詰め直さないと」。
ハル
ハル…車を磨きたいだけなのに、最後は動物園でヤクの毛刈りですか！
棟梁
棟梁現場では毎日起きる。タイポ（書き間違い）を直そうとしたら設定のバグが見つかる。直そうとしたらTLS証明書の問題、デプロイの仕組みが壊れている、原因はLinuxが古い、結局サーバ全部のOS更新――全部「ちょっとした書き間違い」を直すためにね。
ハル
ハルなんでインフラだと特にこうなるんですか？
棟梁
棟梁インフラが密結合で重複が多いからだ。絡まった箱から1本抜こうとして全部のケーブルを引き抜くようなものさ。

🏗️ たとえ話：壁紙の張り替えのはずが大改修

「壁紙を1枚張り替えたい」と思ったら、下地にカビ。直そうと開けたら配管が腐っている。配管を替えるなら床も剥がす。床を剥がすなら家具を全部運び出す――壁紙1枚のはずが、家まるごと大改修になる。建物の各部が絡み合っているほど、こうなりやすい。

📝 この項のまとめ

  • ヤクの毛刈り＝目的の作業に着くまでに無関係な小作業が連鎖すること。
  • インフラは密結合・重複が多いので特に起こりやすい。

8.1.3 理由その3: 本質的複雑性（やることが本来多い）

要するに： 遅れの3つめは本質的複雑性。本番に必要なタスクが本来長く、多くの人がそれを知らずに見積もりから落とす。

ハル
ハル1つめと2つめは「道具のせいで起きる面倒」って感じですね。
棟梁
棟梁鋭いね。その2つは偶有的複雑性だ。たとえばC++でメモリ管理のバグに悩むのは、別の言語を選べば消える面倒だからね。
ハル
ハル反対語があるんですか？
棟梁
棟梁本質的複雑性だ。「市場に勝てるアルゴリズムを見つける」のはどの言語でも必要な難しさ――これが本質的。インフラの3つめはこっちだ。本番に必要なタスクのリストがもともとすごく長い。問題は、多くの人がその大半を知らず、重い項目をまるごと見積もりから落とすことだ。

🏗️ たとえ話：建築基準法の項目は本来多い

耐震・防火・避難経路・配線・換気・バリアフリー…本物の建物に必要な項目は、法律で本来たくさん決まっている。これは「どの工法を選んでも」減らせない。素人は「壁と屋根があればいい」と思って、この長い項目表を見積もりから丸ごと落としてしまう。だから半年の工事が予定に入らないんだ。

🟣 なぜ必要か / これを知ると

  • 遅延を「偶有的（道具のせい）」と「本質的（課題そのもの）」に分けて見られると、対処法が変わる。
  • 本質的に長いタスクリストの存在を知れば、見積もりを現実に近づけられる。

📝 この項のまとめ

  • 理由1（未熟）と理由2（ヤク刈り）は偶有的複雑性。
  • 理由3（タスクが本来多い）は本質的複雑性。
  • 多くの人がこのリストを知らず、見積もりから落としてしまう。

8.3.1 小さなモジュール

要するに： 1つのことだけをする小さなモジュールを組み合わせて作るべき。大きなモジュールは遅い・危険・直せない。

ハル
ハル初心者って、開発・ステージング・本番を全部1枚の設計図に書いちゃいがちですよね。僕もやってました。
棟梁
棟梁良くない。数百行を超える、あるいは関係する設備をいくつもまとめた「大きなモジュール」は有害と見なすべきだ。6つの弊害がある。
🐢

1 遅い

全インフラが1枚だと plan が20分かかることも。

🔓

2 セキュアでない

直すのに全部の鍵が要り、皆が管理者になる＝最小権限の原則に反する。

💥

3 リスク大

卵を一つの籠に。stageの小変更で本番DBを壊しうる。

🤯

4 理解しにくい

一箇所に集まるほど読めず、高くつくミスに。

👀

5 レビューしにくい

数千行のplanは誰も読まず、危険な赤い1行を見逃す。

🧪

6 テストしにくい

大量のインフラコードのテストはほぼ不可能（9章）。

大きなモジュールの6つの弊害（テキスト版）
# 大きなモジュールの6つの弊害
1. 遅い:        全インフラが1枚だと terraform plan が20分かかることも
2. セキュアでない: 何か直すのに全部へのアクセス権が要る→皆が管理者になり最小権限の原則に反する
3. リスクが大きい: 卵を一つの籠に。ステージングの小変更のつもりが本番DBを壊す事故が起こりうる
4. 理解しにくい:  コードが一箇所に集まるほど読めなくなる→高くつくミスにつながる
5. レビューしにくい: 数千行のplan出力は誰も読まず「DBが消える赤い1行」を見逃す
6. テストしにくい:  大量のインフラコードのテストはほぼ不可能(9章で再論)

🏗️ たとえ話：1枚の巨大な設計図 vs 部品ごとの図面

家じゅうの配管・配線・構造・内装を1枚の巨大な図面に描き込むと、検査官は読みきれず、危険な箇所を見逃す。しかも壁紙1枚を直すのにも建物全部の鍵が必要になり、誰もが全部の鍵を持つ羽目になる。だから本物の現場では「構造図」「電気図」「給排水図」と図面を分け、1図面=1つの役目にする。Terraformも同じだ。

ハル
ハル4つめの「理解しにくい」が地味に怖いです。
棟梁
棟梁terraform planの出力が数千行になると誰も読まない。データベースが消されようとしている赤い1行にも気づかないんだ。
ハル
ハルじゃあ、どう直すんですか？
棟梁
棟梁『Clean Code』の言葉だ。「関数の最初のルールは小さくあること。2つめはもっと小さくあること」。2万行の1枚設計図は、1つのことだけする小さなモジュールに割る。

  • 小さく割れば、planが速くなり、権限を絞れ、事故の波及範囲も小さくなる。
  • 割れば、読みやすく・レビューしやすく・テストしやすくなる。
  • 巨大な1枚設計図を、安全に組み合わせられる部品群に作り変えられる。

📝 この項のまとめ

  • 大きなモジュールは「遅い・セキュアでない・リスク大・理解しにくい・レビューしにくい・テストしにくい」。
  • 数百行超、または複数の関係薄い設備をまとめたモジュールは有害と見なす。
  • 1つのことだけする小さなモジュールに割って組み合わせる。
  • webserver-cluster を asg-rolling-deploy / alb / hello-world-app の3つに分割する。

8.3.2 組み合わせ可能なモジュール

要するに： あらゆるものを入力変数で受け取り、出力変数で返し、小さなモジュールを合成して複雑なモジュールを作る。

ハル
ハル小さく割れたのはいいですけど、バラバラの部品をどうやって組み合わせるんですか？
棟梁
棟梁Unix哲学にこんな言葉がある。「1つのことをうまくやるプログラムを書こう。組み合わせて動くプログラムを書こう」。これは関数の合成だ。Rubyの小さな例を見よう。

このコードは、足し算・引き算・掛け算という小さな関数を作り、それらを組み合わせて1つの計算を作る例です。

関数の合成の例（Ruby）
# 加算を行うシンプルな関数
def add(x, y)
  return x + y
end

# 減算を行うシンプルな関数
def sub(x, y)
  return x - y
end

# 乗算を行うシンプルな関数
def multiply(x, y)
  return x * y
end

# 小さな関数を組み合わせた複雑な関数（add と sub の出力を multiply に渡す）
def do_calculation(x, y)
  return multiply(add(x, y), sub(x, y))
end
棟梁
棟梁組み合わせやすくする一番のコツは副作用を減らすことだ。外から勝手に状態を読まず入力で受け取る。外へ勝手に書かず結果は出力で返す。そうすると推測・テスト・再利用がしやすくなる。「すべてを入力変数で渡し、すべてを出力変数で返し、小さなモジュールを合成する」だ。
ハル
ハル具体的にはどうやるんですか？
棟梁
棟梁asg-rolling-deploy の variables.tf に入力変数を4つ足すんだ。

🏗️ たとえ話：規格化された建材を組み上げる

本物の建物は、規格に合った柱・梁・サッシを「差し込み口」でつないで組み上げる。各建材は「どこに置くか（区画）」「どの配管とつなぐか」を外から指定できるよう、接続口が標準化されている。だから同じ柱を別の家でも使い回せる。Terraformの部品も、設定を“外から差し込める入口（入力変数）”にすれば、いろいろな建物に使い回せる。

このコードは、サーバ群を「どの区画に建てるか」「どのロードバランサにつなぐか」「健康チェックの方式」「起動時の仕込みスクリプト」を、すべて外から差し込めるようにする入口（入力変数）です。

asg-rolling-deploy に足す4つの入力変数（HCL）
# このブロックは「サーバ群をどの区画に建てるか」を外から受け取る入口
variable "subnet_ids" {
  description = "デプロイ先のサブネットID"  # ①どの区画に建てるか
  type        = list(string)               # ②文字列の一覧で受け取る
}

# このブロックは「どのロードバランサにサーバを登録するか」を外から受け取る入口
variable "target_group_arns" {
  description = "サーバを登録するELBターゲットグループのARN"  # ①つなぐ先
  type        = list(string)
  default     = []  # ②未指定なら「ロードバランサなし」で建てられる
}

# このブロックは「健康チェックのやり方」を外から受け取る入口
variable "health_check_type" {
  description = "実行する健康チェックの種類。EC2かELBのどちらか"  # ①EC2かELB
  type        = string
  default     = "EC2"  # ②未指定ならEC2方式
}

# このブロックは「起動時に各サーバで走らせる仕込みスクリプト」を外から受け取る入口
variable "user_data" {
  description = "各インスタンスが起動時に実行するユーザーデータスクリプト"  # ①どんなアプリでも仕込める
  type        = string
  default     = null  # ②未指定なら何も仕込まない
}
棟梁
棟梁subnet_idsは「どの区画に建てるか」。target_group_arnsとhealth_check_typeは「ロードバランサとどう組み合わせるか」。これで「ロードバランサなし」「ALB1つ」「NLB複数」など色々な用途に使える。

このコードは、サーバ群（ASG）本体と、サーバ1台の作り方（起動設定）に、外から受け取った設定を差し込む部分です。

ASGと起動設定に外からの値を渡す（HCL）
# このブロックは「サーバ群(ASG)本体」を建てる設計図。組み合わせの設定を外から受ける
resource "aws_autoscaling_group" "example" {
  name                 = var.cluster_name
  launch_configuration = aws_launch_configuration.example.name
  vpc_zone_identifier  = var.subnet_ids  # ①どの区画に建てるか(外から)

  target_group_arns    = var.target_group_arns  # ②つなぐロードバランサ(外から)
  health_check_type    = var.health_check_type  # ③健康チェックの方式(外から)

  min_size = var.min_size
  max_size = var.max_size
  # (...)
}

# このブロックは「サーバ1台の作り方(起動設定)」。仕込みスクリプトを外から受ける
resource "aws_launch_configuration" "example" {
  image_id        = var.ami
  instance_type   = var.instance_type
  security_groups = [aws_security_group.instance.id]
  user_data       = var.user_data  # ①外から受け取った仕込みスクリプトを使う

  lifecycle {
    create_before_destroy = true  # ②壊す前に新しいものを作る(無停止のため)
  }
}
ハル
ハルなんで出力を増やすと再利用性が上がるんですか？
棟梁
棟梁利用者がその出力を使って、セキュリティグループに自分で新しい通行ルールを足す、といった追加の振る舞いができるからだよ。出口が多いほど外から拡張しやすい。だからoutputs.tfに出力を足す。

このコードは、建てたサーバ群やロードバランサの「名前」「住所」「ルールのID」などを外に返す出口（出力変数）です。利用者がこれを使って後から拡張できます。

asg-rolling-deploy と alb の出力（HCL）

output "asg_name" {
  value       = aws_autoscaling_group.example.name  # ①サーバ群の名前を返す
  description = "Auto Scaling Groupの名前"
}
output "instance_security_group_id" {
  value       = aws_security_group.instance.id  # ②利用者が後からルールを足せる
  description = "EC2インスタンスのセキュリティグループID"
}

# alb の outputs.tf
output "alb_dns_name" {
  value       = aws_lb.example.dns_name  # ①ブラウザでアクセスする住所
  description = "ロードバランサのドメイン名"
}
output "alb_http_listener_arn" {
  value       = aws_lb_listener.http.arn  # ②利用者が転送ルールを足すのに使う
  description = "HTTPリスナーのARN"
}
output "alb_security_group_id" {
  value       = aws_security_group.alb.id  # ③利用者がルールを足すのに使う
  description = "ALBのセキュリティグループID"
}
棟梁
棟梁最後に、この2つの部品を使って「Hello, World」アプリを建てるhello-world-appモジュールに書き換える。environment変数を足し、作ったasg-rolling-deployとalbを呼び出すんだ。
ハル
ハル${var.environment}を名前にくっつけてるのはなぜですか？
棟梁
棟梁命名規則を強制するためだ。これでhello-world-stage、hello-world-prodのように環境ごとに名前が分かれる（名前空間が分かれる）。混ざらないんだ。

このコードは、環境名を受け取る入口と、作った2つの部品（ASG・ALB）を呼び出して、このアプリ用に設定する部分です。

hello-world-app が部品を呼び出す（HCL）
# このブロックは「今どの環境に建てているか(stage/prod等)」を外から受け取る入口
variable "environment" {
  description = "デプロイ先の環境名"  # ①命名規則を強制するのに使う
  type        = string
}

# このブロックは「サーバ群の部品を呼び出して、このアプリ用に設定する」
module "asg" {
  source = "../../cluster/asg-rolling-deploy"  # ①さっき作った部品を指す

  cluster_name  = "hello-world-${var.environment}"  # ②環境名で名前空間を分ける
  ami           = var.ami
  instance_type = var.instance_type

  user_data     = templatefile("${path.module}/user-data.sh", {
    server_port = var.server_port
    db_address  = data.terraform_remote_state.db.outputs.address
    db_port     = data.terraform_remote_state.db.outputs.port
    server_text = var.server_text
  })

  min_size           = var.min_size
  max_size           = var.max_size
  enable_autoscaling = var.enable_autoscaling

  subnet_ids        = data.aws_subnets.default.ids        # ③区画を渡す
  target_group_arns = [aws_lb_target_group.asg.arn]       # ④このアプリの宛先グループ
  health_check_type = "ELB"                               # ⑤ロードバランサ方式で健康チェック

  custom_tags = var.custom_tags
}

# このブロックは「ロードバランサの部品を呼び出して建てる」
module "alb" {
  source = "../../networking/alb"  # ①さっき作ったALB部品を指す

  alb_name   = "hello-world-${var.environment}"  # ②環境名込みの名前
  subnet_ids = data.aws_subnets.default.ids       # ③区画を渡す
}

このコードは、このアプリ専用の届け先グループと転送ルールを設定し、2つの部品からの大事な出力をこのモジュールからも外に出す部分です。

ターゲットグループ・転送ルール・出力（HCL）
# このブロックは「このアプリ専用の宛先グループ(届け先の集まり)」を建てる
resource "aws_lb_target_group" "asg" {
  name     = "hello-world-${var.environment}"  # ①環境名込みの名前
  port     = var.server_port
  protocol = "HTTP"
  vpc_id   = data.aws_vpc.default.id

  health_check {
    path                = "/"
    protocol            = "HTTP"
    matcher             = "200"   # ②200(正常)が返れば生きている

🏗️ たとえ話：自分で点検する建物

8.3.3.1 バリデーション

要するに： validationブロックは入力変数の値が条件を満たすか検査し、満たさなければ自分で書いたエラーメッセージを出す。ただし「同じ変数しか参照できない」制限がある。

ハル
ハルバリデーションって何ですか？
棟梁
棟梁Terraform 0.13から、型より細かいチェックを入力変数に足せる。例えばinstance_typeに「無料枠の2つのどちらかであること」を保証できる。

このコードは、機械の大きさ（instance_type）が無料枠のどちらかかを入口で検査し、違えば自分で書いたエラーを出します。

validation の基本（HCL）
# このブロックは「機械の大きさ(instance_type)が無料枠か」を入口で検査する
variable "instance_type" {
  description = "動かすEC2インスタンスの種類（例: t2.micro）"
  type        = string

  validation {
    # ①無料枠の2つのどちらかに含まれていればtrue(合格)
    condition     = contains(["t2.micro", "t3.micro"], var.instance_type)
    error_message = "Only free tier is allowed: t2.micro | t3.micro."  # ②不合格時に出す説明
  }
}

無料枠でない機械を指定して実行すると、こんなエラーが出ます（原因＝検査に不合格）。

不合格時のエラー出力（ターミナル）
# 無料枠でないインスタンスを指定して apply するとこのエラーが出る
$ terraform apply -var instance_type="m4.large"
│ Error: Invalid value for variable
│   on main.tf line 17:
│    1: variable "instance_type" {
│     │ var.instance_type is "m4.large"
│ Only free tier is allowed: t2.micro | t3.micro.
│ This was checked by the validation rule at main.tf:21,3-13.

このコードは、サーバの最小台数を「0より多い」「10以下」の2つの観点から検査する例です。1つの変数に検査を複数足せます。

1変数に複数の validation（HCL）
# このブロックは「サーバの最小台数」を2つの観点から検査する
variable "min_size" {
  description = "ASG内のEC2インスタンスの最小数"
  type        = number

  validation {
    condition     = var.min_size > 0  # ①0以下だと全停止＝障害になるので禁止
    error_message = "ASGs can't be empty or we'll have an outage!"
  }
  validation {
    condition     = var.min_size <= 10  # ②10より多いとコストがかさむので禁止
    error_message = "ASGs must have 10 or fewer instances to keep costs down."
  }
}
ハル
ハル何でもこれでチェックできるんですか？
棟梁
棟梁いや、大きな制限がある。validationのconditionは、そのブロックがある入力変数しか参照できないんだ。他の変数・ローカル変数・リソース・データソースを参照しようとするとエラーになる。
ハル
ハルじゃあ何ができないんですか？
棟梁
棟梁「2つの変数のうち片方だけ設定されていること」のような複数変数にまたがる検査や、「指定AMIがx86_64という種類であること」のような動的な検査はできない。基本的な入力の掃除には便利だが、それ以上は次のprecondition/postconditionが必要だ。

📝 この項のまとめ

  • validationは入力変数の値を条件で検査し、不合格なら自作のエラーを出す。
  • 1変数に複数のvalidationを書ける。
  • 制限: そのブロックがある入力変数しか参照できない。
  • 複数変数にまたがる検査や動的な検査はprecondition/postconditionが必要。

8.3.3.2 事前条件と事後条件

要するに： preconditionは変更を当てる前の前提を点検し、postconditionは当てた後の約束事を点検する。selfキーワードで自分自身の属性を参照できる。

ハル
ハル事前条件と事後条件って、いつ点検するんですか？
棟梁
棟梁名前のとおり。precondition（事前条件）はapplyの前にエラーを捕まえ、postcondition（事後条件）はapplyの後に捕まえる。Terraform 1.2から、リソース・データソース・出力変数で使える。さっきの無料枠チェックも、ハードコードした古くなるリストでなく、データソースで常に最新情報を取って点検できる。

このコードは、指定された機械の情報をAWSから取り、「建てる前に無料枠か」を事前条件で点検する例です。常に最新情報で判定します。

precondition の例（HCL）
# このデータソースは「指定された機械の種類の情報」をAWSから取ってくる
data "aws_ec2_instance_type" "instance" {
  instance_type = var.instance_type
}

# このブロックは「起動設定」。建てる前に無料枠かを precondition で点検する
resource "aws_launch_configuration" "example" {
  image_id        = var.ami
  instance_type   = var.instance_type
  security_groups = [aws_security_group.instance.id]
  user_data       = var.user_data

  lifecycle {
    create_before_destroy = true
    precondition {
      # ①AWSが「無料枠対象」と言っていればtrue(合格)。常に最新情報で判定
      condition     = data.aws_ec2_instance_type.instance.free_tier_eligible
      error_message = "${var.instance_type} is not part of the AWS Free Tier!"
    }
  }
}
precondition 不合格時のエラー（ターミナル）
# 無料枠でないインスタンスで apply するとこのエラーが出る
$ terraform apply -var instance_type="m4.large"
│ Error: Resource precondition failed
│   on main.tf line 25, in resource "aws_launch_configuration" "example":
│   18:    condition = data.aws_ec2_instance_type.instance.free_tier_eligible
│     │ data.aws_ec2_instance_type.instance.free_tier_eligible is false
│ m4.large is not part of the AWS Free Tier!
ハル
ハルアベイラビリティゾーンって何ですか？
棟梁
棟梁同じ地域内の、電源も建物も独立した別々のデータセンタ群（AZ）だ。別々の場所に建てた棟のようなもの。1棟が停電しても別の棟が生きていれば全体は動き続ける。だから2つ以上のAZに建てておけば障害に耐えられる。それをpostconditionで点検しよう。

このコードは、サーバ群を建てた後に「2つ以上の別棟（AZ）に散ったか」を事後条件で点検する例です。1棟だけだと高可用性にならないので警告します。

postcondition と self（HCL）
# このブロックは「サーバ群」。建てた後に「2つ以上のAZに散ったか」を点検
resource "aws_autoscaling_group" "example" {
  name                 = var.cluster_name
  launch_configuration = aws_launch_configuration.example.name
  vpc_zone_identifier  = var.subnet_ids

  lifecycle {
    postcondition {
      # ①自分が建ったAZの数が1より多ければ合格(高可用性が確保された)
      condition     = length(self.availability_zones) > 1
      error_message = "You must use more than one AZ for high availability!"
    }
  }
  # (...)
}

# self式の文法: 囲んでいるリソース自身の属性を指す
self.<ATTRIBUTE>
ハル
ハルselfって何ですか？
棟梁
棟梁self式だ。postcondition・connection・provisionerの中だけで使える。普通の参照だとリソースが自分自身を参照して循環依存のエラーになる。selfはそれを避ける特別な代替策なんだ。

📝 この項のまとめ

  • preconditionは「当てる前」、postconditionは「当てた後」の点検（Terraform 1.2から）。
  • どちらもconditionとerror_messageを持つ。
  • preconditionはデータソースで最新情報を使った安定したチェックができる。
  • postconditionのselfで自分自身の属性を参照できる（循環依存を避ける特別な書き方）。

8.3.3.3 バリデーション、事前条件、事後条件の使い時

要するに： 入力の掃除はvalidation、当てる前の前提はprecondition、当てた後の約束事はpostcondition、それ以上の高度な点検は自動テストツールを使う。

🧹

1 入力の掃除 → validation

不正な変数を渡させない。変更が当たる「前」に基本的な問題を捕まえる。変数のそばに書けて読みやすい。

⏱️

2 前提のチェック → precondition

当たる「前」の前提を点検（複数変数やデータソースを使える）。なるべく早くエラーを捕まえる。

📐

3 約束事の強制 → postcondition

当たった「後」の振る舞いを点検。利用者は「指定通りに建つ、さもなくば止まる」と信用できる。

🤖

4 高度な点検 → 自動テスト

OPA・Terratestなど（9章）。HTTP応答確認・リトライ・内部網接続など。

使い分けの指針（テキスト版）
# 使い分けの指針（すべて本番レベルのモジュールで使うべき）
1. 基本的な入力のサニタイズ → validation
   ・不正な変数を渡させない。変更が当たる「前」に基本的な問題を捕まえる
   ・preconditionより弱いが、変数のそばに書けて読みやすく保守しやすい
2. 基本的な前提のチェック → precondition
   ・変更が当たる「前」に満たすべき前提を点検（複数変数やデータソースを使う検査など）
3. 基本的な約束事の強制 → postcondition
   ・変更が当たった「後」のモジュールの振る舞いを点検
   ・メンテナにとっては守るべき振る舞いの明示になり、リファクタ時に誤って消すのを防ぐ
4. さらに高度な前提/約束事の強制 → 自動テストツール(OPA, Terratestなど。9章)
ハル
ハル4つめの「自動テストツール」は、なんで必要なんですか？ 3つで足りないんですか？
棟梁
棟梁3つはどれも基本的なチェックしかできない。例えば「建てた後、HTTPリクエストに応えられるか」を点検したいとする。デプロイは非同期だから何度もリトライが要るが、Terraformのhttpプロバイダにリトライの仕組みはない。内部用サービスはパブリックインターネットから届かないし、内部網やVPN接続もTerraformだけでは難しい。だから高度な点検は9章のOPAやTerratestに任せるんだ。

🟣 なぜ必要か / これを知ると

  • 不正な入力やおかしな結果を、デプロイの前後で自動的に捕まえられる。
  • 利用者・メンテナの双方に「守るべき約束」を明示できる。
  • どの検査をどの道具で行うか正しく選べる。

📝 この項のまとめ

  • validation＝入力の掃除、precondition＝当てる前の前提、postcondition＝当てた後の約束。
  • 3つとも本番レベルのモジュールで使うべき。
  • 3つは基本的なチェックのみ。HTTP応答確認やリトライ、内部網接続などはできない。
  • 高度な点検は自動テストツール（OPA, Terratest）に任せる（9章）。

要するに： すべての依存関係をバージョン固定する。Terraformコア・プロバイダ・モジュールの3つを特定バージョンに固定し、デプロイを予測可能で繰り返し可能にする。

ハル
ハルバージョン管理って、コードの履歴を残すあれですか？
棟梁
棟梁ここでは2種類ある。①モジュールの依存関係のバージョン管理と、②モジュール自体のバージョン管理だ。Terraformコードが頼るものは3種類ある。
🔧

1 Terraformコア

依存する terraform 本体のバージョン。

required_version
🔌

2 プロバイダ

aws プロバイダなど、各プロバイダのバージョン。

required_providers
📦

3 モジュール

moduleブロックでダウンロードする依存モジュール。

ref付きURL

🏗️ たとえ話：使う建材と工具を型番で固定する

同じ家をもう1棟建てるとき、「だいたい同じ材木」では仕上がりが変わってしまう。だから本物の現場は、使った建材・金具・工具を“型番”まで記録して固定する。バージョン固定はこれだ。型番を固定すれば、今日建てても3年後に建てても同じ建物になり、不具合が出たら前の型番に戻せる。

ハル
ハルなんで固定するんですか？ 新しいほうがいいんじゃ？
棟梁
棟梁固定すると、デプロイが予測可能で繰り返し可能になる。コードを変えなければ今applyしても3年後でも同じ結果だ。バージョン更新は、常に意図的・慎重に、コードに明示して行うべきなんだ。

① Terraformコアのバージョン固定

このコードは、Terraform本体のバージョンを「1.xでなければダメ」または「ちょうど1.2.3」と決める指定です。

required_version（HCL）
# メジャーだけ固定（1.x なら何でも）
terraform {
  required_version = ">= 1.0.0, < 2.0.0"  # 1.0.0以上、2.0.0未満
}

# 本番レベルではマイナー・パッチも固定（ちょうど1.2.3）
terraform {
  required_version = "1.2.3"
}

either choose another supported Terraform version or update the root module's

ハル
ハルメジャーバージョンって何ですか？
棟梁
棟梁番号は「メジャー.マイナー.パッチ」だ。1.2.3なら1がメジャー、2がマイナー（機能追加）、3がパッチ（小修正）。メジャー間は後方互換性がないから1→2は壊れる変更を含みうる。1.0.0以降は公式の互換性の約束があるが、うっかり上がると新機能のズレやバグの恐れがあるから、メジャーは最低限、マイナー・パッチも固定して慎重に上げる。

② プロバイダのバージョン固定

このコードは、使うプロバイダ（AWS）の出どころとバージョンを釘で留める指定です。~> 4.0は「4.xのどれか」という意味です。

required_providers（HCL）
terraform {
  required_version = ">= 1.0.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"  # ①AWSプロバイダの出どころ
      version = "~> 4.0"          # ②4.xのどれか（>= 4.0, < 5.0 と同じ）
    }
  }
}
ハル
ハルマイナーやパッチは固定しなくていいんですか？
棟梁
棟梁Terraform 0.14.0以降はロックファイルで自動的に固定される。初めてterraform initすると.terraform.lock.hclが作られ、2つの情報が記録される。
ロックファイルに記録される2つの情報（テキスト版）
# .terraform.lock.hcl に記録される2つの情報
1. 使用する各プロバイダの正確なバージョン
   ・バージョン管理にチェックインすれば、以降どこで init しても全く同じ版を拾う
   ・明示的に上げたい時: 制約を更新→ terraform init -upgrade → 確認してコミット
2. 各プロバイダのチェックサム（中身の指紋のようなもの）
   ・以降の init でチェックサムが変わるとエラー。悪意あるコードへの差し替えを防ぐ
   ・署名付きプロバイダなら署名の正当性も確認される
棟梁
棟梁チェックサムは中身の指紋だ。こっそり差し替えられても指紋が合わずエラーになる安全装置だ。ただし既定ではinitしたOSの指紋しか記録しない。チームで複数OSを使うなら全プラットフォームの指紋を記録する。
複数OSのチェックサムを記録（ターミナル）
# チームで複数OSを使う場合、全プラットフォームのチェックサムを記録
terraform providers lock \
  -platform=windows_amd64 \  # 64ビット Windows
  -platform=darwin_amd64 \   # 64ビット macOS
  -platform=darwin_arm64 \   # 64ビット macOS (ARM)
  -platform=linux_amd64      # 64ビット Linux

③ モジュールのバージョン固定 / ④ モジュール自体のバージョン管理

このコードは、依存モジュールの出どころを「特定のGitタグ（v0.0.5）」に釘で留めるsource指定と、自分のモジュールにバージョンタグを付けて公開するコマンドです。

ref付きURL と Gitタグ（HCL / bash）

# モジュールに v0.0.5 タグを付けて公開（セマンティックバージョニング）
$ git tag -a "v0.0.5" -m "Create new hello-world-app module"
$ git push --follow-tags
ハル
ハルコード自体のバージョンはどうやって付けるんですか？
棟梁
棟梁セマンティックバージョニングに従ったGitタグだ。例えばステージングにv0.0.5を建てるならこう書く。

このコードは、固定したバージョン（v0.0.5）の hello-world-app モジュールをステージング環境に建てる設計図です。

固定バージョンをステージングに建てる（HCL）

  db_remote_state_bucket = "(YOUR_BUCKET_NAME)"

}

# ロードバランサの住所を素通しする出口
output "alb_dns_name" {
  value       = module.hello_world_app.alb_dns_name

}

ハル
ハルバージョンを固定しておくと、何が嬉しいんですか？
棟梁
棟梁問題なく動けば、本番にも全く同じバージョン＝全く同じコードを建てられる。しかも問題が起きたら、古いバージョンを建て直してロールバックできる。バージョン管理しているからこそできる安全策だ。

Terraformレジストリ（再利用部品の公開棚）

ハル
ハル作ったモジュールを世界に公開することもできるんですか？
棟梁
棟梁Terraformレジストリに登録するんだ。AWS・Google Cloud・Azureなど、コミュニティ手入れのモジュールがたくさんある。登録には決まった要件がある。
レジストリ登録要件と書式（テキスト / HCL）
# パブリックTerraformレジストリへの登録要件
1. モジュールはパブリックなGitHubリポジトリに置く
2. リポジトリ名は terraform-<PROVIDER>-<NAME>（例: aws, rds）
3. 決められたファイル構造（ルートにコード、README.md、main.tf/variables.tf/outputs.tf）
4. 各リリースにセマンティックバージョニングのGitタグを付ける

# レジストリのモジュールは短いURL + version 引数で使える
module "rds" {
  source  = "terraform-aws-modules/rds/aws"  # ①短いURL
  version = "4.4.0"                            # ②バージョンは別の引数
  # (...)
}

社内だけで共有したいときは、Terraform Cloud / EnterpriseのプライベートTerraformレジストリが同じ使い方で使えます。

🟣 なぜ必要か / これを知ると

  • すべての依存とコードを固定すると、いつ・どこで実行しても同じ結果になる（再現性）。
  • 問題が起きたら古いバージョンに戻して安全にロールバックできる。
  • レジストリを使えば、自作モジュールを世界や社内に再利用可能な形で配れる。

📝 この項のまとめ

  • 3種類の依存（Terraformコア・プロバイダ・モジュール）をすべてバージョン固定する。
  • コアはrequired_version、プロバイダはrequired_providers＋ロックファイル、モジュールはref付きGit URLで固定。
  • tfenvと.terraform-versionで環境ごとのTerraformバージョンを自動切り替えできる。
  • モジュール自体はセマンティックバージョニングのGitタグで管理し、ロールバックできる。
  • Terraformレジストリ（公開/プライベート）に登録すれば、短いURL＋version引数で配布・利用できる。

8.3.5 Terraformモジュールの先へ（Terraformの抜け道）

要するに： Terraformで書けない処理のために、プロビジョナ・null_resource・externalデータソースという抜け道がある。ただし移植性が下がり不安定になるので控えめに使う。

ハル
ハルインフラって、全部Terraformで済むんですか？
棟梁
棟梁いや。現場ではDocker、Packer、Chef、Puppet、それに「DevOps界のダクトテープであり接着剤であり主役でもある」信頼のBashスクリプトも使う。これらのコードもTerraformと一緒にmodulesフォルダに置ける。さらにTerraformから別のコードを動かす「抜け道」が3つあるんだ。
📜

1 プロビジョナ

apply/destroy時にローカルやリモートでスクリプトを実行。

🫙

2 null_resource

特定のリソースに紐付けずにスクリプトを実行。

🔗

3 external

外部コマンドを実行し、その結果をTerraform内で使う。

🏗️ たとえ話：規格外の特注工事

建材を規格品で組み上げるのが基本だが、どうしても規格品では作れない箇所には、職人が手作業で特注の細工を入れる。仕上がりは良くても、その職人がいないと再現できず、別の現場へは持っていきにくい。抜け道も同じで、便利だが「この環境でしか動かない」不安定さを抱える。最後の手段だ。

8.3.5.1 プロビジョナ

ハル
ハルプロビジョナって何ですか？
棟梁
棟梁Terraform実行時にスクリプトを走らせる仕組みだ。ブート処理、設定管理、後始末などに使う。種類がいくつかある。
💻

local-exec

自分のローカルマシンでスクリプトを実行。

🌐

remote-exec

リモートのリソース(EC2など)上でスクリプトを実行。

📁

file

ファイルをリモートのリソースへコピーする。

このコードは、サーバを建てた後にローカルマシンでスクリプト（ローカルOSの情報表示）を走らせる例です。

local-exec の例（HCL / ターミナル）
# このブロックは「サーバを建てた後、ローカルでスクリプトを走らせる」
resource "aws_instance" "example" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t2.micro"

  provisioner "local-exec" {
    command = "echo \"Hello, World from $(uname -smp)\""  # ①ローカルOS情報を表示
  }
}

# apply するとローカルマシンでスクリプトが走る
aws_instance.example (local-exec): Hello, World from Darwin x86_64 i386
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
棟梁
棟梁remote-execはリモートのEC2で動かす。そのためにはTerraformクライアントが①ネットワーク経由で通信でき（セキュリティグループで許可）、②認証できる（SSHやWinRM）必要がある。サンプルはUbuntuだからSSH鍵を使う。

このコードは、SSH（ポート22）を許可する通行ルールと、試しやすいようTerraformで秘密鍵を自動生成し公開鍵をAWSへ上げる部分です（本番では鍵はTerraformとは別に管理すべき）。

SSH準備（セキュリティグループ・鍵生成）（HCL）
# ポート22(SSH)への接続を許可する通行ルール
resource "aws_security_group" "instance" {
  ingress {
    from_port = 22
    to_port   = 22
    protocol  = "tcp"
    # この例を簡単に試せるように、すべてのSSH接続を許可。実世界では信頼できるIPのみに。
    cidr_blocks = ["0.0.0.0/0"]  # ①どこからでも許可(本番では危険)
  }
}

# この例を簡単に試せるように、Terraformでプライベートキーを生成（本番は別管理）
resource "tls_private_key" "example" {
  algorithm = "RSA"
  rsa_bits  = 4096
}

# 生成した公開鍵をAWSへアップロード
resource "aws_key_pair" "generated_key" {
  public_key = tls_private_key.example.public_key_openssh  # ①作った鍵の公開側
}
ハル
ハルなんでこの鍵生成は本番に向かないんですか？
棟梁
棟梁秘密鍵がTerraformステートに保存されてしまうからだ。秘密の鍵がステートに丸見えになる。学習にはいいが本番には向かない。

このコードは、Ubuntuサーバを1台建ててSSH用の鍵を紐付け、そのサーバ上でスクリプトを走らせ（remote-exec）、つなぎ方をconnectionで教える部分です。

remote-exec と connection（HCL）
# Ubuntuサーバを1台建て、SSH用の鍵を紐付け、リモートでスクリプトを走らせる
resource "aws_instance" "example" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.instance.id]
  key_name               = aws_key_pair.generated_key.key_name  # ①鍵を紐付け

  provisioner "remote-exec" {
    # ①command ではなく inline で「実行するコマンドの一覧」を渡す
    inline = ["echo \"Hello, World from $(uname -smp)\""]
  }

  connection {
    type        = "ssh"                              # ①SSHでつなぐ
    host        = self.public_ip                     # ②このサーバ自身のパブリックIP(self)
    user        = "ubuntu"                           # ③Ubuntuの既定ユーザー名
    private_key = tls_private_key.example.private_key_pem  # ④自動生成した秘密鍵
  }
}
apply の動き（ターミナル）
$ terraform apply
aws_instance.example: Creating...
aws_instance.example (remote-exec): Connecting to remote host via SSH...
(... 数回繰り返す ...)
aws_instance.example (remote-exec): Connected!
aws_instance.example (remote-exec): Hello, World from Linux x86_64 x86_64
Apply complete! Resources: 4 added, 0 changed, 0 destroyed.
ハル
ハル「Connecting...」が何回も出てますね。プロビジョナって毎回走るんですか？
棟梁
棟梁remote-execはEC2がいつ接続を受けられるか正確には知らないから、成功かタイムアウト（既定5分）まで何度も繰り返す。それと、既定は作成時プロビジョナで初回だけ走る。when = destroyを付けると削除時に走る。複数付けると上から順に実行し、on_failureでcontinue（無視）かabort（中止）を選べる。

プロビジョナとユーザーデータ — どちらを使う？

ハル
ハルremote-execとユーザーデータ、どっちを使えばいいんですか？
棟梁
棟梁普通はユーザーデータの方が有益だと著者は言う。理由を挙げよう。
🔐

1 安全・楽

SSH/WinRM不要、AWS APIアクセスだけで済む（どのみち必須）。

📈

2 ASGと併用

オートスケール等で起動した全サーバに起動時スクリプトを実行できる。

🔎

3 確認しやすい

EC2コンソールで内容も実行ログも見られる。デバッグに便利。

ハル
ハルじゃあプロビジョナを使う利点はないんですか？
棟梁
棟梁現実的な利点が1つある。ユーザーデータは16KBまでの長さ制限があるが、プロビジョナのスクリプトは任意の長さにできる。長い仕込みが必要ならそこだけプロビジョナの出番だ。

📝 この項のまとめ

  • プロビジョナはlocal-exec（ローカル）、remote-exec（リモート）、file（コピー）などがある。
  • remote-execはネットワーク疎通とSSH/WinRM認証が必要。
  • 既定は作成時プロビジョナ（初回のみ）。when = destroyで削除時プロビジョナになる。
  • 複数指定は上から順に実行。on_failureでcontinue/abortを選べる。
  • 通常はユーザーデータの方が有益。プロビジョナの利点は長さ無制限。

8.3.5.2 null_resourceとプロビジョナ

要するに： null_resourceは何も作らない器。プロビジョナを紐付けて任意のスクリプトを走らせられ、triggersの値が変わると再実行される。

ハル
ハルプロビジョナはリソースの中にしか書けないんですよね。特定のリソースに紐付けずに走らせたいときは？
棟梁
棟梁null_resourceを使う。これにプロビジョナを書けば、実際のリソースに紐付けずにスクリプトを走らせられる。
ハル
ハル毎回applyのたびに走らせたいときは？
棟梁
棟梁triggersに、呼ぶたびに新しい値を返すuuid()を入れればいい。毎回値が変わるから毎回作り直され、再実行される。

このコードは、何も作らない器（null_resource）でスクリプトを走らせる例と、apply のたびに必ず走らせる（uuid()で毎回作り直す）例です。

null_resource と triggers（HCL / ターミナル）
# 何も作らない器でローカルスクリプトを走らせる
resource "null_resource" "example" {
  provisioner "local-exec" {
    command = "echo \"Hello, World from $(uname -smp)\""  # ①ローカルOS情報を表示
  }
}

# apply のたびに必ずスクリプトを走らせる器
resource "null_resource" "example" {
  triggers = {
    uuid = uuid()  # ①毎回違う値→毎回作り直し→毎回再実行
  }
  provisioner "local-exec" {
    command = "echo \"Hello, World from $(uname -smp)\""
  }
}

# apply するたびに local-exec が実行される
$ terraform apply
null_resource.example (local-exec): Hello, World from Darwin x86_64 i386
$ terraform apply
null_resource.example (local-exec): Hello, World from Darwin x86_64 i386

📝 この項のまとめ

  • null_resourceは何も作らないが、プロビジョナを紐付けてスクリプトを実行できる。
  • triggers（キーと値のマップ）の値が変わると再作成され、プロビジョナが再実行される。
  • triggersにuuid()を入れると、apply のたびに毎回再実行できる。

8.3.5.3 外部データソース

要するに： externalデータソースは外部プログラムをJSONでやりとりして呼び出し、その結果をTerraform内で使う抜け道。移植性が下がるので控えめに。

ハル
ハルスクリプトでデータを取ってきて、それをTerraformコードの中で使いたいときは、プロビジョナでいいんですか？
棟梁
棟梁「データを取得してTerraformコード内で使う」のが目的なら、externalデータソースを使う。約束事（プロトコル）はこうだ。
1

Terraform → 外部プログラム

query 引数の中身をJSONとして標準入力で渡す。

2

外部プログラム → Terraform

結果をJSONで標準出力に書く。Terraform側は result 出力属性でそのJSONを取り出せる。

このコードは、標準入力をそのまま返すBashを外部コマンドとして呼び、渡したデータがそのまま結果として戻ってくる例です。

external データソースの例（HCL / ターミナル）
# 外部コマンドを呼び、渡したデータをそのまま受け取る
data "external" "echo" {
  program = ["bash", "-c", "cat /dev/stdin"]  # ①標準入力をそのまま返すBash
  query = {
    foo = "bar"  # ②外部プログラムに渡すデータ
  }
}

output "echo"     { value = data.external.echo.result }      # 結果全体
output "echo_foo" { value = data.external.echo.result.foo }  # foo の値だけ

# apply すると、渡したデータがそのまま返ってくる
$ terraform apply
Outputs:
echo = {
  "foo" = "bar"
}
echo_foo = "bar"
棟梁
棟梁data.external.<NAME>.resultが返ってきたJSON全体を持ち、.result.<PATH>で中身を読み出せる。
ハル
ハル便利ですね！ どんどん使っていいですか？
棟梁
棟梁いや、控えめに。抜け道はコードの移植性を下げて不安定にする。今のコードはBash依存だから、このモジュールはWindowsからデプロイできない。既存のデータソースで取れないデータが本当に必要なときの、最後の抜け道だと思っておけ。

🟣 なぜ必要か / これを知ると

  • Terraformの宣言だけでは書けない処理（スクリプト実行、外部データ取得）を補える。
  • 別ツール（Bash, Packer等）とTerraformを統合できる。
  • 抜け道の代償（移植性低下・不安定さ）を知れば、使うべき場面を見極められる。

📝 この項のまとめ

  • Terraformで書けない処理の抜け道は、プロビジョナ・null_resource・externalデータソースの3つ。
  • externalは外部コマンドとJSON（標準入出力）でやりとりし、resultで結果を取り込む。
  • 抜け道は移植性を下げ不安定にするので、控えめに使う（例: Bash依存だとWindowsで動かない）。

章末の理解度チェック自分の言葉で答えてみよう（全5問）

第1問本番レベルのインフラが時間のかかる3つの理由

本番レベルのインフラ構築がなぜ時間がかかるのか、3つの理由を自分の言葉で説明してください。また「偶有的複雑性」と「本質的複雑性」のどちらに当たるかも添えてください。

✅ 解答例
1つめは分野がまだ生まれたてで道具も手法も未熟だから（偶有的）。2つめはヤクの毛刈り、つまり目的の作業にたどり着く前に無関係な小作業が次々連鎖するから（偶有的）。3つめは本番に必要なタスクがもともと多く、多くの人がそれを見積もりから落とすから（本質的）。
📝 採点ポイント
  • 3つの理由（未熟さ・ヤクの毛刈り・タスクが本来多い）を挙げている
  • ヤクの毛刈りを「無関係な小作業の連鎖」と説明できている
  • 偶有的（道具のせい）と本質的（課題そのもの）の区別を正しく対応づけている
第2問大きなモジュールの弊害

全インフラを1つの大きなモジュールにまとめると、どんな問題が起きますか。3つ以上挙げて説明してください。

✅ 解答例
planの実行が遅くなる。何か直すのに全体への権限が要り、皆が管理者になって最小権限の原則に反する。ミスの波及範囲が大きく、ステージングの小変更のつもりで本番DBを壊しかねない。コードもplan出力も膨大で読めず、危険な変更を見逃す。テストもほぼ不可能になる。
📝 採点ポイント
  • 「遅い・セキュアでない・リスク大・理解しにくい・レビューしにくい・テストしにくい」のうち3つ以上を挙げている
  • 「セキュアでない」を最小権限の原則と結びつけて説明できている
  • 解決策として「小さなモジュールに割る」ことに触れている
第3問validation / precondition / postcondition の使い分け

validationブロック、preconditionブロック、postconditionブロックは、それぞれどんなときに使いますか。また、これらでは対応できない高度な点検はどうしますか。

✅ 解答例
validationは入力変数の基本的な掃除（同じ変数しか参照できない）。preconditionは変更を当てる前の前提チェック（複数変数やデータソースを使える）。postconditionは当てた後の約束事チェック（selfで自分の属性を参照できる）。HTTP応答確認やリトライ、内部網接続のような高度な点検は、OPAやTerratestなどの自動テストツールを使う。
📝 採点ポイント
  • validation＝入力の掃除、precondition＝当てる前、postcondition＝当てた後、と対応づけている
  • validationは同じ変数しか参照できないという制限に触れている
  • 高度な点検は自動テストツール（OPA/Terratest）が必要と述べている
第4問3つの依存関係のバージョン固定

Terraformコードの3種類の依存関係とは何ですか。それぞれをバージョン固定する方法と、固定する理由を説明してください。

✅ 解答例
Terraformコア・プロバイダ・モジュールの3つ。コアはrequired_version、プロバイダはrequired_providers（マイナー/パッチは.terraform.lock.hclで自動固定）、モジュールはrefでGitタグを指定したURLで固定する。固定する理由は、コードを変えなければいつ・どこで実行しても同じ結果になり、デプロイが予測可能で繰り返し可能になるから。問題時に古い版へロールバックもできる。
📝 採点ポイント
  • 3種類（コア・プロバイダ・モジュール）を正しく挙げている
  • それぞれの固定方法（required_version / required_providers＋ロックファイル / ref付きURL）を述べている
  • 固定の理由（再現性・ロールバック）を説明できている
第5問Terraformの抜け道とその注意

Terraformで書けない処理のための「抜け道」を3つ挙げ、使うときの注意点を説明してください。

✅ 解答例
プロビジョナ（apply/destroy時にローカルやリモートでスクリプト実行）、null_resource（何も作らない器にプロビジョナを紐付けて実行）、externalデータソース（外部コマンドとJSONでやりとりして結果を取り込む）の3つ。注意点は、移植性が下がり不安定になること。例えばBash依存のexternalはWindowsで動かないので、控えめに最後の手段として使う。
📝 採点ポイント
  • 抜け道3つ（プロビジョナ・null_resource・external）を挙げている
  • externalがJSON（標準入出力）でやりとりすることに触れている
  • 移植性低下・不安定さの注意点（例: Bash依存はWindows不可）を述べている
