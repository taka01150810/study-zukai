ステート / ステートファイル state file

Terraformが「何をどこに建てたか」を書き留める台帳。設計図のリソースと実物を結ぶ対応表。

バックエンド backend

台帳をどこに読み書きするかを決める仕組み。ローカル（手元）かリモート（共有金庫）か。

S3 Simple Storage Service

AWSの貸し倉庫サービス。ここでは台帳をしまう「金庫」の役。

DynamoDB ダイナモDB

Amazonのキーバリューデータベース。ここでは「今だれが作業中」を記録する「鍵」の役。

ロック lock

2人が同時に台帳を書き換えて壊さないよう、順番待ちさせる鍵の仕組み。

ワークスペース workspace

同じ設計図の台帳を、いくつもの別棚に分けて持つ仕組み。実験向き。

バージョニング versioning

金庫の中身を上書きするたびに、古い版も全部とっておく機能。巻き戻せる。

シークレット secret

パスワードなどの秘密情報。台帳に丸見えで書かれるので扱いに注意。

プレーンテキスト plain text

暗号化されていない、そのまま読める素の文字。

部分設定 partial configuration

backend設定の共通部分を別ファイルに出し、残りを後から渡す方法。コピペを減らす。

コンポーネント component

一緒にデプロイされやすいリソースのひとかたまり（ネットワーク、DB、Webなど）。

terraform_remote_state

別の現場の台帳を読み取り専用で開き、出力値を借りてくるデータソース。

データソース data source

外から情報を読み取るだけの仕組み。書き換えはしない。

RDS Relational Database Service

AWSがデータベースの運用を肩代わりしてくれるサービス。

templatefile

外部ファイルをテンプレートとして読み、変数の値を埋めて文字列にするビルトイン関数。

冪等性 べきとうせい

何回やっても結果が同じになる性質。`init`は何度実行しても安全。

prevent_destroy

大事なリソースを誤って消そうとするとエラーで止める、おまもり設定。

三項演算子 ternary

「もし〜なら A、でなければ B」を1行で書く書き方（`条件 ? A : B`）。

🏗️ この章の世界

工房のみんなで街を作っています。何をどこに建てたかは「現場台帳（建築記録簿）」に書き留めます。台帳をどこにしまうか（金庫）、誰かが書いている間どう待たせるか（鍵）、現場ごとにどう分けるか——この章ではすべてを「台帳・金庫・鍵」のたとえで説明します。

🤔 なぜこれを学ぶのか

  • 台帳の置き場所を間違えると、チーム作業で建物が二重に建ったり消えたりする事故が起きる。
  • インフラのバグは「アプリの一部が壊れる」で済まず、街全体・データベース全体が吹き飛ぶほど影響が大きい。
  • 環境（テスト用・本番用）を分けないと、テストのつもりで本番を壊す悲劇が起きる。

✅ これを知ったらできること

  • チーム全員で安全に同じインフラをいじる仕組み（金庫＋鍵）を組める。
  • 環境やコンポーネントごとに台帳を分け、事故の被害を最小化する設計ができる。
  • ある現場の台帳から別の現場が情報を読み出す（DBの住所をWebサーバへ渡す等）使い方ができる。
3.1

Terraformステートとは

台帳は「設計図のリソース」と「実物」を結ぶ対応表

🧭 要するに：ステートファイルは「設計図のリソース」と「実物のインフラ」を結ぶ対応表で、Terraformはこれを見て差分を判断する。手で触らないのが鉄則。

🏗️ たとえ話

工房は工事をするたびに「何をどこに建てたか」を1冊の現場台帳に書き留めます。台帳の各ページには「設計図に書いた建物の呼び名」と「実際に建った建物の住所札（ID）」が一対一で並んでいます。棟梁は次の工事のたびに、現場へ行って実物の今の様子を確認し、台帳と設計図を見比べて「ここが違う」という差分を見つけるのです。

ハル
ハル棟梁、Terraformって apply のたびに「前に建てたやつ」をちゃんと覚えてますよね。どうやって覚えてるんですか？
棟梁
棟梁工事のたびに「何をどこに建てたか」を1冊の台帳に書き留めているんだ。これをステートと呼ぶ。記録するファイルがステートファイルだよ。
ハル
ハル台帳！ どこに置いてあるんですか？
棟梁
棟梁いまの作業フォルダの中だ。/foo/bar で実行したら、デフォルトで /foo/bar/terraform.tfstate という台帳ができる。中身はJSONで、「設計図に書いたリソース」と「実際にAWSに建ったモノ」の対応表になっている。

下は「サーバを1台建てる設計図」です（読まなくてOK）。

HCL：更地にサーバを1台建てる設計図
# このコードは更地にサーバを1台建てる設計図
resource "aws_instance" "example" {  # ① AWSのサーバ1台。名前は example
  ami           = "ami-0fb653ca2d3203ac1"  # ② ami = サーバに入れておくOSの型番
  instance_type = "t2.micro"               # ③ サーバの大きさ（t2.micro = いちばん小さい型）
}

ハル
ハルこの id の i-0bc4bbe5b84387543 っていうのが…？
棟梁
棟梁それが実物サーバの番号（住所札）だ。Terraformは「設計図の example＝ID i-0bc4… のサーバ」だとこの台帳で知る。実行のたびにAWSから今の状態を取ってきて、手元の設計図と見比べる。その差分が plan の出力だよ。
ハル
ハルじゃあ台帳を私が直接書き換えてもいいですか？
棟梁
棟梁やめておきなさい。台帳はTerraformが内部で使うプライベートな帳簿だ。手で書き換えたり、読むコードを自作してはいけない。操作が必要なら terraform import や terraform state という専用コマンドを使う（5章で扱う）。

🤔 なぜ必要か

  • Terraformが「管理すべきインフラ」を見分けられるのは、この台帳のおかげ。
  • 仕組みを知れば、plan の差分がなぜ出るのかを正しく読める。

📝 この項のまとめ

  • 台帳（terraform.tfstate）は実行ごとに自動で作られ、JSONで書かれる。
  • 中身は「設計図のリソース」と「実物のリソースのID」の対応表。
  • 実行のたびにAWSから実物の状態を取り、設計図と比べて差分を出す。
  • 台帳は手で編集しない。必要なら terraform import / terraform state を使う。

3.2

ステートファイルの共有ストレージ

台帳はGitでなくS3の金庫へ。鍵はDynamoDB

🧭 要するに：台帳は素テキストの秘密入りなのでGitには置かず、S3の金庫（暗号化＋バージョニング＋公開禁止）に置き、DynamoDBで鍵をかける。

🏗️ たとえ話

台帳をみんなの回覧板（Git）で回すと、最新版を取り忘れたり戻し忘れたりして混乱します。しかも台帳には金庫の暗証番号（パスワード）まで丸見えで書いてある。だから台帳は工房の頑丈な金庫（S3）にしまい、入口に「今だれかが書き込み中」を示す鍵（DynamoDB）を付けます。金庫は中身を自動で暗号化し、古い版も全部とっておきます。

ハル
ハルみんなで同じ台帳を見るなら、Gitに入れちゃえばいいんじゃ？
棟梁
棟梁一見よさそうだろう。でもあまりいい考えではない。理由が3つある。
ハル
ハルえっ、ダメなんですか。なんで？
棟梁
棟梁一つ目は「手作業ミス」。最新の台帳を引っ張る（プル）のを忘れたり、終わって押し戻す（プッシュ）のを忘れたり。古い台帳で作業すると巻き戻しや二重建てが起きる。二つ目は「ロック」。Gitには2人同時の apply を止める鍵がほぼ無い。
ハル
ハル三つ目は？
棟梁
棟梁シークレットだ。台帳は全部プレーンテキストで書かれる。DBを作るとユーザー名とパスワードが丸見えで書き込まれる。そんなものGitには置けない。
ハル
ハルたしかに…。じゃあ台帳はどこに？
棟梁
棟梁Terraformのバックエンドを使う。普段はローカルバックエンド（手元）。これをリモートバックエンドに変えると、台帳を共有の金庫に置ける。候補はS3、Azure Blob、Google Cloud Storage、Terraform Cloud/Enterpriseなど。

リモートバックエンドが3つの問題をどう解決するか

問題リモートバックエンドの解決
手作業ミスplan/apply のたびに台帳を金庫から自動で取り出し、終わると自動で戻す。取り違えゼロ。
ロック多くが鍵を標準装備。apply時に自動で鍵を取り、作業中なら空くのを待つ。-lock-timeout=10m で待ち時間も指定可。
シークレット送受信時・保管時の暗号化を標準装備。アクセス権（S3ならIAMポリシー）で誰が見られるか制御できる。

金庫（S3バケット）を建てる

まずどの地域に建てるかを決め（読まなくてOK）、金庫そのものを作ります。

HCL：プロバイダ（地域）と金庫の作成
# どの地域(リージョン)に建てるかを決める設定
provider "aws" {
  region = "us-east-2"  # ① us-east-2 = アメリカ・オハイオの地域
}

# 台帳をしまうための金庫(S3バケット)を1つ建てる
resource "aws_s3_bucket" "terraform_state" {
  bucket = "terraform-up-and-running-state"  # ① 金庫の名前。世界で重複NGなので自分専用に変える

  # 誤って金庫ごと削除するのを防ぐおまもり
  lifecycle {
    prevent_destroy = true  # ② trueなら、この金庫を消そうとするとエラーで止まる
  }
}
ハル
ハルbucket の名前ってなんでもいい？
棟梁
棟梁いや、S3バケット名は全AWS顧客の中で世界に1つだけ。terraform-up-and-running-state は私が使い済みだから、君は自分専用に変えること。使ったバケット名とリージョン名は後で使うのでメモ。
ハル
ハルprevent_destroy っていうのは？
棟梁
棟梁2章の create_before_destroy に続く2つ目のライフサイクル設定だ。true にすると、そのリソースを消す操作でエラーが出て止まる。台帳を全部しまう大事な金庫をうっかり消さないためのおまもりだよ。本当に消すときはこの設定をコメントアウトする。

金庫を守る3つの層

1

バージョニング

金庫の中身を上書きするたびに古い版もとっておく。問題が起きたら古い版に戻せる。

2

保管時の暗号化

金庫に入れる全データを自動で暗号化（AES256）。

3

パブリックアクセスのブロック

「だれでも見られる公開状態」を全方向から禁止する。

HCL：金庫を守る3層（バージョニング・暗号化・公開禁止）
# ① 上書きのたびに古い版もとっておく(バージョニング)
resource "aws_s3_bucket_versioning" "enabled" {
  bucket = aws_s3_bucket.terraform_state.id
  versioning_configuration {
    status = "Enabled"  # 過去の版を全部保存。古い版に戻せる
  }
}

# ② 金庫に入れたデータを自動で暗号化
resource "aws_s3_bucket_server_side_encryption_configuration" "default" {
  bucket = aws_s3_bucket.terraform_state.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"  # 標準的な強い暗号方式
    }
  }
}

# ③ 金庫が丸ごと公開されるのを明示的に禁止
resource "aws_s3_bucket_public_access_block" "public_access" {
  bucket                  = aws_s3_bucket.terraform_state.id
  block_public_acls       = true  # 4つすべてtrueで公開設定を全方向から禁止
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
ハル
ハルS3ってもともと非公開なのに、なんでわざわざ禁止するんですか？
棟梁
棟梁確かにデフォルトは非公開だ。でもS3は画像・CSS・JS・HTMLの配信にもよく使われるから、うっかり公開設定にするのも簡単なんだ。台帳には秘密が入りうるから、保護の層を1段余計に足しておく。

鍵（DynamoDBテーブル）を作る

ハル
ハルDynamoDBって何ですか？
棟梁
棟梁Amazonの分散キーバリューストアだ。鍵に必要な「強い整合性のある読み込み」と「条件付き書き込み」を備えている。完全マネージドで安価、たいてい無料枠に収まる。
ハル
ハルそれで鍵がかけられると？
棟梁
棟梁そうだ。LockID という主キーを持つテーブルを作る。このスペルと大文字小文字は完全に一致させること。
HCL：鍵の役目をするDynamoDBテーブル
# 「誰かが作業中」を記録して鍵の役目をするDynamoDBテーブル
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-up-and-running-locks"  # ① テーブル名。自分専用に変える
  billing_mode = "PAY_PER_REQUEST"                 # ② 使った分だけ課金
  hash_key     = "LockID"                          # ③ 鍵となる見出し。LockIDと完全一致

  attribute {
    name = "LockID"  # ④ LockIDという項目を文字列で用意
    type = "S"       # ⑤ S = String(文字列)
  }
}

ここまで書いたら、初期化して金庫と鍵を実際に建てます。

bash：初期化して金庫と鍵を建てる
# プロバイダのコードを取得して初期化し、金庫と鍵を建てる
terraform init
terraform apply

台帳を金庫にしまう（バックエンド設定）

ハル
ハルこれで金庫と鍵ができましたね。台帳はもう金庫に入ってる？
棟梁
棟梁まだだ。今は台帳がローカルのまま。terraform ブロックの中にバックエンド設定を足して、台帳を金庫(暗号化＆ロック付き)に保存するよう指定する必要がある。
HCL：バックエンド設定の型 と S3用の設定
# 台帳の置き場所を教える設定の「型」
terraform {
  backend "<BACKEND_NAME>" {
    [CONFIG...]
  }
}

# 台帳をS3の金庫に保存し、DynamoDBで鍵をかける設定
terraform {
  backend "s3" {
    bucket         = "terraform-up-and-running-state"        # ① 台帳をしまう金庫の名前

3.3

Terraformバックエンドの制限

鶏が先か卵が先か問題と、変数が使えない問題

🧭 要するに：バックエンドには2つの落とし穴がある。①金庫自体をTerraformで作る順番問題、②backend内で変数が使えずコピペが増える問題。後者は部分設定やTerragruntで軽減する。

🏗️ たとえ話

台帳をしまう金庫そのものを、台帳に記録しながら工房が建てるという妙な状況です。だから「まず金庫を手元の台帳で建て、できたら金庫に台帳を移す」と2段階で進めます。さらに金庫の住所欄には、走り書きのメモ（変数）が使えず、各現場の台帳ごとに住所を手書きで写す必要がある。写し間違えると別の現場の台帳を上書きしてしまうので要注意です。

制限1：鶏が先か卵が先か

ハル
ハル完璧じゃないですか！ でも…台帳をしまう金庫を、Terraform自身で作りましたよね？ その金庫の台帳はどこに？
棟梁
棟梁鋭い。それが1つ目の制限、「鶏が先か卵が先か」だ。これは2段階で対処する。
🏗️

金庫を作る（2ステップ）

① S3バケットとDynamoDBを作るコードをローカルバックエンドで実行してデプロイ。
② backend 設定を足し、terraform init でローカルの台帳をS3へコピー。

🧹

金庫を消す（逆順2ステップ）

① コードから backend 設定を消し、init で台帳をローカルに戻す。
② terraform destroy で金庫と鍵を消す。

棟梁
棟梁面倒に見えるが、金庫と鍵は全Terraformコードで共有できるから、この手順は基本1回だけ（AWSアカウントを複数作るならアカウントごとに1回）。一度作れば、後は backend 設定を書くだけだ。

制限2：backendの中では変数が使えない

棟梁
棟梁もっと厄介だ。backend ブロックの中では変数や参照が使えない。たとえばこう書いても動かない。
HCL：これは動かない例（backend内で変数は不可）

  }

ハル
ハル変数が使えないと、モジュールごとに金庫名やリージョンを毎回手でコピペ？
棟梁
棟梁その通り（補足: モジュール＝コードを再利用しやすく構造化する仕組み。実コードは小さなモジュールの寄せ集めになる、と今は思っておけばいい。詳しくは後章）。しかも厄介なのは key だけはコピーしてはいけない点だ。別モジュールと同じ key にすると台帳を上書きしてしまう。つまり「他はコピペ、key だけ毎回手で変える」。これがミスの温床だ。
ハル
ハルコピペ地獄ですね…減らす方法は？
棟梁

棟梁

🤔 なぜ必要か

  • 順番を知らないと、金庫を作る前にbackend設定を書いてつまずく。
  • コピペ問題の対処法を知れば、多数のモジュール・環境でもミスを減らせる。

📝 この項のまとめ

  • 制限1: 金庫はTerraformで作るので「作成は2ステップ、削除は逆順2ステップ」。基本1回で済む。
  • 制限2: backend ブロックでは変数・参照が使えない。
  • key だけはコピペ厳禁。モジュールごとに一意にする。
  • コピペ削減策は「部分設定（-backend-config）」か「Terragrunt」。
3.4

ステートファイルの分離

船の隔壁のように、現場ごとに台帳を仕切る

🧭 要するに：全インフラを1冊の台帳にまとめると、1か所のミスが全体を壊す。船の隔壁のように仕切り、台帳を分ける。分け方は2つ：ワークスペースとファイルレイアウト。

🏗️ たとえ話

1冊の台帳に全現場を書くと、テスト現場のページを直すつもりが本番現場のページを破ってしまう事故が起きます。最悪、台帳ごと水没して全現場が吹き飛ぶことも。だから船のように、現場を隔壁（仕切り壁）で区切り、浸水を1区画に閉じ込めます。仕切り方は2つ。手早い実験向けの「別棚（ワークスペース）」と、本番向けにがっちり分ける「別の部屋（フォルダレイアウト）」です。

ハル
ハル共有も鍵も解決しましたね。残るは…分離でしたっけ？
棟梁
棟梁そうだ。全インフラを1ファイルにまとめると台帳も1冊にまとまり、どこか1か所のミスが全体を壊しかねない。
ハル
ハルたとえばどんな悲劇が？
棟梁
棟梁新版をステージングだけに入れるつもりが本番を壊す。最悪、台帳全体を壊したり、ロック無しでTerraformの稀なバグを踏むと全環境の全インフラが吹き飛ぶ。だから船の隔壁のように設計にも仕切りを入れる（図3-3）。環境を別々のTerraform設定にすれば、1つの問題が他から完全に切り離される。

コマンドを打たない限り、今どの棚にいるかコードやターミナルから分からない。確認しづらく保守が難しい。

⚠️

棟梁
棟梁（補足: 厳密にはS3のパスごとにIAMポリシーを変えて権限を分けることもできるが管理が複雑になる。AWSのベストプラクティスは環境ごとにアカウントを分けることを推奨—7章。）だから環境分離にワークスペースは適切でない。（補足: 公式ドキュメントも同じ指摘だが他段落に埋もれている。昔ワークスペースは environments と呼ばれ混乱する人が多い。）正しい環境分離は次節のファイルレイアウトを使う。
棟梁
棟梁次に進む前に、3つの棚に建てたEC2を消しておこう。terraform workspace select <棚名> で各棚に移り、それぞれ terraform destroy を実行する。

🤔 なぜ必要か

  • 本番に触れず安全に実験用のコピーを作れる。
  • ワークスペースの限界を知り、環境分離にはファイルレイアウトを選べるようになる。

📝 この項のまとめ

  • ワークスペースは台帳を別棚に分ける。最初は default。new/select/list/show で操作。
  • 棚ごとに台帳は完全独立。切り替え＝保存パスの切り替え（S3の env: 配下）。
  • terraform.workspace で棚名を読み、振る舞いを変えられる（三項演算子など）。
  • 欠点: 同じバックエンド・同じ権限、今いる棚が見えにくい、ミスを誘う。
  • 環境分離には使わない。実験用に使う。

ファイルレイアウトによる分離

🧭 要するに：本番の環境分離はワークスペースでなくフォルダ分け（環境ごと→コンポーネントごと）で行い、環境ごとに別バックエンド・別認証・別権限を使う。利点は明確さと分離、裏返しの欠点はフォルダ多数・コピペ増・依存参照の難しさ。

🏗️ たとえ話

現場ごとに別の部屋（フォルダ）を用意し、部屋ごとに別の金庫・別の鍵・別の入室許可証を割り当てます。さらに部屋の中も「ネットワーク棟」「サービス棟」「データ倉庫」と区画を分ける。月1回しか触らないネットワーク棟と、1日に何度も改装するサービス棟を同じ部屋に置くと、改装のたびにネットワーク棟を壊す危険を負うからです。台帳の置き場所も部屋の住所と揃えれば、迷子の台帳が出ません。

各環境のファイルを別フォルダに（例: ステージングは stage、本番は prod）。

🔑

環境ごとに違うバックエンド・違う認証情報・違うアクセス権（例: 別のAWSアカウント、別のS3バケット）。

棟梁

ハル

棟梁

推奨ファイルレイアウト（3階層）

1

トップ＝環境フォルダ

stage（本番直前・テスト用）／prod（本番）／mgmt（DevOpsツール用。踏み台・CIサーバ。mgmt=managementの略）／global（全環境共通のS3・IAM等）

2

その中＝コンポーネントフォルダ

vpc（ネットワークトポロジ）／services（アプリ・マイクロサービス。各アプリ別フォルダ）／data-storage（MySQL・Redis等。各データストア別フォルダ）

3

その中＝設定ファイル（命名規則）

variables.tf（入力変数）／outputs.tf（出力変数）／main.tf（リソースとデータソース）

ハル
ハルファイル名って決まってる？ 別の名前じゃダメ？
棟梁
棟梁Terraform自身はカレントの .tf を全部探すから名前は何でも動く。でも仲間は気にする。一貫した推測できる名前なら、入力変数・出力変数・リソースがどこにあるかすぐ分かる。これは「従うべき最低限」だ。さらに進める例もある。
ファイル名役割（さらに進めた例）
dependencies.tfデータソースを全部ここに集め、外部依存を分かりやすくする。
providers.tfprovider ブロックを集め、どのプロバイダにどんな認証が要るか一目で分かる。
main-xxx.tfmain.tfが長くなったら論理で分割（main-iam.tf、main-s3.tf等）。main- プレフィックスで関連リソースが固まる。多すぎるなら小さなモジュールに分ける兆候（4章）。

🧰 並べ替えの手順

  • この章のS3金庫コードは global/s3 フォルダへ。出力変数（s3_bucket_arn・dynamodb_table_name）は outputs.tf へ。
  • フォルダ移動のときは隠しフォルダ .terraform も一緒に移す。忘れると再初期化が必要。
  • 2章のWebサーバクラスタは stage/services/webserver-cluster へ（今はステージング用。次章で本番用を足す）。.terraform のコピーを忘れず、入力変数を variables.tf、出力変数を outputs.tf へ。
  • WebサーバクラスタがS3をバックエンドに使うよう更新。global/s3/main.tf の backend 設定をコピペし、key だけ stage/services/webserver-cluster/terraform.tfstate に変える。コードの場所と台帳の場所が一致して関連が分かりやすい。

棟梁

分離

環境間・コンポーネント間がほどよく分離され、壊れても被害が一部にとどまる。

棟梁
棟梁ただし、これらの利点はある意味では欠点でもある。
欠点内容解決策
複数フォルダを扱う1コマンドで全部壊さずに済む反面、1コマンドで全部作ることもできない。各フォルダで apply が要る。10章 Terragruntの run-all で複数フォルダ同時実行。
コピペが増える同じ frontend-app・backend-app が stage と prod 両方に出るなど重複が増える。全コピペは不要。4章でDRYに保つモジュールを学ぶ。
依存関係が難しい同じ設定なら属性参照（例 aws_db_instance.foo.address）で直結できるが、別フォルダだと参照不可。10章 Terragruntの dependency ブロック、または次節の terraform_remote_state。

🤔 なぜ必要か

  • 環境やコンポーネントを物理的に分け、事故の被害範囲を最小化できる。
  • 推奨レイアウトと命名規則に沿って、チームで探しやすいプロジェクトを組める。

📝 この項のまとめ

  • 完全分離＝別フォルダ＋別バックエンド・別認証・別権限。
  • 階層は「環境（stage/prod/mgmt/global）→コンポーネント（vpc/services/data-storage）→ファイル（main.tf/variables.tf/outputs.tf）」。
  • ファイル名は自由だが、一貫した命名でチームが探しやすくなる。
  • 移動時は .terraform も移す。key はコードのフォルダ位置とそろえる。
  • 欠点（フォルダ多数・コピペ・依存参照）はTerragruntやモジュール、terraform_remote_state で補える。
3.5

terraform_remote_stateデータソース

別の現場の台帳を読み取り専用で開いて、値を借りる

🧭 要するに：フォルダを分けても、terraform_remote_state（読み取り専用）で別の現場の台帳から出力値を借りられる。Bashの埋め込みは templatefile 関数で外部ファイルに出して整える。

🏗️ たとえ話

部屋を分けたら、データ倉庫（データベース）の住所をサービス棟（Webサーバ）から直接見られなくなりました。そこでサービス棟は、データ倉庫の台帳を閲覧専用で借りてきます。台帳に書き込みはできないので、データ倉庫を壊す心配はゼロ。倉庫が台帳に書いた「住所」と「受付番号（ポート）」だけを、読み取って使うのです。

ハル
ハルフォルダを分けたら、データベースの住所をWebサーバから参照できなくなりましたよね。どうつなぐ？
棟梁
棟梁そこで terraform_remote_state の出番だ。別のTerraform設定が保存した台帳を読み出すデータソースだよ。
ハル
ハル例で見たいです。
棟梁
棟梁WebサーバクラスタがMySQLと通信するとする。耐久性・可用性の高いDBを自前運用は大変だから Amazon RDS を使う（図3-9）。MySQL・PostgreSQL・SQL Server・Oracle等に対応。
ハル
ハルデータベースとWebサーバは同じフォルダに入れちゃダメ？
棟梁
棟梁避けたい。Webサーバはずっと頻繁にデプロイするから、そのたびにDBを壊すリスクは負いたくない。stage/data-stores/mysql という新フォルダを作り、基本ファイルを置く（図3-10）。

データベースを作る

RDSにMySQLを1台建てる設計図です。ユーザー名・パスワードをどうするかが次のテーマ（読まなくてOK）。

HCL：RDSにMySQLを1台建てる（パスワードは未定）
# RDSにMySQLデータベースを1台建てる設計図
provider "aws" {
  region = "us-east-2"  # ① 建てる地域
}

resource "aws_db_instance" "example" {
  identifier_prefix   = "terraform-up-and-running"  # ② 名前の頭につける文字
  engine              = "mysql"                      # ③ 種類はMySQL
  allocated_storage   = 10                           # ④ ストレージ10GB
  instance_class      = "db.t2.micro"                # ⑤ 小さいサイズ(無料枠内)
  skip_final_snapshot = true                         # ⑥ 削除時の最終バックアップを取らない(学習用)
  db_name             = "example_database"           # ⑦ データベースの名前

  # このユーザ名とパスワードはどう設定すべきか？
  username = "???"  # ⑧ ← ここをどうするかが次のテーマ
  password = "???"  # ⑨ ← 秘密の情報なので素のまま書けない
}

📋 このデータベースの設定

  • エンジンはMySQL。ストレージ10GB。
  • 仮想CPU1つ・メモリ1GBの db.t2.micro（AWS無料枠内）。
  • 学習・テスト用なので最終スナップショットは無効（有効にして final_snapshot_identifier を設定しないと削除が失敗する）。

秘密情報は変数＋環境変数で渡す

ハル
ハルユーザー名とパスワード、どうするんですか？ さっき「台帳に丸見えで書かれる」って…。
棟梁
棟梁その通り、機密情報を素テキストでコードに書いてはいけない（6章で詳しく扱う）。今は簡単な方法。パスワードをTerraformの外（パスワードマネージャ）に保存し、それを環境変数でTerraformに渡す。まず variables.tf に変数を定義する。
HCL：ユーザ名・パスワードを「秘密の入力」として受ける箱
# データベースのユーザ名とパスワードを「秘密の入力」として受け取る箱
variable "db_username" {
  description = "データベースのユーザ名"  # ① 説明
  type        = string                    # ② 文字列
  sensitive   = true                      # ③ 機密。plan/applyでも値を画面に出さない
}

variable "db_password" {
  description = "データベースのパスワード"
  type        = string
  sensitive   = true                      # ④ こちらも機密扱い
}
棟梁
棟梁sensitive = true は「これは機密だ」という印。plan や apply でも値を表示しなくなる。あえてデフォルト値を持たせていない点に注目—機密を素テキストで保存しないためだ。値は環境変数で渡す。では2つの変数を aws_db_instance に渡そう。
HCL：秘密の箱の中身をユーザ名・パスワードに渡す
# さっき用意した秘密の箱の中身を、ユーザ名・パスワードに渡す
resource "aws_db_instance" "example" {
  identifier_prefix   = "terraform-up-and-running"
  engine              = "mysql"
  allocated_storage   = 10
  instance_class      = "db.t2.micro"
  skip_final_snapshot = true
  db_name             = "example_database"

  username = var.db_username  # ① 変数から受け取る(素のパスワードはコードに書かない)
  password = var.db_password  # ②
}

DBの台帳をS3に保存し、住所とポートを出力する

HCL：DBの台帳の保存先 と 出力変数
# データベースの台帳をS3の stage/data-stores/mysql に保存
terraform {
  backend "s3" {
    bucket         = "terraform-up-and-running-state"
    key            = "stage/data-stores/mysql/terraform.tfstate"  # ① コードの場所とそろえた置き場所
    region         = "us-east-2"
    dynamodb_table = "terraform-up-and-running-locks"
    encrypt        = true
  }
}

# データベースの「接続先の住所」と「ポート番号」を外に公開
output "address" {
  value       = aws_db_instance.example.address  # ① 接続先アドレス
  description = "このエンドポイントでデータベースに接続する"
}

output "port" {
  value       = aws_db_instance.example.port  # ② 接続に使うポート番号
  description = "データベースが待ち受けているポート"
}
棟梁
棟梁変数の値は環境変数で渡す。入力変数 foo には TF_VAR_foo という環境変数で渡せる、と覚えているね。
bash：環境変数でユーザ名・パスワードを渡す（Mac/Linux／Windows）
# Linux / Unix / macOS（カッコ内は自分の値に置き換える）
$ export TF_VAR_db_username="(YOUR_DB_USERNAME)"
$ export TF_VAR_db_password="(YOUR_DB_PASSWORD)"

# Windows
$ set TF_VAR_db_username="(YOUR_DB_USERNAME)"
$ set TF_VAR_db_password="(YOUR_DB_PASSWORD)"
bash：apply でデータベースを作る（約10分かかる）
# データベースを作る。終わると住所とポートが表示される
$ terraform apply
(...)
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Outputs:

address = "terraform-up-and-running.cowu6mts6srx.us-east-2.rds.amazonaws.com"
port = 3306

Webサーバ側からDBの台帳を読み出す

棟梁
棟梁この出力はDBの台帳（S3の stage/data-stores/mysql/terraform.tfstate）にも保存される。Webサーバ側コードに terraform_remote_state を足せば、その出力を読み出せる。
HCL：DBの台帳を読み取り専用で開く
# DBの台帳を読み取り専用で開き、出力値を借りてくる
data "terraform_remote_state" "db" {
  backend = "s3"  # ① 読み出す台帳はS3にある

  config = {
    bucket = "(YOUR_BUCKET_NAME)"                       # ② DBが台帳をしまった金庫
    key    = "stage/data-stores/mysql/terraform.tfstate" # ③ その中の台帳の場所
    region = "us-east-2"                                # ④ 金庫の地域
  }
}
ハル
ハルこれってWebサーバ側からDBの台帳を書き換えちゃう危険は？
棟梁
棟梁良い心配だ。だが大丈夫。terraform_remote_state が返すデータは読み取り専用。Webサーバのコードがこの台帳を書き換えることは絶対にない。DBに何の問題も起こさず情報だけ取れる（図3-11: DBが台帳を書き込み、Webサーバが同じ金庫から読み出す）。出力変数は属性参照でこう取り出せる。
HCL：別の現場の台帳から出力値を取り出す型
# 別の現場の台帳から出力値を取り出すときの書き方の型
data.terraform_remote_state.<NAME>.outputs.<ATTRIBUTE>

起動スクリプトに住所・ポートを表示させる

HCL：起動時にDBの住所とポートをHTMLに書き出す（インライン）
# 起動時にデータベースの住所とポートをHTMLに書き出して表示
user_data = <<EOF
#!/bin/bash
echo "Hello, World" >> index.html
echo "${data.terraform_remote_state.db.outputs.address}" >> index.html  # ① 台帳から借りた住所
echo "${data.terraform_remote_state.db.outputs.port}" >> index.html      # ② 台帳から借りたポート
nohup busybox httpd -f -p ${var.server_port} &
EOF
ハル
ハルなんだか中にBashが埋め込まれてて、ごちゃごちゃしてきましたね…。
棟梁
棟梁その通り。コードの中に別のコード（Bash）を埋めると保守が難しい。Bashを外部ファイルに出そう。そのために templatefile というビルトイン関数を使う。

ビルトイン関数を知る（format と terraform console）

HCL／bash：ビルトイン関数の型・format・terraform console

function_name(...)

# formatは指定の書式に値を当てはめて文字列にする関数
format(<FMT>, <ARGS>, ...)

# 対話コンソールでformat関数を試す

ハル
ハルコンソールで色々試して、インフラを壊しちゃう心配は？
棟梁
棟梁ない。terraform console は読み取り専用だから、間違ってインフラや台帳を変える恐れはない。文字列・数・リスト・マップを扱う関数が色々ある。その1つが templatefile だ。

templatefile で Bash を外部ファイルに出す

HCL：templatefile の型
# templatefileはPATHのファイルをテンプレートとして読み込み、VARSの値を埋めて文字列にする
templatefile(<PATH>, <VARS>)
棟梁
棟梁「テンプレートとしてレンダリング」とは、PATH のファイルの中でTerraformの文字列補間が使えるようになり、VARS から値を埋めて中身を組み立てることだ。ユーザーデータを stage/services/webserver-cluster/user-data.sh に出そう。
bash：外部スクリプト user-data.sh
# 起動時にDB情報入りのHTMLを作り、簡易Webサーバを立ち上げるスクリプト
#!/bin/bash

cat > index.html <<EOF
<h1>Hello, World</h1>
<p>DB address: ${db_address}</p>
<p>DB port: ${db_port}</p>
EOF

nohup busybox httpd -f -p ${server_port} &

🔧 元のスクリプトからの変更点

  • 使えるのは templatefile の2番目の引数で渡した変数だけ。だからプレフィックス不要（${var.server_port} ではなく ${server_port}）。
  • ブラウザで見やすいよう一部をHTML（<h1> 等）に変えている。

最後に、起動設定の user_data を templatefile 呼び出しに変え、必要な変数をマップで渡します。

HCL：user_data を templatefile に変える
# 外部スクリプトをテンプレートとして読み込み、サーバ起動時に流し込む
resource "aws_launch_configuration" "example" {
  image_id        = "ami-0fb653ca2d3203ac1"
  instance_type   = "t2.micro"
  security_groups = [aws_security_group.instance.id]

  # ユーザデータをテンプレートとしてレンダリング
  user_data = templatefile("user-data.sh", {
    server_port = var.server_port                              # ① 待ち受けポート
    db_address  = data.terraform_remote_state.db.outputs.address  # ② 台帳から借りた住所
    db_port     = data.terraform_remote_state.db.outputs.port     # ③ 台帳から借りたポート
  })

  # Auto Scaling Groupで起動設定を使うときは必須
  lifecycle {
    create_before_destroy = true  # ④ 新しいものを先に作ってから古いものを消す
  }
}
棟梁
棟梁これでBashをインラインで書くよりずっと綺麗になった。apply でデプロイし、インスタンスがALB（ロードバランサ）に登録されるのを待ってからALBのURLを開くと、DBの住所とポートが表示される（図3-12）。
ハル
ハルできた！ Webサーバがデータベースの住所とポートを、プログラムから取れてますね。
棟梁
棟梁おめでとう。Webフレームワーク（Ruby on Rails等）なら、これを環境変数や設定ファイルに渡して、DBライブラリ（ActiveRecord等）から実際にDBへ接続できる。

🤔 なぜ必要か

  • 環境やコンポーネントを分けたまま、現場同士で安全に情報を受け渡せる。
  • DBの住所など、変わりうる値をコードに直書きせず動的に取得できる。
  • スクリプトを外部化し、コードの中にコードを埋める保守の悪さを避けられる。

📝 この項のまとめ

  • terraform_remote_state は別設定の台帳を読み取り専用で読み出すデータソース。
  • 取り出しは data.terraform_remote_state.<NAME>.outputs.<ATTRIBUTE>。
  • 機密情報（DBのユーザ名・パスワード）は sensitive = true の変数＋環境変数 TF_VAR_xxx で渡す。
  • templatefile(<PATH>, <VARS>) で外部スクリプトに変数を埋め込める。プレフィックス不要の ${名前}。
  • terraform console は読み取り専用で関数を安全に試せる。

第1問ステートファイルの役割

Terraformのステートファイル（台帳）は何のために存在し、なぜ手で編集してはいけないのか、自分の言葉で説明してください。

✅ 解答例を見る
ステートファイルは、設計図に書いたリソースと、実際にクラウドに建ったモノ（そのID）を結びつける対応表です。Terraformはこれを見て実物の現状と設計図を比べ、差分を plan として出します。Terraformが内部で使うプライベートな帳簿なので、手で書き換えると対応が崩れ、必要なら terraform import や terraform state を使います。
📝 採点ポイント
・「設計図のリソース」と「実物（ID）」の対応表だと説明できている
・差分（plan）の判断に使うと触れている
・手編集はせず専用コマンドを使う、と述べている
第2問S3とDynamoDBの役割分担

ステートをS3に保存するとき、DynamoDBは何のために一緒に使うのですか。S3とDynamoDBそれぞれの役目を説明してください。

✅ 解答例を見る
S3は台帳そのものを共有保管する金庫の役目で、暗号化やバージョニングもしてくれます。DynamoDBは「今だれかが作業中」を記録する鍵（ロック）の役目です。2人が同時に apply して台帳が壊れるのを防ぎ、作業中なら鍵が空くのを待たせます。
📝 採点ポイント
・S3＝台帳の共有保管（金庫）と説明できている
・DynamoDB＝ロック（鍵）と説明できている
・同時実行による台帳破壊を防ぐ目的に触れている
第3問ワークスペースを本番分離に使わない理由

ステージングと本番を分けるのに、Terraformワークスペースを使うのが適切でないのはなぜですか。

✅ 解答例を見る
全ワークスペースの台帳が同じバックエンド（同じS3バケット）に入り、同じ認証・同じアクセス権を共有するため、環境ごとに権限を分けられません。また、コマンドを打たないと今どの棚にいるか分からず、間違った環境にデプロイしやすい。これらが本番分離に向かない理由です。
📝 採点ポイント
・同じバックエンド・同じ認証/権限を共有する点に触れている
・今いる棚が見えにくくミスを誘う点に触れている
・本番分離にはフォルダレイアウトを使うべきと述べている
第4問backendブロックの制限とその回避

backend ブロックには「変数が使えない」という制限があります。これがなぜ問題で、どう回避できるかを説明してください。

✅ 解答例を見る
変数が使えないため、モジュールごとに金庫名・リージョン・鍵テーブル名を手でコピペする必要があり、さらに key だけは台帳の上書きを防ぐため一意に変えなければならず、ミスが起きやすくなります。回避策は、共通設定をファイルに出して terraform init -backend-config=ファイル で渡す部分設定や、Terragruntの利用です。
📝 採点ポイント
・変数不可ゆえにコピペが増えると説明できている
・key は一意にする必要があると触れている
・部分設定（-backend-config）またはTerragruntを挙げている
第5問terraform_remote_stateの使いどころ

環境やコンポーネントをフォルダで分けると、データベースの住所などを別フォルダのコードから直接参照できなくなります。terraform_remote_state はこれをどう解決しますか。

✅ 解答例を見る
データベース側が出力した値はその台帳に保存されます。Webサーバ側は terraform_remote_state データソースでその台帳を読み取り専用で開き、outputs を通じて住所やポートを借りてこられます。読み取り専用なのでデータベースの台帳を壊す心配はありません。
📝 採点ポイント
・別設定の台帳から出力値を読み出す仕組みだと説明できている
・読み取り専用で安全だと触れている
・outputs を介して値を取得する点に触れている
