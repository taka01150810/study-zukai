3.1

RAGについて

3つの段階と、その実装

要するに：RAGは①インデックス化、②検索、③生成の3段階です。まず①のおさらいから。

リク
リクRAGは3つの段階からなる。①インデックス化（外のデータを前処理して数値の並びをベクトルストアに入れる。2章でやった）、②検索（質問に応じて関係する数値の並びとデータを取り出す）、③生成（元の指示文と取り出したデータを合わせて最終の指示文を作りLLMに送る）。まずインデックス化を、もう一度ゼロから。
コードを見る（1行ずつ説明つき）
# 読み取り役・埋め込みモデル・切り分け役・ベクトルストアの部品を読み込む。
from langchain_community.document_loaders import TextLoader
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_postgres.vectorstores import PGVector

# 資料のファイルを読み込んで、Document の一覧にする。
raw_documents = TextLoader('./test.txt').load()

# 1,000文字ずつ、200文字重ねながらかたまりに切り分ける。
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
documents = text_splitter.split_documents(raw_documents)

# 埋め込みモデルの呼び出し口と、データベースへのつなぎ先を用意する。
model = OpenAIEmbeddings()
connection = 'postgresql+psycopg://langchain:langchain@localhost:6024/langchain'

# かたまりを数値に変えて保存する。ここまでが「インデックス化」で、1回やれば以後使い回せる。
db = PGVector.from_documents(documents, model, connection=connection)

3.1.2 取得した内容で回答を生成する

要するに：取り出したかたまりを指示文の {context} に入れ、質問と一緒にモデルへ渡します。

コードを見る（1行ずつ説明つき）
# チャットモデルと、役割つきの雛形の部品を読み込む。
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# 保存済みのベクトルストアから取り出し係を作る。
retriever = db.as_retriever()

# 指示文の雛形を作る。「渡した材料の中だけを見て答えて」と縛るのが要点。
# この一文がないと、モデルが自分の記憶で勝手に答えてしまうことがある。
prompt = ChatPromptTemplate.from_template("""以下のコンテキストのみに基づいて質問に答えてください:
{context}

質問: {question}
""")

# 答えを作るモデルを用意する。毎回同じ答えになるよう temperature=0 にする。
llm = ChatOpenAI(model_name="gpt-4o-mini", temperature=0)

# 「雛形に入れる → モデルに渡す」を1本につなぐ。
chain = prompt | llm

# まず質問に関係する資料を取り出す。
docs = retriever.invoke("古代ギリシャ哲学史における主要人物は誰ですか？")

# 取り出した資料を材料に、同じ質問への答えを作らせる。
print(chain.invoke({"context": docs, "question": "古代ギリシャ哲学史における主要人物は誰ですか？"}))
# --- 実行結果 ---
# ソクラテス、プラトン、アリストテレスが主要人物として挙げられます。
リク
リクこの取り出し→整形→生成の流れを、1つの関数にまとめると使い回しやすい。
コードを見る（1行ずつ説明つき）
# ふつうの関数に、部品と同じ呼び方を付けるための印を読み込む。
from langchain_core.runnables import chain

# 取り出し係・雛形・モデルを、それぞれ1つずつ用意しておく。
retriever = db.as_retriever()
prompt = ChatPromptTemplate.from_template("""以下のコンテキストのみに基づいて質問に答えてください:
{context}

質問: {question}
""")
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# この印を付けると、関数が invoke などで呼べる部品になる。
@chain
def qa(input):
    # 1) 質問に関係する資料を取り出す。
    docs = retriever.invoke(input)
    # 2) 取り出した資料と質問を雛形に入れて、送る指示文を組み立てる。
    formatted = prompt.invoke({"context": docs, "question": input})
    # 3) 組み立てた指示文をモデルに渡して答えを作らせる。
    answer = llm.invoke(formatted)
    # 4) 答えを返す。使う側は質問1つを渡すだけでよくなる。
    return answer

# 質問を1つ渡すだけで、取り出しから答えの生成までが行われる。
print(qa.invoke("古代ギリシャ哲学史における主要人物は誰ですか？"))
# --- 実行結果 ---
# ソクラテス、プラトン、アリストテレスが主要人物として挙げられます。

3.2.1 Rewrite-Retrieve-Read ― 検索の前に書き直す

要するに：検索する前に、LLMに「検索に向いた言い方」へ書き直させます。とても単純ですが効果があります。

リク
リクMicrosoftの研究チームのRewrite-Retrieve-Readは、検索の前にLLMに質問を書き直させる、すごく単純な手法だ。たとえば、こんな言葉足らずな質問を投げると——「今朝目覚めて歯を磨き、ニュースを読んで、コンロの食べ物を忘れて……古代ギリシャ哲学史の主要人物は誰？」——モデルは要らない情報に気を取られて「コンテキストに情報がありません」と答えてしまう。

3.2.2 マルチクエリ検索 ― 複数の言い方で探す

要するに：1つの質問から複数の言い方を作り、それぞれで検索して、結果を1つにまとめます。

リク
リク1つの言い方だけだと、必要な情報の全体をとらえきれないことがある。マルチクエリ検索は、LLMに元の質問から複数の言い方を作らせて、それぞれを同時に検索して、結果を合わせる。1つの質問が複数の見方に関わるときに効く。
コードを見る（1行ずつ説明つき）
# 役割つきの雛形の部品を読み込む。

# 言い方を変えることで、1つの言い方では届かなかった資料にも当たるようにする。
perspectives_prompt = ChatPromptTemplate.from_template(
    """あなたはAI言語モデルのアシスタントです。与えられたユーザーの質問の5つの
    異なるバージョンを生成し、ベクトルストアから関連ドキュメントを取得してください。
    質問を多面的に生成することで、距離ベースの類似検索の制限を克服する手助けをします。

def parse_queries_output(message):

# 「雛形 → モデル → 行に分ける」を1本につないで、質問の言い換えを作る係にする。
query_gen = perspectives_prompt | llm | parse_queries_output

# 「一覧の一覧」（質問ごとの検索結果）を受け取り、重なりを取り除いて1本の一覧にする。
def get_unique_union(document_lists):

    deduped_docs = {
        doc.page_content: doc
        for sublist in document_lists for doc in sublist
    }
    # 辞書に残った中身だけを取り出して、一覧の形に戻す。
    return list(deduped_docs.values())

# batch は一覧を受け取ってまとめて処理するので、5回順番に呼ぶより速い。
retrieval_chain = query_gen | retriever.batch | get_unique_union

# 質問を1つ渡すだけで、5通りで検索した結果がまとめて返る。
docs = retrieval_chain.invoke({"question": "古代ギリシャ哲学史における主要人物は誰ですか？"})

3.2.3 RAG-Fusion ― 順位を統合して並べ直す

要するに：マルチクエリに並べ直しを足したものです。「どの言い方でも上位に来たもの」を最上位に押し上げます。

リク
リクRAG-Fusionはマルチクエリ検索に似ているけど、取り出した資料全部に並べ直しの手順を加える。RRFという計算で、複数の検索結果の順位を合わせて、1つの順位に作り直す。各言い方での順位を合わせると、最も関係の深い資料が上位に上がってくる。点数の尺度が違う結果どうしを合わせるのに向いている。
コードを見る（1行ずつ説明つき）
# 複数の検索結果（一覧の一覧）を受け取り、順位をもとに1本の順位に作り直す。
def reciprocal_rank_fusion(results: list[list], k=60):
    # 資料ごとの合計点を入れる箱と、本文から資料本体を引くための箱を用意する。
    fused_scores = {}
    documents = {}
    # 言い換えごとの検索結果を、1本ずつ順に見ていく。
    for docs in results:
        # その結果の中での順位（0番目、1番目…）と資料を一緒に取り出す。
        for rank, doc in enumerate(docs):
            # 本文を、その資料を見分けるための目印として使う。
            doc_str = doc.page_content
            # 初めて出てきた資料なら、点数を0から始める。
            if doc_str not in fused_scores:
                fused_scores[doc_str] = 0
                documents[doc_str] = doc
            # 順位が上（数字が小さい）ほど大きな点数を足す。
            # どの言い方でも上位に来た資料は、何度も足されて合計が大きくなる。
            fused_scores[doc_str] += 1 / (rank + k)
    # 合計点の高い順に並べ直す。
    reranked_doc_strs = sorted(fused_scores, key=lambda d: fused_scores[d], reverse=True)
    # 並べ直した順に、資料の本体を取り出して返す。
    return [documents[doc_str] for doc_str in reranked_doc_strs]

# 「言い換えを作る → まとめて検索 → 順位を統合して並べ直す」を1本につなぐ。
retrieval_chain = generate_queries | retriever.batch | reciprocal_rank_fusion

🔎 具体例：RRFの点数計算（k＝60のとき）

ある資料Aが、5通りの言い方のうち3通りで1位（順位0）だったとします。点数は 1/(0+60) ＝ 0.0167 が3回足されて0.05。

資料Bは、5通り全部で4位（順位3）でした。点数は 1/(3+60) ＝ 0.0159 が5回足されて0.079。Bのほうが上になります。

つまり「一部で突出」より「どの見方でもそこそこ上位」が評価されます。k を大きくすると順位の差が縮まり、下位の資料の影響が強まります。

リク
リクRAG-Fusionの強みは、利用者の意図を的確にとらえて、複雑な質問を扱いながら探す範囲を広げて、思いがけない資料と出会えるようにすることだ。

3.2.4 HyDE（仮想ドキュメント埋め込み） ― 仮の答えで探す

要するに：質問から「仮の答えの文章」を作り、その文章で検索します。答えの文章のほうが、答えが書いてある資料に近いからです。

リク
リク最後にHyDE。利用者の質問から仮の文章（仮の回答文）を作って、それを数値に変えて近いものを探す手法だ。
ソラ
ソラなんで仮の回答を作るんですか？
リク
リク理由はね——LLMが作った仮の文章のほうが、元の質問よりも「関係する本物の資料」に近い数値を持つんだ。質問より、答えらしい文章のほうが、答えが書いてある資料に似ているからね。

🔎 具体例：質問文と資料の書き方の差

質問：「古代ギリシャ哲学史の主要人物は？」——これは疑問形の短い文です。

資料：「ソクラテスは問答法を用い、その弟子プラトンはイデア論を展開した。さらにアリストテレスは…」——こちらは平叙文の説明です。

疑問形と説明文は書き方が違うため、数値の位置も離れがちです。そこで先に「ソクラテス、プラトン、アリストテレスなどが挙げられる」という仮の答えを作り、その文章で検索します。答えらしい文章どうしなので位置が近く、正しい資料に当たりやすくなります。仮の答えの内容が間違っていても構いません。検索の道しるべとして使うだけだからです。

コードを見る（1行ずつ説明つき）
# 雛形・文字列の取り出し役・チャットモデルの部品を読み込む。
from langchain.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

# 「この質問に答える文章を書いて」と頼む指示文を作る。ここで作るのは仮の答え。
prompt_hyde = ChatPromptTemplate.from_template(
    """質問に答える文章を書いてください。\n 質問: {question} \n 文章:""")

# 「雛形 → モデル → 文字列だけ取り出す」を1本につないで、仮の答えを作る係にする。
generate_doc = prompt_hyde | ChatOpenAI(temperature=0) | StrOutputParser()

# 作った仮の答えを、そのまま取り出し係に渡す。
# 質問文ではなく、この仮の答えの文章が数値に変えられて検索に使われる。
retrieval_chain = generate_doc | retriever

# 質問を1つ渡すと、仮の答えを経由して関係する資料が返る。
docs = retrieval_chain.invoke({"question": "古代ギリシャ哲学史における主要人物は誰ですか？"})

# 返ってきた件数を確認する。
print(len(docs))
# --- 実行結果 ---
# 4
リク
リクあとは取り出した資料を材料として最終の指示文に渡して答えを作る。まとめると、クエリ変換は「利用者の質問を1つ以上の新しい質問に作り替えて、結果を合わせる」こと。代表的なやり方は——関係ない文言を取り除く、過去のやり取りで補う（「LAはどう？」を「LAの天気」に）、関連する質問も出して幅広く集める、複雑な質問を単純な質問に分ける、など。どれを使うかは用途しだいだ。

🟢 この項のまとめ

  • Rewrite-Retrieve-Read：検索前にLLMで質問を明確に書き直す。単純だがLLM呼び出しが2回で待ち時間増。
  • マルチクエリ検索：複数の言い方を作って同時に検索、重なりを除いてまとめる。
  • RAG-Fusion：マルチクエリ＋RRFによる並べ直し。複数の見方で上位のものを浮かび上がらせる。
  • HyDE：質問から仮の答えの文章を作り、その数値で検索（答えの文章のほうが資料に近い）。

要するに：データは1か所とは限りません。質問を、答えを持っていそうな保管場所へ振り分けます。

リク

3.3.1 論理ルーティング ― LLMに選ばせる

要するに：候補の一覧をLLMに見せて、「どれを使うべきか」を決まった形で答えさせます。

リク
リク論理ルーティングは、複数の保管場所の情報をLLMに与えて、どれを使うべきかをLLM自身に判断させる。GPT-4oみたいな決まった形で答えられるモデルで、各質問をどれかの行き先に分類する。形を定義して、決まった形の出力を得るんだ。
コードを見る（1行ずつ説明つき）
# 選択肢を限定する型と、雛形・モデル・スキーマの部品を読み込む。
from typing import Literal
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field

# 返してほしい答えの形を決める。ここでは「行き先の名前」を1つだけ返させる。
class RouteQuery(BaseModel):
    """ユーザーの質問を最も適切なデータソースにルーティングする"""
    # Literal で、この2つの文字列以外は答えられないようにしている。
    datasource: Literal["python_docs", "js_docs"] = Field(
        ...,
        description="ユーザーの質問に対して最も関連性の高いデータソースを選択する"
    )

# 判断に使うモデルを用意する。毎回同じ判断になるよう temperature=0 にする。
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 上で決めた形を守らせる設定に変える。
structured_llm = llm.with_structured_output(RouteQuery)

# 何を基準に選ぶかを、前提の指示として書いておく。
system = """あなたはユーザーの質問を適切なデータソースにルーティングする専門家です。
質問で言及されているプログラミング言語に基づき、関連データソースへルーティングしてください。"""

# 前提の指示と、利用者の質問を並べた雛形を作る。
prompt = ChatPromptTemplate.from_messages([("system", system), ("human", "{question}")])

# 「雛形 → 形を守るモデル」をつないで、振り分け係にする。
router = prompt | structured_llm

# 実際に質問を投げてみる。Pythonの話なので python_docs が選ばれる。
print(router.invoke({"question": "Pythonでチェーンを作るには？"}))
# --- 実行結果 ---
# datasource='python_docs'

def choose_route(result):

3.3.2 セマンティックルーティング ― 意味の近さで選ぶ

要するに：各行き先を表す文章をあらかじめ数値にしておき、質問に最も近いものを選びます。LLMに判断させません。

コードを見る（1行ずつ説明つき）
# 近さを測る計算、文字列の取り出し役、雛形、印、モデルと埋め込みを読み込む。
from langchain.utils.math import cosine_similarity
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import PromptTemplate
from langchain_core.runnables import chain
from langchain_openai import ChatOpenAI, OpenAIEmbeddings

# 物理の質問向けの指示文を用意する。{query} に実際の質問が入る。
physics_template = """あなたは非常に賢い物理学の教授です。物理の質問に対して、簡潔かつ
わかりやすい形で答えるのが得意です。答えがわからない場合は、正直にわからないと認めてください。

質問です:
{query}"""

# 数学の質問向けの指示文も用意する。
math_template = """あなたは優れた数学者です。難しい問題を要素に分解し、それぞれに回答し、
それらを組み合わせてより大きな問いに答えられるので、数学の質問が得意です。

質問です:
{query}"""

# 埋め込みモデルの呼び出し口を作る。
embeddings = OpenAIEmbeddings()

# 2つの指示文を一覧にまとめる。
prompt_templates = [physics_template, math_template]

# 2つの指示文をあらかじめ数値に変えておく。質問が来るたびに変換しなくて済む。
prompt_embeddings = embeddings.embed_documents(prompt_templates)

# 印を付けて、この関数も部品として呼べるようにする。
@chain
def prompt_router(query):
    # 1) 質問を数値に変える。
    query_embedding = embeddings.embed_query(query)
    # 2) 質問の数値と、2つの指示文の数値それぞれとの近さを計算する。
    similarity = cosine_similarity([query_embedding], prompt_embeddings)[0]
    # 3) 最も近かったほうの指示文を選ぶ。argmax は最大値の位置を返す。
    most_similar = prompt_templates[similarity.argmax()]
    # 4) 選んだ指示文を、使える雛形の形にして返す。
    return PromptTemplate.from_template(most_similar)

# 「指示文を選ぶ → モデルに渡す → 文字列だけ取り出す」を1本につなぐ。
semantic_router = prompt_router | ChatOpenAI() | StrOutputParser()

# 物理の質問を投げる。物理向けの指示文のほうが意味が近いので、そちらが選ばれる。
print(semantic_router.invoke("ブラックホールとは何ですか？"))

# ブラックホールは、非常に強い重力によって光さえも脱出できない天体です。…

  • 論理ルーティング：決まった形で答えられるモデルで、スキーマに従い行き先を分類。出力のばらつきに備え小文字化＋部分一致で丈夫に。
  • セマンティックルーティング：各行き先を表す文章を数値にして、質問の数値と最も近いものを選ぶ。
  • 保管場所はベクトルストア・データベース・各種サービスなど多岐にわたる。
3.4

クエリ構築

日本語を、データベースが読める形に変える

要するに：実務のデータの多くは表の形で保管されています。クエリ構築は、日本語の質問をその保管場所の命令文に変換します。

リク
リクRAGは決まった形を持たないデータの検索に有効だけど、実際に運用されているデータの大半は表の形で、データベースに入っている。それに決まった形を持たないデータにも、大事な情報を含む付随情報が付いている。クエリ構築は、日本語の質問を、対象のデータベースが読める命令文に変えることだ。
ソラ
ソラたとえば？
リク
リク「1980年のエイリアンを題材にした映画は？」を考えてみて。これは決まった形を持たない話題（「エイリアン」、意味での検索向き）と、はっきりした条件（公開年 == 1980）の両方を含んでいる。
💭

意味で探す部分

「エイリアンを題材にした」——あらすじの文章を数値にして、近いものを探します。

🔢

条件で絞る部分

「1980年の」——公開年がちょうど1980のものだけに絞ります。数値の近さでは正確に扱えません。

3.4.1 テキストからメタデータへのフィルタリング

要するに：SelfQueryRetriever が、日本語の質問を「絞り込み条件」と「意味で探す言葉」の2つに自動で切り分けてくれます。

リク
リク多くのベクトルストアは、付随情報で検索を絞り込める。LangChainの SelfQueryRetriever は、日本語の質問を条件付きの検索に変える作業をまとめてくれる。LLMで、質問とあらかじめ決めておいた項目の一覧から、絞り込み条件を取り出して実行するんだ。

from langchain.retrievers.self_query.base import SelfQueryRetriever

# 説明はLLMが読むので、日本語で分かりやすく書いておく。

3.4.2 テキストからSQLへの変換

要するに：日本語の質問をSQLに変換して実行します。ただし安全対策が必須です。

リク
リクSQLと表形式のデータベースは、決まった形のデータの主な保管先だけど、日本語で直接やり取りはできない。LLMで利用者の質問をSQLに変換できる。うまく働かせるには2つ——①データベースの説明（テーブルの定義や実際の数行を指示文に渡す）、②見本の提示（質問とSQLの組を数件示す）。
コードを見る（1行ずつ説明つき）
# SQLを実行する道具、データベースへのつなぎ役、質問をSQLに変える部品を読み込む。
from langchain_community.tools import QuerySQLDatabaseTool
from langchain_community.utilities import SQLDatabase
from langchain.chains import create_sql_query_chain
from langchain_openai import ChatOpenAI

# 対象のデータベースにつなぐ。つないだ時点で、表の構造がLLMに渡せる形で読み取られる。
db = SQLDatabase.from_uri("sqlite:///Chinook.db")

# SQLを書く役のモデルを用意する。毎回同じSQLになるよう temperature=0 にする。
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 「日本語の質問 → SQL」に変換する係を作る。表の構造が自動で指示文に含まれる。
write_query = create_sql_query_chain(llm, db)

# 「SQL → 実行して結果を返す」道具を用意する。
execute_query = QuerySQLDatabaseTool(db=db)

# 2つをつないで、「質問を渡すと結果が返る」1本の流れにする。
chain = write_query | execute_query

# 日本語で質問する。内部では COUNT(*) を使うSQLが作られて実行される。
print(chain.invoke('従業員は何人いますか？'))
# --- 実行結果 ---
# [(8,)]
ソラ
ソラLLMが作ったSQLを本番のデータベースで実行するの、危なくないですか？
リク
リク本当に大事な懸念だ。LLMが作ったSQLを本番のデータベースで制限なく実行するのは危険だ。対策は3つある。これは一例で、LLMアプリの安全性は今も研究が進む分野だよ。
👁️

① 読み取り専用で実行する

データを見ることはできるが、書き換えや削除はできない権限で動かします。

🚧

② テーブルの権限を絞る

その利用者に、対象のテーブル以外へのアクセス権を与えません。

⏱️

③ 時間で打ち切る

アプリ側で上限時間を決め、重い処理が長時間走り続けないようにします。

🟣 なぜ危険なのか

  • LLMの出力はもともとばらつくため、意図しない削除や書き換えのSQLを作る可能性があるから。
  • 全件を突き合わせるような重い処理を作ってしまうと、データベース全体が遅くなり、他の利用者にも影響が出るから。
  • 利用者の入力次第で、見せてはいけないテーブルの中身まで引き出せてしまう可能性があるから。

🟢 この項のまとめ

  • クエリ構築：日本語を、データベースやベクトルストアの命令文（SQL・絞り込み条件）に変える。
  • SelfQueryRetriever：質問を「絞り込み条件」＋「本文を探す言葉」に分ける。項目の一覧を先に決めておく。
  • テキスト→SQL：データベースの説明（テーブル定義・実データの数行）と見本の提示で精度を上げる。
  • 安全策：読み取り専用の利用者・テーブル権限の制限・時間での打ち切り。

第1問RAGの3段階

❓ RAGの3つの段階（インデックス化・検索・生成）を、それぞれ何をするかを含めて説明してください。

✅ 解答例
インデックス化は、外のデータを前処理し、文章を数値の並びに変えてベクトルストアに入れる（2章で扱った準備段階）。検索は、利用者の質問を数値に変え、ベクトルストアから最も近い数値の並びと対応する文章のかたまりを取り出す。生成は、取り出した資料を元の指示文に材料として組み込み、LLMに送って正確で最新の答えを作らせる。手で材料を貼り付けるのではなく、この3段階で自動的に関係する情報を取り出して渡す。
📝 採点ポイント
□ インデックス化＝前処理して数値の並びをベクトルストアに格納、に触れている
□ 検索＝質問を数値に変え関係するかたまりを取得、に触れている
□ 生成＝取得データを材料に組み込んでLLMで回答、に触れている
第2問kは大きい方がいい？

❓ 検索で取り出す件数 k を大きくすればするほど良いわけではないのはなぜですか。

✅ 解答例
取り出す件数が増えるほど、アプリの処理が遅くなり、指示文が大きくなって答えを作る費用も上がる。さらに、関係のない文章を含むかたまりが混ざって、LLMが嘘の回答を作る危険も高まる。だから「常に多く取ればよい」わけではなく、質問に本当に関係する適切な件数に絞る方が、速さ・費用・正確さのつり合いが良い。
📝 採点ポイント
□ 件数が多いと処理が遅く・費用が上がる、に触れている
□ 関係のないかたまりが混ざって嘘の回答を招く、に触れている
□ 適切な件数に絞る方が良い、に触れている
第3問クエリ変換の使い分け

❓ Rewrite-Retrieve-Read・マルチクエリ検索・HyDEの3つを、それぞれどんな手法か説明してください。

✅ 解答例
Rewrite-Retrieve-Readは、検索の前にLLMで利用者の曖昧・言葉足らずな質問を、より良い検索の言い方に書き直してから検索する手法。マルチクエリ検索は、元の質問からLLMに複数の言い方を作らせ、それぞれ同時に検索して結果の重なりを除いてまとめる手法（1つの質問が複数の見方に関わるとき有効）。HyDEは、質問から仮の答えの文章を作り、その数値で近いものを探す手法（質問より答えの文章のほうが、本物の関係する資料に近い数値を持つため）。
📝 採点ポイント
□ Rewrite-Retrieve-Read＝検索前に質問を書き直す、に触れている
□ マルチクエリ＝複数の言い方を作って統合、に触れている
□ HyDE＝仮の答えの文章を作りその数値で検索、に触れている
第4問ルーティングの2種類

❓ 論理ルーティングとセマンティックルーティングの違いを説明してください。

✅ 解答例
論理ルーティングは、複数の保管場所の情報をLLMに与え、決まった形で答えられるモデルで、スキーマに従って「どの保管場所を使うべきか」をLLM自身に分類・判断させる。セマンティックルーティングは、各保管場所を表す複数の文章をあらかじめ数値にしておき、利用者の質問の数値との近さを計算して、最も近い文章（保管場所）を選ぶ。前者はLLMの判断、後者は意味の近さの計算で振り分ける。
📝 採点ポイント
□ 論理ルーティング＝LLMが決まった形で保管場所を分類、に触れている
□ セマンティックルーティング＝文章を数値にして近さで選ぶ、に触れている
□ 両者の判断基準の違い（LLMの判断 vs 意味の近さ）に触れている
第5問テキストからSQLの安全策

❓ LLMが作ったSQLを本番のデータベースで実行する際、なぜ危険で、どんな安全策が必要ですか。

✅ 解答例
LLMの出力はもともとばらつきがあり、想定外の壊すような命令（削除や重い集計など）を作る恐れがあるから、本番のデータベースで制限なく実行するのは危険。安全策は、①読み取り専用の利用者で実行する、②その利用者に対象にしたいテーブル以外へのアクセス権を与えない、③アプリ側で上限時間を決めて重い処理が長時間走らないようにする。これらは一例で、LLMアプリの安全性は今も研究が進む分野なので、推奨される内容は更新され続ける。
📝 採点ポイント
□ LLM出力はばらつき想定外の命令を作りうる、に触れている
□ 読み取り専用・テーブル権限の制限・時間での打ち切り、のうち複数を挙げている
□ 安全性は研究途上で推奨内容が更新される、に触れている（できれば）
