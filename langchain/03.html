RAG 検索拡張生成

答える前に、関係する資料を自動で探してきて、それを見ながらAIに答えさせる仕組み。テスト中にカンニングペーパーを見て答えるイメージ。

文章を作るのが得意なAI（ChatGPTの頭脳）。物知りだけど学習した時点までの情報しか知らない。

最新・正確

📚 たとえ話：物知り司書も「最新の新聞」は別

レファレンス係の司書はとても物知りですが、知識は「研修を受けた時点」まで。最新ニュースを聞かれると、記憶だけだと古い答えをしてしまいます。そこで、カウンターの脇に最新の関連資料をそっと置いてあげると、それを見て正しく答えられます。これがRAG。毎回あなたが資料を手で探して渡すのは大変なので、質問に合わせて資料を自動で出してくる係を作るのがこの章の目標です。

3.1

RAGについて

3フェーズの全体像とインデックス化のおさらい
リク
リクRAGは3つのフェーズからなる。①インデックス化（外部データを前処理して埋め込みをベクトルストアに格納。2章でやった）、②検索（クエリに基づき関連埋め込みとデータを取得）、③生成（元のプロンプトと取得データを統合して最終プロンプトを作りLLMに送る）。まずインデックス化を、もう一度ゼロから。

このコードは何をしている？ → 文書を読み込み、ちょうどよい長さに分割し、意味の座標に変換して書庫（PGVector）に保存します。2章のおさらいです。

Python：インデックス化のおさらい（読み込み→分割→埋め込み→保存）
# このコードがやること（おさらい）: ドキュメントを読み込み→分割→埋め込み→PGVectorに保存する。
from langchain_community.document_loaders import TextLoader
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_postgres.vectorstores import PGVector

raw_documents = TextLoader('./test.txt').load()
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
documents = text_splitter.split_documents(raw_documents)

model = OpenAIEmbeddings()
connection = 'postgresql+psycopg://langchain:langchain@localhost:6024/langchain'
db = PGVector.from_documents(documents, model, connection=connection)

3.1.2　関連ドキュメントを用いてLLM予測を生成する

リク
リク最後の生成フェーズ。取得したドキュメントをコンテキストとして元のプロンプトに追加して、モデルを呼ぶんだ。

このコードは何をしている？ → 取ってきた資料を「参考にしてね」と添えて、AIに質問に答えさせます。

Python：取得した資料をコンテキストに回答を生成する

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

retriever = db.as_retriever()

prompt = ChatPromptTemplate.from_template("""以下のコンテキストのみに基づいて質問に答えてください:
{context}

質問: {question}
""")

llm = ChatOpenAI(model_name="gpt-4o-mini", temperature=0)
chain = prompt | llm

docs = retriever.invoke("古代ギリシャ哲学史における主要人物は誰ですか？")
chain.invoke({"context": docs, "question": "古代ギリシャ哲学史における主要人物は誰ですか？"})
リク
リクこの「取得 → 整形 → 生成」のロジックを、1つの関数にまとめると再利用しやすい。

このコードは何をしている？ → 「質問だけで呼べる」QA係を1つにパッケージ化します。中で取得→整形→生成を順に行います。

Python：取得→整形→生成を1つの関数にまとめる
# このコードがやること: 「質問だけで呼べる」QA関数を作る。中で取得→整形→生成を順に行う。
# @chain デコレーターが、この関数を実行可能なチェーンに変換する。
from langchain_core.runnables import chain

retriever = db.as_retriever()
prompt = ChatPromptTemplate.from_template("""以下のコンテキストのみに基づいて質問に答えてください:
{context}

質問: {question}
""")
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

@chain
def qa(input):
    docs = retriever.invoke(input)                              # 関連ドキュメントを取得
    formatted = prompt.invoke({"context": docs, "question": input})  # プロンプトを整形
    answer = llm.invoke(formatted)                             # 回答を生成
    return answer

qa.invoke("古代ギリシャ哲学史における主要人物は誰ですか？")
リク
リク取得したドキュメントも一緒に返せば（return {"answer": answer, "docs": docs}）、後で根拠を確認できる。複数ステップを1つの関数にカプセル化する——これが実用的なLLMアプリの鍵だ。

📚 たとえ話：「探して・読んで・答える」を1人の係にまとめる

毎回あなたが「本を探す人」「要約する人」「答えを書く人」を別々に呼ぶのは面倒。そこで、相談を受けたら自分で本を探し、整理し、回答まで書いてくれる一人前のレファレンス係を雇い、名前（関数）を付けます。これで「質問するだけ」で済みます。さらに「どの本を見たか（docs）」もメモして返せば、後から根拠を確認できます。

📝 要するに（3.1）

  • RAGは「インデックス化（保存）→検索（as_retrieverで関連チャンク取得、kで件数制御）→生成（コンテキストとして渡して回答）」の3フェーズ。
  • 複数ステップを1つの関数にカプセル化すると再利用しやすい。
  • 基本RAGはできるが、本番にはクエリ変換・ルーティング・クエリ構築が要る。

📌 この項のまとめ

  • RAGは外部コンテキストをLLMに与えて精度を高める。LLM単体は最新情報を知らずハルシネーションしうる。
  • 3フェーズ：インデックス化・検索・生成。手作業のコピペでなく自動で関連情報を取得して渡す。
  • as_retriever で検索を抽象化。k で取得件数を制御（多すぎは遅延・コスト・ハルシネーションの元）。
  • 取得→整形→生成を1関数にカプセル化（@chain）。本番にはクエリ変換・ルーティング・クエリ構築が必要。
3.2

クエリの変換

曖昧な質問を、検索しやすい形に作り変える
リク
リク基本RAGの大きな課題は、出力がユーザーのクエリ品質に依存しすぎること。本番ではクエリは不完全・曖昧・言葉足らずになりがちで、ハルシネーションを招く。クエリ変換は、ユーザー入力を加工してこれに対処する戦略群だ。

3.2.1　Rewrite-Retrieve-Read

リク
リクMicrosoftの研究チームのRewrite-Retrieve-Readは、検索の前にLLMにクエリを書き換えさせる、すごくシンプルな手法だ。たとえば、こんな言葉足らずなクエリ——「今朝目覚めて歯を磨き、ニュースを読んで、コンロの食べ物を忘れて……古代ギリシャ哲学史の主要人物は誰？」——を投げると、モデルは不要な情報に気を取られて「コンテキストに情報がありません」と答えてしまう。
ソラ
ソラ余計な話が多すぎますね。
R

Rewrite（書き換え）

LLMが余計な話を削り「古代ギリシャ哲学の主要人物」へ整える。

R

Retrieve（検索）

書き換えた良いクエリで書庫を検索する。

R

Read（生成）

取得した資料を読んで、元の質問に答える。

このコードは何をしている？ → 検索の前にLLMで「より良い検索クエリ」に書き換えてから検索します。

Python：クエリを書き換えてから検索する
# このコードがやること: 検索の前に、LLMで「より良い検索クエリ」に書き換えてから検索する。
rewrite_prompt = ChatPromptTemplate.from_template(
    """Webの検索エンジンでより良い回答を得るための検索クエリを生成し、
    クエリ末尾に '**' を付けてください。質問: {x} 回答:""")

def parse_rewriter_output(message):
    return message.content.strip('"').strip("**")

rewriter = rewrite_prompt | llm | parse_rewriter_output

3.2.2　マルチクエリ検索

リク
リク単一のクエリだけだと、必要な情報の全貌を捉えきれないことがある。マルチクエリ検索は、LLMに元のクエリから複数のクエリを生成させて、それぞれを並列に検索して、結果を統合する。1つの質問が複数の視点に依存するときに有効だ。

このコードは何をしている？ → 元の質問から「5つの違う言い方」を作ります。

Python：質問を5つのバージョンに増やす
# このコードがやること: 元の質問から5つの異なるバージョンの質問を生成する。
from langchain.prompts import ChatPromptTemplate

perspectives_prompt = ChatPromptTemplate.from_template(
    """あなたはAI言語モデルのアシスタントです。与えられたユーザーの質問の5つの
    異なるバージョンを生成し、ベクトルストアから関連ドキュメントを取得してください。
    質問を多面的に生成することで、距離ベースの類似検索の制限を克服する手助けをします。
    これらの代替質問は改行で区切ってください。元の質問: {question}""")

def parse_queries_output(message):
    return message.content.split('\n')

query_gen = perspectives_prompt | llm | parse_queries_output
リク
リク次に、生成された各クエリで並列に取得して、重複を排除する。

このコードは何をしている？ → 各質問の検索結果をまとめて、同じ本文のものは1つに統合します。

Python：結果をまとめて重複を取り除く
# このコードがやること: 各クエリで取得した結果（2重リスト）をフラット化し、本文をキーに重複排除する。
def get_unique_union(document_lists):
    deduped_docs = {
        doc.page_content: doc
        for sublist in document_lists for doc in sublist
    }
    return list(deduped_docs.values())

# query_gen で複数クエリ生成 → retriever.batch で並列取得 → 重複排除
retrieval_chain = query_gen | retriever.batch | get_unique_union
ソラ
ソラ.batch で並列に取得するんですね。同じリトリーバーに似たクエリを投げるから、重複が出ると。
リク
リクそう、だから重複排除する。ここでは辞書のキーにドキュメント本文を使って重複をなくしている。新しいロジックは全部 retrieval_chain にカプセル化されている。QAチェーン本体は以前とほぼ同じだ。各テクニックを独立したチェーンとして実装するのが、再利用や組み合わせの鍵なんだ。

📚 たとえ話：1人の相談を、3人の司書に別の言い方で頼む

「健康にいい食べ物は？」という相談を、「栄養学の本」「運動と食事の本」「病気予防の本」と切り口を変えて複数の司書に同時に頼み、集まった本から重複（同じ本）を除いて1つの山にします。1つの聞き方では見つからなかった良書も拾えます。

3.2.3　RAG-Fusion

リク
リクRAG-Fusionはマルチクエリ検索に似ているけど、取得したドキュメント全部に再ランク付けステップを加える。RRF（Reciprocal Rank Fusion）アルゴリズムを使って、複数の検索結果のランクを統合して、1つのランキングに再構成する。各クエリでの順位を結合すると、最も関連性の高いドキュメントが上位に上がってくる。スコアのスケールが違うクエリ結果を組み合わせるのに向いている。

このコードは何をしている？ → 複数の検索結果を「RRF」という方式で1つの順位に統合し、本当に役立つ順に並べ直します（複数のリストで上位にいる本ほど高得点）。

Python：RRFで複数の検索結果を統合・再ランク付け
# このコードがやること: 複数の検索結果（リストのリスト）を RRF で統合・再ランク付けする。
# RRFの式 1/(rank + k) で、各ドキュメントが複数リストで上位にあるほど高スコアになる。
def reciprocal_rank_fusion(results: list[list], k=60):
    fused_scores = {}
    documents = {}
    for docs in results:                       # 各クエリの結果リストを走査
        for rank, doc in enumerate(docs):      # その中の順位を取得
            doc_str = doc.page_content         # 本文をキーに一意化
            if doc_str not in fused_scores:
                fused_scores[doc_str] = 0
                documents[doc_str] = doc
            fused_scores[doc_str] += 1 / (rank + k)  # RRFの式でスコアを加算
    # スコアの降順でソートして再ランク付け済みリストを返す
    reranked_doc_strs = sorted(fused_scores, key=lambda d: fused_scores[d], reverse=True)
    return [documents[doc_str] for doc_str in reranked_doc_strs]

retrieval_chain = generate_queries | retriever.batch | reciprocal_rank_fusion
リク
リクk は、順位の低いドキュメントが最終リストに与える影響度を調整する。大きいほど下位の影響が大きくなる。RAG-Fusionの強みは、ユーザーの意図を的確に捉えて、複雑なクエリを扱いつつ取得範囲を広げて、思いがけないドキュメントとの出会い（セレンディピティ）を可能にすることだ。

📚 たとえ話：複数の司書の「おすすめ順」を合算して総合ランキング

マルチクエリで複数の司書が本を選びますが、それぞれ自分なりの「おすすめ順」を付けています。RAG-Fusionは、各司書のおすすめ順を点数化して合算し、みんなが上位に挙げた本ほど高得点とする総合ランキングを作ります。1人だけが推した珍しい良書（思いがけない出会い）も、上位に食い込むチャンスがあります。

このコードは何をしている？ → 質問に答える「仮の文章」を先に作り、その文章で検索します。

Python：仮の回答文（HyDE）で検索する

from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

# 仮想ドキュメントをリトリーバーに渡す（その埋め込みで類似検索する）

リク
リクあとは取得したドキュメントをコンテキストに最終プロンプトへ渡して回答を生成する。まとめると、クエリ変換は「ユーザーのクエリを1つ以上の新しいクエリに書き換えて、結果を統合する」こと。代表的な変換は——無関係な文言を取り除く、過去の会話履歴で補強する（「LAはどう？」を「LAの天気」に）、関連クエリも発行して幅広く集める、複雑な質問を単純な質問に分解する、など。どれを使うかはユースケース次第だ。

📚 たとえ話：「こんな答えの本のはず」と当たりを付けて棚を探す

「ブラックホールって何？」という質問文を持って棚を歩いても、棚に並ぶのは“質問”ではなく“解説文”なので、ピンとくる本が見つかりにくい。そこで司書はまず「ブラックホールとは重力が極端に強い天体で…」という仮の解説文を頭の中で書いてから、それに似た本を探します。質問より“答えっぽい文”の方が、答えが載った本に似ているのです。

📝 要するに（3.2）

  • クエリ変換は、曖昧・不完全なユーザークエリを検索に適した形に加工する。
  • Rewrite-Retrieve-Read（書き換え）、マルチクエリ（多面的に複数生成して統合）、RAG-Fusion（RRFで再ランク付け）、HyDE（仮の回答文を作って検索）がある。
  • 各テクニックは独立したチェーンとして実装すると再利用しやすい。

📌 この項のまとめ

  • Rewrite-Retrieve-Read：検索前にLLMでクエリを明確に書き換える。シンプルだがLLM呼び出しが2回でレイテンシー増。
  • マルチクエリ検索：複数バージョンの質問を生成し並列検索、重複排除して統合。
  • RAG-Fusion：マルチクエリ＋RRFによる再ランク付け。複数視点の上位を浮かび上がらせる。
  • HyDE：質問から仮の回答文を生成し、その埋め込みで検索（回答文の方がドキュメントに近い）。

クエリルーティング

質問を「どの書庫・どの担当」に送るか決める
リク
リク必要なデータは1つのベクトルストアだけじゃなく、リレーショナルDBや別のベクトルストアに散在することがある。たとえばLangChainのPythonドキュメント用とJavaScriptドキュメント用に2つのベクトルストアがあるとき、質問を解決できそうなデータソースへルーティング（転送）する必要がある。

📚 たとえ話：館内の「総合受付」が専門コーナーへ案内する

大きな図書館には、文学コーナー・科学コーナー・郷土資料室など複数の専門部署があります。来館者全員をまず総合受付が出迎え、「そのご相談は科学コーナーですね」と適切な部署へ案内します。これがルーティング。案内のしかたには2通り（論理／セマンティック）あります。

3.3.1　論理ルーティング

リク
リク論理ルーティングは、複数のデータソースの情報をLLMに与えて、どれを使うべきかをLLM自身に推論させる。GPT-4oみたいな関数呼び出し対応モデルで、各クエリをルートのどれかに分類する。スキーマを定義して、構造化された出力を得るんだ。

このコードは何をしている？ → 質問を「python_docs か js_docs のどちらに送るか」を、決まった形（RouteQuery）で判定する案内係を作ります。

Python：構造化出力でデータソースを判定するルーター
# このコードがやること: 「質問を python_docs か js_docs のどちらにルーティングするか」を
# 構造化出力（RouteQuery）で判定するルーターを作る。
from typing import Literal
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field

# データモデル（どのデータソースを選ぶか）
class RouteQuery(BaseModel):
    """ユーザーの質問を最も適切なデータソースにルーティングする"""
    datasource: Literal["python_docs", "js_docs"] = Field(
        ...,
        description="ユーザーの質問に対して最も関連性の高いデータソースを選択する"
    )

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_llm = llm.with_structured_output(RouteQuery)

system = """あなたはユーザーの質問を適切なデータソースにルーティングする専門家です。
質問で言及されているプログラミング言語に基づき、関連データソースへルーティングしてください。"""
prompt = ChatPromptTemplate.from_messages([("system", system), ("human", "{question}")])

router = prompt | structured_llm
リク
リク判定したデータソースを別の関数に渡して、追加ロジックを実行できる。

このコードは何をしている？ → 案内係の判定結果に応じて、対応するチェーンを選びます。

Python：判定結果に応じて対応するチェーンを選ぶ
# このコードがやること: ルーターの判定結果に応じて、対応するチェーンを選ぶ。
def choose_route(result):
    if "python_docs" in result.datasource.lower():
        return "chain for python_docs"
    else:
        return "chain for js_docs"

full_chain = router | RunnableLambda(choose_route)
ソラ
ソラresult.datasource をそのまま比較せず、小文字化して部分マッチしてますね。
リク
リク鋭い。LLMの出力は本質的にランダムだから、スキーマ通りの文字列を返さないこともある。小文字化＋部分マッチで、チェーンの堅牢性を保っているんだ。LLM出力のランダム性への耐性は、常に意識すべき重要なテーマだ。論理ルーティングは、参照すべきデータソースが明確に列挙できるケース（ベクトルストア・RDB・各種API）で真価を発揮する。

📚 たとえ話：受付が「どの部署か」を判断して送る

総合受付の係員が、相談内容を聞いて頭で考え「これは郷土資料室ですね」と判断して案内します。ただし係員も人間、たまに言い間違える（LLMのランダム性）ので、聞き手は「ゴウドシリョウシツでも郷土資料室でも同じ部署」と受け止める柔軟さ（小文字化＋部分マッチ）を持って取りこぼしを防ぎます。

3.3.2　セマンティックルーティング

リク
リクセマンティックルーティングは、論理ルーティングと違って、各データソースを表す複数のプロンプトをユーザーのクエリと一緒に埋め込んで、ベクトル類似度検索で最も近いプロンプトを選ぶ。

このコードは何をしている？ → 物理用と数学用の2つの「先生プロンプト」を先に埋め込んでおき、質問の意味に最も近い方を選んで答えさせます。

Python：意味の近さでプロンプト（先生）を選ぶ
# このコードがやること: 物理用と数学用の2つのプロンプトを埋め込んでおき、
# 質問の埋め込みと最も近い方のプロンプトを選んで回答する。
from langchain.utils.math import cosine_similarity
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import PromptTemplate
from langchain_core.runnables import chain
from langchain_openai import ChatOpenAI, OpenAIEmbeddings

physics_template = """あなたは非常に賢い物理学の教授です。物理の質問に対して、簡潔かつ
わかりやすい形で答えるのが得意です。答えがわからない場合は、正直にわからないと認めてください。

質問です:
{query}"""

math_template = """あなたは優れた数学者です。難しい問題を要素に分解し、それぞれに回答し、
それらを組み合わせてより大きな問いに答えられるので、数学の質問が得意です。

質問です:
{query}"""

# 2つのプロンプトを埋め込む
embeddings = OpenAIEmbeddings()
prompt_templates = [physics_template, math_template]
prompt_embeddings = embeddings.embed_documents(prompt_templates)

@chain
def prompt_router(query):
    query_embedding = embeddings.embed_query(query)              # 質問を埋め込む
    similarity = cosine_similarity([query_embedding], prompt_embeddings)[0]  # 類似度
    most_similar = prompt_templates[similarity.argmax()]        # 最も近いプロンプトを選ぶ
    return PromptTemplate.from_template(most_similar)

semantic_router = prompt_router | ChatOpenAI() | StrOutputParser()

print(semantic_router.invoke("ブラックホールとは何ですか？"))  # → 物理プロンプトが選ばれる
ソラ
ソラ「ブラックホールとは？」だと、物理の教授プロンプトが選ばれるんですね。

  • クエリルーティングは、質問を適切なデータソースへ振り分ける。
  • 論理ルーティング（LLMが構造化出力でデータソースを選ぶ）と、セマンティックルーティング（データソースを表すプロンプトを埋め込み、質問と最も近いものを選ぶ）がある。

📌 この項のまとめ

  • 論理ルーティング：関数呼び出し対応モデルで、構造化出力（スキーマ）に従いデータソースを分類。出力のランダム性に備え小文字化＋部分マッチで堅牢に。
  • セマンティックルーティング：各データソースを表すプロンプトを埋め込み、質問の埋め込みと最も近いものを選ぶ。
  • データソースはベクトルストア・RDB・各種APIなど多岐にわたる。

リク
リクRAGは非構造化データのベクトル検索に有効だけど、実運用のデータの大半は構造化されていて、RDBに入っている。それに非構造化データにも、重要な情報を含む構造化メタデータが付いている。クエリ構築は、自然言語のクエリを、対象のデータベースやデータソースのクエリ言語に変換することだ。
ソラ
ソラたとえば？

📖

非構造化トピック

3.4.1　テキストからメタデータへのフィルタリング

リク
リク多くのベクトルストアは、メタデータでベクトル検索を絞り込める。LangChainの SelfQueryRetriever は、自然言語クエリを構造化クエリに変換するのを抽象化してくれる。LLMで、質問とあらかじめ定義したメタデータスキーマから、メタデータフィルターを抽出して実行するんだ。

このコードは何をしている？ → 映画のメタデータ（ジャンル・公開年・監督・評価）を定義し、「評価8.5以上のSF映画は？」のような質問から、自動でフィルター付き検索をします。

Python：SelfQueryRetrieverで自動フィルター検索
# このコードがやること: 映画のメタデータ（ジャンル・公開年・監督・評価）を定義し、
# 「評価8.5以上のSF映画は？」のような質問から、自動でフィルター付き検索をする。
from langchain.chains.query_constructor.base import AttributeInfo
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain_openai import ChatOpenAI

# 検索条件にできる属性を定義（name は構造なので英語、description は説明）
fields = [
    AttributeInfo(name="genre", description="映画のジャンル", type="string or list[string]"),
    AttributeInfo(name="year", description="映画の公開年", type="integer"),
    AttributeInfo(name="director", description="映画の監督", type="string"),
    AttributeInfo(name="rating", description="映画の1〜10の評価", type="float"),
]
description = "映画の簡単な要約"

llm = ChatOpenAI(temperature=0)

print(retriever.invoke("評価が高い（8.5以上）のSF映画は何ですか？"))

リクこれでリトリーバーは、クエリを2つに分割する——①各ドキュメントのメタデータに適用するフィルター（rating > 8.5、genre = SF）、②本文へのセマンティック検索クエリ。手順は、プロンプトをLLMに送る → フィルターと検索クエリを抽出 → フィルターをベクトルストアの形式に変換 → フィルター適用して類似検索、だ。

3.4.2　テキストからSQLへの変換

リク
リクSQLとRDBは構造化データの主要なストレージだけど、自然言語で直接やり取りできない。LLMでユーザーの質問をSQLに変換できる。効果的にするには——①データベースの説明（CREATE TABLE 定義やサンプル行をプロンプトに渡す）、②Few-shotの例（質問とSQLの組を数件示す）。

このコードは何をしている？ → ユーザーの質問をSQLに翻訳し（write_query）、それを台帳に対して実行します（execute_query）。

Python：質問をSQLに変換して実行する
# このコードがやること: ユーザーの質問をSQLに変換し（write_query）、それを実行する（execute_query）。
from langchain_community.tools import QuerySQLDatabaseTool
from langchain_community.utilities import SQLDatabase
from langchain.chains import create_sql_query_chain
from langchain_openai import ChatOpenAI

db = SQLDatabase.from_uri("sqlite:///Chinook.db")  # データベースの接続情報
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

write_query = create_sql_query_chain(llm, db)   # 質問 → SQL
execute_query = QuerySQLDatabaseTool(db=db)     # SQL を実行
chain = write_query | execute_query

chain.invoke('従業員は何人いますか？')
ソラ
ソラLLMが作ったSQLを本番DBで実行するの、危なくないですか？
リク
リク本当に大事な懸念だ。LLMが生成したSQLを本番DBで無制限に実行するのは危険だ。対策は——①読み取り専用ユーザーで実行する、②そのユーザーに対象テーブル以外のアクセス権を与えない、③アプリ側でタイムアウトを設定して高負荷クエリが長時間走らないようにする。これは一例で、LLMアプリの安全性は今も研究が進む分野だ。
👀

🔒

対象テーブル以外には触れないよう権限を制限。

⏱️

重いクエリが長時間走らないよう時間制限を設ける。

第1問RAGの3フェーズ

✅ 解答例

第2問kは大きい方がいい？

検索で取得するドキュメント数 k を大きくすればするほど良いわけではないのはなぜですか。

✅ 解答例
取得数が増えるほど、アプリの処理が遅くなり、プロンプトが大きくなって回答の生成コストも上がる。さらに、無関係なテキストを含むチャンクが混入して、LLMがハルシネーションを起こすリスクも高まる。だから「常に多く取ればよい」わけではなく、質問に本当に関連する適切な件数に絞る方が、速度・コスト・精度のバランスが良い。
📝 採点ポイント
□ 取得数が多いと処理が遅く・コストが上がる、に触れている ／ □ 無関係なチャンクが混入してハルシネーションを招く、に触れている ／ □ 適切な件数に絞る方が良い、に触れている
第3問クエリ変換の使い分け

Rewrite-Retrieve-Read・マルチクエリ検索・HyDEの3つのクエリ変換を、それぞれどんな手法か説明してください。

✅ 解答例
Rewrite-Retrieve-Readは、検索の前にLLMでユーザーの曖昧・言葉足らずなクエリを、より良い検索クエリに書き換えてから検索する手法。マルチクエリ検索は、元の質問からLLMに複数のバージョンの質問を生成させ、それぞれ並列に検索して結果を重複排除して統合する手法（1つの質問が複数視点に依存するとき有効）。HyDEは、質問から仮の回答文（仮想ドキュメント）を生成し、その埋め込みで類似検索する手法（質問より回答文の方が、本物の関連ドキュメントに近いベクトルを持つため）。
📝 採点ポイント
□ Rewrite-Retrieve-Read＝検索前にクエリを書き換える、に触れている ／ □ マルチクエリ＝複数バージョンを生成し統合、に触れている ／ □ HyDE＝仮の回答文を生成しその埋め込みで検索、に触れている
第4問ルーティングの2種類

論理ルーティングとセマンティックルーティングの違いを説明してください。

✅ 解答例
論理ルーティングは、複数のデータソースの情報をLLMに与え、関数呼び出し対応モデルで、構造化出力（スキーマ）に従って「どのデータソースを使うべきか」をLLM自身に分類・推論させる。セマンティックルーティングは、各データソースを表す複数のプロンプトをあらかじめ埋め込んでおき、ユーザーのクエリの埋め込みとベクトル類似度を計算して、最も近いプロンプト（データソース）を選ぶ。前者はLLMの判断、後者は意味の近さ（埋め込み）で振り分ける。
📝 採点ポイント
□ 論理ルーティング＝LLMが構造化出力でデータソースを分類、に触れている ／ □ セマンティックルーティング＝プロンプトを埋め込み類似度で選ぶ、に触れている ／ □ 両者の判断基準の違い（LLMの推論 vs 意味の近さ）に触れている
第5問テキストからSQLの安全策

✅ 解答例

□ LLM出力はランダムで想定外のクエリを生成しうる、に触れている ／ □ 読み取り専用ユーザー・テーブル権限の制限・タイムアウト、のうち複数を挙げている ／ □ 安全性は研究途上で推奨事項が更新される、に触れている（できれば）
