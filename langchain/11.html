11. LLM を使って構築する
― ユーザーに届ける3つの形 ―

LLM は「ちょっとずれた入力」を受け取れる柔軟な相手。でもその代わり「ちょっとずれた結果」も返す。だから、これまでのアプリの作り方では足りない場面が出てきます。この章では、LLM をユーザーの手に届ける3つの UX パターン（チャットボット／共同編集／アンビエント）を、やさしく図解します。

LLM 大規模言語モデル

大量の文章を学んだ「言葉のプロ」。あいまいな質問にも答えてくれるが、毎回ぴったり同じとは限らない。工房に来た“気のきく新人”。

UX / UI 使い心地・見た目

UXは「使ったときの体験・使い心地」、UIは「画面やボタンなどの見た目・操作部分」。お店でいう“接客と内装の心地よさ”。

インターフェース 接点

人とソフトが触れ合う窓口。ボタン・入力欄・チャット欄など。工房の“受付カウンター”にあたる。

パレット（道具箱）

アプリにあらかじめ用意された道具・部品の一式。工房の壁にかかった“決まった道具一式”。

キャンバス（作業台）

ユーザーが道具を使って作品を組み立てる作業スペース。工房の“作業台”そのもの。

チャットボット

文字で会話して手伝ってくれる相手。工房の“相談カウンターに座る新人”。

チャットモデル

何度も続く会話のために調整された LLM。受け答えが得意な“おしゃべり上手な新人”。

会話履歴

これまでのやり取りの記録。新人が“さっきの話”を覚えているメモ帳。

ストリーミング出力

答えを全部できてから出すのではなく、少しずつ流して見せること。料理を一品ずつ出すイメージ。

レイテンシー 待ち時間

答えが返ってくるまでの待ち時間。少しずつ出せば“待たされ感”が減る。

ツール呼び出し

LLM がアプリの機能（道具）を呼んで使うこと。新人が“工房の道具を自分で取って使う”。

ヒューマンインザループ

AI が勝手に進めず、要所で人に確認させる仕組み。新人が“親方の許可をもらってから手を入れる”。

共同編集

複数人で同じものを一緒に作ること。新人を“もう一人の作り手”として迎える。

共有状態

みんなが同じ“今の作品の状態”を見て編集できること。同じ作業台を全員でのぞける状態。

タスクマネージャー

長くかかる仕事を順番に管理し、失敗しても立て直す係。工房の“工程表・段取り係”。

フォークのマージ

別々に進めた作業を後で1つに合体させること。二手に分かれた作業を“合流”させる。

CRDT / OT

同時編集のぶつかり（競合）を自動でうまく合わせる仕組み。重なった作業を“もめずに自動でならす”技。

並行性

人と AI が同時に動くときの、割り込み・中止・順番待ちへの対応。作業台が混んだときの“さばき方”。

元に戻す/やり直す

前の状態に戻したり、戻したのをもう一度進めたりできること。作りかけを“一手戻す”。

中間出力

完成を待たず、できた途中の分から少しずつ出すこと。一文ずつ書いて渡すイメージ。

アンビエントコンピューティング 環境型

裏でずっと働いて、大事なことが起きたら知らせてくれるソフト。夜も“見回る番人”。

トリガー きっかけ

外から新しい情報を受け取る入口。番人が“異変を感じ取る合図”。

ポーリング

定期的にこちらから見に行って情報を取りに行くこと。番人が“見回りに行く”。

長期記憶

過去に受け取った情報をためておくデータベース。番人の“ぶ厚い日誌”。

リフレクション 内省・学習

過去の出来事から「何が大事か」を学び、見張りのルールを直すこと。番人が“経験から目を肥やす”。

出力の要約

大量の結果から「新しい・大事な分」だけにまとめて見せること。日誌の“要点だけ報告”。

エージェント

目的のために自分で考えて手順を進める AI。指示を待たず動ける“働き手”。

道具箱（パレット）＋作業台（キャンバス）

リク先輩たとえば Figma。Web サイトやアプリのデザインを作るソフトだ。あと Microsoft Word や Google Docs みたいな文書作成ソフトもそう。これらは共通して、2つの部分でできている。

ソラなるほど、「道具箱」と「作業台」みたいな感じですね。

ソラ
ソラ……それって当たり前じゃないんですか？
リク
リク先輩言われてみると奇妙な指摘だよね。でも LLM を中心に据えたソフトでは、必ずしもそうとは限らないんだ。LLM は「事前に決められた要素」じゃなく、その場で新しいコンテンツを生成する。じゃあ、もし LLM ネイティブのワープロを作るとしたら、この「道具箱とキャンバス」の構図はどう変わるのか？——この章では、その問いに対する3つの解決パターンを、既存アプリに足しやすい順に見ていく。

従来型アプリの2つの部分

🧰

① パレット（道具箱）

あらかじめ用意された基本部品。Figma＝線・図形・選択・ペイント。Word＝表・リスト・見出し・画像枠・スペルチェック・コメント。設計時点で全部わかっている。

🗒️

② キャンバス（作業台）

その道具を配置して組み立てる場所。Word なら白紙のページ。ユーザーが自分で組み立てる。

なぜ LLM だと前提が崩れるのか

前

従来型の前提

機能（道具）は設計時に全部わかっている。だから道具箱に並べておける。

毎回同じ命令 → 同じ結果。安心して使える。
L

LLM の振る舞い

事前に決めた部品ではなく、その場で新しいコンテンツを生成する。

何が出るか前もって決め打ちできない＝道具箱に並べきれない。
→

だから新しい UX が要る

「道具箱＋作業台」だけでは足りない。次の3パターンで補う。

要するに：Figma や Word のような従来型アプリは「決められた道具箱（パレット）＋作業台（キャンバス）」でできており、機能が事前に全部分かっている前提に立つ。LLM はその場でコンテンツを生成するため、この前提が崩れ、新しい UX パターンが必要になる。

🟣 なぜこれが必要か / これを知ったらできること

  • 従来型インターフェースの前提を理解すると、なぜ LLM アプリに新しい設計が要るのかが腑に落ちる。
  • 「道具箱とキャンバス」という枠組みを知ると、自分のアプリの構造を分解して考えられるようになる。

🟢 この項のまとめ

  • 従来型アプリ（Figma, Word など）は「パレット（道具箱）＋キャンバス（作業台）」の構成。
  • この構成は「機能が事前に完全に把握されている」という前提に立つ。
  • LLM はその場でコンテンツを生成するため、この前提が崩れ、新しい UX パターンが必要。

🏠 たとえ話：壁にかかった道具一式 vs 自分で道具を生み出す新人

これまでの工房は、壁に決まった道具一式（パレット）がかかっていて、職人はそれを作業台（キャンバス）に持ち出して作りました。道具の数も種類も最初から決まっていたから、段取りも安心。ところが新人（LLM）は、その場で必要な道具や部品を自分で生み出してしまう。壁の道具一式だけを前提にした工房の作り方では、この新人をうまく活かせません。だから「新人の働き場所」を3通り考え直すのです。

11.1

インタラクティブなチャットボット

一番足しやすい：受付カウンターの相談役

対話で学ぶ

ソラ
ソラ最初は一番足しやすいパターンからですよね。何ですか？
リク
リク先輩チャットボットだ。既存のアプリに AI アシスタントとして機能を足して、アイデア出しの相手にする。一番手軽な手段だね。代表例は、VSCode のサイドバーで使える GitHub Copilot Chat だ。
ソラ
ソラあ、コード書いてるときに横で質問できるやつ！
リク
リク先輩そう。これをもう一歩進めると、アシスタントとメインアプリの間に通信ポイントをいくつか足せる。たとえば VSCode では、アシスタントが今編集中のファイルや、ユーザーが選択したコードを「見る」ことができる。逆に、アシスタントがエディタにテキストを挿入・編集することもできる。これでユーザーと LLM の基本的なコラボレーションが成立する。
ソラ
ソラ見るだけじゃなく、書き込みもできるんですね。
リク
リク先輩ちなみに、こういうストリーミングチャット形式は今の LLM アプリの典型例だ。開発者が最初に学ぶのも、企業が既存アプリに最初に組み込むのも、たいていこの形。ただ将来は、これが「LLM 時代のコマンドライン」——つまりプログラミングに最も近い、ちょっとマニアックな存在になる可能性もある、という見方もあるよ。
ソラ
ソラへえ、今の主流が将来はニッチになるかもって、面白い見方ですね。
リク
リク先輩さて、基本的なチャットボットを作るのに必要な部品はこうだ。チャットモデル（複数ターンの会話に向けてダイアログチューニングされたモデル）と、会話履歴（過去のやり取りを覚えていないと、意味のある会話が続かない）。この2つが土台だ。
ソラ
ソラ「helloのその先」に進むには記憶が要る、ってことですね。
リク
リク先輩その通り。さらに、よく足す要素が3つある。ストリーミング出力（トークンや文ごとに少しずつ出して、LLM の待ち時間＝レイテンシーを感じさせない）、ツール呼び出し（「選択中のテキストを取得するツール」「文末にテキストを挿入するツール」などをモデルに公開して、アプリのキャンバスと連携させる）、そしてヒューマンインザループ（アプリに変更を加える前にユーザーに確認させたり、編集を許可したりする制御）だ。
ソラ
ソラ全部、これまでの章で学んだ部品ですね！ストリーミングもツール呼び出しもヒューマンインザループも。
リク
リク先輩そうだろう。これまでの知識が、ここで一つのプロダクトの形に組み上がるんだ。

土台の2部品

🗣️

チャットモデル

複数ターンの会話に向けて調整（ダイアログチューニング）された LLM。受け答えが得意。

📒

会話履歴

過去のやり取りを覚えておく記録。これが無いと意味のある会話が続かない（「helloのその先」へ進めない）。

よく足す3部品

💧

ストリーミング出力

トークンや文ごとに少しずつ出す。待ち時間（レイテンシー）を感じさせない。

🔧

ツール呼び出し

「選択テキストを取得」「文末に挿入」などの道具をモデルに公開し、アプリのキャンバスと連携。

✋

ヒューマンインザループ

アプリに変更を加える前に、ユーザーに確認・編集させる制御。

アプリとの「通信ポイント」（見る／書き込む）

👀

見る

編集中のファイルや、ユーザーが選択したコードをアシスタントが「見る」。

✍️

書き込む

エディタにテキストを挿入・編集する。これで基本的なコラボが成立。

下は、土台の「チャットモデル＋会話履歴」をつないで会話を続けるだけの最小イメージです（開かなくてOK）。

イメージコード：会話履歴を覚えるチャットボットの骨組み（Python） 
# 会話に向けて調整されたチャットモデルを用意する
from langchain.chat_models import init_chat_model
from langchain_core.messages import HumanMessage, AIMessage

model = init_chat_model("gpt-4o")

# 会話履歴：過去のやり取りをリストにためておく（これが「記憶」）
history = [
    HumanMessage("営業メールの件名を考えて"),
    AIMessage("承知しました。商品名を教えてください。"),
    HumanMessage("新作の水筒です"),
]

# 履歴ごと渡すから、文脈をふまえた返事になる（helloのその先へ）
for chunk in model.stream(history):   # stream＝少しずつ流して出す（ストリーミング出力）
    print(chunk.content, end="")

要するに：チャットボットは既存アプリに最も足しやすいパターン。チャットモデルと会話履歴が土台で、ストリーミング出力・ツール呼び出し・ヒューマンインザループを足すと、アプリのキャンバスと連携する本格的な AI アシスタントになる。

🟣 なぜこれが必要か / これを知ったらできること

  • 既存アプリに LLM を組み込む最初の一歩として、最も現実的なパターンだから。
  • 必要な部品を知ると、Copilot のようなアシスタントを自分のアプリに設計できるようになる。

🟢 この項のまとめ

  • チャットボットは既存アプリに最も足しやすい LLM パターン（例: GitHub Copilot Chat）。
  • 土台の部品: チャットモデル＋会話履歴。
  • 追加でよく使う部品: ストリーミング出力、ツール呼び出し、ヒューマンインザループ。
  • アプリとの通信ポイント（見る/書き込む）を足すと、本格的なコラボが成立する。

🏠 たとえ話：受付カウンターに座る相談役の新人

まずは新人を受付カウンターに座らせます。お客さんは横の窓口で「こんな感じにしたいんだけど」と相談でき、新人はアイデア出しの相手になります（チャットボット）。ここに通信ポイントを足すと、新人は今お客さんが広げている図面（編集中のファイル・選択箇所）を“見て”、必要なら図面に書き込むこともできます。
土台は、会話上手な新人（チャットモデル）と、さっきの話を覚えるメモ帳（会話履歴）。さらに「一文ずつ口に出す（ストリーミング）」「壁の道具を自分で取って使う（ツール呼び出し）」「手を入れる前に親方の許可をもらう（ヒューマンインザループ）」を足すと、ちゃんとした相談役になります。

🪶

コパイロット型

常時起動して次の文を提案する。横でずっと付き添うイメージ。

🕵️

ドラフター型

非同期に動き、特定トピックを調べて後で組み込めるセクションを持ち帰る。

実現に必要な6つの仕組み

🪟

共有状態

エージェントも今の文書状態を解釈し、互換性のある形で編集できる。人間と対等。

🗂️

タスクマネージャー

複数ステップ・長時間・途中失敗もある処理を、信頼性高くスケジューリング/オーケストレーション。

🔀

フォークのマージ

LLM の出力とユーザーの作業を統合。手動（Git）か自動（CRDT/OT）で競合解決。

⏯️

並行性

割り込み・キャンセル・処理の振り替え・キューイングなど同時処理に対応。

↩️

元に戻す/やり直す

考えを変えて過去の状態に戻せる。LLM アプリも対応が必要。

💧

中間出力

段階的に生成して、できた端から少しずつ受け取る。マージしやすい（1文ずつ書く感覚）。

要するに：共同編集パターンは、LLM エージェントを「文書に貢献するもう一人のユーザー」として扱う。共有状態・タスクマネージャー・フォークのマージ・並行性・元に戻す/やり直す・中間出力といった、人間同士の共同編集に近い仕組みが必要になる。

🟣 なぜこれが必要か / これを知ったらできること

  • 文書作成ソフトのように「一緒に作る」体験に LLM を組み込むには、共同編集の発想が要るから。
  • 必要な仕組みを知ると、Copilot 型・Drafter 型の協働機能を設計できるようになる。

🟢 この項のまとめ

  • 共同編集の3形態: 保存して送信／バージョン管理／リアルタイム共同編集（同時性が高くなる順）。
  • LLM エージェントを「文書に貢献するユーザーの1人」として扱う（コパイロット型・ドラフター型）。
  • 必要な仕組み: 共有状態、タスクマネージャー、フォークのマージ（CRDT/OT）、並行性、元に戻す/やり直す、中間出力。

🏠 たとえ話：同じ作業台に立つ“相棒職人”の新人

今度は新人を、お客さんと同じ作業台に立たせます。新人はもう一人の作り手（共同編集）。ずっと横で次の一手を提案する相棒（コパイロット型）にもなれば、奥の工房でじっくり下調べをして後でパーツを持ち帰る職人（ドラフター型）にもなれます。
うまくやるには、全員が同じ作りかけを見られること（共有状態）、長い工程を段取りし失敗しても立て直す段取り係（タスクマネージャー）、二手に分かれた作業をもめずに合流させる技（フォークのマージ＝CRDT/OT）、作業台が混んでもさばけること（並行性）、一手戻せること（元に戻す/やり直す）、そして一文ずつ手渡す進め方（中間出力）が要ります。

🎯

役に立つ

🪶

実用的

大量の通知ルールを事前に作る手間をかけずに済む。

→ この2つを両立するのが難しい。LLM の推論能力を使うと、より多くの「面白いこと」を検出でき、ルールの手動設定も大幅に減らせる（便利かつ手間いらず）。

コラボレーション vs アンビエント（最大の違い＝同時性）

🤝

コラボレーション

ユーザーと LLM が同時に作業し、互いの結果を活かし合う。

🌙

アンビエント

ユーザーがまったく別のことをしている間に、LLM が裏で延々と処理を続ける。

実現に必要な5つの構成要素

1

トリガー

環境から新しい情報を受け取るか、定期的にポーリング（見に行って取得）。この継続的な情報の流れがアンビエントの出発点。

2

長期記憶

過去に受け取った情報を保持するデータベース。これが無いと「新しく興味深いことが起きたか」を判定できない。

3

リフレクション（学習）

過去の出来事から「何が面白いか」を学習。LLM が長期記憶を更新したり、検出ルールを直したりする内省ステップ。

4

出力の要約

裏のエージェントは情報を生成しすぎがち。結果を要約し「新しい」「注目すべき」分だけを見せる。

5

タスクマネージャー

継続的に裏で動かすための、タスク管理・新規実行のキューイング・エラー処理と復旧。共同編集と共通の部品。

要するに：アンビエントコンピューティングは、ユーザーが別のことをしている間に LLM がバックグラウンドで動き続け、「注目すべきこと」が起きたら知らせるパターン。LLM の推論で「面白いこと」の検出を賢く・手間なくできる。必要な要素はトリガー・長期記憶・リフレクション・出力の要約・タスクマネージャー。

🟣 なぜこれが必要か / これを知ったらできること

  • 「常に見張って、大事なときだけ教えてくれる」体験は強力だが、従来はルール設定が大変だった。LLM がそれを解決できる。
  • 必要な要素を知ると、バックグラウンドで自律的に働くエージェント型サービスを設計できるようになる。

🟢 この項のまとめ

  • アンビエントコンピューティング = 常時バックグラウンドで動き、注目すべきことが起きたら通知する。
  • 普及の壁は「面白い＝注目すべき」の定義。LLM の推論能力がこれを賢く・手間なく実現する。
  • コラボレーションとの違いは同時性（共同作業 vs 裏で継続処理）。
  • 必要な要素: トリガー、長期記憶、リフレクション（学習）、出力の要約、タスクマネージャー。

🏠 たとえ話：閉店後も町を見回る“夜の番人”の新人

難しいのは「何を“気になること”とするか」。役に立つ（知りたい時に知らせる）と実用的（見張りルールを大量に決めずに済む）を両立させるのが壁ですが、目の利く新人（LLM の推論）なら自分で察してくれます。

🔁 共通の合言葉：「近道はない。まず粗削りでも作って、ユーザーの声を聞き、試行錯誤を繰り返す」

🏠 たとえ話：一人の新人を、お店の3つの場所で活かす

同じ新人でも、受付カウンター（相談役）→作業台（相棒職人）→夜の見回り（番人）と、立たせる場所で役割が変わりました。手前ほどお店に置きやすく、奥ほど準備が要ります。そして親方（リク先輩）の最後の言葉——「近道はない。まず粗削りでも一品出して、お客さんの声を聞き、改良を重ねろ」。これが工房を育てる唯一の道です。

第1問なぜ新しい UX が必要か

LLM を組み込んだアプリで、従来型の「道具箱（パレット）＋キャンバス」型インターフェースが不十分になりやすいのはなぜですか。

✅ 解答例
従来型インターフェースは「ソフトの機能が事前に完全に分かっている」という前提に立ち、用意された道具を組み合わせて使う。一方 LLM は、曖昧な入力に寛容な代わりに「少しずれた」結果を返すことがあり、その場で新しいコンテンツを生成する。つまり「毎回同じ命令には同じ結果」という従来の信頼性の前提が崩れる。事前に全機能を決め打ちする従来型では、この性質をうまく扱えないため、新しい UX パターンが必要になる。
📝 採点ポイント
□ 従来型は「機能が事前に分かっている」前提に立つ、に触れている ／ □ LLM は揺れる結果を返す/その場で生成する、に触れている ／ □ 「毎回同じ結果」という信頼性の前提が崩れる、に触れている
第2問チャットボットの構成要素

基本的なチャットボットを作るのに必要な「土台の部品」2つと、よく追加される部品3つを挙げてください。

✅ 解答例
土台の部品は、複数ターンの会話に向けてダイアログチューニングされた「チャットモデル」と、過去のやり取りを覚えておく「会話履歴」の2つ。会話履歴がないと、意味のある対話が続かない。よく追加される部品は、待ち時間を感じさせない「ストリーミング出力」、アプリのキャンバスと連携するための「ツール呼び出し」、アプリへの変更をユーザーに確認・編集させる「ヒューマンインザループ」の3つ。
📝 採点ポイント
□ 土台＝チャットモデルと会話履歴、を挙げている ／ □ 追加部品としてストリーミング出力に触れている ／ □ 追加部品としてツール呼び出しに触れている ／ □ 追加部品としてヒューマンインザループに触れている
第3問共同編集での LLM の扱い

「LLM との共同編集」パターンでは、LLM エージェントをどう位置づけますか。また、必要になる仕組みを2つ以上挙げてください。

✅ 解答例
LLM エージェントを「共有文書に貢献するユーザーの1人」として扱う。常時起動して次の文を提案する「コパイロット」型や、非同期に調べ物をして後で組み込む「ドラフター」型がある。必要な仕組みには、エージェントも文書状態を解釈して編集できる「共有状態」、長時間処理を信頼性高く回す「タスクマネージャー」、LLM の出力をユーザーの作業と統合する「フォークのマージ（CRDT や OT で自動解決）」、割り込みやキャンセルへの「並行性」対応、「元に戻す/やり直す」、段階的に出す「中間出力」などがある。
📝 採点ポイント
□ LLM を「文書に貢献するユーザーの1人」として扱う、に触れている ／ □ 共有状態・タスクマネージャー・フォークのマージなどから2つ以上挙げている ／ □ フォークのマージで CRDT/OT のような自動解決に触れている（あれば加点）
第4問コラボレーションとアンビエントの違い

「共同編集（コラボレーション）」と「アンビエントコンピューティング」の最大の違いは何ですか。

✅ 解答例
最大の違いは「同時性」。コラボレーションは、ユーザーと LLM が（通常またはときどき）同時に作業し、互いの作業結果を活かし合う。一方アンビエントは、ユーザーがまったく別のことをしている間に、LLM がバックグラウンドで継続的に処理を行い、「注目すべきこと」が起きたら知らせる。一緒に作業するか、裏で勝手に働き続けるか、の違いである。
📝 採点ポイント
□ 違いは「同時性」だと明示している ／ □ コラボ＝ユーザーと LLM が同時に作業、に触れている ／ □ アンビエント＝ユーザーが別のことをしている間に裏で処理、に触れている
第5問アンビエントに必要な要素

アンビエントコンピューティングを実現するのに必要な構成要素を3つ以上挙げ、そのうち1つを簡単に説明してください。

✅ 解答例
必要な要素は、トリガー、長期記憶、リフレクション（学習）、出力の要約、タスクマネージャーなど。たとえば「長期記憶」は、過去に受け取った情報を保持するデータベースで、これが無いと「新しく興味深いことが起きたか」を判定できない。また「リフレクション」は、過去の出来事から「何が面白いか」を学習し、検出ルールを更新するステップである。
📝 採点ポイント
□ トリガー/長期記憶/リフレクション/出力の要約/タスクマネージャーから3つ以上挙げている ／ □ そのうち1つの役割を正しく説明している ／ □ 「過去を覚える/学習する」ことが検出に必要、という趣旨に触れている（あれば加点）
