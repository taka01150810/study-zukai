認知アーキテクチャ cognitive architecture

LLMアプリが目的までに踏むステップの「設計図・レシピ」。部品（プロンプト・RAG・メモリ）の組み合わせ方のこと。建設なら「どう組み立てるかの図面」。

自律性 autonomy

LLMがどれだけ自由に決めて動けるか。建設なら「職人にどこまで任せるか」。高いほど便利だが暴走の余地も増える。

信頼性 reliability

出てくる結果をどこまで信用できるか。建設なら「仕上がりが図面どおりと言い切れるか」。

LLM 大規模言語モデル

大量の文章を学んで、言葉を理解・生成するAI。建設現場の「言葉の達人の職人」。

LangGraph

LLMアプリの処理の流れを「グラフ（点と線）」で組み立てる道具。建設の「工程表を線でつなぐツール」。

グラフ／ノード／エッジ graph / node / edge

処理の流れ図。ノード＝作業工程（職人）、エッジ＝次にどこへ進むかをつなぐ矢印。

ステート state

工程の間で受け渡す「現場の作業ノート」。途中の入力・出力・会話履歴をここに書いて次の職人に渡す。

チェーン chain / フローエンジニアリング

決まった順番でLLMを複数回呼ぶ流れ。建設なら「基礎→壁→屋根」と必ず同じ順で進む工程表。

ルーター router

次にどの工程へ進むかをLLMに選ばせる仕組み。建設なら「現場監督が状況を見て次の班を指名」する。

条件付きエッジ add_conditional_edges

判定結果に応じて進む先を切り替える分かれ道の矢印。図では破線。監督の指示で進路が分岐する。

入力／出力スキーマ Input / Output

「受け取る項目」と「最後に返す項目」を分けて決める仕組み。残りは現場内部のメモ（中間ステート）。

RAG 検索拡張生成

答える前に資料を検索して、それを見ながら答える方式。カンニングペーパーを見て答えるイメージ。

Text-to-SQL

「各製品の売上は？」のような普通の言葉を、データベースへの命令文（SQL）に変える機能。

temperature 温度

LLMの返事の「ゆらぎ」設定。低いと堅実で安定、高いと自由で自然な文章になる。

エージェント agent

ルーターよりさらに自律性が高い設計図。次章のテーマ。最も強力な認知アーキテクチャ。

部品が揃った。あとは「組み合わせ方」だ
ソラ
生徒・ソラプロンプト・RAG・メモリ、部品は揃いました。これをどう組み合わせるんですか？
リク
先生・リクレンガとモルタルで、プールも平屋も作れる。違いは「組み合わせ方＝アーキテクチャ」だよ。

この章では、LLMアプリの「設計図（認知アーキテクチャ）」を学びます。鍵となるのは「自律性 vs 信頼性」のトレードオフ。LLMにどこまで決めさせるかで、コード（0）→LLM呼び出し（1）→チェーン（2）→ルーター（3）という段階があります。LangGraphで、LLM呼び出し・チェーン・ルーターの3つを実装しながら理解します。

🏗️ たとえ話：同じレンガで、プールも平屋も

同じレンガとモルタル（＝部品）でも、積み方の設計図が違えば、できあがるのはスイミングプールにも平屋にもなります。LLMアプリも同じ。手元の材料（プロンプト・RAG・メモリ）をどう組み立てるかが、便利な建物になるか危ない建物になるかを決めます。だから「設計図選び」が現場で一番大事な判断なのです。

なぜこれが必要か / これを知るとできること

学ぶ動機

🤔 なぜ学ぶ価値があるのか

  • 同じ部品でも、組み合わせ方（アーキテクチャ）次第で、役立つアプリにも危ないアプリにもなるから。

  • 条件付きエッジ（add_conditional_edges）で、LLMの判断に応じて経路を分岐させられる。

自律性 vs 信頼性のトレードオフ

リク
リクそこに重要なトレードオフが見える。自律性（自由に行動できる程度）と信頼性（出力をどこまで信用できるか）だ。より多く自動化すれば便利だけど、行き過ぎれば「送ってほしくないメール」を送る。自律性を測る指標は、「振る舞いのどれだけをLLMが決めて、どれだけをコードが決めるか」だ。

🏗️ たとえ話：職人にどこまで任せるか

現場には2つの相反する願いがあります。「職人に任せれば任せるほど（自律性）、いちいち施主に確認せず工事が速く進む」。でも「任せすぎると、施主が望まない壁を勝手に建ててしまう（信頼性が落ちる）」。便利さと事故のリスクは、いつも表裏一体なのです。

自律性には3段階あります。LLMにどこまで決めさせるか、で区別します。

📝

① 出力を決めさせる

特定ステップの出力だけをLLMに任せる。例：返信案の下書きを書かせる。

自律性 低
🔀

② 次のステップを選ばせる

用意した選択肢から次に何をするかを選ばせる。例：アーカイブ／返信／マークの3択。

自律性 中
🛠️

③ ステップ自体を決めさせる

取り得るステップそのものを決めさせる。組み込まれていない動的アクションのコードを書かせる。

自律性 高

リク
リクこの役割分担（LLM・開発者・ユーザー）の典型パターンを認知アーキテクチャと呼ぶ。LLMアプリが踏むステップのレシピだ。順番に見よう。本章はこの3つ（1〜3）を実装する。次章でさらに自律的なエージェントを扱うよ。

0コードLLMを使わない普通のソフトふつうのプログラム

5.1

LLM呼び出しアーキテクチャ

LLMを1回だけ呼ぶ、いちばんシンプルな形
リク
リクまずLLM呼び出しアーキテクチャ。4章のチャットボットがこれだ。LLMを1回だけ呼んで、ユーザーのメッセージに直接レスポンスする。
S

START

ユーザーのメッセージを受け取る。

1

chatbot（LLMを1回呼ぶ）

受け取ったメッセージをそのままLLMに渡し、返事を作る。

E

END

返事を返して終わり。

⬇️ このコードは、LLMを1回呼ぶだけの最小のグラフ（START→chatbot→END）です。4章のおさらいなので、開かなくてもOK。

Python ― 最小のLLM呼び出しグラフ
# このコードがやること: LLMを1回呼ぶだけの最小グラフ（START→chatbot→END）。4章のおさらい。
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI

model = ChatOpenAI()

class State(TypedDict):
    messages: Annotated[list, add_messages]

def chatbot(state: State):
    answer = model.invoke(state["messages"])
    return {"messages": [answer]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, 'chatbot')
builder.add_edge('chatbot', END)

graph = builder.compile()
リク
リク最もシンプルだけど、出番は多い。NotionなどのAI機能（要約・翻訳）は単一のLLM呼び出しで実現できるし、想定するUX次第ではシンプルなSQLクエリ生成もこれで十分だ。

🏗️ たとえ話：1人の職人に一仕事だけ頼む

「この壁を1枚だけ塗って」と1人の職人に1回だけ仕事を頼むイメージ。難しい段取りはなく、頼んだら結果が返ってくる。シンプルですが、「要約して」「翻訳して」など、ちょっとした仕事ならこれで十分役に立ちます。

5.2

チェーンアーキテクチャ

決まった順序で、複数回LLMを呼ぶ
リク
リク次にチェーンアーキテクチャ。あらかじめ定義した順序で複数回LLMを呼ぶ。何度起動しても入力や結果は違うけど、呼び出しの順序は常に同一だ。これはフローエンジニアリングとも呼ばれる。
ソラ
ソラたとえば？
リク
リクText-to-SQLアプリだ。①ユーザーの自然言語クエリとDBスキーマからSQLを生成するLLM呼び出し→②生成したSQLを、非技術ユーザーにもわかるように解説するLLM呼び出し。これで、生成クエリがユーザーの意図に合っているか確認できる。
S

START（入力：user_query）

「各製品の売上は？」のような普通の言葉の質問だけを受け取る。

1

generate_sql（SQLを生成）

質問からSQLを作る。安定させたいので temperature 低め。

2

explain_sql（SQLを解説）

作ったSQLを、非エンジニアにも分かるよう自然な文章で説明。temperature 高め。

E

END（出力：sql_query / sql_explanation）

SQLとその解説を返す。順番はいつも固定。

⬇️ このコードは、2段階のチェーンの組み立て図です。必ず START→generate_sql→explain_sql→END の順で実行されます。

Python ― 2段階チェーン（SQL生成→解説）の組み立て
# このコードがやること: 2段階のチェーン。
#  generate_sql = ユーザーの質問からSQLを生成（temperature低めで安定）。
#  explain_sql = そのSQLを平易に解説（temperature高めで自然な文章）。
# START → generate_sql → explain_sql → END と必ず同じ順で実行される。
from typing import Annotated, TypedDict
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

model_low_temp = ChatOpenAI(temperature=0.1)   # SQL生成用（安定）
model_high_temp = ChatOpenAI(temperature=0.7)  # 自然言語の解説用

class State(TypedDict):
    messages: Annotated[list, add_messages]  # 会話履歴
    user_query: str       # 入力
    sql_query: str        # 出力
    sql_explanation: str  # 出力

class Input(TypedDict):
    user_query: str

class Output(TypedDict):
    sql_query: str
    sql_explanation: str

generate_prompt = SystemMessage(
    "あなたはユーザーの質問に基づいてSQLクエリを生成する有能なデータアナリストです。")

def generate_sql(state: State) -> State:
    user_message = HumanMessage(state["user_query"])
    messages = [generate_prompt, *state["messages"], user_message]
    res = model_low_temp.invoke(messages)
    return {"sql_query": res.content, "messages": [user_message, res]}

explain_prompt = SystemMessage(
    "あなたはユーザーにSQLクエリを説明する有能なデータアナリストです。")

def explain_sql(state: State) -> State:
    messages = [explain_prompt, *state["messages"]]  # ユーザークエリと生成SQLを含む
    res = model_high_temp.invoke(messages)
    return {"sql_explanation": res.content, "messages": res}

builder = StateGraph(State, input=Input, output=Output)
builder.add_node("generate_sql", generate_sql)
builder.add_node("explain_sql", explain_sql)
builder.add_edge(START, "generate_sql")
builder.add_edge("generate_sql", "explain_sql")
builder.add_edge("explain_sql", END)

graph = builder.compile()

⬇️ こう呼び出すと「各製品の売上高は？」に対し、SQLとその解説が返ります。

Python ― 実行
# このコードがやること: 「各製品の売上高は？」と尋ねると、SQLとその解説が返る。
graph.invoke({"user_query": "各製品の売上高はいくらですか？"})

⬇️ 返ってくる中身（SQL文と、その日本語の解説）。

出力例 ― SQLと解説
# 出力（SQLと、その解説）{
  "sql_query": "SELECT product_name, SUM(sales_amount) AS total_sales FROM sales GROUP BY product_name;",
  "sql_explanation": "このクエリは、sales_amount 列を製品ごとに合計し、product_name でグループ化して、各製品の売上高を取得します。",
}
リク
リクまず generate_sql が sql_query を設定して messages を更新、続いて explain_sql が生成SQLを使って sql_explanation を設定する。順序は固定だ。注目してほしいのは、StateGraph 作成時に入力スキーマ（Input）と出力スキーマ（Output）を分けて指定できること。どの項目をユーザー入力として受け取って、どれを出力として返すかを制御できる。残りのステート項目はノード内部の中間ステートだ。
📥

入力スキーマ（Input）

外から受け取る項目だけ。ここでは user_query のみ。

📤

出力スキーマ（Output）

最後に返す項目。sql_query と sql_explanation。

messages など残りの項目は、外には返さない「現場内部のメモ（中間ステート）」です。

🏗️ たとえ話：基礎→壁の固定工程表

チェーンは「基礎を打つ班→壁を建てる班」と、いつも同じ順番で進む工程表です。日によって部屋の大きさ（入力）は違っても、工程の順番は変わりません。さらに「施主から受け取る注文書（入力）」と「最後に施主へ渡す完成報告書（出力）」を分けて決められるので、途中の作業メモは現場内に残し、必要な物だけを施主に渡せます。

5.3

ルーターアーキテクチャ

次のステップをLLMに選ばせる
リク
リク最後にルーターアーキテクチャ。次に取るべきステップの決定をLLMに委ねて、自律性をさらに高める。チェーンが静的な手順を常に実行するのに対して、ルーターは定義済みの複数ステップから、どれを実行するかをLLMに選ばせる。
ソラ
ソラたとえば？
リク
リク異なるドメインのドキュメントを複数のインデックスに格納したRAGアプリだ。プロンプトに無関係な情報を含めないとLLMの性能は上がるから、各クエリに正しいインデックスを選んで、そこだけ検索すべきだ。この選択をLLMに任せる。流れは——①ユーザークエリとインデックスの説明から、どのインデックスを使うか選ぶLLM呼び出し→②選んだインデックスを検索→③取得ドキュメントとクエリから回答を生成するLLM呼び出し。
ソラ
ソラ昔はどうやってたんですか？
リク
リクLLM以前は、ML技術で分類モデルを構築して、クエリとインデックスを対応付けたデータセットを手作業で作っていた。すごく手間だった。LLMは人間の言語をエンコードしているから、ほぼゼロショット、あるいは少数の例で、この分類モデルの役割を果たせる。医療記録用と保険FAQ用の2つのインデックスを例に実装しよう。

流れ：質問を見て、進む先を分岐する

S

START（入力：user_query）

「新型コロナの治療は補償されますか？」などの質問を受け取る。

1

router（LLMがドメインを選ぶ）

質問を「医療記録(records)」か「保険FAQ(insurance)」のどちらに送るかをLLMが判定。

🔀 records を選んだら → 医療記録を検索するノードへ
🔀 insurance を選んだら → 保険FAQを検索するノードへ

⬇️ このコードは、質問を「医療記録」か「保険FAQ」に振り分け、選ばれた側だけ検索して回答するルーターの組み立て図です。pick_retriever が分かれ道を担います。

Python ― ルーター（条件付きエッジで分岐）
# このコードがやること: 質問を「医療記録(records)」か「保険FAQ(insurance)」にルーティングし、
# 選ばれた方のインデックスを検索して回答を生成する。
#  router_node = LLMにドメインを選ばせる。
#  pick_retriever = 選ばれたドメインに応じて、次に実行するノードを返す（条件付きエッジ）。
from typing import Annotated, Literal, TypedDict
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_core.vectorstores.in_memory import InMemoryVectorStore
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

embeddings = OpenAIEmbeddings()
model_low_temp = ChatOpenAI(temperature=0.1)
model_high_temp = ChatOpenAI(temperature=0.7)

class State(TypedDict):
    messages: Annotated[list, add_messages]
    user_query: str                              # 入力
    domain: Literal["records", "insurance"]      # 出力（選ばれたドメイン）
    documents: list[Document]
    answer: str

class Input(TypedDict):
    user_query: str

class Output(TypedDict):
    documents: list[Document]
    answer: str

# 2つのインデックス（中身のインデックス化は2章参照）
medical_records_retriever = InMemoryVectorStore.from_documents([], embeddings).as_retriever()
insurance_faqs_retriever = InMemoryVectorStore.from_documents([], embeddings).as_retriever()

router_prompt = SystemMessage(
    """ユーザーの問い合わせをどのドメインへルーティングするか決定してください。
    選べるドメインは2つです:
      - records: 患者の診断、治療、処方などの医療記録を含む。
      - insurance: 保険契約、請求、補償に関するFAQを含む。
    出力はドメイン名のみとしてください。""")

def router_node(state: State) -> State:
    user_message = HumanMessage(state["user_query"])
    messages = [router_prompt, *state["messages"], user_message]
    res = model_low_temp.invoke(messages)
    return {"domain": res.content, "messages": [user_message, res]}

def pick_retriever(state: State) -> Literal["retrieve_medical_records", "retrieve_insurance_faqs"]:
    if state["domain"] == "records":
        return "retrieve_medical_records"
    else:
        return "retrieve_insurance_faqs"

def retrieve_medical_records(state: State) -> State:
    return {"documents": medical_records_retriever.invoke(state["user_query"])}

def retrieve_insurance_faqs(state: State) -> State:
    return {"documents": insurance_faqs_retriever.invoke(state["user_query"])}

medical_records_prompt = SystemMessage(
    "あなたは患者の医療記録（診断・治療・処方など）に基づいて質問に答える有能な医療チャットボットです。")
insurance_faqs_prompt = SystemMessage(
    "あなたは保険契約・請求・補償に関するFAQに回答する有能な医療保険チャットボットです。")

def generate_answer(state: State) -> State:
    prompt = medical_records_prompt if state["domain"] == "records" else insurance_faqs_prompt
    messages = [prompt, *state["messages"], HumanMessage(f"Documents: {state['documents']}")]
    res = model_high_temp.invoke(messages)
    return {"answer": res.content, "messages": res}

builder = StateGraph(State, input=Input, output=Output)
builder.add_node("router", router_node)
builder.add_node("retrieve_medical_records", retrieve_medical_records)
builder.add_node("retrieve_insurance_faqs", retrieve_insurance_faqs)
builder.add_node("generate_answer", generate_answer)
builder.add_edge(START, "router")
builder.add_conditional_edges("router", pick_retriever)   # LLMの判断で経路を分岐
builder.add_edge("retrieve_medical_records", "generate_answer")
builder.add_edge("retrieve_insurance_faqs", "generate_answer")
builder.add_edge("generate_answer", END)

graph = builder.compile()

ソラadd_conditional_edges がポイントですね。

リクそう。グラフには2つの経路（医療記録／保険FAQ）があって、両方とも最初に router を通って、最後に generate_answer で終わる。pick_retriever 関数が、LLMの選んだ domain を2つのノードのどちらかにマッピングする条件付きエッジだ。実行してみよう。

この章を読み終わったあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問認知アーキテクチャとは

認知アーキテクチャとは何ですか。「レンガとモルタル」のたとえを使って説明してください。

✅ 解答例
認知アーキテクチャとは、LLMアプリが目的を達成するために踏むべきステップのレシピ、つまり「部品（プロンプト・RAG・メモリなど）の組み合わせ方＝設計図」のこと。レンガとモルタルという同じ素材でも、組み合わせ方次第でスイミングプールにも平屋にもなるように、LLMアプリも、手元の部品をどう組み合わせるかで用途がまったく変わる。だから、どう組み合わせるかを決めることが最も重要な意思決定になる。
📝 採点ポイント
□ 認知アーキテクチャ＝部品の組み合わせ方（ステップのレシピ）、に触れている ／ □ 同じ素材でも組み合わせ方で用途が変わる、というたとえを使っている ／ □ アーキテクチャ選択が重要な意思決定、に触れている
第2問自律性と信頼性

「自律性」と「信頼性」のトレードオフとは何ですか。メールアシスタントの例で説明してください。

✅ 解答例
自律性は「LLMがどれだけ自由に行動できるか」、信頼性は「その出力をどこまで信用できるか」。両者はトレードオフの関係にある。メールアシスタントの例では、より多くの作業を自動化（自律性を高く）すれば便利になるが、行き過ぎると「自分なら絶対に送らないメール」を勝手に送ってしまう事態が避けられない。自律性を測る指標は「振る舞いのどれだけをLLMが決め、どれだけをコードが決めるか」で、出力だけ／次のステップ／ステップ自体、と段階がある。
📝 採点ポイント
□ 自律性＝自由に行動できる程度、信頼性＝出力を信用できる程度、に触れている ／ □ 自動化を進めると便利だが事故（送ってほしくないメール）のリスク、に触れている ／ □ LLMにどこまで決めさせるかの段階に触れている
第3問チェーンとルーターの違い

チェーンアーキテクチャとルーターアーキテクチャの違いを説明してください。

✅ 解答例
チェーンは、あらかじめ定義された順序で複数回LLMを呼ぶ。入力や結果は毎回違っても、実行されるステップの順序は常に同一（例：Text-to-SQLで、SQL生成→SQL解説の順を必ず実行）。ルーターは、次に取るべきステップの選択をLLMに委ねる。定義済みの複数ステップの中から、どれを実行するかをLLMに選ばせる（例：複数インデックスのRAGで、クエリに応じてどのインデックスを検索するかをLLMが決める）。ルーターの方が自律性が高い。
📝 採点ポイント
□ チェーン＝固定の順序で複数回呼ぶ、に触れている ／ □ ルーター＝次のステップをLLMに選ばせる、に触れている ／ □ ルーターの方が自律性が高い、に触れている
第4問条件付きエッジ

ルーターアーキテクチャで使う「条件付きエッジ（add_conditional_edges）」は、何をするものですか。

✅ 解答例
条件付きエッジは、固定の経路ではなく、関数の判定結果に応じて次に実行するノードを動的に選ぶエッジ。ルーターの例では、router ノードでLLMがドメイン（recordsかinsurance）を選び、pick_retriever 関数がそのドメインに応じて「医療記録を検索するノード」か「保険FAQを検索するノード」のどちらかを返す。これにより、LLMの判断に応じてグラフの経路が分岐する。図では破線で示される。
📝 採点ポイント
□ 関数の判定結果に応じて次のノードを動的に選ぶ、に触れている ／ □ LLMの判断（domain）に応じて経路が分岐する、に触れている ／ □ ルーターアーキテクチャの実装に使われる、に触れている
第5問入力/出力スキーマの分離

StateGraph で入力スキーマと出力スキーマを分けて指定できると、何が嬉しいですか。

✅ 解答例
入力スキーマと出力スキーマを分けると、ステートのうち「どの項目をユーザー入力として受け取り、どの項目を最終出力として返すか」を柔軟に制御できる。例えばText-to-SQLのチェーンでは、入力は user_query だけ、出力は sql_query と sql_explanation、というふうに指定できる。残りのステート項目（messagesなど）はノード内部の中間ステートとして使われ、ユーザーに返す最終出力には含めない。これにより、外部とのインターフェースが明確になる。
📝 採点ポイント
□ どの項目を入力として受け取り、どれを出力として返すかを制御できる、に触れている ／ □ 残りは中間ステートとして使う、に触れている ／ □ 外部インターフェースが明確になる、に触れている（できれば）
