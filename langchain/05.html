🎬

この章のあらすじ

部品ではなく、組み合わせ方の話

「プロンプト・RAG・メモリ、部品は揃いました。これをどう組み合わせるんですか？」とソラ。リク先輩は「同じ部品でも、組み合わせ方を変えれば別のアプリになる。その組み合わせ方がアーキテクチャだよ」と答えます。

この章では、LLMアプリの「設計図（認知アーキテクチャ）」を学びます。鍵になるのは「自律性 と 信頼性」のつり合い。LLMにどこまで決めさせるかで、コード（0）→LLM呼び出し（1）→チェーン（2）→ルーター（3）という段階があります。LangGraphで、後ろの3つを実装しながら理解します。

🎯

要するに

この章を1枠でまとめると

部品（プロンプト・RAG・メモリ）をどう組み合わせるかが「認知アーキテクチャ」です。これは「自律性（LLMにどこまで自由に決めさせるか）」と「信頼性（出力をどこまで信用できるか）」のつり合いで選びます。自律性が上がるほど便利になりますが、行動を制御する仕組みも厳密に必要になります。

🕊️

自律性を上げると

できることが増え、人の手間が減ります。ただし想定外の行動が起きる余地も増えます。

🛡️

信頼性を上げると

結果が読めるようになります。ただし手順を細かく決める必要があり、柔軟さは失われます。

📌

なぜこれが必要か／これを知ると何ができるか

学ぶ理由と、身につくこと

🟣 なぜ学ぶ価値があるのか

  • 同じ部品でも、組み合わせ方しだいで、役に立つアプリにも危ないアプリにもなるから。
  • 「自律性と信頼性」を意識しないと、便利さを追って「送ってほしくないメールを送る」ような事故を起こすから。
  • LLMにどこまで決めさせるか（出力だけ／次の手順／手順そのもの）で、設計の選択肢が変わるから。

🟢 これを知ったらできるようになること

  • 認知アーキテクチャの段階（コード→LLM呼び出し→チェーン→ルーター）を理解し、用途に応じて選べる。
  • LangGraphで、LLM呼び出し・チェーン・ルーターの3つを実装できる。
  • 条件付きエッジ（add_conditional_edges）で、LLMの判断に応じて道筋を分けられる。
  • 入力の形と出力の形を分けて、途中だけで使うデータを管理できる。
📖

導入 ― 自律性と信頼性のつり合い

メールアシスタントで考える
ソラ
ソラ先生、プロンプト・RAG・メモリと部品が揃いました。あとは？
リク
リクいい段階に来たね。同じ部品を使っても、並べ方と役割の分け方を変えれば、まったく別の性質のアプリになる。それを決めるのがアーキテクチャだ。LLMアプリでは、RAG・プロンプト・メモリをどう組み合わせるかが最も重要な判断になる。
ソラ
ソラたとえば、どんなアプリを考えるんですか？
リク
リクメールアシスタントを作るとしよう。興味のないメールを自動で片づけて、一部に自動で返信して、残りを「後で確認」として印を付ける。守るべき条件はこうだ——①利用者の手を止めるのを最小限に（時間を節約するため）、②自分なら絶対に送らないメールを送らない。
ソラ
ソラ便利だけど、勝手に変なメールを送られたら困ります。
リク
リクそこに重要なつり合いが見える。自律性（自由に行動できる程度）と信頼性（出力をどこまで信用できるか）だ。多く自動化すれば便利だけど、行き過ぎれば「送ってほしくないメール」を送る。自律性を測る目安は、「振る舞いのどれだけをLLMが決めて、どれだけをコードが決めるか」だ。

LLMに何を決めさせるか ― 3段階

✍️

① 出力を決めさせる

手順は人が固定し、その中の1つの結果だけをLLMに作らせます。例：返信文の下書き。

自律性 低
🔀

② 次の手順を選ばせる

用意した選択肢の中から、次に何をするかをLLMに選ばせます。例：片づける／返信する／印を付ける の3択。

自律性 中
🧠

③ 手順そのものを決めさせる

用意していない行動を、LLM自身にコードとして書かせます。

自律性 高

🔎 具体例：段階ごとに何が起きるか（メール1通に対して）

①出力だけ：「返信文を書いて」と頼み、出てきた文章を人が読んで送信ボタンを押す。誤りがあっても送信前に気づけます。

②次の手順：LLMが「これは返信すべき」と判断し、自動で返信まで進む。判断を誤ると、返信不要のメールに返信してしまいます。

③手順そのもの：LLMが「このメールには添付ファイルを解析して集計表を作って返すべきだ」と判断し、そのためのコードを自分で書いて実行する。できることは広がりますが、何が起きるか事前に読めません。

5.1

LLM呼び出しアーキテクチャ

1回呼ぶだけ

要するに：LLMを1回だけ呼んで、利用者の発言にそのまま答えます。4章のチャットボットがこれです。

START

入口。利用者の発言を受け取ります。

→

chatbot

LLMを1回呼んで答えを作ります。

→

END

出口。答えを返します。

コードを見る（1行ずつ説明つき）
# 型の道具、グラフの土台、追記の更新方法、チャットモデルを読み込む。
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_openai import ChatOpenAI

# モデルの呼び出し口を作る。
model = ChatOpenAI()

# 持ち回るデータの形を決める。会話の履歴を1項目だけ持つ。
class State(TypedDict):
    messages: Annotated[list, add_messages]

# 唯一の処理。今の履歴をまるごとモデルに渡して、返答を履歴に足す。
def chatbot(state: State):
    answer = model.invoke(state["messages"])
    return {"messages": [answer]}

# 組み立て役を作り、処理を1つだけ登録する。
builder = StateGraph(State)
builder.add_node("chatbot", chatbot)

# 入口→chatbot→出口 と一直線につなぐ。分岐はない。
builder.add_edge(START, 'chatbot')
builder.add_edge('chatbot', END)

# 実行できる形に仕上げる。
graph = builder.compile()
リク
リク最も単純だけど、出番は多い。NotionなどのAI機能（要約・翻訳）は1回のLLM呼び出しで作れるし、想定する使い勝手しだいでは単純なSQLの生成もこれで十分だ。

要するに：あらかじめ決めた順番で複数回LLMを呼びます。入力や結果は毎回違っても、呼ぶ順番はいつも同じです。

リク次にチェーンアーキテクチャ。あらかじめ決めた順番で複数回LLMを呼ぶ。何度動かしても入力や結果は違うけど、呼び出しの順番は常に同じだ。これはフローエンジニアリングとも呼ばれる。
ソラ
ソラたとえば？
リク
リク日本語からSQLを作るアプリだ。①利用者の質問とデータベースの構造からSQLを作るLLM呼び出し→②作ったSQLを、技術に詳しくない人にも分かるように説明するLLM呼び出し。これで、作られたSQLが意図に合っているか確認できる。

START

→

質問からSQLを作ります（ばらつきを抑えた設定）。

temperature 0.1
→

explain_sql

そのSQLを平易に説明します（自然な文章になる設定）。

→

END

コードを見る（1行ずつ説明つき）
# 型の道具、メッセージの入れ物、モデル、グラフの土台、追記の更新方法を読み込む。
from typing import Annotated, TypedDict
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

# SQLを作る役のモデル。文法を外すと動かないので、ばらつきを小さくする。
model_low_temp = ChatOpenAI(temperature=0.1)

# 説明を書く役のモデル。読みやすい文章にしたいので、ばらつきを大きめにする。
model_high_temp = ChatOpenAI(temperature=0.7)

# 処理の間で持ち回るデータの形を決める。4項目すべてを内部で使う。
class State(TypedDict):
    messages: Annotated[list, add_messages]  # 会話の履歴
    user_query: str       # 外から受け取る質問
    sql_query: str        # 作られたSQL
    sql_explanation: str  # SQLの説明

# 外から受け取る項目だけを書いた形。利用者はこれだけ渡せばよい。
class Input(TypedDict):
    user_query: str

# 外へ返す項目だけを書いた形。会話の履歴は返さない。
class Output(TypedDict):
    sql_query: str
    sql_explanation: str

# 1つ目の処理に与える前提の指示。
generate_prompt = SystemMessage(
    "あなたはユーザーの質問に基づいてSQLクエリを生成する有能なデータアナリストです。")

# 1つ目の処理：質問からSQLを作る。
def generate_sql(state: State) -> State:
    # 受け取った質問を、利用者の発言の形にする。
    user_message = HumanMessage(state["user_query"])
    # 前提の指示、これまでの履歴、今回の質問を順に並べる。
    messages = [generate_prompt, *state["messages"], user_message]
    # ばらつきの小さいモデルに渡して、SQLを作らせる。
    res = model_low_temp.invoke(messages)
    # 作られたSQLを記録し、質問と返答を履歴に足す（次の処理がこれを読む）。
    return {"sql_query": res.content, "messages": [user_message, res]}

# 2つ目の処理に与える前提の指示。
explain_prompt = SystemMessage(
    "あなたはユーザーにSQLクエリを説明する有能なデータアナリストです。")

# 2つ目の処理：作られたSQLを説明する。
def explain_sql(state: State) -> State:
    # 履歴には、1つ目の処理で足した「質問」と「作られたSQL」がすでに入っている。
    messages = [explain_prompt, *state["messages"]]
    # 読みやすさ重視のモデルに渡して、説明を書かせる。
    res = model_high_temp.invoke(messages)
    # 説明を記録し、履歴にも足す。
    return {"sql_explanation": res.content, "messages": res}

# 組み立て役を作る。持ち回る形・受け取る形・返す形の3つを別々に指定できる。
builder = StateGraph(State, input=Input, output=Output)

# 2つの処理を登録する。
builder.add_node("generate_sql", generate_sql)
builder.add_node("explain_sql", explain_sql)

# 入口→生成→説明→出口 と一直線につなぐ。この順番は変わらない。
builder.add_edge(START, "generate_sql")
builder.add_edge("generate_sql", "explain_sql")
builder.add_edge("explain_sql", END)

# 実行できる形に仕上げる。
graph = builder.compile()

# 質問を1つ渡すと、SQLとその説明の2つが返る。履歴は返らない（返す形に含めていないため）。
print(graph.invoke({"user_query": "各製品の売上高はいくらですか？"}))
# --- 実行結果 ---
# {
#   "sql_query": "SELECT product_name, SUM(sales_amount) AS total_sales FROM sales GROUP BY product_name;",
#   "sql_explanation": "このクエリは、sales_amount 列を製品ごとに合計し、product_name でグループ化して、各製品の売上高を取得します。",
# }
リク
リクまず generate_sql が sql_query を決めて履歴を更新、続いて explain_sql が作られたSQLを使って sql_explanation を決める。順番は固定だ。注目してほしいのは、StateGraph を作るときに受け取る形と返す形を分けて指定できること。どの項目を利用者から受け取って、どれを返すかを決められる。残りの項目は処理の途中でだけ使うデータだ。

🟣 なぜ受け取る形と返す形を分けるのか

  • 利用者が渡すべき項目がはっきりして、間違った使い方をされにくくなるから。
  • 会話の履歴のような内部の作業用データを、外に漏らさずに済むから。
  • 後から内部の作りを変えても、外から見た使い方が変わらずに済むから。
5.3

ルーターアーキテクチャ

次に何をするかをLLMに選ばせる

要するに：用意しておいた複数の処理のうち、どれを実行するかをLLMに選ばせます。チェーンより自律性が上がります。

リク
リク最後にルーターアーキテクチャ。次に取るべき手順の判断をLLMに任せて、自律性をさらに高める。チェーンが決まった手順を常に実行するのに対して、ルーターは用意しておいた複数の手順から、どれを実行するかをLLMに選ばせる。
ソラ

リク

ソラ昔はどうやってたんですか？
リク

取り出した資料から答えを作る

from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

# 埋め込みモデルと、2種類のモデル（判断用と回答用）を用意する。
embeddings = OpenAIEmbeddings()
model_low_temp = ChatOpenAI(temperature=0.1)   # 判断がぶれないように
model_high_temp = ChatOpenAI(temperature=0.7)  # 回答が自然になるように

# 持ち回るデータの形を決める。domain には2つの値しか入らないよう限定している。
class State(TypedDict):
    messages: Annotated[list, add_messages]
    user_query: str                              # 外から受け取る質問
    domain: Literal["records", "insurance"]      # LLMが選んだ分野
    documents: list[Document]                     # 取り出した資料
    answer: str                                   # 最終の答え

# 外から受け取る項目だけの形。
class Input(TypedDict):
    user_query: str

# 外へ返す項目だけの形。根拠になった資料も一緒に返す。
class Output(TypedDict):
    documents: list[Document]
    answer: str

# 2つの保管場所を用意する（中身の入れ方は2章を参照）。
medical_records_retriever = InMemoryVectorStore.from_documents([], embeddings).as_retriever()
insurance_faqs_retriever = InMemoryVectorStore.from_documents([], embeddings).as_retriever()

# 判断役への前提の指示。選択肢とその中身を説明し、名前だけを答えさせる。
#「出力はドメイン名のみ」と縛るのは、後の処理で文字列を比べやすくするため。
router_prompt = SystemMessage(
    """ユーザーの問い合わせをどのドメインへルーティングするか決定してください。
    選べるドメインは2つです:
      - records: 患者の診断、治療、処方などの医療記録を含む。
      - insurance: 保険契約、請求、補償に関するFAQを含む。
    出力はドメイン名のみとしてください。""")

# 判断の処理：質問を読んで、どちらの分野かを決める。
def router_node(state: State) -> State:
    user_message = HumanMessage(state["user_query"])
    messages = [router_prompt, *state["messages"], user_message]
    res = model_low_temp.invoke(messages)
    # 返ってきた分野名を記録する。次の分岐でこの値が使われる。
    return {"domain": res.content, "messages": [user_message, res]}

# 分岐を決める関数。次に動かす処理の「名前」を返すのがポイント。
def pick_retriever(state: State) -> Literal["retrieve_medical_records", "retrieve_insurance_faqs"]:
    if state["domain"] == "records":
        return "retrieve_medical_records"
    else:
        return "retrieve_insurance_faqs"

# 分岐先その1：医療記録の保管場所から資料を取り出す。
def retrieve_medical_records(state: State) -> State:
    return {"documents": medical_records_retriever.invoke(state["user_query"])}

# 分岐先その2：保険FAQの保管場所から資料を取り出す。
def retrieve_insurance_faqs(state: State) -> State:
    return {"documents": insurance_faqs_retriever.invoke(state["user_query"])}

# 回答役への前提の指示を、分野ごとに2つ用意する。
medical_records_prompt = SystemMessage(
    "あなたは患者の医療記録（診断・治療・処方など）に基づいて質問に答える有能な医療チャットボットです。")
insurance_faqs_prompt = SystemMessage(
    "あなたは保険契約・請求・補償に関するFAQに回答する有能な医療保険チャットボットです。")

# 回答の処理：どちらの道を通ってきても、最後はここに来る。
def generate_answer(state: State) -> State:
    # 選ばれた分野に合わせて、使う前提の指示を切り替える。
    prompt = medical_records_prompt if state["domain"] == "records" else insurance_faqs_prompt
    # 前提の指示、履歴、そして取り出した資料を並べて渡す。
    messages = [prompt, *state["messages"], HumanMessage(f"Documents: {state['documents']}")]
    res = model_high_temp.invoke(messages)
    return {"answer": res.content, "messages": res}

# 組み立て役を作り、4つの処理をすべて登録する。
builder = StateGraph(State, input=Input, output=Output)
builder.add_node("router", router_node)
builder.add_node("retrieve_medical_records", retrieve_medical_records)
builder.add_node("retrieve_insurance_faqs", retrieve_insurance_faqs)
builder.add_node("generate_answer", generate_answer)

# 入口からは、まず必ず判断の処理へ進む。
builder.add_edge(START, "router")

# 判断の処理のあとは、pick_retriever が返す名前によって進む先が変わる。
# 固定のつなぎではなく、実行するたびに行き先が決まる点が普通のエッジとの違い。
builder.add_conditional_edges("router", pick_retriever)

# どちらの検索処理からも、同じ回答の処理へ合流させる。
builder.add_edge("retrieve_medical_records", "generate_answer")
builder.add_edge("retrieve_insurance_faqs", "generate_answer")

# 回答の処理が終わったら出口へ。
builder.add_edge("generate_answer", END)

# 実行できる形に仕上げる。
graph = builder.compile()
ソラ
ソラadd_conditional_edges がポイントですね。

🔎 具体例：質問を変えると通る道が変わる

「新型コロナウイルスの治療は補償されていますか？」→ 補償の話なので domain は insurance。保険FAQの保管場所だけが検索されます。

「山田さんに処方されている薬は？」→ 処方の話なので domain は records。医療記録の保管場所だけが検索されます。

どちらの場合も、関係のないほうの保管場所は一度も検索されません。無関係な文章が指示文に混ざらないので、答えの精度が上がり、料金も抑えられます。

🟢 この項のまとめ

  • 認知アーキテクチャ＝部品の組み合わせ方（アプリの設計図）。「自律性と信頼性」のつり合いで選ぶ。
  • 段階：0コード→1 LLM呼び出し（翻訳・要約など）→2チェーン（決まった順番で複数回、フローエンジニアリング）→3ルーター（LLMが次の手順を選ぶ）。
  • チェーン：受け取る形と返す形を分けて、途中だけで使うデータを管理できる（例：質問→SQL生成→説明）。
  • ルーター：add_conditional_edges で、LLMの判断（domain）に応じて道筋を分ける。
  • 自律性が高まるほどできることは増えるが、行動を制御する仕組みも厳密に必要。

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問認知アーキテクチャとは

❓ 認知アーキテクチャとは何ですか。なぜそれが重要な判断になるのかも含めて説明してください。

✅ 解答例
認知アーキテクチャとは、LLMアプリが目的を達成するために踏む手順の組み立て方、つまり「部品（プロンプト・RAG・メモリなど）をどう組み合わせるか＝設計図」のこと。同じ部品を使っても、並べ方と役割の分け方を変えれば、まったく性質の違うアプリになる。たとえばLLMを1回呼ぶだけの構成と、LLMに次の手順を選ばせる構成では、できることも危険性もまるで違う。だから、どう組み合わせるかを決めることが最も重要な判断になる。
📝 採点ポイント
□ 認知アーキテクチャ＝部品の組み合わせ方（手順の組み立て方）、に触れている
□ 同じ部品でも組み合わせ方で性質が変わる、に触れている
□ アーキテクチャの選択が重要な判断、に触れている
第2問自律性と信頼性

❓ 「自律性」と「信頼性」のつり合いとは何ですか。メールアシスタントの例で説明してください。

✅ 解答例
自律性は「LLMがどれだけ自由に行動できるか」、信頼性は「その出力をどこまで信用できるか」。両者は片方を強めるともう片方が弱まる関係にある。メールアシスタントの例では、より多くの作業を自動化（自律性を高く）すれば便利になるが、行き過ぎると「自分なら絶対に送らないメール」を勝手に送ってしまう事態が避けられない。自律性を測る目安は「振る舞いのどれだけをLLMが決め、どれだけをコードが決めるか」で、出力だけ／次の手順／手順そのもの、と段階がある。
📝 採点ポイント
□ 自律性＝自由に行動できる程度、信頼性＝出力を信用できる程度、に触れている
□ 自動化を進めると便利だが事故（送ってほしくないメール）の危険、に触れている
□ LLMにどこまで決めさせるかの段階に触れている
第3問チェーンとルーターの違い

❓ チェーンアーキテクチャとルーターアーキテクチャの違いを説明してください。

✅ 解答例
チェーンは、あらかじめ決めた順番で複数回LLMを呼ぶ。入力や結果は毎回違っても、実行される手順の順番は常に同じ（例：質問からSQLを作る→そのSQLを説明する、の順を必ず実行）。ルーターは、次に取るべき手順の選択をLLMに任せる。用意しておいた複数の手順の中から、どれを実行するかをLLMに選ばせる（例：複数の保管場所を持つRAGで、質問に応じてどこを検索するかをLLMが決める）。ルーターのほうが自律性が高い。
📝 採点ポイント
□ チェーン＝決まった順番で複数回呼ぶ、に触れている
□ ルーター＝次の手順をLLMに選ばせる、に触れている
□ ルーターのほうが自律性が高い、に触れている
第4問条件付きエッジ

❓ ルーターアーキテクチャで使う「条件付きエッジ（add_conditional_edges）」は、何をするものですか。

✅ 解答例
条件付きエッジは、固定の道筋ではなく、関数の判定結果に応じて次に実行する処理を動的に選ぶつながり。ルーターの例では、router でLLMが分野（records か insurance）を選び、pick_retriever 関数がその分野に応じて「医療記録を検索する処理」か「保険FAQを検索する処理」のどちらかの名前を返す。これにより、LLMの判断に応じてグラフの道筋が分かれる。
📝 採点ポイント
□ 関数の判定結果に応じて次の処理を動的に選ぶ、に触れている
□ LLMの判断（domain）に応じて道筋が分かれる、に触れている
□ ルーターアーキテクチャの実装に使われる、に触れている
第5問受け取る形と返す形の分離

❓ StateGraph で入力の形と出力の形を分けて指定できると、何が嬉しいですか。

✅ 解答例
入力の形と出力の形を分けると、持ち回るデータのうち「どの項目を利用者からの入力として受け取り、どの項目を最終の出力として返すか」を柔軟に決められる。たとえば質問からSQLを作るチェーンでは、入力は user_query だけ、出力は sql_query と sql_explanation、というふうに指定できる。残りの項目（messagesなど）は処理の途中でだけ使い、利用者に返す最終の出力には含めない。これにより、外から見た使い方がはっきりする。
📝 採点ポイント
□ どの項目を入力として受け取り、どれを出力として返すかを決められる、に触れている
□ 残りは途中だけで使うデータになる、に触れている
□ 外から見た使い方がはっきりする、に触れている（できれば）
