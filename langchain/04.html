この章のあらすじ

忘れてしまうチャットボットに記憶を付ける

「先生、うちのチャットボット、さっき名前を教えたのに忘れちゃうんです！」とソラ。リク先輩は「LLMはステートレス——前の会話を覚えていないんだ。だから記憶を外付けする」と説明します。

この章では、過去のやり取りを記憶する仕組みを、LangChain社のライブラリLangGraphで作ります。グラフ（ステート・ノード・エッジ）の考え方を学び、チェックポインタで会話を保存し、「スレッド」で利用者ごとに会話を分けます。さらに、長くなった履歴を切り落とす・絞り込む・まとめる方法も学びます。

🎯

この章を1枠でまとめると

LLMはステートレス——毎回まっさらで、前のやり取りを覚えていません。だから、過去の会話を記憶する仕組みを外付けして、それを毎回まとめて渡す必要があります。LangGraphを使うと、ステート（共有データ）・ノード（処理）・エッジ（つながり）でアプリを組み立て、チェックポインタで会話を自動保存し、スレッドで利用者ごとに会話を分けられます。

学ぶ理由と、身につくこと

🟣 なぜ学ぶ価値があるのか

  • LLMは前の会話を覚えていないので、記憶がないと「さっきの話」が通じないから。
  • 全履歴をただ保存するだけでは、確実な更新・消えない保存・件数の調整ができず、本番で行き詰まるから。
  • 履歴が長くなると1回に扱える上限を超え、注意が散って嘘の回答が増えるから。

🟢 これを知ったらできるようになること

  • LangGraphのステート・ノード・エッジで StateGraph を組み立てられる。
  • チェックポインタ（メモリ／SQLite／Postgres）で会話を保存し、スレッドで利用者ごとに分けられる。
  • get_state／update_state でステートを確認・編集できる。
  • trim_messages・filter_messages・merge_message_runs で履歴を整えられる。

導入 ― LLMは前を覚えていない

ステートレスという性質
ソラ
ソラ先生、3章でRAGができました。でも、チャットボットに名前を教えても、次の質問では忘れてるんです……。
リク
リクそれはね、LLMがステートレスだからだ。毎回の入力は独立していて、モデルは以前の入力や返答を記憶していない。だから、過去の会話を追える記憶の仕組みを外付けして、その履歴を最終の指示文に含めて渡す。そうすると、LLMに「記憶」を持たせられる。
ソラ
ソラ自分で覚えてくれるわけじゃないんですね。

🔎 具体例：実際に何が送られているか

利用者から見ると、1回目「私はJackです」、2回目「私の名前は？」という会話です。しかしLLMに実際に届いているのは、記憶がない場合、2回目は「私の名前は？」の1文だけ。名前の情報はどこにもないので、答えられません。

記憶を付けると、2回目に届くのは「私はJackです」「はい、Jackさん」「私の名前は？」という3件まとめてになります。答えが書いてあるので答えられます。モデルは変わっていません。送っている内容が変わっただけです。

4.1

チャットボットメモリシステムの構築

いちばん単純なやり方と、その限界

要するに：最も単純なのは、全履歴を一覧として保存し、毎回まるごと指示文に差し込むこと。うまく動きますが、本番では4つの課題が出ます。

リク
リク丈夫な記憶の仕組みには2つの設計の判断がある——①どう保存するか、②どう取り出すか。最も単純なのは、全履歴をメッセージの一覧として保存して、毎回の終わりに最新の1件を足して、それを指示文に差し込んでモデルに渡すことだ。
コードを見る（1行ずつ説明つき）
# 役割つきの雛形と、チャットモデルの部品を読み込む。
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

# 雛形を作る。placeholder は「ここに会話の履歴を丸ごと差し込む」という意味。
# 1件ずつ書くのではなく、何件あっても一度に入れられるのが利点。
prompt = ChatPromptTemplate.from_messages([
    ("system", "あなたは優秀なアシスタントです。質問に対して全力で答えてください。"),
    ("placeholder", "{messages}"),
])

# モデルの呼び出し口を作る。
model = ChatOpenAI()

# 「雛形 → モデル」を1本につなぐ。
chain = prompt | model

# 過去のやり取り2件と、新しい質問1件をまとめて渡す。
# モデルは3件すべてを一度に読むので、「さっき」が何を指すか分かる。
print(chain.invoke({
    "messages": [
        ("human", "この文を英語からフランス語に翻訳してください: I love programming."),
        ("ai", "J'adore programmer."),
        ("human", "さっき何て言いましたか？"),
    ],
}))
# --- 実行結果 ---
# さっき「J'adore programmer.」と言いました。フランス語で「私はプログラミングが大好きです」という意味です。
ソラ
ソラ過去の会話を入れたら、ちゃんと文脈を理解しましたね！
リク
リク単純でうまく動く。でも本番だと課題がある。これを解決するのがLangGraphだ。
⚛️

① 確実に一括で更新したい

途中で失敗したときに、質問だけ記録されて返答が記録されない、といった中途半端な状態を避けたい。

💾

② 消えない場所に保存したい

プログラムを終了しても会話が残るよう、データベースなどに保存したい。

🔢

③ 渡す件数を調整したい

どのメッセージを何件保持し、次にどれだけ渡すかを決めたい。

🔧

④ 中身を確認・編集したい

LLMの呼び出しとは別に、保存されている内容を見たり直したりしたい。

4.2

LangGraphについて

3つのキーワードと、グラフの3要素

要するに：LangGraphは、複数の担い手が複数の段階で、途中経過を持ち回りながら動く仕組みを作るためのライブラリです。

リク
リクLangGraphは、マルチアクター・マルチステップ・ステートフルな認知アーキテクチャ（グラフと呼ぶ）を作るためのライブラリだ。1つずつ説明しよう。
ソラ
ソラ用語が難しいです……。
👥

マルチアクター（複数の担い手）

答えを作るのが得意なLLMと、最新情報を集めるのが得意な検索を組み合わせる、といった形。PerplexityやArc Searchがその例です。誰がいつ・どの順で・どう仕事を渡すかを調整する層が必要になります。

🪜

マルチステップ（複数の段階）

担い手が別の担い手に仕事を渡すたびに、次の段階が予約されます。渡す相手がいなくなるまで続き、最終結果にたどり着きます。

📌

ステートフル（途中経過を持つ）

段階をまたいで連携するには、途中経過の記録が要ります。記録しないままLLMを2回呼ぶと、同じ結果が返ってしまいます。

各担い手から途中経過を集めて、全員が共有する1つの中央の記録として更新します。これにより、各計算の前後で状態を保存でき、途中で止めて再開でき、エラーから復旧でき、人が途中に割り込んで確認することもできます。

グラフを構成する3要素

ソラ
ソラグラフって、何でできてるんですか？
リク
リク3要素だ。①ステート——アプリが受け取って、実行中に変えたり作ったりするデータ。②ノード——各段階を表すただの関数。今のステートを受け取って、更新した内容を返す。③エッジ——ノードとノードのつながり。最初から最後までの道筋を決める（固定の道筋や、関数で次を決める分かれ道）。LangGraphは図で見る機能や不具合探しの支援も備えていて、そのまま本番に出せる。
要素正体役割この章での例
ステートデータ（辞書）処理全体で共有する途中経過messages（会話の履歴）
ノード関数1つの処理。ステートを受け取り更新分を返すchatbot（LLMを呼ぶ）
エッジつながりの定義どのノードの次にどのノードへ進むかSTART→chatbot→END
4.3

StateGraphを作成する

ステート→ノード→エッジ→仕上げ

要するに：①ステートの形を決める→②ノードを足す→③エッジでつなぐ→④仕上げる、の4手順です。

1

ステートの形を決める

どんなデータを持ち回るか、そしてそれをどう更新するか（上書きか追記か）を決めます。

2

ノードを足す

実際の処理を行う関数に、名前を付けて登録します。

3

エッジでつなぐ

入口から出口までの道筋を決めます。

4

仕上げる（compile）

実行できる形にします。これで invoke や stream で呼べます。

① ステートを定義する

コードを見る（1行ずつ説明つき）
# 型に追加の指示を付ける道具と、辞書の形を決める道具を読み込む。
from typing import Annotated, TypedDict

# グラフの土台と、入口・出口を表す印を読み込む。
from langgraph.graph import StateGraph, START, END

# 会話の履歴用の「追記する」更新の仕方を読み込む。
from langgraph.graph.message import add_messages

# 持ち回るデータの形を決める。ここでは messages という項目を1つだけ持つ。
class State(TypedDict):
    # 中身は一覧（list）。add_messages を添えると「上書きせず後ろに足す」意味になる。
    # これを添えないと、更新のたびに前の履歴が消えてしまう。
    messages: Annotated[list, add_messages]

# 決めた形を渡して、グラフの組み立て役を作る。
builder = StateGraph(State)
リク
リクグラフを定義するとき、最初にやるのがステートの定義だ。ステートには「形」と「更新の仕方を決めるリデューサー」が含まれる。ここでは messages という項目に add_messages が付いていて、「新しいメッセージを既存の一覧に足す」という意味だ。リデューサーがない項目は、更新のたびに上書きされる。
ソラ
ソラリデューサーって？
リク
リク単純な関数で、1つ目に今のステート、2つ目に書き込まれる値を受け取って、合わせた結果を返す。一番単純なのは「新しい値を一覧の後ろに足して返す」関数だ。

🔎 具体例：リデューサーの有無で結果がどう違うか

今のステートが messages = ["こんにちは", "はい、どうも"] で、ノードが {"messages": ["名前は？"]} を返したとします。

リデューサーなし（上書き）→ ["名前は？"]。前の2件が消えます。add_messages あり（追記）→ ["こんにちは", "はい、どうも", "名前は？"]。会話が積み上がります。

② ノードを追加する

コードを見る（1行ずつ説明つき）
# チャットモデルの部品を読み込む。
from langchain_openai import ChatOpenAI

# モデルの呼び出し口を作る。
model = ChatOpenAI()

# 1つの処理を表す関数を書く。引数として、今のステートがそのまま渡ってくる。
def chatbot(state: State):
    # ステートの中の会話の履歴を、まるごとモデルに渡して返答をもらう。
    answer = model.invoke(state["messages"])
    # 更新したい項目だけを返す。add_messages が付いているので、履歴の後ろに足される。
    return {"messages": [answer]}

# グラフにこの処理を登録する。1つ目は見分けるための名前、2つ目は実行する関数。
builder.add_node("chatbot", chatbot)

③④ エッジでつないで、仕上げる

コードを見る（1行ずつ説明つき）
# 入口から chatbot へ進む道をつくる。これで「どこから始めるか」が決まる。
builder.add_edge(START, 'chatbot')

# chatbot から出口へ進む道をつくる。「どこで終わるか」の指定（省略もできる）。
builder.add_edge('chatbot', END)

# 組み立てたものを、実行できる形に仕上げる。これで invoke や stream で呼べる。
graph = builder.compile()

graph.get_graph().draw_mermaid_png() で、組み立てた流れを図として見ることもできます。実行してみましょう。

コードを見る（1行ずつ説明つき）
# 「これは利用者の発言」という札を付ける入れ物を読み込む。
from langchain_core.messages import HumanMessage

# 入力を、さきほど決めたステートと同じ形（messages に一覧）で用意する。
user_input = {"messages": [HumanMessage('hi!')]}

# グラフを動かす。stream は、1つの段階が終わるたびにその結果を返してくれる。
for chunk in graph.stream(user_input):
    # どのノードが何を返したかが、そのまま表示される。
    print(chunk)
# --- 実行結果 ---
# { "chatbot": { "messages": [AIMessage("How can I help you?")] } }
リク
リク入力が、さっき決めた State と同じ形（messages という項目にメッセージの一覧）になっている点に注目。stream() は各段階の後にステート全体を返してくれる。

# メモリ上に保存する保存先を読み込む。
from langgraph.checkpoint.memory import InMemorySaver

# 仕上げるときに保存先を渡す。これだけで、各段階の終わりにステートが保存されるようになる。

スレッドで会話を分ける

コードを見る（1行ずつ説明つき）
# この会話のまとまりを見分けるための名札を用意する。ここでは "1" という名前。
thread1 = {"configurable": {"thread_id": "1"}}

# 1回目：名前を伝える。名札を一緒に渡すことで、この会話として保存される。

# { "chatbot": { "messages": [AIMessage("How can I help you, Jack?")] } }

# 2回目：同じ名札を渡して質問する。保存済みの2件が自動で読み戻され、
# 新しい質問と合わせた計3件がモデルに届くので、名前を答えられる。
result_2 = graph.invoke(
    { "messages": [HumanMessage("what is my name?")] },
    thread1
)
print(result_2)
# --- 実行結果 ---
# { "chatbot": { "messages": [AIMessage("Your name is Jack")] } }
ソラ
ソラちゃんと「Jack」って覚えてました！thread1 が鍵ですか？
リク
リクそう。thread1 は、このやり取りが特定の履歴（LangGraphでは「スレッド」と呼ぶ）に属することを示す名札だ。スレッドは初めて使われたときに自動で作られて、好きな文字列（普通は重複しないIDの文字列）が使える。スレッドのおかげで、複数の利用者が互いに混ざらない別々の会話を持てる。
リク
リク仕組みはこうだ。1回目は chatbot が1件のメッセージを受け取って、返答を作る。両方が保存される。2回目は同じスレッドだから、ノードに3件（保存済みの2件＋新しい質問）が渡る。これが記憶の正体だ。

🔎 具体例：スレッドを分けると何が起きるか

名札 "1" で「私はJackです」と伝え、そのあと名札 "1" で「私の名前は？」と聞くと「Jack」と返ります。

ところが、名札 "2" で同じ質問をすると、そちらの履歴は空なので「お名前を教えていただいていません」と返ります。実際のアプリでは、利用者IDや会話IDをこの名札に使うことで、他人の会話が混ざるのを防げます。

ステートを直接見る・書き換える

コードを見る（1行ずつ説明つき）
# 名札を渡して、その会話の今のステートを取り出す。中身の確認や不具合探しに使う。
print(graph.get_state(thread1))
# --- 実行結果 ---
# StateSnapshot(values={'messages': [HumanMessage('hi, my name is Jack!'),
#   AIMessage('How can I help you, Jack?'), HumanMessage('what is my name?'),
#   AIMessage('Your name is Jack')]}, ...)

# LLMを呼ばずに、履歴へ1件だけ書き足す。次にこの会話を使うときに反映される。
graph.update_state(thread1, {"messages": [HumanMessage('I like LLMs!')]})

4.5.1 メッセージをトリミングする

要するに：1回に扱えるトークン数には上限があります。超えると拒否されるか途中で切られるので、渡す件数を先に制限します。

リク
リクLLMにはコンテキストウィンドウの上限がある。最終の指示文がそれを超えると、拒否されるか切り捨てられる。情報が多すぎると注意が散って嘘の回答も起きる。だから履歴から渡す件数を制限する。trim_messages を使うんだ。
コードを見る（1行ずつ説明つき）
# メッセージの入れ物と、切り落とす部品を読み込む。
from langchain_core.messages import AIMessage, SystemMessage, HumanMessage, trim_messages
from langchain_openai import ChatOpenAI

# 切り落とし役を作る。以下の6つが、どう切るかを決める設定。
trimmer = trim_messages(
    # 残してよい合計のトークン数の上限。これを超える分が切り落とされる。
    max_tokens=65,
    # どちら側を優先して残すか。last は新しいほうを残す（first なら古いほう）。
    strategy="last",
    # トークン数を、実際に使うモデルの数え方で計算する。
    token_counter=ChatOpenAI(model="gpt-4o-mini"),
    # 前提の指示は、古くても必ず残す。これがないと役割設定が消えてしまう。
    include_system=True,
    # 1件のメッセージを途中で切ることを禁じる。超えるなら丸ごと落とす。
    allow_partial=False,
    # 残った履歴が、利用者の発言から始まるようにそろえる。
    # これがないと「返答だけあって質問がない」不自然な履歴になることがある。
    start_on="human",
)

# 切り落とす対象として、11件の会話履歴を用意する。
messages = [
    SystemMessage(content="あなたは優秀なアシスタントです"),
    HumanMessage(content="こんにちは！ 私はボブです"),
    AIMessage(content="こんにちは！"),
    HumanMessage(content="バニラアイスが好きです"),
    AIMessage(content="いいですね"),
    HumanMessage(content="2 + 2 は？"),
    AIMessage(content="4"),
    HumanMessage(content="ありがとう"),
    AIMessage(content="どういたしまして！"),
    HumanMessage(content="楽しんでる？"),
    AIMessage(content="はい！"),
]

# 実際に切り落とす。前提の指示と、新しいほうの数件だけが残る。
print(trimmer.invoke(messages))
# --- 実行結果 ---
# [SystemMessage('あなたは優秀なアシスタントです'),
#  HumanMessage('2 + 2 は？'), AIMessage('4'),
#  HumanMessage('ありがとう'), AIMessage('どういたしまして！'),
#  HumanMessage('楽しんでる？'), AIMessage('はい！')]
# ↑「ボブです」「バニラアイス」の古い4件は落ちた。名前を聞かれても答えられなくなる点に注意
設定意味指定しないと
max_tokens残す合計トークン数の上限上限を超えてモデルに拒否される
strategylast＝新しい方を残す／first＝古い方を残す会話では通常 last が適切
token_counter数え方をどのモデルに合わせるか実際の消費と数え方がずれる
include_system前提の指示を必ず残すか役割の設定が消えて口調が変わる
allow_partial1件を途中で切ってよいか文の途中で切れた不完全な発言が残る
start_on残す履歴の先頭をどの種類にそろえるか質問のない返答だけが残ることがある

4.5.2 メッセージをフィルタリングする

要するに：履歴が増えると、いろいろな種類の発言が混ざります。種類・ID・名前を基準に、必要なものだけを取り出せます。

コードを見る（1行ずつ説明つき）
# メッセージの入れ物と、絞り込む部品を読み込む。
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, filter_messages

# 種類・ID・名前がばらばらの5件を用意する。
messages = [
    SystemMessage("you are a good assistant", id="1"),
    HumanMessage("example input", id="2", name="example_user"),
    AIMessage("example output", id="3", name="example_assistant"),
    HumanMessage("real input", id="4", name="bob"),
    AIMessage("real output", id="5", name="alice"),
]

# 利用者の発言だけを取り出す。前提の指示とモデルの返答は除かれる。
print(filter_messages(messages, include_types="human"))
# --- 実行結果 ---
# [HumanMessage('example input', id='2'), HumanMessage('real input', id='4')]

# 名前を指定して除く。ここでは見本用の2件を取り除いている。
print(filter_messages(messages, exclude_names=["example_user", "example_assistant"]))
# --- 実行結果 ---
# [SystemMessage('you are a good assistant', id='1'),
#  HumanMessage('real input', id='4'), AIMessage('real output', id='5')]

# 種類で絞ったうえで、さらに特定のIDだけを取り除く、という併用もできる。
print(filter_messages(messages, include_types=[HumanMessage, AIMessage], exclude_ids=["3"]))
# --- 実行結果 ---
# [HumanMessage('example input', id='2'), HumanMessage('real input', id='4'),
#  AIMessage('real output', id='5')]
リク
リクfilter_messages は、自分で呼ぶ形でも、つなぐ形でも使えるから、処理の流れの中に組み込める（chain = filter_ | model）。

4.5.3 連続するメッセージをマージする

要するに：モデルによっては、同じ種類の発言が続く入力を受け付けません。続いている分を1つにまとめます。

リク
リク一部のモデル（Anthropicなど）は、同じ種類のメッセージが連続する入力を受け付けない。merge_message_runs で、続いている同じ種類をまとめられる。
コードを見る（1行ずつ説明つき）
# メッセージの入れ物と、まとめる部品を読み込む。
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, merge_message_runs

# 同じ種類が2件ずつ続いた6件を用意する。
messages = [
    SystemMessage("あなたは優秀なアシスタントです。"),
    SystemMessage("あなたは常にジョークで返答します。"),
    HumanMessage([{"type": "text", "text": "なぜlangchainと呼ばれているのか不思議です"}]),
    HumanMessage("それと、ハリソンはいったい誰を追いかけているの？"),
    AIMessage("「WordRope」や「SentenceString」では響きがイマイチだったのでしょうね！"),
    AIMessage("きっとオフィスで最後の一杯のコーヒーを追いかけているのでしょう！"),
]

# 続いている同じ種類を1件にまとめる。6件が3件になる。
# どちらも文字列なら改行でつなぎ、片方が中身の一覧なら結果も一覧になる。
print(merge_message_runs(messages))
# --- 実行結果 ---
# [SystemMessage('あなたは優秀なアシスタントです。\nあなたは常にジョークで返答します。'),
#  HumanMessage([{'type': 'text', 'text': 'なぜlangchainと呼ばれているのか不思議です'},
#                {'type': 'text', 'text': 'それと、ハリソンはいったい誰を追いかけているの？'}]),
#  AIMessage('「WordRope」や「SentenceString」では響きがイマイチだったのでしょうね！\n'
#            'きっとオフィスで最後の一杯のコーヒーを追いかけているのでしょう！')]
リク
リクまとめると、両方が文字列なら改行でつながる。片方が中身の一覧なら、まとめた後も一覧になる。これも chain = merger | model のようにつなげられる。

🟢 この項のまとめ

  • LLMはステートレス。履歴をメッセージの一覧として保存し、毎回まとめて渡すと記憶になる。ただし素朴な保存は本番で課題（確実な更新・消えない保存・件数の調整）。
  • LangGraph：複数の担い手・複数の段階・途中経過を持ち回るグラフ。3要素はステート（共有データ）・ノード（処理関数）・エッジ（つながり）。
  • ステートの更新の仕方はリデューサーで決める（add_messages は追記）。
  • チェックポインタ（メモリ／SQLite／Postgres）で会話を保存。スレッド（thread_id）で利用者ごとに分ける。get_state／update_state で確認・編集。
  • 履歴の修正：trim_messages（件数・トークンの制限）・filter_messages（種類・ID・名前で絞る）・merge_message_runs（続いている同種をまとめる）。

章末の理解度チェック（全5問）

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問ステートレスと記憶

❓ LLMが「ステートレス」とはどういう意味ですか。それでもチャットボットが過去の会話を覚えているように見えるのはなぜですか。

✅ 解答例
ステートレスとは、LLMの毎回の入力が独立していて、モデルが以前の入力や返答を記憶していないという意味。つまりLLM自身は前の会話を覚えていない。それでも覚えているように見えるのは、アプリ側で記憶の仕組みを外付けして、過去の会話をメッセージの一覧として保存し、毎回その履歴を最終の指示文に含めてLLMに渡しているから。LLMは渡された履歴を材料として読んで、覚えているかのように答える。
📝 採点ポイント
□ ステートレス＝毎回の入力が独立、前を記憶しない、に触れている
□ アプリ側で履歴を保存し指示文に含めて渡す、に触れている
□ LLM自身が覚えているわけではない、に触れている
第2問グラフの3要素

❓ LangGraphのグラフを構成する3要素（ステート・ノード・エッジ）を、それぞれ説明してください。

✅ 解答例
ステートは、アプリが外から受け取り、実行中に変えたり作ったりする共有データ（例：messagesの一覧）。更新の仕方はリデューサーで決める。ノードは、各段階を表す関数で、今のステートを受け取り、更新する内容を返す（例：LLMを呼ぶchatbotノード）。エッジは、ノードとノードのつながりで、最初から最後までの道筋を決める。固定の道筋や、関数で次を決める分かれ道を設定できる。
📝 採点ポイント
□ ステート＝実行中に変わる共有データ、に触れている
□ ノード＝今のステートを受け取り更新する関数、に触れている
□ エッジ＝ノード間のつながり・道筋、に触れている
第3問チェックポインタとスレッド

❓ チェックポインタと「スレッド（thread_id）」は、それぞれ何のためにありますか。

✅ 解答例
チェックポインタは、各段階の終わりにグラフのステートを保存する部品。これにより、次の呼び出しがまっさらな状態から始まらず、最新のステートを読み戻して新しい入力と合わせて実行できる（メモリ／SQLite／Postgresなどがある）。スレッド（thread_id）は、そのやり取りがどの会話の履歴に属するかを示す名札。スレッドを分けることで、複数の利用者が互いに混ざらない別々の会話を持てる。
📝 採点ポイント
□ チェックポインタ＝ステートを保存する部品、に触れている
□ 次の呼び出しで最新ステートを読み戻して合わせる、に触れている
□ スレッド＝会話を見分け、利用者ごとに分ける、に触れている
第4問なぜ履歴を整えるのか

❓ チャット履歴が長くなったとき、なぜ切り落とし（メッセージの制限）が必要なのですか。

✅ 解答例
LLMには1回に扱えるトークン数の上限（コンテキストウィンドウ）があり、最終の指示文がそれを超えるとモデルが拒否するか途中で切り捨ててしまうから。また、情報量が多すぎる指示文はモデルの注意を散らし、嘘の回答を引き起こす可能性もある。だから履歴から渡す件数を制限する。実際には、新しいメッセージを優先して残せばよい（trim_messages の strategy="last"）。
📝 採点ポイント
□ 上限を超えると拒否／切り捨てられる、に触れている
□ 情報が多すぎると注意が散り嘘の回答を招く、に触れている
□ 新しいメッセージを優先して残す、に触れている
第5問履歴の3つの修正法

❓ チャット履歴を修正する3つの方法（切り落とし・絞り込み・まとめ）を、それぞれ何をするかを説明してください。

✅ 解答例
切り落とし（trim_messages）は、1回に扱える上限に収まるよう、保持するメッセージ数やトークン数を制限する（新しいほうを優先して残すなど）。絞り込み（filter_messages）は、メッセージの種類（利用者・モデルなど）・ID・名前を基準に、必要なものだけを取り出したり不要なものを除いたりする。まとめ（merge_message_runs）は、同じ種類のメッセージが続いている場合に1つにまとめる（一部のモデルが続いた同種の発言を受け付けないため）。
📝 採点ポイント
□ 切り落とし＝件数／トークン数を制限、に触れている
□ 絞り込み＝種類・ID・名前で選ぶ、に触れている
□ まとめ＝続いている同種を結合、に触れている
