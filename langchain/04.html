📚 かんたん用語集

この章に出てくる専門用語を、やさしい言葉と「宿」のたとえで先に押さえておきましょう。

LLM 大規模言語モデル

文章を読んで答えを作るAIの本体。賢いけれど、前のやり取りは自分では覚えていません。宿でいう「会話上手な接客スタッフ」。

ステートレス stateless

「状態を持たない」。LLMは毎回まっさらで、前に何を話したか覚えていない性質のこと。毎朝記憶がリセットされる接客スタッフのイメージ。

メモリ memory

過去の会話を保存しておく外付けの仕組み。これを毎回スタッフに見せると、覚えているように振る舞えます。宿の「宿帳（ゲストブック）」。

LangGraph

会話アプリを「ステート・ノード・エッジ」で組み立てるためのLangChain社のライブラリ。宿の「業務マニュアルと動線設計」。

ステート State / 状態

アプリ全体で共有する中央のデータ（ここでは会話メッセージの一覧）。宿でいう「いま開いている宿帳のページ」。

ノード Node

1つの作業を表す関数（処理のかたまり）。ステートを受け取り、更新を返します。宿の「ひとつの持ち場（受付など）」。

エッジ Edge

ノードとノードのつながり＝処理の進む道筋。宿の「お客さまを次の持ち場へ案内する動線」。

リデューサー Reducer

ステートをどう更新するかを決める関数。add_messagesは「上書きせず追記する」やり方。宿帳に「線で消さず追記」するルール。

チェックポインタ checkpointer

各ステップごとにステートを保存する保存係。宿でいう「宿帳を金庫にしまう仕組み」。InMemory/SQLite/Postgresの種類があります。

スレッド thread / thread_id

どの会話の履歴かを区別する識別子。お客さまごとに別の宿帳ページを持たせる「宿泊カード番号」。

コンテキストウィンドウ

LLMが一度に読める文章量（トークン数）の上限。机の上に広げられる書類の枚数の限界。超えると読めません。

ハルシネーション hallucination

AIがもっともらしい嘘を作ってしまうこと。情報が多すぎて注意が散ると起きやすくなります。

トリミング / フィルタ / マージ

長くなった履歴を整える3手段。順に「件数を減らす」「種類で選ぶ」「連続を1つにまとめる」。宿帳の整理術。

何の話をするのか、ざっくり

「先生、うちのチャットボット、さっき名前を教えたのに忘れちゃうんです！」――この章は、過去のチャットを記憶するメモリシステムを、LangChain社のライブラリLangGraphで作る話です。

リク先輩は「LLMはステートレス――前の会話を覚えていないんだ。だから“メモリ”を外付けする」と説明します。グラフ（ステート・ノード・エッジ）の考え方を学び、チェックポインタで会話を永続化し、スレッドでユーザーごとに会話を分けます。さらに、長くなった履歴をトリミング・フィルタリング・マージで整える方法も学びます。

🏨 たとえ話：このページの舞台「記憶のおもてなし宿」

これから登場する黄色い箱は、ぜんぶ1つの旅館を舞台にします。接客スタッフ（＝LLM）はとても話し上手ですが、毎朝記憶がリセットされてしまう体質。そこで宿は「宿帳（ゲストブック）」を用意し、お客さまの過去のやり取りを書き留めて、接客のたびにスタッフへ見せます。すると、まるで覚えているかのようにおもてなしできる――これがこの章のすべてです。

🎯

要するに ／ なぜ必要か

この章の核心と動機

要するに：LLMは「ステートレス」――毎回独立していて、前のやり取りを覚えていません。だから過去の会話を記憶するメモリを外付けし、毎回プロンプトに含めて渡します。LangGraphなら、ステート（共有データ）・ノード（処理）・エッジ（つながり）でアプリを組み立て、チェックポインタで会話を自動保存し、スレッドでユーザーごとに会話を分けられます。

🟣 なぜ学ぶ価値があるのか

  • LLMはステートレスで前の会話を覚えていないので、メモリがないと「さっきの話」が通じないから。
  • 全履歴を素朴に保存するだけでは、アトミックな更新・永続化・件数制御ができず本番で破綻するから。
  • 履歴が長くなるとコンテキストウィンドウを超え、注意が散ってハルシネーションを起こすから。

✅ これを知ったらできるようになること

  • LangGraphのステート・ノード・エッジで StateGraph を組み立てられる。
  • チェックポインタ（InMemory/SQLite/Postgres）で会話を永続化し、スレッドでユーザーごとに会話を分けられる。
  • get_state/update_state でステートを確認・編集できる。
  • trim_messages・filter_messages・merge_message_runs で履歴を整えられる。

4.1

チャットボットメモリシステムの構築

いちばんシンプルなメモリ＝全履歴をリストで持つ

堅牢なメモリシステムには2つの設計判断があります――①ステートの保存方法と②ステートの参照（クエリ）方法。最もシンプルなのは、全チャット履歴をメッセージのリストとして保存し、各ターン後に最新メッセージを追加して、それをプロンプトに挿入してモデルに渡す方法です。

リク
先生・リク全チャット履歴をメッセージのリストとして保存して、各ターン後に最新メッセージを追加して、それをプロンプトに挿入してモデルに渡す。これが一番シンプルだ。

↓ このコードは、過去の会話（人間とAIのやり取り）をプロンプトに含めて、「さっき何て言った？」という追質問に文脈をふまえて答えさせるものです。{messages}の所に会話履歴が差し込まれます。

Python：履歴をプロンプトに差し込んで答えさせる
# Python
# このコードがやること: 過去の会話（人間とAIのやり取り）をプロンプトに含めて、
# 「さっき何て言った？」という追質問に文脈をふまえて答えさせる。
# placeholder の {messages} に会話履歴が差し込まれる。
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_messages([
    ("system", "あなたは優秀なアシスタントです。質問に対して全力で答えてください。"),
    ("placeholder", "{messages}"),
])

model = ChatOpenAI()
chain = prompt | model

chain.invoke({
    "messages": [
        ("human", "この文を英語からフランス語に翻訳してください: I love programming."),
        ("ai", "J'adore programmer."),
        ("human", "さっき何て言いましたか？"),
    ],
})

4.2

LangGraphについて

マルチアクター・マルチステップ・ステートフルなグラフ

LangGraphは、マルチアクター・マルチステップ・ステートフルな認知アーキテクチャ（グラフと呼ぶ）を実装するライブラリです。3つの難しい言葉を1つずつほどいていきます。

ソラ
弟子・ソラ用語が難しいです……。

3つのキーワードをほどく

👥

マルチアクター

専門家チームが協働するように、複数のアクターを組み合わせると強くなる。回答が得意なLLMと、最新情報集めが得意な検索エンジンを組むなど（Perplexity・Arc Searchが例）。「誰がいつ・どの順で・どう作業を受け渡すか」を調整するレイヤーが要る。

複数の働き手
⏱️

マルチステップ

あるアクターが別のアクターへ処理を渡すたび、やり取りを把握する必要がある。これを「時間軸上の複数の離散ステップ」としてモデル化。渡す相手がいなくなるまで続き、最終結果に到達する。

段階を踏む
🧾

ステートフル

ステップをまたいで連携するにはステート（状態）の追跡が要る。記録しないままLLMを2回呼ぶと同じ結果に。各アクターから取り出し、全員が共有する単一の中央ステートとして更新する。

状態を持つ

🟣 ステートフルだと何がうれしいか

  • 各計算の前後でスナップショット保存ができる。
  • 一時停止・再開・エラー復旧ができる。
  • ヒューマンインザループ制御（人が途中で確認・介入）ができる。

🏨 たとえ話：宿は1人では回らない

大きな宿は、フロント係・仲居さん・板前さんなど複数の働き手（マルチアクター）が、受付→案内→食事提供と順に仕事を受け渡し（マルチステップ）ます。そして全員が同じ宿帳（ステート）を見て「このお客さまは何号室で、苦手な食材は何か」を共有する。宿帳がなければ、板前さんは毎回イチから聞き直すことになります。これがステートフルな宿＝LangGraphです。

🏨 たとえ話：宿の設計図そのもの

ステート＝いま開いている宿帳のページ。ノード＝受付・案内などひとつひとつの持ち場（係）。エッジ＝「受付が終わったら客室へ」というお客さまの案内動線。この3つを決めれば、お客さまが入口から出口まで迷わず流れる――それがグラフです。

4.3

StateGraphを作成する

ステート定義 → ノード追加 → エッジ接続 → コンパイル

シンプルなチャットボットを作ります。流れは ①StateGraphを作りステートを定義 → ②chatbotノードを追加 → ③エッジを接続 → ④コンパイル の4ステップ。順に見ていきます。

1

ステートを定義する

messagesというキーを用意し、add_messagesリデューサーで「上書きせず追記」と決める。

2

chatbotノードを追加する

現在のメッセージをLLMに渡して答えを得る関数を、ノードとしてグラフに登録する。

3

エッジを追加する

START→chatbot→END とつないで、開始と終了の道筋を決める。

① ステートを定義する

↓ このコードは、グラフのステートを定義します。messagesはリストで、add_messagesリデューサーにより「上書きせず追記」されます。

Python：ステート（State）の定義
# Python
# このコードがやること: グラフのステートを定義する。
# messages はリストで、add_messages リデューサーにより「上書きせず追記」される。
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    # messagesの型は list。add_messages はこのステートの更新方法を定義する。
    # 既存のメッセージを置き換えるのではなくリストへ追記する。
    messages: Annotated[list, add_messages]

builder = StateGraph(State)
リク
先生・リクステートには「形（スキーマ）」と「更新方法を示すリデューサー関数」が含まれる。ここではmessagesにadd_messagesが付いていて「新しいメッセージを既存のリストへ追記する」という意味だ。リデューサーがないキーは、更新のたびに上書きされる。
ソラ
弟子・ソラリデューサーって？
リク
先生・リク単純な関数だ。第1引数に現在のステート、第2引数に書き込まれる値を受け取って、マージした次のステートを返す。一番単純なのは「次の値をリストに追加して返す」関数。次にchatbotノード（作業の単位＝関数）を追加する。

🏨 たとえ話：宿帳は線で消さず追記する

リデューサーadd_messagesは「宿帳の書き方ルール」です。お客さまが新しく何か言うたび、前の記録を消しゴムで消して書き直すのではなく、次の行に書き足す。だから過去のやり取りがちゃんと積み重なっていきます。ルールが無い項目は、新しい内容で上書きされてしまいます。

② chatbotノードを追加する

↓ このコードは、現在のメッセージをLLMに渡して回答を得るノードを定義し、グラフに追加します。

Python：chatbotノードの定義と追加
# Python
# このコードがやること: 現在のメッセージをLLMに渡して回答を得るノードを定義し、グラフに追加する。
from langchain_openai import ChatOpenAI

model = ChatOpenAI()

def chatbot(state: State):
    answer = model.invoke(state["messages"])
    return {"messages": [answer]}  # add_messages により履歴に追記される

# 第1引数はノードの一意の名前、第2引数は実行する関数
builder.add_node("chatbot", chatbot)

③④ エッジを追加してコンパイルする

↓ このコードは、START→chatbot→END とつなぎ、グラフを実行可能オブジェクトにコンパイルします。

Python：エッジ接続とコンパイル
# Python
# このコードがやること: START→chatbot→END とつなぎ、グラフを実行可能オブジェクトにコンパイルする。
builder.add_edge(START, 'chatbot')   # どこから始めるか
builder.add_edge('chatbot', END)     # どこで終わるか（省略可）

graph = builder.compile()  # invoke() や stream() で呼べるようになる
リク
先生・リクgraph.get_graph().draw_mermaid_png()でグラフを可視化できる。実行はstream()でできるよ。

実行してみる

↓ このコードは「hi!」を入力してグラフを実行し、各ステップの結果をストリーム表示します。

リク
先生・リク入力が、さっき定義したStateと同じ形（messagesキーにメッセージのリスト）になっている点に注目。stream()は各ステップ後にステート全体をストリーミングする。

✅ この項のまとめ

  • グラフ作りは「ステート定義 → ノード追加 → エッジ接続 → コンパイル」の順。
  • ステートは「形（スキーマ）」＋「更新方法＝リデューサー」。add_messagesは追記。
  • ノードは「現在のステートを受け取り、更新を返す関数」。
  • 入力もステートと同じ形。stream()は各ステップ後にステート全体を返す。
4.4

StateGraphにメモリを追加する

チェックポインタとスレッドで記憶させる

4.5.1 メッセージをトリミングする

リク
先生・リクLLMにはコンテキストウィンドウの上限がある。最終プロンプトがそれを超えると、拒否されるか切り捨てられる。情報が多すぎると注意が散ってハルシネーションも起きる。だから履歴から渡すメッセージ数を制限する。trim_messages関数を使う。

↓ このコードは、メッセージリストを末尾(last)から最大65トークン分だけ残すようにトリミングします。

Python：trim_messages で履歴を切り詰める
# Python
# このコードがやること: メッセージリストを、末尾(last)から最大65トークン分だけ残すようトリミングする。
from langchain_core.messages import AIMessage, SystemMessage, HumanMessage, trim_messages
from langchain_openai import ChatOpenAI

trimmer = trim_messages(
    max_tokens=65,
    strategy="last",                              # 末尾（最新）を優先して残す
    token_counter=ChatOpenAI(model="gpt-4o-mini"),# このモデルのトークナイザで数える
    include_system=True,                          # システムメッセージは必ず残す
    allow_partial=False,                          # メッセージの途中で切らない
    start_on="human",                             # 人間のメッセージから始まるようにする
)

messages = [
    SystemMessage(content="あなたは優秀なアシスタントです"),
    HumanMessage(content="こんにちは！ 私はボブです"),
    AIMessage(content="こんにちは！"),
    HumanMessage(content="バニラアイスが好きです"),
    AIMessage(content="いいですね"),
    HumanMessage(content="2 + 2 は？"),
    AIMessage(content="4"),
    HumanMessage(content="ありがとう"),
    AIMessage(content="どういたしまして！"),
    HumanMessage(content="楽しんでる？"),
    AIMessage(content="はい！"),
]

trimmer.invoke(messages)

パラメータのポイント

パラメータ意味
strategy="last"リスト末尾（最新）を優先して残す（firstなら古い方を優先）。
token_counter=…モデルを渡して、そのトークナイザで文章量を計測する。
include_system=Trueシステムメッセージ（役割の指示）は必ず残す。
allow_partial=False最後のメッセージの途中切りを禁止（超えるなら丸ごと削除）。
start_on="human"対応する人間のメッセージなしにAIメッセージだけ残る状況を防ぐ。

🟣 なぜトリミングが必要か

  • 最終プロンプトがコンテキストウィンドウを超えると、モデルが拒否するか途中で切り捨ててしまうから。
  • 情報量が多すぎると注意が散り、ハルシネーション（もっともらしい嘘）を起こしやすくなるから。
  • だから最新のメッセージを優先して残す（strategy="last"）のが実用的。

🏨 たとえ話：分厚い宿帳から「直近のページ」だけ渡す

宿帳が分厚くなりすぎると、スタッフの机（コンテキストウィンドウ）に乗りきりません。乗りきらない書類は読めず、量が多すぎると要点を見失って勘違い（ハルシネーション）も起きる。だから店主は直近のページ（最新の会話）を優先して渡し、宿のルール書き（システムメッセージ）は必ず添える。途中で切れた半端なページは渡さない――これがトリミングです。

4.5.2 メッセージをフィルタリングする

リク
先生・リク履歴が増えると、いろんなメッセージタイプ・サブチェーン・モデルが混ざる。filter_messagesで、タイプ・ID・名前を基準に絞り込める。

↓ このコードは、メッセージのうち人間(human)のメッセージだけを抽出します。名前で除外したり、タイプ指定＋ID除外もできます。

Python：filter_messages で絞り込む
# Python
# このコードがやること: メッセージのうち、人間(human)のメッセージだけを抽出する。
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, filter_messages

messages = [
    SystemMessage("you are a good assistant", id="1"),
    HumanMessage("example input", id="2", name="example_user"),
    AIMessage("example output", id="3", name="example_assistant"),
    HumanMessage("real input", id="4", name="bob"),
    AIMessage("real output", id="5", name="alice"),
]

filter_messages(messages, include_types="human")
# → 人間のメッセージ（id=2, id=4）だけが返る

# 特定の名前を除外する
filter_messages(messages, exclude_names=["example_user", "example_assistant"])

# タイプを指定し、特定のIDを除外する
filter_messages(messages, include_types=[HumanMessage, AIMessage], exclude_ids=["3"])
リク
先生・リクfilter_messagesは命令的にも宣言的にも使えるから、チェーン内で組み合わせられる（chain = filter_ | model）。

🏨 たとえ話：宿帳から「お客さまの発言だけ」を抜き出す

宿帳には、お客さまの言葉・スタッフの返事・お試しの記入見本などが混ざっています。フィルタリングは「お客さまの発言だけ抜き出す」「記入見本の行は除く」のように、種類・記入者の名前・行番号(ID)で必要な記録だけを選び出すこと。狙った情報だけを机に並べられます。

4.5.3 連続するメッセージをマージする

リク
先生・リク一部のモデル（Anthropicなど）は、同じ種類のメッセージが連続する入力を受け付けない。merge_message_runsで、連続する同種メッセージをマージできる。

↓ このコードは、連続する同じ種類のメッセージ（System2連続・Human2連続・AI2連続）を、それぞれ1つにマージします。

Python：merge_message_runs で連続を結合
# Python
# このコードがやること: 連続する同じ種類のメッセージ（System2連続、Human2連続、AI2連続）を1つにマージする。
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, merge_message_runs

messages = [
    SystemMessage("あなたは優秀なアシスタントです。"),
    SystemMessage("あなたは常にジョークで返答します。"),
    HumanMessage([{"type": "text", "text": "なぜlangchainと呼ばれているのか不思議です"}]),
    HumanMessage("それと、ハリソンはいったい誰を追いかけているの？"),
    AIMessage("「WordRope」や「SentenceString」では響きがイマイチだったのでしょうね！"),
    AIMessage("きっとオフィスで最後の一杯のコーヒーを追いかけているのでしょう！"),
]

merge_message_runs(messages)
リク
先生・リクマージで、両方が文字列なら改行で連結される。片方がコンテンツブロックのリストなら、マージ後もリストになる。これもchain = merger | modelのように組み合わせられる。

🏨 たとえ話：同じ人の連続メモを1枚にまとめる

宿帳に「スタッフへの指示」が2行続けて書いてあると、一部の几帳面なスタッフ（一部のモデル）は「同じ種類が連続している」と混乱します。そこでマージは、連続する同じ種類のメモを1枚にまとめる整理術。文字どうしなら改行でつなぎ、片方が箱入りメモ（リスト）ならまとめても箱入りのまま――きれいに渡せます。

✅ 4.5 要するに ／ この項のまとめ

  • 要するに：LLMはステートレスなのでメモリを外付けする。LangGraphのステート・ノード・エッジでグラフを組み、チェックポインタで永続化、スレッドでユーザーごとに分離。履歴はトリミング（件数制限）・フィルタリング（種類で絞る）・マージ（連続を結合）で整える。
  • LLMはステートレス。履歴をメッセージのリストとして保存しプロンプトに含めるとメモリになる。素朴な保存は本番で課題（アトミック更新・永続化・件数制御）。
  • LangGraph：マルチアクター・マルチステップ・ステートフルなグラフ。3要素はステート（共有データ）・ノード（処理関数）・エッジ（接続）。
  • ステートは更新方法をリデューサー（add_messagesは追記）で定義する。
  • チェックポインタ（InMemory/SQLite/Postgres）で永続化。スレッド（thread_id）でユーザーごとに分離。get_state/update_stateで確認・編集。
  • 履歴の修正：trim_messages（件数/トークン制限）・filter_messages（タイプ・ID・名前で絞る）・merge_message_runs（連続する同種を結合）。

自分の言葉で答えてみよう

この章を読み終わったあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問ステートレスとメモリ

LLMが「ステートレス」とはどういう意味ですか。それでもチャットボットが過去の会話を覚えているように見えるのはなぜですか。

✅ 解答例
ステートレスとは、LLMの各回のプロンプト入力が独立していて、モデルが以前のプロンプトやレスポンスを記憶していないという意味。つまりLLM自身は前の会話を覚えていない。それでも覚えているように見えるのは、アプリ側でメモリシステムを外付けして、過去の会話をメッセージのリストとして保存し、毎回その履歴を最終プロンプトに含めてLLMに渡しているから。LLMは渡された履歴を「文脈」として読んで、覚えているかのように答える。
📝 採点ポイント
□ ステートレス＝各入力が独立、前を記憶しない、に触れている ／ □ アプリ側で履歴を保存しプロンプトに含めて渡す、に触れている ／ □ LLM自身が覚えているわけではない、に触れている
第2問グラフの3要素

LangGraphのグラフを構成する3要素（ステート・ノード・エッジ）を、それぞれ説明してください。

✅ 解答例
ステートは、アプリが外から受け取り、実行中に変更・生成する共有データ（例：messagesのリスト）。更新方法はリデューサー関数で定義する。ノードは、各ステップを表す関数で、現在のステートを入力に受け取り、ステートを更新する値を返す（例：LLMを呼ぶchatbotノード）。エッジは、ノード間の接続で、最初から最後までの経路を決める。固定経路（Bの後は必ずD）や、関数で次を判定する条件付き経路を設定できる。
📝 採点ポイント
□ ステート＝実行中に変更・生成される共有データ、に触れている ／ □ ノード＝現在のステートを受け取り更新する関数、に触れている ／ □ エッジ＝ノード間の接続・経路、に触れている
第3問チェックポインタとスレッド

チェックポインタと「スレッド（thread_id）」は、それぞれ何のためにありますか。

✅ 解答例
チェックポインタは、各ステップ終了時にグラフのステートを保存（永続化）するストレージアダプター。これにより、次の呼び出しが完全な初期状態から始まらず、最新のステートを取得して新しい入力とマージして実行できる（InMemory/SQLite/Postgresなどがある）。スレッド（thread_id）は、そのチャットがどの会話履歴に属するかを示す識別子。スレッドを分けることで、複数のユーザーが互いに干渉しない独立した会話を持てる。
📝 採点ポイント
□ チェックポインタ＝ステートを永続化するアダプター、に触れている ／ □ 次の呼び出しで最新ステートを取得しマージする、に触れている ／ □ スレッド＝会話を識別し、ユーザーごとに分離する、に触れている
第4問なぜ履歴を整えるのか

チャット履歴が長くなったとき、なぜトリミング（メッセージの制限）が必要なのですか。

✅ 解答例
LLMにはコンテキストウィンドウ（受け取れるトークン数の上限）があり、最終プロンプトがそれを超えるとモデルが拒否するか途中で切り捨ててしまうから。また、情報量が多すぎるプロンプトはモデルの注意を散らし、ハルシネーションを引き起こす可能性もある。だから履歴からプロンプトに渡すメッセージ数を制限する。実用上は、最新のメッセージを優先して残せばよい（trim_messages の strategy="last"）。
📝 採点ポイント
□ コンテキストウィンドウを超えると拒否/切り捨てられる、に触れている ／ □ 情報過多で注意が散りハルシネーションを起こす、に触れている ／ □ 最新のメッセージを優先して残す、に触れている
第5問履歴の3つの修正法

チャット履歴を修正する3つの方法（トリミング・フィルタリング・マージ）を、それぞれ何をするかを説明してください。

✅ 解答例
トリミング（trim_messages）は、コンテキストウィンドウに収まるよう、保持するメッセージ数やトークン数を制限する（末尾＝最新を優先するなど）。フィルタリング（filter_messages）は、メッセージのタイプ（human/aiなど）・ID・名前を基準に、必要なメッセージだけを抽出したり不要なものを除外したりする。マージ（merge_message_runs）は、同じ種類のメッセージが連続する場合に1つにまとめる（一部のモデルが連続する同種メッセージを受け付けないため）。
📝 採点ポイント
□ トリミング＝件数/トークン数を制限、に触れている ／ □ フィルタリング＝タイプ・ID・名前で絞る、に触れている ／ □ マージ＝連続する同種メッセージを結合、に触れている
🌱

メモリ付きチャットボットを動かす

本章のStateGraphを写経し、チェックポインタを付けて、同じスレッドで「名前を伝える→名前を聞く」を試す。覚えていることを確認。

🔀

スレッドを分ける

thread_idを "1" と "2" で分けて、片方で伝えた名前がもう片方では通じないことを確かめる。会話の分離を体感。

グラフを可視化する

Jupyterでgraph.get_graph().draw_mermaid_png()を実行し、START→chatbot→END の図を見てみる。

✂️

トリミングで遊ぶ

max_tokensを小さくして、どのメッセージが残るかを観察し、strategyをfirst/lastで切り替えてみる。

📘

LangGraph公式チュートリアル

「LangGraph の Quickstart」（公式ドキュメント）で、メモリ付きチャットボットの作り方を確認する。

🗄️

永続化アダプターを切り替える

InMemorySaverをSqliteSaverに変えて、アプリを再起動しても会話が残ることを確認する。
