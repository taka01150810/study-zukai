7.1

リフレクションアーキテクチャ

書く→批評する→直す

要するに：文章を作る指示文と、批評する指示文を交互に繰り返すループです。1回で完成させず、何度も直します。

リク
リクリフレクションは、生成のための指示文と、修正や振り返りのための指示文を、交互に繰り返すループだ。実際の制作の進め方をそのまま形にしている——この本の文章も、著者・査読者・編集者が何度もやり取りして仕上げたものだよ。
ソラ
ソラ自己批評、ですね。
リク
リクそう。人間の思考のうち、反射的・本能的なものをシステム1、理性的で見直しをするものをシステム2と捉えられる（ダニエル・カーネマンの『ファスト＆スロー』だね）。自己批評を正しく使うと、LLMアプリをシステム2に近い振る舞いに寄せられる。例として、3段落のエッセイを書く機能を作ろう。

generate（生成）

草稿を書きます。2回目以降は、受け取った批評をふまえて書き直します。

⇄

reflect（批評）

教師の立場で、長さ・内容の深さ・文体などの改善点を出します。

↻ 3往復したら終了。最後は必ず generate で終わる（受け取った指摘に全部対応するため）
コードを見る（1行ずつ説明つき）
# 型の道具、メッセージの入れ物、モデル、グラフの部品を読み込む。
from typing import Annotated, TypedDict
from langchain_core.messages import AIMessage, BaseMessage, HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

# モデルの呼び出し口を作る。生成にも批評にも同じモデルを使う。
model = ChatOpenAI()

# 持ち回るデータの形を決める。やり取りが積み上がっていく。
class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

# 書く役への前提の指示。「批評があれば直す」と書いておくのが要点。
generate_prompt = SystemMessage(
    "あなたは優れた三段落のエッセイを執筆するエッセイアシスタントです。"
    "ユーザーのリクエストに対して最高のエッセイを生成してください。"
    "ユーザーから批評があった場合は、前回の試作の修正版を作成してください。")

# 書く処理：前提の指示と、これまでのやり取りを渡して文章を書かせる。
def generate(state: State) -> State:
    answer = model.invoke([generate_prompt] + state["messages"])
    return {"messages": [answer]}

# 批評する役への前提の指示。何を見て指摘するかを具体的に書いておく。
reflection_prompt = SystemMessage(
    "あなたはエッセイの提出物を採点する教師です。批評と改善のためのアドバイスをしてください。"
    "長さ、内容の深さ、文体などを含む詳細な改善項目を提案してください。")

# 批評する処理：発言の役割を入れ替えてから渡すのが最大の工夫。
def reflect(state: State) -> State:
    # モデルの返答は利用者の発言に、利用者の発言はモデルの返答に、と入れ替える対応表を作る。
    cls_map = {AIMessage: HumanMessage, HumanMessage: AIMessage}
    # 前提の指示と、最初の依頼文はそのまま。それ以降を入れ替える。
    # これでモデルは「他人が書いた文章を採点している」と受け取り、遠慮なく指摘できる。
    translated = [reflection_prompt, state["messages"][0]] + [
        cls_map[msg.__class__](content=msg.content) for msg in state["messages"][1:]
    ]
    answer = model.invoke(translated)
    # 出てきた批評を「利用者からの意見」の形にして履歴に足す。
    # こうすると次の generate は、それを直すべき指摘として受け取る。
    return {"messages": [HumanMessage(content=answer.content)]}

# 続けるか終わるかの判定。1往復で2件ずつ増えるので、6件を超えたら3往復したことになる。
def should_continue(state: State):
    if len(state["messages"]) > 6:
        return END
    else:
        return "reflect"

# 組み立て役を作り、2つの処理を登録する。
builder = StateGraph(State)
builder.add_node("generate", generate)
builder.add_node("reflect", reflect)

# 入口からは、まず書く処理へ。
builder.add_edge(START, "generate")

# 書いたあとは、判定によって「批評へ進む」か「終了する」かが決まる。
builder.add_conditional_edges("generate", should_continue)

# 批評したあとは、必ず書く処理へ戻る。ここでループが閉じる。
builder.add_edge("reflect", "generate")

# 実行できる形に仕上げる。
graph = builder.compile()

なぜ役割を入れ替えるのか

ソラ
ソラreflect で、メッセージの役割を入れ替えているのはなぜですか？
リク
リク鋭い。reflect の処理は、LLMに「利用者が書いたエッセイを採点している」と受け取らせている。逆に generate の処理は、その批評を「利用者から来た」と受け取らせている。これは、会話向けに調整された多くのLLMが「人間の発言とAIの返答が交互に並ぶ形」で学習されているからだ。同じ側の発言が続くと性能が落ちることがあるから、この工夫で役割を入れ替えているんだ。

🔎 具体例：3往復で文章がどう変わるか

1回目の草稿：「読書は大切です。知識が増えます。だから読書をしましょう。」（各段落2文、内容が薄い）

1回目の批評：「各段落が短すぎます。具体的な例や数値がありません。3段落それぞれの役割（導入・論拠・結論）が不明瞭です。」

2回目の草稿：批評の3点に対応して、段落ごとの役割を明示し、具体例を追加した文章になります。

2回目の批評：「例は良くなりました。ただし文体が単調で、接続の言葉が繰り返されています。」→3回目の草稿でそこが直ります。指摘のたびに別の観点が出るので、回を重ねるほど細かい部分が整っていきます。

止め方と、2つの応用

リク
リクこの例では生成と批評の回数があらかじめ決まっていて、最後に generate を実行して終わる——受け取った指摘にすべて対応するためだ。他の止め方もある——批評の処理が終わりを判断して、指摘がなくなったら止める、とかね。
ソラ
ソラ自己批評で、出力が良くなるんですね。

LangGraphのサブグラフ

グラフの中にグラフを入れる

要するに：サブグラフは「別のグラフの一部として使われるグラフ」です。マルチエージェントの土台になります。

リク
リクマルチエージェントの前に、それを可能にする考え方——サブグラフを学ぼう。
👥

使い道① マルチエージェント

1体のエージェントを丸ごと1つの処理として、大きなグラフに組み込めます。

♻️

使い道② 使い回し

いくつかの処理のまとまりを、複数のグラフで共通して使えます。

🤝

使い道③ 分担して開発

受け取る形と返す形さえ決めておけば、中身を知らなくても外側を作れます。複数チームで並行して作業できます。

組み込み方は2つあります。①そのまま処理として置く（親と子でデータの項目名を共有し、変換がいらないとき）、②変換する関数を挟む（形が違って、前後で入れ替えが必要なとき）。

7.2.1 サブグラフを直接呼び出す

要するに：親と子が同じ項目名を持っていれば、そのまま1つの処理として置けます。その共通の項目名が、両者のやり取りの通り道になります。

コードを見る（1行ずつ説明つき）
# グラフの部品と、形を決める道具を読み込む。
from langgraph.graph import START, StateGraph
from typing import TypedDict

# 外側のグラフが持ち回るデータの形。項目は foo の1つだけ。
class State(TypedDict):
    foo: str  # この名前を、内側のグラフとそろえておく

# 内側のグラフが持ち回るデータの形。foo は外側と共通、bar は内側だけのもの。
class SubgraphState(TypedDict):
    foo: str  # 外側と名前が同じなので、ここを通じて値が行き来する
    bar: str

# 内側の処理。共通の項目 foo を書き換えることで、外側に結果を渡せる。
def subgraph_node(state: SubgraphState):
    return {"foo": state["foo"] + "bar"}

# 内側のグラフを組み立てて、実行できる形に仕上げる。
subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node(subgraph_node)
# （ここに入口や出口のつなぎが入る）
subgraph = subgraph_builder.compile()

# 外側のグラフを組み立てる。
builder = StateGraph(State)

# 仕上げ済みの内側のグラフを、そのまま1つの処理として登録する。
# 外側から見ると、ふつうの処理を1つ足したのと変わらない。
builder.add_node("subgraph", subgraph)
# （ここに入口や出口のつなぎが入る）
graph = builder.compile()

# 実行すると、外側の foo が内側に渡り、書き換えられて戻ってくる。
print(graph.invoke({"foo": "hello"}))
# --- 実行結果 ---
# {'foo': 'hellobar'}   ← 内側だけの項目 bar は外側には出てこない
リク
リク共通の項目名以外を渡そうとしても無視される。だから、やり取りしたい値は名前をそろえておく必要がある。

7.2.2 関数でサブグラフを呼び出す

要するに：親と子でまったく違う形にしたいときは、間に変換する関数を置きます。行きと帰りで項目名を入れ替えます。

コードを見る（1行ずつ説明つき）
# 外側のグラフが持ち回るデータの形。項目は foo。
class State(TypedDict):
    foo: str

# 内側のグラフの形。bar と baz で、外側とは名前がまったく違う。
class SubgraphState(TypedDict):
    bar: str  # 外側とは共有していない
    baz: str

# 内側の処理。内側の名前だけを使って動く。外側のことは知らない。
def subgraph_node(state: SubgraphState):
    return {"bar": state["bar"] + "baz"}

# 内側のグラフを組み立てて仕上げる。
subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node(subgraph_node)
# （ここに入口や出口のつなぎが入る）
subgraph = subgraph_builder.compile()

# 変換を担当する処理。外側と内側の名前の違いをここで吸収する。
def node(state: State):
    # 行き：外側の foo の値を、内側が期待する bar という名前に付け替えて渡す。
    response = subgraph.invoke({"bar": state["foo"]})
    # 帰り：内側が返した bar の値を、外側の foo という名前に戻す。
    return {"foo": response["bar"]}

# 外側のグラフには、内側のグラフではなく「変換する処理」のほうを登録する。
builder = StateGraph(State)
builder.add_node(node)
# （ここに入口や出口のつなぎが入る）
graph = builder.compile()

# 実行すると、名前が違っていても正しく値が行き来する。
print(graph.invoke({"foo": "hello"}))
# --- 実行結果 ---
# {'foo': 'hellobaz'}
そのまま処理として置く変換する関数を挟む
条件親と子で項目名が共通親と子で形が違う
登録するもの仕上げ済みのサブグラフ変換を行う関数
変換の手間不要行きと帰りで自分で書く
向く場面同じチームで設計をそろえたとき別々に作った部品をつなぐとき

マルチエージェントアーキテクチャ

1体で無理なら、分ける

要するに：機能が多すぎる・情報が複雑すぎる・分野ごとの専門性が要る——こうした場面では、アプリを複数の小さな独立したエージェントに分けます。

リク
リクエージェントが大きく複雑になると問題が出る——①使える機能が多すぎて次に使うものを間違える（6章で対処したね）、②扱う情報が複雑すぎて1体では追えない（指示文の長さや情報量がモデルの力を超える）。それに、計画・調査・計算みたいに分野ごとに専門の仕組みを使いたいこともある。
ソラ
ソラ1体じゃ無理なら、分けるんですね。
リク
リクそう。アプリを複数の小さな独立したエージェントに分けて、組み合わせる。各エージェントは、指示文＋LLM呼び出しのような単純なものから、6章のエージェントのような複雑なものまでありうる。つなぎ方は4つある。
🕸️

ネットワーク

すべてのエージェントが互いにやり取りできます。次に誰を動かすかも各自が決められます。自由ですが、制御は難しくなります。

7.3.1 スーパーバイザーアーキテクチャ

要するに：各エージェントを処理として登録し、さらに「次に誰を呼ぶか」を決める管理役を置きます。条件付きエッジで振り分けます。

supervisor（管理役）

これまでのやり取りを見て、次に動かす担当か、終了かを決めます。

⇄

researcher（調査担当）

調べる仕事を担当します。終わったら管理役に戻ります。

⇄

coder（コード担当）

コードを書く仕事を担当します。終わったら管理役に戻ります。

↻ 担当が終わるたびに管理役へ戻り、続けるか終わるかを判断し直す

まず管理役を作る

コードを見る（1行ずつ説明つき）
# 選択肢を限定する型、モデル、形を決める道具を読み込む。
from typing import Literal
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

# 管理役に返させる答えの形を決める。next にはこの3つ以外を入れられない。
# FINISH は「もう終わってよい」という合図。
class SupervisorDecision(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

# 判断がぶれないよう、ばらつきを0にしたモデルを用意する。
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 上で決めた形を必ず守らせる設定に変える。
model = model.with_structured_output(SupervisorDecision)

# 担当の一覧。名前がそのまま指示文に埋め込まれるので、意味の分かる名前にする。
agents = ["researcher", "coder"]

# やり取りの前に置く指示。管理役としての役割と、終了の合図を説明する。
system_prompt_part_1 = f"""あなたは、以下の作業者間の会話を管理するスーパーバイザーです: {agents}。
ユーザーのリクエストに基づき、次に行う作業者を指示してください。それぞれの作業者はタスクを実行し、
その結果とステータスを返します。作業が完了したら「FINISH」と返信してください。"""

# やり取りの後ろに置く指示。ここで改めて選ばせることで、判断がぶれにくくなる。
system_prompt_part_2 = f"""上記の会話を踏まえて、次に行動すべき作業者は誰ですか？
それとも終了しますか？ 次から選んでください: {', '.join(agents)}, FINISH"""

# 管理役の処理：前の指示・これまでのやり取り・後ろの指示、の順に並べて渡す。
def supervisor(state):
    messages = [
        ("system", system_prompt_part_1),
        *state["messages"],
        ("system", system_prompt_part_2)
    ]
    # 決められた形でしか答えられないので、必ず3つのうちどれかが返る。
    return model.invoke(messages)
ソラ
ソラエージェントの名前って大事ですか？
リク
リクすごく大事だ。担当の名前は、意味が分かって互いに区別できる必要がある。agent_1、agent_2 だと、LLMはどの担当がどの仕事に向いているか判断できない。必要なら各担当の役割や特徴を指示文に足すといい。

🟣 なぜ名前が結果を左右するのか

  • 管理役に渡されるのは名前と一覧だけで、中身の実装は見えていないから。名前が唯一の手がかりになります。
  • LLMは言葉の意味から判断するので、researcher なら「調べる仕事」と結びつけられますが、agent_1 では何も手がかりがありません。

担当をつないでグラフにする

コードを見る（1行ずつ説明つき）
# 選択肢を限定する型、モデル、グラフの部品を読み込む。
from typing import Literal
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, MessagesState, START

# 各担当が使うモデルの呼び出し口を作る。
model = ChatOpenAI()

# 持ち回るデータの形。next には管理役が決めた行き先が入る。
class AgentState(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

# 調査担当の処理。調べた結果を、共通のやり取りの記録に足す。
def researcher(state: AgentState):
    response = model.invoke("～省略～")
    return {"messages": [response]}

# コード担当の処理。書いた結果を、同じ記録に足す。
# 同じ記録を共有しているので、互いの作業内容を見られる。
def coder(state: AgentState):
    response = model.invoke("～省略～")
    return {"messages": [response]}

# 組み立て役を作り、管理役と2つの担当を登録する。
builder = StateGraph(AgentState)
builder.add_node(supervisor)
builder.add_node(researcher)
builder.add_node(coder)

# 入口からは、まず管理役へ進む。
builder.add_edge(START, "supervisor")

# 管理役が決めた next の値が、そのまま次に進む処理の名前になる。
# FINISH が返れば終了、担当名が返ればその担当へ進む。
builder.add_conditional_edges("supervisor", lambda state: state["next"])

# どちらの担当も、仕事を終えたら必ず管理役へ戻る。
builder.add_edge("researcher", "supervisor")
builder.add_edge("coder", "supervisor")

# 実行できる形に仕上げる。
supervisor = builder.compile()
リク
リクこの例では、進み具合が全部 messages の記録に残るから、調査担当とコード担当は互いの作業を確認できる。別のやり方もある——担当自体を1つのグラフにして内側だけの記録を持たせて、作業の要点だけを外に出す、とかね。担当が終わったら、また管理役に戻して、続けるか・誰に任せるかを決める。担当自身に「出力を利用者に返すか」を判断させることもできる（調査担当と管理役の間のつなぎを、調査担当が書き換えた項目を読む条件付きエッジに置き換える）。
ソラ
ソラ6章のルーターに似てますけど、エージェント同士が管理役を通して何度もやり取りするんですね。

🔎 具体例：1つの依頼が処理される流れ

依頼：「2023年の日本の家計貯蓄率を調べて、それをグラフにするPythonコードを書いて」

①管理役 →「researcher」を指名。②調査担当が数値を調べて記録に残す。③管理役に戻る →「coder」を指名。④コード担当が、記録に残った数値を読んでグラフを描くコードを書く。⑤管理役に戻る →「FINISH」。ここで終了。

管理役は3回呼ばれています。何回呼ばれるかは依頼の内容によって変わります。

🟢 この項のまとめ

  • リフレクション：書く処理と批評する処理のループ。役割を入れ替えて、同じ側の発言が続くのを避ける。回数固定や批評側の終了判断で止める。外部の道具で裏付けると効果的。
  • サブグラフ：別のグラフの中で使うグラフ。そのまま置く（項目名を共有）か、変換する関数を挟む（形が違う）の2通り。
  • マルチエージェント：1体では扱えない複雑さや、分野ごとの専門性に対応。構成はネットワーク・スーパーバイザー・階層的・カスタム。
  • スーパーバイザー：管理役が次に呼ぶ担当を決まった形で決め、条件付きエッジで振り分ける。担当の名前は区別しやすくする。

章末の理解度チェック（全5問）

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問リフレクション

❓ リフレクションアーキテクチャとは何ですか。なぜ出力の質が上がるのかも含めて説明してください。

✅ 解答例
リフレクションは、生成のための指示文と、批評・振り返りのための指示文を交互に繰り返すループ。エッセイの例なら、generateの処理が草稿を書き、reflectの処理が教師の立場で批評し、それをふまえてgenerateが直す、を繰り返す。これは、本の文章が著者・査読者・編集者のやり取りで仕上がるのと同じ進め方。一発で完璧な出力を出すのではなく、自己批評で何度も磨き直すので質が上がる。人間の思考でいう、じっくり考える側（システム2）に近い振る舞いになる。
📝 採点ポイント
□ 生成と批評を交互に繰り返すループ、に触れている
□ 実際の制作過程と同じ進め方であることに触れている
□ 自己批評で質が上がる、に触れている
第2問役割の入れ替え

❓ リフレクションの実装で、reflect の処理がメッセージの役割（モデル／利用者）を入れ替えているのはなぜですか。

✅ 解答例
会話向けに調整された多くのLLMは「人間の発言とAIの返答が交互に並ぶ形」で学習されているため、同じ側の発言が続くと性能が落ちることがある。そこで reflect の処理では役割を入れ替えて、LLMに「自分の出力を、他人が書いた提出物として採点している」と受け取らせる。逆に generate の処理では、その批評を「利用者から来た意見」として扱う。この工夫で性能の低下を防いでいる。
📝 採点ポイント
□ LLMは交互の形で学習され、同じ側が続くと性能が落ちる、に触れている
□ 役割を入れ替えて自分の出力を他人の提出物として批評させる、に触れている
□ 性能低下を防ぐため、に触れている
第3問サブグラフの2つの組み込み方

❓ サブグラフを親グラフに組み込む2つの方法を、どんなときに使うかを含めて説明してください。

✅ 解答例
①そのまま1つの処理として置く方法：親グラフとサブグラフが持ち回るデータの項目名を共有しているときに使う。共通の項目名がやり取りの通り道になり、変換がいらない。②サブグラフを呼ぶ関数を1つの処理として置く方法：親とサブグラフの形が違うときに使う。その関数の中で、親のデータをサブグラフ用の名前に付け替えて渡し、返ってきた値を親用の名前に戻す。形が違って変換が必要な場合に便利。
📝 採点ポイント
□ そのまま置く＝項目名を共有、変換不要、に触れている
□ 関数で呼ぶ＝形が違い変換が必要、に触れている
□ それぞれの使い分けに触れている
第4問マルチエージェントの構成

❓ マルチエージェントの4つの構成（ネットワーク・スーパーバイザー・階層的・カスタム）のうち、スーパーバイザーとは何ですか。

✅ 解答例
スーパーバイザーは、各エージェントが1体の管理役とだけやり取りする構成。管理役が「次にどのエージェント（複数可）を呼ぶか」を決める。ネットワーク（全員が互いにやり取り）よりも制御しやすく、階層的（管理役の上にさらに管理役）よりも単純で、できることと使いやすさのつり合いが良い。実装では、管理役が決まった形で次の担当（またはFINISH）を決め、条件付きエッジでその担当へ振り分ける。
📝 採点ポイント
□ 各エージェントが管理役とだけやり取りする、に触れている
□ 管理役が次に呼ぶエージェントを決める、に触れている
□ できることと使いやすさのつり合いが良い、に触れている
第5問いつ拡張を使うか

❓ リフレクションやマルチエージェントは強力ですが、新しいエージェントを作るときにいきなり使うべきではないと言われます。なぜですか。

✅ 解答例
これらの拡張は構造を複雑にし、待ち時間や費用、不具合を追う難しさを増やすから。リフレクションは生成と批評を繰り返すぶん待ち時間が増え、マルチエージェントは複数のエージェントの連携で複雑さが増す。多くの場合、6章で説明した単純なエージェントの形で十分な性能が出る。だから、まず単純なものから始めて、それで足りないと分かったときに初めて拡張に手を伸ばすのが最善（本書を貫く「まず単純に」の原則）。
📝 採点ポイント
□ 拡張は複雑さ・待ち時間・費用を増やす、に触れている
□ 多くの場合は単純な形で十分、に触れている
□ まず単純から始め、足りないときに拡張する、に触れている
