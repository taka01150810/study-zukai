この章のあらすじ・要するに・なぜ必要か

基本エージェントを2方向に拡張する

あらすじ：「エージェントって、自分の答えを見直したりしないんですか？」とソラ。リク先輩は「させられるよ。それが“リフレクション”だ」と答えます。この章では6章の基本エージェントを2方向に拡張します。①リフレクション＝LLMに自分の出力を振り返らせて批評させ、修正を繰り返す（著者と編集者のやり取りのよう）。②マルチエージェント＝1体では難しい問題を、複数の専門エージェントの連携で解く。土台となるLangGraphのサブグラフも学び、最後に実用的なスーパーバイザーアーキテクチャを実装します。

🎯 要するに

基本エージェントは2つに拡張できます。リフレクションは、生成→批評→修正のループで、LLMを「じっくり考える（システム2）」ように振る舞わせます。マルチエージェントは、アプリを複数の小さな独立エージェントに分割して連携させます。その実装の土台がサブグラフ（別のグラフの中で使うグラフ）。代表的な構成が、スーパーバイザーが「次にどのエージェントを動かすか」を決めるスーパーバイザーアーキテクチャです。

🗞️ たとえ話：新聞社の編集部

この章はぜんぶ新聞社の編集部でたとえます。リフレクション＝1人の記者が「自分で原稿を書いて→自分で校正して→直す」を繰り返すこと。マルチエージェント＝政治記者・経済記者・スポーツ記者など専門の記者を集めて、編集長（スーパーバイザー）が「次は誰に取材させるか」をさばくこと。サブグラフ＝編集部の中にある「写真部」のような専門チームです。

📌 なぜこれが必要か / これを知ったらできること

  • なぜ学ぶ価値があるか：LLMは一発で完璧な出力を出せないことが多く、自己批評で品質を上げられるから。
  • エージェントにツールやコンテキストを詰め込みすぎると、1体では処理しきれなくなるから。
  • 計画・調査・数学など分野ごとに専門サブシステムを使いたい場面があるから。
  • できるようになること：リフレクション（生成→批評→修正）を実装して出力品質を上げられる。
  • LangGraphのサブグラフを、ステート共有あり／なしの2通りで親グラフに組み込める。
  • マルチエージェントの構成（ネットワーク・スーパーバイザー・階層的・カスタム）を理解できる。
  • スーパーバイザーアーキテクチャを実装して、複数の専門エージェントを協調させられる。

7.1

リフレクションアーキテクチャ

生成と批評を交互に繰り返して、自分で原稿を磨く

要するに：リフレクションは「生成のプロンプト」と「批評・振り返りのプロンプト」を交互に繰り返すループ。一発で出すのではなく、自己批評で何度もブラッシュアップして品質を上げます。

リク
師匠・リクリフレクションは、生成のためのプロンプトと、修正や振り返りのためのプロンプトを、交互に繰り返すループだ。人間の創作プロセスを模している――この本の文章も、著者・査読者・編集者が何度もやり取りして仕上げたものだ。
ソラ
弟子・ソラ自己批評、ですね。
リク
師匠・リクそう。人間の思考のうち、反応的・本能的なものをシステム1、理性的・内省的なものをシステム2と捉えられる（ダニエル・カーネマンの『ファスト＆スロー』だね）。自己批評を正しく適用すると、LLMアプリをシステム2のような振る舞いに近づけられる。例として、3段落のエッセイを書く機能を作ろう。generate（生成）ノードと reflect（批評）ノードのループだ。

🗞️ たとえ話：原稿を磨く記者

generateノード＝原稿を書く記者、reflectノード＝それを赤入れする校正担当です。記者が初稿を出す→校正担当が「2段落目が浅い、もっと具体例を」と赤を入れる→記者が赤を反映して書き直す。これを数回くり返して締め切りまでに記事を仕上げる、その流れがリフレクションです。直感で殴り書きするシステム1ではなく、何度も推敲するシステム2の働き方です。

生成→批評のループ（しくみ）

下のサイクルが、エッセイを仕上げるリフレクションの流れです。generate（書く）と reflect（批評）を行ったり来たりし、メッセージが一定数たまったら終了します。

① generate（生成）

エッセイの草稿を書く。2回目以降は、もらった批評をふまえて修正版を書く。

記者が原稿を書く
→

② should_continue（判定）

メッセージが6件を超えた？ → 超えたらEND（終了）。まだならreflectへ。

締め切りが来たか確認
→

③ reflect（批評）

教師の立場で、長さ・内容の深さ・文体などの改善点を出す。

校正担当が赤入れ
↩ ③の批評は②を通って①に戻り、3回の「生成→批評」を終えると最後に generate して完成。

このコードは「エッセイを書く→批評する→直す」を3回くり返すループの設計図です。generate＝草稿を書く／批評をふまえ修正、reflect＝教師として批評、should_continue＝メッセージが6件を超えたら終了、を担当します。

Python ― リフレクション（エッセイ生成）のコード 
# このコードがやること: エッセイを書くリフレクションのループ。
#  generate = エッセイの草稿を書く/批評をふまえて修正する。
#  reflect  = 教師として批評と改善案を出す。
#  should_continue = メッセージが6件を超えたら終了（3回の生成→批評で終わる）。
from typing import Annotated, TypedDict
from langchain_core.messages import AIMessage, BaseMessage, HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

model = ChatOpenAI()

class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

generate_prompt = SystemMessage(
    "あなたは優れた三段落のエッセイを執筆するエッセイアシスタントです。"
    "ユーザーのリクエストに対して最高のエッセイを生成してください。"
    "ユーザーから批評があった場合は、前回の試作の修正版を作成してください。")

def generate(state: State) -> State:
    answer = model.invoke([generate_prompt] + state["messages"])
    return {"messages": [answer]}

reflection_prompt = SystemMessage(
    "あなたはエッセイの提出物を採点する教師です。批評と改善のためのアドバイスをしてください。"
    "長さ、内容の深さ、文体などを含む詳細な改善項目を提案してください。")

def reflect(state: State) -> State:
    # メッセージの役割を入れ替えて、LLMが自分の出力を「他人の提出物」として批評するようにする
    cls_map = {AIMessage: HumanMessage, HumanMessage: AIMessage}
    translated = [reflection_prompt, state["messages"][0]] + [
        cls_map[msg.__class__](content=msg.content) for msg in state["messages"][1:]
    ]
    answer = model.invoke(translated)
    # 批評を、ジェネレーターにとっての「人間のフィードバック」として扱う
    return {"messages": [HumanMessage(content=answer.content)]}

def should_continue(state: State):
    if len(state["messages"]) > 6:  # 3回繰り返し（各2メッセージ）で終了
        return END
    else:
        return "reflect"

builder = StateGraph(State)
builder.add_node("generate", generate)
builder.add_node("reflect", reflect)
builder.add_edge(START, "generate")
builder.add_conditional_edges("generate", should_continue)
builder.add_edge("reflect", "generate")

graph = builder.compile()

役割の入れ替えという“裏技”

ソラ
弟子・ソラreflect で、メッセージの役割を入れ替えているのはなぜですか？
リク
師匠・リク鋭い。reflect ノードは、LLMに「ユーザーが書いたエッセイを批評している」と思わせている。逆に generate ノードは、その批評を「ユーザーから来た」と思わせている。これは、対話調整された多くのLLMが「人間とAIのメッセージのペア」で学習されているからだ。同じ人物からの連続メッセージが多いとパフォーマンスが悪化することがあるから、この“裏技”で役割を入れ替えているんだ。
✍️

generateノードの視点

「届いた批評はユーザーからのフィードバックだ」と思って、それに応えて書き直す。

批評＝人間からの声
🔍

reflectノードの視点

「これは他人が提出したエッセイだ」と思って、教師の立場で遠慮なく赤を入れる。

自分の出力＝他人の提出物

🗞️ たとえ話：あえて立場を入れ替える

自分の書いた原稿は甘く見てしまいがち。そこで校正のときは「これは他人が書いた原稿だ」というつもりで赤を入れ、書き直すときは「読者からの要望が届いた」というつもりで応える。立場を入れ替えると、同じ人がやっても客観的に良くできる――そういう編集部の知恵です。

バリエーション（止め方・他の応用）

リク
師匠・リクこの例では生成→批評の回数があらかじめ決まっていて、最後に generate を実行して終わる――求められた修正にすべて対応するためだ。他の終了方法もある――reflect ステップが終了判断をして、コメントがなくなったらプロセスを終わらせる、とかね。
ソラ
弟子・ソラ自己批評で、出力が良くなるんですね。
リク
師匠・リクそう。バリエーションもある。①6章のエージェントにリフレクションステップを組み込んで、ユーザーへ出力を送る直前の最後のノードに置く（批評がユーザー自身から来たように見えて、介入なしに最終出力を改善できる。ただしレイテンシーは増える）。②外部情報で裏付ける――コード生成エージェントなら、リフレクションの前に生成コードをリンターやコンパイラに通して、検出されたエラーをリフレクションへの入力にする。適用できる場面ならぜひ試すといい、最終品質が上がるからね。
⏱️

止め方A：回数固定

「生成→批評を3回やったら終わり」と最初から決める。最後は generate で締める。

🛑

止め方B：批評が判断

reflect が「もう直すところなし」と判断したら終了する。

🧰

応用：外部で裏付け

コードならリンター/コンパイラに通し、出たエラーを批評の材料にする。

🔁 7.1のまとめ

  • リフレクション＝生成ノードと批評ノードのループ。LLMを内省的（システム2）に振る舞わせる。
  • reflectでは役割を入れ替えて、連続同種メッセージによる性能低下を避ける。
  • 止め方は「回数固定」または「批評が終了判断」。最後はgenerateで締める例。
  • リンター等の外部情報で裏付けると効果的（ただしレイテンシーは増える）。
7.2

LangGraphのサブグラフ

別のグラフの中で部品として使う、小さなグラフ

要するに：サブグラフは「別のグラフの一部として使われるグラフ」。マルチエージェントの土台になる技術です。親グラフへの追加方法は2通りあります。

リク
師匠・リクマルチエージェントの前に、それを可能にする技術概念――サブグラフを学ぼう。サブグラフは「別のグラフの一部として使われるグラフ」だ。使い道は――①マルチエージェントシステムの構築、②ノードのセットを複数のグラフで再利用、③複数チームでグラフの異なる部分を独立して作業（インターフェース＝入出力スキーマさえ守れば、詳細を知らなくても親グラフを構築できる）。
リク
師匠・リク親グラフにサブグラフを追加する方法は2つある――①サブグラフを直接呼ぶノードを追加（親とサブグラフがステートのキーを共有、変換不要なとき）、②サブグラフを呼ぶ関数を持つノードを追加（スキーマが異なり、前後で変換が必要なとき）。
🤝

使い道①

マルチエージェントシステムを組み立てる土台にする。

♻️

使い道②

ノードのまとまりを、いくつものグラフで再利用する。

👥

使い道③

複数チームが独立作業。入出力のスキーマさえ守ればOK。

🗞️ たとえ話：編集部の中の「写真部」

大きな編集部（親グラフ）の中に、写真の専門チーム「写真部」（サブグラフ）があるイメージ。編集部は「どんな写真を、どの形式で渡すか」さえ取り決めておけば、写真部の内部のやり方をいちいち知らなくても仕事を頼めます。だから複数チームが独立して動けるのです。

7.2.1 サブグラフを直接呼び出す

リク
師匠・リク最も簡単なのは、サブグラフを直接ノードとして接続すること。親とサブグラフがステートのキーを共有しているのが重要だ。共有キーがグラフ間の通信に使われる。
1

親もサブグラフも、同じキー foo を持つ

共有しているキーが、そのまま2つのグラフの通信路になる。

2

サブグラフをそのままノードとして親に追加

変換は不要。コンパイル済みのサブグラフを「subgraph」という名前のノードとして置くだけ。

3

共有キー以外は無視される

共有していないキー（例：bar）を渡しても、相手側では使われない。

✅ スキーマがそろっている → そのままつなげる最短ルート

このコードは、親グラフとサブグラフが同じ項目名 foo でやり取りする例です。サブグラフを「subgraph」という名前のノードとして親にそのままくっつけます。

Python ― サブグラフを直接呼び出す 
# このコードがやること: 親グラフとサブグラフが共有キー foo でやり取りする例。
# サブグラフを「subgraph」という名前のノードとして親に直接追加する。
from langgraph.graph import START, StateGraph
from typing import TypedDict

class State(TypedDict):
    foo: str  # このキーはサブグラフと共有されている

class SubgraphState(TypedDict):
    foo: str  # このキーは親グラフと共有されている
    bar: str

def subgraph_node(state: SubgraphState):
    # 共有キー foo を通じて親グラフと通信できる
    return {"foo": state["foo"] + "bar"}

subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node(subgraph_node)
# ～省略～
subgraph = subgraph_builder.compile()

# 親グラフ。コンパイル済みサブグラフをそのままノードとして追加する
builder = StateGraph(State)
builder.add_node("subgraph", subgraph)
# ～省略～
graph = builder.compile()

7.2.2 関数でサブグラフを呼び出す

リク
師匠・リクまったく異なるスキーマでサブグラフを定義したいときは、サブグラフを呼ぶ関数を持つノードを作る。その関数で、親のステートをサブグラフ用に変換して呼んで、返り値を親用に戻す。
1

親は foo、サブグラフは bar / baz（様式が違う）

そのままでは渡せない。間に「変換する係（node関数）」を置く。

2

node関数で 親→サブグラフ へ変換して呼ぶ

foo の中身を bar に詰め替えてからサブグラフを実行する。

3

返り値を サブグラフ→親 へ戻す

サブグラフが返した bar を、親の foo に詰め替えて返す。

⚠️ スキーマが違う → 直接つなげず、変換ノードを1枚はさむ必要がある

このコードは、親（foo）とサブグラフ（bar, baz）で様式が違う場合に、間の関数 node でステートを詰め替えてからサブグラフを呼び、結果を親に戻す例です。

Python ― 関数でサブグラフを呼び出す 
# このコードがやること: 親(foo)とサブグラフ(bar, baz)でスキーマが違う場合、
# node 関数の中でステートを変換してサブグラフを呼び、結果を親のステートに戻す。
class State(TypedDict):
    foo: str

class SubgraphState(TypedDict):
    bar: str  # 親グラフとは共有していない
    baz: str

def subgraph_node(state: SubgraphState):
    return {"bar": state["bar"] + "baz"}

subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node(subgraph_node)
# ～省略～
subgraph = subgraph_builder.compile()

def node(state: State):
    response = subgraph.invoke({"bar": state["foo"]})  # 親→サブグラフへ変換して呼ぶ
    return {"foo": response["bar"]}                    # サブグラフ→親へ戻す

builder = StateGraph(State)
builder.add_node(node)  # コンパイル済みサブグラフでなく、変換する関数 node を追加
# ～省略～
graph = builder.compile()

7.3.1 スーパーバイザーアーキテクチャ

リク
師匠・リク各エージェントをノードとしてグラフに追加して、次に呼ぶべきエージェントを決めるスーパーバイザーノードも追加する。条件付きエッジで、スーパーバイザーの決定に基づいて適切なエージェントへ進める。まずスーパーバイザーノードを見よう。
1

START → supervisor（編集長が登場）

最初に必ずスーパーバイザーへ進む。

2

supervisor が次の担当を決める

構造化出力で next ＝ researcher / coder / FINISH のどれかを返す。

3

条件付きエッジで該当エージェントへ振り分け

next が researcher なら調査担当へ、coder ならコード担当へ。

✅ researcher / coder → 仕事をして supervisor に戻る
🏁 FINISH → ここで終了
4

各担当 → 再び supervisor

仕事が終わったら毎回スーパーバイザーに戻り、「次どうするか」をまた決める。

🗞️ たとえ話：編集長のさばき

スーパーバイザー＝編集長、researcher＝調査記者、coder＝整理記者（紙面づくり担当）です。編集長は「まず調査記者に裏取りを」「次は整理記者に紙面化を」と次の担当を1人ずつ指名します。担当が仕事を終えるたびに編集長に戻り、必要がなくなったら「FINISH（校了）」と告げて締めます。

このコードは、スーパーバイザーが「次に動かす担当（researcher / coder）または FINISH（終了）」を決まった様式で決める部分です。SupervisorDecision という様式に従って判断します。

Python ― スーパーバイザーノード（次の担当を決める） 
# このコードがやること: スーパーバイザーが「次に動かす作業者（researcher/coder）または FINISH」を
# 構造化出力で決める。SupervisorDecision のスキーマに従って判断する。
from typing import Literal
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

class SupervisorDecision(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
model = model.with_structured_output(SupervisorDecision)

agents = ["researcher", "coder"]

system_prompt_part_1 = f"""あなたは、以下の作業者間の会話を管理するスーパーバイザーです: {agents}。
ユーザーのリクエストに基づき、次に行う作業者を指示してください。それぞれの作業者はタスクを実行し、
その結果とステータスを返します。作業が完了したら「FINISH」と返信してください。"""

system_prompt_part_2 = f"""上記の会話を踏まえて、次に行動すべき作業者は誰ですか？
それとも終了しますか？ 次から選んでください: {', '.join(agents)}, FINISH"""

def supervisor(state):
    messages = [
        ("system", system_prompt_part_1),
        *state["messages"],
        ("system", system_prompt_part_2)
    ]
    return model.invoke(messages)

🗞️ たとえ話：肩書きをはっきりさせる

名簿に「記者A」「記者B」とだけ書いてあったら、編集長は誰に何を頼めばいいか分かりません。「調査記者」「整理記者」と役割が分かる名前にしておくこと――それがエージェントの命名の鉄則です。

このコードは、supervisor・researcher・coder の3つの担当をグラフにまとめ、スーパーバイザーの決定（next）に応じて振り分ける全体図です。各担当は仕事のあと、必ずスーパーバイザーに戻ります。

Python ― 3ノードを統合したグラフ 
# このコードがやること: supervisor・researcher・coder の3ノードをグラフにし、
# スーパーバイザーの決定（state["next"]）に応じて条件付きエッジで振り分ける。
# 各エージェントは処理後、再びスーパーバイザーに戻る。
from typing import Literal
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, MessagesState, START

model = ChatOpenAI()

class AgentState(BaseModel):
    next: Literal["researcher", "coder", "FINISH"]

def researcher(state: AgentState):
    response = model.invoke("～省略～")
    return {"messages": [response]}

def coder(state: AgentState):
    response = model.invoke("～省略～")
    return {"messages": [response]}

builder = StateGraph(AgentState)
builder.add_node(supervisor)
builder.add_node(researcher)
builder.add_node(coder)

builder.add_edge(START, "supervisor")
# スーパーバイザーの決定（next）に応じて、いずれかのエージェントへ進むか終了する
builder.add_conditional_edges("supervisor", lambda state: state["next"])
builder.add_edge("researcher", "supervisor")
builder.add_edge("coder", "supervisor")

supervisor = builder.compile()
リク
師匠・リクこの例では、進行状況が全部 messages リストに記録されるから、リサーチャーとコーダーは互いの作業を確認できる。別の方法もある――サブエージェント自体を1つのグラフにして内部ステートを持たせて、作業の概要だけ出力する、とかね。エージェントが処理を終えたら、再びスーパーバイザーにルーティングして、続けるか・どのエージェントに委譲するかを決める。各サブエージェント自身に「出力をユーザーに返すか」判断させることもできる（リサーチャーとスーパーバイザーの間のエッジを、リサーチャーが更新したステートのキーを読む条件付きエッジに置き換える）。

🔁 7.3 全体のまとめ（要するに＋この項のまとめ）

  • 要するに：拡張は2つ＝リフレクション（自己批評でシステム2のように振る舞う）と、マルチエージェント（複数の独立エージェントを連携）。土台はサブグラフ。代表構成はスーパーバイザー。

  • マルチエージェント：1体で扱えない複雑さ・専門分野に対応。構成はネットワーク・スーパーバイザー・階層的・カスタム。
  • スーパーバイザー：構造化出力で次のエージェントを決め、条件付きエッジで振り分ける。エージェント名は区別しやすく。

この章を読み終わったあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問リフレクション

リフレクションアーキテクチャとは何ですか。なぜ出力品質が上がるのかを、人間のたとえを使って説明してください。

✅ 解答例
リフレクションは、生成のためのプロンプトと、批評・振り返りのためのプロンプトを交互に繰り返すループ。エッセイの例なら、generateノードが草稿を書き、reflectノードが教師として批評し、それをふまえてgenerateが修正する、を繰り返す。これは、本の文章が著者・査読者・編集者のやり取りで仕上がるように、人間の創作プロセスを模している。一発で完璧な出力を出すのではなく、自己批評で内省的（システム2）に何度もブラッシュアップするので、品質が上がる。
📝 採点ポイント
□ 生成と批評を交互に繰り返すループ、に触れている ／ □ 著者と編集者など人間の創作プロセスのたとえを使っている ／ □ 自己批評で品質が上がる、に触れている
第2問役割の入れ替え

リフレクションの実装で、reflect ノードがメッセージの役割（AI/Human）を入れ替えているのはなぜですか。

✅ 解答例
対話調整された多くのLLMは「人間とAIのメッセージのペア」で学習されているため、同じ人物（同じ役割）からの連続したメッセージが多いとパフォーマンスが悪化することがある。そこで reflect ノードでは役割を入れ替えて、LLMに「自分の出力（AIメッセージ）を、他人（人間）の提出物として批評している」と思わせる。逆に generate ノードでは、その批評を「ユーザーから来たフィードバック」として扱う。この“裏技”でパフォーマンスの悪化を防いでいる。
📝 採点ポイント
□ LLMは人間とAIのペアで学習され、連続同種メッセージで性能が落ちる、に触れている ／ □ 役割を入れ替えて自分の出力を他人の提出物として批評させる、に触れている ／ □ パフォーマンス悪化を防ぐため、に触れている
第3問サブグラフの2つの追加方法

サブグラフを親グラフに追加する2つの方法を、どんなときに使うかを含めて説明してください。

✅ 解答例
①サブグラフを直接ノードとして接続する方法：親グラフとサブグラフがステートのキーを共有しているときに使う。共有キーがグラフ間の通信に使われ、ステートの変換が不要。②サブグラフを呼ぶ関数を持つノードを追加する方法：親グラフとサブグラフのスキーマが異なるときに使う。その関数の中で、親のステートをサブグラフ用に変換して呼び、返り値を親用のステートに戻す。スキーマが違って変換が必要な場合に便利。
📝 採点ポイント
□ 直接接続＝キーを共有、変換不要、に触れている ／ □ 関数で呼ぶ＝スキーマが異なり変換が必要、に触れている ／ □ それぞれの使い分けに触れている
第4問マルチエージェントの構成

マルチエージェントの4つの構成（ネットワーク・スーパーバイザー・階層的・カスタム）のうち、スーパーバイザーとは何ですか。

✅ 解答例
スーパーバイザーは、各エージェントが1つのスーパーバイザーエージェントとだけ通信する構成。スーパーバイザーが「次にどのエージェント（複数可）を呼ぶか」を決定する。ネットワーク（全員が互いに通信）よりも制御しやすく、階層的（スーパーバイザーの上にさらにスーパーバイザー）よりシンプルで、能力と使いやすさのバランスが良い。実装では、スーパーバイザーが構造化出力で次のエージェント（またはFINISH）を決め、条件付きエッジで該当エージェントへ振り分ける。
📝 採点ポイント
□ 各エージェントがスーパーバイザーとだけ通信する、に触れている ／ □ スーパーバイザーが次に呼ぶエージェントを決める、に触れている ／ □ 能力と使いやすさのバランスが良い、に触れている
第5問いつ拡張を使うか

リフレクションやマルチエージェントは強力ですが、新しいエージェントを作るときにいきなり使うべきではないと言われます。なぜですか。

✅ 解答例
これらの拡張はアーキテクチャを複雑にし、レイテンシーやコスト、デバッグの難しさを増やすから。リフレクションは生成・批評を繰り返すぶんレイテンシーが増え、マルチエージェントは複数エージェントの連携で複雑さが増す。多くの場合、6章で説明した単純なエージェントアーキテクチャで十分な性能が出る。だから、まず単純なものから始めて、それで足りないと分かったときに初めて拡張に手を伸ばすのがベスト（本書を貫く「最もシンプルに」の原則）。
📝 採点ポイント
□ 拡張は複雑さ・レイテンシー・コストを増やす、に触れている ／ □ 多くの場合は単純なアーキテクチャで十分、に触れている ／ □ まず単純から始め、足りないときに拡張する、に触れている
🌱

初心者がこの内容を理解するための次のステップ

手を動かして確かめよう
🔁

リフレクションを動かす

本章のエッセイ生成のリフレクションを写経し、繰り返し回数（should_continue のしきい値）を変えて、批評と修正がどう繰り返されるか観察しましょう。

📝

批評を読む

各ループの reflect の出力（批評）を表示して、LLMが自分の出力をどう評価しているかを見てみましょう。

🧩

サブグラフを試す

簡単なサブグラフを作り、「直接接続」と「関数で呼ぶ」の両方で親グラフに組み込んで、ステートの流れを確認しましょう。

🎩

スーパーバイザーを実装する

researcher / coder の中身を簡単に埋めて、スーパーバイザーがどちらを呼ぶかをログで追いましょう。

📚

LangGraph公式のマルチエージェント

LangGraph の「Multi-agent」概念ページ（langchain-ai.github.io の langgraph/concepts/multi_agent）で、スーパーバイザー・ネットワーク・階層的の図解を確認しましょう。

🧭

「まず単純に」を実践する

自分が作りたいエージェントについて、本当にリフレクションやマルチエージェントが必要か、まず単純な6章のアーキテクチャで足りないかを考えてみましょう。
