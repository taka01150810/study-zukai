📚 かんたん用語集

この章に出てくる言葉を、専門知識なしで読める形にまとめました。

ライブラリ

誰かが作って公開している、便利な部品のかたまり。自分のプログラムに読み込んで使います。LangChainもその1つ。

API

他社のサービスを、プログラムから呼び出して使うための窓口。OpenAI APIを呼ぶと、その場でLLMが答えを返してくれます。

APIキー

そのサービスを「誰が使ったか」を識別するための長い文字列。料金の請求先にもなるので、他人に見せてはいけません。

環境変数

プログラムの外側（パソコン側）に置いておく設定値。APIキーをコードに直接書かずに済ませるために使います。

コンポーネント部品

LangChainが用意している、決まった役目を持つ部品。モデル・プロンプトテンプレート・出力パーサーなど。

LLMインターフェース

文字列を渡すと、その続きの文字列が返ってくる、いちばん単純な使い方。

チャットモデルインターフェース

役割つきの発言の一覧を渡して、返答を1件受け取る使い方。会話のやり取りができます。

HumanMessage

「これは利用者の発言です」という札を付けた入れ物。

AIMessage

「これはモデルの返答です」という札を付けた入れ物。

SystemMessage

「これはモデルが従うべき前提の指示です」という札を付けた入れ物。

temperature

答えのばらつき具合を決める数値。小さいと毎回似た答え、大きいと毎回ちがう答えになります。

max_tokens

返答の長さの上限。小さすぎると文が途中で切れます。料金の上限にもなります。

プロンプトテンプレート

指示文の「毎回同じ部分」と「毎回差し替える部分」を分けて書いた雛形。

プレースホルダー

雛形の中の「あとで値を入れる場所」。{context} のように波括弧で書きます。

構造化出力

ただの文章ではなく、JSONやCSVのように決まった形で返してもらうこと。他のプログラムにそのまま渡せます。

JSON

「名前と値」の組み合わせでデータを書き表す、広く使われている形式。

スキーマ

「どんな名前の項目が、どんな種類の値で入るか」を先に決めた設計図。

Pydantic

Pythonでスキーマを書くためのライブラリ。項目名と型を書いておくと、値が正しいか確認してくれます。

with_structured_output

スキーマをモデルに伝え、返ってきた答えがその形になっているか確認する機能。

出力パーサー

モデルが返した文章を、リストやXMLなど扱いやすい形に変換する部品。

Runnableインターフェース

LangChainの部品すべてに共通する使い方の決まり。invoke / batch / stream の3つがあります。

invoke

入力を1つ渡して、出力を1つ受け取る呼び出し方。

batch

入力をまとめて渡して、出力をまとめて受け取る呼び出し方。1件ずつより速く済みます。

stream

できあがった部分から順に少しずつ受け取る呼び出し方。画面に文字が流れて出てくるのはこれ。

チェーン

部品を順につないだ流れ。プロンプト→モデル→出力パーサー、のように並べます。

命令型コンポジション

部品を関数の中で自分の手で順に呼んで組み立てるやり方。

LCEL宣言型

template | model のように縦棒でつないで組み立てるやり方。並列実行や逐次出力を自動でやってくれます。

土台になる部品を1つずつ触る

「いよいよコードですか！」と身を乗り出すソラ。リク先輩は「まずはLangChainの基本部品を1つずつ触ろう」と、開発環境のセットアップから始めます。

LLMを呼び出す／チャットモデルで役割を使い分ける／指示文をテンプレート化して使い回す／答えをJSONなど決まった形で受け取る／部品を組み合わせる——この章で、LangChainアプリの土台になる部品をすべて体験します。最後に、すべての部品が共通の「Runnableインターフェース」で動くこと、組み合わせ方には命令型とLCEL（宣言型）の2つがあることを学びます。

なぜこれが必要か／これを知ると何ができるか

学ぶ理由と、身につくこと

🟣 なぜ学ぶ価値があるのか

  • LLM提供元のAPIを直接呼ぶこともできるが、会社ごとの細かな違いに悩まされる。LangChainがその違いを吸収してくれるから。
  • 指示文をコードに直接書き込むと使い回せない。テンプレート化を知らないと、同じ文章を何度も書く羽目になるから。
  • LLMの答えがただの文章だと、他のプログラムに渡しにくい。決まった形（JSONなど）で受け取る方法を知ると、アプリの一部として組み込めるから。

🟢 これを知ったらできるようになること

  • LangChainでLLM／チャットモデルを呼び出し、system／user／assistantの役割を使い分けられる。
  • プロンプトテンプレートで差し替えを扱い、指示文を使い回せる。
  • with_structured_output や出力パーサーで、JSON・CSVなど決まった形の出力を得られる。
  • 共通の使い方（invoke／batch／stream）を理解し、命令型とLCELで部品を組み合わせられる。
📖

CoTやツール呼び出しみたいな、よく使うやり方の見本の実装が最初から入っています。LLMを素早く試す最短ルートです。

各部品が同じ仕様なので、モデルも出力パーサーも、コードを書き直さずに差し替えられます。

③ 全体を束ねる機能

動きを記録する仕組み、共通の使い方、長時間の処理の中断・再開・やり直しなど。

ソラ
ソラ差し替えられるって、たとえば？
リク
リクOpenAIとAnthropic、2つの主要な提供元のチャットモデルを考えてみて。両方とも「型」と「内容」を持つメッセージを受け取って、生成したメッセージを返す。でも、同じ会話で両方を使おうとすると、メッセージの書き方のわずかな違いで問題が起きる。LangChainはこの違いを吸収して、特定の会社に縛られないアプリを作れるようにする。実際、OpenAIとAnthropicを同じチャットボットの会話の中で動かしても問題なく動くんだ。
ソラ
ソラそれは便利！本書ではどの部品を使うんですか？
リク
リクLLM／チャットモデルと埋め込みはOpenAI、ベクトルストアはPGVectorだ。でもどれも代わりのもの（Anthropic、Ollama、Cohere、Weaviate、OpenSearchなど）に入れ替えられる。じゃあ、まずセットアップからだ。

🔎 具体例：「差し替えられる」とはどういうことか

OpenAIのモデルで動くチャットボットを100行のコードで書いたとします。あとで「Anthropicのモデルのほうが自分の用途に合う」と分かったとき、LangChainを使っていなければ、送信の書き方も返答の読み取り方も違うので、大部分を書き直すことになります。

LangChainを使っていれば、ChatOpenAI() を ChatAnthropic() に変える1行だけで残り99行はそのまま動きます。

1.2

LangChainでLLMを使う

2種類の呼び出し方

要するに：呼び出し方は2種類あります。①LLMインターフェース＝文字列を渡すと続きが返る。②チャットモデルインターフェース＝役割つきの発言の一覧を渡して、返答を受け取る。

➡️

① LLMインターフェース

入力：1つの文字列。出力：その続きの文字列。単純な穴埋めや続きの生成に向きます。

💬

② チャットモデルインターフェース

入力：役割つきの発言の一覧。出力：モデルの返答1件。会話や、前提の指示を与えたいときに向きます。

LLMインターフェース ― 文字列の続きを予測する

次のコードは、「The sky is（空は）」の続きをLLMに予測させています。

コードを見る（1行ずつ説明つき）
# OpenAIのLLMを使うための部品を読み込む。
from langchain_openai.llms import OpenAI

# 使うモデルの名前を指定して、呼び出し口を1つ作る。ここでは文字列の続きを書くタイプのモデル。
model = OpenAI(model="gpt-3.5-turbo-instruct")

# 文字列を1つ渡して、その続きを書いてもらう。
# 「空は」のあとには色を表す語が来る文章が学習時に多かったので、色が返る。
print(model.invoke("The sky is"))
# --- 実行結果 ---
# Blue!
ソラ
ソラmodel というパラメータって何ですか？
リク
リクLLMやチャットモデルで最もよく設定する項目で、使う土台のモデルを指定する。多くの提供元は、性能と料金のバランスが違う複数のモデルを出している（大きいモデルほど高性能だが高価で遅い）。他に便利な設定が2つ。temperature（答えのばらつき。小さいと毎回似た答え、大きいと毎回ちがう答え）と max_tokens（返答の長さと料金の上限。小さすぎると文が途中で切れる）だ。
ソラ
ソラ0章で出た temperature ですね。次はチャットモデル？
設定項目何を決めるか小さくすると大きくすると
model使う土台のモデル大きいモデルほど高性能・高価・遅い。用途に合わせて選ぶ
temperature答えのばらつき毎回ほぼ同じ答え（0で最も安定）毎回ちがう答え。意外性が出る
max_tokens返答の長さの上限料金は抑えられるが文が途中で切れる長い返答が書けるが料金は増える

チャットモデルインターフェース ― 役割つきで会話する

リク
リクチャットモデルの呼び方は、双方向の対話ができる。0章でやったように、メッセージをsystem（指示）・user（質問）・assistant（モデルの返答）の役割に分けて扱うんだ。

次のコードは、チャットモデルに「フランスの首都は？」と尋ねています。

コードを見る（1行ずつ説明つき）
# OpenAIのチャットモデルを使うための部品を読み込む。
from langchain_openai.chat_models import ChatOpenAI

# 「これは利用者の発言です」という札を付けるための入れ物を読み込む。
from langchain_core.messages import HumanMessage

# チャットモデルの呼び出し口を1つ作る。モデル名を省くと既定のものが選ばれる。
model = ChatOpenAI()

# 質問を「利用者の発言」の札を付けて、一覧（リスト）に1件だけ入れる。
# チャットモデルには、1つの文字列ではなく、この一覧の形で渡す決まりになっている。
prompt = [HumanMessage("フランスの首都は？")]

# 一覧をモデルに渡す。返ってくるのは「モデルの返答」の札が付いた入れ物。
print(model.invoke(prompt))
# --- 実行結果 ---
# AIMessage(content='フランスの首都はパリです。')

4種類のメッセージの入れ物

🙋

HumanMessage

利用者の発言。アプリの利用者が入力した文章を入れます。

🤖

AIMessage

モデルの返答。過去の返答を履歴として渡すときもこれを使います。

⚙️

SystemMessage

モデルが従うべき前提の指示。開発者が先に仕込みます。

🏷️

ChatMessage

上の3つ以外の、任意の役割を自分で名付けたいときに使います。

SystemMessageで返答のスタイルを決める

次のコードは、「感嘆符を3つ付けて答えて」と前提の指示を与えたうえで質問しています。

コードを見る（1行ずつ説明つき）
# 「利用者の発言」と「前提の指示」、2種類の札を読み込む。
from langchain_core.messages import HumanMessage, SystemMessage

# チャットモデルの部品を読み込む。
from langchain_openai.chat_models import ChatOpenAI

# チャットモデルの呼び出し口を作る。
model = ChatOpenAI()

# 返答の書き方についての前提の指示を用意する。利用者には見えない部分。
system_msg = SystemMessage(
    "あなたは優秀なアシスタントです。質問に対して3つの感嘆符を付けて回答してください。"
)

# 実際の質問を用意する。ここには感嘆符の話は一切書かない。
human_msg = HumanMessage("フランスの首都は？")

# 前提の指示 → 質問 の順に並べて渡す。モデルは前提の指示に従った書き方で答える。
# 質問文に何も書いていないのに感嘆符が3つ付くのは、前提の指示が効いているから。
print(model.invoke([system_msg, human_msg]))
# --- 実行結果 ---
# AIMessage('パリ！！！')
ソラ
ソラユーザーの質問には「感嘆符を付けて」なんて書いてないのに、ちゃんと付きましたね！
リク
リクそこがポイント。SystemMessage で一貫した返答のスタイルをあらかじめ設定できるんだ。ユーザーの入力に関係なくね。

🔎 具体例：SystemMessageを変えると何が変わるか

質問はずっと「フランスの首都は？」のまま、前提の指示だけを変えてみます。

「3つの感嘆符を付けて」→パリ！！！／「必ず英語で答えて」→Paris.／「小学生にも分かる言葉で2文で」→フランスの首都はパリです。エッフェル塔がある大きな街です。／「JSONで答えて」→{"capital": "パリ"}

アプリ全体で返答の形をそろえたいときは、質問側ではなく前提の指示側に書きます。

リクそこでプロンプトテンプレートだ。毎回同じ文章と、送信ごとに差し替える場所を分けて書ける。波括弧 {...} が差し替える場所になる。

PromptTemplate ― 1つの文字列の雛形

次のコードは、資料と質問を差し替えられる雛形を作り、実際の値を入れています。

コードを見る（1行ずつ説明つき）
# 文字列の雛形を作るための部品を読み込む。
from langchain_core.prompts import PromptTemplate

# 毎回同じ文章はそのまま書き、差し替える場所だけ波括弧で名前を付けておく。
# ここでは {context}（資料）と {question}（質問）の2か所が差し替え場所。

LLMの出力形式を指定する

文章ではなく、機械が読める形で受け取る

要するに：答えを普通の文章ではなく、JSON・XML・CSV・コードといった決まった形で返してもらえば、そのまま他のプログラムに渡せます。

リク
リクただの文章も便利だけど、JSON・XML・CSV・コードみたいな機械が読み取れる決まった形で出力させたいこともある。そうすれば、他のコードにそのまま渡して、大きなアプリの一部にできる。

🟣 なぜ決まった形で受け取りたいのか

  • 普通の文章のままだと、答えのどこが「回答本体」でどこが「理由」なのかをプログラムが判別できないから。
  • 画面に表示したり、データベースに保存したりするには、項目ごとに分かれている必要があるから。
  • 形が毎回ゆれると、後続の処理がその都度エラーになるから。

1.4.1 JSON出力 ― スキーマを決めて守らせる

要するに：先に「どんな項目が入るか」のスキーマを書いておき、それをモデルに伝えて、返ってきた答えがその形になっているか確認します。

次のコードは、「回答」と「その根拠」の2項目を持つ形で答えさせています。

コードを見る（1行ずつ説明つき）
# チャットモデルの部品と、スキーマを書くための部品を読み込む。
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

# 返してほしいデータの形を、項目名と種類の組で書き表す。
class AnswerWithJustification(BaseModel):
    '''ユーザーの質問への回答と、その回答の正当性（根拠）を含むデータモデル'''
    # answer は文字列。質問への回答そのものを入れる。
    answer: str
    '''ユーザーの質問への回答'''
    # justification も文字列。なぜその回答になるのかの説明を入れる。
    justification: str
    '''回答の正当性を示す根拠'''

# チャットモデルの呼び出し口を作る。temperature=0 にして毎回同じ答えが返るようにする。
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 上で決めた形を守らせる設定に変える。この1行が、形の指示と答えの確認をまとめて担当する。
structured_llm = llm.with_structured_output(AnswerWithJustification)

# 質問する。答えは普通の文章ではなく、answer と justification の2項目に分かれて返る。
print(structured_llm.invoke("レンガ1ポンドと羽毛1ポンドではどちらが重いですか？"))
# --- 実行結果 ---
# {
#   answer: "重さは同じです",
#   justification: "レンガも羽毛もどちらも1ポンドなので重さは同じです。しかし、体積は…"
# }
ソラ
ソラPythonは Pydantic でスキーマを定義するんですね。with_structured_output は何をしてるんですか？
リク
リク2つのことをしている。①スキーマを JSON Schema（項目の種類・名前・説明を表す書き方）に変換してLLMに渡す。②返ってきた出力を同じスキーマで確認する。だからLLMがスキーマ通りの形を確実に返してくれるんだ。
1

スキーマを書く

「answer（文字列）と justification（文字列）を持つ」と決めます。

2

モデルに形を伝える

スキーマがモデルに読める書き方に変換され、指示に付け足されます。

3

モデルが答える

決められた項目名で答えを返します。

4

返ってきた形を確認する

項目が足りない、種類が違う、といった場合はここで分かります。

確認を通れば、そのまま画面表示やデータベース保存に使えます。

LLMアプリケーションの多くのピースを組み立てる

共通の使い方と、2つの組み立て方

1.5.1 Runnableインターフェース ― すべての部品に共通の使い方

要するに：モデルも雛形も出力パーサーも、全部 invoke() で呼べました。これは偶然ではなく、すべての部品が同じ使い方の決まりに従っているからです。

リク
リクここまでのコード例、全部 invoke() を使っていたことに気づいたかな。実は、モデルも雛形も出力パーサーも、共通の使い方を持っているんだ。これがRunnableインターフェースだ。3つの呼び方がある。
ソラ
ソラ3つ？
1️⃣

invoke()

入力を1つ渡して、出力を1つ受け取ります。いちばん基本の呼び方。

📚

batch()

入力をまとめて渡して、出力をまとめて受け取ります。1件ずつ呼ぶより効率よく処理されます。

💧

stream()

できあがった部分から順に少しずつ受け取ります。画面に文字が流れて出てくるのはこれです。

さらに、やり直し・別の手段への切り替え・形の確認なども組み込まれていて、Pythonでは各呼び方に非同期版（待ち時間の間に別の処理を進められる版）があります。だから、1つの部品で覚えた使い方が、他のすべてにそのまま通じます。

次のコードは、同じモデルに対して3つの呼び方を順に使っています。

コードを見る（1行ずつ説明つき）
# チャットモデルの部品を読み込む。
from langchain_openai import ChatOpenAI

# 呼び出し口を1つ作る。以下の3つの呼び方は、すべてこの同じ口に対して使える。
model = ChatOpenAI()

# ① invoke：文章を1つ渡して、返答を1つ受け取る。
completion = model.invoke('Hi there!')
print(completion)
# --- 実行結果 ---
# Hi!

# ② batch：文章を2つまとめて渡して、返答を2つまとめて受け取る。
# 2回 invoke するより、まとめて送るぶん待ち時間が短くなる。
completions = model.batch(['Hi there!', 'Bye!'])
print(completions)
# --- 実行結果 ---
# ['Hi!', 'See you!']

# ③ stream：返答ができあがった部分から順に受け取る。全部書き終わるのを待たない。
# 下の for は、届いたかけらを1つずつ取り出して画面に出している。
for token in model.stream('Bye!'):
    print(token)
# --- 実行結果 ---
# Good
# bye
# !

🔎 具体例：3つの呼び方の使い分け

invoke：利用者が1件質問して1件答えを返す、ごく普通のチャット画面。

batch：500件の問い合わせメールをまとめて分類する夜間処理。1件ずつ500回呼ぶと待ち時間が積み上がりますが、まとめて渡せば大幅に短縮できます。

stream：長い文章を書かせるとき。全部書き終わるまで20秒かかる場合でも、streamなら1秒目から文字が出始めるので、利用者は待たされている感じがしません。

部品の組み合わせ方は2つある

リク
リクこれらの部品は、2つの方法で組み合わせられる。①命令型——model.invoke(...) のように自分の手で順に呼ぶ。②宣言型——LCEL（LangChain Expression Language）を使う。表で違いを見よう。
命令型宣言型（LCEL）
書き方Python（普段どおりの書き方）LCEL（| でつなぐ）
同時に走らせる自分でスレッドなどを使って書く自動
少しずつ出す（ストリーミング）yield を使って自分で書く自動
待ち時間に他を進める（非同期）async の関数に書き換える自動

1.5.2 命令型コンポジション ― 関数にまとめて自分で書く

要するに：部品を関数の中で順に呼んで、1つのまとまりにします。関数の中に自由な処理を書けるのが利点です。

次のコードは、雛形とモデルを chatbot という1つの関数にまとめています。

コードを見る（1行ずつ説明つき）
# チャットモデル、役割つきの雛形、そして関数に共通の使い方を付ける印を読み込む。
from langchain_openai.chat_models import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import chain

# 前提の指示と、差し替え場所つきの質問文で、役割つきの雛形を作る。
template = ChatPromptTemplate.from_messages([
    ('system', 'あなたは親切なアシスタントです。'),
    ('human', '{question}'),
])

# モデルの呼び出し口も作る。
model = ChatOpenAI()

# この印を付けると、ふつうの関数に invoke / batch / stream の使い方が備わる。
@chain
def chatbot(values):
    # 受け取った値を雛形に入れて、送る発言の一覧を組み立てる。
    prompt = template.invoke(values)
    # 組み立てた一覧をモデルに渡し、その返答をそのまま関数の答えとして返す。
    return model.invoke(prompt)

# できあがった chatbot は、部品と同じように invoke で呼べる。
print(chatbot.invoke({"question": "どのモデルプロバイダーがLLMを提供していますか？"}))
# --- 実行結果 ---
# OpenAI、Anthropic、Google、Cohere などがLLMを提供しています。
リク
リク慣れた書き方で、関数の中に自由に処理を書ける。少しずつ出力させたいなら、yield を使って書き換える。

次のコードは、同じ chatbot を「できた部分から少しずつ返す」形に書き換えています。

コードを見る（1行ずつ説明つき）
# 印を付けて、この関数にも共通の使い方を備えさせる。
@chain
def chatbot(values):
    # 受け取った値を雛形に入れて、送る発言の一覧を組み立てる。
    prompt = template.invoke(values)
    # モデルから届いたかけらを1つずつ受け取り、
    for token in model.stream(prompt):
        # return ではなく yield で、その場ですぐ呼び出し元に渡す。
        # return だと全部そろうまで待つが、yield なら届いた順に渡せる。
        yield token

# 呼ぶ側も、届いたかけらを1つずつ受け取って画面に出す。
for part in chatbot.stream({"question": "どのモデルプロバイダーがLLMを提供していますか？"}):
    print(part)
# --- 実行結果 ---
# OpenAI
# 、
# Anthropic
# 、…（届いた順に1つずつ表示される）
リク
リク待ち時間の間に他の処理を進めたいなら async def と ainvoke に書き換える。つまり、やりたいことが増えるたびに書き換えが必要になるんだ。

1.5.3 宣言型コンポジション（LCEL） ― 縦棒でつなぐ

要するに：template | model のように部品を縦棒でつなぐだけ。同時実行・少しずつ出力・待ち時間の活用は、書き換えなしで自動的に効きます。

リク
リクLCEL（LangChain Expression Language）は、部品を組み合わせるための宣言型の書き方だ。自動での同時実行・少しずつの出力・記録・待ち時間の活用に対応していて、効率のよい実行の段取りに変換してくれる。さっきの例をLCELで書き直すと——

次のコードは、同じチャットボットを縦棒1本で組み立てています。

コードを見る（1行ずつ説明つき）
# チャットモデルと、役割つきの雛形の部品を読み込む。
from langchain_openai.chat_models import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# 前提の指示と、差し替え場所つきの質問文で雛形を作る（命令型のときと全く同じ）。
template = ChatPromptTemplate.from_messages([
    ('system', 'あなたは親切なアシスタントです。'),
    ('human', '{question}'),
])

# モデルの呼び出し口も作る（ここも全く同じ）。
model = ChatOpenAI()

# 縦棒でつなぐ。「雛形の出力を、そのままモデルの入力にする」という意味になる。
# 関数を書かずに、この1行だけで命令型のときと同じものができあがる。
chatbot = template | model

# つないだものも、部品と同じように invoke で呼べる。
print(chatbot.invoke({"question": "どのモデルプロバイダーがLLMを提供していますか？"}))
# --- 実行結果 ---
# OpenAI、Anthropic、Google、Cohere などがLLMを提供しています。

# 少しずつ出力させたいときも、書き換えは不要。呼び方を stream に変えるだけで動く。
for part in chatbot.stream({"question": "どのモデルプロバイダーがLLMを提供していますか？"}):
    print(part)
# --- 実行結果 ---
# OpenAI
# 、
# Anthropic
# 、…（届いた順に1つずつ表示される）
ソラ
ソラtemplate | model ……縦棒でつなぐの、すっきりしてますね！
リク
リクそう。重要なのは、命令型でもLCELでも、最後の行（invoke／stream／batch の呼び出し）は同じってこと。しかもLCELなら、少しずつ出力させるための追加の書き換えは一切いらない——chatbot.stream(...) を呼ぶだけで動く。
ソラ
ソラどっちを使えばいいんですか？
リク
リク命令型は自分で書く処理が多いとき、宣言型（LCEL）は既にある部品を最小限の手直しで組み立てたいとき、だ。場面で使い分けよう。
🛠️

命令型が向く場面

途中に条件分岐を入れたい、外部のデータベースを読みたい、独自の後処理をしたい——関数の中に自由に書ける必要があるとき。

🔗

LCELが向く場面

雛形→モデル→出力パーサーのように、既にある部品を順につなぐだけでよいとき。書く量が最小で、同時実行なども自動で効きます。

🟢 この項のまとめ

  • すべての部品は共通の使い方：invoke（1件）・batch（まとめて）・stream（少しずつ）。やり直しや切り替えも組み込み。
  • 命令型：関数（@chain）にまとめて普段どおり書く。自分で書く処理が多いとき向き。
  • LCEL（宣言型）：template | model のように縦棒でつなぐ。同時実行・少しずつの出力・待ち時間の活用が自動。最小限の手直しで済ませたいとき向き。
  • どちらも最後の呼び方（invoke／stream／batch）は同じ。

章末の理解度チェック（全5問）

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問なぜLangChainか

❓ LLM提供元のAPIを直接叩けるのに、なぜLangChainを使う価値があるのですか。理由を挙げて説明してください。

✅ 解答例
理由は3つ。①組み込みのやり方：CoTやツール呼び出しなどよく使うやり方の見本の実装が同梱され、素早く試せる。②置き換え可能な部品：モデル・出力パーサーなどが同じ仕様なので、コードを書き直さずに差し替えられ、1社に縛られるのを避けられる（OpenAIとAnthropicを同じ会話で使うことすら可能）。③全体を束ねる機能：動きを記録する仕組み、共通の使い方、長時間の処理の中断・再開・やり直し。
📝 採点ポイント
□ 組み込みのやり方（見本の実装）に触れている
□ 差し替え可能な部品（1社に縛られない）に触れている
□ 全体を束ねる機能（共通の使い方等）に触れている
第2問2つのインターフェース

❓ LLMインターフェースとチャットモデルインターフェースの違いを説明してください。チャットモデルの3つの役割も挙げてください。

✅ 解答例
LLMインターフェースは、文字列を入力に受け取り、その続き（テキスト）を返すだけの単純なもの。チャットモデルインターフェースは、利用者とモデルの双方向のやり取りができ、メッセージをsystem（モデルへの前提の指示）・user（利用者の質問や内容）・assistant（モデルが生成した返答）の3つの役割に分けて扱う。SystemMessageで一貫した返答のスタイルをあらかじめ設定できる。
📝 採点ポイント
□ LLM＝文字列入力→続き、チャット＝役割つきの双方向、の違いに触れている
□ system／user／assistantの3役割を挙げている
□ SystemMessageで返答スタイルを設定できる、に触れている（できれば）
第3問プロンプトテンプレート

❓ プロンプトテンプレートを使うと何が嬉しいのですか。{context} のような差し替え場所の役割とともに説明してください。

✅ 解答例
プロンプトテンプレートを使うと、指示文の「毎回同じ部分」と「送信ごとに差し替える部分」を分けて書ける。{context} や {question} のような波括弧で囲んだ部分が差し替え場所で、invoke に渡した値で実行時に置き換わる。これにより、同じ指示文を毎回そのまま書かずに使い回せ、資料や質問だけを変えられる。雛形は「複数の具体的な指示文を作るための元の形」。
📝 採点ポイント
□ 毎回同じ文章と差し替え場所を分けて書ける、に触れている
□ 差し替え場所が実行時に値で置き換わる、に触れている
□ 指示文を使い回せる、に触れている
第4問構造化出力

❓ なぜLLMにJSONなど決まった形の出力をさせたいのですか。with_structured_output は何をしてくれますか。

✅ 解答例
普通の文章ではなくJSONなど決まった形で出力させると、その出力を他のプログラムにそのまま渡せて、画面への送信やデータベースへの保存ができ、LLMを大きなアプリの一部として組み込める。with_structured_output は、定義したスキーマ（PythonではPydantic）をJSON Schemaに変換してLLMに渡し、さらに返ってきた出力を同じスキーマで確認する。これにより、LLMがスキーマ通りの形を確実に返してくれる。
📝 採点ポイント
□ 決まった形の出力は他のプログラムに渡せてアプリに組み込める、に触れている
□ スキーマをLLMに渡す、に触れている
□ 返ってきた出力をスキーマで確認する、に触れている
第5問命令型とLCEL

❓ 部品を組み合わせる「命令型」と「LCEL（宣言型）」の違いを説明し、それぞれどんなときに向くかを述べてください。

✅ 解答例
命令型は、部品を関数（@chain）にまとめて、普段どおりのPythonの書き方で書く方法。関数の中に自由な処理を書けるので、自分で書く処理が多いときに向く。LCEL（宣言型）は、template | model のように縦棒で部品をつなぐ方法で、同時実行・少しずつの出力・待ち時間の活用に自動で対応し、効率のよい実行の段取りに変換される。既にある部品を最小限の手直しで組み立てたいときに向く。どちらも最後の呼び方（invoke／stream／batch）は同じ。
📝 採点ポイント
□ 命令型＝関数にまとめて普通に書く、自由な処理向き、に触れている
□ LCEL＝縦棒でつなぐ宣言型、自動対応、最小限の手直し向き、に触れている
□ どちらも呼び方は共通、に触れている（できれば）
