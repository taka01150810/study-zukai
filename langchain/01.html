LLM 大規模言語モデル

大量の文章を学んだ「文章の続きを予想するすごく賢いAI」。文字を入れると、それらしい続きを返します。

LangChain ラングチェーン

LLMを使うアプリを作るための「規格のそろった部品セット」。部品を組み合わせてアプリを作れます。

コンポーネント 部品

LangChainの「ひとつひとつの部品」。LLM・プロンプト・出力パーサーなどがこれにあたります。

チャットモデル 対話AI

役割（指示・質問・返答）を分けて会話できるLLM。普段使うチャットAIはこのタイプです。

役割（ロール） system / user / assistant

会話の発言を3種類に分けたもの。systemは「AIへの指示」、userは「ユーザーの発言」、assistantは「AIの返答」。

プロンプト AIへの指示文

AIに渡す文章。これ次第で答えが大きく変わります。

プロンプトテンプレート 指示文のひな型

毎回同じ部分はそのまま、変わる部分だけ穴あきにした指示文のひな型。穴に値を入れて使い回せます。

プレースホルダー 差し替え枠

テンプレートの中の {...} の部分。あとから実際の値を入れる「差し替え用の枠」です。

構造化出力 形のそろった出力

ただの文章ではなく、JSONなど「決まった形」で答えを返すこと。他のプログラムにそのまま渡せます。

JSON ジェイソン

「名前: 値」で情報を並べる、機械が読みやすいデータの書き方。アプリ同士のやり取りでよく使います。

スキーマ 形の取り決め

「答えはこういう項目をこの型で持つこと」という出力の設計図。これに沿った答えだけを受け取れます。

出力パーサー 整形係

AIが返した文章を、リストやXMLなど「使いやすい形」に変換してくれる部品。

Runnableインターフェース 共通の操作口

すべての部品が共通で持つ「同じ操作のしかた」。invoke / batch / stream の3つの呼び方が全部品で使えます。

invoke / batch / stream 呼び方3種

invoke=1個入れて1個もらう、batch=まとめて入れてまとめてもらう、stream=少しずつ受け取る。

命令型コンポジション 手で組む

部品を関数にまとめて、普通のプログラムとして手書きで組み合わせる方法。自由に細工できます。

LCEL（宣言型） パイプでつなぐ

部品 | 部品 のように記号でつなぐだけで組み合わせる方法。自動でうまく実行してくれます。

temperature ゆらぎ

出力のばらつき具合。小さいと毎回ほぼ同じ、大きいと創造的でバラバラになります。

max_tokens 長さの上限

出力の長さ（とコスト）の上限。小さすぎると文が途中で切れます。

APIキー 合鍵

OpenAIなどのサービスを使うための「あなた専用の合鍵」。これがないと呼び出せません。

この章のあらすじ

これから何をやるのか

「いよいよコードですか！」と身を乗り出すソラ。リク先輩は「まずはLangChainの“基本部品”を1つずつ触ろう」と、開発環境のセットアップから始めます。

LLMを呼び出す → チャットモデルで役割（system / user / assistant）を使い分ける → プロンプトをテンプレート化して再利用する → 出力をJSONなど構造化された形式で受け取る → そして部品を組み合わせる。この章で、LangChainアプリの土台となる構成要素をすべて体験します。最後に、すべての部品が共通のRunnableインターフェースで動くこと、組み合わせ方には命令型とLCEL（宣言型）の2つがあることを学びます。

🧱 たとえ話：今日は「ブロック組み立て工房」に入門

この章は、規格のそろったブロックでロボットを組み立てる工房に弟子入りする日です。ブロックには「文章を予想するブロック（LLM）」「指示を整えるブロック（プロンプト）」「形を整えるブロック（出力パーサー）」があります。すごいのは、どのブロックも差し込み口の形が同じこと。だから自由に差し替えたり、つなげたりできます。今日は、これらのブロックを1個ずつ手に取り、最後にカチッとつなげてロボット（アプリ）を組み立てます。

🎯

要するに

一言でいうと

LangChainは、LLMアプリでよく使うパターンを「部品（コンポーネント）」として提供する。すべての部品が共通の操作口（invoke・batch・stream）を持ち、差し替え可能で、組み合わせられます。

この章で身につくのは4つ。①LLMの呼び出し ②プロンプトの再利用 ③構造化出力 ④部品の組み立て方（命令型とLCEL）。これがLangChainアプリの土台です。

🧱 たとえ話：工房の合言葉「規格がそろっているから自由」

この工房のブロックは、メーカーが違っても差し込み口がぴったり同じ規格です。だから「このブロックをあのブロックに替えても」「ブロック同士をつなげても」設計をやり直さずに済みます。今日覚える4つの作業は、ブロックの使い方の基本セットです。

なぜこれが必要か／これを知ったらできること

学ぶ意味とゴール

🤔 なぜ学ぶ価値があるのか

  • LLMプロバイダーのAPIを直接叩くこともできるが、プロバイダーごとの細かな差異に悩まされる。LangChainがそれを抽象化してくれるから。
  • プロンプトをハードコード（ベタ書き）すると再利用できない。テンプレート化を知らないと、同じ文章を何度も書く羽目になるから。
  • LLMの出力がただのテキストだと、他のコードに渡しにくい。構造化（JSONなど）の方法を知ると、アプリの一部として組み込めるから。

✅ これを知ったらできるようになること

  • LangChainでLLM／チャットモデルを呼び出し、system / user / assistantの役割を使い分けられる。
  • プロンプトテンプレートで動的入力を扱い、プロンプトを再利用できる。
  • with_structured_output や出力パーサーで、JSON・CSVなど構造化された出力を得られる。
  • 共通のRunnableインターフェース（invoke/batch/stream）を理解し、命令型とLCELで部品を組み合わせられる。

3つの理由

LangChainを使う3つの理由

🧩

① 一般的なパターンが組み込み済み

CoT（考えを順に書かせる）やツール呼び出しなど、よく使うパターンのリファレンス実装が同梱。LLMを素早く試す最短ルート。

すぐ試せる
🔄

② 置き換え可能なコンポーネント

各部品は同一仕様だから、LLM・チャットモデル・出力パーサーを、コードを書き直さずに差し替えられる。

差し替え自由
🎛️

③ オーケストレーション機能

可観測性のためのコールバック、共通インターフェース、長時間実行の中断・再開・再試行。

運用を支える
ソラ
弟子・ソラ差し替えられるって、たとえば？
リク

🧱 たとえ話：差し込み口が同じだから、別メーカーのブロックでも置ける

OpenAI製のブロックとAnthropic製のブロックは、見た目や中身が少し違います。でもこの工房では、差し込み口の形（共通の規格）が同じになるよう調整されています。だから、ロボットの「頭」のブロックをOpenAI製からAnthropic製に取り替えても、土台を作り直す必要はありません。同じ作業台の上で、2社のブロックを混ぜて使うこともできます。

1.2

LangChainでLLMを使う

2種類の呼び出し口

LangChainがLLMとやり取りする入口は2種類。①LLMインターフェース（文字列を入れると続きを予測して返すだけ）と、②チャットモデルインターフェース（役割つきの双方向対話）です。

📝

① LLMインターフェース

文字列のプロンプトを入れると、その続き（予測結果）をテキストで返すだけ。シンプル。

入力＝ただの文章
💬

② チャットモデルインターフェース

役割（system / user / assistant）つきのメッセージで、双方向の対話ができる。

入力＝役割つきメッセージ

まずはLLMインターフェース

▼ このコードがやること：OpenAIのLLMを呼び出し、「The sky is（空は）」の続きを予測させる。

LLMを呼び出す（Python）
# Python
# このコードがやること: OpenAIのLLMを呼び出し、「The sky is（空は）」の続きを予測させる。
from langchain_openai.llms import OpenAI

model = OpenAI(model="gpt-3.5-turbo-instruct")

model.invoke("The sky is")  # 「空は」の続きを予測
同じことを JavaScript で（JavaScript）
// JavaScript
// 同じことを JavaScript で行う
import { OpenAI } from "@langchain/openai";

const model = new OpenAI({ model: "gpt-3.5-turbo-instruct" });

await model.invoke("The sky is");
出力例（bash）
# 出力（「空は青い！」と予測した）
Blue!

次にチャットモデルインターフェース

リク

3つの役割（ロール）

🧭

system（指示）

AIが従うべき指示・枠組み。「丁寧に答えて」など、振る舞いを設定する。

🙋

user（質問）

ユーザーからの質問やコンテンツ。HumanMessage で表す。

🤖

assistant（返答）

モデルが生成したレスポンス。AIMessage で返ってくる。

▼ このコードがやること：チャットモデルに「フランスの首都は？」と尋ねる（HumanMessage＝ユーザーからのメッセージを表す入れ物）。

チャットモデルに質問する（Python）
# Python
# このコードがやること: チャットモデルに「フランスの首都は？」と尋ねる。
# HumanMessage = 人間（ユーザー）からのメッセージを表す入れ物。
from langchain_openai.chat_models import ChatOpenAI
from langchain_core.messages import HumanMessage

model = ChatOpenAI()
prompt = [HumanMessage("フランスの首都は？")]
model.invoke(prompt)
同じことを JavaScript で（JavaScript）
// JavaScript
import { ChatOpenAI } from "@langchain/openai";
import { HumanMessage } from "@langchain/core/messages";

const model = new ChatOpenAI();
const prompt = [new HumanMessage("フランスの首都は？")];
await model.invoke(prompt);
出力例（bash）
# 出力（AIMessage = アシスタント役の返答）
AIMessage(content='フランスの首都はパリです。')
リク
先生・リク単一の文字列じゃなく、役割つきの複数メッセージを使う。代表的なメッセージ型は——HumanMessage（ユーザー役）、AIMessage（アシスタント役）、SystemMessage（システム役、AIが従う指示）、ChatMessage（任意の役割）だ。SystemMessage を組み込んでみよう。

▼ このコードがやること：SystemMessage で「感嘆符を3つ付けて答えよ」と指示し、その上で「フランスの首都は？」と尋ねる。

SystemMessageでスタイルを指定する（Python）
# Python
# このコードがやること: SystemMessage で「感嘆符を3つ付けて答えよ」と指示し、
# その上で「フランスの首都は？」と尋ねる。
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai.chat_models import ChatOpenAI

model = ChatOpenAI()
system_msg = SystemMessage(
    "あなたは優秀なアシスタントです。質問に対して3つの感嘆符を付けて回答してください。"
)
human_msg = HumanMessage("フランスの首都は？")
model.invoke([system_msg, human_msg])
同じことを JavaScript で（JavaScript）
// JavaScript
import { ChatOpenAI } from "@langchain/openai";
import { HumanMessage, SystemMessage } from "@langchain/core/messages";

const model = new ChatOpenAI();
const prompt = [
  new SystemMessage(
    "あなたは優秀なアシスタントです。質問に対して3つの感嘆符を付けて回答してください。"
  ),
  new HumanMessage("フランスの首都は？"),
];

await model.invoke(prompt);
出力例（bash）
# 出力（system の指示に従い、感嘆符が3つ付いた）

🧱 たとえ話：ブロックに2つの差し込み口がある

「文章を予想するブロック」には差し込み口が2種類あります。①シンプル口（LLM）は、紙きれ（ただの文章）を1枚差すと続きを書いて返す。②会話口（チャット）は、付箋を3色に分けて差せます——青＝ユーザーの質問、黄＝AIへの作業指示（system）、緑＝AIの返答。黄色い「作業指示メモ（SystemMessage）」を先に貼っておくと、どんな質問が来ても同じ調子で答えてくれます。

この項のまとめ

  • 入口は2種類：LLM（文字列→予測）とチャットモデル（役割つき双方向対話）。
  • チャットモデルの役割：system（指示）・user（質問）・assistant（返答）。
  • メッセージ型：HumanMessage / AIMessage / SystemMessage / ChatMessage。
  • SystemMessageで、ユーザー入力に関係なく応答スタイルを固定できる。
1.3

LLMプロンプトを再利用する

指示文のひな型

プロンプトは出力に大きく影響します。でも具体的な指示文を毎回ベタ書きするのは面倒。そこでプロンプトテンプレートを使い、「毎回同じ部分（静的テキスト）」と「差し替える部分（プレースホルダー）」を分けて書きます。

リク
先生・リクプロンプトは出力に大きく影響する。でも、こういう具体的なプロンプトを毎回ベタ書きするのは面倒だ。

▼ これは「コンテキスト」と「質問」が固定で書かれた、再利用できないプロンプトの例（テキスト）。

ベタ書きのプロンプト（text）
# コンテキスト付きの質問プロンプト（コンテキストと質問がハードコードされている）
以下のコンテキストに基づいて質問に答えてください。提供された情報で答えられない場合は
「I don't know」と答えてください。

コンテキスト: NLPの最新の進歩は大規模言語モデル（LLM）によって牽引されています。…
（中略）開発者は Hugging Face の transformers ライブラリや、OpenAI・Cohere の
ライブラリを通じてこれらのモデルを利用できます。

質問: どのモデルプロバイダーがLLMを提供していますか？

回答:
ソラ
弟子・ソラコンテキストと質問が固定されてますね。動的に変えたい……。
リク
先生・リクそこでプロンプトテンプレートだ。静的なテキストと、送信ごとに差し替えるプレースホルダーを分けて書ける。波括弧 {...} がプレースホルダーになる。

テンプレートの仕組み

1

静的テキスト＋プレースホルダーでひな型を作る

「以下のコンテキストに基づいて…」は固定。{context} と {question} は差し替え枠。

2

invoke に実際の値を渡す

▼ このコードがやること：「回答(answer)とその根拠(justification)を持つJSON」を返すようスキーマを定義し、with_structured_output でモデルに守らせる。質問は「レンガ1ポンドと羽毛1ポンド、どちらが重い？」。

with_structured_output でJSONを得る（Python）
# Python
# このコードがやること: 「回答(answer)とその根拠(justification)を持つJSON」を返すよう
# スキーマ（Pydanticモデル）を定義し、with_structured_output でモデルに守らせる。
# 質問は「レンガ1ポンドと羽毛1ポンド、どちらが重い？」。
from langchain_openai import ChatOpenAI
from pydantic import BaseModel

class AnswerWithJustification(BaseModel):
    '''ユーザーの質問への回答と、その回答の正当性（根拠）を含むデータモデル'''
    answer: str
    '''ユーザーの質問への回答'''
    justification: str
    '''回答の正当性を示す根拠'''

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_llm = llm.with_structured_output(AnswerWithJustification)
structured_llm.invoke("レンガ1ポンドと羽毛1ポンドではどちらが重いですか？")
同じことを JavaScript で（JavaScript）
// JavaScript

import { z } from "zod";

const answerSchema = z
  .object({
    answer: z.string().describe("ユーザーの質問への回答"),
    justification: z.string().describe(`回答の正当性を示す根拠`),

  .describe("ユーザーの質問への回答と、その回答の正当性（根拠）を含むデータモデル");

const model = new ChatOpenAI({

① スキーマをLLMに渡す

✅

② 出力を検証する

AIに「適当に部品を渡して」と頼むと、バラバラの形で返ってきて困ります。そこで、「ここに answer、ここに justification を入れてね」と仕切りの決まった箱（スキーマ）を先に渡します。AIはその仕切りに合わせて部品を入れて返してくれるうえ、受け取り口で「ちゃんと仕切り通りか」を検査します。これで、後工程のブロックにそのまま渡せる、形のそろった完成品が手に入ります。

1.5.1　Runnableインターフェース

リク
先生・リクここまでのコード例、全部 invoke() を使っていたことに気づいたかな。実は、モデルもプロンプトテンプレートも出力パーサーも、共通のインターフェースを持っているんだ。これがRunnableインターフェースだ。3つのメソッドがある。
ソラ
弟子・ソラ3つ？
リク
先生・リク①invoke()——単一の入力を単一の出力に変換。②batch()——複数の入力を効率よく複数の出力に変換。③stream()——単一の入力を受け取り、生成され次第その一部をストリームとして返す。さらにリトライ・フォールバック・スキーマ検証も組み込まれていて、Pythonでは各メソッドに asyncio 版がある。だから、1つの部品で覚えたインターフェースが、他のすべてに適用できる。

3つの共通メソッド

①

invoke()

単一の入力 → 単一の出力。いちばん基本の呼び方。

1個→1個
②

batch()

複数の入力 → 効率よく複数の出力。まとめて処理。

まとめて
③

stream()

単一の入力 → 生成され次第、少しずつ返す。

逐次

▼ このコードがやること：同じ model に対して invoke / batch / stream の3メソッドを使う。

3つの呼び方を試す（Python）
# Python
# このコードがやること: 同じ model に対して invoke / batch / stream の3メソッドを使う。
from langchain_openai import ChatOpenAI

model = ChatOpenAI()

completion = model.invoke('Hi there!')        # 単一入力→単一出力
# Hi!

completions = model.batch(['Hi there!', 'Bye!'])  # 複数入力→複数出力
# ['Hi!', 'See you!']

for token in model.stream('Bye!'):            # 単一入力→少しずつストリーム出力
    print(token)
    # Good
    # bye
    # !
同じことを JavaScript で（JavaScript）

  console.log(token);  // Good / bye / !
}

🧱 たとえ話：全ブロック共通の「差し込み口の形」

この工房のすごさは、どのブロックも差し込み口の形（操作のしかた）がまったく同じこと。差し込み方は3パターン——「カチッ1回（invoke）」「まとめてカチカチ（batch）」「少しずつスルスル（stream）」。一度この差し込み方を覚えれば、文章ブロックでも指示ブロックでも仕分けブロックでも、同じ手つきで扱えます。だから初めて触るブロックでも迷いません。

1.5.2　命令型コンポジション

リク
先生・リク命令型コンポジションは、部品を関数やクラスにまとめて、普段通りにコードを書く手法だ。プロンプト・モデル・（必要なら出力パーサー）を組み合わせる。

▼ このコードがやること：テンプレートとモデルを1つの関数 chatbot にまとめる（@chain デコレーターが、その関数にRunnableインターフェースを付与する）。

関数にまとめる（Python）
# Python
# このコードがやること: テンプレートとモデルを1つの関数 chatbot にまとめる。
# @chain デコレーターが、その関数に Runnable インターフェース（invoke等）を付与する。
from langchain_openai.chat_models import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import chain

# 構成要素を定義する
template = ChatPromptTemplate.from_messages([
    ('system', 'あなたは親切なアシスタントです。'),
    ('human', '{question}'),
])

model = ChatOpenAI()

# それらを関数にまとめる
@chain
def chatbot(values):
    prompt = template.invoke(values)
    return model.invoke(prompt)

# 実行例
chatbot.invoke({"question": "どのモデルプロバイダーがLLMを提供していますか？"})
同じことを JavaScript で（JavaScript）
// JavaScript
import { ChatOpenAI } from "@langchain/openai";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { RunnableLambda } from "@langchain/core/runnables";

const template = ChatPromptTemplate.fromMessages([
  ["system", "あなたは親切なアシスタントです。"],
  ["human", "{question}"],
]);

const model = new ChatOpenAI();

// RunnableLambda が、定義した関数に Runnable インターフェースを付与する
const chatbot = RunnableLambda.from(async (values) => {
  const prompt = await template.invoke(values);
  return await model.invoke(prompt);
});

await chatbot.invoke({
  question: "どのモデルプロバイダーがLLMを提供していますか？",
});

先生・リク慣れ親しんだ構文で、関数内に自由にロジックを書ける。ストリーミングしたいなら、yield を使って書き換える。

▼ このコードがやること：model.stream の結果を yield して、chatbot 自体をストリーム対応にする。

ストリーム対応にする（Python）
# Python
# このコードがやること: model.stream の結果を yield して、chatbot 自体をストリーム対応にする。
@chain
def chatbot(values):
    prompt = template.invoke(values)
    for token in model.stream(prompt):
        yield token

for part in chatbot.stream({"question": "どのモデルプロバイダーがLLMを提供していますか？"}):
    print(part)

🧱 たとえ話：自分の手で配線して、間に細工を入れる

命令型は、ブロック同士を自分の手で配線するやり方です。「指示ブロックに値を入れて → 出てきた結果を文章ブロックに渡す」という配線を、自分の作業手順書（関数）として書きます。途中に「ここでチェックを入れる」「条件で分岐する」など好きな細工を挟めるのが強み。@chain という名札を付ければ、この手作り装置にも工房共通の差し込み口（invoke等）が付きます。

命令型 vs LCEL：どっちを使う？

🔧

命令型コンポジション

関数（@chain / RunnableLambda）にまとめて、普通に書く。途中に自由なロジックを書ける。

カスタムロジックが多いとき
🔗

LCEL（宣言型）

template | model のようにパイプでつなぐ。自動で並列化・ストリーミング・最適化。

最小カスタマイズで組むとき

🧱 たとえ話：レール式で「カチッ」とつなぐ

LCELは、ブロックをレールに沿ってカチッとつなぐやり方です。指示ブロック | 文章ブロック と書くだけで、間の配線は工房が自動でやってくれます。しかも「速く流す（並列化）」「少しずつ出す（ストリーミング）」といった最適化まで自動。手で配線する命令型に比べて細かい細工はしにくいけれど、既製ブロックをサッと組むなら最速です。どちらで組んでも、完成した装置の最後の差し込み口（invoke等）は同じなので安心です。

要するに：LangChainの部品（LLM/チャットモデル・プロンプトテンプレート・出力パーサー）は、すべて共通のRunnableインターフェース（invoke/batch/stream）を持つ。組み合わせ方は2つ——命令型（関数にまとめて普通に書く、カスタムロジック向き）とLCEL（| でつなぐ宣言型、最小カスタマイズで自動最適化）。

この項のまとめ

  • すべての部品は共通のRunnableインターフェース：invoke（単一）・batch（複数）・stream（逐次）。リトライ・フォールバック等も組み込み。
  • 命令型コンポジション：関数（@chain/RunnableLambda）にまとめて普通に書く。カスタムロジックを多く書きたいとき向き。
  • LCEL（宣言型）：template | model のようにパイプでつなぐ。自動並列化・ストリーミング・非同期。最小カスタマイズ向き。
  • どちらも最後の呼び出し方（invoke/stream/batch）は同じ。

自分の言葉で答えてみよう

読み終わったあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問なぜLangChainか

LLMプロバイダーのAPIを直接叩けるのに、なぜLangChainを使う価値があるのですか。理由を挙げて説明してください。

✅ 解答例
理由は3つ。①組み込みパターン：CoTやツール呼び出しなどよく使うパターンのリファレンス実装が同梱され、素早く試せる。②置き換え可能なコンポーネント：LLM・チャットモデル・出力パーサーなどが同一仕様なので、コードを書き直さずに差し替えられ、プロバイダーロックインを避けられる（OpenAIとAnthropicを同じ会話で使うことすら可能）。③オーケストレーション：可観測性のためのコールバック、共通インターフェース、長時間実行の中断・再開・再試行。
📝 採点ポイント
□ 組み込みパターン（リファレンス実装）に触れている
□ 差し替え可能なコンポーネント（プロバイダーロックイン回避）に触れている
□ オーケストレーション（共通インターフェース等）に触れている
第2問2つのインターフェース

LLMインターフェースとチャットモデルインターフェースの違いを説明してください。チャットモデルの3つの役割（ロール）も挙げてください。

✅ 解答例
LLMインターフェースは、文字列プロンプトを入力に受け取り、予測結果（テキスト）を返すだけのシンプルなもの。チャットモデルインターフェースは、ユーザーとモデルの双方向の対話ができ、メッセージをsystem（モデルへの指示・枠組み）・user（ユーザーの質問やコンテンツ）・assistant（モデルが生成したレスポンス）の3つの役割に分けて扱う。SystemMessageで一貫した応答スタイルをあらかじめ設定できる。
📝 採点ポイント
□ LLM＝文字列入力→予測、チャット＝役割つきの双方向対話、の違いに触れている
□ system/user/assistantの3役割を挙げている
□ SystemMessageで応答スタイルを設定できる、に触れている（できれば）
第3問プロンプトテンプレート

プロンプトテンプレートを使うと何が嬉しいのですか。{context} のようなプレースホルダーの役割とともに説明してください。

✅ 解答例
プロンプトテンプレートを使うと、プロンプトの「静的なテキスト（毎回同じ部分）」と「送信ごとに差し替える部分」を分けて書ける。{context} や {question} のような波括弧で囲んだ部分がプレースホルダーで、invoke に渡した値で実行時に置換される。これにより、同じプロンプトを毎回ベタ書きせずに再利用でき、コンテキストや質問だけを動的に変えられる。テンプレートは「複数の具体的なプロンプトを生成するレシピ」のようなもの。
📝 採点ポイント
□ 静的テキストとプレースホルダーを分けて書ける、に触れている
□ プレースホルダーが実行時に値で置換される、に触れている
□ プロンプトを再利用できる、に触れている
第4問構造化出力

なぜLLMにJSONなどの構造化された出力をさせたいのですか。with_structured_output は何をしてくれますか。

✅ 解答例
プレーンテキストではなくJSONなど構造化された形式で出力させると、その出力を他のコードにそのまま渡せて、フロントエンドへの送信やDBへの保存ができ、LLMを大規模アプリの一部として組み込める。with_structured_output は、定義したスキーマ（PythonはPydantic、JavaScriptはZod）をJSON Schemaに変換してLLMに渡し、さらに返ってきた出力を同じスキーマで検証する。これにより、LLMがスキーマ通りの形式を確実に返してくれる。
📝 採点ポイント
□ 構造化出力は他のコードに渡せてアプリに組み込める、に触れている
□ スキーマをLLMに渡す、に触れている
□ 返ってきた出力をスキーマで検証する、に触れている
第5問命令型とLCEL

部品を組み合わせる「命令型」と「LCEL（宣言型）」の違いを説明し、それぞれどんなときに向くかを述べてください。

✅ 解答例
命令型は、部品を関数（@chainやRunnableLambda）にまとめて、普段通りのPython/JavaScript構文で書く方法。関数内に自由にロジックを書けるので、カスタムロジックを多く書きたいときに向く。LCEL（宣言型）は、template | model のようにパイプ演算子で部品をつなぐ方法で、自動並列化・ストリーミング・非同期をサポートし、最適化された実行計画にコンパイルされる。既存の部品を最小限のカスタマイズで組み立てたいときに向く。どちらも最後の呼び出し方（invoke/stream/batch）は同じ。
📝 採点ポイント
□ 命令型＝関数にまとめて普通に書く、カスタムロジック向き、に触れている
□ LCEL＝パイプでつなぐ宣言型、自動最適化、最小カスタマイズ向き、に触れている
□ どちらも呼び出し方は共通、に触れている（できれば）
