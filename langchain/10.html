あらすじ・要するに・なぜ必要か

デプロイは「ゴール」ではなく「本当のスタート」

前章でソラはアプリを本番にデプロイした。だがリク先輩いわく「ここからが本当のスタート」。 LLMは同じ質問でも違う答えを返し、平気でウソをつく。今日は、その気まぐれなAIの品質を保ち続ける仕組みを学ぶ。

ソラ
弟子・ソラついに本番にデプロイできました！もう完成ですね！
リク
師匠・リク先輩おめでとう。……でも残念ながら、ここからが本当のスタートなんだ。LLMは「決定論的じゃない」。同じ質問でも毎回同じ答えとは限らないし、もっともらしいウソもつく。だからテスト・評価・監視・修正を回し続ける仕組みが要る。

⚠️ なぜ必要か / 放っておくと何が起きるか

  • LLMは決まった答えを返さない上に、もっともらしいハルシネーション（ウソ）を平気で言う → ユーザーに誤情報が届く。
  • その誤りは会社のブランドや顧客の信頼を一気に損なう大きなリスクになる。
  • 品質を測り続ける仕組みがないと、性能が劣化していても気づけない。

✅ これを知ったらできること

  • アプリ自身がエラーに気づいて直す仕組み（自己修正RAG）を組める。
  • 本番に出す前に「前より悪くなっていないか」を自動チェックできる。
  • 本番稼働中のAIを監視し、問題を改善ループへ戻せる。
10.1

開発サイクルにおけるテストテクニック

設計・検証・本番運用 ― 3フェーズで役割が違う

要するに：LLMアプリのテストは「設計」「検証」「本番運用」の3フェーズで役割が異なり、3つがつながって継続的改善サイクルを形作る。

3つのフェーズと、それぞれの目的

① 設計フェーズ

アプリを作っている真っ最中。テストを実行時アサーション（その場の合否チェック）として組み込み、失敗をLLMに伝えて自己修正させる。

目的：エラーがユーザーに届く前にアプリ内で処理する
→

② 検証フェーズ

本番にデプロイする直前のテスト。実ユーザーに公開する前に問題を洗い出す。

目的：リグレッション（前より性能が悪くなること）を見つけて直す
→

③ 本番運用フェーズ

実際にユーザーが使っている状態を監視するテスト。実ユーザーに影響するエラーを検知する。

目的：見つけた問題を①②へフィードバックする
🔁 設計 → テスト → デプロイ → モニタリング → 修正 → 再設計 …… この輪が継続的改善サイクル

🍳 たとえ話：新しい料理をお店で出すまで

① 設計＝キッチンで作りながら自分で味見する。変だったらその場で直す。② 検証＝お客さんに出す直前に、いつもの味より落ちていないか試食する。③ 本番運用＝実際にお客さんに出して、感想を集める。そして集めた声をまたレシピ改良に活かす。

AIアプリのテストも、これとまったく同じ「3段階＋ぐるぐる改善」なんです。

ソラ
テストって普通のプログラムでも書きますよね。何が違うんですか？
リク
LLMは気まぐれだから、テストを1か所だけやっても品質は守れない。開発の各段階に合ったテストを置く必要があるんだ。

📌 この項のまとめ

  • 設計＝開発中。実行時アサーションで、エラーがユーザーに届く前に自己修正させる。
  • 検証＝デプロイ直前。リグレッション（性能の後退）を見つけて直す。
  • 本番運用＝稼働中。実ユーザーへの影響を監視し、前2フェーズにフィードバック。
  • この3つがつながり、設計→テスト→デプロイ→監視→修正→再設計の改善サイクルになる。
10.2

設計フェーズ ― 自己修正RAG

LLM自身に良し悪しを採点させ、ダメなら別の手段へ切り替える

要するに：設計フェーズでは、LLM自身に検索結果や答えの良し悪しを採点させ、ダメなら別の手段に切り替える「自己修正RAG」をLangGraphで組む。判定結果は構造化して制御フローの分岐に使う。

ソラ
「アプリが自己修正する」って、具体的にどうやるんですか？
リク
RAGは検索が不正確だとハルシネーションを起こしやすい。そこでLLM自身に「検索した情報は本当に質問に関係あるか？」を評価させ、LangGraphで制御フロー（処理の流れ）を組む。これが自己修正RAGだ。

自己修正RAG の流れ

1

ルーティング

質問を適切な検索方法（ベクトルストア検索 or Web検索）に振り分ける。

2

ドキュメント検索＋関連性の採点

ベクトルストアでドキュメントを検索し、その関連性をLLMが yes/no で採点する。

no（無関係）→ ⑤ Web検索にフォールバック
3

回答を生成

関連ありと判断したら、その情報をもとに答えを生成する。

4

ハルシネーション確認

生成した答えがウソでないか・質問に答えているかを確認する。

正確で適切 → ✅ ユーザーに見せる
ウソ／質問に答えていない → ⑤ Web検索にフォールバック
5

Web検索にフォールバック（切り替え）

transform_query ノードで質問をWeb検索向けに書き換え、情報を取り直して再挑戦。繰り返しながら品質を上げる。

🍳 たとえ話：注文を受けた慎重な料理人

自己修正RAGは、すごく慎重な料理人のようなもの。①まず冷蔵庫から食材を取り出し（検索）、②「この食材、この注文に本当に合う？」と確かめ（関連性チェック）、③料理を仕上げ、④盛り付け前に味見し（おかしくないか確認）、⑤イマイチなら別の食材を買い直す（Web検索に切り替え）。この「確かめて、ダメなら戻る」を繰り返すから、変な料理（ハルシネーション）がお客さんに出ないんです。

コード①：3つのブログ記事をインデックス化

記事を読み込み → 250文字ごとに小さく分割 → ベクトルストアに入れて検索できるようにする準備。

▶ Python を表示
# 3つのブログ記事を読み込み → 小さく分割 → 検索できるようにする
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.document_loaders import WebBaseLoader
from langchain_community.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings

urls = [
    "https://blog.langchain.dev/top-5-langgraph-agents-in-production-2024/",
    "https://blog.langchain.dev/langchain-state-of-ai-2024/",
    "https://blog.langchain.dev/introducing-ambient-agents/",
]
# 各URLを読み込み、入れ子のリストを1本に平らにする
docs = [WebBaseLoader(url).load() for url in urls]
docs_list = [item for sublist in docs for item in sublist]

# 長い記事を250文字ごとの小さなチャンクに切り分ける
text_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=250, chunk_overlap=0)
doc_splits = text_splitter.split_documents(docs_list)

# ベクトルストアに追加（各チャンクを埋め込みベクトルにして保存）
vectorstore = InMemoryVectorStore.from_documents(
    documents=doc_splits, embedding=OpenAIEmbeddings())
retriever = vectorstore.as_retriever()

results = retriever.invoke(
    "2024年に本番環境で使用されている2つのLangGraphエージェントは何ですか？")
print("検索結果: \n", results)
▶ JavaScript を表示
// URLから記事を読み込み、分割し、ベクトルストアに入れる
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { OpenAIEmbeddings } from "@langchain/openai";
import { MemoryVectorStore } from "langchain/vectorstores/memory";
import { CheerioWebBaseLoader } from "@langchain/community/document_loaders/web/cheerio";

const urls = [
  "https://blog.langchain.dev/top-5-langgraph-agents-in-production-2024/",
  "https://blog.langchain.dev/langchain-state-of-ai-2024/",
  "https://blog.langchain.dev/introducing-ambient-agents/",
];

const loadDocs = async (urls) => {
  const docs = [];
  for (const url of urls) {
    const loader = new CheerioWebBaseLoader(url);
    docs.push(...(await loader.load()));
  }
  return docs;
};
const docsList = await loadDocs(urls);

const textSplitter = new RecursiveCharacterTextSplitter({ chunkSize: 250, chunkOverlap: 0 });
const docSplits = await textSplitter.splitDocuments(docsList);

const vectorstore = await MemoryVectorStore.fromDocuments(docSplits, new OpenAIEmbeddings());
const retriever = vectorstore.asRetriever();

const question = "2024年に本番環境で使用されている2つのLangGraphエージェントは何ですか？";
const docs = await retriever.invoke(question);
console.log("検索したドキュメント: \n", docs[0]?.page_content);

コード②：検索結果の関連性を yes/no で採点（構造化出力）

採点結果を binary_score（yes か no）という形に固定するのがポイント。プログラムで扱える形にして制御フローの分岐に使う。

▶ Python を表示
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field

# データモデル: 採点結果を yes/no の文字列に固定する
class GradeDocuments(BaseModel):
    """取得したドキュメントの関連性確認のためのバイナリスコア"""
    binary_score: str = Field(
        description="ドキュメントは質問に関連していますか、'yes' または 'no'")

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_llm_grader = llm.with_structured_output(GradeDocuments)

system = """あなたは、取得したドキュメントがユーザーの質問にどれだけ関連しているかを評価する採点者です。
ドキュメントに質問に関連するキーワードや意味内容が含まれていれば、関連ありとして評価してください。
「yes」または「no」のバイナリスコアを付けてください。"""

grade_prompt = ChatPromptTemplate.from_messages([
    ("system", system),
    ("human", "取得したドキュメント: \n\n {document} \n\n ユーザーの質問: {question}"),
])

retrieval_grader = grade_prompt | structured_llm_grader
question = "agent memory"
docs = retriever.invoke(question)
doc_txt = docs[0].page_content
retrieval_grader.invoke({"question": question, "document": doc_txt})
▶ JavaScript を表示
// 同じ採点器を Zod スキーマで。binary_score(yes/no)に固定する
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { z } from "zod";
import { ChatOpenAI } from "@langchain/openai";

const GradeDocumentsSchema = z.object({
  binary_score: z.string().describe("ドキュメントは質問に関連していますか、'yes' または 'no'"),
});

const llm = new ChatOpenAI({ model: "gpt-4o-mini", temperature: 0 });
const structuredLLMGrader = llm.withStructuredOutput(GradeDocumentsSchema);

const systemMessage = `あなたは、取得したドキュメントがユーザーの質問にどれだけ関連しているかを評価する採点者です。
「yes」または「no」のバイナリスコアを付けてください。`;

const gradePrompt = ChatPromptTemplate.fromMessages([
  { role: "system", content: systemMessage },
  { role: "human", content: "取得したドキュメント: \n\n {document} \n\n ユーザーの質問: {question}" },
]);

const retrievalGrader = gradePrompt.pipe(structuredLLMGrader);
const question = "agent memory";
const docs = await retriever.invoke(question);
await retrievalGrader.invoke({ question, document: docs[1]?.pageContent });

ソラ
出力が binary_score='yes' って、ちゃんと決まった形で返ってきてますね。
リク
ここが大事。Pydantic（Python）や Zod（JS）で2択の判断をプログラムで扱える形にしている。これで「yesなら生成ノードへ、noならWeb検索へ」と分岐できる。LangSmithを使えばノード間のトレースを画面で見ながらデバッグできるよ。

⚠️ なぜ必要か

  • 検索ベースのRAGは検索のズレでハルシネーションを起こしやすい → アプリ自身に品質チェックさせる必要がある。
  • LLMの判定を構造化出力にすると、その結果でグラフの分岐を制御できる。

📌 この項のまとめ

  • 自己修正RAG＝「ルーティング → 検索 → 関連性採点 → 生成 → ハルシネーション確認 → ダメならWeb検索にフォールバック」。
  • LLMに関連性を yes/no で採点させ、Pydantic/Zod で構造化出力にする。
  • 構造化された判定結果で、LangGraph の制御フローの次ノードを決める。
  • LangSmith でノード間のトレースを可視化しデバッグできる。

10.3.1

データセットを作成する

「入力」と「期待される出力」のペア集 ＝ お手本集

要するに：検証の前に「入力」と「期待される出力」のペアを集めたデータセットを用意する。作り方は3つ、LangSmith には3種類のデータセット形式がある。

🍳 たとえ話：料理の「完成見本」

データセットは、お店のマニュアルにある「注文」と「完成見本の写真・正解レシピ」のセットだと思ってください。見本がなければ、出来上がった料理が正解かどうか比べようがありませんよね。AIアプリも同じで、まず「この注文にはこう仕上げてほしい」という見本集を用意して、はじめて味（性能）を採点できるのです。

データセットの作り方 ― 3つ

✍️

① 手動で作る

想定ユーザー入力と理想の答えを人が手で書く。高品質なものを10〜50個用意し、運用で見つかったエッジケースを少しずつ足す。

小さく始める
🗂️

② アプリログから作る

本番が動き出したら実際のユーザー入力を記録し、後からデータセットに足す。現実的でよくある質問を集められる。

実データで育てる
🧪

③ 合成データ

いろんなシナリオやエッジケースを真似て擬似生成したデータ。実データが足りないときに役立つ。

不足を補う

種類形向いている用途
kv（key-value）
★おすすめ・デフォルト		好きなキーと値のペア一番汎用的。複数の入出力を持つチェーンやエージェントの評価に向く
llmプロンプト1つ・レスポンス1つシンプルに言語モデルを評価する用
chatチャットメッセージのやり取りチャットボット向け

［Datasets and Testing］→［+ New Dataset］で作成。CSVアップロードや、［Add Example］でJSONによる入出力追加もできる。迷ったら最も柔軟な kv。

⚠️ なぜ必要か

  • 「正解」のセットがないと、出力が良いか悪いか測りようがない。
  • 作り方と種類を知ると、自分のアプリに合った評価基盤を準備できる。

📌 この項のまとめ

  • データセット＝入力と期待される出力のペア集。
  • 作り方は ①手動 ②アプリログ ③合成データ。手動で小さく始めて実データで育てる。
  • LangSmith は kv / llm / chat の3種類。最も柔軟なのは kv。
10.3.2

評価基準を定義する

出力を「どう採点するか」＝ 3種類の評価器

要するに：評価器には「人間」「ヒューリスティック（コードによる計算）」「LLM-as-a-judge（AIによる採点）」の3種類がある。あらかじめ用意したテスト一式でまとめて評価することを「オフライン評価」と呼び、各データに正解（グラウンドトゥルース）をラベル付けして突き合わせる。

3種類の評価器

🧑‍⚖️

① 人間の評価器

コードで表せない定性的な良し悪し（文章の自然さなど）を人がスコア付け。LangSmith のアノテーションキューで効率よく集める。

⚙️

② ヒューリスティック評価器

ハードコードした関数やアサーションで計算。「出力が正しいJSONか」のように正解不要のものと、正解と突き合わせるものがある。スキーマチェックなどコード生成に便利。

🤖

③ LLM-as-a-judge

人間の採点ルールをLLMのプロンプトに組み込み、「この答えは正解に照らして正しいか」をLLMに評価させる。

導入順とコツ

1

ヒューリスティック評価器

まずはシンプルなものから始める。

2

人間の評価器

定性的な基準を固める。

3

LLM-as-a-judge へ移行

人間の採点を自動化。基準がしっかり固まってから規模を広げる。

⚠️ コツ：「0〜10点で採点して」のような曖昧な指示は避ける。人間が再現しやすいシンプルなプロンプトにする。
ソラ
確かに、10点と8点の違いって人間でも説明しにくいですもんね……。

⚠️ なぜ必要か

  • どんな指標で採点するか決めないと、性能を客観的に比較できない。
  • 3種の使い分けを知ると、自動採点を段階的に構築できる。

📌 この項のまとめ

  • オフライン評価＝用意したテスト一式でまとめて評価。正解（グラウンドトゥルース）と突き合わせる。
  • 評価器は ①人間 ②ヒューリスティック ③LLM-as-a-judge。
  • 導入順は ヒューリスティック → 人間 → LLM-as-a-judge。
  • LLM-as-a-judge では曖昧なスコア指示を避け、再現しやすいシンプルなプロンプトに。
10.3.2.1

LLM-as-a-judge のパフォーマンスを向上させる

人間の修正を Few-shot の例として貯める

要するに：LLM-as-a-judge の精度は、人間の修正を Few-shot（少数の例）として貯めて次回のプロンプトに組み込むことで、徐々に人間の好みに近づけられる。

ソラ
AIが採点した結果ってどこまで信用できるんですか？
リク
まさにそこが問題。精度を上げるにはプロンプト改良に手間がかかる。そこでLangSmith は「Few-shotプロンプト」を用意している。人間がした修正をお手本として保存し、次回以降の採点に組み込めるんだ。

自己改善の流れ

1

LLM評価器が採点

答えを採点してフィードバックを出す。

2

人間が修正を加える

人間の好みや判断を反映する。

3

Few-shot の例として保存

その修正を LangSmith に保存。理由のメモも付けられる。

4

次回プロンプトに組み込み

保存した例が次回以降のプロンプトに自動で組み込まれ、使うほど人間の好みに近づく。

設定：［Datasets and Testing］→対象データセット→［Add Auto-Evaluator］→ LLM-as-a-judge を選択→［Create Few-Shot Evaluator］。修正を貯めるデータセットが自動生成され、採点基準は整数やブール（真偽値）で指定できる。

📌 この項のまとめ

  • LLM-as-a-judge の信頼性向上には Few-shot プロンプトが有効。
  • 人間の修正をお手本として保存し、次回以降の採点に組み込む。
  • 使うほど人間の好みに整合し、プロンプト改良の手間を減らせる。
10.3.2.2

ペアワイズ評価

絶対点ではなく「2つを並べてどっちが良いか」

要するに：ペアワイズ評価は、2つの出力を並べてどちらが優れているかを比べる方法。絶対的な点数付けより認知負荷が低く、LangSmith がネイティブ対応している。

😵

絶対スコア（つらい）

「この答えは80点」と1個に点を付ける。基準が分かりにくく、人にもLLMにも負担が大きい。

⚖️

ペアワイズ（楽）

「AとB、どっちが有益？具体的？安全？」と2つを比べる。「どっちが好き？」なら答えやすい。

LangSmith は違うバージョンのアプリの出力を並べて可視化。［Pairwise Experiments］タブで各ペアの詳細を見られ、［RANKED_PREFERENCE］スコアをクリックすれば各評価の履歴も追える。

📌 この項のまとめ

  • ペアワイズ評価＝2つの出力を比較し、どちらが基準を満たすか判断。
  • 絶対スコアより人間・LLM の負担が小さい。
  • LangSmith の［Pairwise Experiments］タブで比較・可視化できる。
10.3.3

リグレッションテスト

「100%合格」ではなく「前より悪くなっていないか」

要するに：AIはドリフト（データ分布の変化やモデル更新で結果が変わること）があるので「100%合格」を前提にできない。代わりに、ベースライン（基準にする過去バージョン）と比べて性能が後退していないかを見るリグレッションテストを行う。

🍳 たとえ話：看板メニューの味、落ちてない？

レシピを少し変えたとき、大事なのは「満点の味かどうか」より「いつもの看板メニューより味が落ちていないか」ですよね。AIも、プロンプトやモデルをいじると、知らないうちに前より悪くなることがあります。だから「100点満点」ではなく「前のバージョンより味が後退していないか」を確かめるのです。

🖥️

従来のソフトウェア

テストが100%パスすれば安定動作を保証できる。絶対評価。

🤖

AIアプリ

ドリフトで結果が変わるので、評価データセットで必ずしも100%パスしない。前バージョンとの比較が基準。

ソラ
えっ、じゃあ何を基準にすればいいんですか？
リク
「100%合格」じゃなく「前より悪くなっていないか」を見る。LangSmith の比較ビューがこれをサポートしていて、後退した実行と改善した実行が色違いでハイライトされる。［Comparing Experiments］ダッシュボードでベースラインを設定して予期せぬ後退を検出できる。モデルやプロンプトを乗り換えるとき特に役立つ。

⚠️ なぜ必要か

  • LLMやプロンプトを更新したとき、知らないうちに性能が下がる危険がある。それを検出する。
  • これを知ると、アプリを長期間にわたり高性能に保てる。

📌 この項のまとめ

  • 従来テストは100%パスを期待するが、AIはドリフトで結果が変わるためそうはいかない。
  • リグレッションテスト＝更新がベースラインに対して後退していないかを保証する。
  • LangSmith の比較ビューで、後退・改善した例を色分けして確認できる。
10.3.4

エージェントのエンドツーエンド評価

最終結果だけでなく「途中の動き」も見る ― 3つの粒度

要するに：エージェントは制御フローの判断にLLMを使うため毎回結果が大きく変わる（呼ぶツール・ループ・ステップ数がバラつく）。だから理想的には3つの粒度（細かさ）でテストする。

📦

① レスポンス

最終的な答えに注目。エージェントをブラックボックスとして扱い、タスクを完了できたかで判断。
入力＝プロンプト(＋ツール)、出力＝最終レスポンス。

🔍

② 単一ステップ

特定のツール呼び出しや判断1つを深掘り。
出力＝ツール呼び出し。

🧭

③ 軌跡（トラジェクトリ）

辿った全ステップを見る。
出力＝ツール呼び出しのリスト。

➡️

def predict_sql_agent_messages(example: dict):
    msg = {"messages": ("user", example["input"])}
    messages = graph.invoke(msg, config)
    return {"response": messages}

def find_tool_calls(messages):
    """返ってきたメッセージから、呼ばれたツール名を全部拾う"""
    return [tc['name']
        for m in messages['messages'] for tc in getattr(m, 'tool_calls', [])]

expected = ['sql_db_list_tables', 'sql_db_schema',
            'sql_db_query_checker', 'sql_db_query', 'check_result']

# ① 順不同で全部呼ばれたか
def contains_all_tool_calls_any_order(root_run: Run, example: Example) -> dict:
    tool_calls = find_tool_calls(root_run.outputs["response"])
    score = 1 if set(expected) <= set(tool_calls) else 0
    return {"score": int(score), "key": "multi_tool_call_any_order"}

# ② 正しい順番で全部呼ばれたか
def contains_all_tool_calls_in_order(root_run: Run, example: Example) -> dict:
    tool_calls = find_tool_calls(root_run.outputs["response"])
    it = iter(tool_calls)
    score = 1 if all(elem in it for elem in expected) else 0
    return {"score": int(score), "key": "multi_tool_call_in_order"}

# ③ 正しい順かつ余計な呼び出しなしで完全一致か
def contains_all_tool_calls_in_order_exact_match(root_run: Run, example: Example) -> dict:
    tool_calls = find_tool_calls(root_run.outputs["response"])
    score = 1 if tool_calls == expected else 0
    return {"score": int(score), "key": "multi_tool_call_in_exact_order"}

experiment_results = evaluate(
    predict_sql_agent_messages, data=dataset_name,
    evaluators=[contains_all_tool_calls_any_order,
                contains_all_tool_calls_in_order,
                contains_all_tool_calls_in_order_exact_match],

import { evaluate } from "langsmith/evaluation";

function predictSqlAgentMessages(example) {
  const msg = { messages: [{ role: "user", content: example.input }] };
  const messages = graph.invoke(msg, config);
  return { response: messages };
}

function findToolCalls({ messages }) {
  return messages.flatMap((m) => m.tool_calls?.map((tc) => tc.name) || []);
}

const expected = ["sql_db_list_tables", "sql_db_schema",
  "sql_db_query_checker", "sql_db_query", "check_result"];

// ① 順不同で全部
function containsAllToolCallsAnyOrder(rootRun, example) {
  const toolCalls = findToolCalls(rootRun.outputs.response);
  const score = expected.every((tool) => toolCalls.includes(tool)) ? 1 : 0;
  return { score, key: "multi_tool_call_any_order" };
}

// ② 正しい順番で全部
function containsAllToolCallsInOrder(rootRun, example) {
  const toolCalls = findToolCalls(rootRun.outputs.response);
  const score = expected.every((tool) => {
    let found = false;
    for (let call of toolCalls) { if (call === tool) { found = true; break; } }
    return found;
  }) ? 1 : 0;
  return { score, key: "multi_tool_call_in_order" };
}

// ③ 完全一致
function containsAllToolCallsInOrderExactMatch(rootRun, example) {
  const toolCalls = findToolCalls(rootRun.outputs.response);
  const score = JSON.stringify(toolCalls) === JSON.stringify(expected) ? 1 : 0;
  return { score, key: "multi_tool_call_in_exact_order" };
}

const experimentResults = evaluate(predictSqlAgentMessages, {
  data: datasetName,
  evaluators: [containsAllToolCallsAnyOrder, containsAllToolCallsInOrder,
               containsAllToolCallsInOrderExactMatch],
  numRepetitions: 3 });
ソラ
「順不同でOK」「順番もぴったり」「余計なものも無しで完全一致」の3段階で厳しさを変えられるんですね。
リク
タスクによって、順番が大事なときと呼びさえすればいいときがあるからね。どれもLangSmith の画面で確認・デバッグできる。エージェントはツール呼び出しがばらつきやすいから、こうしたテストでコスト増や信頼性低下を防ぐんだ。

⚠️ なぜ必要か

  • エージェントは実行ごとに動きが大きく変わるので、最終結果だけ見ても原因が分からない。途中も見る必要がある。
  • 3粒度のテストを知ると、問題箇所を特定し、コスト増や暴走を防げる。

📌 この項のまとめ（10.3.4 全体）

  • エージェント評価の3粒度：レスポンス（最終結果）／単一ステップ（個々の判断）／軌跡（全ステップの並び）。
  • 最終レスポンスはブラックボックスとして LLM-as-a-judge で評価。
  • 単一ステップは「最初のツールが期待通りか」を確認。
  • 軌跡は「順不同／順序通り／完全一致」の3種類の厳しさで評価できる。
  • num_repetitions で複数回実行し、ばらつきを考慮する。

章末の理解度チェック

自分の言葉で答えてみよう ― 詰まる問題こそ伸びしろ
第1問3つのフェーズ

「設計」「検証」「本番運用」の3フェーズは、それぞれ何のためにテストを行うのか説明してください。

✅ 解答例
設計フェーズは、開発中のアプリにエラー処理を組み込み、エラーがユーザーに届く前にLLMに自己修正させるためのテストを行う。検証フェーズは、デプロイ直前に、前のバージョンより性能が悪くなっていないか（リグレッション）を見つけて直すためのテストを行う。本番運用フェーズは、実ユーザーに影響するエラーを監視・検知し、その結果を設計・検証フェーズにフィードバックするためのテストを行う。3つがつながって継続的改善のサイクルになる。
📝 採点ポイント
□ 設計＝ユーザーに届く前の自己修正 ／ □ 検証＝デプロイ直前のリグレッション検出 ／ □ 本番運用＝稼働中の監視とフィードバック ／ □ 3つがつながって改善サイクルになる
第2問自己修正RAG

設計フェーズで作る「自己修正RAG」とはどういう仕組みか、なぜ必要なのかを説明してください。

✅ 解答例
基本的なRAGは、検索してきた情報が不正確だったり不足していると、もっともらしいウソ（ハルシネーション）を起こしやすい。自己修正RAGは、LLM自身に「検索結果は質問に関連しているか」「生成した答えはハルシネーションでないか」を採点させ、ダメならWeb検索などにフォールバックして情報を取り直す仕組み。LangGraphで制御フローを組み、採点結果を構造化出力にして次にどのノードへ進むかを判断する。これにより繰り返し答えを作りながら自己修正し、出力品質を上げられる。
📝 採点ポイント
□ RAGはハルシネーションを起こしやすい前提 ／ □ LLM自身に関連性や答えを採点させる ／ □ ダメなときにフォールバック（Web検索など） ／ □ LangGraphと構造化出力で分岐を制御
第3問リグレッションテスト

AIアプリのテストが、従来のソフトウェアのように「100%合格」を前提にできないのはなぜですか。代わりに何を見ますか。

✅ 解答例
AIモデルの出力は、データ分布の変化やモデルの更新による劣化（ドリフト）で結果が大きく変わることがあるため、評価データセットで必ずしも100%合格するとは限らない。そこで絶対的な合格ではなく「ベースライン（基準にする過去のバージョン）に対して性能が後退していないか」を見るリグレッションテストを行う。LangSmith の比較ビューで、後退した実行と改善した実行を色分けで確認できる。
📝 採点ポイント
□ ドリフト（分布変化やモデル更新による劣化）で結果が変わる ／ □ だから100%合格を前提にできない ／ □ ベースラインとの比較で後退を見る
第4問エージェントの3粒度テスト

エージェントをテストする3つの粒度「レスポンス」「単一ステップ」「軌跡」は、それぞれ何を見るものですか。

✅ 解答例
レスポンスは、エージェントを中身の見えない箱として扱い、最終的な答えでタスクを完了できたかを見る（LLM-as-a-judgeで評価）。単一ステップは、特定のツール呼び出しや判断1つを深掘りし、正しいツールを選んだかを見る。軌跡は、エージェントが辿った全ステップ（どのツールをどの順番で呼んだか）を見て、期待通りの流れだったかを評価する。
📝 採点ポイント
□ レスポンス＝最終的な答え/タスク完了 ／ □ 単一ステップ＝個々のツール呼び出しや判断 ／ □ 軌跡＝全ステップの並び/順番
第5問オフライン評価とオンライン評価

検証フェーズの「オフライン評価」と本番運用フェーズの「オンライン評価」は何が違いますか。

✅ 解答例
オフライン評価は、あらかじめ用意したテストデータセットを使い、各データに「期待される出力（グラウンドトゥルース＝正解）」をラベル付けして、アプリの答えと正解を比べる方式。本番前に一括（バッチ）で行う。一方オンライン評価は、本番には比べるための正解が存在しないため、ユーザー入力を処理するリアルタイムで性能をスコアリングする方式。ユーザーフィードバックやLLM-as-a-judgeを使って、正解なしで品質を評価する。
📝 採点ポイント
□ オフライン＝事前データセット＋正解との比較 ／ □ オンライン＝本番でリアルタイム・正解なし ／ □ オンラインではユーザーフィードバックやLLM-as-a-judgeを使う
🌱
