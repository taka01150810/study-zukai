10.1

開発サイクルにおけるテストテクニック

3つの段階、3つの目的

要するに：テストは、開発の3つの段階それぞれで役割が違います。3つがつながって、ぐるぐる回る輪になります。

ソラ

段階いつ目的やること
設計作っている最中誤りを利用者に届かせないその場での合否チェック→失敗をLLMに伝えて自己修正

🟢 この項のまとめ

  • 設計の段階＝開発中。その場での合否チェックで、誤りが利用者に届く前に自己修正させる。
  • 検証の段階＝公開の直前。前より悪くなっていないかを見つけて直す。
  • 本番運用の段階＝稼働中。利用者への影響を監視し、前の2段階に返す。
  • この3つがつながり、設計→テスト→公開→監視→修正→再設計の改善の輪になる。

設計フェーズ

アプリ自身に採点させ、駄目なら切り替える

要するに：自己修正RAGを組みます。検索結果が質問に関係あるかをLLMに採点させ、駄目ならWeb検索に切り替えて取り直します。

ソラ
ソラ設計の段階の「アプリが自己修正する」って、具体的にどうやるんですか？
リク
リクRAGを例にしよう。RAGは、質問に答えるために関係する情報を検索してきて、それを材料にLLMが答えを作る仕組みだったね。でも、検索が的外れだったり情報が足りなかったりすると、嘘を作りやすい。
ソラ
ソラありそうですね……。検索がズレてたら答えもズレますもんね。
リク
リクそこでLLM自身に「検索してきた情報は本当に質問に関係あるか？」を採点させる。そしてLangGraphで処理の流れを組むんだ。これが「自己修正RAG」だ。
1

振り分け

質問を、適切な探し方（ベクトルストア検索か、Web検索か）に振り分けます。

2

検索して、関連性を採点する

ベクトルストア検索に回ったら資料を探し、その関連性をLLMが採点します。

3

答えを作る

関連ありと判断したら、その情報をもとに答えを作ります。

関連なしと判断されたら、5へ（Web検索に切り替え）。
4

嘘でないか確認する

作った答えが渡した資料に基づいているかを確認し、正確で適切なときだけ利用者に見せます。

問題なければ、ここで終了。
質問に答えられていなければ、5へ。
5

Web検索に切り替える

質問をWeb検索向けに書き換えて、情報を取り直します。そして2に戻ります。

ソラ
ソラおお、何重にもチェックが入ってる……！ダメだったらやり直すんですね。
リク
リクそう。繰り返し答えを作りながら自己修正して、出力の質を上げていくんだ。まずは題材として、3つのブログ記事を検索できる形に整えてみよう。

# 切り分け役、Web読み取り役、保管場所、埋め込みモデルなどの部品を読み込む。
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.document_loaders import WebBaseLoader
from langchain_community.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field

# 検索対象にしたい3つの記事の場所を並べる。
urls = [
    "https://blog.langchain.dev/top-5-langgraph-agents-in-production-2024/",
    "https://blog.langchain.dev/langchain-state-of-ai-2024/",
    "https://blog.langchain.dev/introducing-ambient-agents/",
]

# 各ページを読み込む。1ページから複数の資料が返ることがあるので、二重の一覧になる。
docs = [WebBaseLoader(url).load() for url in urls]

# 二重になっている一覧を、1本の平らな一覧にならし直す。
docs_list = [item for sublist in docs for item in sublist]

# 長い記事を250文字ずつのかたまりに切る役を作る。重ねは0にしている。
text_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=250, chunk_overlap=0
)

# 実際に切り分ける。
doc_splits = text_splitter.split_documents(docs_list)

# 各かたまりを数値に変えて、メモリ上の保管場所に入れる。
vectorstore = InMemoryVectorStore.from_documents(
    documents=doc_splits,
    embedding=OpenAIEmbeddings(),
)

# 質問を渡すと関係する資料を返す係を作る。
retriever = vectorstore.as_retriever()

# 実際に質問を投げて、関係する資料が取れるか確かめる。
results = retriever.invoke(
    "2024年に本番環境で使用されている2つのLangGraphエージェントは何ですか？")
print("検索結果: \n", results)

# 雛形・モデル・スキーマの部品を読み込む。
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field

# 採点結果の形を決める。答えは必ず1つの項目に入る文字列になる。
class GradeDocuments(BaseModel):
    """取得したドキュメントの関連性確認のためのバイナリスコア"""
    # yes か no のどちらかを入れる項目。説明文はLLMも読む。
    binary_score: str = Field(
        description="ドキュメントは質問に関連していますか、'yes' または 'no'"
    )

# 採点役のモデルを用意する。判断がぶれないよう、ばらつきを0にする。
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 上で決めた形を必ず守らせる設定に変える。これで返り値が必ず yes か no になる。
structured_llm_grader = llm.with_structured_output(GradeDocuments)

# 採点役としての立場と、判断の基準を前提の指示として書く。
system = """あなたは、取得したドキュメントがユーザーの質問にどれだけ関連しているかを評価する採点者です。
ドキュメントに質問に関連するキーワードや意味内容が含まれていれば、関連ありとして評価してください。
ドキュメントが質問に関連しているかどうかを示すために、「yes」または「no」のバイナリスコアを付けてください。"""

# 前提の指示と、採点対象（資料と質問）を並べた雛形を作る。
grade_prompt = ChatPromptTemplate.from_messages(
    [
        ("system", system),
        ("human", "取得したドキュメント: \n\n {document} \n\n ユーザーの質問: {question}"),
    ]
)

#「雛形 → 形を守るモデル」をつないで、採点する仕組みを作る。
retrieval_grader = grade_prompt | structured_llm_grader

# 試しに質問を1つ用意して、関係する資料を取ってくる。
question = "agent memory"
docs = retriever.invoke(question)

# 先頭の資料の本文だけを取り出して、採点にかける。
doc_txt = docs[0].page_content

# 採点する。答えは自由な文章ではなく、決まった形で返る。
print(retrieval_grader.invoke({"question": question, "document": doc_txt}))
# --- 実行結果 ---
# binary_score='yes'

🔎 具体例：採点があるかないかで何が変わるか

手元の資料は「LangGraphのブログ記事3本」だけです。ここに「今日の東京の天気は？」と聞かれたとします。

採点なし：検索は必ず何かを返すので、天気とは無関係な記事のかたまりが渡され、LLMはその断片から無理やり答えを作ります。結果はもっともらしい嘘になります。

採点あり：binary_score='no' と判定され、Web検索に切り替わります。正しい天気の情報を取り直してから答えるので、嘘になりません。

🟢 この項のまとめ

  • 自己修正RAGは「振り分け → 検索 → 関連性の採点 → 生成 → 嘘でないかの確認 → 駄目ならWeb検索へ切り替え」という流れ。

コードを見る（1行ずつ説明つき）
# エージェントを最後まで動かし、履歴を丸ごと返す。
def predict_sql_agent_messages(example: dict):
    """回答評価に使う"""
    msg = {"messages": ("user", example["input"])}
    messages = graph.invoke(msg, config)
    # 最終の答えだけでなく、途中の全ての発言を返すのがここでの違い。
    return {"response": messages}

# 履歴の中から、呼ばれた機能の名前だけを出てきた順に拾い出す。
def find_tool_calls(messages):
    tool_calls = [
        tc['name']
        for m in messages['messages'] for tc in getattr(m, 'tool_calls', [])
    ]
    return tool_calls

# 【厳しさ1】期待した機能が、順番は問わず全部呼ばれたかを見る。
def contains_all_tool_calls_any_order(
    root_run: Run, example: Example
) -> dict:
    """期待したツールが「順不同で」全部呼ばれたか確認する"""
    # 呼ばれてほしい機能の一覧。
    expected = [
        'sql_db_list_tables',
        'sql_db_schema',
        'sql_db_query_checker',
        'sql_db_query',
        'check_result'
    ]
    messages = root_run.outputs["response"]
    tool_calls = find_tool_calls(messages)
    # 期待した5つがすべて含まれていれば1点。順番も回数も問わない。
    if set(expected) <= set(tool_calls):
        score = 1
    else:
        score = 0
    return {"score": int(score), "key": "multi_tool_call_any_order"}

# 【厳しさ2】期待した機能が、正しい順番で全部呼ばれたかを見る。
def contains_all_tool_calls_in_order(root_run: Run, example: Example) -> dict:
    """期待したツールが「正しい順番で」全部呼ばれたか確認する"""
    messages = root_run.outputs["response"]
    tool_calls = find_tool_calls(messages)
    # 前から順に1回だけ通る形にして、後戻りできないようにする。
    it = iter(tool_calls)
    expected = [
        'sql_db_list_tables',
        'sql_db_schema',
        'sql_db_query_checker',
        'sql_db_query',
        'check_result'
    ]
    # 期待した順に見つかっていけば1点。間に別の呼び出しが挟まっていてもよい。
    if all(elem in it for elem in expected):
        score = 1
    else:
        score = 0
    return {"score": int(score), "key": "multi_tool_call_in_order"}

# 【厳しさ3】正しい順番で、余計な呼び出しも一切ないかを見る。
def contains_all_tool_calls_in_order_exact_match(
    root_run: Run, example: Example
) -> dict:
    """期待したツールが「正しい順番」かつ「余計な呼び出しなし」で完全一致か確認する"""
    expected = [
        'sql_db_list_tables',
        'sql_db_schema',
        'sql_db_query_checker',
        'sql_db_query',
        'check_result'
    ]
    messages = root_run.outputs["response"]
    tool_calls = find_tool_calls(messages)
    # 並びがまったく同じときだけ1点。1回でも余計に呼べば0点になる。
    if tool_calls == expected:
        score = 1
    else:
        score = 0
    return {"score": int(score), "key": "multi_tool_call_in_exact_order"}

# 3つの採点役をまとめて回す。厳しさの違いが並んで見えるので比べやすい。
experiment_results = evaluate(
    predict_sql_agent_messages,
    data=dataset_name,
    evaluators=[
        contains_all_tool_calls_any_order,
        contains_all_tool_calls_in_order,
        contains_all_tool_calls_in_order_exact_match
    ],
    num_repetitions=3,
)
# --- 実行結果 ---
# multi_tool_call_any_order        : 1.0   （必要な機能は全部呼べている）
# multi_tool_call_in_order         : 1.0   （順番も守れている）
# multi_tool_call_in_exact_order   : 0.33  （余計な呼び出しが混じっている回がある）
ソラ
ソラ「順不同でOK」「順番もぴったり」「余計なものも無しで完全一致」の3段階で厳しさを変えられるんですね。
リク
リクそう。仕事によって、順番が大事なときと、呼びさえすればいいときがあるからね。これらはどれもLangSmithの画面で確認・調査できる。エージェントは呼び出しがばらつきやすいから、こうしたテストで費用の増加や信頼性の低下を防ぐんだ。

🔎 具体例：3つの厳しさの点数の違い

実際に呼ばれた並びが [list_tables, schema, query_checker, schema, query, check_result] だったとします（schema を2回呼んでいる）。

順不同：期待した5つはすべて含まれるので1点。正しい順：期待した順に現れているので1点。完全一致：余計な schema が1回混じっているので0点。

この3つを並べて見ると、「必要なことはできているが、無駄な呼び出しが1回ある」と分かります。無駄な呼び出しは費用と待ち時間に直結するので、改善の手がかりになります。

🟢 この項のまとめ

  • エージェント評価の3つの細かさ：最終の答え／1つの判断／たどった手順の並び。
  • 最終の答えは、中身を見ずにLLMに採点させる。
  • 1つの判断は「最初の機能が期待どおりか」を1点／0点で確かめる。
  • 手順の並びは「順不同／順番どおり／完全一致」の3段階の厳しさで評価できる。
  • num_repetitions で複数回実行し、ばらつきを考える。

章末の理解度チェック（全5問）

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問3つの段階

❓ LLMアプリ開発の「設計」「検証」「本番運用」の3つの段階は、それぞれ何のためにテストを行うのか説明してください。

✅ 解答例
設計の段階は、開発中のアプリに誤りへの対処を組み込み、誤りが利用者に届く前にLLMに自己修正させるためのテストを行う。検証の段階は、本番に出す直前に、前のバージョンより性能が悪くなっていないかを見つけて直すためのテストを行う。本番運用の段階は、実際の利用者に影響する誤りを監視・検知し、その結果を設計・検証の段階に戻すためのテストを行う。この3つがつながって継続的な改善の輪になる。
📝 採点ポイント
□ 設計＝利用者に届く前の自己修正、に触れている
□ 検証＝公開直前の後退の検出、に触れている
□ 本番運用＝稼働中の監視と前段階への還元、に触れている
□ 3つがつながって改善の輪になることに触れている
第2問自己修正RAG

❓ 設計の段階で作る「自己修正RAG」とはどういう仕組みか、なぜ必要なのかを説明してください。

✅ 解答例
基本のRAGは、検索してきた情報が不正確だったり足りなかったりすると、もっともらしい嘘を起こしやすい。自己修正RAGは、LLM自身に「検索結果は質問に関係しているか」「作った答えは嘘でないか」を採点させ、駄目ならWeb検索などに切り替えて情報を取り直す仕組み。LangGraphで処理の流れを組み、採点結果を決まった形の出力にして、次にどの処理へ進むかを決める。これにより、繰り返し答えを作りながら自己修正し、出力の質を上げられる。
📝 採点ポイント
□ RAGは嘘を起こしやすい、という前提に触れている
□ LLM自身に関連性や答えを採点させる点に触れている
□ 駄目なときに切り替える（Web検索など）点に触れている
□ LangGraphと決まった形の出力で分岐を制御する点に触れている
第3問リグレッションテスト

❓ AIアプリのテストが、従来のソフトウェアのように「100%合格」を前提にできないのはなぜですか。代わりに何を見ますか。

✅ 解答例
AIの出力は、データの傾向の変化やモデルの更新による変化（ドリフト）で結果が大きく変わることがあるため、評価用のデータで必ずしも100%合格するとは限らない。そこで、絶対的な合格ではなく「比較の基準にする過去のバージョンに対して性能が後退していないか」を見るリグレッションテストを行う。LangSmithの比較画面を使うと、後退した実行と良くなった実行を色分けで確認できる。
📝 採点ポイント
□ ドリフト（傾向の変化やモデル更新による変化）で結果が変わることに触れている
□ だから100%合格を前提にできない、という結論に触れている
□ 過去のバージョンとの比較で後退を見る、という点に触れている
第4問エージェントの3つの細かさ

❓ エージェントをテストする3つの細かさ「最終の答え」「1つの判断」「たどった手順」は、それぞれ何を見るものですか。

✅ 解答例
最終の答えは、エージェントの中身を見ずに、最終的な答えで仕事を終えられたかを見る（LLMに採点させる）。1つの判断は、特定の機能の呼び出しや判断1つを深く見て、正しい機能を選んだかを確かめる。たどった手順は、エージェントが通った全ての段階（どの機能をどの順番で呼んだか）を見て、期待どおりの流れだったかを評価する。
📝 採点ポイント
□ 最終の答え＝最終結果／仕事の完了、に触れている
□ 1つの判断＝個々の機能の呼び出しや判断、に触れている
□ たどった手順＝全段階の並び／順番、に触れている
第5問オフライン評価とオンライン評価

❓ 検証の段階の「オフライン評価」と本番運用の段階の「オンライン評価」は何が違いますか。

✅ 解答例
オフライン評価は、あらかじめ用意したテスト用のデータを使い、各データに「期待される出力＝正解」を付けて、アプリの答えと正解を比べる方式。公開前にまとめて行う。一方オンライン評価は、本番には比べるための正解が存在しないため、利用者の入力を処理しているその場で成績を点数化する方式。利用者の反応やLLMによる採点を使って、正解なしで品質を評価する。
📝 採点ポイント
□ オフライン評価＝事前のデータ＋正解との比較、に触れている
□ オンライン評価＝本番でその場、正解なし、に触れている
□ オンラインでは利用者の反応やLLMによる採点を使う点に触れている
