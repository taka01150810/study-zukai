この章のあらすじ

止まるタイミングまでLLMが決める

「ルーターよりもっと自律的なのがエージェントですよね？」とソラ。リク先輩は「そう、エージェントはいつ止まるかさえ自分で決めるんだ」と答えます。

この章では、今のLLMアーキテクチャで最も重要な「エージェントアーキテクチャ」を学びます。鍵はPlan-Doループ——「行動を計画する→実行する」を、LLMが「もう答えが出た」と判断するまで繰り返します。これが有名なReActです。LangGraphで基本のエージェントを実装し、さらに「常に最初にツールを呼ぶ」「多くのツールを扱う」という拡張も学びます。

なぜこれが必要か／これを知ると何ができるか

学ぶ理由と、身につくこと

🟣 なぜ学ぶ価値があるのか

  • 何段階も要る問題（調べて→計算して→答える）は、「何回必要か・いつ止まるか」をLLMに任せないと解けないから。
  • ルーターまでは道筋が固定だったが、エージェントは「踏む手順の数」自体をLLMが決める点で本質的に違うから。
  • 使える機能が増えるとLLMが正しいものを選べなくなるので、その対処法を知る必要があるから。

🟢 これを知ったらできるようになること

  • Plan-Doループ（ReAct）の仕組みと、LLMが止めどきを決める意味を説明できる。
  • LangGraphで、モデルの処理とツールの処理をぐるぐる回す基本のエージェントを実装できる。
  • 「常に最初に特定のツールを呼ぶ」拡張で、待ち時間を減らし動きを固定できる。
  • 検索の手順を1つ挟んで、多くのツールから関係するものだけを絞り込める。

6.1

Plan-Doループ

止めどきをLLMが決める

要するに：5章までと決定的に違うのはLLM駆動ループです。ふつうのループは止める条件を人が書きますが、ここではLLMが止めどきを決めます。

リク
リクエージェントアーキテクチャが5章と決定的に違うのは、まだ扱っていない考え方——LLM駆動ループだ。プログラムを書く人ならループは知っているね。止める条件に当たるまで同じ処理を繰り返す。エージェントの鍵は、止める条件をLLMに決めさせることだ。

6.2

LangGraphエージェントを構築する

2つの処理をぐるぐる回す

要するに：モデルの処理とツールの処理を用意して、その間をループさせます。抜けるかどうかを判定するのが tools_condition です。

model

今の履歴を見て、「この機能を使いたい」か「もう答えられる」かを決めます。

LLMを呼ぶ
⇄

tools

モデルが申告した機能を実際に実行し、結果を履歴に足します。

LLMは呼ばない
↻ modelがツールを申告した限り、この2つを行き来し続ける。申告がなくなった時点で終了
コードを見る（1行ずつ説明つき）
# 文字列を数式として安全に評価する道具と、型の道具を読み込む。
import ast
from typing import Annotated, TypedDict

# 検索の機能、機能を登録する印、モデル、グラフの部品、便利な既製の部品を読み込む。
from langchain_community.tools.ddg_search.tool import DuckDuckGoSearchRun
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

# この印を付けると、ふつうの関数がLLMの使える機能になる。
@tool
def calculator(query: str) -> str:
    # この説明文は、そのままLLMに「何をする機能か」として伝わる。だから丁寧に書く。
    """シンプルな電卓ツール。入力は数式。"""
    # 受け取った文字列を数式として計算する。計算はPythonがやるので必ず正確。
    return ast.literal_eval(query)

# 検索の機能を1つ用意する。
search = DuckDuckGoSearchRun()

# 使える機能を一覧にまとめる。ここに足すだけで機能を増やせる。
tools = [search, calculator]

# モデルに「この2つが使えます」と教える。これで機能を申告できるようになる。
model = ChatOpenAI(temperature=0.1).bind_tools(tools)

# 持ち回るデータの形を決める。会話の履歴だけを持つ。
class State(TypedDict):
    messages: Annotated[list, add_messages]

# モデルの処理：今の履歴を渡して、次に何をするかを決めさせる。
# 返答には「使いたい機能の申告」が入ることもあれば、最終の答えが入ることもある。
def model_node(state: State) -> State:
    res = model.invoke(state["messages"])
    return {"messages": res}

# 組み立て役を作る。
builder = StateGraph(State)

# モデルの処理を登録する。
builder.add_node("model", model_node)

# ツールを実行する処理を登録する。既製の部品なので自分で書かなくてよい。
# 申告された機能を実行し、結果を履歴に足す。途中で失敗した場合は、
# エラーの内容を結果としてLLMに渡すので、LLMが立て直しを判断できる。
builder.add_node("tools", ToolNode(tools))

# 入口からは、まずモデルの処理へ進む。
builder.add_edge(START, "model")

# モデルの処理のあと、使いたい機能の申告があれば tools へ、なければ終了する。
# この判定が「ループを続けるか止めるか」を決めている。
builder.add_conditional_edges("model", tools_condition)

# ツールを実行したら、必ずモデルの処理へ戻る。ここでループが閉じる。
builder.add_edge("tools", "model")

# 実行できる形に仕上げる。
graph = builder.compile()
🧰

ポイント① 機能は差し替え可能

検索と電卓の2つを使っています。一覧に足したり入れ替えたりするだけで増減できます。

📦

ポイント② 既製の部品が使える

ToolNode は申告された機能を実行して結果を返します。失敗しても、その内容を結果としてLLMに渡します。tools_condition は続けるか止めるかを判定します。

🔁

ポイント③ 終わりを決めるのはモデル

モデルとツールの間をぐるぐる回り、終わるタイミングを決めるのはモデル自身。これがエージェントの重要な性質です。

実行して、ループを目で追う

リク
リク流れはこうだ。①モデルの処理が検索を使うと判断→判定によりツールの処理へ→②ツールの処理が検索を実行して結果を受け取る→③モデルの処理がもう一度呼ばれ、検索結果を見て最終の答えを作る（追加の申告なし）→判定が終了を選ぶ。じゃあ、この基本に拡張を加えよう。

🔎 具体例：質問によってループの回数が変わる

「日本の首都は？」→ 調べる必要すらないので、モデルは1回で答えます。ループ0周。

「第30代大統領は死亡時に何歳？」→ 検索が1回必要。ループ1周。

「第30代大統領は、妻の母が亡くなったとき何歳？」→ 大統領の生年を調べ、義母の没年を調べ、引き算する。ループ3周。

この回数はコードのどこにも書かれていません。毎回LLMが決めています。

6.3

常に最初にツールを呼び出す

1回目の判断を省く

要するに：「最初は必ず検索すべき」と分かっているなら、1回目のLLM呼び出しを省けます。待ち時間が減り、誤った判断も防げます。

リク
リク標準のエージェントは、LLMが常に「次にどの機能を使うか」を判断する。柔軟だけど、動きが読めないという代償がある。もし開発者が「検索の機能は必ず最初に呼ぶべき」と分かっているなら、固定する利点がある。ただし、そういうはっきりした決まりがないアプリにこれを入れると、かえって悪くなる。
⚡

利点① 待ち時間が減る

1回目のLLM呼び出し（どの機能を使うか決める呼び出し）をまるごと省けます。

🎯

利点② 誤った判断を防げる

LLMが「検索は不要」と誤って判断してしまうのを防げます。

コードを見る（1行ずつ説明つき）
# 数式の評価、型の道具、重複しないIDを作る道具を読み込む。
import ast
from typing import Annotated, TypedDict
from uuid import uuid4

# 検索の機能、メッセージの入れ物、機能を登録する印、モデル、グラフの部品を読み込む。
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.messages import AIMessage, ToolCall
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

# 電卓の機能を用意する（前の例と同じ）。
@tool
def calculator(query: str) -> str:
    """シンプルな電卓ツール。入力は数式。"""
    return ast.literal_eval(query)

# 検索の機能と一覧、そして機能を教えたモデルを用意する（ここまで前の例と同じ）。
search = DuckDuckGoSearchRun()
tools = [search, calculator]
model = ChatOpenAI(temperature=0.1).bind_tools(tools)

# 持ち回るデータの形を決める。
class State(TypedDict):
    messages: Annotated[list, add_messages]

# 通常のモデルの処理。2回目以降はこちらが使われる。
def model_node(state: State) -> State:
    res = model.invoke(state["messages"])
    return {"messages": res}

# 1回目だけ使う処理。ここが今回の主役で、LLMをまったく呼ばない。
def first_model(state: State) -> State:
    # 履歴のいちばん最後、つまり利用者が今書いた文章をそのまま取り出す。
    query = state["messages"][-1].content
    # その文章を検索語として、「検索の機能を使いたい」という申告を自分で組み立てる。
    # 本来はLLMが作るこの申告を、人が決め打ちで作っている。
    search_tool_call = ToolCall(name="duckduckgo_search", args={"query": query}, id=uuid4().hex)
    # 申告だけを持つ「モデルの返答」の形にして返す。本文は空でよい。
    return {"messages": AIMessage(content="", tool_calls=[search_tool_call])}

# 組み立て役を作り、3つの処理を登録する。
builder = StateGraph(State)
builder.add_node("first_model", first_model)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode(tools))

# 入口からは、まず必ず first_model へ（ここではLLMを呼ばない）。
builder.add_edge(START, "first_model")

# その次も判定を挟まず、必ずツールの処理へ。つまり検索は確実に1回行われる。
builder.add_edge("first_model", "tools")

# ここから先は通常のエージェントと同じ。申告があれば続き、なければ終了。
builder.add_conditional_edges("model", tools_condition)
builder.add_edge("tools", "model")

# 実行できる形に仕上げる。
graph = builder.compile()
リク
リク違いは——最初に first_model を通るけど、これはLLMをまったく呼ばない。利用者の文章をそのまま検索語にして、検索の申告を作るだけ。そのあと tools に進んで、いつもの流れに戻る。これで1回目のLLM呼び出しを省けた。
注意：「必ず最初にこれを呼ぶ」というはっきりした決まりがないアプリでこれをやると、不要な検索が毎回走って、かえって遅く・高くなります。
6.4

多くのツールを扱う

選択肢が多すぎると選べなくなる

要するに：使える機能が10個を超えると、LLMは適切なものを選べなくなります。先に関係しそうなものだけに絞ってから渡します。

リク
リクLLMは、指示文に選択肢や情報が大量にあると処理が難しくなる。使える機能が10個以上になると、適切なものを選ぶ力が落ち始める。最も単純な解決策は、選べる機能を減らすこと。でも、質問に応じて多くの機能を使わせたいときは？
ソラ
ソラ全部渡すと選べなくなるけど、減らすと使えない……。
リク
リクそこで検索の手順を1つ挟むんだ。今の質問に最も関係する機能を先に絞り込んで、全部ではなく一部だけをLLMに渡す。呼び出しの費用も減る。ただしこの手順は待ち時間を足すから、機能を増やして性能が落ちた場合にだけ入れる。
1

各機能の説明文を保存しておく

「シンプルな電卓ツール。入力は数式。」といった説明文を数値にして、名前と一緒に保管します。

2

質問に近い説明文を探す

利用者の質問を数値にして、意味が近い説明文を持つ機能だけを取り出します。

3

絞った機能だけをモデルに渡す

30個あっても、渡すのは関係する3〜4個だけ。あとは通常のエージェントと同じです。

選択肢が減るので、正しい機能を選びやすくなり、送るトークン数も減ります。
コードを見る（1行ずつ説明つき）
# 数式の評価と型の道具を読み込む。
import ast
from typing import Annotated, TypedDict

# 検索の機能、資料の入れ物、メッセージの入れ物、機能を登録する印を読み込む。
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage
from langchain_core.tools import tool

# メモリ上のベクトルストア、モデルと埋め込み、グラフの部品を読み込む。
from langchain_core.vectorstores.in_memory import InMemoryVectorStore
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

# 電卓の機能を用意する。説明文が、あとで検索の対象になる。
@tool
def calculator(query: str) -> str:
    """シンプルな電卓ツール。入力は数式。"""
    return ast.literal_eval(query)

# 検索の機能と、機能の一覧を用意する。
search = DuckDuckGoSearchRun()
tools = [search, calculator]

# 埋め込みモデルと、モデルの呼び出し口を用意する。
# ここでは bind_tools をまだ呼ばない。渡す機能は毎回変わるため。
embeddings = OpenAIEmbeddings()
model = ChatOpenAI(temperature=0.1)

# 各機能の「説明文」を本文にして保管する。名前は付随情報として持たせる。
# これで「質問に意味が近い説明文の機能」を探せるようになる。
tools_retriever = InMemoryVectorStore.from_documents(
    [Document(tool.description, metadata={"name": tool.name}) for tool in tools],
    embeddings,
).as_retriever()

# 持ち回るデータの形を決める。絞り込んだ機能の名前も持ち回る。
class State(TypedDict):
    messages: Annotated[list, add_messages]
    selected_tools: list[str]

# モデルの処理：絞り込まれた機能だけを渡してから呼ぶ。
def model_node(state: State) -> State:
    # 名前が一致するものだけを、全機能の一覧から取り出す。
    selected_tools = [tool for tool in tools if tool.name in state["selected_tools"]]
    # その場で「この機能たちが使えます」と教えてから呼ぶ。全部は渡さない。
    res = model.bind_tools(selected_tools).invoke(state["messages"])
    return {"messages": res}

# 絞り込みの処理：質問に関係する機能を選ぶ。
def select_tools(state: State) -> State:
    # 履歴のいちばん最後、つまり今の質問を取り出す。
    query = state["messages"][-1].content
    # 質問に意味が近い説明文を持つ機能を検索する。
    tool_docs = tools_retriever.invoke(query)
    # 見つかった機能の名前だけを取り出して記録する。
    return {"selected_tools": [doc.metadata["name"] for doc in tool_docs]}

# 組み立て役を作り、3つの処理を登録する。
builder = StateGraph(State)
builder.add_node("select_tools", select_tools)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode(tools))

# 入口では、まず機能を絞り込む。ループに入る前の1回だけ行う。
builder.add_edge(START, "select_tools")

# 絞り込みが終わったらモデルの処理へ。
builder.add_edge("select_tools", "model")

# ここから先は通常のエージェントと同じループ。
builder.add_conditional_edges("model", tools_condition)
builder.add_edge("tools", "model")

# 実行できる形に仕上げる。
graph = builder.compile()
リク
リク通常のエージェントとほぼ同じで、ループに入る前に select_tools でいったん止まるだけだ。最初に取り出し係に質問を投げて、今の質問に最も関係する機能を取得して、そのあといつものエージェントの形に進む。
ソラ
ソラ3章のセマンティックルーティングに似てますね。機能を意味で絞り込むんだ。

🔎 具体例：30個の機能があるとき

社内向けに、勤怠照会・経費申請・在庫確認・売上集計・会議室予約……と30個の機能を用意したとします。全部の説明文を毎回指示文に入れると、それだけで数千トークンになり、LLMは「勤怠照会」と「シフト確認」の区別がつかなくなります。

先に絞り込みを入れると、「昨日の残業時間は？」という質問には勤怠関連の3個だけが渡ります。選択肢が10分の1になるので選び間違いが減り、送るトークン数も大きく減ります。代わりに、絞り込みの検索1回ぶんの待ち時間が増えます。

🟢 この項のまとめ

  • エージェント＝行動するもの。行動には「何をすべきか決める力・複数の選択肢・外の世界の情報」が必要。
  • ツール呼び出し＋CoTでPlan-Doループ（ReAct）。最大の特徴は、止めどきをLLM自身が決めること。
  • LangGraphでの実装：ToolNode（ツールの実行）と tools_condition（続けるか止めるかの判定）で、モデルとツールの間をループ。
  • 拡張1：常に最初に特定のツールを呼ぶ（1回目のLLM呼び出しを省いて待ち時間を削減、誤判断も防止）。はっきりした決まりがある場合のみ。
  • 拡張2：絞り込みの手順（select_tools）で、多くの機能から質問に関係するものだけを選ぶ。待ち時間が増える点に注意。

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問エージェントとは

❓ 「エージェント（行動するもの）」であるために必要な3つの条件を挙げて説明してください。

✅ 解答例
①何をすべきかを決める力が必要。②決めるには複数の選択肢が必要（選ぶものが1つしかなければ決断ではない）。③決めるには外の世界（自分の外側）の情報が必要。だからエージェント型のLLMアプリは、今の状態と目指す状態を材料に、1つ以上の行動から選ぶ。これはツール呼び出し（選べる行動を見せる）とCoT（順を追って考える）の組み合わせで作られる。
📝 採点ポイント
□ 何をすべきか決める力、に触れている
□ 複数の選択肢が必要、に触れている
□ 外の世界の情報が必要、に触れている
第2問Plan-Doループ

❓ エージェントアーキテクチャの核心である「Plan-Doループ」とは何ですか。5章のルーターと何が決定的に違いますか。

✅ 解答例
Plan-Doループは「行動を計画する→その行動を実行する」を、止める条件に当たるまで繰り返すLLM駆動のループ。たとえば「検索する→結果を見て計算する→答える」のように、何段階必要かが事前に決まっていない問題を解ける。ルーターとの決定的な違いは、ルーターは用意された道筋の中から選ぶだけで手順の数は固定だが、エージェントは「踏む手順の数」自体が変わり、ループを止めるタイミングをLLM自身が決めること。決める役をLLMに渡している点が本質。
📝 採点ポイント
□ 計画→実行を止める条件まで繰り返すループ、に触れている
□ 手順の数が事前に決まっていない、に触れている
□ 止めるタイミングをLLM自身が決める、に触れている
第3問ToolNodeとtools_condition

❓ LangGraphでエージェントを作るときの ToolNode と tools_condition は、それぞれ何をしますか。

✅ 解答例
ToolNode はグラフ上の処理で、履歴に入っている最新のモデルの返答が申告したツール呼び出しを実行し、それぞれの結果を ToolMessage として返す。ツールが失敗した場合は、エラーの内容で ToolMessage を作りLLMに渡す（LLMが立て直しを判断できる）。tools_condition は条件付きエッジの関数で、最新の返答を見て、実行すべきツールの申告があればツールの処理へ進ませ、なければグラフを終了させる。この2つで、モデルとツールの間のループと停止が実現する。
📝 採点ポイント
□ ToolNode＝申告されたツールを実行し結果をToolMessageで返す、に触れている
□ tools_condition＝申告があればtoolsへ、なければ終了する判定、に触れている
□ この2つでループと停止を実現、に触れている
第4問最初にツールを呼ぶ拡張

❓ 「常に最初に特定のツールを呼ぶ」拡張は、どんな利点があり、どんなときに導入すべきですか。

✅ 解答例
利点は2つ。①1回目のLLM呼び出し（どのツールを呼ぶか判断する呼び出し）を省けるので、全体の待ち時間が減る。②LLMが「検索は不要」と誤って判断するのを防げる。first_model の処理でLLMを呼ばずに、利用者の文章をそのまま検索語にして検索ツールの申告を作る。ただし、導入すべきなのは「常に最初にこのツールを呼ぶべき」というはっきりした決まりがアプリにある場合だけ。そうでないアプリにこの制限を入れると、かえって悪くなる。
📝 採点ポイント
□ 1回目のLLM呼び出しを省いて待ち時間を減らす、に触れている
□ LLMが誤って判断するのを防ぐ、に触れている
□ はっきりした決まりがある場合のみ導入すべき、に触れている
第5問多くのツールを扱う

❓ ツールが多数（10個以上など）あるとどんな問題が起きますか。どう対処しますか。

✅ 解答例
ツールが多数になると、指示文に大量の選択肢が含まれ、LLMが適切なツールを選ぶ力が落ちる。対処は、絞り込みの手順（select_tools）を使うこと。各ツールの説明文をベクトルストアに入れておき、今の質問に最も関係するツールだけを検索で絞り込んで、全体ではなく一部だけをLLMに渡す。呼び出しの費用も減る。ただしこの手順は待ち時間を足すので、ツールを増やして性能が落ちた場合にだけ導入すべき。
📝 採点ポイント
□ ツールが多いとLLMの選択の力が落ちる、に触れている
□ 絞り込みの手順で関係するツールだけにする、に触れている
□ 待ち時間が増えるので必要なときだけ導入、に触れている
