📚 かんたん用語集

この章に出てくる専門用語を、できるだけ日常の言葉で説明します。分からなくなったらここに戻ってきてください。

エージェント agent

「行動するもの」。何をすべきか自分で決めて動くAIのこと。探偵事務所でいう探偵そのもの。

LLM 大規模言語モデル

大量の文章で学んだAIの頭脳。質問に答えたり、次に何をすべきか考えたりする。探偵の頭脳にあたる。

ツール呼び出し tool calling

AIに「使える道具の一覧」を見せ、どれを使うか選んで指示を出させる仕組み。探偵が捜査道具を選んで使うイメージ。

CoT Chain of Thought

「順を追って考えてね」と一歩ずつ推論させる手法。探偵の推理の積み重ね。

Plan-Doループ 計画→実行ループ

「①次の手を計画する→②実行する」を、答えが出るまで繰り返すこと。探偵の「調べる→次を考える」の繰り返し捜査。

停止条件 いつ止まるか

ループを終わらせる合図。エージェントではこれをAI自身が決めるのが最大の特徴。探偵が「事件解決だ」と宣言する瞬間。

ReAct Reasoning + Acting

「推論（考える）」と「行動（道具を使う）」を交互に繰り返す有名なパターン。Plan-Doループの正式名。

ルーター router

前章（5章）の仕組み。決められた経路の中から1つを選ぶだけ。探偵でいう「最初に行く部屋を1つ選ぶだけ」で、ぐるぐる回らない。

LangGraph ラングラフ

AIの処理の流れを「点（ノード）と矢印（エッジ）」の地図で組み立てる道具。探偵の捜査手順書を作るためのもの。

ノード node

流れの中の「処理の一手」。探偵の手順書の1コマ。この章では「モデルノード（考える）」「ツールノード（道具を使う）」が出る。

条件付きエッジ conditional edge

「もし◯◯なら右、そうでなければ左」と進路を分ける矢印。探偵が「まだ調べる？それとも解決？」を分岐する所。

ToolNode ツールノード

LangGraph付属の便利部品。AIが「使う」と決めた道具を実際に動かして結果を返す。探偵の鑑識係。

tools_condition 条件関数

LangGraph付属の便利部品。「使う道具があれば道具へ、なければ終了」を判定する。探偵の「捜査続行か解決か」の判定役。

レイテンシー latency

処理にかかる「待ち時間」。短いほど速い。AIへの問い合わせを1回減らすと、その分待ち時間が縮む。

RAG 検索拡張

答える前に関連情報を検索して、必要な分だけ手元に用意すること。ここではたくさんの道具から関係するものだけ選び出すのに使う。

ベクトルストア vector store

文章を「意味の近さ」で探せるようにしまっておく棚。似た意味のものをサッと取り出せる。探偵の意味で引ける道具棚。

プランニング性能 計画する力

AIが「次にどの手を打つべきか」を正しく選べる力。選択肢が多すぎると、この力が落ちる。

🎯 要するに

エージェントとは「行動するもの」。行動には、複数の選択肢から何をすべきかを決める能力と、外部環境の情報が必要です。LLMエージェントは「ツール呼び出し」と「CoT」を組み合わせて、Plan-Doループ（計画→実行）を回します。最大の特徴は、ループを止めるタイミング（停止条件）をLLM自身が決めること。LangGraphでは、モデルノードとツールノードの間をループさせ、条件付きエッジで停止を判断します。

このページでは、AIを探偵、AIへの質問を依頼（事件）、道具（検索や電卓）を捜査道具、最終的な答えを事件解決に置きかえて説明します。ふつうの受付係（前章のルーター）は「最初にどの部屋へ通すか」を選ぶだけ。でも探偵は、自分で「次は聞き込み、その次は鑑識……もう犯人が分かった、捜査終了！」と、手順も回数も終わりも自分で決めて動きます。

📌 なぜこれが必要か／これを知ったらできること

  • なぜ学ぶ価値があるのか：多段階の問題（調べて→計算して→答える）は、「何ステップ必要か・いつ止まるか」をLLMに委ねないと解けないから。
  • ルーターまでは経路が固定だったが、エージェントは「取るべきステップ数」自体をLLMが決める点で本質的に違うから。
  • ツールが増えるとLLMが正しいツールを選べなくなるので、その対処法を知る必要があるから。
  • できるようになること①：Plan-Doループ（ReActパターン）の仕組みと、LLMが停止条件を決める意味を説明できる。
  • できるようになること②：LangGraphで、モデルノードとツールノードをループさせる基本エージェントを実装できる。
  • できるようになること③：「常に最初に特定のツールを呼ぶ」拡張で、レイテンシーを削減し挙動を固定できる。
  • できるようになること④：RAGステップで、多くのツールから関連するものだけを絞り込める。

6.2

LangGraphエージェントを構築する

モデルノードとツールノードをループさせる
リク
リク検索ツールにDuckDuckGo（検索エンジン）を使う。基本的なエージェントの実装だ。

この設計図を読み解こう：探偵（model）が「道具を使う」と言えば鑑識係（tools）へ、「もう要らない」と言えば終了。鑑識が終わったら必ず探偵へ戻る――この往復がエージェントの本体です。

グラフ（捜査手順書）の全体像

S

START → model（モデルノード）

依頼を受け取ったら、まず探偵が「次にどの道具を使うか／もう答えるか」を考える。

?

条件付きエッジ（tools_condition）

探偵の判断を見て分岐する。

✅ 使う道具がある → tools（鑑識係）へ
⛔ 使う道具がない → そのまま終了（事件解決）

T

tools（ツールノード）

探偵が要求した道具を実際に動かし、結果を持ち帰る。

🔁

tools → model（必ず戻る）

結果を持って必ず探偵に戻る。そしてまた「次の一手」を考える。ここでループが生まれる。

下のコードは、検索（DuckDuckGo）と電卓の2つの道具を持つ探偵を作り、上の往復をつなげているだけです。読み飛ばしてOK。

Python：基本エージェントの実装 
# このコードがやること: 検索(DuckDuckGo)と電卓の2つのツールを持つエージェントを作る。
#  model_node = LLMが「どのツールを呼ぶか/もう答えるか」を判断する。
#  ToolNode = モデルが要求したツールを実行する（prebuiltの便利ノード）。
#  tools_condition = 実行すべきツールがあればtoolsへ、なければ終了する条件付きエッジ。
# model と tools の間をループする。
import ast
from typing import Annotated, TypedDict
from langchain_community.tools.ddg_search.tool import DuckDuckGoSearchRun
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def calculator(query: str) -> str:
    """シンプルな電卓ツール。入力は数式。"""
    return ast.literal_eval(query)

search = DuckDuckGoSearchRun()
tools = [search, calculator]
model = ChatOpenAI(temperature=0.1).bind_tools(tools)

class State(TypedDict):
    messages: Annotated[list, add_messages]

def model_node(state: State) -> State:
    res = model.invoke(state["messages"])
    return {"messages": res}

builder = StateGraph(State)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "model")
builder.add_conditional_edges("model", tools_condition)  # ツールがあればtoolsへ、なければ終了
builder.add_edge("tools", "model")                       # ツール実行後はmodelへ戻る（ループ）

graph = builder.compile()

このコードの3つのポイント（リクの解説）

  • ① 2ツール構成：検索と電卓を使い、簡単に追加・置き換えできる（Pythonの例はカスタムツールの作り方も示している）。
  • ② 付属の便利関数を使う：ToolNode はステートの最新AIメッセージが要求するツール呼び出しを実行して、結果を ToolMessage で返す（ツールが例外を出したらエラーメッセージを ToolMessage にしてLLMに渡す）。tools_condition は条件付きエッジ関数で、実行すべきツールがあればツールノードへ、なければグラフを終了する。
  • ③ ループする：グラフはモデルノードとツールノードの間でループする。終了タイミングを決めるのはモデル自身――これがエージェントの重要な特性だ。

実行してみる

下のコードは「第30代大統領は死亡時に何歳だった？」を投げて、各ノードの動きを1つずつ表示します。読み飛ばしてOK。

Python：エージェントを実行する 
# このコードがやること: 「第30代大統領は死亡時に何歳だった？」を投げ、各ノードの動きをストリーム表示する。
from langchain_core.messages import HumanMessage

user_input = {
    "messages": [HumanMessage("How old was the 30th president of the United States when he died?")]
}
for c in graph.stream(user_input):
    print(c)

🕵️ たとえ話：探偵と鑑識係の往復

探偵（model）が「この指紋を鑑識に回せ」と指示すると、判定役（tools_condition）が鑑識係（tools）へ案件を回します。鑑識係は分析して結果を探偵に返却。探偵は結果を見て「これで犯人が分かった、事件解決」と宣言――判定役はもう鑑識へ回さず、捜査を終了します。誰が「終わり」と言うかというと、いつでも探偵自身です。

6.3

常に最初にツールを呼び出す

挙動を固定して速くする拡張
リク
リク標準のエージェントは、LLMが常に「次にどのツールを呼ぶか」を判断する。柔軟だけど、予測不能というコストがある。もし開発者が「検索ツールは必ず最初に呼ぶべき」と知っているなら、固定する利点がある。
⚡

利点① レイテンシー削減

最初のLLM呼び出し（どの道具を使うか考える1回）をスキップできるので、待ち時間が減る。

🛡️

利点② 誤判断を防ぐ

LLMが「検索は不要」と誤って判断するのを防げる。必ず検索してから考えさせられる。

⚠️ 注意：いつ入れるべきか

  • 導入してよいのは「常に最初にこのツールを呼ぶべき」という明確な規則がアプリにある場合だけ。
  • そういう明確な規則がないアプリにこの制約を入れると、かえって悪化する（必要ないのに毎回検索してしまう等）。

どう変わるか

1

START → first_model（新ノード）

ここがミソ。LLMをまったく呼ばない。ユーザーのメッセージをそのまま検索クエリにして、検索ツールの呼び出しを作るだけ。

2

first_model → tools（必ず検索）

判断を挟まず、いきなり検索を実行する。

3

tools → model（いつものループへ合流）

あとは標準エージェントと同じ。モデルとツールの往復に戻る。

下のコードは first_model ノードを足し、LLMを呼ばずにユーザーの質問をそのまま検索クエリにして、必ず最初に検索を実行します。読み飛ばしてOK。

Python：常に最初に検索する拡張 
# このコードがやること: first_model ノードで、LLMを呼ばずにユーザーの質問をそのまま検索クエリにして
# 必ず最初に検索ツールを呼ぶ。その後は通常のエージェントループに合流する。
import ast
from typing import Annotated, TypedDict
from uuid import uuid4
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.messages import AIMessage, ToolCall
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def calculator(query: str) -> str:
    """シンプルな電卓ツール。入力は数式。"""
    return ast.literal_eval(query)

search = DuckDuckGoSearchRun()
tools = [search, calculator]
model = ChatOpenAI(temperature=0.1).bind_tools(tools)

class State(TypedDict):
    messages: Annotated[list, add_messages]

def model_node(state: State) -> State:
    res = model.invoke(state["messages"])
    return {"messages": res}

def first_model(state: State) -> State:
    # LLMを呼ばずに、最後のユーザーメッセージをそのまま検索クエリにする
    query = state["messages"][-1].content
    search_tool_call = ToolCall(name="duckduckgo_search", args={"query": query}, id=uuid4().hex)
    return {"messages": AIMessage(content="", tool_calls=[search_tool_call])}

builder = StateGraph(State)
builder.add_node("first_model", first_model)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "first_model")     # まず必ず first_model
builder.add_edge("first_model", "tools")   # そして必ず tools（検索）
builder.add_conditional_edges("model", tools_condition)
builder.add_edge("tools", "model")

graph = builder.compile()

このまとめ（リクの解説）

  • 違いは――最初に first_model を呼ぶけど、これはLLMをまったく呼ばない。
  • ユーザーのメッセージをそのまま検索クエリにして、検索ツールのツール呼び出しを作るだけ。
  • その後 tools に進んで、いつものフローに戻る。これで最初のLLM呼び出しを省略できた。

🕵️ たとえ話：「まず現場検証」を所のルールにする

どんな事件でも「最初に必ず現場検証する」と事務所のルールで決まっているなら、探偵に「現場へ行くべき？」と毎回考えさせる必要はありません。受付の段階で直行させれば、考える手間（＝最初のLLM呼び出し）が省けて、捜査が速く始まります。ただしこれは「必ず現場検証が要る事件しか来ない」事務所でだけ有効。電話相談だけで済む依頼まで現場へ走らせると、かえって無駄足になります。

6.4

多くのツールを扱う

道具が増えすぎたらRAGで絞る
リク
リクLLMは、プロンプトに複数の選択肢や大量の情報があると処理が難しくなる。ツールが10個以上になると、適切なツールを選ぶ能力（プランニング性能）が落ち始める。最も単純な解決策は、LLMが選べるツールを減らすこと。でも、クエリに応じて多くのツールを使わせたいときは？
ソラ
ソラ全部渡すと選べなくなるけど、減らすと使えない……。
リク
リクそこで RAGステップだ。現在のクエリに最も関連するツールを先に絞り込んで、ツール群全体じゃなく一部だけをLLMに渡す。LLM呼び出しコストも減る。ただしRAGステップは追加のレイテンシーを生むから、ツールを増やしてパフォーマンスが落ちた場合にだけ導入する。
😵

解決：RAGで絞る

事件に必要な道具だけ持って出かける

どう変わるか

1

START → select_tools（新ノード）

まずリトリーバー（意味で引ける棚）にクエリを投げ、関連するツールだけを取得する。

2

絞り込んだ少数のツールだけをLLMに渡す。

3

model ⇄ tools の往復へ。標準アーキテクチャと同じ。

下のコードは、各ツールの説明文を「意味で引ける棚（ベクトルストア）」に入れておき、select_tools ノードで今のクエリに関連するツールだけ取り出してLLMに渡します。読み飛ばしてOK。

Python：多くのツールをRAGで絞る拡張 
# このコードがやること: ツールの説明文をベクトルストアに入れておき、select_tools ノードで
# 現在のクエリに関連するツールだけを取り出して、それだけをLLMに渡す。
import ast
from typing import Annotated, TypedDict
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage
from langchain_core.tools import tool
from langchain_core.vectorstores.in_memory import InMemoryVectorStore
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langgraph.graph import START, StateGraph
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def calculator(query: str) -> str:
    """シンプルな電卓ツール。入力は数式。"""
    return ast.literal_eval(query)

search = DuckDuckGoSearchRun()
tools = [search, calculator]

embeddings = OpenAIEmbeddings()
model = ChatOpenAI(temperature=0.1)

# 各ツールの「説明文」をベクトルストアに入れる（名前をメタデータに）
tools_retriever = InMemoryVectorStore.from_documents(
    [Document(tool.description, metadata={"name": tool.name}) for tool in tools],
    embeddings,
).as_retriever()

class State(TypedDict):
    messages: Annotated[list, add_messages]
    selected_tools: list[str]

def model_node(state: State) -> State:
    selected_tools = [tool for tool in tools if tool.name in state["selected_tools"]]
    res = model.bind_tools(selected_tools).invoke(state["messages"])  # 絞ったツールだけ渡す
    return {"messages": res}

def select_tools(state: State) -> State:
    query = state["messages"][-1].content
    tool_docs = tools_retriever.invoke(query)  # クエリに関連するツールを検索
    return {"selected_tools": [doc.metadata["name"] for doc in tool_docs]}

builder = StateGraph(State)
builder.add_node("select_tools", select_tools)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "select_tools")     # まずツールを絞る
builder.add_edge("select_tools", "model")
builder.add_conditional_edges("model", tools_condition)
builder.add_edge("tools", "model")

graph = builder.compile()

このまとめ（リクの解説）

  • 通常のエージェントとほぼ同じで、エージェントループに入る前に select_tools ノードで止まるだけ。
  • 最初にリトリーバーにクエリを発行して、現在のクエリに最も関連するツールを取得する。
  • その後、いつものエージェントアーキテクチャ（モデルとツールの往復）に進む。
ソラ
ソラ3章のセマンティックルーティングに似てますね。ツールを意味で絞り込むんだ。

🕵️ たとえ話：事件にあった道具だけ鞄に詰める

探偵事務所の倉庫には何十種類もの捜査道具があります。全部を持って現場へ行ったら、鞄が重くてどれを使うか迷うだけ。そこで出発前に「今回は毒殺事件だから、検査キットと顕微鏡だけ」と事件の内容に合う道具を意味で選んで鞄に詰めるのがRAGステップです。選ぶ手間（待ち時間）は増えるので、道具が多すぎて迷い始めたときにだけ取り入れます。

自分の言葉で答えてみよう

この章を読み終わったあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問エージェントとは

「エージェント（行動するもの）」であるために必要な3つの条件を挙げて説明してください。

✅ 解答例
①何をすべきかを決める能力が必要。②決めるには複数の選択肢が必要（選択肢のない決断は決断ではない）。③決めるには外部環境（自分の外側にあるもの）の情報が必要。だからエージェント型LLMアプリは、LLMを使って、現在の状態と望む状態のコンテキストが与えられたとき、1つ以上の行動コースから選択する。これはツール呼び出し（選べるアクションを提示）とCoT（ステップバイステップで考える）の組み合わせで実装される。
📝 採点ポイント
□ 何をすべきか決める能力、に触れている ／ □ 複数の選択肢が必要、に触れている ／ □ 外部環境の情報が必要、に触れている
第2問Plan-Doループ

エージェントアーキテクチャの核心である「Plan-Doループ」とは何ですか。5章のルーターと何が決定的に違いますか。

✅ 解答例
Plan-Doループは「行動を計画する→その行動を実行する」を、停止条件にヒットするまで繰り返すLLM駆動ループ。例えば「検索する→結果を見て計算する→答える」のように、何ステップ必要かが事前に決まっていない問題を解ける。ルーターとの決定的な違いは、ルーターは定義済みの経路の中から選ぶだけで経路は固定だが、エージェントは「取るべきステップ数」自体が可変で、ループを止めるタイミング（停止条件）をLLM自身が決めること。LLMに意思決定の主体を委ねる点が本質。
📝 採点ポイント
□ 計画→実行を停止条件まで繰り返すループ、に触れている ／ □ ステップ数が事前に決まっていない、に触れている ／ □ 停止タイミングをLLM自身が決める、に触れている
第3問ToolNodeとtools_condition

LangGraphでエージェントを作るときの ToolNode と tools_condition は、それぞれ何をしますか。

✅ 解答例
ToolNode はグラフ上のノードで、ステートに保存された最新のAIメッセージが要求するツール呼び出しを実行し、それぞれの結果を ToolMessage として返す。ツールが例外を出した場合は、エラーメッセージで ToolMessage を作りLLMに渡す（LLMが対応を判断できる）。tools_condition は条件付きエッジ関数で、最新のAIメッセージを見て、実行すべきツールがあればツールノードへ遷移させ、なければグラフを終了させる。この2つで、モデルとツールの間のループと停止を実現する。
📝 採点ポイント
□ ToolNode＝要求されたツールを実行し結果をToolMessageで返す、に触れている ／ □ tools_condition＝ツールがあればtoolsへ、なければ終了する条件付きエッジ、に触れている ／ □ この2つでループと停止を実現、に触れている
第4問最初にツールを呼ぶ拡張

「常に最初に特定のツールを呼ぶ」拡張は、どんな利点があり、どんなときに導入すべきですか。

✅ 解答例
利点は2つ。①最初のLLM呼び出し（どのツールを呼ぶか判断する呼び出し）をスキップできるので、全体のレイテンシーが減る。②LLMが「検索ツールを呼ぶ必要がない」と誤判断するのを防げる。first_model ノードでLLMを呼ばずに、ユーザーのメッセージをそのまま検索クエリにして検索ツールを呼ぶ。ただし、導入すべきなのは「常に最初にこのツールを呼ぶべき」という明確な規則がアプリにある場合だけ。そうでないアプリにこの制約を入れると、かえって悪化する。
📝 採点ポイント
□ 最初のLLM呼び出しをスキップしてレイテンシーを減らす、に触れている ／ □ LLMが誤判断するのを防ぐ、に触れている ／ □ 明確な規則がある場合のみ導入すべき、に触れている
第5問多くのツールを扱う

ツールが多数（10個以上など）あるとどんな問題が起きますか。どう対処しますか。

✅ 解答例
ツールが多数になると、プロンプトに大量の選択肢が含まれ、LLMが適切なツールを選ぶ能力（プランニング性能）が低下する。対処は、RAGステップ（select_tools）を使うこと。各ツールの説明文をベクトルストアに入れておき、現在のユーザークエリに最も関連するツールだけを検索で絞り込んで、ツール群全体ではなくその一部だけをLLMに渡す。LLM呼び出しコストも減る。ただしRAGステップは追加のレイテンシーを生むので、ツールを増やしてパフォーマンスが落ちた場合にだけ導入すべき。
📝 採点ポイント
□ ツールが多いとLLMの選択能力が落ちる、に触れている ／ □ RAGステップで関連ツールだけを絞り込む、に触れている ／ □ 追加レイテンシーがあるので必要時のみ導入、に触れている
