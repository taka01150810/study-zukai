デプロイ deploy

作ったアプリを本番環境に置いて、外部のユーザーが使えるようにすること。組み立て終わったロケットを発射台に乗せて「打ち上げる」イメージ。

本番環境 production

実際のユーザーが使う、世に公開された場所。自分のPC（＝工場の中）の反対側＝宇宙空間。

ローカル local

自分のPCの中だけで動かしている状態。まだ工場の中で組み立て・試運転している段階。

ベクトルストア vector store

文章を数字の列（ベクトル）にして保存し、「似ているもの」を探せる保管庫。本書ではSupabaseを使う。

Supabase スーパベース

PostgreSQLというデータベース＋pgvector拡張で作るベクトルストア。ロケットの「燃料・部品の保管庫」。

埋め込み embedding

文章の意味を数字の列に変換したもの。意味が近い文章は数字も近くなる。OpenAIの埋め込みは1536個の数字（1536次元）。

LangSmith ラングスミス

LLMアプリのデバッグ・テスト・監視をまとめてできる道具。打ち上げを見守る「管制室（モニター画面）」。

モニタリング monitoring

本番で動くアプリの利用状況・エラー・コストなどを監視すること。管制室で計器をずっと見る作業。

LangGraph Platform プラットフォーム

エージェントを大規模に動かしてホスティングするマネージドサービス（運用を肩代わりしてくれる外部の発射場）。

エージェント agent

自分で考えて道具を使い、目的を達成するAI。ここでは打ち上げる「ロケット本体」。

スケール（水平スケーリング） scaling

利用が増えたとき、機械を増やして負荷を分散すること。発射台や管制官を増やして混雑をさばくイメージ。

アシスタント Assistants

グラフ（ロケットの設計図）に設定を加えた1機体。同じ設計図から設定違いの機体を何機も作れる。

スレッド Threads

1回の対話・実行の流れと、その途中状態をぜんぶ記録した飛行ログ。

チェックポイント checkpoint

飛行ログの「ある瞬間のスナップショット」。あとで巻き戻したり続きから飛べる。

実行（Run） Runs

アシスタント（機体）を1回呼び出して動かす操作。1回の飛行。

Cronジョブ cron

決めたスケジュールで自動的にグラフを動かす仕組み。毎朝6時に自動点検飛行を行う予約。

ストリーミング streaming

結果を一気にではなく、できた端から少しずつ送ること。管制室に飛行データがリアルタイムで届く感じ。

ヒューマンインザループ HITL

重要な所で人間が確認・承認を挟む仕組み。大事な操作前に管制官がGoサインを出す。

ダブルテキスト double texting

前の実行が終わる前にユーザーが次のメッセージを送ってくる状況と、その対処法。

Webフック webhook

実行が終わったら、こちらのアプリへ自動で「終わったよ」と通知する仕組み。着陸完了の自動連絡。

langgraph.json 設定ファイル

どのコードを使い・どのグラフを動かし・どの環境変数を読むかを書く設計書。打ち上げの「フライトプラン」。

langgraph dev ローカル開発サーバー

本番に出す前に自分のPCで試すための起動コマンド。打ち上げ前のリハーサル（地上試験）。

LangGraph Studio スタジオ

エージェントを目で見て、対話して、デバッグできる画面。ロケットの設計・点検を行う管制プレイグラウンド。

最小権限 least privilege

アプリに必要なことだけ許可し、余計な権限を与えないこと。乗組員に必要な鍵だけ渡す。

多層防御 defense in depth

1つの防御に頼らず、何重にも守ること。隔壁を何枚も重ねる安全設計。

プロンプトインジェクション prompt injection

悪意ある入力でAIに本来の指示を無視させ、おかしな動きをさせる攻撃。管制への偽の指令。

レートリミット rate limit

短時間に大量のリクエストが来ないよう、回数に上限をつけること。発射回数の制限。

サンドボックス sandbox

外に影響が出ないよう、隔離された箱の中で動かすこと。閉じた試験室で安全に動かすイメージ。

あらすじ

「いいアプリができたけど、これ、まだ自分のPCの中だけですよね……」とソラ。リク先輩は「そう、外部のユーザーはまだ使えない。本番環境にデプロイして初めて世に出るんだ」と答えます。この章では、作ったAIアプリを本番環境に出す方法を学びます。ベクトルストア（Supabase）、モニタリング（LangSmith）、バックエンドAPI（LangGraph Platform）を組み合わせ、ローカルでテストしてからワンクリックでデプロイ。最後に、LLMアプリ特有のセキュリティ（権限の最小化・誤用の想定・多層防御）も押さえます。

🎯 要するに

ローカルで動くアプリを本番に出すには、ホスティング・データ保存・モニタリングのサービスが要ります。本書では Supabase（ベクトルストア）、LangSmith（デバッグ・監視）、LangGraph Platform（エージェントをスケールしてホスティングするマネージドサービス）を使います。langgraph.json で設定し、langgraph dev でローカルテストし、LangSmith UIからデプロイします。そして、LLMアプリ特有のセキュリティ（最小権限・誤用の想定・多層防御）が不可欠です。

② ベクトルストア ― Supabaseを保管庫にする

リク
リクSupabase（PostgreSQL＋pgvector拡張）を使う。プロジェクトを作って、URLと service_role キーを .env に設定。SQLエディタで pgvector を有効化して、documents テーブルと match_documents 関数を作る。

▼ 下のコードは「ベクトルを入れる保管棚（documentsテーブル）を作る」命令です。読み飛ばしてOK。

SQL：pgvectorを有効化して documents テーブルを作る 
-- pgvector拡張を有効化し、ベクトルを格納する documents テーブルを作る
create extension vector;

create table documents (
  id bigserial primary key,
  content text,             -- Document.pageContent に対応
  metadata jsonb,           -- Document.metadata に対応
  embedding vector(1536)    -- OpenAIの埋め込みは1536次元
);

▼ 下のコードは「探したい文章に近いものを保管棚から取り出す検索係（match_documents関数）」を作る命令です。読み飛ばしてOK。

SQL：match_documents 関数（似たドキュメントを返す） 
-- ドキュメントを検索する関数：query_embedding に近いものをコサイン類似度で返す
create function match_documents (
  query_embedding vector(1536),
  match_count int DEFAULT null,
  filter jsonb DEFAULT '{}'
) returns table (
  id bigint, content text, metadata jsonb, embedding jsonb, similarity float
)
language plpgsql
as $$
#variable_conflict use_column
begin
  return query
  select id, content, metadata,
    (embedding::text)::jsonb as embedding,
    1 - (documents.embedding <=> query_embedding) as similarity  -- 類似度スコア
  from documents
  where metadata @> filter                          -- メタデータでフィルタ
  order by documents.embedding <=> query_embedding  -- 類似度順
  limit match_count;
end;
$$;
リク
リクmatch_documents は、query_embedding をコサイン類似度で documents のベクトルと比べて、①メタデータ条件でフィルタ →②類似度の高い順 →③match_count 件に制限する。これでSupabaseをベクトルストアとして使える。

検索係の3ステップ

1

メタデータでフィルタ

条件（filter）に合う棚だけに絞り込む。

2

類似度の高い順に並べる

探したい文章のベクトルに近いものから順番に。

3

match_count 件に制限

上位から指定件数だけ返す。

▼ 下のコードは「SupabaseをLangChainの保管庫として登録し、『このドキュメントは何について？』と検索して試す」ものです。読み飛ばしてOK。

Python：Supabaseをベクトルストアとして使い、類似検索をテスト 
# Python
# このコードがやること: SupabaseをLangChainのベクトルストアとして使い、類似検索をテストする。
import os
from langchain_community.vectorstores import SupabaseVectorStore
from langchain_openai import OpenAIEmbeddings
from supabase.client import Client, create_client

supabase_url = os.environ.get("SUPABASE_URL")
supabase_key = os.environ.get("SUPABASE_SERVICE_ROLE_KEY")
supabase: Client = create_client(supabase_url, supabase_key)

embeddings = OpenAIEmbeddings()

vector_store = SupabaseVectorStore(
    embedding=embeddings, client=supabase,
    table_name="documents", query_name="match_documents",
)

# 類似検索のテスト
query = "このドキュメントは何についてのものですか？"
matched_docs = vector_store.similarity_search(query)
print(matched_docs[0].page_content)

③ バックエンドAPI ― LangGraph Platform（発射場）

リク
リクLangGraphアプリをデプロイするにはLangGraph Platformを使う。LangGraphエージェントを大規模にデプロイ・ホスティングするマネージドサービスだ。
ソラ
ソラなんで専用のサービスが要るんですか？
リク
リクエージェントのユースケースが拡大すると、タスクの偏りで特定のエージェントに負荷が集中して、システム全体がダウンしうる。LangGraph Platformは、水平スケーリング可能なタスクキュー・サーバー・PostgresベースのチェックポインタDBで、多数の同時ユーザーに対応し、大規模なステートを効率的に管理する。ストリーミングやヒューマンインザループに加えて、ダブルテキストの再送信操作、長時間タスクの非同期バックグラウンドジョブ、定期実行のCronジョブも提供する。LangGraph Studioもあって、ワンクリックでデプロイできる。

🚀 たとえ話：自前の打ち上げ vs プロの発射場

1機だけ飛ばすなら自宅の庭でもいいかもしれません。でも何百機も、たくさんの利用者から同時に打ち上げ依頼が来たら、自分一人ではさばけず管制塔がパンクします（＝負荷集中でダウン）。LangGraph Platformは、発射台も管制官も必要なだけ増やせるプロの発射場。飛行ログ（チェックポイント）も巨大な倉庫に安全に保管してくれます。

Values各スーパーステップ後のステート全体
Messages完全なメッセージとトークン
Updatesノードごとの更新だけ
Events全イベント（トークン単位も）
Debugデバッグイベント

ダブルテキストの4対策（連投が来たとき）

対策やること
Reject（拒否）新しいメッセージを受け付けない
Enqueue（順番待ち）今の実行が完了してから別実行として処理
Interrupt（割り込み）今の実行を割り込んで途中保存し、新しい方へ
Rollback（巻き戻し）今の実行を巻き戻し、新入力を後続として扱う

🚀 たとえ話：打ち上げ中に「やっぱり別の指令」が来たら

飛行中の機体に管制官が新しい指令を送ったとき、どうするか——「いま忙しいから無視（Reject）」「順番待ちで後で（Enqueue）」「今のを一時停止して新しい方へ（Interrupt）」「今のをなかったことにして新しい方を続きに（Rollback）」。状況に応じて選びます。

✅ 9.2 のまとめ

  • データモデルは4つ：アシスタント（機体）・スレッド（飛行ログ）・実行（1回の飛行）・Cronジョブ（自動予約）。
  • チェックポイント＝飛行ログの特定時点のステート。
  • 機能は5つ：ストリーミング・HITL・ダブルテキスト・ステートレス実行・Webフック。

▼ 下のコードは「使う部品・動かすグラフ・読む環境変数」を書いたフライトプランです。読み飛ばしてOK。

JSON：langgraph.json（設定ファイル）

    "env": ".env"

プロパティ意味

※ このファイルは、コンパイル済みグラフを含むコードと同じか上の階層に置きます。

▼ 下のコードは「リハーサル中のサーバーに『サンフランシスコの天気は？』と聞き、答えを少しずつ受け取る」テストです。読み飛ばしてOK。

Python：SDKでローカルサーバーに接続し、ストリーム受信 
# Python
# このコードがやること: LangGraph SDKでローカルサーバーに接続し、スレッドを作って
# 「サンフランシスコの天気は？」を投げ、更新をストリーム受信する。
from langgraph_sdk import get_client

client = get_client()  # デフォルトポートならurl省略可
assistant_id = "agent"  # "agent" という名前でデプロイされたグラフ
thread = await client.threads.create()

input = {"messages": [{"role": "user", "content": "サンフランシスコの天気はどうですか？"}]}

async for chunk in client.runs.stream(
    thread["thread_id"], assistant_id, input=input, stream_mode="updates",
):
    print(f"新しいイベントを受信: {chunk.event}...")
    print(chunk.data)
    print("\n\n")

9.4

セキュリティ

最小権限・誤用の想定・多層防御
AIアプリは強力ですが、データの破損・紛失、機密情報への不正アクセス、パフォーマンス低下のリスクにさらされています。一般的なベストプラクティスが3つあります。

🚀 たとえ話：宇宙船の安全設計

ロケットは強力なぶん、扱いを誤れば大事故になります。だから——乗組員には必要な鍵だけ渡す（最小権限）、渡した鍵は最悪の使われ方をすると想定して設計する（誤用の想定）、隔壁を何枚も重ねて1枚破られても次で止める（多層防御）。これがLLMアプリの安全設計と同じです。

3つのベストプラクティス

🔑

① 権限の最小化

必要な権限だけ付与。読み取り専用の認証情報を使い、機密リソースへのアクセスを禁止、コンテナでサンドボックス化を検討。

必要な鍵だけ渡す
⚠️

② 誤用を想定

認証情報は、割り当てられた権限の範囲内であらゆる方法で使われうると常に仮定。DB認証情報が削除を許すなら、LLMは実際に削除しうると仮定する。

最悪を想定
🛡️

③ 多層防御

1つの層に頼らず、複数の層を組み合わせる（読み取り専用権限＋サンドボックスの両方）。

隔壁を重ねる

第1問デプロイの3コンポーネント

AIアプリを本番デプロイするのに本書が使う3つのサービス（Supabase・LangSmith・LangGraph Platform）は、それぞれ何の役割ですか。

✅ 解答例
Supabaseはベクトルストア（PostgreSQL＋pgvector拡張）で、データの埋め込みを保存し類似検索を行う。LangSmithはモニタリングとデバッグのオールインワンプラットフォームで、LLMアプリのデバッグ・共同開発・テスト・監視を行い、本番の利用状況・エラー・コストを可視化する。LangGraph PlatformはバックエンドAPIで、LangGraphエージェントを大規模にスケール・ホスティングするマネージドサービス。負荷集中によるダウンを防ぎ、ストリーミング・ヒューマンインザループ・ダブルテキスト・Cronジョブなどを提供する。
📝 採点ポイント
□ Supabase＝ベクトルストア、に触れている ／ □ LangSmith＝モニタリング・デバッグ、に触れている ／ □ LangGraph Platform＝スケーラブルなバックエンド/ホスティング、に触れている
第2問なぜLangGraph Platformか

エージェントアプリをデプロイするのに、なぜLangGraph Platformのような専用サービスが役立つのですか。

✅ 解答例
エージェントのユースケースが拡大すると、タスクの偏りによって特定のエージェントに負荷が集中し、システム全体のダウンタイムを引き起こす可能性があるから。LangGraph Platformは、水平スケーリング可能なタスクキュー・サーバー・PostgresベースのチェックポインタDBで、多数の同時ユーザーに対応し、大規模なステートやスレッドを効率的に保存・管理する。これにより障害耐性のあるスケーラブルなシステムを実現できる。加えて、ダブルテキストの再送信・非同期バックグラウンドジョブ・Cronジョブ・Studioでの可視化なども提供する。
📝 採点ポイント
□ 負荷集中によるダウンの可能性に触れている ／ □ 水平スケーリング・チェックポインタDBで多数の同時ユーザーに対応、に触れている ／ □ 障害耐性・スケーラビリティ、に触れている
第3問APIのデータモデル

LangGraph Platform APIの「アシスタント」と「スレッド」は、それぞれ何ですか。

✅ 解答例
アシスタントは、コンパイル済みグラフ（CompiledGraph）を構成したインスタンス。グラフの認知アーキテクチャを抽象化し、インスタンス固有の設定やメタデータを保持する。同じグラフを複数のアシスタントが、設定やメタデータを変えて参照でき、振る舞いを切り替えられる。スレッドは、実行グループの累積のステートを保存するもの。実行をスレッド上で行うと、その時点のグラフステートが永続化され、現在および過去のステートを取得できる。特定時点のステートを「チェックポイント」と呼ぶ（4章のスレッドと同じ考え方）。
📝 採点ポイント
□ アシスタント＝グラフのインスタンス（設定・メタデータを保持）、に触れている ／ □ スレッド＝実行の累積ステートを保存、に触れている ／ □ チェックポイント（特定時点のステート）に触れている
第4問デプロイの手順

AIアプリをデプロイするまでの大まかな手順を、langgraph.json・ローカルテスト・デプロイの順で説明してください。

✅ 解答例
まず langgraph.json という設定ファイルを用意し、依存パッケージ（dependencies）、グラフIDとその定義へのパスのマッピング（graphs）、環境変数（env）を指定する。次にLangGraph CLIをインストールして langgraph dev でローカル開発サーバーを起動し、LangGraph Studio UIやSDK、cURLでアプリが正しく動くかテストする（デプロイ前にエラーや依存の衝突を検出できる）。最後にLangSmith UIのDeploymentsタブから「New Deployment」を選び、GitHub連携・設定ファイルのパス・ブランチ・開発タイプ（Production）・環境変数（機密はSecret）を入力してデプロイする。
📝 採点ポイント
□ langgraph.json で dependencies/graphs/env を設定、に触れている ／ □ langgraph dev でローカルテスト、に触れている ／ □ LangSmith UIからデプロイ（GitHub連携・環境変数）に触れている
第5問LLMアプリのセキュリティ

LLMアプリのセキュリティのベストプラクティス3つ（権限の最小化・誤用の想定・多層防御）を、データベースアクセスの例で説明してください。

✅ 解答例
権限の最小化は、アプリに必要な権限だけを与えること。DBアクセスなら、エージェントが必要とするテーブルへのアクセスに限定し、読み取り専用の認証情報を発行する。誤用の想定は、認証情報が割り当てられた権限の範囲内であらゆる方法で使われうると仮定すること。DB認証情報が削除を許可しているなら、それを使えるLLMは実際にテーブルを削除しうると仮定する。多層防御は、1つの層に頼らず複数の防御を組み合わせること。読み取り専用権限とサンドボックスの両方を使い、LLMが意図したデータにしかアクセスできないようにする。加えてレートリミットやプロンプトインジェクション対策も行う。
📝 採点ポイント
□ 権限の最小化（読み取り専用・テーブル限定）に触れている ／ □ 誤用の想定（権限内で何でもしうると仮定）に触れている ／ □ 多層防御（複数の層を組み合わせる）に触れている
