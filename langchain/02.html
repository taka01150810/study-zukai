📚 たとえ話：本の中身を「整理番号」に置きかえる

埋め込みは、本の中身を要約した整理番号（数字の列）のようなもの。番号を見ても本文そのものは読めません（不可逆）。だから図書館では、整理番号と本の現物を両方保管します。番号にしておくと「番号が近い＝中身が似ている」と計算で探せるのが利点です。

2.2.1

LLM登場以前の埋め込みBag-of-Words／疎な埋め込み

リク
師匠・リクLLM以前から、コンピューターサイエンティストは埋め込みを使っていた――全文検索やスパムフィルターなどでね。単純な例を見よう。3つの英文を使う（ここは英語の単語の数え方を説明するので、英文のまま示すよ）。
例文（英語）意味
What a sunny day.なんていい天気だ
Such bright skies today.今日の空はとても明るい
I haven't seen a sunny day in weeks.ここ数週間、晴れた日を見ていない
リク
師匠・リク各文に含まれるユニークな単語を列挙して、文ごとに「その単語が何回出るか」を数える。出てこなければ0、1回なら1、というふうに。

リク
師匠・リクたとえば「I haven't seen a sunny day in weeks」の埋め込みは 0 1 1 1 0 0 … 1 という数値列になる。これがBag-of-Words（BoW）モデルだ。要素の多くが0だから疎な埋め込み（疎ベクトル）とも呼ぶ。英文は膨大な英単語のうちごく一部しか使わないからね。
ソラ
弟子・ソラこれで何ができるんですか？
リク
師匠・リクキーワード検索（指定の単語を含む文書を探す）や、ドキュメント分類（スパム/非スパムの平均と比べる）に使える。でも大きな欠点がある――意味をまったく考慮せず、単語の有無だけで表現すること。「sunny day」と「bright skies」は意味が似ているのに、共通語がないから全然違う埋め込みになる。スパマーが「スパム語」を類義語に置き換えると、フィルターをすり抜けてしまう。

⚠️ Bag-of-Words の弱点

  • 単語の有無・回数だけを見て、意味をまったく考えない。
  • 「sunny day」と「bright skies」は意味が近いのに、共通の単語がないと全然別物と判定される。
  • 類義語に置き換えるだけでスパムフィルターをすり抜けられてしまう。

📚 たとえ話：本文を読まず「目次の単語」だけで分類する整理係

Bag-of-Wordsは、本の中身を読まずに目次に出てくる単語を数えるだけで本を仕分ける整理係のようなもの。「晴れの本」と「明るい空の本」は内容が近いのに、たまたま同じ単語が無いと別の棚に入れてしまう。中身（意味）を見ていないので、言葉を言い換えられると簡単にだまされます。

2.2.2 / 2.2.3

LLMベースの埋め込みとセマンティック埋め込み密な埋め込み・コサイン類似度

リク
師匠・リクそこでLLMベースの埋め込みだ。埋め込みモデルは、LLMの学習プロセスから派生した仕組みと考えられる。LLMは膨大なテキストを学んで「文脈における単語や文の意味」を理解する。その意味（セマンティクス）を数値表現として抽出したものが埋め込みだ。実際は、埋め込み生成に特化して学習されたモデルが多い。
リク
師匠・リク埋め込みモデルは、テキストを入力に、その意味を100〜2,000次元くらいの浮動小数点数の配列で出力する。さっきの疎な埋め込みと違って、ほぼすべての次元が0以外の値を取るから密な埋め込みと呼ぶ。
ソラ
弟子・ソラ「意味の近さ」って、どう測るんですか？
リク
師匠・リクlion（ライオン）・pet（ペット）・dog（犬）の3語を考えてみて。直感的に最も似ているのは pet と dog だ。でもコンピューターは直感を理解できないから、数値に翻訳する。意味が近い単語ほど数列が近い位置に、遠い単語は遠い位置に来るように。これを3次元空間にプロットすると、pet と dog のベクトル間距離が lion との距離より短くなる。角度も小さくなる。
リク
師匠・リク2つのベクトルの類似度を測る代表的な手法がコサイン類似度だ。2つのベクトルのドット積を、それぞれの大きさの積で割って、0から1（厳密には−1から1）の範囲で返す。1に近いほど似ていて、0は無相関、−1に近いほど非類似。たとえば pet と dog は0.75、pet と lion は0.1、という具合だ。
ソラ
弟子・ソラ意味を数値にして、近さを計算できるんですね！
リク
師匠・リクそう。これで、テスラの年次報告書みたいな大量テキストから「質問に最も関連するドキュメント」をLLMに見つけさせられる。埋め込みには他にも面白い性質がある――近い点の集合は同じトピック（クラスタリングで抽出できる）、複数の埋め込みの平均はその集合全体の意味、king − man + woman ≒ queen のような足し算引き算で意味空間を移動できる、画像や音声も埋め込めるモデルもある。用途は検索・クラスタリング・分類・推薦・異常検出と多岐にわたるよ。

埋め込みの面白い性質：近い点の集まり＝同じトピック（クラスタリングで抽出）／複数の埋め込みの平均＝その集合全体の意味／king − man + woman ≒ queen のように意味空間を足し算引き算で移動できる／画像や音声も埋め込めるモデルもある。

📚 たとえ話：意味で並ぶ「賢い整理番号」と、棚の近さ

密な埋め込みは、本の中身（意味）まで読んで付ける整理番号。だから「ペットの本」と「犬の本」は番号が近く、書架でも隣どうしに並びます（コサイン類似度0.75）。「ライオンの本」は少し離れた棚（0.1）。利用者が「犬について」と聞けば、整理係は番号が近い棚へ一直線。中身を読んで番号をふったからこそ、言い換えられても正しい棚を選べるのです。

📝 要するに（2.2全体）

  • 埋め込み＝テキストの数値表現（不可逆なので元テキストも保存）。数値化で「単語に計算ができる」。
  • 疎な埋め込み（Bag-of-Words）：単語の出現回数だけ。意味を無視するので類義語に弱い。
  • 密な埋め込み（セマンティック）：意味を100〜2,000次元の数値で表す。意味が近いほどベクトルも近い。
  • コサイン類似度：2ベクトルの近さを測る（1に近いほど類似）。検索・クラスタリング・分類・推薦などに使える。

補足

コンテキストウィンドウの補足なぜ分割が要るか

リク
師匠・リクコンテキストウィンドウは、入力と出力の合計に適用される。たとえば上限が100で入力が90トークンなら、出力は最大10トークンに制限される。典型的には8,192トークンなどだ。英語では1トークンが約3〜4文字だったね。

📚 たとえ話：机に一度に広げられる紙の枚数には限りがある

コンテキストウィンドウは、司書の机の広さ。広げられる紙の合計枚数が決まっていて、参考資料（入力）で机を埋めすぎると、答えを書く紙（出力）の余白が無くなります。だから、分厚い資料はあらかじめ薄い抜き刷りに分けておくのです。

2.4

テキストを分割するステップ②：チャンク分割

リク
師匠・リク大きなテキストを分割するのは簡単そうで、実は複雑だ。「意味的に関連するテキストどうしを同じチャンクに保つ」のが難しい。LangChainは RecursiveCharacterTextSplitter を提供している。
ソラ
弟子・ソラどうやって分割するんですか？
リク
師匠・リク優先度順の区切り文字リストを使う。①段落区切り \n\n → ②行区切り \n → ③単語区切り（スペース）。たとえばチャンクサイズを1,000文字にするなら、まず段落で分割して、それでも超える段落は行で、というふうに、すべてのチャンクが所定の長さ以下になるまで繰り返す。

分割の優先順位（自然な切れ目から順に試す）

1

まず段落で切る（\n\n）

一番自然な切れ目。これで収まればOK。

2

段落が長すぎたら行で切る（\n）

段落単独でも長いとき、行単位に細かくする。

3

それでも長ければ単語（スペース）で切る

すべてのチャンクが所定の長さ以下になるまで繰り返す。

このコードは、ドキュメントを1,000文字ずつのチャンクに分割するもの。chunk_overlap=200 は、隣り合うチャンクを200文字重ねて文脈を保つ設定です。

Python：1,000文字ずつに分割（200文字オーバーラップ）
# このコードがやること: ドキュメントを1,000文字ずつのチャンクに分割する。
# chunk_overlap=200 は、隣り合うチャンクを200文字重ねて文脈を保つための設定。
from langchain_text_splitters import RecursiveCharacterTextSplitter

loader = TextLoader("./test.txt")
docs = loader.load()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
)
splitted_docs = splitter.split_documents(docs)
リク
師匠・リクchunk_overlap=200 で、隣り合うチャンクを200文字分重ねている。これで段落 → 行 → 単語という自然な区切りで、最大1,000文字のチャンクに分かれる。この RecursiveCharacterTextSplitter は、ソースコードやMarkdownを「意味単位」で分割することもできる。from_language メソッドで言語固有のキーワードを区切り文字に使えば、関数の本体が分割されるのを防げる。プログラミング言語は文章より構造が明確だから、オーバーラップは少なめでいい。

🔗 なぜオーバーラップ（重なり）が要るのか

  • 境目でブツッと切ると、前後の文脈が分断され、検索時に意味が伝わりにくくなるから。
  • 隣のチャンクと少し重ねておけば、つなぎ目の話題も両方のチャンクに残り、文脈を保てる。
  • 構造が明確なコードでは切れ目がはっきりしているので、重なりは少なめでよい。

このコードは、Pythonコードを「関数の区切り」など言語の構造を意識して分割する例です。

Python：コードを言語の構造で分割する
# このコードがやること: Pythonコードを、言語の構造（関数の区切りなど）を意識して分割する。
from langchain_text_splitters import (
    Language,
    RecursiveCharacterTextSplitter,
)

PYTHON_CODE = """
def hello_world():
    print("Hello, World!")

# 関数を呼び出す
hello_world()
"""
python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON, chunk_size=50, chunk_overlap=0
)
python_docs = python_splitter.create_documents([PYTHON_CODE])

出力では、関数の定義と呼び出し部分が、それぞれ別のチャンクに分かれます。

出力例
# 出力（関数定義が1つのチャンク、呼び出し部分が別のチャンクに分かれた）
[Document(page_content='def hello_world():\n    print("Hello, World!")'),
 Document(page_content='# 関数を呼び出す\nhello_world()')]
リク
師匠・リクcreate_documents は、ドキュメントのリストじゃなく文字列のリストを引数に取る。生テキストしか手元にないときに便利だ。第2引数に、各文字列に対応するメタデータのリストを渡すこともできる。Markdownの例だと、見出しは1つのチャンク、その下の本文は別のチャンク、というふうに自然な区切りで分割されて、渡したメタデータ（source など）が各ドキュメントに付与される。
ソラ
弟子・ソラメタデータを付けておけば、後で「これはどこから来た情報か」を追跡できるんですね。

📚 たとえ話：意味の切れ目で分冊する「裁断係」

テキストスプリッターは、分厚い本を読みやすく分ける裁断係。やみくもに枚数で切るのではなく、まず章（段落）→ 節（行）→ 文（単語）と自然な切れ目を優先します。さらに、隣の分冊と数ページ重ねて綴じる（オーバーラップ）ことで、章をまたいだ話の流れも失いません。プログラムの本なら「関数のまとまり」で区切るので、説明が途中でちぎれないのです。

テキストの埋め込みを生成するステップ③：埋め込み

このコードは、5つの文をまとめて埋め込み（数値ベクトル）に変換するものです。

Python：複数の文をまとめて埋め込む

出力例
# 出力（各文が1,536個ほどの数値の配列＝埋め込みに変換される。下は最初の文の一部）
[

  ... 3 more items

リク
師匠・リク複数のドキュメントを同時に埋め込める点に注目。1つずつより効率的なんだ。3つの機能――ドキュメントローダー（テキスト化）・テキストスプリッター（分割）・埋め込みモデル（数値化）――を組み合わせると、「読み込む → 分割する → 埋め込む」という流れになる。

このコードは、ドキュメントを「読み込む→分割する→埋め込む」という一連の流れをまとめたものです。

Python：読み込み→分割→埋め込みの一連の流れ
# このコードがやること: ドキュメントを「読み込む→分割する→埋め込む」一連の流れ。
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings

# 1) ドキュメントを読み込む
loader = TextLoader("./test.txt")
doc = loader.load()

# 2) ドキュメントを分割する
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = text_splitter.split_documents(doc)

# 3) 各チャンクを埋め込む
embeddings_model = OpenAIEmbeddings()
embeddings = embeddings_model.embed_documents(
    [chunk.page_content for chunk in chunks]
)
リク
師匠・リク埋め込みを生成したら、次はそれを「ベクトルストア」に格納する。

📚 たとえ話：分冊にまとめて「整理番号」を割りふる係

埋め込みモデルは、裁断された分冊（チャンク）に意味を表す整理番号をふる係。1冊ずつより、まとめて持ち込んだ方が手早く番号付けできます（一括埋め込みが効率的）。質問が来たときも、質問文に同じやり方で番号をふって、近い番号の棚を探します。

2.6

埋め込みをベクトルストアに保存するステップ④：保存・検索

リク
師匠・リクベクトルストアは、埋め込みを保存して、コサイン類似度みたいな複雑な計算を効率的・高速に実行するよう設計されたデータベースだ。構造化データ（JSONやリレーショナルDB）に特化した従来型DBと違って、テキストや画像みたいな非構造化データを扱う。CRUD（作成・読み取り・更新・削除）と検索ができる。
ソラ
弟子・ソラ専用のDBを増やすのは大変そうですね。
リク
師匠・リクいい懸念だ。ベクトルストアには欠点もある――比較的新しくて長期運用が未知数、学習コストが高い、DBが増えると複雑さが増す。幸い、PostgreSQL（広く使われるオープンソースのリレーショナルDB）の pgvector 拡張で、ベクトルストア機能が使える。使い慣れたDB1つで、users テーブルみたいなトランザクションテーブルと、ベクトル検索用テーブルの両方を運用できるんだ。本書ではこのPGVectorを使う。

⚖️ 専用ベクトルストアの欠点と、PGVectorの利点

  • 欠点：比較的新しく長期運用が未知数／学習コストが高い／DBが増えて複雑になる。
  • 利点：PostgreSQLのpgvector拡張なら、使い慣れたDB1つで通常テーブルとベクトル検索を両立できる。
  • 専用DBを増やさずに済むので、運用がシンプルになる。

このコマンドは、Dockerで pgvector 付きのPostgreSQLを6024ポートで起動する準備です。

bash：PGVector（pgvector付きPostgreSQL）をDockerで起動
# PGVector のセットアップ: Docker で PostgreSQL（pgvector付き）を6024ポートで起動する
docker run \
    --name pgvector-container \
    -e POSTGRES_USER=langchain \
    -e POSTGRES_PASSWORD=langchain \
    -e POSTGRES_DB=langchain \
    -p 6024:5432 \
    -d pgvector/pgvector:pg16

# 接続文字列（コードから使う）:
# postgresql+psycopg://langchain:langchain@localhost:6024/langchain
リク
師匠・リクドキュメントをPGVectorに読み込んで、分割して、埋め込んで、保存する例だ。

このコードは、ドキュメントを読み込み→分割→埋め込み→PGVectorに保存する、4ステップ通しの例です。

Python：読み込み→分割→埋め込み→PGVectorに保存
# このコードがやること: ドキュメントを読み込み→分割→埋め込み→PGVectorに保存する。
import uuid
from langchain_community.document_loaders import TextLoader
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_postgres.vectorstores import PGVector
from langchain_core.documents import Document

# ドキュメントを読み込んでチャンクに分割する
raw_documents = TextLoader('./test.txt').load()
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
documents = text_splitter.split_documents(raw_documents)

# チャンクごとに埋め込みを生成してベクトルストアに保存する
embeddings_model = OpenAIEmbeddings()
connection = 'postgresql+psycopg://langchain:langchain@localhost:6024/langchain'
db = PGVector.from_documents(documents, embeddings_model, connection=connection)
リク
師匠・リクfrom_documents は、Postgresに接続して、初回はテーブルを作って、各ドキュメントを埋め込んで、埋め込み・メタデータ・本文を保存する。検索はこうだ。

このコードは、質問「query」に最も近いドキュメントを4個取り出す検索です。

Python：クエリに近いドキュメントを検索
# このコードがやること: クエリ "query" に最も近いドキュメントを4個取得する。
db.similarity_search("query", k=4)
リク
師匠・リク検索の流れは――①クエリを埋め込みモデルで埋め込む → ②保存済みの埋め込みからクエリに最も近いN個（ここでは4個）を探す → ③それぞれのテキストとメタデータを取得 → ④類似度順に並んだ Document のリストを返す（最も似たものが先頭）。ドキュメントの追加や削除もできる。

類似検索（similarity_search）の流れ

1

クエリを埋め込む

質問文を、保存時と同じやり方で数値ベクトルに変換する。

2

最も近いN個を探す

保存済みの埋め込みから、クエリに一番近いもの（ここでは4個）を選ぶ。

3

テキストとメタデータを取得

近かったチャンクの本文と出典情報を引き出す。

4

類似度順に並べて返す

最も似たものが先頭のDocumentリストとして返る。

このコードは、既存のDBに2つのドキュメントを追加し、片方をIDで削除する例です。IDを付けておくと後で更新・削除できます。

Python：ドキュメントの追加と削除
# このコードがやること: 既存のDBに2つのドキュメントを追加する。id を付けておくと後で更新・削除できる。
ids = [str(uuid.uuid4()), str(uuid.uuid4())]
db.add_documents(
    [
        Document(
            page_content="池には猫がいる",
            metadata={"location": "pond", "topic": "animals"},
        ),
        Document(
            page_content="池にはアヒルもいる",
            metadata={"location": "pond", "topic": "animals"},
        ),
    ],
    ids=ids,
)

# 2つ目のドキュメントを UUID 指定で削除する
db.delete(ids=[ids[1]])

📚 たとえ話：整理番号順に並ぶ「巨大な書架」

ベクトルストアは、整理番号順にずらりと並んだ巨大な書架。利用者が質問すると、その質問にも整理番号をふり、番号が近い棚の本を上位4冊だけ素早く抜き出します（similarity_search, k=4）。新しい本を棚に足す（追加）、入れ替える（更新）、廃棄する（削除）こともでき、これがCRUDです。PGVectorなら、いつもの図書館システムにこの検索棚を増設するだけで済みます。

2.7

ドキュメントの変更を追跡するインデックス化API

リク
師匠・リクベクトルストアの大きな課題が「頻繁に変化するデータへの対応」だ。データが変わると再インデックスが必要で、埋め込みの再計算や重複が高コストになる。LangChainにはインデックス化APIがあって、ドキュメントとベクトルストアを簡単に同期できる。RecordManager（レコードマネージャー）クラスが、各ドキュメントのハッシュ・書き込み時刻・ソースIDを保存して、書き込み状況を管理するんだ。
ソラ
弟子・ソラ古いデータの削除はどうするんですか？
リク
師匠・リククリーンアップモードで制御する。①None モード――自動クリーンアップなし、手動で削除。②Incremental（増分）モード――ソースドキュメントの内容が変わったら、以前のバージョンを削除する。③Full（完全）モード――さらに、インデックス対象になっていないドキュメントも削除する。

3つのクリーンアップモード

このコードは、レコードマネージャーでドキュメントとベクトルストアを同期する例。1回目は両方登録、2回目は同じなので追加されず（重複防止）、3回目は1つ目を変更して古い版が消えます。

Python：レコードマネージャーでインデックスを同期
# このコードがやること: レコードマネージャーで、ドキュメントとベクトルストアを同期する。
#  1回目: 両方のドキュメントがインデックスされる。
#  2回目: 同じなので追加されない（重複を防ぐ）。
#  3回目: 1つ目を変更すると、新バージョンが書かれ、同じソースの古いバージョンは削除される。
from langchain.indexes import SQLRecordManager, index
from langchain_postgres.vectorstores import PGVector
from langchain_openai import OpenAIEmbeddings
from langchain.docstore.document import Document

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"
collection_name = "my_docs"
embeddings_model = OpenAIEmbeddings(model="text-embedding-3-small")
namespace = "my_docs_namespace"

vectorstore = PGVector(
    embeddings=embeddings_model,
    collection_name=collection_name,
    connection=connection,
    use_jsonb=True,
)

record_manager = SQLRecordManager(
    namespace,
    db_url="postgresql+psycopg://langchain:langchain@localhost:6024/langchain",
)
record_manager.create_schema()  # スキーマが存在しない場合は作成する

docs = [
    Document(page_content='池には猫がいる', metadata={"id": 1, "source": "cats.txt"}),
    Document(page_content='池にはアヒルもいる', metadata={"id": 2, "source": "ducks.txt"}),
]

# ドキュメントをインデックスする（incremental で重複を防ぐ、source をソースIDに使う）
index_1 = index(docs, record_manager, vectorstore,
                cleanup="incremental", source_id_key="source")
print("Index attempt 1:", index_1)

# 2回目: 同じなので追加されない
index_2 = index(docs, record_manager, vectorstore,
                cleanup="incremental", source_id_key="source")
print("Index attempt 2:", index_2)

# 3回目: 1つ目を変更 → 新バージョンが書かれ、古いバージョンは削除される
docs[0].page_content = "このドキュメントを更新しました！"
index_3 = index(docs, record_manager, vectorstore,
                cleanup="incremental", source_id_key="source")
print("Index attempt 3:", index_3)

MultiVectorRetriever：検索と回答生成の情報を切り離す

リク

検索用（要約）と回答用（実物）を分ける流れ

1

表を要約して埋め込む

表の内容を短く要約し、元の表への参照IDを付けて検索用ベクトルストアへ。

2

3

このコードは（要点）、各チャンクをLLMで要約し、要約を検索用ストア・元チャンクを回答用ストアに分けて格納する MultiVectorRetriever を作る例です。

Python：MultiVectorRetriever を作る
# このコードがやること（要点）: 各チャンクをLLMで要約し、要約をベクトルストアに（検索用）、
# 元のチャンクをドキュメントストアに（回答用）格納する MultiVectorRetriever を作る。
import uuid
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_postgres.vectorstores import PGVector
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.documents import Document
from langchain.retrievers.multi_vector import MultiVectorRetriever
from langchain.storage import InMemoryStore
from langchain_community.document_loaders import TextLoader

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"
embeddings_model = OpenAIEmbeddings()
docs = TextLoader("./test.txt", encoding="utf-8").load()
chunks = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200).split_documents(docs)

# 各チャンクをLLMで要約する
prompt = ChatPromptTemplate.from_template("以下のドキュメントを要約してください:\n\n{doc}")
llm = ChatOpenAI(temperature=0, model="gpt-4o-mini")
summarize_chain = {"doc": lambda x: x.page_content} | prompt | llm | StrOutputParser()
summaries = summarize_chain.batch(chunks, {"max_concurrency": 5})

# 要約用ベクトルストアと、元チャンク用ドキュメントストアを用意する
vectorstore = PGVector(embeddings=embeddings_model, collection_name="summaries",
                       connection=connection, use_jsonb=True)
store = InMemoryStore()
id_key = "doc_id"
retriever = MultiVectorRetriever(vectorstore=vectorstore, docstore=store, id_key=id_key)

# 各要約に、対応する元チャンクのIDを紐付ける
doc_ids = [str(uuid.uuid4()) for _ in chunks]
summary_docs = [Document(page_content=s, metadata={id_key: doc_ids[i]})
                for i, s in enumerate(summaries)]
retriever.vectorstore.add_documents(summary_docs)        # 要約を検索用に追加
retriever.docstore.mset(list(zip(doc_ids, chunks)))      # 元チャンクを回答用に格納

# クエリで「要約」を検索 → その参照先の「元の大きなチャンク」を取得する
retrieved_docs = retriever.invoke("哲学の章")

MultiVectorRetrieverは、カード目録と書庫を分けた図書館。利用者は薄くて探しやすいカード（要約）をめくって目的の本を見つけますが、実際に渡されるのは書庫の分厚い現物（元の表や本文）。表のような壊れやすい資料も、現物は書庫に丁寧に保管したまま、目録だけで素早く検索できるのです。

2.8.2

RAPTOR：木構造検索のための再帰的抽象化

リク
師匠・リクRAGは「1つの文書の特定の事実を聞く低レベルな質問」と「多数の文書にまたがる概念を抽出する高レベルな質問」の両方に対応しなきゃいけない。通常のk近傍法による検索だと、両方を同時に扱うのが難しい。
リク
師匠・リクRAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）は、より高レベルの概念を捉えた要約を生成して、それらを埋め込み、クラスタリングして、さらに各クラスターを要約する――これを再帰的に繰り返す。結果として「高次の概念を持つ要約ツリー」ができる。この要約群と元のドキュメントを一緒にインデックス化すれば、低レベルから高レベルまで幅広い質問をカバーできるんだ。

🧩 なぜ「ツリー（木）」が要るのか

  • 「ある1文の事実」を聞く低レベル質問と、「全体を貫く概念」を聞く高レベル質問の両方に答えたいから。
  • 普通の近傍検索は細かいチャンク向きで、文書全体にまたがる大きな概念をすくいにくいから。
  • 要約 → まとめ → さらに要約…と階層を作れば、どの粒度の質問にも対応できる。

再帰的に要約を重ねるサイクル

① 要約する

高レベルの概念を捉えた要約を生成する。

→

② 埋め込む

要約を数値ベクトルに変換する。

→

③ クラスタリング

似た要約をグループにまとめる。

→

④ さらに要約

各グループをもう一段要約し、①へ戻って繰り返す。

🔁 これを再帰的に繰り返すと「高次の概念を持つ要約ツリー」ができる（要約群＋元の文書を一緒にインデックス化）

📚 たとえ話：分野 → ジャンル → 全集と階層化する書架案内

RAPTORは、図書館の多層フロアガイド。1冊ごとの本（細かい事実）の上に「ジャンル別の解説板」を置き、さらにその上に「フロア全体のテーマ案内」を置く――と段階的にまとめます。これで「この本の◯ページの数字は？」という細かい質問にも、「この図書館は全体として何を集めているの？」という大きな質問にも、同じ案内図で答えられます。

2.8.3

ColBERT：埋め込みの最適化

リク
師匠・リク埋め込みモデルの課題の1つは、「テキストを固定長の埋め込みに圧縮する」こと。圧縮は検索に有効だけど、無関係/冗長なコンテンツまで埋め込むとハルシネーションの原因になる。ColBERTは――①ドキュメントとクエリの各トークンについてコンテキスト埋め込みを生成 → ②各クエリトークンとドキュメント内の全トークンの類似度を計算 → ③最大類似度スコアを合計してドキュメントごとのスコアを算出。より細かい粒度で検索精度が上がる。

ColBERT：トークン単位で精密に測る3ステップ

1

トークンごとに埋め込む

ドキュメントとクエリの「各単語（トークン）」について、文脈込みの埋め込みを作る。

2

総当たりで類似度を計算

各クエリトークンと、ドキュメント内の全トークンの類似度を計算する。

3

最大スコアを合計

クエリトークンごとの最大類似度を足し合わせ、ドキュメントのスコアにする。

結果：1つに圧縮するより細かい粒度で、検索精度が上がる。

このコードは、ColBERT（RAGatouille経由）で宮崎駿のWikipediaページをインデックスし、「宮崎が設立したアニメーションスタジオは？」を検索する例です。

Python：ColBERT で宮崎駿のページを検索
# このコードがやること: ColBERT（RAGatouille経由）で宮崎駿のWikipediaページをインデックスし、
# 「宮崎が設立したアニメーションスタジオは？」を検索する。

# （get_wikipedia_page でページ全文を取得する関数は省略）

RAG.index(collection=[full_document], index_name="Miyazaki-123",

# クエリ（英語クエリだが、検索対象が英語Wikipediaなのでそのまま）

第1問なぜRAGが必要か

LLMは賢いのに、なぜRAGで外部データを渡す必要があるのですか。LLMの知識の2つの制限を挙げて説明してください。

✅ 解答例
LLMの知識には2つの制限があるから。①非公開データ：公開されていない社外秘の情報などは学習データに含まれない。②時事情報：LLMの学習にはデータ収集から始まる長期間の工程が必要で、学習データが確定した日付以降の出来事は知らない（ナレッジカットオフ）。どちらの場合も、知らないことを聞くとハルシネーション（もっともらしい嘘）を起こしやすい。プロンプトを工夫しても知識自体の不足は補えないので、RAGで関連する正しいデータをコンテキストとして渡す。
📝 採点ポイント
□ 非公開データは学習に含まれない、に触れている ／ □ 時事情報（ナレッジカットオフ）に触れている ／ □ 知らないことを聞くとハルシネーションを起こす、に触れている
第2問疎な埋め込みと密な埋め込み

Bag-of-Words（疎な埋め込み）とセマンティック（密な埋め込み）の違いを説明してください。前者の欠点も述べてください。

✅ 解答例
Bag-of-Wordsは、文に含まれる各単語の出現回数を数えて数値列にする方法で、ほとんどの要素が0になる疎なベクトル。キーワード検索や分類に使えるが、単語の有無だけで意味を一切考慮しないのが欠点。「sunny day」と「bright skies」は意味が近いのに、共通語がないと全然違う埋め込みになり、類義語に置き換えられると検索やフィルターをすり抜ける。一方、密なセマンティック埋め込みは、LLMベースのモデルが「意味」を100〜2,000次元の数値で表現し、意味が近いほどベクトルも近くなる。
📝 採点ポイント
□ Bag-of-Words＝単語の出現回数、疎、意味を無視、に触れている ／ □ 類義語に弱いという欠点に触れている ／ □ 密なセマンティック埋め込み＝意味を数値化、意味が近いほど近い、に触れている
第3問インデックス化の4ステップ

ドキュメントをLLMで使えるようにする「インデックス化」の4ステップを、順を追って説明してください。

✅ 解答例
①テキスト化：ドキュメントローダーで、PDFやWebなど各形式からテキストとメタデータを持つDocumentを抽出する。②分割：テキストスプリッター（RecursiveCharacterTextSplitter）で、段落→行→単語の優先順で意味を保ちながら、コンテキストウィンドウに収まる扱いやすいチャンクに分割する（オーバーラップで文脈を維持）。③埋め込み：埋め込みモデルで、各チャンクを意味を表す密な数値ベクトルに変換する。④保存：ベクトルストア（PGVectorなど）に埋め込み・本文・メタデータを保存し、質問に関連する箇所を素早く検索できるようにする。
📝 採点ポイント
□ テキスト化→分割→埋め込み→保存の4ステップを順に挙げている ／ □ 各ステップで使う道具（ローダー・スプリッター・埋め込みモデル・ベクトルストア）に触れている ／ □ 分割の目的（コンテキストウィンドウに収める）に触れている
第4問ベクトルストアとPGVector

ベクトルストアとは何ですか。専用のベクトルストアではなくPGVectorを使う利点は何ですか。

✅ 解答例
ベクトルストアは、埋め込みを保存し、コサイン類似度のような計算を効率的・高速に実行できるよう設計された、非構造化データ向けのデータベース。CRUDと類似検索ができる。専用ベクトルストアは新しくて長期運用が未知数、学習コストが高い、DBが増えて複雑になる、という欠点がある。PGVectorは、広く使われるオープンソースのPostgreSQLのpgvector拡張なので、使い慣れたDB1つで、通常のトランザクションテーブルとベクトル検索用テーブルの両方を運用でき、追加のDBを増やさずに済むのが利点。
📝 採点ポイント
□ ベクトルストア＝埋め込みを保存し高速に類似検索するDB、に触れている ／ □ 専用ベクトルストアの欠点（新しい・学習コスト・複雑さ）に触れている ／ □ PGVectorは既存のPostgreSQLを活用でき、DBを増やさずに済む、に触れている
第5問MultiVectorRetriever

表を含むドキュメントをそのまま分割・埋め込みすると何が問題で、MultiVectorRetrieverはどう解決しますか。

✅ 解答例
表を含むドキュメントを単にテキストとして分割すると、表の構造が壊れて情報が失われ、回答に必要な内容を完全な形で渡せない。MultiVectorRetrieverは「検索に使う情報」と「回答生成に使うドキュメント」を切り離す。たとえば表の内容を要約して埋め込み（要約に元の表への参照IDを付ける）、元の表は別のドキュメントストアに格納する。クエリで要約が取得されたら、その参照先の元の表をコンテキストとしてLLMに渡す。これで、検索しやすさと、回答に必要な完全な情報の両立ができる。
📝 採点ポイント
□ 表を単純に分割すると情報が失われる、に触れている ／ □ 検索用（要約）と回答用（元データ）を切り離す、に触れている ／ □ 要約で検索→参照先の元データをコンテキストに渡す、に触れている
