信頼性 reliability

出てくる答えをどこまで信用できるか。事故なく正しく着く度合い。

片方を上げると片方が下がる関係。自律性と信頼性はシーソー。

「今の技術で両立できる限界の線」。これを外へ押し広げるのが目標。

答えが返るまでの時間。配車を頼んでから到着までの時間。

最終回答の前の、各ステップの途中結果。今どの道を走っているかの実況。

ステート state（状態）

今までに積み上がった情報のまとまり。走行ログ・現在地。

処理の途中に人が入って止めたり承認したりする仕組み。運行管理センターの人。

特定の操作の前に自動で止まり、人の許可を待つこと。「決済前に確認」。

フォーク fork（分岐）

同じ地点から枝分かれして、別バージョンを試すこと。別ルートを並行で走らせる。

8.1

構造化された出力

決まった形で答えさせて予測性を上げる

下流（後の処理）が特定の形（項目名と型）を期待していたり、自由文だと扱いにくいとき、LLMにきっちりした形で答えさせます。予測性が上がるのがメリット。

リク
リクLLMが構造化された出力を返すのはとても重要だ。下流で特定のスキーマを期待していたり、自由形式テキストを避けて予測性を高めたいからね。

LangChainは共通インターフェース with_structured_output で、これらを簡単に使えるようにしてくれます。

🚕 たとえ話：自由メモ vs 配車伝票

運転AIに「どこへ行く？」と聞いて、自由メモで「えーっと渋谷あたり…」と返ってくると、後の精算係が困ります。そこで配車伝票（出発地・目的地・料金…という決まった欄）を渡しておく。AIは欄を埋めるだけ。これが構造化出力。欄ごとに「ここは目的地」と説明書きを付けておくと、AIがどの情報をどこに書くか間違えません。

コードで見る①：スキーマ（伝票の様式）を定義する

「ジョークのセットアップ（前ふり）とオチ」を持つ様式を定義します。各欄の説明（description）が、AIへの「ここに何を書くか」のヒントになります。

Python：Joke スキーマの定義 
# Python
# このコードがやること: 「ジョークのセットアップ(setup)とオチ(punchline)」を持つスキーマを定義する。
# 各フィールドの description は、LLMがどの部分をどのフィールドに入れるか判断する手がかりになる。
from pydantic import BaseModel, Field

class Joke(BaseModel):
    setup: str = Field(description="ジョークのセットアップ")
    punchline: str = Field(description="ジョークのオチ")
リク
リク各フィールドに説明を加えるのが大事だ。フィールド名とともに、LLMが「出力のどの部分をどのフィールドに入れるか」を判断する材料になる。このスキーマに従わせてみよう。

コードで見る②：スキーマをモデルに設定して質問する

様式（Joke）をモデルに設定し、「猫のジョークを教えて」と尋ねます。返った出力はスキーマで検証され、合わなければエラーになります。

Python：with_structured_output で質問 
# Python
# このコードがやること: スキーマ(Joke)をモデルに設定し、「猫のジョークを教えて」と尋ねる。
# 返ってきた出力はスキーマで検証される（合わなければバリデーションエラー）。
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
model = model.with_structured_output(Joke)

model.invoke("猫についてのジョークを教えてください")

返ってくる答え（setup と punchline を持つ構造化データ）：

出力例 
# 出力（setup と punchline を持つ構造化データが返る）
{
    setup: "なぜ野生の猫はポーカーをしないのですか？",
    punchline: "イカサマ師（チーター）が多すぎるから。"
}

💡 ここでのポイント

  • 低い temperature（0に近い）は、スキーマに合わない出力を減らす。
  • スキーマにPydantic（JS：Zod）を渡すと、バリデーションに使われ、合わない出力ならバリデーションエラーが返る。
  • このパターンは、独立したツールとしても、大きなアプリの一部（5章のルーティング）としても使える。

8.1.1　中間出力

途中経過を見せて待ち時間を快適に

アーキテクチャが複雑になるほど、実行に時間がかかります。でもユーザーは数秒以内を期待。対策はストリーミング——動作中にリアルタイムで途中経過を見せること。

リク
リク複数のステップやノードが順番に（またはループで）つながると、最終回答まで時間がかかる。LangGraphでは stream() で、各ノードが完了するたびに出力を得られるんだ。

グラフを stream で実行し、各ノードが終わるたびに更新を表示します。

Python：stream でノードごとの中間出力 
# Python
# このコードがやること: グラフを stream で実行し、各ノードが完了するたびに結果（更新）を表示する。
from langchain_core.messages import HumanMessage

user_input = {
    "messages": [HumanMessage("アメリカ合衆国の第30代大統領は、亡くなったとき何歳でしたか？")]
}

for c in graph.stream(user_input, stream_mode='updates'):
    print(c)
リク
リク各出力は「ノード名をキー、ノードの出力を値」とする辞書だ。どのノードが動いたか、ステートがどう積み上がるかが見える。stream_mode には複数モードがあるよ。

stream_mode の種類

モードいつ何を出すか
updates（デフォルト）各ノードの更新（差分）を出す
valuesステートが変わるたびに全体を出す
debug詳細なイベントを出す
checkpointチェックポイント保存時に出す
task / task_resultノードの開始時／終了時に出す

これらは組み合わせて使うこともできます。

🚕 たとえ話：「あと3分」表示があるから待てる

配車アプリで何も表示されないと、お客は「来ないのでは？」と不安でキャンセルします。でも地図に車が動いて「あと3分」「今◯◯交差点」と途中経過が出れば、同じ待ち時間でも安心して待てます。stream はこの「実況中継」。updates は通過した駅だけ、values は毎回ルート全体を表示する違いです。

8.1.2　LLM出力をトークンごとにストリーミングする

単語が出るたびに逐次表示

チャットボットのように、単語（トークン）が生成されるたびに逐次表示したいこともあります。astream_events で、各LLM呼び出しからトークン単位のストリーミングが得られます。

LLMがトークン（単語のかけら）を作るたびに表示します。生成中チャンク（chunk）を順に出します。

Python：astream_events でトークン単位ストリーミング 
# Python
# このコードがやること: astream_events で、LLMがトークン（単語）を生成するたびに表示する。
# on_chat_model_stream イベントの中身（chunk）を順に出力する。
user_input = {
    "messages": [HumanMessage("アメリカ合衆国第30代大統領が亡くなったとき、何歳でしたか。")]
}

output = app.astream_events(user_input, version="v2")

async for event in output:
    if event["event"] == "on_chat_model_stream":
        content = event["data"]["chunk"].content
        if content:
            print(content)
リク
リクこれで、LLMが各トークンを生成した瞬間に出力される。タイピングするように表示される、あれだね。

8.1.1 が「駅ごとの通過報告」なら、こちらは運転AIの音声ガイドを一語ずつ垂れ流すイメージ。「つ・ぎ・は・右・折・し・ま・す」と1文字ずつ届くので、まだ全部しゃべり終わる前から内容が見えて、待っている感じが消えます。

8.1.3　ヒューマンインザループモダリティ

人が処理に介入して信頼性を高める

自律性を高めるほど、人は制御を手放してエージェントに能力を委ねます。LangGraphの共有ステートパターンは、アプリを観測・中断・修正しやすくします。これで人が介入する各モードが使えます。まずチェックポインタをアタッチします（4章でやった）。

ソラ
ソラどんなモードがあるんですか？
リク
リクまず割り込み（interrupt）。最もシンプルで、ユーザーが出力を見ながら適切なときに手動で中断する。中断時のステート（最後の完了ステップの時点）が保存され、そこから「再開」「新入力で再起動」「何もしない」を選べる。

astream で実行しつつ、外部イベント（event）がセットされたら中断します。thread_id でこの操作を識別します。

Python：割り込み（外部イベントで中断） 
# Python
# このコードがやること: astream で実行しつつ、外部のイベント(event)がセットされたら中断する。
# aclosing でストリームを適切に閉じる。thread_id でこの操作を識別する。
from langchain_core.messages import HumanMessage
import asyncio

event = asyncio.Event()

user_input = {
    "messages": [HumanMessage("アメリカ合衆国第30代大統領が亡くなったとき、何歳でしたか。")]
}
config = {"configurable": {"thread_id": "1"}}

async with aclosing(graph.astream(user_input, config)) as stream:
    async for chunk in stream:
        if event.is_set():
            break
        else:
            ...  # 出力を使って何かを行う

# アプリケーション内の他の場所
event.set()
リク
リク2つ目は承認（authorize）。特定のノードが呼ばれたらユーザーに制御を渡す。多くはツール呼び出しの前の確認だ。interrupt_before=['tools'] で、tools ノードに入る直前まで実行して止める。

tools ノードに入る直前で止めて、ツール実行を承認するか確認できるようにします。

Python：承認（interrupt_before でツールの前に停止） 
# Python

▶

再開（resume）

入力を None にして再度呼ぶ。「直前の処理を続行せよ」の合図。

↻

再起動（restart）

新しい入力とともに呼ぶ。現在のステートを保持して新入力をマージし、最初のノードからやり直す。状態を破棄したいなら thread_id を変える。

⑂

8.1.4　マルチタスクLLM（ダブルテキスト）

前の答えが終わる前に次の入力が来る

回答に時間がかかると、前の処理が終わる前にユーザーが新しい入力を送ってくる——これがダブルテキスト。扱い方は5つあります。

リク
リクLLMが遅くて長い出力を生成するときや、マルチステップで連鎖するとき、特に重要になる問題だ。5つの扱い方を見ていこう。
🚫

① 同時入力を拒否する

処理中に来た入力を全部拒否。最も単純だが、並行処理の管理を呼び出し側に委ねることになる。

短所：丸投げ
🧵

② 単独で扱う

新入力を独立した呼び出しとみなし、新しいスレッドを作る。複数会話に拡張できるが、2つの呼び出しを別々に示すことになる。

短所：会話が分断
🚶‍♂️🚶‍♀️

③ キューに入れる

来た入力を行列に溜め、現在の処理が終わってから処理。到着順によらず結果が同じだが、無制限に膨らむ・入力が古くなる恐れ（前の回答に依存する入力に不向き）。

短所：古くなる/膨らむ
⏹️

④ 割り込み

新入力が来たら現在の処理を放棄し、新入力でチェーンを再開。何を保持するか選べる。レイテンシー改善・陳腐な出力を防げるが、1度に1入力、ステート設計前提で壊れやすい。

短所：1入力のみ
⑂🔀

⑤ フォークとマージ

新入力を並列処理し、完了時に最終ステートをマージ。競合なくマージできる設計（CRDTなど）か手動解決すれば総合的に最良——適時処理・受信時刻に依存しない出力・任意数の並行実行。

長所：総合的に最良
リク
リクこれらの一部はLangGraph Platform（9章）で実装されている。レイテンシーが改善しても、同時入力の扱いは課題であり続ける——どんなに生産的な人でも時間は有限で、要求に優先順位を付けなきゃいけないのと同じだ。

🚕 たとえ話：配車中にお客が追加注文してきたら？

1台で配車処理している最中に、同じお客が「やっぱり別の場所にも寄って」と追加注文。①拒否＝「いま処理中なので後で」と断る。②単独で扱う＝別のタクシーを新たに手配する。③キュー＝注文を行列に並べ、今の配車が終わってから順に対応。④割り込み＝今の配車をやめ、新しい注文でやり直す。⑤フォークとマージ＝2台を同時に走らせ、終わったら2つの結果をうまく1つにまとめる。状況に応じて店長が方針を選びます。

章末の理解度チェック（全5問）

自分の言葉で答えてみよう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」。解答例と採点ポイントは折りたたみの中です。

第1問自律性と信頼性のフロンティア

「自律性と信頼性のフロンティア（境界線）」とは何ですか。開発者は何を目指しますか。

✅ 解答例
自律性（人の関与なしにどこまでできるか）と信頼性（出力をどこまで信用できるか）はトレードオフの関係にあり、それを曲線（フロンティア）として表せる。曲線上の各点が、両者のバランスが違う最適なアーキテクチャ（チェーンは信頼性高め・自律性低め、エージェントはその逆）。開発者が目指すのは、このフロンティアを外側にシフトさせること——同じ信頼性のままより自律的に、または同じ自律性のままより信頼性を高くすること。構造化出力・ストリーミング・ヒューマンインザループなどの技でそれを実現する。
📝 採点ポイント
□ 自律性と信頼性のトレードオフを曲線で表す、に触れている ／ □ チェーンとエージェントでバランスが違う、に触れている ／ □ フロンティアを外側にシフトさせるのが目標、に触れている
第2問構造化出力

LLMに構造化された出力をさせる方法を挙げ、with_structured_output が何をしてくれるか説明してください。

✅ 解答例
方法は3つ。プロンプト（希望の形式で返すよう依頼するが保証はない）、ツール呼び出し（出力可能なスキーマから選ばせる）、JSONモード（有効なJSONを強制）。with_structured_output は、これらの共通インターフェースで、スキーマ（PythonはPydantic、JavaScriptはZod、またはJSON Schema）を渡すと、構造化された出力を生成するためのパラメータや出力パーサーを追加してくれる。さらに、PydanticやZodを渡せばそれをバリデーションに使い、LLMがスキーマに合わない出力を出した場合はバリデーションエラーを返す。
📝 採点ポイント
□ プロンプト・ツール呼び出し・JSONモードの3方法に触れている ／ □ with_structured_output にスキーマを渡す、に触れている ／ □ バリデーション（スキーマに合わないとエラー）に触れている
第3問ストリーミングの意義

複雑なLLMアプリはレイテンシーが大きくなります。なぜストリーミング（中間出力）がユーザビリティの維持に役立つのですか。

✅ 解答例
複雑なアーキテクチャは複数のステップやループを通るため、最終回答までに時間がかかる。ほとんどのユーザーは数秒以内の結果を期待するので、何も見せずに待たせると離脱の原因になる。ストリーミングは、アプリの動作中にリアルタイムで出力（各ノードの中間結果や、LLMのトークン単位の生成）を見せる。レイテンシー自体は減らなくても、進行状況が見えることでユーザーは安心して待てる。LangGraphでは stream（ノード単位）や astream_events（トークン単位）で実現する。
📝 採点ポイント
□ 複雑なアーキテクチャはレイテンシーが大きい、に触れている ／ □ 進行状況/中間出力を見せると待てる、に触れている ／ □ stream（ノード単位）やトークン単位のストリーミングに触れている
第4問ヒューマンインザループ

ヒューマンインザループの「割り込み」と「承認」の違いを説明してください。なぜ自律的なアーキテクチャでこれが重要なのですか。

✅ 解答例
割り込み（interrupt）は、ユーザーが出力を見ながら、適切だと判断したときに手動で中断する方法。承認（authorize）は、特定のノード（多くはツール呼び出し）が呼ばれる前に、あらかじめ自動で一時停止してユーザーに確認を求める方法（interrupt_before）。自律的なアーキテクチャでは、エージェントが人の関与なしに行動するため、危険なツール実行などの前に人が中断・承認・取り消しできる仕組みがないと、意図しない挙動を防げない。だからヒューマンインザループは、自律的なアーキテクチャの信頼性を高めるのに重要。
📝 採点ポイント
□ 割り込み＝ユーザーが手動で中断、に触れている ／ □ 承認＝特定ノードの前に自動で一時停止して確認、に触れている ／ □ 自律的なアーキテクチャの信頼性を高める、に触れている
第5問同時入力の扱い

「ダブルテキスト（同時入力）」の扱い方のうち「キューに入れる」と「割り込み」の違いを、それぞれの長所・短所を含めて説明してください。

✅ 解答例
キューに入れるは、処理中に受け取った入力をキューに溜めて、現在の処理が終わってから順に処理する。任意の数を受け付けられ、到着タイミングによらず結果が同じだが、キューが無制限に膨らむ可能性があり、入力が処理される頃には古くなっていることがある（前の回答に依存する入力には不向き）。割り込みは、新しい入力を受け取ると現在の処理を放棄して新しい入力で再開する。新入力をすぐ処理できてレイテンシーが改善し陳腐な出力を防げるが、1度に1入力に限られ、部分的なステートを保持するには前提とした設計が必要で、出力が受信タイミングに左右される。
📝 採点ポイント
□ キュー＝溜めて順に処理、到着順によらず同じ結果だが古くなる/膨らむ、に触れている ／ □ 割り込み＝現在を放棄して新入力で再開、すぐ処理できるが1入力に限られる、に触れている ／ □ それぞれの長所・短所を対比している
