両立できないものを、両立に近づける

「エージェントは自律的で便利だけど、信頼できないんですよね……」とソラ。リク先輩は「そう、自律性と信頼性はつり合いの関係だ。でも、その境界線を外側に押し広げる技がある」と答えます。

この章では、5章で触れた「自律性と信頼性」のつり合いを掘り下げ、両立させるための実践的なやり方を学びます。構造化された出力（結果が読めるようにする）、ストリーミング・中間出力（待ち時間を受け入れてもらう）、ヒューマンインザループ（人が入って信頼性を高める）、そしてダブルテキスト（同時に来た入力の扱い方）です。

学ぶ理由と、身につくこと

🟣 なぜ学ぶ価値があるのか

  • 自律性を上げると信頼性が下がる、というつり合いを理解しないと、便利さを追って事故を起こすから。
  • 複雑な作りは待ち時間が長く、何も見せないと利用者が離れてしまうから。
  • 自律的なエージェントこそ、人が止めたり承認したりできる仕組みがないと危険だから。

🟢 これを知ったらできるようになること

  • with_structured_output で出力を読める形にできる。
  • stream の各受け取り方や、文字のかたまり単位のストリーミングで、進み具合を見せられる。
  • ヒューマンインザループ（割り込み・承認・再開・再起動・編集・フォーク）で人の介入を組み込める。
  • 同時に来た入力の5つの扱い方を、用途に応じて選べる。

押し広げた境界線

🔎 具体例：境界線が外側に動くとはどういうことか

メールの自動返信エージェントを考えます。技を使う前：完全自動にすると誤送信が怖いので、すべての返信を人が読んでから送る運用にしていました。自律性は低いままです。

技を使った後：送信という危険な操作の直前だけ自動で止めて確認を求める（承認）ようにしました。人が確認するのは1通あたり2秒。それ以外の下書き・分類・整理はすべて自動で進みます。誤送信の危険は前と同じくらい低いのに、人の作業は大幅に減りました——これが「同じ信頼性のまま、自律性を上げた」状態です。

8.1

構造化された出力

結果が読める形にする

要するに：後ろの処理が特定の形を期待しているとき、自由な文章のままだと使えません。決められた形で返させると、結果が読めるようになります。

リク
リクLLMが決まった形で答えるのはとても重要だ。後ろの処理が特定の形（項目の名前と種類）を期待していたり、自由な文章を避けて結果を読めるようにしたいからね。やり方は3つある。
📝

① 指示文で頼む

「この形で返して」と文章でお願いします。単純ですが、守られる保証はありません。

🔧

② ツール呼び出しを使う

出せる形をあらかじめ用意しておき、その中から選ばせます。

🔒

③ JSONモード

必ずJSONの形で答えるよう、モデル側の設定で強制します。

LangChainは with_structured_output という共通の呼び方で、これらをまとめて簡単にしてくれます。

コードを見る（1行ずつ説明つき）
# スキーマを書くための部品を読み込む。
from pydantic import BaseModel, Field

# 返してほしいデータの形を決める。ここでは2つの項目を持つ形。
class Joke(BaseModel):
    # 前振りの部分。description はLLMも読むので、何を入れるかを具体的に書く。
    setup: str = Field(description="ジョークのセットアップ")
    # 落ちの部分。この説明があるから、LLMはどちらにどの文を入れるか判断できる。
    punchline: str = Field(description="ジョークのオチ")
リク
リク各項目に説明を加えるのが大事だ。項目名と合わせて、LLMが「出力のどの部分をどの項目に入れるか」を判断する材料になる。このスキーマに従わせてみよう。
コードを見る（1行ずつ説明つき）
# チャットモデルの部品を読み込む。
from langchain_openai import ChatOpenAI

# モデルの呼び出し口を作る。ばらつきを0にすると、形から外れた答えが減る。
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# さきほど決めた形を必ず守らせる設定に変える。
# 形の指示をモデルに伝えるのと、返ってきた値の確認の両方をここが担当する。
model = model.with_structured_output(Joke)

# 質問する。答えは1本の文章ではなく、2つの項目に分かれて返る。
# もし形に合わない答えが返ったら、ここでエラーになるので気づける。
print(model.invoke("猫についてのジョークを教えてください"))
# --- 実行結果 ---
# {
#     setup: "なぜ野生の猫はポーカーをしないのですか？",
#     punchline: "イカサマ師（チーター）が多すぎるから。"
# }

🟣 ポイント3つ

  • ばらつきを小さく（temperature を低く）すると、形から外れた出力が減ります。
  • Pydanticで書いた形は、そのまま確認にも使われます。合わない出力が返れば、その場でエラーになります。
  • この作り方は、単独の機能としても、大きなアプリの一部（5章の振り分け）としても役に立ちます。

8.1.1 中間出力

要するに：処理が複雑になるほど時間がかかります。途中の結果を順に見せることで、待ち時間があっても利用者は待てるようになります。

リク
リク作りが複雑になるほど、実行に時間がかかる。処理がいくつも順番に、あるいは繰り返しでつながるからね。でも利用者は数秒以内の結果を期待している。対処が途中経過を順に返すことだ。LangGraphでは stream() で、処理が1つ終わるたびに結果を受け取れる。
コードを見る（1行ずつ説明つき）
#「これは利用者の発言」という札を付ける入れ物を読み込む。
from langchain_core.messages import HumanMessage

# 何段階か必要な質問を用意する。
user_input = {
    "messages": [HumanMessage("アメリカ合衆国の第30代大統領は、亡くなったとき何歳でしたか？")]
}

# updates を指定すると、処理が1つ終わるたびに「その処理が更新した分」だけが届く。
# 全部終わるのを待たないので、進み具合をそのまま画面に出せる。
for c in graph.stream(user_input, stream_mode='updates'):
    print(c)
# --- 実行結果 ---
# {'model': {'messages': AIMessage(content='', tool_calls=[...])}}
# {'tools': {'messages': [ToolMessage(content='Calvin Coolidge …')]}}
# {'model': {'messages': AIMessage(content='60歳でした。')}}
# ↑ 処理の名前がそのままキーになっているので、どこまで進んだかが分かる
受け取り方いつ届くか何が届くか
updates（既定）処理が1つ終わるたびその処理が更新した分だけ
values途中経過が変わるたびその時点のデータ全体
debug細かい出来事ごと詳しい内部の記録
checkpoint途中経過が保存されたとき保存された内容
task / task_result処理の開始時／終了時開始や終了の知らせ

これらは組み合わせて指定することもできます。

8.1.2 LLM出力をトークンごとにストリーミングする

要するに：処理単位ではなく、文字のかたまりが作られた瞬間に受け取ります。文字が流れて出てくる、あの見え方です。

コードを見る（1行ずつ説明つき）
# 何段階か必要な質問を用意する。
user_input = {
    "messages": [HumanMessage("アメリカ合衆国第30代大統領が亡くなったとき、何歳でしたか。")]
}

# 細かい出来事を1つずつ受け取る形で実行する。処理単位より細かい単位で届く。
output = app.astream_events(user_input, version="v2")

# 届いた出来事を1つずつ順に取り出す。
async for event in output:
    # 出来事にはいろいろな種類があるので、文字が作られたときのものだけを選ぶ。
    if event["event"] == "on_chat_model_stream":
        # その出来事に含まれている、今できたばかりの文字のかたまりを取り出す。
        content = event["data"]["chunk"].content
        # 中身が空のこともあるので、何か入っているときだけ画面に出す。
        if content:
            print(content)
# --- 実行結果 ---
# 第
# 30
# 代
# 大統領
# は
# …（できた順に少しずつ届く）

🔎 具体例：見え方がどれだけ変わるか

答えを書き終わるまでに合計12秒かかる質問があるとします。

ストリーミングなし：12秒間まっさらな画面。利用者は「壊れたのでは」と思い、多くは途中で離れます。

処理単位（updates）：3秒後に「検索しています」、7秒後に「結果を読んでいます」と表示。進んでいることが分かります。

文字単位：1.5秒後には最初の文字が出始め、そのまま流れるように続きます。合計時間は12秒のままですが、体感の待ち時間は大きく縮みます。

8.1.3 ヒューマンインザループ ― 人が介入する

要するに：自律性を上げるほど、人は制御を手放します。だからこそ「途中で人が入れる」仕組みが要ります。まず4章のチェックポインタを付けておくのが前提です。

リク
リク自律性を高めるほど、人は制御を手放してエージェントに任せることになる。LangGraphの「途中経過を共有する」作りは、動きを観察・中断・修正しやすくする。これで人が途中に入るやり方が使える。まずチェックポインタを付ける（4章でやったね）。

① 割り込み ― 人が好きなときに止める

リク
リクまず割り込み。最も単純で、利用者が出力を見ながら、適切だと思ったときに手で止める。止めた時点（最後に完了した段階）の状態が保存される。そこから——その時点から続ける、新しい入力を送ってやり直す、何もしない、が選べる。
コードを見る（1行ずつ説明つき）
# メッセージの入れ物と、待ち合わせに使う道具を読み込む。
from langchain_core.messages import HumanMessage
import asyncio

# 「止めてほしい」という合図を入れておくための旗を1つ用意する。最初は下りている。
event = asyncio.Event()

# 実行する質問を用意する。
user_input = {
    "messages": [HumanMessage("アメリカ合衆国第30代大統領が亡くなったとき、何歳でしたか。")]
}

# この実行を見分けるための名札を付ける。止めた状態はこの名札に紐づいて保存される。
config = {"configurable": {"thread_id": "1"}}

# 途中経過を受け取りながら実行する。aclosing は、途中で抜けても後始末を確実に行うためのもの。
async with aclosing(graph.astream(user_input, config)) as stream:
    # 届いた途中経過を1つずつ受け取る。
    async for chunk in stream:
        # 旗が上がっていたら、そこで受け取るのをやめる（＝止める）。
        if event.is_set():
            break
        else:
            # 旗が下りている間は、届いた内容を使って画面表示などを行う。
            ...

# アプリの別の場所（例：利用者が「停止」ボタンを押したとき）でこの旗を上げる。
# 上の繰り返しが次に一巡したときに、それを見て止まる。
event.set()

② 承認 ― 危ない処理の直前で自動的に止める

リク
リク2つ目は承認。特定の処理が呼ばれたら人に制御を渡す。多くはツールを実行する前の確認に使う。interrupt_before=['tools'] で、ツールの処理に入る直前まで実行して止まる。
コードを見る（1行ずつ説明つき）
# 実行する質問を用意する。
user_input = {
    "messages": [HumanMessage("アメリカ合衆国第30代大統領が亡くなったとき、何歳でしたか？")]
}

# この実行を見分けるための名札。止まった状態はここに保存される。
config = {"configurable": {"thread_id": "1"}}

# tools の処理に入る「直前」で自動的に止まるよう指定して実行する。
# 人が止めるのを待つのではなく、危ない操作の前で必ず止まるのが割り込みとの違い。
output = graph.astream(user_input, config, interrupt_before=['tools'])

# 止まるまでの途中経過を受け取り、画面に「この操作を実行してよいか」を表示するなどする。
async for c in output:
    ...

③〜⑥ 再開・再起動・編集・フォーク

▶️

再開

入力を None にしてもう一度呼びます。「さっきの続きをやって」という合図になります。

🔄

再起動

新しい入力と一緒に呼びます。今の状態を保ったまま新しい入力を足し、最初の処理からやり直します。状態を捨てたいときは名札（thread_id）を変えます。

🔎 具体例：割り込みと承認の使い分け

割り込みが向く場面：長い調査レポートを書かせている途中で、利用者が読んでいて「方向性が違う」と気づいたとき。人が判断して止めます。止めなければずっと続きます。

承認が向く場面：メールの送信、ファイルの削除、決済など、取り返しがつかない操作。人が気づくかどうかに頼らず、必ずその直前で止まります。

8.1.4 マルチタスクLLM（ダブルテキスト）

要するに：答えに時間がかかると、前の処理が終わる前に利用者が次の入力を送ってきます。これをどうさばくか、5つのやり方があります。

リク
リク最後に、複数の入力を同時に処理する問題だ。LLMが遅くて長い出力を作るときや、何段階も連なるときに特に重要になる。答えに時間がかかると、前の処理が終わる前に利用者が新しい入力を送ってくる——これがダブルテキストだ。扱い方は5つある。
やり方何をする長所短所
拒否する処理中に来た入力をすべて断るいちばん単純同時に来たときの面倒を、呼ぶ側に押し付けることになる
単独で扱う別の会話として新しい名札を作るいくらでも増やせる（複数の相手と同時に会話など）2つの別々のやり取りとして表示することになる
キューに入れる順番待ちに溜め、今の処理が終わってから順に処理何件でも受け付けられ、届いた順に関係なく結果が同じ列が際限なく伸びうる。処理される頃には内容が古くなる（前の答えに依存する入力には不向き）
割り込む今の処理をやめて、新しい入力でやり直すすぐ処理でき、古い出力を防げる一度に1件しか扱えない。どこまで残すかを前提にした設計が必要で壊れやすい
分けて、あとで合わせる並行して処理し、終わったら状態をまとめるすぐ処理でき、届いた時刻にも左右されず、何件でも並行できるぶつからずにまとめられる設計（CRDTなど）か、手作業での解決が必要

割り込むやり方には、どこまで残すかで選択肢があります——何も残さない／最後に完了した段階まで残す／進行中のものも残す／今の処理が終わるのを待つ。

🔎 具体例：同じ状況でも結果が変わる

利用者が「東京の明日の天気は？」と送り、答えを待っている3秒の間に「あ、大阪で」と送ったとします。

拒否：2件目は届かず、東京の天気だけが返ります。キュー：東京の天気が返ったあと、大阪の天気も返ります（2件とも返る）。割り込み：東京の処理は捨てられ、大阪の天気だけが返ります。この場合は割り込みが利用者の意図に最も近いですが、「東京の次に大阪も知りたかった」ならキューが正解です。どれが正しいかは用途で決まります。

リク
リクこれらの一部はLangGraph Platform（9章）で実装されている。待ち時間が短くなっても、同時に来た入力の扱いは課題であり続ける——どんなに手際のよい人でも時間は有限で、依頼に優先順位を付けなきゃいけないのと同じだ。

🟢 この項のまとめ

  • 自律性と信頼性の境界線を外側へ動かすのが目標。ほかに待ち時間・自律性・ばらつきの目標も互いに対立する。
  • 構造化出力：with_structured_output に形（Pydantic）を渡し、確認つきで結果を読める形にする。項目の説明が重要。
  • ストリーミング：stream（updates／valuesなど）で処理ごとの途中経過を見せる。astream_events で文字のかたまり単位も。
  • 人の介入：割り込み・承認（interrupt_before）・再開（None で続行）・再起動（新しい入力）・状態の編集・フォーク。組み合わせて使う。
  • ダブルテキスト：拒否・単独で扱う・キュー・割り込み・分けて合わせる。用途に応じて選ぶ。

章末の理解度チェック（全5問）

自分の言葉で答えてみましょう

スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問自律性と信頼性の境界線

❓ 「自律性と信頼性の境界線」とは何ですか。開発者は何を目指しますか。

✅ 解答例
自律性（人の手を借りずにどこまでできるか）と信頼性（出力をどこまで信用できるか）はつり合いの関係にあり、それを1本の線として表せる。線の上の各点が、両者のつり合いが違う最適な作り方（チェーンは信頼性が高め・自律性が低め、エージェントはその逆）。開発者が目指すのは、この線を外側に動かすこと——同じ信頼性のままより自律的に、または同じ自律性のままより信頼できるように。構造化出力・ストリーミング・人の介入などの技でそれを実現する。
📝 採点ポイント
□ 自律性と信頼性のつり合いを線で表す、に触れている
□ チェーンとエージェントでつり合いが違う、に触れている
□ 線を外側に動かすのが目標、に触れている
第2問構造化出力

❓ LLMに決まった形の出力をさせる方法を挙げ、with_structured_output が何をしてくれるか説明してください。

✅ 解答例
方法は3つ。指示文で頼む（希望の形で返すよう依頼するが保証はない）、ツール呼び出しを使う（出せる形の中から選ばせる）、JSONモード（必ずJSONの形にさせる）。with_structured_output は、これらをまとめた共通の呼び方で、形（PythonではPydantic、またはJSON Schema）を渡すと、決まった形の出力を得るための設定や変換の部品を足してくれる。さらに、Pydanticを渡せばそれを確認にも使い、LLMが形に合わない出力を出した場合はエラーを返す。
📝 採点ポイント
□ 指示文・ツール呼び出し・JSONモードの3方法に触れている
□ with_structured_output に形を渡す、に触れている
□ 確認（形に合わないとエラー）に触れている
第3問ストリーミングの意義

❓ 複雑なLLMアプリは待ち時間が長くなります。なぜ途中経過を見せることが使いやすさの維持に役立つのですか。

✅ 解答例
複雑な作りは複数の処理や繰り返しを通るため、最終の答えまでに時間がかかる。ほとんどの利用者は数秒以内の結果を期待するので、何も見せずに待たせると離れる原因になる。途中経過を見せると、動作中に各処理の結果や、文字が作られていく様子がリアルタイムで届く。待ち時間そのものは減らなくても、進んでいることが分かるので利用者は安心して待てる。LangGraphでは stream（処理単位）や astream_events（文字のかたまり単位）で実現する。
📝 採点ポイント
□ 複雑な作りは待ち時間が長い、に触れている
□ 進み具合／途中経過を見せると待てる、に触れている
□ 処理単位と文字のかたまり単位のストリーミングに触れている
第4問人の介入

❓ 人の介入の「割り込み」と「承認」の違いを説明してください。なぜ自律的な作りでこれが重要なのですか。

✅ 解答例
割り込みは、利用者が出力を見ながら、適切だと判断したときに手で止める方法。承認は、特定の処理（多くはツールの実行）が呼ばれる前に、あらかじめ自動で止まって利用者に確認を求める方法（interrupt_before）。自律的な作りでは、エージェントが人の手を借りずに動くため、危険な操作の前に人が止めたり承認したり取り消したりできる仕組みがないと、意図しない動きを防げない。だから人の介入は、自律的な作りの信頼性を高めるのに重要。
📝 採点ポイント
□ 割り込み＝利用者が手で止める、に触れている
□ 承認＝特定の処理の前に自動で止まって確認、に触れている
□ 自律的な作りの信頼性を高める、に触れている
第5問同時入力の扱い

❓ 「ダブルテキスト（同時入力）」の扱い方のうち「キューに入れる」と「割り込む」の違いを、それぞれの長所・短所を含めて説明してください。

✅ 解答例
キューに入れるは、処理中に来た入力を順番待ちに溜めて、今の処理が終わってから順に処理する。何件でも受け付けられ、届いた順に関係なく結果が同じだが、列が際限なく伸びうるし、処理される頃には内容が古くなっていることがある（前の答えに依存する入力には不向き）。割り込むは、新しい入力を受け取ると今の処理をやめて新しい入力でやり直す。すぐ処理できて待ち時間が改善し、古い出力を防げるが、一度に1件しか扱えず、どこまで残すかを前提にした設計が必要で、出力が届いたタイミングに左右される。
📝 採点ポイント
□ キュー＝溜めて順に処理、届いた順によらず同じ結果だが古くなる／伸びる、に触れている
□ 割り込む＝今の処理をやめて新しい入力でやり直す、すぐ処理できるが1件に限られる、に触れている
□ それぞれの長所・短所を対比している
