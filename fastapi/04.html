Starlette

FastAPI の土台になっている軽量な Web の部品。問い合わせの解析と返事の組み立てを担当します。

ASGI

Python のプログラムと Web サーバをつなぐ、非同期に対応した取り決め。返事待ちの間に別の処理を進められます。

WSGI

ASGI より前からある取り決め。1つの依頼を処理し終えてから次に進む方式です。

ブロッキング

ある処理が終わるまで、次に進めず止まっている状態のこと。

ビジーウェイト

返事が来るのを待つ間、処理装置が何の仕事もしていない状態。

並列 parallelism

複数の処理装置で、本当に同じ瞬間に複数の処理が動いていること。

並行 concurrency

1つの処理装置が複数の仕事を切り替えて進め、全体として同時に進んでいる状態を作ること。

プロセス process

OS が管理する、プログラムの実行のひとまとまり。それぞれが自分用のメモリを持ちます。

プリエンプティブ

OS が自分の判断で処理を一時停止したり再開したりして、資源を公平に分ける方式のこと。

multiprocessing

プロセスを複数立ち上げて、重い計算を分担させるための Python の標準機能です。

スレッド thread

1つのプロセスの中で並行して動く実行の単位。プロセスより軽い代わりに扱いが難しくなります。

スレッドプール

あらかじめ用意しておいたスレッドの集まり。仕事が来たら空いているものに割り当てます。

concurrent.futures

プロセスとスレッドの両方を、同じような書き方で使えるようにした Python の機能です。

グリーンスレッド

OS ではなく、プログラム自身の側で管理する軽い実行の単位。切り替えは自分から譲る形で行われます。

協調的 cooperative

切り替えのタイミングを、実行中の側が自分で譲ることで決める方式。OS が強制的に止めるのとは逆です。

モンキーパッチ

もとからある機能の中身を、動かしたまま別のものに差し替えること。

コールバック

「この出来事が起きたら、この処理を呼ぶ」とあらかじめ登録しておくやり方です。

ジェネレーター

yield を使い、途中で止まって次に呼ばれたら続きから動く処理。全部を一度に用意しなくて済みます。

yield

「ここで1つ値を返して、いったん止まる」という指示。次に呼ばれるとこの続きから動きます。

asyncio

Python の標準の非同期の仕組み。async と await を使って書きます。

async def

「この処理は途中で中断できる」と宣言する書き方です。

await

「ここで待つ。ただし待っている間は他の処理を進めてよい」という指示です。

イベントループ

「返事が届いたものはないか」を繰り返し確認し、届いたものから処理を再開する仕組みです。

I/Oバウンド

処理時間の大半が、通信やファイルの返事待ちで占められている処理のこと。

CPUバウンド

処理時間の大半が計算そのものに使われている処理のこと。待ち時間がありません。

ディスパッチ

来た仕事を、適切な処理の担当に振り分けることです。

並行処理の種類並列と並行の違い

要するに：「並列 = 複数の処理装置で本当に同時」、「並行 = 1つの処理装置で切り替えて同時に見せる」。Web は返事待ちが多いので、並行の効果が大きくなります。

タカ
タカ師匠非同期の中身に入る前に、「同時にたくさんやる」方法を一覧しておこう。並行と並列の違いはおさらいになるけど大事だ。
タカ
タカ師匠並列コンピューティングは、仕事を複数の専用の処理装置に同時に分散する。画像処理や機械学習の「大量に計算する」用途で多い。
タカ
タカ師匠並行コンピューティングは、1つの処理装置が複数の仕事を切り替えて実行する。仕事ごとに所要時間が違うので、全体の所要時間を縮めたい。ファイルやネットワークの読み書きは計算より千〜百万倍遅いから、待っている時間を別の仕事に充てたい。
ハル
ハルWeb アプリって、まさにその「遅い処理」を大量にやるんですよね。
タカ
タカ師匠その通り。どうやって Web サーバを速くするか、複数の選択肢を見ていこう。
🧮

並列

複数の処理装置に仕事を分けて、本当に同じ瞬間に動かします。計算量そのものを分担したいときに使います。

画像処理・機械学習
🔄

並行

1つの処理装置が、待ち時間の間に別の仕事を進めます。計算量は減りませんが、無駄な待ちが消えます。

Web サーバ

🔎 具体例：数字で見る待ち時間の大きさ

処理装置が1回の計算をするのにかかる時間を1ナノ秒（10億分の1秒）とすると、ネットワークの向こうから返事が返るまでは 50 ミリ秒ほどかかることがあります。これは 5000 万倍の差です。返事を待つ 50 ミリ秒の間、その処理装置は 5000 万回分の計算ができたはずの時間を何もせずに過ごしていることになります。この時間を別の依頼の処理に充てるのが並行のねらいです。

💡 なぜこれが必要か／これを知ったらできること

  • 並列と並行の区別が明確になる
  • Web の性能が頭打ちになる原因（返事待ち）が分かる

✅ この項のまとめ

  • 並列: 複数の処理装置で同時に
  • 並行: 1つの処理装置で切り替えて
  • Web は返事待ちが多いので並行が効く

オペレーティングシステムプロセス重い計算は複数プロセスで

要するに：プロセスは OS が管理する実行の単位です。計算中心の並列処理には複数プロセス（multiprocessing）が定石です。

タカ
タカ師匠OS はメモリ、処理装置、機器、ネットワークなどの資源を割り振っている。OS が動かすプログラムはすべて、1つまたは複数のプロセスでコードを実行する。
タカ
タカ師匠OS は各プロセスに、処理装置を使えるタイミングなど、資源への管理された安全な使用権を渡す。
ハル
ハル「プリエンプティブ」って何ですか？
タカ
タカ師匠プリエンプティブなプロセスの割り当ては、どのプロセスにも処理装置やメモリを独占させない方式。OS が常にプロセスを一時停止したり再開したりして、資源を公平に分ける。
タカ
タカ師匠開発者にとっては「考えなくてよい」のがありがたいところ。ありがたくないのは、「変えたくても、あまり変えられない」こと。
タカ
タカ師匠計算の負荷が高い Python のアプリでは、複数プロセスで OS に管理させるのが普通の解決策。Python の標準の機能に multiprocessing がある。

🔎 具体例：計算中心の処理を分担させる

100万件のデータをそれぞれ複雑な式で計算する処理があり、1件あたり 0.01 秒かかるとします。1つのプロセスで順に処理すると約 2.8 時間です。この処理には返事待ちが一切ないので、非同期にしても短くなりません。処理装置が8個あるパソコンで multiprocessing を使い8つのプロセスに分けると、実際に8か所で同時に計算が進むので、約 21 分に短縮できます。

💡 なぜこれが必要か／これを知ったらできること

  • 「重い計算は multiprocessing で別プロセスにする」という定石を知れる
  • OS が割り振りを行っていることを意識できる

✅ この項のまとめ

  • プロセス = OS が管理する実行の単位
  • プリエンプティブ = OS が自動で一時停止・再開する
  • 重い計算は multiprocessing で分散

オペレーティングシステム・スレッドFastAPI が内部で使うもの

要するに：スレッドは返事待ちの多い処理に有効です。ただし扱いは難しく、FastAPI はスレッドプールを内部に持って、同期の処理を自動で振り分けてくれます。

タカ
タカ師匠1つのプロセスの中で、複数のスレッドを走らせることもできる。Python の標準の機能に threading がある。
タカ
タカ師匠一般的な指針として、返事待ち中心ならスレッド、計算中心なら複数プロセスが推奨されることが多い。
ハル
ハルスレッドのほうが軽そうですね。
タカ
タカ師匠確かに軽いけど、書くのが厄介で、見つけにくい不具合を引き起こす。複数のスレッドが同じデータを同時に書き換えると、結果が実行のたびに変わることがあって、原因の特定が難しい。
タカ
タカ師匠昔は Python のプロセス用の機能とスレッド用の機能が別々で、開発者はどちらかの難解な詳細を学ばないといけなかった。concurrent.futures という新しめのパッケージが、両方を同じような書き方で使いやすくしている。
タカ
タカ師匠あとで分かるけど、新しい非同期の書き方を使えばスレッドの利点をもっと簡単に得られる。FastAPI はスレッドプールを通じて、通常の同期の処理（async def ではなく def）も自動的にスレッドで動かしてくれる。
処理の種類向いている手段理由
返事待ち中心（I/Oバウンド）スレッド／非同期待ち時間に別の仕事を進められる
計算中心（CPUバウンド）複数プロセス待ち時間がないので、処理装置の数を増やすしかない

💡 なぜこれが必要か／これを知ったらできること

  • 「FastAPI で def のままでも非同期のサーバが回る」理由が分かる
  • 返事待ちと計算の使い分けの基本がつかめる

✅ この項のまとめ

  • スレッド = 1つのプロセス内の並行実行の単位
  • 返事待ち向け（計算中心は複数プロセス）
  • 不具合が見つけにくい性質がある
  • concurrent.futures で扱いやすい書き方ができる
  • FastAPI は内部のスレッドプールで同期の処理をさばく

タカ

コールバック出来事に処理を結びつける

要するに：コールバックは、出来事が起きたときに処理を呼ぶ方式で並行を実現します。書きやすさでは async/await に劣ることが多いです。

タカ
タカ師匠ゲームや画面操作のような対話型のアプリの開発者は、コールバックをよく知っているはず。「マウスのクリック、キー入力、時間切れなどの出来事に、対応する処理を結びつける」やり方。
タカ
タカ師匠Python では Twisted が代表的なコールバック用のフレームワーク。この方式のコードは、処理の順番が上から下に読めなくなるので追いにくい。

🔎 具体例：読む順番が入れ替わる

「データを取ってきて、加工して、保存する」という3段階をコールバックで書くと、「取ってくる処理に、加工する処理を渡し、その加工する処理の中に保存する処理を渡す」という入れ子になります。実際に動く順番は内側から外側なのに、コードの見た目は外側から内側です。段階が5つ、6つと増えるほど、どこで何が起きるのかを追うのが難しくなります。async/await はこれを、上から下に読める形に戻すために作られました。

💡 なぜこれが必要か／これを知ったらできること

  • コールバックが深く入れ子になる問題の意味が分かる
  • async/await が解こうとしている読みにくさの問題が見える

✅ この項のまとめ

  • コールバック = 出来事が起きたときに処理を呼ぶ方式
  • 代表: Twisted
  • コードが追いにくくなる傾向

Pythonジェネレーター中断と再開ができる処理

要するに：ジェネレーターは yield で途中停止・再開できる処理です。メモリの使用が少なく、async/await の考え方の土台にもなっています。

タカ
タカ師匠普通の Python の処理は、頭から最後まで（あるいは return まで）一気に実行する。
タカ
タカ師匠でも ジェネレーターは、途中で止まって、戻って、また続きから実行できる。鍵は yield というキーワードだ。

まず、3つのセリフを全部まとめて返す普通の書き方です。

コードを見る（1行ずつ説明つき）
# doh という処理を作る。呼ばれると中身を最後まで一気に実行する。
def doh():
    # 3つの文字列を並べた一覧を作り、それをまとめて返す。
    # この時点で3つ全部がメモリの上に用意される。
    return [
        "Oh!",
        "A deer!",
        "A female deer!",
    ]

# 返ってきた一覧を先頭から1つずつ取り出し、line という名前で扱う。
for line in doh():
    # 取り出した1つを画面に出す。これを要素の数だけ繰り返す。
    print(line)
# --- 実行結果 ---
# Oh!
# A deer!
# A female deer!
タカ
タカ師匠一覧が小さい時はこれで問題ない。でも何十万行ものセリフを全部一覧にするとなると、メモリを使い切ってしまう。
タカ
タカ師匠そこでジェネレーターだ。

同じ3つのセリフを、1つずつ渡しては止まる書き方にしたものです。使う側の書き方は変わりません。

コードを見る（1行ずつ説明つき）
# doh2 という処理を作る。yield を含むので、呼んでもすぐには中身が動かない。
def doh2():
    # yield は「1つ渡して、ここで止まる」という指示。次に呼ばれるとこの次の行から動く。
    yield "Oh!"
    # 2回目に呼ばれたとき、この行から動いて2つめを渡し、また止まる。
    yield "A deer!"
    # 3回目に呼ばれたとき、3つめを渡す。以降は渡すものがないので繰り返しが終わる。
    yield "A female deer!"

# 使う側の書き方は上の例とまったく同じ。違うのは、必要になった瞬間に1つずつ作られること。
for line in doh2():
    # 受け取った1つを画面に出す。
    print(line)
# --- 実行結果 ---
# Oh!
# A deer!
# A female deer!
# 表示は同じだが、3つ全部を同時にメモリに置いてはいない。
タカ
タカ師匠繰り返しのコードは同じに見えるけど、doh2() はジェネレーターのオブジェクトを返す。Python は最初の文字列を渡したあと、次の回のために止まった位置を記憶しておく。セリフを使い切るまでこれを繰り返す。
タカ
タカ師匠yield を含む処理はすべてジェネレーターだ。途中で止まって再開できる、というこの仕組みは、次の async/await の自然な前段なんだ。

🔎 具体例：巨大なログファイルを読む

10GB のログファイルから、エラーを含む行だけを数えたいとします。全部を一覧としてメモリに読み込むと、10GB 分の空きが必要になり、多くのパソコンでは止まってしまいます。

ジェネレーターで1行ずつ渡す形にすれば、同時にメモリに置かれるのは1行分だけです。10GB のファイルでも、数百バイト程度のメモリで最後まで処理できます。

💡 なぜこれが必要か／これを知ったらできること

  • メモリを節約しながら大量のデータを処理できる
  • async/await の「中断と再開」の考え方をつかめる

✅ この項のまとめ

  • 通常の処理: 最後まで一気に実行
  • ジェネレーター: yield で中断・再開できる
  • 大量データや少しずつ届くデータに適する

Pythonのasync、await、asyncio3秒の待ちが消える

要するに：async def で定義した処理は await で呼びます。asyncio で並行に走らせます。FastAPI はこの仕組みの上に立っています。

タカ
タカ師匠Python の asyncio の機能は複数のバージョンをかけて導入された。少なくとも Python 3.7 を使っていれば、async と await が予約された言葉になっている。

同期版と非同期版の比較

まず同期版。質問を表示し、3秒止まってから答えを表示します。

コードを見る（1行ずつ説明つき）
# 時間に関する標準の機能を取り込む。
import time

# 質問を表示する処理。
def q():
    # 質問の文章を画面に出す。
    print("ねえ、なんで Web エンジニアは劇場が好きなの？")
    # 3秒間まるごと止まる。この間、このプログラムは他に何もできない。
    time.sleep(3)

# 答えを表示する処理。
def a():
    # 答えの文章を画面に出す。
    print("だってサーバとレスポンスのキャッチボールが見られるから！")

# q を呼ぶ。中の3秒の停止が終わるまで、次の行には進まない。
q()
# q が完全に終わってから、ようやく a が呼ばれる。
a()
# --- 実行結果 ---
# ねえ、なんで Web エンジニアは劇場が好きなの？
# （3秒の沈黙）
# だってサーバとレスポンスのキャッチボールが見られるから！
タカ
タカ師匠質問と答えの間に3秒の空白。間がもたないよね。

次に非同期版。同じ3秒の待ちがありますが、待っている間に答えの表示が進みます。

コードを見る（1行ずつ説明つき）
# 非同期の仕組みを使うための標準の機能を取り込む。
import asyncio

# async を付けると「この処理は途中で中断できる」という宣言になる。
async def q():
    # 質問の文章を画面に出す。
    print("ねえ、なんで Web エンジニアは劇場が好きなの？")
    # await は「ここで3秒待つが、待っている間は他の処理を進めてよい」という指示。
    await asyncio.sleep(3)

# こちらも中断できる処理として宣言する。
async def a():
    # 答えの文章を画面に出す。待ちがないのですぐ終わる。
    print("だってサーバとレスポンスのキャッチボールが見られるから！")

# 全体をまとめて動かすための処理。
async def main():
    # gather は「これらを同時に始めて、全部終わるまで待つ」という指示。
    # q が3秒の待ちに入った瞬間、a の実行に切り替わる。
    await asyncio.gather(q(), a())

# run は、非同期の処理を動かすための入口。ここから全体が始まる。
asyncio.run(main())
# --- 実行結果 ---
# ねえ、なんで Web エンジニアは劇場が好きなの？
# だってサーバとレスポンスのキャッチボールが見られるから！
# （3秒の沈黙）
# 待ちの3秒が最後に回り、質問と答えが続けて表示される。
タカ
タカ師匠質問の直後に答えが飛んでくる。テンポが良くなっただろう？
タカ
タカ師匠補足。asyncio.gather() と asyncio.run() を使ったけど、非同期の処理の呼び方は他にもある。FastAPI を使う場合は、これらを自分で呼ぶ必要はない。

非同期版を動かしたときの Python の動き

2

q() は中断できる処理。「3秒後に戻ってくる」と登録して、いったん手を離す。

3

待ちがないので、すぐに答えを表示して終わる。

4

残っているのは q() の3秒の待ちだけ。

他にやることがないので、この時間は本当に待つしかない。

6

q() の続きが再開し、全体が終わる。

タカ
タカ師匠この例では asyncio.sleep() を「ファイルの読み取りや Web への問い合わせなど、時間のかかる処理」の代わりに使っている。await は、時間のかかる処理の前に置く。さらに、その処理の定義は def の前に async を付ける必要がある。

感染するルール

タカ
タカ師匠重要なルール：ある処理を async def で定義したら、呼ぶ側はその呼び出しの前に await を付けないといけない。そして呼ぶ側自身も async def で宣言する必要があり、さらにそれを呼ぶ側も…と続く。
ハル
ハル連鎖するんですね。
タカ
タカ師匠ちなみに、別の非同期の処理への await の呼び出しを含んでいなくても、処理を async として宣言することはできる。エラーにはならない。

🔗 連鎖の形

FastAPIと非同期def でも async def でもよい理由

要するに：FastAPI のパス関数は async def でも def でも書けます。前者はイベントループ、後者はスレッドプールに、FastAPI が自動で振り分けます。

タカ
タカ師匠長い回り道が終わって、ようやく FastAPI に戻る。
タカ
タカ師匠Web サーバは多くの「待ち時間」を使っている。だから待ち時間を避けられれば性能が上がる。他の Web サーバはスレッドや gevent で対処している。FastAPI が Python の Web フレームワークの中で最速級なのは、土台の Starlette が ASGI に対応し、いくつか独自の工夫を加えているから。
タカ
タカ師匠注意点。async と await だけでコードが速くなるわけじゃない。むしろ非同期の準備の分だけ少し遅くなることもある。async の主な用途は 返事待ちの長い時間を避けることだ。
ハル
ハル何でもかんでも async にすればいい、というわけじゃないんですね。
タカ
タカ師匠その通り。

返事の前に1秒待つ窓口を、非同期で書いた例です。

コードを見る（1行ずつ説明つき）
# 非同期の仕組みを使うための標準の機能を取り込む。
import asyncio
# 枠組み本体を取り出す。
from fastapi import FastAPI

# アプリ全体を作る。
app = FastAPI()

# /hi への GET をこの下の処理に結びつける。
@app.get("/hi")
# async を付けているので、この処理は途中で中断できる。
async def greet():
    # 1秒待つ。待っている間、サーバは他の問い合わせを処理できる。
    await asyncio.sleep(1)
    # 待ち終わってから、この文字を返す。
    return "Hello? World?"
# --- 問い合わせた結果（1秒後） ---
# "Hello? World?"

タカ
タカ師匠このコードは挨拶を返す前に1秒休む。同期版（time.sleep(1)）との唯一の違いは、非同期版では待ち時間の間にサーバが他の問い合わせを処理できること。

タカ師匠asyncio.sleep(1) は、データベースへのアクセスや Web ページの取得のような「1秒かかる本物の処理」の代わりだ。後の章で、Web層 → サービス層 → データ層の呼び出しを実際にやって、待ち時間を実際の作業に充てる例を見るよ。
タカ

内部の二段構え

タカ
タカ師匠内部の話。FastAPI は非同期のパス関数のためのイベントループと、同期のパス関数のためのスレッドプールを並行して走らせている。開発者が細かい仕組みを知らなくていいのが、本当に大きな利点だ。asyncio.gather() や asyncio.run() を自分で呼ばなくて済む。
🔄

async def のパス関数

イベントループに乗ります。await のところで他の依頼に切り替わります。

非同期のライブラリを使うとき
🧵

def のパス関数

スレッドプールに振り分けられます。1つが止まっても、他のスレッドが別の依頼を処理します。

同期のライブラリしかないとき

🔎 具体例：async def の中で同期の待ちを書いてしまうと

async def のパス関数の中で、うっかり time.sleep(1)（同期の待ち）を書いたとします。これはイベントループそのものを1秒間止めてしまうため、その1秒の間、他のすべての依頼も止まります。100人が同時にアクセスしていれば、100人全員が待たされます。

同じ場所で await asyncio.sleep(1)（非同期の待ち）と書けば、その1秒の間に他の依頼が処理されます。逆に、同期の待ちしか使えないライブラリなら、パス関数を def（async なし）で書けば、スレッドプールに回されるので他の依頼は止まりません。

  • 「def と async def、どちらで書くべきか」を、返事待ちの有無で判断できる
  • FastAPI 内部の二段構え（イベントループ + スレッドプール）が見える

✅ この項のまとめ

  • async def のパス関数 → イベントループ
  • def のパス関数 → スレッドプール
  • FastAPI が自動で振り分ける
  • 返事待ちの有無を意識して使い分ける

間奏曲：待ち時間のある段取り原文「手がかりの家を掃除する」

📌 この節の扱いについて

原文はこの節で、古い屋敷の清掃作業を題材に非同期の考え方を説明しています。この図解ではたとえ話としてではなく、実際に「乾燥待ち」という待ち時間がある作業を、どう並べれば早く終わるかという段取りそのものの問題として扱います。プログラムの待ち時間と同じ性質の問題が、実際の作業計画でも起きる、という話です。

要するに：待ち時間を別の作業に充てるかどうかで、全体の所要時間が変わります。「待ちがあるところに、詰め込む余地がある」というのがこの節の中身です。

タカ
タカ師匠清掃の仕事を考えよう。作業を最短で終わらせたい。理想は人手を増やすことだけど、作業するのは君ひとりだ。
タカ
タカ師匠やり方の選択肢は2つ。①ある部屋ですべてを済ませてから次の部屋へ、②部屋をまたいで同じ作業をまとめてやる。
タカ
タカ師匠合計時間に差はあるか？ あるかもしれない。けど、もっと重要なのは「どの作業に長い待ち時間が含まれているか」だ。例えば床。ワックスを塗ったあと、家具を戻す前に何時間も乾燥を待つ必要がある。

1部屋あたりの作業手順

1

細かいほこりを取り除く

静電気で付いている部分を先に処理する。

2

家具を全部ホールに移動

床全体を作業できる状態にする。

3

床の汚れを落としてワックスを塗る

ここまでは手を動かし続ける作業。

4

選択：乾燥を待つ間どうするか

(A) その場で乾くのを待つ。手は空いているが何もしない。
(B) 次の部屋の作業を始める。最後の部屋まで終えたら、乾いた順に家具を戻す。
ハル
ハル(A) が同期、(B) が非同期…！
タカ
タカ師匠その通り。乾燥を待つのが同期のやり方で、時間に余裕があって休憩を取りたいときには向く。もう一方は非同期で、各部屋の待ち時間を別の部屋の作業に充てる。

🔎 具体例：数字で見る差

部屋が4つ、1部屋あたり「手を動かす作業 30分」＋「乾燥待ち 2時間」だとします。

(A) その場で待つ場合：（30分 + 2時間）× 4部屋 = 10時間。このうち8時間は何もしていません。

(B) 待ちの間に次へ進む場合：4部屋分の作業 30分 × 4 = 2時間を先に済ませ、最後の部屋の乾燥 2時間を待って終了。合計 約4時間。手を動かす時間は同じ2時間ですが、待ちが重なった分だけ短くなります。

これは Web サーバでも同じです。1件の外部問い合わせに 0.5 秒かかるとき、100件を順に処理すれば 50秒、待ちの間に次を送れば 1秒程度で済みます。

タカ
タカ師匠この話の教訓は3つ。①要件は矛盾していたり、想定外だったりする、②時間と労力の見積もりは多くの要因に左右される、③作業の順番の決め方は、決まった正解がある話ではなく、状況を見て判断するものだ。

💡 なぜこれが必要か／これを知ったらできること

  • 非同期の本質を、コードを離れた段取りの問題として理解できる
  • 「待ちがあるところに、詰め込む余地がある」と覚えられる

✅ この項のまとめ

  • 同期: 待ちをそのまま受け入れる分かりやすい順番
  • 非同期: 待ち時間を別の作業に充てる進め方
  • 順番の設計は、決まった正解のある話ではない

章末の理解度チェック全5問

第1問Starlette と FastAPI

Starlette と FastAPI の関係を、初めて聞く人に説明してください。「ASGI」というキーワードを使ってください。

✅ 解答例
Starlette は Tom Christie が作った軽量な ASGI（非同期の Python Web 標準）フレームワーク。FastAPI はその Starlette を土台にして、型ヒントによる自動の確認、Pydantic のモデル、自動ドキュメント生成などを上乗せした「使いやすさを足したフレームワーク」。FastAPI が速い理由のひとつは、土台の Starlette が ASGI に対応していて非同期に強いから。
📝 採点ポイント
□ Starlette が ASGI 基盤であることを述べている
□ FastAPI が Starlette を土台に使っていることに触れている
□ FastAPI が Starlette に加えた価値（型ヒント、Pydantic、自動ドキュメント）に言及
第2問並行と並列の違い

「並行（concurrency）」と「並列（parallelism）」の違いを、自分の言葉で説明してください。Web サーバの性能向上にどちらが効果的ですか？

✅ 解答例
並列は本当に複数の処理装置で同じ瞬間に処理を走らせること。並行は1つの処理装置で複数の仕事を切り替えながら進めて、「同時に進んでいるように見せる」こと。Web サーバは返事待ち（データベース、ネットワーク、ファイル）が大半で、処理装置が暇な時間が多いので、待ち時間を埋める「並行」が効果的。
📝 採点ポイント
□ 並列＝複数の処理装置、並行＝1つで切り替え、という区別をしている
□ Web は返事待ちが中心だという認識を述べている
□ 並行が Web に効果的という結論
第3問ジェネレーターと async/await

Python のジェネレーターと async/await はどのように関連していますか？「中断と再開」というキーワードを使って説明してください。

✅ 解答例
通常の処理は最初から最後まで一気に実行するが、ジェネレーターは yield で途中で中断・再開できる。yield で止まった位置を Python が記憶しておき、次に呼ばれたときに続きから走る。async/await も同じ発想で、await で処理が中断して別の処理に切り替わり、待っていた結果が来たら再開する。ジェネレーターの中断・再開の仕組みが、async/await の土台になっている。
📝 採点ポイント
□ ジェネレーターの「中断・再開」を説明している
□ async/await も同じ発想であると述べている
□ yield と await の役割の似ている点に触れている
第4問FastAPI における def と async def

FastAPI でパス関数を書くとき、def と async def のどちらを使うべきですか？ それぞれ FastAPI 内部でどう扱われますか？

✅ 解答例
返事待ち（データベースや外部の窓口へのアクセス）があるパス関数は async def で書いて非同期のライブラリを使うと、待ち時間に別の依頼を処理できて効率が良い。逆に返事待ちがない、もしくは同期のライブラリしか使えない場合は def で良い。FastAPI は内部で、async def のパス関数を非同期のイベントループで動かし、def のパス関数をスレッドプールに振り分けるので、どちらでも適切に並行処理される。
📝 採点ポイント
□ async def は返事待ちがあるときに効果的、と述べている
□ def でも問題なく動く、と説明している
□ FastAPI 内部の「イベントループ + スレッドプール」の二段構えに触れている
第5問async の連鎖する性質

async def で処理を定義したときに、その呼び出し側に発生する制約を説明してください。「連鎖する」というニュアンスも含めてどうぞ。

✅ 解答例
async def で定義された処理を呼ぶ側は、その呼び出しの前に await を付ける必要がある。そして await を使うには、呼ぶ側自身も async def で宣言されていないといけない。さらにその呼ぶ側を呼ぶコードも…と連鎖していくので、「async は感染する」と言われる。FastAPI の中では FastAPI 自身がパス関数を呼ぶので、利用者が await を書く必要はないが、別の async def を自分で呼ぶときは await が必要。
📝 採点ポイント
□ await が必要になる、と述べている
□ 呼ぶ側自身も async def でなければならない連鎖に触れている
□ FastAPI の中では利用者が await を書かなくていい点に触れている

asyncio.gather() の例を自分で書く

複数の待ちを同時に始めると、全体がどれだけ短くなるか確かめる。

コードを見る（1行ずつ説明つき）
# 非同期の仕組みと、時間を測るための機能を取り込む。
import asyncio, time

# 指定された秒数だけ待って、終わったことを知らせる処理。
async def wait(n):
    # n 秒待つ。待っている間、他の処理を進めてよい。
    await asyncio.sleep(n)
    # 何秒待ったかを返す。
    return n

async def main():
    # 開始時刻を記録する。
    start = time.time()
    # 1秒、2秒、3秒の待ちを同時に始める。順に足すと6秒だが…
    await asyncio.gather(wait(1), wait(2), wait(3))
    # 実際にかかった時間を計算して表示する。
    print(round(time.time() - start, 1))

# 全体を動かす。
asyncio.run(main())
# --- 実行結果 ---
# 3.0
# 6秒ではなく、いちばん長い3秒で終わる。待ちが重なったため。
