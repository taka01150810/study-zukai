トランザクション

データベースの種類ごとに少しずつ違う、SQL の書き方の差のことです。

正規形

データの重複を減らすための、表の作り方の決まり。1つのマスに1つの値、などです。

重複を減らす形に整えることと、あえて重複を持たせて取り出しを速くすることです。

SQLAlchemy3つの段階

要するに：SQLAlchemy は「コア」「式言語」「ORM」の3段階です。素の SQL で足りるうちはそれで、複雑になったら上の段階へ移ります。

タカ
タカ師匠Python の SQL 用のパッケージで最も広く使われている。「SQLAlchemy といえば ORM」と説明されることが多いけど、実際は複数の段階からできている。

コア

タカ
タカ師匠SQLAlchemy の土台は コアだ。中身は、①共通の呼び出し方を実装した接続の管理役、②種類と接続部品と対象を表す住所、③つながりを何本か用意しておく仕組み、④ひとまとまりの操作を確定・取り消しする仕組み、⑤種類ごとの書き方の差の吸収、⑥素の SQL による問い合わせ、⑦次に説明する組み立てによる問い合わせ。
タカ
タカ師匠書き方の差を吸収してくれるおかげで、SQLAlchemy はいろいろな種類のデータベースを扱える。
タカ
タカ師匠私自身は素の接続部品を使ってきたし、これからも使うけど、大規模なサイトや、特定の種類の機能を活かしたいなら、SQLAlchemy を使う価値がある。

SQLAlchemy 式言語

タカ
タカ師匠これは ORM ではない。表に対する問い合わせを、別のやり方で表すものだ。保存の構造を Python の型（表・列）に対応づけ、操作を Python の処理（選ぶ・入れる）に対応づける。これらは最終的に素の SQL の文字列に変換され、何が起きたかを確認できる。データベースの種類に依存しない。

まず、これまで書いてきた素の SQL の書き方です（第10章の再掲）。

コードを見る（1行ずつ説明つき）
# 名前を指定して1件を取得する処理。
def get_one(name: str) -> Explorer:
    # SQL の文を、文字列としてそのまま書いている。
    qry = "select * from explorer where name=:name"
    # 目印に入れる値を用意する。
    params = {"name": name}
    # 実行する。
    curs.execute(qry, params)
    # 1件を取り出して、扱いやすい形に変換して返す。
    return row_to_model(curs.fetchone())

同じことを、Python のコードで組み立てる書き方です。

コードを見る（1行ずつ説明つき）
# 必要な部品をまとめて取り込む。
from sqlalchemy import create_engine, MetaData, Table, Column, String, select

# 接続の管理役を作る。文字列の中に、種類と場所が含まれている。
# sqlite:/// のあとがファイル名。種類を変えるときは、ここを書き換えるだけでよい。
engine = create_engine("sqlite:///cryptid.db")
# 表の定義をまとめて持っておく入れ物を作る。
metadata = MetaData()

# 表の形を Python のコードで定義する。SQL の create table にあたる。
explorer_table = Table(
    "explorer", metadata,
    # 名前の列。文字を入れ、1件を特定する項目にする。
    Column("name", String, primary_key=True),
    # 国コードの列。
    Column("country", String),
    # 説明の列。
    Column("description", String),
)

# 定義した表を、実際のデータベースに作る。すでにあれば何もしない。
metadata.create_all(engine)

# 名前を指定して1件を取得する処理。
def get_one(name: str) -> Explorer:
    # SQL の文字列を書く代わりに、Python の処理を組み合わせて問い合わせを作る。
    # .c は「その表の列」を指す書き方。== で条件を表す。
    stmt = select(explorer_table).where(explorer_table.c.name == name)
    # with を使うと、この範囲を抜けるときに、つながりが自動で閉じられる。
    with engine.connect() as conn:
        # 組み立てた問い合わせを実行し、1件を取り出す。
        row = conn.execute(stmt).fetchone()
    # 扱いやすい形に変換して返す。
    return row_to_model(row)
# --- この書き方の利点 ---
# 列の名前を間違えると、実行前に気づける（文字列ではなく名前として書くため）。
# データベースの種類が変わっても、この書き方は変えなくてよい。
タカ
タカ師匠SQL が難しいと感じるなら試す価値がある。公式より読みやすい解説もある。

ORM

タカ
タカ師匠ORM は、表や SQL の考え方ではなく、その分野のデータの形で問い合わせを表す。式言語よりずっと複雑だ。完全に対象を中心に据えた書き方を好む開発者は、たいてい ORM を選ぶ。
タカ
タカ師匠FastAPI 関連の多くの本は、データベースの説明ですぐ ORM に飛びつく。気持ちは分かるけど、問題が2つある。別の考え方を新しく学ぶ必要があること、そして SQLAlchemy は優れたパッケージだが、包み隠した部分が常に隠れたままとは限らないことだ。
タカ
タカ師匠いちばん単純な進め方は「まず SQL だけを使い、手に負えなくなったら式言語や ORM に移る」だと私は思う。

SQL の文字列を自分で書く。何が起きるか完全に見えます。

まずここから

Python の処理を組み合わせて問い合わせを作る。種類に依存しません。

SQL が複雑になったら
→

ORM

データの形そのもので操作する。対象を中心に据えた書き方です。

全体を対象中心にしたいなら
↺ 上の段階ほど書く量は減りますが、覚えることが増え、内部で何が起きているかが見えにくくなります。

🔎 具体例：「包み隠した部分が隠れたままとは限らない」とは

ORM を使うと、user.orders と書くだけで注文の一覧が取れます。便利ですが、これが利用者100人分のループの中にあると、内部では101回の問い合わせが発行されます（1回で利用者を取り、100回それぞれの注文を取る）。1回で済むはずが101回になり、極端に遅くなります。

この問題に気づいて直すには、結局「内部でどんな SQL が出ているか」を理解する必要があります。SQL を隠したはずが、性能の問題を通じて表に出てくる、というのがここで言われている点です。

✅ この項のまとめ

  • SQLAlchemy = コア + 式言語 + ORM の階層

  • 式言語: Python のコードで組み立てる問い合わせ
  • ORM: データの形そのものでの問い合わせ

EdgeDBSQL の書きにくさを避ける試み

要するに：SQL には、問い合わせを組み合わせにくいという弱点があります。EdgeDB はそれを避ける新しい言語を提案しています。

タカ
タカ師匠SQL は成功したけど、問い合わせを書きにくくする設計上の弱点がある。SQL の土台にある数学の考え方と違って、SQL という言語自体は組み合わせにくい。大きな問い合わせの中に問い合わせを入れ子にするのが難しく、複雑で長いコードになる。
タカ
タカ師匠EdgeDB は Python の非同期の仕組みの作者によって、Python で書かれたデータベースだ。「SQL の次」あるいは「つながりを扱う表形式」と説明される。内部では PostgreSQL を使っている。
タカ
タカ師匠これが提供するのは EdgeQL だ。SQL の書きにくい部分を避けた新しい問い合わせの言語で、実際には PostgreSQL が実行する SQL に翻訳される。
タカ
タカ師匠これが EdgeDB を越えて広まるか、SQL の代わりになるかは、時間が経てば分かる。

🔎 具体例：「組み合わせにくい」とはどういうことか

「各国の探検家のうち、その国でいちばん説明が長い1人」を取りたいとします。SQL では、まず国ごとの最大の長さを求める問い合わせを書き、それを別の問い合わせの中に埋め込み、さらに元の表と結合する、という書き方になります。3つの部分が入れ子と結合で絡み合い、1つのまとまりとして読みにくくなります。

「小さな問い合わせを部品として作り、それを組み合わせて大きな問い合わせにする」ということが、SQL では素直にできません。これが弱点として指摘されている点です。

✅ この項のまとめ

  • SQL の弱点: 組み合わせにくい
  • EdgeDB = SQL の次を目指す。内部は PostgreSQL
  • EdgeQL = SQL の代わりを目指す問い合わせの言語

要するに：大量のデータを Faker で作って、書き込みと読み取りの時間を測ります。そこから、まとめて入れる窓口や、ページ分割の必要性が見えてきます。

タカ
タカ師匠本書のデータの例はごくわずかだ。データベースを本当に試すには、数百万件が欲しい。手で足すより、Faker のような Python のパッケージを使うほうが楽だ。名前・場所など、いろいろな種類のデータを素早く作れる。

10万件を作り、書き込みと読み取りの時間を測る確認用のコードです。

コードを見る（1行ずつ説明つき）
# 環境変数の設定と、時間の測定に使う標準の機能を取り込む。
import os
import time
# それらしい仮のデータを作る道具を取り込む。
from faker import Faker
# すでにある場合の知らせを取り込む。
from errors import Duplicate

# 取り込みより前に、確認専用のファイルを保存先に指定する。本物を汚さないため。
os.environ["CRYPTID_SQLITE_DB"] = "cryptid_load.db"

# ここから下で、データの形と各層を取り込む。
from model.explorer import Explorer
from data import explorer as data
from service import explorer as service
import requests

# 作る件数。アンダースコアは桁の読みやすさのためのもので、値には影響しない。
NUM = 100_000

# データを大量に作って保存する処理。
def load():
    # 仮のデータを作る道具を用意する。
    fake = Faker()
    # 開始の時刻を記録する。monotonic は、途中で時計が変わっても影響を受けない測り方。
    start = time.monotonic()
    # 実際に保存できた件数を数えるための変数。
    count = 0
    # 指定した回数だけ繰り返す。_ は「値を使わない」という意味の名前。
    for _ in range(NUM):
        # それらしい名前を作る。
        name = fake.name()
        # それらしい国コードを作る。
        country = fake.country_code()
        # それらしい1文を作る。
        description = fake.sentence()
        try:
            # 作ったデータを保存する。
            data.create(Explorer(name=name, country=country, description=description))
            count += 1
        # 同じ名前がすでにある場合は、何もせず次に進む。
        # Faker は限られた候補から名前を作るので、繰り返すと重複が出る。
        except Duplicate:
            pass
    # 終了の時刻を記録する。
    end = time.monotonic()
    # 実際に保存できた件数を表示する。
    print(f"{count} rows")
    # かかった時間を表示する。
    print(f"write time: {end - start}")

# データ層から直接、全件を読む時間を測る。
def read_db():
    start = time.monotonic()
    # 結果は使わないので _ に捨てている。時間だけを測りたいため。
    _ = data.get_all()
    end = time.monotonic()
    print(f"db read time: {end - start}")

# 窓口を経由して全件を読む時間を測る。
def read_api():
    start = time.monotonic()
    # 実際に通信して取得する。
    r = requests.get("http://localhost:8000/explorer")
    # 受け取った内容を Python の値に直すところまで含めて測る。
    _ = r.json()
    end = time.monotonic()
    print(f"api read time: {end - start}")

# 直接動かされたときだけ、下を実行する。
if __name__ == "__main__":
    load()
    read_db()
    # 2回呼ぶのは、1回目に含まれる準備の時間を除くため。
    # これで、窓口経由との比較が公平になる。
    read_db()
    read_api()
タカ
タカ師匠ポイントは2つ。①すでにある場合の知らせを受け止めて無視している。Faker は限られた候補から名前を作るので、繰り返すと重複が出る。結果として10万件に届かないこともある。②読み取りを2回呼んでいる。1回目に含まれる立ち上がりの時間を除いて、窓口経由との比較を公平にするためだ。

第1問SQLAlchemy の3段階

SQLAlchemy の3つの段階（コア／式言語／ORM）について、それぞれ何を扱うか説明してください。どう使い分けますか？

✅ 解答例
コア：共通の呼び出し方を実装した接続の管理役、つながりの使い回し、ひとまとまりの操作の確定と取り消し、種類ごとの書き方の差の吸収、素の SQL の実行を担ういちばん下の段階。素の SQL を書くならここ。式言語：SQL を Python のコード（表・列・選ぶ処理など）で組み立てる中間の段階。ORM ではなく、表を直接扱うが、Python らしく書ける。ORM：その分野のデータの形で問い合わせを表すいちばん上の段階。型と対象でデータベースを操作する。使い分けは、単純なアプリなら素の SQL とコアで十分。SQL が複雑になったら式言語、全体を対象中心にしたければ ORM。
📝 採点ポイント
□ 3つの段階すべてに触れている
□ それぞれの抽象の度合いの違いを説明している
□ 使い分けの指針を述べている
第2問SQLModel

SQLModel とは何ですか？ SQLAlchemy の ORM と Pydantic それぞれとの関係を含めて説明してください。

✅ 解答例
SQLModel は FastAPI の作者が作った Python のライブラリで、SQLAlchemy の ORM と、Pydantic のデータの定義・確認を組み合わせたもの。1つの定義で「データベースの表の形」と「FastAPI の受け渡しの形」の両方として使える。SQLAlchemy だけだと別に Pydantic の定義も書く必要があるが、SQLModel ならそれが不要。FastAPI との組み合わせを優先する場合の選択肢。
📝 採点ポイント
□ SQLAlchemy の ORM と Pydantic の組み合わせ、と述べている
□ 1つの定義で両方を兼ねられる、という利点に触れている
□ FastAPI の作者による、という背景に触れている
第3問SQL と NoSQL の選択

表形式のデータベースと、そうでないもののどちらを選ぶか、どんな観点で判断しますか？「今の SQL は JSON も扱える」という事実を踏まえて答えてください。

✅ 解答例
データが長方形の表に収まる規則的なものなら、表形式のもの（PostgreSQL、SQLite）が向く。理由は、そろった強力な機能（他の表との結びつき、追加の索引、結合）、ひとまとまりの操作の保証、内容の一貫性。データが「でこぼこ」で形が定まらないなら、表形式でないもの（MongoDB、Redis、Elasticsearch）。ただし今の表形式のものは JSON の列に対応していて、表の中に半分だけ構造化されたデータを持てる。「どちらか」の二択ではなく、「ほぼ規則的だが一部が柔軟」なら JSON に対応した表形式、「ほとんど柔軟」なら表形式でないもの、と段階的に判断するのが今どき。
📝 採点ポイント
□ 両方の強みに触れている
□ JSON に対応した表形式のものの存在に言及している
□ 二択ではなく段階的な選択、という考え方に触れている
第4問Faker で確認用のデータを作る

開発中にデータベースの性能を確かめる際、なぜ Faker のようなライブラリが便利ですか？ どんなことに使いますか？

✅ 解答例
実際の運用ではデータベースに数万〜数百万件が入るが、開発の初期は手で数件入れる程度。それでは、詰まりの原因（問い合わせの遅さ、索引の不足、ページ分割の必要性など）が見えない。Faker は名前・住所・国コード・電話番号・文章など、それらしい仮のデータを素早く大量に作れる Python のライブラリ。これで確認用のデータベースに10万件入れて、全件取得の時間、書き込みの速さ、窓口経由の応答時間を測り、本番に出す前に詰まりを見つけられる。
📝 採点ポイント
□ 実際の運用とのデータ量の差に触れている
□ Faker がそれらしいデータを作ることに触れている
□ 詰まりの発見・性能の確認という用途に触れている
第5問FastAPI と AI のモデル

FastAPI と Hugging Face の transformers を組み合わせて、AI の機能を持つ窓口を作る基本的な手順を説明してください。注意点（言葉の混同、幻覚など）も含めてどうぞ。

✅ 解答例
①pip install torch torchvision transformers で用意する。②FastAPI のアプリの中で pipeline() を使って学習済みのモデルを読み込む（例：小さなもの）。③窓口（例：/ai）で、住所のうしろの条件として入力を受け取り、モデルに渡した結果を返す。注意点：AI の「モデル」と Pydantic の「モデル」は別のものなので混同しない。小さなモデルは品質が低く、もっともらしいが事実と異なる答えを返す幻覚が起きる。大きなものは品質が高いが、自分の機械で動かすには多くの計算の資源が必要。
📝 採点ポイント
□ 用意する手順とパッケージに触れている
□ pipeline() でモデルを読み込む方法を述べている
□ AI の「モデル」と Pydantic の「モデル」の違いに触れている
□ 幻覚に言及している
