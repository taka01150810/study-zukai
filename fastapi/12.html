単体テスト

1つの処理だけを取り出して、期待どおりに動くかを確かめることです。

統合テスト

層と層のつなぎ目が、正しくやり取りできているかを確かめることです。

フルテスト

外からの問い合わせからデータベースまで、全部を通して確かめることです。

テストピラミッド

単体を多く、統合を中くらい、全体を少なく、という数の配分を表した考え方です。

リグレッション

直したはずの場所や、動いていた場所が、別の変更で壊れてしまうことです。

pytest

Python でテストを書いて動かすための、いちばん広く使われている道具です。

assert

「ここはこうなっているはず」と書く行。違えばその場でテストが失敗します。

fixture

テストで使う準備（データや接続）を用意して、必要なテストに渡す pytest の仕組みです。

スコープ

その準備を、どの範囲で1回作るか。テストごと、ファイルごと、全体で1回などがあります。

パラメータ化

1つのテストに、いくつもの入力を順に与えて確かめる書き方です。

分離 isolation

確かめたい処理だけを動かし、その先の処理は動かさないようにすることです。

モック mock

実行中に、ある処理を別のものに一時的に差し替える方法です。

ダブル／フェイク

本物の代わりに用意した、確認用の別の実装のことです。

構造テスト

中の作り（どの処理を呼んでいるか）を知ったうえで確かめるやり方です。

振る舞いテスト

中の作りを知らずに、入力と出力だけで確かめるやり方です。

ファーストクラスオブジェクト

処理そのものを、値と同じように渡したり入れ替えたりできる性質のことです。

コンテキストマネージャ

with と一緒に書き、その範囲の中だけ何かを有効にする書き方です。

プロパティベーステスト

入力を人が考えるのではなく、条件から自動で大量に作って試すやり方です。

OpenAPIスキーマ

API の仕様を決まった形式で書き表したもの。FastAPI が自動で作ります。

Hypothesis

入力を自動で作り出す、プロパティベーステストの土台になるパッケージです。

Schemathesis

OpenAPI の仕様を読んで、API に対するテストを自動で作って実行する道具です。

TestClient

実際の通信を行わずに、プログラムの中から窓口を直接呼べる FastAPI の仕組みです。

負荷テスト

大量の問い合わせが来たときに、どこまで耐えられるかを確かめることです。

Locust

負荷の確認を Python のコードで書ける、定番の道具です。

リポジトリ・パターン

データの出し入れの方法を1か所にまとめ、保存先を差し替えやすくする設計です。

Unit of Work

ひとまとまりの操作を、全部成功か全部取り消しかのどちらかにする仕組みです。

この章のあらすじ確認する人は何を試すか

タカ師匠は古い冗談でハルを笑わせます。「確認担当の技術者がバーに入った。ビールを1本注文した。0本注文した。99999999本注文した。トカゲを注文した。-1本注文した。意味のない文字列を注文した。そこへ最初の本物の客が入ってきて、トイレはどこかと尋ねた。バーは炎上した」。ハルは大笑い。本章では、pytest による単体・統合・全体の確認、差し替えの2つのやり方、仕様から自動でテストを作る方法、負荷の確認まで、全体像を学びます。

🔎 この冗談が言っていること

確認担当の人は「想定内の入力」だけでなく、0、極端に大きい数、種類の違うもの、負の数、意味のない文字列といった想定外の入力を試します。それらはすべて通ります。しかし、実際の利用者が持ち込んだのは「トイレはどこか」という、そもそも想定されていなかった問いでした。

つまり、入力の値をいくら網羅しても、「そういう使われ方をするとは考えていなかった」という抜けは残る、という話です。この章で学ぶのは、少なくとも値の網羅は自動化できる、という部分です。

どこでテストするかテストピラミッド

要するに：確認は 単体（多）→ 統合（中）→ 全体（少）の配分で組むのが基本です。

タカ
タカ師匠確認は3種類に分けられる。単体：層の中の、個々の処理。統合：層をまたいだつながり。全体：API 全体と、その下の全部。
タカ
タカ師匠これをテストピラミッドと呼ぶ。幅は、それぞれに含めるべき数の相対的な多さを示す。底（単体）がいちばん多く、頂点（全体）がいちばん少ない。
フルテスト数件。全部を通して確かめる。遅く、手間がかかる。
統合テスト中くらいの数。層と層のつなぎ目を確かめる。
単体テスト大量。1つの処理を確かめる。速く、失敗の場所がすぐ分かる。

🔎 具体例：逆の配分だとどうなるか

全体を通す確認ばかり100件書いたとします。1件あたり2秒かかるなら、全部で200秒。しかも、どこか1か所が壊れると、その場所を通るすべてが赤くなります。100件が同時に失敗し、原因の場所を探すことになります。

単体の確認が多ければ、1件あたり0.01秒で終わり、失敗するのは壊れた処理に対応する1〜2件だけです。どこが原因かが、失敗した名前を見ただけで分かります。

✅ この項のまとめ

  • 単体: 処理1つの確認。いちばん多く書く
  • 統合: 層と層のつながり。中くらいの数
  • 全体: すべてを通した確認。少なめ

何をテストすべきか入力の種類とエラーの場所

要するに：入力の種類（欠け／重複／種類違い／巨大 など）を網羅します。どの層でエラーが起きるかも意識します。

タカ
タカ師匠入力に対して正しい出力が出るかを確かめる。次のような入力を試すといい。①項目が欠けている、②重複している、③種類が違う、④並び順が違う、⑤正しくない値、⑥非常に大きい入力や出力。
タカ
タカ師匠問題はどこでも起きうる。①Web層：Pydantic が形の違いを見つけて 422 を返す。②データ層：データベースが、欠け・重複・SQL の誤りで失敗を出す。巨大な結果を一度に渡すと、時間切れやメモリ不足になる。③どの層でも：ふつうの書き間違い。
🕳️

欠けている

必要な項目が入っていない。

👯

重複している

すでにあるものと同じ。

🔤

種類が違う

数のはずが文字になっている。

🔀

並び順が違う

想定と違う順で届く。

🚫

正しくない値

範囲の外、あり得ない値。

🐘

非常に大きい

時間切れやメモリ不足の原因になる。

✅ この項のまとめ

  • 入力の型: 欠け／重複／種類違い／巨大／正しくない値
  • Web層: 形が合わなければ 422
  • データ層: データベースからの失敗、メモリ不足

レイアウトテストをどこに置くか

モック実行中に処理を差し替える

要するに：モックは処理を実行中に差し替えます。書き方は4通りあります。中の作りを知って行うため、構造の確認寄りです。

タカ
タカ師匠本書の構成では、住所 → Web層の処理 → サービス層 → データ層 → データベース、と呼び出しがつながる。
タカ
タカ師匠単体の確認は単純に聞こえるけど、ほとんどの処理は他の処理を呼ぶので、その先をどう抑えるかが問題になる。
タカ
タカ師匠Python では処理そのものを値のように扱えるので、ある処理を別の処理で置き換えられる。unittest には差し替えのための機能がある。
タカ
タカ師匠差し替えは切り離しの手段として人気だけど、「結果よりもコードの中の作りについての知識を必要としすぎる」という批判もある。構造の確認（中が見える、差し替え）と 振る舞いの確認（中を知らない、別の実装）の違いだ。

まず、呼ばれる側の小さなファイルです。

コードを見る（1行ずつ説明つき）
# 決まった前置きの文章を返すだけの処理。
def preamble() -> str:
    return "The answer to your question is: "

それを呼ぶ側のファイルです。前置きに、足し算の結果をつなげて返します。

コードを見る（1行ずつ説明つき）
# 前置きを返すファイルを取り込む。
import mod1

# 2つの数を受け取り、前置きの文章と足し算の結果をつなげて返す。
def summer(a: int, b: int) -> str:
    # str() は数を文字に変換する。文字と文字は + でつなげられる。
    return mod1.preamble() + str(a + b)

まずは差し替えなしで、そのまま確かめてみます。

コードを見る（1行ずつ説明つき）
# 確かめたいファイルを取り込む。
import mod2

def test_summer():
    # 5 と 6 を渡して呼ぶ。中で前置きと 11 がつながる。
    result = mod2.summer(5, 6)
    # 前置きも含めた文字列全体が一致することを確かめる。
    assert result == "The answer to your question is: 11"
コードを見る（1行ずつ説明つき）
# -q は表示を最小限にする指定。
$ pytest -q test_summer1.py
# --- 実行結果 ---
# .                                                          [100%]
# 1 passed in 0.04s
# ドット1つが、通ったテスト1件を表す。
タカ
タカ師匠でも、前置きの文章は付け足しであって、「足し算が正しいか」だけを確かめたいとしたら？ 前置きを差し替えて無くしてしまう。

差し替えの書き方を4通り並べたものです。どれも結果は同じです。

コードを見る（1行ずつ説明つき）
# 差し替えのための機能を取り込む。
from unittest import mock
# 確かめたいファイルを取り込む。
import mod2

# 書き方1：with の範囲の中だけ差し替える。
def test_caller_a():
    # 文字列で「どの処理を差し替えるか」を指定し、返す値を空にする。
    with mock.patch("mod1.preamble", return_value=""):
        # この中では、前置きが空になる。
        result = mod2.summer(5, 6)
        # 足し算の結果だけが返ることを確かめる。
        assert result == "11"

# 書き方2：差し替えたものに名前を付け、返す値を後から設定する。
def test_caller_b():
    with mock.patch("mod1.preamble") as mock_preamble:
        # 名前を通して、返す値を空に設定する。
        mock_preamble.return_value = ""
        result = mod2.summer(5, 6)
        assert result == "11"

# 書き方3：処理の上に飾りとして書く。差し替えたものは引数として渡ってくる。
@mock.patch("mod1.preamble", return_value="")
def test_caller_c(mock_preamble):
    # この処理の間ずっと差し替えが効いている。with で囲む必要がない。
    result = mod2.summer(5, 6)
    assert result == "11"

# 書き方4：書き方2とほぼ同じ。返す値を別の呼び出しで設定している。
def test_caller_d():
    with mock.patch("mod1.preamble") as mock_preamble:
        mock_preamble.return_value = ""
        result = mod2.summer(5, 6)
        assert result == "11"
# --- 実行結果 ---
# ....                                                       [100%]
# 4 passed in 0.13s
タカ
タカ師匠4通りを解説する。①書き方1：with の範囲の中だけ差し替える。指定するのは "mod1.preamble"（完全な名前の文字列）と、返す値。②書き方2：as で差し替えたものに名前を付けて使う。③書き方3：処理の上に飾りとして書く。差し替えたものは引数として渡る。④書き方4：ほぼ2と同じで、返す値を別の行で設定している。
タカ
タカ師匠重要な点。差し替える対象の文字列の名前は、確かめたいコード（ここでは summer()）の中で呼ばれている書き方と一致していないといけない。差し替えの仕組みは、その名前をたどって、元のものへの参照を断ち切るからだ。
タカ
タカ師匠結果として、4つの確認すべてで summer(5, 6) を呼んだとき、本物ではなく差し替えたものが呼ばれる。差し替えたものは空の文字を返すので、summer() は足し算の結果だけを返す。
タカ
タカ師匠差し替えは複雑だ。詳しくは Python の公式の説明を参照してくれ。

🔎 具体例：名前の指定を間違えるとどうなるか

mod2.py が from mod1 import preamble と書いていた場合、mod2 の中には preamble という名前が直接できています。このとき mock.patch("mod1.preamble") と書いても、mod2 が持っている名前は差し替わりません。本物が呼ばれ、テストは前置き付きの文字列を受け取って失敗します。

この場合は mock.patch("mod2.preamble") と、呼ばれる側から見た名前を指定します。これが「中の作りを知る必要がある」と言われる理由です。

✅ この項のまとめ

  • mock.patch() で処理を差し替える
  • 4つの書き方（with ／ as ／ 飾り ／ 別の行で設定）
  • 差し替えの対象は「呼ばれる側から見た名前」で指定
  • 構造の確認 = 中の作りの知識が要る

リポジトリ・パターン本書では未実装だが知っておく

要するに：データの出し入れをまとめる設計と、ひとまとまりの操作を全部成功か全部取り消しにする仕組みです。本書では実装しませんが、選択肢として知っておく価値があります。

タカ
タカ師匠本書では実装しないけど、興味深いリポジトリ・パターンがある。単純な中間のデータの置き場で、これまでの仮のデータ層に似ている。実際のデータベース向けに、差し替え可能な保存先とやり取りする。
タカ
タカ師匠関連して Unit of Work という考え方もある。ひとまとまりの操作が、全体として確定されるか、全部取り消されるかのどちらかになることを保証する。これまで本書の問い合わせは1回で完結していたけど、実際のデータベースでは、複数の段階を踏む処理が必要になる。
タカ
タカ師匠リポジトリ・パターンは依存性注入とも関係が深い。

🔎 具体例：全部成功か全部取り消しが必要な場面

「口座Aから1万円引いて、口座Bに1万円足す」という処理を考えます。1つ目が成功し、2つ目の直前でサーバが落ちたとすると、1万円がどこにも存在しない状態になります。

ひとまとまりとして扱えば、2つ目が失敗した時点で1つ目も取り消され、元の状態に戻ります。「途中まで進んだ状態」が残らないことが保証されます。

✅ この項のまとめ

  • リポジトリ = データの置き場をまとめる設計
  • Unit of Work = ひとまとまりの操作の全部成功か全部取り消し
  • 依存性注入と相性が良い

第1問テストピラミッド

「テストピラミッド」とは何ですか？ なぜピラミッドの形になるのか、3層それぞれの役割と数の配分を説明してください。

✅ 解答例
確認の種類と数の理想的な配分を示した図。底に「単体の確認」（いちばん多い）、中央に「統合の確認」（中くらい）、頂点に「全体の確認」（いちばん少ない）を置く形。単体は速くて手間が少なく、処理1つを切り離して確かめるので大量に書ける。全体の確認は遅く手間がかかり、すべての層を通るので少数に絞る。この形は、手間と確かめられる範囲の釣り合いを表している。
📝 採点ポイント
□ 単体／統合／全体 の3層を挙げている
□ それぞれの数の配分（多→中→少）を述べている
□ 手間と確かめられる範囲の釣り合いに触れている
第2問モックとフェイクの違い

確かめたい対象を切り離すための「差し替え」と「別の実装」はどう違いますか？ それぞれの長所と短所を述べてください。

✅ 解答例
差し替えは mock.patch() で実行中に処理を入れ替える方法。長所は確認する側だけで完結し、確かめたいコードを変えなくてよい点。短所は「確かめたい対象がどの処理を呼んでいるか」という中の作りの知識が必要なこと（構造の確認寄り）。別の実装は、確認用のファイルを用意して取り込みの切り替えで入れ替える方法。長所は確かめたい対象がそれを意識しないので振る舞いの確認に近く、本書の fake/ のように使い回しやすい。短所は環境変数や切り替えの記述を、確かめたい側に組み込む必要があること。
📝 採点ポイント
□ 差し替えの仕組みと長所・短所を述べている
□ 別の実装の仕組みと長所・短所を述べている
□ 構造の確認 と 振る舞いの確認 の観点に触れている
第3問準備の仕組みの役割

pytest の準備の仕組み（fixture）とは何ですか？ 範囲（スコープ）による動きの違いも含めて説明してください。

✅ 解答例
確認する処理に、共通の用意（データ、データベースの初期化など）を提供する仕組み。@pytest.fixture という印を付けて定義し、確認する処理の引数として名前を書くと、pytest が自動で呼び出して値を渡してくれる。範囲は function（初期値。各処理の前に新しく実行）、class（まとまりごと）、module（ファイルごと）、session（全体で1回）の4種類。重い用意（データベースへの接続など）は全体で1回、軽い見本のデータは毎回新しく、というのが一般的。
📝 採点ポイント
□ 共通の用意を提供することを述べている
□ 印を付けて定義し、引数で受け取る動きを説明している
□ 範囲（テストごと／全体で1回 など）の使い分けに触れている
第4問単体テストでの切り離し方

本書では Web層・サービス層・データ層 の単体の確認で、それぞれどう「切り離し」を実現していますか？

✅ 解答例
Web層：環境変数 CRYPTID_UNIT_TEST を設定して、サービス層の代わりに fake/ のまとまりを取り込む。サービス層 → データ層 → データベース の呼び出しをすべて仮のものに置き換える。サービス層：同じ環境変数で、データ層の代わりに仮のものを取り込む。データ層：別の環境変数 CRYPTID_SQLITE_DB=":memory:" で、SQLite をファイルではなくメモリ上で動かす。本物の SQL を動かしながら、ファイルを汚さない。
📝 採点ポイント
□ Web層とサービス層の、仮のものへの切り替えに触れている
□ 環境変数 CRYPTID_UNIT_TEST の役割を述べている
□ データ層がメモリ上のデータベースで確認することに触れている
第5問Schemathesis の価値

Schemathesis は何をしてくれる道具ですか？ 自分で書くテストと比べて、何が嬉しいですか？

✅ 解答例
FastAPI が自動で作る OpenAPI の仕様（/openapi.json）を読み込み、各窓口に対して「型と条件にもとづくさまざまな入力」を自動で作って確かめる。自動生成のテストと呼ばれるやり方。自分で書く場合は「壊れそうな入力」を人が考えて書く必要があったが、これは自動でやってくれる。結果として、窓口の数が増えても、確認を用意する手間が増えない。型ヒントが仕様を経由してテストの生成にまで効いてくるのは、FastAPI の作りの思わぬ恩恵。
📝 採点ポイント
□ 仕様から自動でテストを作る仕組みに触れている
□ 自動生成のテストという考え方を述べている
□ 自分で書く場合との手間の比較に触れている
