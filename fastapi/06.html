依存関係 dependency

ある処理を実行するために、その時点で必要になる情報のこと。「誰がアクセスしているか」「データベースの中身」などです。

依存性注入 DI

必要な情報を処理の中で自分で取りに行かず、外から渡してもらう作り方のことです。

依存関数

必要な情報を用意して返す、補助の処理。窓口の処理とは別に書きます。

Depends()

「この処理を、定義したときではなく、問い合わせが来るたびに呼んでほしい」と FastAPI に伝えるための書き方です。

Callable 呼び出せるもの

かっこを付けて実行できるもの。関数やクラスがこれにあたります。

スコープ 適用範囲

その依存関係を、どこまでの範囲に効かせるか。1つの窓口だけか、まとまり単位か、アプリ全体かです。

ルーター APIRouter

関連する窓口をまとめて扱うための入れ物。まとめ単位で共通の設定をかけられます。

prefix 接頭辞

そのまとまりの中の窓口すべてに、先頭に付ける住所の共通部分です。

副作用 side effect

値を返すのではなく、確認して止めたり、記録を残したりといった動作そのものが目的の処理です。

HTTPException

「この番号のエラーで返してほしい」と FastAPI に伝えるための失敗の知らせです。

認証 authentication

「あなたは誰か」を確かめること。名前とパスワードの照合などがこれにあたります。

認可 authorization

「その人に、この操作をする権限があるか」を確かめることです。

モック mock

テストのときに、本物の代わりに使う「決まった値を返すだけの偽物」のことです。

ページネーション

件数の多い一覧を、何ページかに分けて少しずつ返すことです。

メトリック

処理の件数や所要時間など、動作の状況を数値で記録したものです。

OpenAPI

API の仕様を決まった形式で書き表す取り決め。FastAPI はコードからこれを自動で作ります。

dependency_overrides

テストのとき、依存関数を別のものに差し替えるための FastAPI の仕組みです。

ハルは「Header() とか Body() って、なんで引数の初期値の位置に書くの？ 普通の Python と違うけど…」と疑問を持ちます。タカ師匠は「これが FastAPI の真骨頂、依存性注入だよ」と説明を始めます。窓口が必要とする情報を、外部の処理（依存関数）に任せて、FastAPI が自動的に呼び出して結果を渡してくれる仕組みです。テストもしやすく、コードの重複も減り、説明ページにも反映されます。

依存とは何か？「その時点で必要な情報」のこと

要するに：パス関数が「実行のために必要とする情報」を依存関係と呼びます。

タカ
タカ師匠まず「依存関係」という言葉の意味から。依存関係とは、ある時点で必要となる特定の情報のこと。普通は、必要になったときにそれを取りに行くコードを書く。
タカ
タカ師匠Web サービスを書いていると、こんな情報を必要とする。①問い合わせから入力の値を集める、②入力が正しいか確かめる、③窓口を使う人が誰か、権限があるかを確かめる、④データの置き場（多くはデータベース）からデータを取ってくる、⑤動作の記録や状況の数値を出す。
タカ
タカ師匠Web フレームワークは、届いたデータをプログラムで扱える形に変換し、Web の層の処理の中で必要なものを取り出してくれる。

依存関係になりうるものの典型

📥

入力の収集

問い合わせの中から必要な値を取り出す。

✅

入力の確認

取り出した値が条件を満たしているか確かめる。

🔐

認証・認可

誰なのか、権限があるかを確かめる。

🗄️

データの取得

データベースなどから必要な情報を取ってくる。

📊

記録・状況の数値

いつ、誰が、どの窓口を使ったかを残す。

📄

ページ分割の計算

何件目から何件分を返すかを決める。

💡 なぜこれが必要か／これを知ったらできること

  • 「依存関係」という言葉が、抽象的ではなく具体的に見えるようになる
  • どんな処理が依存関係になりうるか、典型例を持てる

✅ この項のまとめ

  • 依存関係 = ある時点で必要な情報
  • 典型: 入力の収集／確認／認証／データ取得／記録／状況の数値

依存関係の問題中で取りに行くと何が困るか

要するに：必要な情報を処理の中で直接取りに行くと、テストできない、見えない依存で壊れる、コードが重複する、説明ページに載らない、という4つの問題が起きます。

タカ
タカ師匠必要なときに必要なものを、外部から見えない形で取ってくる。一見合理的に見えるけど、いくつか問題が起きる。
タカ
タカ師匠①テスト：必要な情報を差し替えられないと、処理の色々な場合を試せない。②見えない依存：詳細を隠しているせいで、外部のコードが変わったとき処理が壊れる。③コードの重複：必要な情報がよくあるもの（利用者の検索、問い合わせからの値の取り出し）だと、複数の処理に同じコードが散らばる。④説明ページへの反映：FastAPI の自動の説明ページは、この仕組みからの情報を必要とする。
ハル
ハル全部「後で直すのがしんどくなる」系の問題ですね。
タカ
タカ師匠その通り。依存性注入はこれらを一気に解決する。
🧪

問題1：テストできない

中で本物のデータベースを呼んでいると、テストのたびにデータベースが必要になります。

👻

問題2：見えない依存

外から見ると何が必要なのか分からないので、外部が変わったとき壊れます。

📑

問題3：コードの重複

同じ「利用者を取ってくる」処理が、10か所にそのまま書かれます。

📘

問題4：説明に載らない

自動生成の説明ページに、その窓口が何を必要とするかが出ません。

🔎 具体例：テストのときに何が起きるか

窓口の処理の中で db.get_user(name) を直接呼んでいるとします。テストを動かすには本物のデータベースを起動し、テスト用の利用者を登録しておく必要があります。「該当する利用者がいない場合」を試したければ、データを消して実行し、また戻す作業が要ります。

この処理を外から渡す形にしておけば、テストでは「常に None を返すだけの偽物」を渡せば済みます。データベースを起動する必要すらありません。

💡 なぜこれが必要か／これを知ったらできること

  • 「この仕組みが無いと何が困るか」が腹に落ちる
  • 依存性注入を導入する動機が持てる

✅ この項のまとめ

  • 問題1: テストが書きにくい
  • 問題2: 見えない依存で壊れやすい
  • 問題3: コードの重複
  • 問題4: 自動の説明ページに反映されない

依存性の注入外から渡す、それだけ

要するに：依存性注入とは、処理が必要とする情報を、処理の中で取りに行くのではなく、外から渡すことです。

タカ
タカ師匠依存性注入という言葉は、響きほど難しくない。処理が必要とする情報を、処理の外から渡すということだ。
タカ
タカ師匠昔からのやり方は、補助の処理を引数として渡し、必要なデータを取得させる、というもの。
🔒

中で取りに行く

処理の中に db.get_user() を直接書きます。外からは何が必要か分からず、差し替えもできません。

従来の書き方
🔓

外から渡す

必要な情報を引数で受け取ります。外から見て必要なものが分かり、差し替えもできます。

依存性注入

  • 依存性注入 = 必要な情報を外から処理に渡す

FastAPI の依存関係Header() の正体

要するに：FastAPI では「引数として宣言すれば、FastAPI が依存関数を呼んで結果を渡してくれる」。Path, Query, Body, Header はすべて、この仕組みの組み込み版です。

タカ
タカ師匠FastAPI はもう一歩進めている。必要な情報を引数として定義すると、FastAPI が自動で呼び出し、戻り値をその引数に渡す。
タカ
タカ師匠例：user_dep という依存関数が、問い合わせの中から名前とパスワードを取って、データベースで照合して、追跡用の文字列を返す。窓口の処理はこの user_dep を「直接呼ぶ」ことはなく、引数として宣言するだけ。FastAPI が呼び出しのときに処理する。
ハル
ハルあ、これ第3章の Header(), Body() と同じ感触ですね。
タカ
タカ師匠その通り！ Path, Query, Body, Header は、データの出どころを表す組み込みの依存関係だ。FastAPI が用意してくれている。これらは処理やクラスで、問い合わせのいろいろな部分から必要なデータを取り出してくれる。
タカ
タカ師匠自分で書くこともできる？ できる。でも自作だと、こういう機能は得られない。①データが正しいかの確認、②形式の変換、③自動の説明ページへの反映。
タカ
タカ師匠第7章で Flask や Django との比較で具体的な違いを見るよ。けれど FastAPI なら、自作の依存関数も組み込みと同じように扱われる。

依存関係を書くDepends() が必要な理由

要するに：依存関数を作り、パス関数の引数に Depends(依存関数) と書きます。Depends() が無いと、定義した時点で1回だけ呼ばれてしまいます。

タカ
タカ師匠FastAPI の依存関係は「実行されるもの」だから、かっこを付けて呼べるものでなければならない。処理（関数）とクラス、つまり ( と ) で呼べるものだ。

名前とパスワードを受け取って確認する、依存関数の例です。

コードを見る（1行ずつ説明つき）
# 枠組み本体、依存関係を宣言する道具、条件を取り出す道具を取り出す。
from fastapi import FastAPI, Depends, Query

# アプリ全体を作る。
app = FastAPI()

# 依存関数。上にパスデコレータが無いので、これ自体は窓口ではない。
# name と password を、住所のうしろの条件から受け取る。... は「必須」の意味。
# 返すのは正しいかどうかの真偽の値、という書き添え。
def user_dep(name: str = Query(...), password: str = Query(...)) -> bool:
    # 本来はここでデータベースと照合するが、この例では常に「正しい」を返す。
    return True

# /user への GET をこの下の処理に結びつける。
@app.get("/user")
# user という引数の値は、上の user_dep から得る、と宣言している。
# Depends で包むことで「今すぐではなく、問い合わせのたびに呼んで」と伝わる。
def get_user(user: bool = Depends(user_dep)) -> dict:
    # 受け取った結果を、項目名を付けて返す。
    return {"valid": user}
# --- /user?name=ハル&password=xxx に問い合わせた結果 ---
# {"valid": true}
# name か password を省くと、パス関数は動かず 422 のエラーが返る。
タカ
タカ師匠user_dep() は依存関数だ。FastAPI のパス関数のように Query などの組み込みの依存関係を知っているけど、上にパスデコレータが無い。これは補助であって、窓口の本体ではない。
タカ
タカ師匠パス関数 get_user() は、引数 user を期待していて、その値は依存関数 user_dep() から得る、と宣言している。
タカ
タカ師匠重要な注意。user_dep は Python の関数そのものだから、引数で user = user_dep とは書けない。user = user_dep() でもダメだ。それだと get_user() が定義されたときに user_dep() を呼んでしまう。使われるときに呼びたいんだ。
タカ
タカ師匠だから FastAPI の Depends() が必要。Depends(user_dep) と書くことで、「定義のときには呼ばず、呼び出しのときに FastAPI が呼んで」と指示できる。
タカ
タカ師匠パス関数の引数には、複数の依存関係を並べられる。

3つの書き方の違い

書き方何が起きるか判定
user = user_dep処理そのものを初期値として入れるだけ。FastAPI は呼んでくれない誤り
user = user_dep()パス関数が定義された時点で1回だけ呼ばれる。問い合わせのたびには呼ばれない誤り
user = Depends(user_dep)問い合わせが来るたびに FastAPI が呼んで、結果を渡す正しい

🔎 具体例：Depends() を忘れるとどうなるか

現在時刻を返す依存関数 now() を t = now() と書いたとします。サーバを起動した瞬間の時刻が1回だけ取得され、その値がずっと使われます。1時間後に問い合わせても、返るのは起動時の時刻です。

t = Depends(now) と書けば、問い合わせが来るたびに now() が呼ばれ、そのときの時刻が入ります。この差は動かしてみるまで気づきにくいので、必ず Depends() で包みます。

💡 なぜこれが必要か／これを知ったらできること

  • 依存関係の最小のコードが書ける
  • Depends() がなぜ必要かを説明できる

✅ この項のまとめ

  • 依存関係は呼び出せるもの（処理またはクラス）
  • 引数: name: type = Depends(depfunc)
  • Depends() が無いと定義のときに呼ばれてしまう
6

依存の範囲（スコープ）パス／ルーター／アプリ全体

要するに：適用範囲は「1つの窓口」「まとまり単位」「アプリ全体」の3段階です。確認だけなら dependencies=[] で、戻り値を使うなら引数として宣言します。

タカ
タカ師匠依存関係の適用範囲は3段階ある。①1つのパス関数、②ルーター（窓口のまとまり）、③アプリ全体。順に見ていこう。

シングルパス（1つの窓口だけ）

引数に書く基本の形です。短く書ける形もあります。

コードを見る（1行ずつ説明つき）
# 基本の形：引数名、その種類、そして Depends で包んだ依存関数を書く。
def pathfunc(name: depfunc = Depends(depfunc)):
    ...

# 短い形：種類の指定から依存関数が分かる場合は、かっこの中を省略できる。
def pathfunc(name: depfunc = Depends()):
    ...
タカ
タカ師匠name が、depfunc の返す値を受け取る変数だ。さっきの例だと、pathfunc が get_user()、depfunc が user_dep()、name が user にあたる。

決まった利用者の情報を返し、それをそのまま返事にする例です。

コードを見る（1行ずつ説明つき）
# 枠組み本体と、依存関係を宣言する道具を取り出す。
from fastapi import FastAPI, Depends

# アプリ全体を作る。
app = FastAPI()

# 依存関数。名前を受け取るが、渡されなければ "anonymous"（名無し）を使う。
def user_dep(name: str = "anonymous") -> dict:
    # 名前と、正しいかどうかを組にして返す。
    return {"name": name, "valid": True}

# /user への GET をこの下の処理に結びつける。
@app.get("/user")
# user の値は user_dep から得る。返ってくるのは項目名と値の組。
def get_user(user: dict = Depends(user_dep)) -> dict:
    # 受け取った内容をそのまま返す。
    return user
# --- /user?name=ハル に問い合わせた結果 ---
# {"name": "ハル", "valid": true}
# --- /user（名前なし）に問い合わせた結果 ---
# {"name": "anonymous", "valid": true}

副作用だけの依存関係

タカ
タカ師匠依存関数が「何かを確かめるだけで、戻り値を使わない」場合、パスデコレータのほうに依存関係を書くこともできる。

デコレータ側に書く形です。

コードを見る（1行ずつ説明つき）
# デコレータの中に dependencies= を書き、角かっこの中に Depends で包んだものを並べる。
# この書き方では、パス関数の引数には何も追加しなくてよい。
@app.method(url, dependencies=[Depends(depfunc)])

特定の名前を拒否する確認だけを行う例です。戻り値は使いません。

コードを見る（1行ずつ説明つき）
# 枠組み本体、依存関係の道具、エラーを返すための道具を取り出す。
from fastapi import FastAPI, Depends, HTTPException

# アプリ全体を作る。
app = FastAPI()

# 確認だけを行う依存関数。何も返さないことに注目。
def check_user(name: str = "anonymous"):
    # 名前が "banned" だったときだけ、次の行に進む。
    if name == "banned":
        # 403（権限が無い）というエラーを出す。ここでパス関数の本体は実行されない。
        raise HTTPException(status_code=403, detail="禁止ユーザー")

# /private への GET を結びつける。dependencies に確認だけの処理を並べている。
@app.get("/private", dependencies=[Depends(check_user)])
# 引数に何も足していない点がポイント。確認は上ですでに済んでいる。
def get_private() -> dict:
    # 確認を通った場合だけ、この中身が返る。
    return {"data": "プライベート情報"}
# --- /private?name=ハル に問い合わせた結果 ---
# {"data": "プライベート情報"}
# --- /private?name=banned に問い合わせた結果 ---
# 403 Forbidden
# {"detail": "禁止ユーザー"}
ハル
ハル「戻り値を使わない／確認だけ」のときはデコレータ側、戻り値を使うときは引数側、ですね。

タカ師匠その通り。

複数のパス（ルーター単位）

タカ
タカ師匠第9章で詳しくやるけど、大きな FastAPI のアプリでは、すべての窓口を一番上に付けるんじゃなく、その下に複数のルーターを定義する。
タカ
タカ師匠ルーター単位で依存関係を宣言すれば、そのルーターの下の全部のパス関数に適用される。

管理用の窓口をまとめ、その全部に確認をかける例です。

コードを見る（1行ずつ説明つき）
# 窓口をまとめる入れ物と、依存関係の道具を取り出す。
from fastapi import APIRouter, Depends

# 身分を確かめる処理。この例では中身を書いていない（pass は何もしないという意味）。
def check_auth():
    pass

# まとまりを作る。prefix はこの中の窓口すべての住所の先頭に付く共通部分。
# dependencies に書いた処理は、この中のすべての窓口の前に実行される。
router = APIRouter(
    prefix="/admin",
    dependencies=[Depends(check_auth)],
)

# app ではなく router に対して結びつける。実際の住所は /admin/users になる。
@router.get("/users")
def get_users():
    # 利用者の名前の一覧を返す。
    return ["alice", "bob"]

# もう1つの窓口。こちらの実際の住所は /admin/logs になる。
@router.get("/logs")
def get_logs():
    # 記録の一覧を返す。
    return ["log1", "log2"]
# --- この設定で起きること ---
# /admin/users と /admin/logs のどちらに来ても、先に check_auth が実行される。
# 窓口が10個に増えても、書き足す必要はない。
タカ
タカ師匠これで router の下の全部のパス関数の前に check_auth() が呼ばれる。

グローバル（アプリ全体）

タカ
タカ師匠一番上の FastAPI のアプリを定義するとき、すべてのパス関数に適用される依存関係を追加することもできる。

すべての窓口に記録を残す例です。

コードを見る（1行ずつ説明つき）
# 枠組み本体と、依存関係の道具を取り出す。
from fastapi import FastAPI, Depends

# 記録を残す処理。この例では中身を書いていない。
def log_request():
    pass

# アプリ全体を作るときに dependencies を渡すと、全部の窓口に適用される。
app = FastAPI(dependencies=[Depends(log_request)])

# 一番上の住所への GET を結びつける。
@app.get("/")
def root():
    # 簡単な内容を返す。
    return {"hello": "world"}
# --- この設定で起きること ---
# どの窓口に問い合わせが来ても、必ず先に log_request が実行される。
# あとから窓口を増やしても、自動的に適用される。
タカ
タカ師匠これで app の下のすべてのパス関数の前に log_request() が呼ばれる。

3つの範囲の使い分け

① パス単位

その窓口だけで必要なもの。引数に Depends() を書く。

例：この窓口だけの利用者取得
→

② ルーター単位

まとまりに共通のもの。APIRouter(dependencies=[...])。

例：管理用の窓口だけ権限確認
→

③ アプリ全体

全部に共通のもの。FastAPI(dependencies=[...])。

例：すべての問い合わせの記録
↺ 広い範囲にかけるほど書く量は減りますが、例外を作りにくくなります。「本当に全部に必要か」を考えて範囲を選びます。

🔎 具体例：範囲を間違えるとどうなるか

ログイン用の窓口を含むアプリ全体に「ログイン済みであること」の確認をかけたとします。すると、ログインする前の人がログインの窓口を使おうとしても、「ログインしていない」という理由で弾かれます。誰もログインできなくなります。

この場合は、ログイン用の窓口を除いたまとまり（ルーター）に対して確認をかけるのが正しい選び方です。逆に、すべての問い合わせを記録する処理なら、アプリ全体にかけて問題ありません。

💡 なぜこれが必要か／これを知ったらできること

  • 「身分の確認は全窓口共通だからアプリ全体、課金は管理用だけだからルーター単位」のように使い分けられる
  • コードの重複を最小にできる

✅ この項のまとめ

  • 範囲は3段階: パス／ルーター／アプリ
  • 戻り値を使う: 引数の Depends()
  • 確認だけ: dependencies=[Depends(...)]

章末の理解度チェック全5問

第1問依存性注入の意味

「依存性注入」とは、ざっくり言って何のことですか？ 普通の関数呼び出しと比べて何が違うのか、自分の言葉で説明してください。

✅ 解答例
依存性注入は「処理が必要とする情報を、処理の中で取りに行くのではなく、外部から引数として渡す」作り方のこと。普通だと処理の中で db.get_user() のように直接呼ぶが、この作り方だと「user」を引数として受け取り、誰がそれを用意するかは外側に任せる。これによりテストでは偽の利用者を渡したり、身分の確認の実装を差し替えたりできる。
📝 採点ポイント
□ 「必要な情報を外から渡す」という発想を述べている
□ 通常の関数呼び出しとの違いに触れている
□ テストのしやすさや差し替えのしやすさに言及している
第2問Depends() が必要な理由

なぜ user = user_dep や user = user_dep() ではなく、user = Depends(user_dep) と書く必要があるのですか？

✅ 解答例
user = user_dep だと処理そのものを初期値として入れるだけで、FastAPI に「これを呼んでくれ」と伝わらない。user = user_dep() だと、パス関数が定義される段階で user_dep() が一度だけ呼ばれてしまい、問い合わせのたびには呼ばれない。Depends(user_dep) は「その処理を覚えておいて、問い合わせごとに呼んで」と FastAPI に指示する仕組み。
📝 採点ポイント
□ user_dep だけだと FastAPI が呼んでくれない、という説明
□ user_dep() だと定義のときに1回だけ呼ばれてしまう、という指摘
□ Depends() が「呼び出しを後回しにする」役割であることを説明
第3問依存関係の範囲

FastAPI で依存関係を適用できる3つの範囲を挙げ、それぞれどんな用途に向いているか説明してください。

✅ 解答例
①1つの窓口：その窓口だけで必要な情報（特定の利用者情報の取得など）に向く。引数で Depends() を使う。②ルーター単位：管理用の窓口だけ権限の確認を入れるなど、一部のまとまりに共通の処理に向く。APIRouter(dependencies=[...]) で宣言。③アプリ全体：全部の窓口で走る記録や共通の身分確認など。FastAPI(dependencies=[...]) で宣言。
📝 採点ポイント
□ パス／ルーター／アプリの3段階を挙げている
□ それぞれの典型的な用途を例示している
□ 宣言の方法（引数 か dependencies=[...] か）に触れている
第4問戻り値を使う／使わない

「戻り値を使わず確認だけしたい依存関係」と「戻り値をパス関数で利用したい依存関係」では、書き方が違います。それぞれどう書きますか？

✅ 解答例
戻り値を使う場合は、パス関数の引数に user: dict = Depends(user_dep) のように書き、引数で戻り値を受け取る。戻り値を使わず確認（身分の確認や入力の確認など）だけしたい場合は、パスデコレータに dependencies=[Depends(check_auth)] のように書く。後者ではパス関数の引数に追加する必要がない。
📝 採点ポイント
□ 戻り値を使う場合は引数の Depends() を述べている
□ 確認だけは dependencies=[Depends(...)] を述べている
□ 両方の用途の違いを正しく説明している
第5問組み込みの依存関係の例

FastAPI の Header(), Query(), Path(), Body() は、実は依存関係の組み込み版です。これらを「依存性注入の文脈」でどう理解できるか、自分の言葉で説明してください。

✅ 解答例
これらはすべて「問い合わせの特定の場所からデータを取り出す依存関数」と捉えられる。たとえば Header() は「添えられた情報から値を取って、その値を引数として渡す」依存関係。Query() も Body() も同じ仕組みで、それぞれ住所のうしろの条件、本体から値を取り出す。自分で書く依存関数と本質は同じで、組み込みのものにはデータの確認・形式の変換・自動の説明ページ生成も付いてくる。
📝 採点ポイント
□ 4つすべてが「依存関係」であると認識している
□ それぞれが「問い合わせの特定の場所から値を取る」役割と述べている
□ 自作の依存関数と同じ仕組み、という統一感に触れている
