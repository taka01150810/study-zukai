サービス層

このサイトが提供する機能の本体。判断や組み合わせの処理を書く場所です。

ビジネスロジック

その業務ならではの決まりごとや判断の処理。「在庫が0なら注文できない」といったものです。

素通し パススルー

受け取ったものを何も加工せず、そのまま次に渡すだけの処理のことです。

リソース

アプリが扱うデータのひとかたまり。生き物、探検家などが1つずつのリソースです。

None

Python で「値が無い」ことを表すもの。「見つからなかった」を伝えるのによく使われます。

例外 exception

処理を続けられない事態が起きたときに投げられる知らせ。受け止めなければ処理は止まります。

TypeError / ValueError

それぞれ「種類が違う」「値が正しくない」ときに使われる、Python にもとから用意された失敗の知らせです。

Optional

「その値でもよいし、無し（None）でもよい」という書き添え。Python 3.9 より前で使います。

pytest

「このコードは期待どおりに動くか」を自動で確かめるプログラムを書くための道具です。

単体テスト unit test

1つの処理だけを取り出して、期待どおりに動くかを確かめることです。

エンドツーエンドテスト

外からの問い合わせからデータベースまで、全部を通して確かめることです。

契約テスト

層と層の間の取り決めが守られているかを確かめることです。

assert

「ここはこうなっているはず」と書く行。違っていればその場でテストが失敗します。

ロギング

いつ、何が起きたかを記録に残すことです。

メトリック

件数や所要時間など、動作の状況を数値で表したものです。

モニタリング／可観測性

その数値を継続して見張り、異常があれば知らせる仕組みです。

Prometheus / Grafana

前者が数値を集める道具、後者がそれを見やすく表示する道具です。

トレース

1回の問い合わせが、どの処理にどれだけ時間を使ったかを段階ごとに記録することです。

OpenTelemetry

記録・数値・追跡のやり方をそろえるための、今の標準的な取り組みです。

サービスの定義サイトの存在理由

要するに：サービス層は業務上の決まりごとの中心です。作成・取得・更新・削除 と「1件／複数件」の組み合わせが基本の型です。

タカ
タカ師匠サービス層はWebサイトの中心であり、存在理由だ。複数の場所から依頼を受け、サイトの核であるデータにアクセスし、返事を返す。
タカ
タカ師匠よくある組み合わせは、①作成／検索／変更（一部または全部）／削除、②1件だけ／複数件。
タカ
タカ師匠RESTful の層では名詞がリソースにあたる。本書では最初のリソースとして「クリプトイド（架空の生き物）」と「探検家（人間）」を使う。
タカ
タカ師匠後で関連するリソースを定義することもできる。①場所、②出来事（遠征、目撃の記録など）。
1件だけ複数件
作成createまとめて作る（必要になれば）
検索get_oneget_all
変更modify / replaceまとめて変える（必要になれば）
削除deleteまとめて消す（必要になれば）

💡 なぜこれが必要か／これを知ったらできること

  • サービス層の存在意義が腹に落ちる
  • 「単に素通しするだけでも、層として作る価値がある」と分かる

✅ この項のまとめ

  • サービス層 = Webサイトの存在理由
  • 基本の型: 作成・取得・更新・削除 × 1件/複数件
  • リソースは名詞。関連するリソースを増やせる

プロテクション認証はどこでやるか

要するに：サービス層はデータの出入りに集中します。身分と権限の確認は上の層（本書では Web層）に任せます。

タカ
タカ師匠層に分けることのいいところは「全部を気にしなくていい」ことだ。サービス層はデータの出入りだけを気にすればいい。
タカ
タカ師匠第11章で身分と権限の確認をやるけど、その面倒な部分は上の層（本書では Web層）が担当できる。
タカ
タカ師匠「作成・変更・削除」の処理は誰にでも開放すべきではないし、取得の処理ですら最終的に制限が必要になることがある。

🔎 具体例：取得にも制限が必要になる場面

探検家の一覧を返す窓口は、最初は誰でも見られてよいかもしれません。しかし後から「連絡先」の項目が追加されると、話が変わります。誰でも一覧を取得できるままだと、全員分の連絡先が外に出ます。

このとき「ログインした人だけ」「本人と管理者だけ」といった制限を、Web層で確認するように追加します。サービス層はデータの出し入れに専念したままでいられます。

💡 なぜこれが必要か／これを知ったらできること

  • 各層の役目を意識して切り分けられる
  • 身分の確認は Web層、業務の決まりごとはサービス層、という分担が見える

✅ この項のまとめ

  • サービス層はデータの出入りに集中
  • 身分と権限の確認は Web層側
  • 書き込みや削除の処理は、将来的に制限が必要

関数最初は素通しでよい

要するに：サービス層は最初は素通しですが、ファイルを分けて各リソースで作ります。import fake.X as data の形で下の層を切り離しておきます。

タカ
タカ師匠creature.py と explorer.py はほとんど同じになる。1つのファイルにまとめたくなるけど、ほぼ必ずどこかで違いが出てくる。最初から2ファイルに分けておくのが正解だ。
タカ
タカ師匠今の時点では、サービス層のファイルはほぼ素通しだ。最初に少し余分な構造を持っておくことが、後で効いてくる典型例だね。

生き物のサービス層です。6つの処理すべてが、下の層に渡して結果を返すだけです。

コードを見る（1行ずつ説明つき）
# 生き物のデータの形を取り込む。返す値の種類を書くために使う。
from model.creature import Creature
# 仮データのファイルを、data という名前で呼べるようにする。
# 第10章で本物のデータ層に差し替えるとき、この1行を変えるだけで済む。
import fake.creature as data

# すべてを返す。下の層に頼んで、返ってきたものをそのまま返す。
def get_all() -> list[Creature]:
    return data.get_all()

# 名前を指定して1件を返す。見つからない場合は None が返る、という書き添え。
def get_one(name: str) -> Creature | None:
    return data.get_one(name)

# 新しく作る。受け取った内容を下の層に渡す。
def create(creature: Creature) -> Creature:
    return data.create(creature)

# 一部を更新する。どれを、どう変えるかを下の層に渡す。
def modify(name: str, creature: Creature) -> Creature:
    return data.modify(name, creature)

# 全体を置き換える。
def replace(name: str, creature: Creature) -> Creature:
    return data.replace(name, creature)

# 削除する。うまくいったかどうかを真偽の値で返す。
def delete(name: str) -> bool:
    return data.delete(name)

探検家のほうも、まったく同じ形です。

# Optional[Creature] は「Creature か、または None」という意味。
# 新しい書き方の Creature | None とまったく同じ意味になる。
def get_one(name: str) -> Optional[Creature]:
    return data.get_one(name)

🔎 具体例：後から決まりごとが入る場所

今の create() は受け取ったものをそのまま下に渡すだけです。しかし後から「同じ名前の生き物がすでにあれば作らない」という決まりが加わったとします。この判断は、Web の事情でもデータベースの事情でもなく、このサイトの決まりごとです。

見つからないときどうするか

タカ
タカ師匠テストする前に、設計の判断が必要だ。Creature や Explorer が見つからない場合、get_one() は何を返すべきか？ ①None を返す、②失敗を投げる、のどちらかだ。
タカ
タカ師匠Python にもとからある失敗の知らせで近いものは、①TypeError：None は Creature とは別の種類だから近いと言える、②ValueError：正しくない値に対する知らせで、get_one(id) に存在しない値を渡す場合に合っている、③自作の知らせ：自分で「見つからない」専用のものを作ることもできる。
タカ
タカ師匠どちらを選んでも、その影響は一番上の層まで波及する。今は失敗を投げるのではなく None でいこう。結局のところ、それが「無い」という意味なんだ。

短所：呼ぶ側が毎回「無いかどうか」を確かめる必要があります。

実際に書いて動かす

サービス層の3つの動きを確かめるテストです。

コードを見る（1行ずつ説明つき）
# 確認に使うデータの形を取り込む。
from model.creature import Creature
# 確かめたい相手（サービス層）を code という名前で取り込む。
# 短い名前にしておくと、テストの中で何度も書くときに読みやすい。
from service import creature as code

# テストで使う見本のデータを1件用意する。仮データの1件目と同じ内容にしてある。
sample = Creature(
    name="Yeti",
    aka="Abominable Snowman",
    country="CN",
    area="Himalayas",
    description="Hirsute Himalayan",
)

# 名前が test_ で始まる処理を、pytest が自動で見つけて実行する。
def test_create():
    # 見本のデータを渡して、作成の処理を呼ぶ。
    resp = code.create(sample)
    # assert は「ここはこうなっているはず」と書く行。
    # 返ってきたものが、渡したものと同じであることを確かめる。違えばここで失敗する。
    assert resp == sample

# 存在するものを取得できるかの確認。
def test_get_exists():
    # 見本の名前を渡して、1件を取得する。
    resp = code.get_one(sample.name)
    # 返ってきたものが見本と同じであることを確かめる。
    assert resp == sample

# 存在しないものを指定したときの確認。
def test_get_missing():
    # 仮データに無い名前を渡してみる。
    resp = code.get_one("boxturtle")
    # 「無い」を表す None が返ることを確かめる。
    # is None と書くのは、None かどうかを調べるときの決まった書き方。
    assert resp is None

タカ師匠注意。第10章では get_one() は見つからない生き物に対して None を返さなくなる（失敗を投げるように設計を変える）ので、test_get_missing() のテストは失敗する。けど、それはその時点で直す。

🔎 具体例：テストが先に壊れることの意味

第10章で get_one() の設計を変えると、test_get_missing() が赤くなります。これは困ったことではなく、むしろ役に立ちます。「この変更は、見つからないときの動きに影響する」と、テストが自動的に教えてくれたからです。

テストが無ければ、この変更の影響に気づくのは、実際に利用者が「見つからないはずの検索でエラー画面が出た」と報告してきたときになります。

💡 なぜこれが必要か／これを知ったらできること

  • 単体テストの最小の形が書けるようになる
  • 「見つからないときどうするか」という設計の議論ができる
  • assert を使った単純なテストの書き方が身につく

✅ この項のまとめ

  • テストの置き場所: test/unit/{web,service,data}/, test/full/
  • pytest は test_ という名前を目印にする
  • 「見つからない」: None か 失敗を投げるか
  • 本章は None、第10章で失敗を投げる形に切り替え

ロギング何が自動で残るか

要するに：FastAPI は窓口への呼び出しの基本的な記録を自動で出しますが、送られた中身までは残しません。

タカ
タカ師匠FastAPI は窓口への呼び出しをそれぞれ記録する。時刻、動詞、住所を含む。ただし本体や添えられた情報で運ばれるデータは記録しない。
コードを見る（1行ずつ説明つき）
# --- サーバを動かしている画面に自動で出る記録の例 ---
# INFO:     127.0.0.1:52375 - "GET /explorer/ HTTP/1.1" 200 OK
#   127.0.0.1:52375 → どこから来たか
#   GET             → どの動詞で
#   /explorer/      → どの住所に
#   200 OK          → どの番号で返したか
# 送った本体（たとえばパスワード）は、この記録には含まれない。

🔎 具体例：中身が記録されないことの意味

ログイン用の窓口に {"name":"ハル","password":"secret123"} を送ったとします。記録に残るのは POST /login 200 OK だけで、パスワードは残りません。これは安全上ありがたい動きです。

逆に「どんな値が送られてきたか調べたい」場合は、自分で記録を追加することになります。そのとき、パスワードなど残してはいけない項目を除く配慮が必要です。

💡 なぜこれが必要か／これを知ったらできること

  • 初期状態の記録で何が見えるかが分かる
  • 大事なデータが記録に残る危険を意識できる

✅ この項のまとめ

  • FastAPI の初期状態: 時刻／動詞／住所 を記録
  • 本体や添えられた情報は記録しない

章末の理解度チェック全5問

第1問サービス層の役割

サービス層は「素通しのコードしか書かないなら不要では？」という意見に、どう答えますか？ 自分の言葉で説明してください。

✅ 解答例
サービス層は最初は素通しに見えるが、必ず後で業務上の決まりごと（リソース同士の関係、権限を確認した後の処理、複雑な検索など）が入る。最初から層を作っておけば、Web層やデータ層に変更が波及せずに済む。後から層を追加するのは何倍も手間がかかる。また、層を分けておけば各層を独立して確認できるという利点もある。
📝 採点ポイント
□ 将来の決まりごとの居場所として必要、と述べている
□ 後から層を追加する手間の大きさに触れている
□ 独立して確認できる、という利点に触れている
第2問見つからない時の方針

get_one(name) で対象が見つからない時、どんな方針がありますか？ それぞれの長所と短所を述べてください。

✅ 解答例
None を返す：単純で、返す種類は Creature | None。長所は失敗を受け止める処理が不要で軽いこと。短所は呼ぶ側で毎回 if x is None: を書く必要があること。失敗を投げる：ValueError や自作の「見つからない」を投げる。長所は正常なときとそうでないときをはっきり分けられ、まとめて受け止められること。短所は想定外のときの負荷と、複数の層をまたいで伝わることへの対応が必要な点。第10章では None から失敗を投げる形に切り替える、というのが本書の選択。
📝 採点ポイント
□ None の方針と失敗を投げる方針の両方を挙げている
□ それぞれの長所・短所を述べている
□ 本書が None → 失敗を投げる形 に切り替えることに触れている
第3問テストの置き場所の設計

本書ではテストのフォルダを test/unit/web/, test/unit/service/, test/unit/data/, test/full/ のように分けています。それぞれの役割と、分ける意義を説明してください。

✅ 解答例
test/unit/ の下は1つの処理だけを確かめるもので、特定の層の処理だけを見て、層の境界を越えない。unit/web/ は Web層のみ、unit/service/ はサービス層のみ、unit/data/ はデータ層のみを確かめる。test/full/ は全部を通した確認で、Web層から実際のデータベースまですべての層を貫いて確かめる。分ける意義は、問題が起きたときにどの層が原因かを切り分けやすくし、確認する範囲・速さ・必要なものを制御できること。
📝 採点ポイント
□ 単体と全体の違いに触れている
□ 各層の確認が境界を越えない、と説明している
□ 問題の切り分け、実行の制御、という利点に触れている
第4問運用に関わる仕事

サービス層には作成・取得・更新・削除以外に「記録・数値・見張り・追跡」といった運用に関わる仕事があります。それぞれの役割を簡潔に説明してください。

✅ 解答例
記録：何が起きたかを残す（時刻、動詞、住所、失敗の内容など）。数値：件数、応答時間の分布、失敗の割合などの統計。見張り：その数値を継続して見て、異常があれば知らせる仕組み。追跡：1回の問い合わせの内訳の時間を、層やサービスごとに記録して見えるようにする。遅れの原因を特定するのに使う。
📝 採点ポイント
□ 4つすべてに触れている
□ 各概念の役割を簡潔に説明している
□ 数値と追跡の違い（全体の傾向 と 1件ごとの内訳）に触れている
第5問取り込みの差し替え

本書のサービス層では import fake.creature as data と書いています。なぜ import fake.creature ではなく、as data で別の名前を付けるのですか？

✅ 解答例
サービス層の中では data という共通の名前で下の層を参照するため。これにより、後で仮のものを本物のデータ層のファイル（たとえば data.creature）に差し替えたとき、サービス層の本文（data.get_all() などの呼び出し）はそのまま動く。取り込みの1行だけ書き換えればよい。これは「実装を差し替えられること」を最初から仕込んでおく設計。
📝 採点ポイント
□ 「data」という共通の名前を使う意図に触れている
□ 後でファイルを差し替えやすくなる利点に触れている
□ 「取り込みの行だけ書き換えれば本文は変わらない」という具体的な利点に言及
