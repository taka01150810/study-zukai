マイクロフレームワーク

必要最小限の機能だけを提供し、足りない部分は別のパッケージで足していく設計の枠組みです。

モノリシック 一体型

必要な機能を1つの大きなまとまりとして全部そろえている作りのことです。

WSGI

Python のプログラムと Web サーバをつなぐ、1件ずつ順に処理する方式の取り決めです。

ASGI

WSGI の非同期版。返事待ちの間に別の処理を進められる方式の取り決めです。

Quart

Flask と同じ書き方のまま、ASGI に対応させたフレームワークです。

jsonify

Flask で、返す値を JSON の形式に変換する命令です。

request オブジェクト

Flask で、届いた問い合わせの内容がまとめて入っているもの。ここから値を取り出します。

ORM

データベースの表を、プログラムの中のデータとして扱えるようにする仕組み。SQL を自動で組み立てます。

ODM

ORM の、表形式ではないデータベース向けの版です。

SQL

データベースに「この条件のデータを取ってきて」と伝えるための言語です。

NoSQL

表の形にしばられないデータベース。Redis、MongoDB などがあります。

SQLAlchemy

Python でデータベースを扱うための定番のパッケージ。SQL を直接書くことも、ORM として使うこともできます。

SQLModel

SQLAlchemy と Pydantic を組み合わせた、FastAPI の作者による新しいパッケージです。

URLConf

Django で、住所と処理の対応を1か所の表にまとめて書く仕組みです。

ビュー関数

Django で、問い合わせを受けて返事を作る処理のこと。他の枠組みのパス関数にあたります。

管理画面 admin

Django が自動で作る、データを追加・編集・削除できる画面です。

テンプレート

決まった形の HTML の中に、その都度の値を差し込んで画面を作る仕組みです。

Jinja

最もよく使われるテンプレートの仕組み。Flask、Django、FastAPI のどれでも使えます。

SSE サーバ送信イベント

サーバ側から、つながっている相手に一方的に情報を送り続ける仕組みです。

WebSocket

サーバと相手が、つながったまま双方向にやり取りを続けられる仕組みです。

キュー queue

時間のかかる仕事を並べておき、手の空いた処理担当が順に取り出す仕組みです。

マルチパート

1回の送信の中に、ファイルと文字などの複数の部分を含める形式です。

Bottle / Litestar / AIOHTTP / Socketify.py

Flask・Django・FastAPI 以外の Python の Web 用の枠組みです。

Flask軽くて習得が早い、順に処理する枠組み

要するに：Flask は軽量で習得が早い、1件ずつ順に処理する方式のマイクロフレームワークです。非同期版として Quart があります。

タカ
タカ師匠まず Flask から。マイクロフレームワークを名乗っている。基本の機能だけを提供して、必要に応じて他のパッケージを足していく設計だ。Django より小さく、最初に覚えるのは早い。
タカ
タカ師匠重要な性質。Flask は ASGI ではなく WSGI が土台の、1件ずつ順に処理する方式だ。新しい非同期のサーバには直接は対応していない。
タカ
タカ師匠ASGI に対応した Flask 互換のものとして Quart がある。

💡 なぜこれが必要か／これを知ったらできること

  • Flask の「軽さ」と「1件ずつ処理する性質」を説明できる
  • 非同期が必要なら Quart や FastAPI だと分かる

✅ この項のまとめ

  • Flask = マイクロフレームワーク
  • WSGI（1件ずつ順に処理）が土台
  • Quart = Flask 互換の ASGI 版
2

パス（Flask と FastAPI の比較）住所の一部を受け取る

要するに：書き方は似ていますが、Flask は <who> という記法で、JSON にするために jsonify() が必要な場合があります。

タカ
タカ師匠両者ともデコレータで住所と窓口を結びつける。第3章の「住所から挨拶する相手を取得」する窓口を、両方で書いてみよう。

⚡ FastAPI

波かっこで置き場所を作り、返した文字は自動で JSON になります。

コードを見る（1行ずつ説明つき）
# 枠組み本体を取り出す。
from fastapi import FastAPI

# アプリ全体を作る。
app = FastAPI()

# 波かっこ {who} が、住所の中の置き場所。GET はデコレータの名前で示す。
@app.get("/hi/{who}")
# 置き場所と同じ名前の引数に、その値が自動で入る。
def greet(who):
    # 返す文字。JSON への変換は書かなくてよい。
    return f"Hello? {who}?"
# --- /hi/Mom に問い合わせた結果 ---
# "Hello? Mom?"

🧩 Flask

不等号で置き場所を作り、動詞を明示し、JSON への変換を自分で呼びます。

コードを見る（1行ずつ説明つき）
# 枠組み本体と、JSON に変換する命令を取り出す。
from flask import Flask, jsonify

# アプリ全体を作る。__name__ は、このファイルの位置を枠組みに教えるための決まり文句。
app = Flask(__name__)

# 不等号 <who> が置き場所。methods で受け付ける動詞を明示している。
@app.route("/hi/<who>", methods=["GET"])
# 置き場所と同じ名前の引数に、その値が入る。ここは FastAPI と同じ。
def greet(who):
    # 文字列を返すときは、JSON にするために jsonify を呼ぶ必要がある。
    return jsonify(f"Hello? {who}?")
# --- /hi/Mom に問い合わせた結果 ---
# "Hello? Mom?"
タカ
タカ師匠ポイントは3つ。①Flask では住所の置き場所が {who} ではなく <who>、②Flask では methods=["GET"] を明示的に書く（書かなければ初期値で GET）、③JSON にしたいなら jsonify() を呼ぶ。
タカ
タカ師匠補足：Flask 2.0 以降は @app.get(...) のような FastAPI と同じ書き方にも対応している。jsonify() は最近の Flask なら項目名と値の組を返す場合は自動で変換してくれるが、文字列のような他の種類では呼ぶ必要がある。

💡 なぜこれが必要か／これを知ったらできること

  • 「FastAPI から Flask へ／Flask から FastAPI へ」移すとき、何が変わるかを把握できる
  • どちらがより宣言的かを判断できる

✅ この項のまとめ

  • FastAPI: {who} + 自動で JSON
  • Flask: <who> + jsonify()（または最近の自動変換）
  • Flask は動詞を明示するのが推奨

クエリパラメータ引数で宣言 vs 手で取り出す

要するに：FastAPI は引数として宣言するだけ。Flask は request.args から自分で取り出します。

⚡ FastAPI

コードを見る（1行ずつ説明つき）
# 枠組み本体を取り出す。
from fastapi import FastAPI

# アプリ全体を作る。
app = FastAPI()

# 住所には置き場所を書いていない。
@app.get("/hi")
# 住所に無い引数なので、住所のうしろの条件から取ると判断される。
# : str の書き添えにより、文字列であることの確認も自動で行われる。
def greet(who: str):
    # 受け取った値を文章に埋め込んで返す。
    return f"Hello? {who}?"
# --- /hi?who=Mom に問い合わせた結果 ---
# "Hello? Mom?"
# --- who を省いた場合 ---
# 422 のエラーが自動で返る。処理の中身は実行されない。

🧩 Flask

コードを見る（1行ずつ説明つき）
# 枠組み本体、届いた問い合わせの入れ物、JSON 変換の命令を取り出す。
from flask import Flask, request, jsonify

# アプリ全体を作る。
app = Flask(__name__)

# 住所と動詞を指定する。
@app.route("/hi", methods=["GET"])
# 引数を書かない。値は処理の中で自分で取りに行く。
def greet():
    # request.args に条件が入っている。そこから who という名前の値を取り出す。
    # 値が無い場合は None が入る。確認は自分で書く必要がある。
    who = request.args.get("who")
    # 文字列を JSON にして返す。
    return jsonify(f"Hello? {who}?")
# --- /hi?who=Mom に問い合わせた結果 ---
# "Hello? Mom?"
# --- who を省いた場合 ---
# "Hello? None?" が返る。エラーにはならない。
タカ
タカ師匠Flask では、届いた問い合わせの入れ物から値を取り出す。住所のうしろの条件は request.args という組み合わせに入っている。
ハル
ハルFastAPI なら引数として宣言するだけで済むんですね。
タカ
タカ師匠そう、その違いが大きい。FastAPI は引数に型ヒントがあれば、Pydantic が確認もしてくれる。Flask は自分で書く。

🔎 具体例：値が無かったときの違い

/hi に who を付けずに問い合わせたとします。FastAPI では処理の中身が実行される前に 422 のエラーが返り、「who が必要です」という内容も含まれます。

Flask では request.args.get("who") が None を返し、そのまま "Hello? None?" という文章ができてしまいます。これを防ぐには if who is None: のような確認を自分で書く必要があります。窓口が20個あれば、20か所に書きます。

💡 なぜこれが必要か／これを知ったらできること

  • 「FastAPI の簡潔さ」が、行数として目に見える
  • データの受け取り方の作法の違いが理解できる

✅ この項のまとめ

  • FastAPI: 引数で宣言、型ヒント付き
  • Flask: request.args.get() で取得

ボディ送られた本体からの取り出し

要するに：本体の取り出しも同じ構図です。FastAPI は引数で宣言、Flask は request.json 経由です。

⚡ FastAPI

コードを見る（1行ずつ説明つき）
# 枠組み本体と、本体から値を取り出す部品を取り出す。
from fastapi import FastAPI, Body

# アプリ全体を作る。
app = FastAPI()

# データを送る動詞である post に結びつける。
@app.post("/hi")
# who は本体から取り出す、という指定。
# embed=True は「本体が {"who": "Mom"} の形で来る」という意味。
def greet(who: str = Body(embed=True)):
    # 取り出した値を文章に埋め込んで返す。
    return f"Hello? {who}?"
# --- {"who": "Mom"} を送った結果 ---
# "Hello? Mom?"

🧩 Flask

コードを見る（1行ずつ説明つき）
# 枠組み本体、問い合わせの入れ物、JSON 変換の命令を取り出す。
from flask import Flask, request, jsonify

# アプリ全体を作る。
app = Flask(__name__)

# 住所と、データを送る動詞を指定する。
@app.route("/hi", methods=["POST"])
# 引数は書かない。
def greet():
    # request.json に、送られてきた本体が入っている。そこから who を取り出す。
    who = request.json.get("who")
    # 文字列を JSON にして返す。
    return jsonify(f"Hello? {who}?")
# --- {"who": "Mom"} を送った結果 ---
# "Hello? Mom?"
タカ
タカ師匠Flask は送られた JSON を request.json に入れている。これも自分で .get("who") する。

💡 なぜこれが必要か／これを知ったらできること

  • 確認込みでデータを引数として受け取れる FastAPI の利点が明確になる

✅ この項のまとめ

  • FastAPI: Body(embed=True) で引数として
  • Flask: request.json.get(...) で取得

ヘッダ4か所すべてで同じ構図

要するに：添えられた情報も同じです。FastAPI は引数で宣言、Flask は request.headers 経由。4か所すべてで一貫した違いです。

⚡ FastAPI

コードを見る（1行ずつ説明つき）
# 枠組み本体と、添えられた情報を取り出す部品を取り出す。
from fastapi import FastAPI, Header

# アプリ全体を作る。
app = FastAPI()

# /hi への GET を結びつける。
@app.get("/hi")
# who は添えられた情報から取り出す、という指定。
def greet(who: str = Header()):
    # 取り出した値を文章に埋め込んで返す。
    return f"Hello? {who}?"
# --- who: Mom を添えて問い合わせた結果 ---
# "Hello? Mom?"

🧩 Flask

コードを見る（1行ずつ説明つき）
# 枠組み本体、問い合わせの入れ物、JSON 変換の命令を取り出す。
from flask import Flask, request, jsonify

# アプリ全体を作る。
app = Flask(__name__)

# 住所と動詞を指定する。
@app.route("/hi", methods=["GET"])
# 引数は書かない。
def greet():
    # request.headers に添えられた情報が入っている。そこから who を取り出す。
    # 名前の大文字と小文字は区別されない。
    who = request.headers.get("who")
    # 文字列を JSON にして返す。
    return jsonify(f"Hello? {who}?")
# --- who: Mom を添えて問い合わせた結果 ---
# "Hello? Mom?"
タカ
タカ師匠同じ形だ。Flask では request.headers から取り出す。名前の大文字と小文字は区別されない。

4か所の比較まとめ

データの場所FastAPIFlask
パス/hi/{who} + 引数 who/hi/<who> + 引数 who
クエリ引数 who: strrequest.args.get("who")
ボディ引数 who: str = Body(embed=True)request.json.get("who")
ヘッダ引数 who: str = Header()request.headers.get("who")
確認型ヒントから自動自分で書く
説明ページ自動生成される別途用意する

💡 なぜこれが必要か／これを知ったらできること

  • 4か所（パス／クエリ／ボディ／ヘッダ）すべてで、FastAPI の書き方の利点を比較できる

✅ この項のまとめ

  • FastAPI: Header() で引数として宣言
  • Flask: request.headers.get(...) で取得
  • 4か所すべてが「引数で宣言するか、問い合わせの入れ物から取るか」という同じ構図

Django大きく複雑、そして全部入り

要するに：Django は機能が全部そろった重量級の一体型です。住所の対応を1つの表にまとめる方式で、データベースの仕組みが内蔵されています。ASGI 対応は 3.0 以降です。

タカ
タカ師匠Django は Flask や FastAPI より大きく複雑だ。公式サイトの言葉を借りれば「締め切りに追われる完璧主義者」が対象。
タカ
タカ師匠内蔵の ORM（データベースの表をプログラムのデータとして扱う仕組み）があり、データベースを裏に持つサイトに便利だ。道具の集まりというよりは「ひとまとまりの大きなアプリ」だね。複雑さと覚える手間に見合うかどうかは、作るもの次第。
タカ
タカ師匠昔から WSGI だったが、3.0 から ASGI にも対応している。
タカ
タカ師匠大きな違い：Django はデコレータを使わず、1つの URLConf という表で住所と処理（ビュー関数と呼ぶ）の対応を定義する。
ハル
ハル一覧で見られるんですね。
タカ
タカ師匠そう、住所を1か所で見られるのは強みだ。逆に「処理を見ただけではどの住所に結びついているか分からない」という欠点もある。
🏷️

デコレータ方式（Flask / FastAPI）

処理のすぐ上に住所が書いてあるので、その処理がどの住所かがすぐ分かります。ただし全体の一覧は自分で探すことになります。

📝

フォーム

三者すべてが、標準的な HTML のフォームに対応しています。

データベース組み込みか、別ライブラリか

要するに：Flask と FastAPI はデータベースの機能を別のライブラリ（SQLAlchemy／SQLModel）に任せます。Django は ORM と管理画面が組み込みです。

タカ
タカ師匠Flask と FastAPI は基本のパッケージにデータベースの機能を含まない。一方 Django はデータベースの機能が中心にある。
タカ
タカ師匠データの層からデータベースを使う方法は4つ。①SQL を直接書く（PostgreSQL、SQLite など）、②表形式でないデータベースを直接使う（Redis、MongoDB、Elasticsearch）、③ORM（SQL を自動で組み立てる）、④ODM（表形式でないデータベース用の同様の仕組み）。
タカ
タカ師匠表形式のデータベースには、SQLAlchemy がよく使われる。SQL を直接書くところから ORM まで、複数の使い方ができる強力なパッケージだ。Flask や FastAPI の開発者の定番の選択だね。
タカ
タカ師匠FastAPI の作者 Sebastián Ramírez は、SQLAlchemy と Pydantic を組み合わせた SQLModel を作っている。第14章で詳しくやる。
タカ
タカ師匠Django は ORM が最初から入っていて、自動で作られる管理画面も持つ。技術者でない人にデータの管理をしてもらう、という用途には便利だが…
ハル
ハル注意点が？
タカ
タカ師匠実際にあった話で、詳しくない人が管理画面の警告を読み違えて、控えから手作業で元に戻す羽目になったことがある。便利だけど、誰でも触れるからこその落とし穴もある。

データベースへの4つのアクセス方法

🗒️

① SQL を直接

問い合わせの文を自分で書きます。細かく制御できます。

🗂️

② NoSQL を直接

表形式でないデータベースを、その方式のまま使います。

🔗

③ ORM

プログラムのデータの操作から、SQL を自動で組み立てます。

📄

④ ODM

ORM と同じことを、表形式でないデータベースに対して行います。

三者のデータベース対応

枠組みデータベース機能典型的な選択管理画面
Flask基本には含まないSQLAlchemy別途用意
FastAPI基本には含まないSQLAlchemy / SQLModel別途用意
DjangoORM が組み込みDjango ORM自動生成

🔎 具体例：管理画面の便利さと危うさ

Django の管理画面があれば、技術者でない担当者がブラウザから商品情報を追加・修正できます。専用の画面を作る手間がゼロで済みます。

一方で、その画面には削除の機能も並んでいます。「関連するデータもまとめて削除されます」という警告の意味が伝わらないまま操作されると、注文履歴まで消えることがあります。誰がどこまで触れるかの設定を、最初にきちんと決めておく必要があります。

💡 なぜこれが必要か／これを知ったらできること

  • データベース中心の案件で Django が選ばれやすい理由が分かる
  • FastAPI + SQLModel という新しい選択肢を知る

✅ この項のまとめ

  • Flask/FastAPI: データベースは別ライブラリ（SQLAlchemy/SQLModel）
  • Django: ORM・管理画面が組み込み
  • 管理画面の便利さと危うさは表裏一体

第1問三大フレームワークの位置づけ

Flask、Django、FastAPI の3つを、それぞれ一言で特徴づけて説明してください。

✅ 解答例
Flask は「マイクロフレームワーク」、必要最低限の機能だけを提供し、外部のライブラリで補う。WSGI が土台（1件ずつ順に処理）。Django は「締め切りに追われる完璧主義者向け」、ORM や管理画面まで内蔵した機能が全部そろった一体型で、大きなデータベース中心のサイトに向く。FastAPI は「型ヒント + Pydantic + ASGI の新しい世代」、軽量で宣言的、自動の説明ページが強みで、非同期にも対応。
📝 採点ポイント
□ Flask が WSGI 土台・マイクロな枠組みであることを述べている
□ Django が機能が全部そろった一体型であることを述べている
□ FastAPI が ASGI・型ヒント・自動ドキュメントを軸にしていることを述べている
第2問リクエストデータ取得の違い

FastAPI と Flask で、添えられた情報（ヘッダ）から値を取り出す書き方はどう違いますか？ それぞれの長所・短所を含めて説明してください。

✅ 解答例
FastAPI は def greet(who: str = Header()): のように、パス関数の引数として宣言する。Flask は request.headers.get("who") のように、共通の入れ物から自分で取り出す。FastAPI の長所は、宣言的で簡潔、型ヒントによる自動の確認、自動の説明ページへの反映。短所は覚える手間。Flask の長所は明示的・自由・単純。短所は同じコードが増え、確認を自分で書く必要があること。
📝 採点ポイント
□ FastAPI の引数で宣言する書き方に触れている
□ Flask の request.headers の書き方に触れている
□ 双方の長所・短所を客観的に述べている
第3問Django のルーティング

Django の住所の対応づけは Flask/FastAPI と何が違いますか？ その違いの長所と短所を述べてください。

✅ 解答例
Flask と FastAPI はデコレータで住所と処理を結びつける（処理の上に @app.get(...) のように書く）。Django はそれをせず、URLConf という1つの表（urls.py）で「この住所はこのビュー関数に」と一覧で定義する。長所は住所の対応を1か所で見わたせること、短所は処理だけを見ても、それがどの住所に結びついているか直接は分からない点。
📝 採点ポイント
□ Django は URLConf の表の方式と述べている
□ Flask/FastAPI はデコレータの方式と述べている
□ 双方の長所・短所（見わたしやすさ と 結びつきの見えやすさ）に触れている
第4問データベース機能

データベース機能において、Django と Flask/FastAPI の違いを説明してください。FastAPI でデータベースを使う場合の典型的な選択肢にも触れてください。

✅ 解答例
Django は ORM が最初から入っていて、管理画面も自動で作られる。データベース中心の業務サイトでは Django が選ばれやすい。Flask と FastAPI は基本のパッケージにデータベース機能を含まず、外部のライブラリで対応する。典型的には SQLAlchemy がよく使われる。FastAPI の作者は SQLAlchemy と Pydantic を組み合わせた SQLModel を作っており、これが新しい選択肢。
📝 採点ポイント
□ Django は ORM/管理画面が組み込み、と述べている
□ Flask/FastAPI は別ライブラリと述べている
□ SQLAlchemy / SQLModel の存在に触れている
第5問他の選択肢

Python の Web フレームワークの主要3つ（Flask, Django, FastAPI）以外にも、興味深い選択肢があります。本書で紹介されているものから2つ以上挙げて、それぞれの特徴を説明してください。

✅ 解答例
Bottle：Python のファイル1つに収まる超軽量なパッケージ。考えを試すことや小さな道具に向く。Litestar：FastAPI と同様 ASGI/Starlette と Pydantic を土台にする。独自の方針を持つ代替案。AIOHTTP：ASGI の呼ぶ側・受ける側の両方を扱える。例のコードが充実。Socketify.py：非常に高い性能を掲げる新しい枠組み。
📝 採点ポイント
□ 2つ以上の枠組みを挙げている
□ それぞれの特徴を正しく説明している
□ 「軽量／高速／代替」など、選ぶ基準が見える説明になっている
