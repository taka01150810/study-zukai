RESTful API設計リソース・ID・URL・動詞

要するに：RESTful はリソース + ID + URL + 動詞の組み合わせです。本書はリソース名を単数形にする方針です。

タカ
タカ師匠HTTP は単なる通信の取り決めだ。けれど、同じ材料でも作り方によって出来上がりが変わるように、HTTP の使い方にもうまい型がある。それが RESTful だ。
タカ
タカ師匠RESTful な設計の中心になる部品は、①リソース（アプリが扱うデータのかたまり）、②ID（1つに特定するための値）、③URL（リソースと ID を組み立てた文字列）、④動詞（URL に対する動作：GET/POST/PUT/PATCH/DELETE）。

HTTP 動詞のおさらい

動詞役割
GETデータを取得する
POST新しく作る
PUT全体を置き換える
PATCH一部を更新する
DELETE削除する
タカ
タカ師匠PUT と PATCH の使い分けは意見が分かれる。一部の更新と全体の置き換えを区別しないなら、片方で足りるかもしれない。

URL の型

型意味例
動詞 /resource/すべてのリソースに対する動作GET /thing → すべての生き物のデータを返す
動詞 /resource/idID で指定した1件に対する動作GET /thing/abc → ID が abc のものだけ返す
タカ
タカ師匠問い合わせは「並べ替え」「ページ分割」「別の処理の実行」のような追加の情報を持つことが多い。これらは住所の一部として / でつなぐか、住所のうしろに ? を付けて var=val の形で表す。住所には長さの制限があるので、大きな内容は本体で送ることが多い。

単数形か複数形か

タカ
タカ師匠名前の付け方の補足。多くの書き手は、リソース名・API の区分名・データベースの表の名前を複数形にすることを勧めている。私は長年それに従ったけど、今は単数形のほうが単純だと考えている。理由は3つ。
タカ
タカ師匠①一部の単語は単数形と複数形が同じ（series, fish）、②不規則な複数形を持つ単語がある（children, people）、③単数と複数を変換するコードが必要な場所が多い。
タカ
タカ師匠本書は単数形を採用する。これは一般的な RESTful の助言とは違うので、同意できなければ気にしなくていい。

🔎 具体例：複数形にすると起きる手間

リソース名を複数形にすると、住所は /explorers、モデルの名前は Explorer、データベースの表は explorers、と場所ごとに形が変わります。コードの中で「モデル名から住所を組み立てる」ような処理を書くとき、Explorer → explorers の変換が必要になります。

fish のように単数形と複数形が同じ語や、person → people のように形が変わる語があると、この変換は単に s を付けるだけでは済みません。単数形でそろえれば、この変換自体が不要になります。

💡 なぜこれが必要か／これを知ったらできること

  • API 設計の標準の型が手に入る
  • 単数形か複数形か、というチーム内の議論に対応できる

✅ この項のまとめ

  • RESTful の4要素: リソース／ID／URL／動詞
  • 主な動詞: GET/POST/PUT/PATCH/DELETE
  • URL の型: /resource と /resource/id
  • 本書はリソース名を単数形にする

最初のWebサイトコードmain.py と自動再起動

要するに：main.py を作って app = FastAPI() を定義し、uvicorn.run(..., reload=True) で起動します。自動再起動があると開発が楽になります。

アプリの入口になるファイルです。一番上の住所に問い合わせると文字を返します。

コードを見る（1行ずつ説明つき）
# 枠組み本体を取り出す。
from fastapi import FastAPI
# サーバを動かす道具を、このファイルの中から使えるように取り込む。
import uvicorn

# アプリ全体を作る。
app = FastAPI()

# 一番上の住所への GET を、この下の処理に結びつける。
@app.get("/")
def top():
    # 動作の確認用に、短い文字を返す。
    return "top here"

# このファイルが直接動かされたときだけ、下を実行する決まり文句。
if __name__ == "__main__":
    # コロンの前がファイル名、後ろが変数名。reload=True で保存のたびに自動再起動する。
    uvicorn.run("main:app", reload=True)

def echo(thing):

        country="FR",

        country="DE",
        description="Myopic machete man"),

    return _explorers

    for e in _explorers:

        if e.name == name:

            return e

    return None

    return explorer

# 一部を更新する処理。今の段階では、受け取ったものをそのまま返すだけ。

    return explorer

# 全体を置き換える処理。こちらも今は、受け取ったものをそのまま返すだけ。

    return explorer

第2問APIRouter の使い方

第3問段階的開発

本書では「最初は Web層に仮のデータを直接書き、徐々に下の層に移動する」という進め方を取ります。この理由を自分の言葉で説明してください。

✅ 解答例

□ 初期段階での複雑さを下げる、という意図に触れている

第4問層の間の通信ルール

Web層・サービス層・データ層の間で守るべき通信のルールは何ですか？ このルールを破ると何が起きますか？

✅ 解答例
ルール：Web層はサービス層だけを呼び、データ層は呼ばない。サービス層はデータ層を呼ぶ。データ層は実際のデータベースや外部のサービスとだけ会話する。各層は隣の層とだけ会話する一方向の流れを守る。これを破ると、Web層の中に SQL などのデータの細部が入り込んだり、データ層が HTTP の事情を知ってしまったりして、変更のときに複数の層が連鎖的に影響を受ける。確認するコードも書きにくくなる。
📝 採点ポイント
□ 「Web→サービス→データ」の一方向に触れている
□ ルール違反による影響（細部の漏れ、確認の難しさ）を説明している
□ 層の事情を漏らさない、という原則に触れている
第5問並べ替えとページ分割をどこで行うか

並べ替えとページ分割は、Web層・サービス層・データ層のどこで行うべきですか？ 理由も含めて説明してください。

✅ 解答例
通常はデータ層（データベース側）で行うのが最適。理由は、データベースは大量の件数の並べ替えやページ分割が得意で、効率よく処理できるから。Web層でやろうとすると、全件をデータベースから取ってきて Python で並べ替えて切り出すことになり、メモリも通信量も無駄になる。FastAPI では条件を Pydantic のモデルにまとめ、Depends() で受け取り、サービス層を通してデータ層に渡す、というのが推奨される形。
