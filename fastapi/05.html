「このどれかの種類ならよい」という意味。Python 3.10 以降は縦棒1本で書けます。

複数の値を順番に並べたもの。後から追加や削除ができます。

型ヒントの書き方

変数に書き添える基本の形です。値を一緒に入れることもできます。

コードを見る（1行ずつ説明つき）
# 名前のうしろにコロンを付け、その値がどんな種類かを書く形。
name: type
# 種類を書いたうえで、イコールで実際の値も入れる形。
name: type = value

# 実例：thing という名前に「文字列を入れる想定」と書き添え、"yeti" を入れる。
thing: str = "yeti"

まとまりを表す型の書き方は、Python 3.9 の前後で変わりました。

コードを見る（1行ずつ説明つき）
# Python 3.9 より前：まとまりの種類は typing から大文字の名前で取り込む必要があった。
from typing import List, Dict, Tuple
# 「整数だけが入った一覧」という意味。
nums: List[int] = [1, 2, 3]

# Python 3.9 以降：取り込みなしで、小文字の組み込みの名前をそのまま使える。
# 意味は上とまったく同じ。こちらのほうが短く読みやすい。
nums: list[int] = [1, 2, 3]

小数の値を入れる例です。

コードを見る（1行ずつ説明つき）
# float は小数を表す種類。計算結果をそのまま入れることもできる。
# 1 を 137.03599913 で割った値が入る。
physics_magic_number: float = 1.0 / 137.03599913

typing の便利な道具

🌀

Any

種類を問わない、という指定です。

🔀

Union

Union[str, int] のように「このどれかならよい」という指定です。

➖

|（3.10以降）

str | int と書けば Union と同じ意味になります。

項目名と値の組み合わせ（辞書）に、型を書き添える3通りの書き方です。

コードを見る（1行ずつ説明つき）
# 書き方1：中身の種類までは指定せず、「辞書である」ことだけを示す。
from typing import Dict
responses: Dict = {200: "ok"}

# 書き方2：角かっこの中に、項目名の種類と値の種類を順に書く。
# ここでは「項目名は整数、値は文字列」という意味になる。
from typing import Dict
responses: Dict[int, str] = {200: "ok"}

# 書き方3：Python 3.9 以降の書き方。取り込み不要で、意味は書き方2と同じ。
responses: dict[int, str] = {200: "ok"}

型だけを書いた行は書けますが、名前だけの行は書けません。その違いを確かめた例です。

コードを見る（1行ずつ説明つき）
# まだ何も入れていない名前をそのまま書くと、「そんな名前は無い」と失敗する。
thing0
# --- 実行結果 ---
# NameError: name 'thing0' is not defined

# 一方、値は入れずに「文字列を入れる想定」とだけ書くのは許される。
# これは書き添えだけを登録している状態で、値はまだ無い。
thing0: str
# --- 実行結果 ---
# 何も表示されず、失敗もしない。

mypy が見つけてくれる間違い

書き添えに反する値を入れても、Python 本体は止めません。

コードを見る（1行ずつ説明つき）
# thing1 は文字列を入れる想定、と書き添えて "yeti" を入れる。
thing1: str = "yeti"
# 同じ名前に整数の 47 を入れる。書き添えに反しているが、Python は何も言わない。
thing1 = 47
# --- 実行結果 ---
# エラーも警告も出ず、そのまま動いてしまう。

上の2行を stuff.py に保存して、mypy にかけてみます。

コードを見る（1行ずつ説明つき）
# mypy のあとに調べたいファイル名を書く。実行はせず、中身だけを調べる。
$ mypy stuff.py
# --- 実行結果 ---
# stuff.py:2: error: Incompatible types in assignment
# (expression has type "int", variable has type "str")
# Found 1 error in 1 file (checked 1 source file)
# 「2行目で、文字列の想定の名前に整数を入れている」と場所つきで指摘してくれる。

関数の戻り値の型ヒント

戻り値の種類は、コロンではなく矢印で書きます。

コードを見る（1行ずつ説明つき）
# かっこの後ろに矢印を書き、そのあとに「返す値の種類」を書く形。
function(args) -> type:

# 実例：get_thing は文字列を返す想定、という書き添え。
def get_thing() -> str:
    # 実際に文字列を返している。書き添えと合っている。
    return "yeti"
# --- 呼び出した結果 ---
# yeti
タカ
タカ師匠自分で定義した設計図や、それらの組み合わせも何でも使える。

🔎 具体例：型ヒントが無いと何が起きるか

def calc(price, tax) という処理があり、実際には price に整数、tax に小数を渡す想定だとします。半年後にこれを使う人は、tax に「10」（10%のつもり）を渡すかもしれません。すると 1000 円の商品が 11000 円になります。エラーは出ず、数字だけが間違います。

def calc(price: int, tax: float) -> int と書いておけば、編集画面が引数の種類を教えてくれますし、mypy が食い違いを指摘します。書き添えは、実行時には何もしませんが、書き手同士の取り決めとして働きます。

💡 なぜこれが必要か／これを知ったらできること

  • 型ヒントの書き方を覚えれば、mypy で型の間違いを事前に見つけられる
  • Python 3.10 以降の | の書き方と、旧来の Union の対応が分かる

✅ この項のまとめ

  • 変数: name: type [= value]
  • 関数の戻り値: -> type
  • まとまり: list[int]、dict[str, int]（3.9以降）
  • どれかを表す: int | str（3.10以降）
  • mypy で型の食い違いを見つけられる

🧭

country：2文字の国コード

タカ
タカ師匠Python の昔からあるデータのまとめ方を並べると：①tuple（変えられない並び）、②list（変えられる並び）、③set（重複しない値の集まり）、④dict（項目名と値の組、項目名には変えられない種類を使う）。

タプルとリスト

5つの値を、変えられない並びとしてまとめた例です。取り出すときは位置の番号を使います。

コードを見る（1行ずつ説明つき）
# 丸かっこで囲むと、あとから変えられない並びになる。値は左から順に並ぶ。
tuple_thing = ("yeti", "CN", "Himalayas", "Hirsute Himalayan", "Abominable Snowman")
# 角かっこの中の 0 は「先頭から0番目」という意味。先頭は1ではなく0から数える。
print("Name is", tuple_thing[0])
# --- 実行結果 ---
# Name is yeti

同じ内容を、あとから変えられる並びにした例です。取り出し方は同じです。

コードを見る（1行ずつ説明つき）
# 角かっこで囲むと、あとから追加や削除ができる並びになる。
list_thing = ["yeti", "CN", "Himalayas", "Hirsute Himalayan", "Abominable Snowman"]
# 取り出し方はタプルと同じで、位置の番号を使う。
print("Name is", list_thing[0])
# --- 実行結果 ---
# Name is yeti
タカ
タカ師匠タプルやリストは位置でしか取り出せない。「何番目に何があるか」を覚えないといけない。

位置の番号に名前を付けて、少し読みやすくした書き方です。

コードを見る（1行ずつ説明つき）
# range(5) は 0,1,2,3,4 という5つの数を作る。それを左の5つの名前に順に割り当てる。
# つまり NAME=0, COUNTRY=1, AREA=2, DESCRIPTION=3, AKA=4 となる。
NAME, COUNTRY, AREA, DESCRIPTION, AKA = range(5)
# 値の並びは先ほどと同じ。
tuple_thing = ("yeti", "CN", "Himalayas", "Hirsute Himalayan", "Abominable Snowman")
# 0 と書く代わりに NAME と書ける。数字の意味が読み取りやすくなる。
print("Name is", tuple_thing[NAME])
# --- 実行結果 ---
# Name is yeti

辞書

項目名と値を組にしてまとめた例です。名前を指定して取り出せます。

コードを見る（1行ずつ説明つき）
# 波かっこで囲み、「項目名: 値」をカンマで区切って並べる。
dict_thing = {
    # 名前は yeti。
    "name": "yeti",
    # 国コードは CN（中国）。
    "country": "CN",
    # 生息地域はヒマラヤ。
    "area": "Himalayas",
    # 説明文。
    "description": "Hirsute Himalayan",
    # 別の呼び名。
    "aka": "Abominable Snowman",
}
# 位置の番号ではなく、項目名を指定して取り出せる。何番目かを覚える必要がない。
print("Name is", dict_thing["name"])
# --- 実行結果 ---
# Name is yeti
タカ
タカ師匠辞書は項目名で取り出せる分、少し扱いやすい。set は重複しない値の集まりなので、こういう「複数の項目をまとめる」用途にはあまり向かない。

namedtuple

位置でも名前でも取り出せるようにした並びです。

コードを見る（1行ずつ説明つき）
# 名前付きの並びを作るための標準の機能を取り込む。
from collections import namedtuple

# 5つの項目名を持つ、新しい形を作る。第1引数はこの形の名前。
CreatureNamedTuple = namedtuple("CreatureNamedTuple",
    "name, country, area, description, aka")
# 作った形に、実際の値を左から順に渡してデータを1件作る。
namedtuple_thing = CreatureNamedTuple("yeti",
    "CN",
    "Himalayas",
    "Hirsute Himalayan",
    "Abominable Snowman")
# 位置の番号でも取り出せる。
print("Name is", namedtuple_thing[0])
# ドットのあとに項目名を書いても取り出せる。こちらのほうが読みやすい。
print("Name is", namedtuple_thing.name)
# --- 実行結果 ---
# Name is yeti
# Name is yeti
# 注意：namedtuple_thing["name"] という書き方はできない。並びであって辞書ではないため。

通常のクラス

自分で設計図を作る書き方です。受け取った値を1つずつ自分に覚えさせる記述が必要です。

コードを見る（1行ずつ説明つき）
# CreatureClass という設計図を作る。
class CreatureClass:
    # データを1件作るときに最初に動く処理。self は作られたそのデータ自身を指す。
    def __init__(self, name, country, area, description, aka):
        # 受け取った name を、自分の name として覚えさせる。以下同様。
        self.name = name
        self.country = country
        self.area = area
        self.description = description
        self.aka = aka

# 設計図に値を渡して、データを1件作る。
class_thing = CreatureClass("yeti", "CN", "Himalayas",
    "Hirsute Himalayan", "Abominable Snowman")
# ドットのあとに項目名を書いて取り出す。
print("Name is", class_thing.name)
# --- 実行結果 ---
# Name is yeti
タカ
タカ師匠普通の設計図はデータだけじゃなく、そのデータに対する処理も持てる。でも「データだけを入れておく箱」が欲しいとき、self.xxx = xxx をたくさん書くのは面倒だ。

dataclass

同じことを、覚えさせる記述なしで書けるようにしたものです。

コードを見る（1行ずつ説明つき）
# データ専用の設計図を作るための標準の機能を取り込む。
from dataclasses import dataclass

# この1行を付けると、受け取った値を自分に覚えさせる処理が自動で作られる。
@dataclass
class CreatureDataClass:
    # 項目名と、その種類を並べて書くだけでよい。self.xxx = xxx は不要。
    name: str
    country: str
    area: str
    description: str
    aka: str

# 使い方は通常の設計図と同じ。値を左から順に渡す。

    "Hirsute Himalayan", "Abominable Snowman")
# ドットのあとに項目名を書いて取り出す。
print("Name is", dc_thing.name)
# --- 実行結果 ---
# Name is yeti
タカ
タカ師匠self.xxx = xxx が消えた！ dataclass は Python における、データを持つことに特化した設計図の機能だ。
タカ
タカ師匠ここまでで「データをまとめる」点はかなり良くなった。でも、あと5つ欲しいものがある。①複数の種類を許すこと、②値が無い場合や省略できる場合の扱い、③初期値、④データの確認、⑤JSON などの形式との相互変換だ。

💡 なぜこれが必要か／これを知ったらできること

  • データのまとめ方の選択肢が一覧できる
  • Pydantic がなぜ「行き着いた形」と言えるか、流れの中で理解できる

✅ この項のまとめ

  • 昔から: tuple / list / dict / set / namedtuple / class
  • 新しめ: dataclass
  • いずれも確認や変換は別に用意する必要がある

model.py：Creature モデル

コードを見る（1行ずつ説明つき）
# Pydantic から、モデルの元になるものを取り出す。
from pydantic import BaseModel

# BaseModel を受け継いで Creature という形を作る。これだけで確認の機能が付く。
class Creature(BaseModel):
    # 名前は文字列。以下の5項目はすべて、渡されなければ失敗する必須の項目。
    name: str
    # 国コードも文字列。
    country: str
    # 地域も文字列。
    area: str
    # 説明も文字列。
    description: str
    # 別名も文字列。
    aka: str
タカ
タカ師匠Creature は Pydantic の BaseModel を受け継いでいる。各項目の : str は、文字列であることを示す型ヒントだ。
タカ
タカ師匠重要な点。この例では全部の項目が必須だ。Pydantic では、型に Optional（省略できる指定）が無ければ、その項目は必ず値を持たなければならない。

コードを見る（1行ずつ説明つき）
# 定義した形を取り込む。

# 先頭のアンダースコアは「外から直接触らないでほしい」という書き手の意思表示。
# list[Creature] は「Creature の形のデータだけが入った一覧」という書き添え。

        name="yeti",
        country="CN",
        area="Himalayas",
        description="Hirsute Himalayan",
        aka="Abominable Snowman",
    ),

        country="US",

        aka="Bigfoot",
    ),

def get_creatures() -> list[Creature]:
    # 用意しておいた一覧をそのまま返す。

タイプを検証する種類が違えばその場で止まる

要するに：Pydantic はデータを作る時点で種類を確認します。合っていなければ ValidationError が出ます。

タカ
タカ師匠ここまでで、①変数と処理に型ヒントを付ける、②Pydantic のモデルを定義して使う、③データの置き場からモデルの一覧を返す、④一覧を JSON に自動変換して相手に返す、を見た。
タカ
タカ師匠では実際にデータを確認してみよう。Creature の項目に、違う種類の値を入れてみる。Pydantic の確認はデータを作る時点で走る。

文字列を入れるべき項目に、わざと一覧を入れてみます。

コードを見る（1行ずつ説明つき）
# 定義した形を取り込む。
from model import Creature

# データを1件作ろうとする。
dragon = Creature(
    # 名前は文字列。ここは問題ない。
    name="dragon",
    # 国コードも文字列。問題ない。
    country="*",
    # 地域も文字列。問題ない。
    area="*",
    # ここが問題。description は文字列の想定だが、角かっこで囲んだ一覧を渡している。
    description=["扁額のような", "炎を吐く"],
    # 別名は文字列。問題ない。
    aka="ドラゴン",
)
# --- 実行結果 ---
# pydantic.error_wrappers.ValidationError:
# 1 validation error for Creature description
#   str type expected (type=type_error.str)
# 「Creature の description で文字列を期待していた」と、項目名つきで教えてくれる。
# dragon という名前にデータは入らず、この行で処理が止まる。
タカ
タカ師匠description に文字列ではなく一覧を入れているので、Pydantic が「文字列を期待していたよ」と失敗を知らせてくれた。

🔎 具体例：確認が無いと、どこで問題が起きるか

もし確認が無ければ、description に一覧が入ったまま処理が進みます。問題が表面化するのは、たとえば画面に表示しようとしたときや、文字数を数えようとしたときです。エラーが出る場所と、間違った値が入った場所が離れているので、原因を探すのに時間がかかります。

Pydantic はデータを作る瞬間に止めるので、間違った値がどこから来たかがすぐ分かります。FastAPI の窓口では、外から届いたデータがこの確認に引っかかると、処理に入る前に 422 のエラーが返ります。

💡 なぜこれが必要か／これを知ったらできること

  • 「確認のコードを書かなくても、モデルが違反を弾いてくれる」と分かる
  • 入力を確かめるコードを大きく減らせる

✅ この項のまとめ

  • データを作る時点で Pydantic が種類を確認する
  • 種類が違うと ValidationError
  • Web の層でも同じように確認される

要するに：Pydantic は種類に加えて、長さ・範囲・文字の並びなどの条件も宣言して書けます。constr、conint、Field() を使います。

タカ

書き方1：constr で最小2文字を求める

名前が2文字未満なら受け付けない、という条件を付けた例です。

コードを見る（1行ずつ説明つき）
# モデルの元になるものと、条件付きの文字列を作る道具を取り出す。
from pydantic import BaseModel, constr

# Creature という形を作る。
class Creature(BaseModel):
    # 単なる文字列ではなく「2文字以上の文字列」という条件付きの種類にしている。
    name: constr(min_length=2)
    country: str
    area: str
    description: str
    aka: str

# 名前に空の文字列を渡してみる。長さ0なので条件を満たさない。
c = Creature(name="", country="*", area="*", description="d", aka="a")
# --- 実行結果 ---
# pydantic.error_wrappers.ValidationError:
#   1 validation error for Creature name
#   ensure this value has at least 2 characters
#   (type=value_error.any_str.min_length)
# 「この値は少なくとも2文字必要」と、条件の内容まで含めて教えてくれる。

書き方2：Field を使う

同じ条件を、別の書き方で表したものです。結果はまったく同じです。

コードを見る（1行ずつ説明つき）
# モデルの元になるものと、項目ごとの条件を書く道具を取り出す。
from pydantic import BaseModel, Field

# Creature という形を作る。
class Creature(BaseModel):
    # 種類は普通の文字列にしておき、条件は Field のほうに書く。
    # 最初の ... は「この項目は必須で、初期値は無い」という意味の記号。
    name: str = Field(..., min_length=2)
    country: str
    area: str
    description: str
    aka: str

# 同じく、名前に空の文字列を渡してみる。
c = Creature(name="", country="*", area="*", description="d", aka="a")
# --- 実行結果 ---
# pydantic.error_wrappers.ValidationError:
#   1 validation error for Creature name
#   ensure this value has at least 2 characters
#   (type=value_error.any_str.min_length)
# 書き方1とまったく同じ結果になる。好みで選んでよい。
タカ
タカ師匠Field(...) の ... は「値が必須で、初期値は無い」という意味だ。
タカ
タカ師匠Pydantic の最小限の紹介はここまで。要点は、データの確認が自動でできること。Web の層やデータの層でデータを受け取るときに、この力が効いてくる。

🔎 具体例：自分で書くとどれだけの量になるか

「name は2〜50文字」「age は0以上120以下の整数」「email は英数字と @ を含む」という3つの条件を、自分で書くとします。項目の存在を確かめる if、種類を確かめる if、範囲を確かめる if、そしてそれぞれのエラーメッセージ…と、3項目で20行以上になります。項目が増えるほど、この量も比例して増えます。

Pydantic なら name: constr(min_length=2, max_length=50) age: conint(ge=0, le=120) のように3行で済み、エラーメッセージも「どの項目が、どの条件に反したか」の形で自動的に作られます。

💡 なぜこれが必要か／これを知ったらできること

  • 「文字列は2〜50文字、ID は正の整数」のような決まりを宣言して書ける
  • 確認のコードがほとんど無くても、崩れにくい API が組める

✅ この項のまとめ

  • 値の確認もモデルの定義に書ける
  • conint, constr: 種類ごとの条件
  • Field(..., min_length=2): 同じ意味の別の書き方
  • ... は「必須・初期値なし」の意味

第1問型ヒントの仕組み

Python の型ヒントは「実行時には強制されない」のに、どうやって役に立つのですか？ mypy と Pydantic それぞれの活用のしかたを説明してください。

✅ 解答例
Python 本体は型ヒントの記述を無視して実行する。けれど型ヒントは情報として残るので、道具が活用できる。mypy は型を調べる道具で、コードを動かさずに解析して型の食い違いを指摘する。Pydantic は型ヒントを「データの形の定義」として使い、データを作る時点で項目の種類を確認する。同じ型ヒントの情報を、用途によって違う道具が利用している。
📝 採点ポイント
□ Python 本体が型ヒントを無視することに触れている
□ mypy が動かさずに型を調べることを述べている
□ Pydantic がデータを作る時点で確認することを述べている
第2問辞書と Pydantic モデルの違い

「とりあえず辞書で受け取って中身を確認しよう」というやり方ではなく、Pydantic のモデルを使うべき理由を、自分の言葉で説明してください。

✅ 解答例
辞書は中身に何が入っているか保証が無いので、項目の存在、種類、値の範囲などをすべて自分で確かめるコードを書かなければならない。Pydantic のモデルなら、BaseModel を受け継いで型ヒントを書くだけで、これらの確認が自動で走る。さらにエラーの内容も分かりやすく、JSON との相互変換も組み込まれている。書くコードが減り、間違いも減り、そのまま説明にもなる。
📝 採点ポイント
□ 辞書は中身が保証されないという欠点に触れている
□ Pydantic が自動で確認してくれることを述べている
□ JSON 変換や、定義がそのまま説明になる点に触れている
第3問BaseModel の必須項目

Pydantic の BaseModel を受け継いだ形で、ある項目を「省略できる」ようにするのと「必須」にするのは、どう書き分けますか？

✅ 解答例
初期状態では Pydantic の項目は必須の扱いで、値を渡さないと ValidationError になる。省略できるようにしたい場合は Optional[str] を型に書き、= None のような初期値を与える。あるいは Python 3.10 以降なら str | None = None の形で同じことを表せる。Field(..., …) の ... は「必須で初期値なし」を明示するためのもの。
📝 採点ポイント
□ 初期状態では必須、という前提に触れている
□ Optional[type] または type | None の書き方に触れている
□ 初期値（= None など）を与える必要がある、と説明している
第4問値の検証

Pydantic で「name は2文字以上の文字列」「age は 0 以上 120 以下の整数」という条件を表すには、どう書きますか？

✅ 解答例
from pydantic import BaseModel, constr, conint と書いたうえで、name: constr(min_length=2)、age: conint(ge=0, le=120) と書く。または Field(..., min_length=2)、Field(..., ge=0, le=120) を使ってもよい。値が条件を満たさないと、データを作る時点で ValidationError が発生する。
📝 採点ポイント
□ constr/conint または Field を使う書き方を示している
□ min_length, ge, le などの正しい指定名を使っている
□ 違反すると ValidationError が出ることに触れている
第5問FastAPI と Pydantic の組み合わせ

Pydantic のモデルを FastAPI のパス関数の戻り値として返すと、どんなことが自動で起きますか？ 返事の側について、自分の言葉で説明してください。

✅ 解答例
FastAPI が内部の jsonable_encoder() で Pydantic のモデルを「JSON にできる形」へ変換し、続いて JSON の文字列にして、Content-Type: application/json を付けて返事として返す。list[Creature] の場合は一覧として返る。これによりパス関数は単純にモデルを返すだけで、JSON の返事ができあがる。変換の命令を手で呼ぶ必要も、日時で失敗する心配も無くなる。
📝 採点ポイント
□ 戻り値を JSON に自動変換することを述べている
□ Content-Type: application/json が自動で付くことに触れている
□ 変換の命令を書く必要が無くなる、という利点に触れている

コードを見る（1行ずつ説明つき）
# モデルの元と、条件付きの種類を作る道具を取り出す。
from pydantic import BaseModel, constr, conint

# 利用者を表す形を作る。
class User(BaseModel):
    # 名前は2文字以上50文字以下の文字列。
    name: constr(min_length=2, max_length=50)
    # 年齢は0以上120以下の整数。ge は以上、le は以下。
    age: conint(ge=0, le=120)

# 条件を満たす値でデータを作る。問題なく作られる。
u = User(name="ハル", age=22)
print(u)
# --- 実行結果 ---
# name='ハル' age=22

# 年齢に範囲外の値を渡してみる。
u2 = User(name="ハル", age=200)
# --- 実行結果 ---
# ValidationError: 1 validation error for User age
#   ensure this value is less than or equal to 120
