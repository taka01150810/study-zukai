エンドポイント endpoint

「この住所に、この動詞で送ったら、この処理をする」という1つの窓口のこと。

パスデコレータ

処理の直前に書く @app.get("/hi") のような1行。「この住所への問い合わせは、下の処理に回して」と指示します。

パス関数

パスデコレータのすぐ下に書く処理。問い合わせを受けて、返す内容を決める部分です。

Uvicorn

作ったプログラムを実際に動かし、外からの問い合わせを待ち受けるサーバー。

localhost / ポート8000

localhost は「今使っているこのパソコン自身」を指す住所。8000 はその中の入口番号です。

--reload

ファイルを保存するたび、サーバーを自動で再起動する指定。開発中に手で止めて起動し直す手間が省けます。

HTTPie

コマンドから窓口に問い合わせて、返ってきた内容を見るための道具。JSON を扱いやすく表示します。

Requests / HTTPX

どちらも Python のプログラムから窓口に問い合わせるためのパッケージ。HTTPX は非同期にも対応しています。

パス path

住所の中の /users/1 のような部分。どのデータを指しているかを表します。

クエリパラメータ

住所のうしろに ?who=Mom の形で付ける追加の指定。省略できる条件を渡すのに使います。

ボディ body

送るデータの本体。作成や更新のときに、まとまったデータをここに入れます。

ヘッダ header

本体とは別に添える情報。身分を示す文字列や、送り手の種類などを入れます。

依存性注入 DI

必要なものを自分で用意せず、外から渡してもらう作り方。FastAPI では引数に書くだけで必要な値が渡ってきます。

冪等（べきとう） idempotent

何度同じことをしても結果が変わらない性質。GET はこの性質を持つべきとされています。

ステータスコード

返事に付く3桁の数字。200 は成功、4xx は送り手側の誤り、5xx はサーバー側の誤りです。

JSON

データを文字列で書き表す形式。FastAPI は返した値を自動でこの形式に変換します。

jsonable_encoder

そのままでは JSON にできないデータ（日時など）を、変換できる形に直す FastAPI の内部処理です。

Pydantic モデル

データの形（項目名と種類）をまとめて宣言したもの。届いた値が合っているかを自動で確かめられます。

response_model

「外に返すときはこの形に絞る」という指定。指定した形にない項目は自動で取り除かれます。

非識別化

データから個人を特定できる項目を取り除くこと。医療情報などを外に出すときに必要になります。

OpenAPI

API の仕様を決まった形式で書き表す取り決め。FastAPI はコードからこれを自動で作ります。

Swagger UI

OpenAPI の内容を、ブラウザで読めて実際に試せるページとして表示する仕組みです。

MIMEタイプ

返すデータが何の種類か（文章か、HTML か、画像か）を表す表記です。

最初のエンドポイント hello.py

「/hi という住所に問い合わせが来たら、Hello? World? という文字を返す」だけのプログラムです。これで Web サーバが1つ完成します。

コードを見る（1行ずつ説明つき）
# fastapi というパッケージから、FastAPI という部品を取り出して使えるようにする。
from fastapi import FastAPI

# アプリ全体を表すものを1つ作り、app という名前で呼べるようにする。
app = FastAPI()

# この1行が「/hi という住所に GET で来た問い合わせは、下の処理に回して」という指示。
@app.get("/hi")
# 実際にその問い合わせを受けたときに動く処理。名前は自由に付けられる。
def greet():
    # この文字を返す。返した値は自動で JSON の形式に変換されて相手に届く。
    return "Hello? World?"
# --- ブラウザで http://localhost:8000/hi を開いた結果 ---
# "Hello? World?"

Uvicorn で起動する2つの方法

方法1：コマンドから起動します。hello がファイル名、app がその中の変数名です。

コードを見る（1行ずつ説明つき）

# --- 実行結果 ---

# INFO:     Started reloader process

方法2：プログラムの中から起動します。ファイルを直接動かすだけでサーバーが立ち上がります。

コードを見る（1行ずつ説明つき）

# サーバを動かすための道具も、プログラムの中から使えるように取り込む。

# アプリ全体を作る。
app = FastAPI()

# /hi への GET をこの下の処理に結びつける。
@app.get("/hi")
def greet():
    # 返す文字。
    return "Hello? World?"

# このファイルが直接動かされたときだけ、下を実行する。
if __name__ == "__main__":
    # hello.py の中の app を、自動再起動を有効にして動かす。
    uvicorn.run("hello:app", reload=True)
# --- 実行結果（python hello.py で動かした場合） ---
# INFO:     Uvicorn running on http://127.0.0.1:8000

🔎 具体例：--reload があるとどう違うか

--reload なしで起動していると、返す文字を "Hello? World?" から "こんにちは" に書き換えても、ブラウザを更新しても表示は変わりません。サーバーは起動したときの内容を持ち続けているからです。毎回 Ctrl+C で止めて、もう一度起動する必要があります。

--reload を付けておくと、ファイルを保存した瞬間にサーバーが自動で再起動し、ブラウザを更新すれば新しい内容が出ます。1文字直すたびに手で再起動する時間がなくなります。

HTTPリクエストデータを置ける4つの場所

要するに：リクエストはパス／クエリ／ボディ／ヘッダの4か所にデータを持てて、FastAPI はそれぞれに専用の書き方を用意しています。

タカ
タカ師匠第1章でみたように、リクエストにはデータを置く場所が複数ある。FastAPI はそれぞれに対して、便利な書き方を用意している。①Header：付随情報、②Path：URL の中、③Query：URL の ? のあと、④Body：本体。
タカ
タカ師匠FastAPI がリクエストのいろいろな部分からデータを渡してくれる仕組みは、最良の特徴の一つで、他の Python の Web フレームワークより洗練されている。引数をパス関数の中で直接宣言できる。これは依存性注入という手法を使っている。第6章で詳しくやるよ。
タカ
タカ師匠例として、who というパラメータを追加して、「Hello? ○○?」と返すようにしてみよう。who を渡す方法を、URL パス／クエリ／ボディ／ヘッダの4通りで試す。
📍

Path（パス）

住所そのものの中。/hi/Mom の Mom。どのデータかを指すのに使います。

❓

Query（クエリ）

住所のうしろ。?who=Mom。省略できる条件に使います。

📦

Body（ボディ）

送るデータの本体。まとまった内容を送るときに使います。

🏷️

Header（ヘッダ）

本体とは別に添える情報。身分証明などに使います。

💡 なぜこれが必要か／これを知ったらできること

  • 「どこにデータを置くか」という設計判断を、4つの選択肢から選べる
  • 依存性注入という言葉の意味がぼんやりつかめる

✅ この項のまとめ

  • リクエストデータの4か所: Header / Path / Query / Body
  • FastAPI はそれぞれを Python の引数に直接対応づける
  • 仕組みは依存性注入（DI）
4

URLパス住所の一部を引数として受け取る

要するに：住所に {name} という書き方を入れると、その位置の値がパス関数の引数として受け取れます。

住所の一部を {who} という置き場所にして、その値を使ってあいさつを返す例です。

コードを見る（1行ずつ説明つき）
# 枠組み本体を取り出す。
from fastapi import FastAPI

# アプリ全体を作る。
app = FastAPI()

# 住所の後半を {who} という置き場所にする。ここに来た文字が who という名前で渡される。
@app.get("/hi/{who}")
# 置き場所と同じ名前の引数を書くと、その値が自動で入ってくる。
def greet(who):
    # 先頭の f を付けた文字列は、波かっこの中の名前を実際の値に置き換える。
    return f"Hello? {who}?"
# --- localhost:8000/hi/Mom を開いた結果 ---
# "Hello? Mom?"
タカ
タカ師匠注意点。住所の文字列 "/hi/{who}" の波かっこは Python の f文字列ではない。これは FastAPI が「住所のこの位置を who という名前の値とみなす」ためのもの。引数 who をパス関数に自動で渡してくれる。
ハル
ハルなるほど、デコレータの住所とパス関数の引数が名前で結びつくんですね。

HTTPie で試すと、返事の中身と付随情報の両方が見られます。

コードを見る（1行ずつ説明つき）
# 住所の最後に Mom を付けて問い合わせる。この Mom が who に入る。
$ http localhost:8000/hi/Mom
# --- 実行結果 ---
# HTTP/1.1 200 OK
# content-length: 13
# content-type: application/json
# date: Thu, 30 Jun 2022 08:09:02 GMT
# server: uvicorn
#
# "Hello? Mom?"

Requests でも同じことができます。

コードを見る（1行ずつ説明つき）
# 問い合わせ用のパッケージを取り込む。
import requests

# 住所の一部として Mom を含めて問い合わせる。
r = requests.get("http://localhost:8000/hi/Mom")
# 返ってきた中身を Python の値に直して表示する。
print(r.json())
# --- 実行結果 ---
# Hello? Mom?
タカ
タカ師匠いずれも "Mom" が住所の一部として渡されて、greet() の who 引数に入り、返事の文字列の一部になる。返事は JSON の文字列だ。

🔎 具体例：現実の API での使いどころ

ユーザー情報を返す窓口を作るとき、@app.get("/users/{user_id}") と書けば、/users/42 への問い合わせで user_id に 42 が入ります。/users/7 なら 7 です。どのユーザーかを指し示す情報なので、省略できません。省略できない指定はパスに置く、というのが基本の使い分けです。

💡 なぜこれが必要か／これを知ったらできること

  • RESTful の「対象を指し示す」書き方で API が書けるようになる
  • /users/{user_id} のような典型的な住所設計が実装できる

✅ この項のまとめ

  • @app.get("/hi/{who}") の {who} は FastAPI 用の置き場所
  • 同じ名前の引数 who がパス関数で受け取れる
  • 波かっこは f文字列ではない

クエリパラメータ住所のうしろに付ける条件

要するに：クエリパラメータは ?key=value&key2=value2 の形式です。デコレータの住所に置き場所が無い場合、引数はクエリとして解釈されます。

タカ
タカ師匠クエリパラメータは、住所の ? 以降に name=value の形式で並ぶ部分のことだ。& で複数並べられる。

先ほどとの違いは、住所に {who} が無いことだけです。それだけで受け取り方が変わります。

コードを見る（1行ずつ説明つき）
# 枠組み本体を取り出す。
from fastapi import FastAPI

# アプリ全体を作る。
app = FastAPI()

# 住所は /hi だけ。波かっこの置き場所を書いていないのがポイント。
@app.get("/hi")
# 住所に who という置き場所が無いので、FastAPI は「who は ? のあとで渡される」と判断する。
def greet(who):
    # 受け取った値を文章に埋め込んで返す。
    return f"Hello? {who}?"
# --- localhost:8000/hi?who=Mom を開いた結果 ---
# "Hello? Mom?"
タカ
タカ師匠ポイントは、デコレータの住所 "/hi" に {who} が無い、ということ。すると FastAPI は「who はクエリパラメータだろう」と判断する。

HTTPie では、住所にそのまま付ける書き方と、== で指定する書き方の2通りがあります。

コードを見る（1行ずつ説明つき）
# 住所のうしろに ?who=Mom を直接書く書き方。-b は本体だけ表示する指定。
$ http -b localhost:8000/hi?who=Mom
# --- 実行結果 ---
# "Hello? Mom?"

# イコールを2つ重ねると、HTTPie がクエリとして組み立ててくれる。空白で区切れて読みやすい。
$ http -b localhost:8000/hi who==Mom
# --- 実行結果 ---
# "Hello? Mom?"

Requests でも2通りの書き方があります。

コードを見る（1行ずつ説明つき）
# 問い合わせ用のパッケージを取り込む。
import requests

# 住所の文字列にそのまま ?who=Mom を書く方法。
r = requests.get("http://localhost:8000/hi?who=Mom")
# 返ってきた中身を表示する。
print(r.json())
# --- 実行結果 ---
# Hello? Mom?
コードを見る（1行ずつ説明つき）
# 問い合わせ用のパッケージを取り込む。
import requests

# 渡したい条件を、項目名と値の組み合わせとして用意する。
params = {"who": "Mom"}
# params= で渡すと、住所のうしろに ?who=Mom を自動で組み立ててくれる。
# 値に空白や記号が入っていても、正しい形に変換してくれるのでこちらが安全。
r = requests.get("http://localhost:8000/hi", params=params)
# 返ってきた中身を表示する。
print(r.json())
# --- 実行結果 ---
# Hello? Mom?

🔎 具体例：一覧の絞り込みと分割表示

商品一覧を返す窓口で、/items?page=3&per_page=20&category=book のように書けば、「3ページ目を、1ページ20件ずつ、本の分類だけ」という指定になります。どれも省略可能で、省略すれば全件・初期値が使われます。このように「あってもなくてもよい条件」はクエリに置きます。

💡 なぜこれが必要か／これを知ったらできること

  • ページ分割や絞り込み条件を住所に表現できる
  • クエリパラメータをパス関数の引数として自然に書ける

✅ この項のまとめ

  • クエリは ?key=value&key=value の形式
  • 住所に置き場所が無い場合、引数は自動でクエリ扱い
  • HTTPie は ==、Requests は params= で指定

ボディ送るデータの本体／GET では使わない

要するに：ボディは POST や PUT などでデータを送るときの本体です。Body(embed=True) で受け取り、{"who": "Mom"} の形式で渡します。

ハル
ハルボディってのは、リクエストの本体ですよね。
タカ
タカ師匠そう。ただし大事な制約がある。GET にはボディは（基本的に）使わない。
ハル
ハルなんでですか？
タカ
タカ師匠HTTP の GET は冪等（べきとう）であるべきとされている。同じ問い合わせをすれば同じ答えが返ってくる、というルールだ。GET はあくまで「取得」だから、サーバへデータを送るのはボディじゃなくてクエリやパス。
タカ
タカ師匠ボディは作成（POST）、更新（PUT, PATCH）のように、サーバにデータを送るときに使う。第9章では GET でも事実上ボディを使いたい場合の回避策にも触れる。

送られてきた本体の中から who の値を取り出す例です。動詞が get ではなく post になっている点に注目してください。

コードを見る（1行ずつ説明つき）
# 枠組み本体に加えて、本体からデータを取り出すための部品も取り出す。
from fastapi import FastAPI, Body

# アプリ全体を作る。
app = FastAPI()

# get ではなく post。データを送る用の動詞に結びつける。
@app.post("/hi")
# who は文字列で、送られてきた本体の中から取り出す、という指定。
# embed=True は「本体が "Mom" ではなく {"who": "Mom"} の形で来る」という意味。
def greet(who: str = Body(embed=True)):
    # 取り出した値を文章に埋め込んで返す。
    return f"Hello? {who}?"
# --- {"who": "Mom"} を送った結果 ---
# "Hello? Mom?"
タカ
タカ師匠Body(embed=True) は重要。JSON の本体から who の値を取る、ということを FastAPI に伝える。さらに embed=True の意味は、「本体は "Mom" だけじゃなくて、{"who": "Mom"} の形になる」ということ。

HTTPie では、イコール1つで JSON の本体を組み立てます。

コードを見る（1行ずつ説明つき）
# イコール1つで書くと、HTTPie は {"who": "Mom"} という本体を作って送る。
# 本体を伴うので、動詞は自動的に POST になる。-v は送受信の全部を表示する指定。
$ http -v localhost:8000/hi who=Mom
# --- 実行結果（前半は自分が送った内容） ---
# POST /hi HTTP/1.1
# Accept: application/json, */*;q=0.5
# Accept-Encoding: gzip, deflate
# Connection: keep-alive

# Content-Type: application/json  ← 本体が JSON 形式であること
# Host: localhost:8000
# User-Agent: HTTPie/3.2.1
#
# {
#     "who": "Mom"                ← これが送った本体
# }
#
# --- 後半は返ってきた内容 ---
# HTTP/1.1 200 OK
# content-length: 13
# content-type: application/json
# date: Thu, 30 Jun 2022 08:37:00 GMT
# server: uvicorn
#
# "Hello? Mom?"

Requests では json= を使って本体を渡します。

コードを見る（1行ずつ説明つき）
# 問い合わせ用のパッケージを取り込む。
import requests

# post は「データを送る」ための問い合わせ。json= に渡した内容が本体になる。
# このとき「中身は JSON 形式です」という付随情報も自動で付けてくれる。
r = requests.post("http://localhost:8000/hi", json={"who": "Mom"})
# 返ってきた中身を表示する。
print(r.json())
# --- 実行結果 ---
# Hello? Mom?

🔎 具体例：冪等であるとはどういうことか

GET /users/42 は、1回叩いても100回叩いても、ユーザー42の情報が返るだけで、サーバー側の状態は変わりません。だから途中で通信が切れたときに何度でも再試行できますし、返事を保存しておいて再利用することもできます。

一方 POST /users でユーザーを新規作成すると、3回送れば3人できてしまいます。この違いがあるため、状態を変える操作は POST / PUT / PATCH に置き、GET には置かない、という約束になっています。

💡 なぜこれが必要か／これを知ったらできること

  • 「GET でデータ送信」という良くない書き方を避け、適切に POST/PUT を選べる
  • JSON 形式でリクエストの本体を扱う基本が身につく

✅ この項のまとめ

  • GET は冪等であるべき。サーバへの送信はクエリ／パスを使う
  • ボディは POST / PUT / PATCH で使う
  • Body(embed=True) で JSON の本体から引数を取り出す
  • HTTPie は =、Requests は json= で JSON を指定

HTTPヘッダ本体とは別に添える情報

要するに：ヘッダは Header() で受け取れます。FastAPI はヘッダ名を小文字に変換し、ハイフンをアンダースコアに変換します。

タカ
タカ師匠最後の引数の渡し場所、ヘッダだ。ヘッダは付随情報を持つ、項目名と値の組み合わせだ。

添えられた情報の中から who を取り出す例です。

コードを見る（1行ずつ説明つき）
# 枠組み本体に加えて、付随情報を取り出すための部品も取り出す。
from fastapi import FastAPI, Header

@app.get("/hi")

# "Hello? Mom?"

どのメソッドがベストか？置き場所の使い分けの指針

要するに：パスは対象の指定、クエリは省略できる条件、ボディは大きな入力。型ヒントがあれば Pydantic が自動で確認します。

タカ
タカ師匠設計の指針として、こう覚えるといい。①住所に対象の指定を入れる（RESTful の標準）、②クエリはページ分割のような省略できる指定、③ボディは全体または一部のまとまったデータのような大きな入力。
タカ
タカ師匠そしてどの場所であれ、データに型ヒントを付ければ、Pydantic が自動で確認してくれる。引数が存在することと、型が正しいことを保証してくれる。
ハル
ハル「必要な引数が無いときに 422 が返る」みたいな確認も自動なんですね。
タカ
タカ師匠その通り。手で書く確認のコードが激減する。
置き場所用途例
URL パス対象の指定（省略できない）/users/42
クエリ省略できる条件?page=2&sort=new
ボディ大きなまとまったデータ登録するユーザー情報一式
ヘッダ本体とは別の付随情報身分を示す文字列

🔎 具体例：自動で確認されるとはどういうことか

def get_item(item_id: int) と書いた窓口に、/items/abc という問い合わせが来たとします。abc は整数ではないので、パス関数の中身は一度も実行されずに 422 のエラーが返ります。返事には「item_id は整数である必要がある」という内容も含まれます。

型ヒントを書かなければ、この確認は自分で if を書いて実装することになります。書く量が減るだけでなく、書き忘れによる不具合も防げます。

タイプ変換日時も返せる理由

要するに：FastAPI は戻り値を jsonable_encoder() で変換できる形に直してから JSON に変換します。だから日時などもそのまま返せます。

タカ
タカ師匠パス関数は何を返してもいい。初期設定では JSONResponse が使われて、FastAPI が JSON の文字列に変換し、長さと種類の付随情報も自動で付ける。Pydantic のモデルも対象だ。
ハル
ハルPython の json.dumps だと、日時を渡すとエラーになりますよね。
タカ
タカ師匠そう、それを避けるために FastAPI は内部で jsonable_encoder() という処理を使っている。どんなデータ構造でも「JSON にできる」Python のデータに変換してから、通常の json.dumps() を呼ぶ。

「そのままでは変換できない」「間に1つ挟めば変換できる」の2つを確かめるテストです。

コードを見る（1行ずつ説明つき）
# データを JSON の文字列に変換する標準の機能を取り込む。
import json
# 日付や時刻を扱う標準の機能を取り込む。
import datetime
# テストを書くための道具を取り込む。
import pytest
# FastAPI が内部で使っている、変換できる形に直す処理を取り込む。
from fastapi.encoders import jsonable_encoder

# 1つめのテスト：そのまま変換しようとすると失敗することを確かめる。
def test_json_raw():
    # 今の日時を取得する。
    now = datetime.datetime.utcnow()
    # この中で TypeError（種類が違うという失敗）が起きることを期待する、という書き方。
    with pytest.raises(TypeError):
        # 日時をそのまま JSON にしようとすると、扱い方が決まっていないので失敗する。
        json.dumps(now)

# 2つめのテスト：間に変換を挟めば成功することを確かめる。
def test_json_via_encoder():
    # 今の日時を取得する。
    now = datetime.datetime.utcnow()
    # 先に「JSON にできる形」に直す。日時は文字列の形に変換される。
    encoded = jsonable_encoder(now)
    # 直したあとなら、通常の変換が問題なく通る。
    result = json.dumps(encoded)
    # 結果が文字列になっていることを確かめる。
    assert isinstance(result, str)
# --- pytest で実行した結果 ---
# 2 passed in 0.03s
# どちらも期待どおりの動きだった、という意味。

🔎 具体例：日時を含むデータを返す

「登録日時つきのユーザー情報」を返す窓口で return {"name": "ハル", "created": datetime.datetime.utcnow()} と書いたとします。標準の変換だけなら、日時の扱い方が決まっていないため失敗します。FastAPI は間に変換を挟むので、実際には {"name":"ハル","created":"2026-08-01T09:15:30.123456"} のような形で返ります。自分で日時を文字列に直すコードを書く必要がありません。

💡 なぜこれが必要か／これを知ったらできること

  • 日時や Pydantic のモデルを返しても問題なく JSON になる理由が分かる
  • 独自の変換処理に踏み込む準備ができる

✅ この項のまとめ

  • 標準の変換だけだと日時で失敗する
  • FastAPI は jsonable_encoder() で前処理する
  • Pydantic のモデルを含むあらゆる戻り値を JSON にできる

モデル・タイプと response_model入力用・内部用・出力用を分ける

要するに：入力用・内部用・出力用のモデルを分けて、response_model で出力用を指定すれば、外に出してはいけない情報の漏れを防げます。

タカ
タカ師匠大きなアプリでは、同じデータでも「入力用」「出力用」「内部用」と複数のモデルを用意したくなる。
ハル
ハルなんでですか？
タカ
タカ師匠例えば①HIPAA（米国の医療情報保護の法律）に従って、出力から個人情報を取り除く必要がある場合（非識別化という）、②利用者の入力に項目を追加して内部で保存する場合（例：作成日時を自動で付ける）。

同じ「タグ」を、入力用・内部用・出力用の3つの形で定義した例です。項目の数がそれぞれ違います。

コードを見る（1行ずつ説明つき）
# 日時を扱うための機能を取り込む。
from datetime import datetime
# データの形を宣言するための土台を取り込む。
from pydantic import BaseModel

# 利用者が送ってくる形。文字列のタグ1項目だけを受け取る。
class TagIn(BaseModel):
    tag: str

# 内部で保存しておく形。タグに加えて、作成日時と外に出せない値を持つ。
class Tag(BaseModel):
    tag: str
    created: datetime
    # この項目は内部だけで使い、外部には返してはいけない。
    secret: str

# 外に返す形。secret を持たないので、この形で返せば漏れることがない。
class TagOut(BaseModel):
    tag: str
    created: datetime
タカ
タカ師匠TagIn が利用者の入力用、Tag が内部用（secret 入り）、TagOut が出力用（secret を含まない）。
ハル
ハルどうやって「内部の Tag を TagOut に変換して返す」っていうのを書くんですか？
タカ
タカ師匠パスデコレータの response_model という指定を使う。FastAPI が自動で絞り込んでくれる。返したもののうち、response_model で指定した形に無い項目はすべて取り除かれる。

作成と取得の2つの窓口です。取得のほうで response_model を指定しています。

コードを見る（1行ずつ説明つき）
# 日時を扱う機能を取り込む。
import datetime
# 枠組み本体を取り出す。
from fastapi import FastAPI
# さきほど定義した3つの形を取り込む。
from model.tag import TagIn, Tag, TagOut
# データの保存や取得を担当する部分を取り込む。
import service.tag as service

# アプリ全体を作る。
app = FastAPI()

# 作成用の窓口。POST でデータを送ってもらう。
@app.post('/')
# 送られてきた内容を TagIn の形として受け取る。合わない場合は自動でエラーになる。
def create(tag_in: TagIn) -> TagIn:
    # 内部で保存する形を組み立てる。受け取ったタグに、作成日時と内部用の値を足す。
    tag: Tag = Tag(
        tag=tag_in.tag,
        created=datetime.datetime.utcnow(),
        secret="shhhh",
    )
    # 組み立てた内部用の形を保存する。
    service.create(tag)
    # 返すのは受け取った入力そのもの。内部用の値は返さない。
    return tag_in

# 取得用の窓口。response_model で「返すときは TagOut の形に絞る」と指定している。
@app.get('/{tag_str}', response_model=TagOut)
# 住所から受け取った文字を使って、1件を取り出す処理。
def get_one(tag_str: str) -> TagOut:
    # 保存してある内部用の形を取り出す。この中には secret も入っている。
    tag: Tag = service.get(tag_str)
    # secret 入りのまま返しているが、response_model の指定により自動で取り除かれる。
    return tag
# --- 取得の窓口に問い合わせた結果 ---
# {"tag": "python", "created": "2026-08-01T09:15:30.123456"}
# secret は含まれていない。
タカ
タカ師匠get_one の中では Tag（secret 入り）を返しているけど、response_model=TagOut が指定されているので、FastAPI は自動で TagOut の形に絞り込む。結果として secret は相手に届かない。

TagIn（入力用）

tag だけ。利用者から受け取る形。

外 → 中
→

Tag（内部用）

tag + created + secret。保存しておく形。

中だけ
→

TagOut（出力用）

tag + created。secret は含まない。

中 → 外
↺ 内部用の形をそのまま返しても、response_model が出口で自動的に絞り込みます。返し忘れではなく、仕組みで防ぐのがポイントです。

🔎 具体例：手で消す方式との違い

response_model を使わず、返す直前に del tag.secret のように手で消す方法もあります。しかしこの方法だと、窓口が10か所あれば10か所すべてに書く必要があり、1か所でも書き忘れれば漏れます。新しい内部用の項目が増えたときも、全部の窓口を見直すことになります。

response_model=TagOut なら、「返す形は TagOut」と1か所で宣言するだけです。内部用の項目が増えても、TagOut に書かない限り外には出ません。

💡 なぜこれが必要か／これを知ったらできること

  • 「うっかり内部用の項目を返した」という事故を防げる
  • HIPAA や GDPR のような法令の要件に対応しやすい

✅ この項のまとめ

  • 入力用（TagIn）／内部用（Tag）／出力用（TagOut）の分離
  • response_model=TagOut で出力を絞り込む
  • 外に出してはいけない情報の漏れを防ぐ実用的なやり方

第1問FastAPI アプリの3点セット

FastAPI で最小の Web アプリを書くために必要な3つの要素を、自分の言葉で説明してください。Uvicorn での起動方法も含めてどうぞ。

✅ 解答例
①app = FastAPI() でアプリ本体を作る、②@app.get("/...") のようなパスデコレータで住所と HTTP の動詞を宣言する、③パス関数を書いて処理と戻り値を定義する。これらを hello.py などに保存して、uvicorn hello:app --reload で Uvicorn 経由で起動する。
📝 採点ポイント
□ FastAPI() の作成に触れている
□ デコレータで住所と動詞を結びつけることに触れている
□ uvicorn ファイル名:変数名 --reload の形式を説明している
第2問リクエストデータの4つの場所

FastAPI ではリクエストのデータを、4つの場所のどこから受け取れますか？ それぞれに対応する FastAPI のクラス名と、典型的な使い分けを説明してください。

✅ 解答例
①Path（住所の中の置き場所、/users/{id} の {id} など）、②Query（住所の ? 以降、ページ分割のような省略できる絞り込み）、③Body（本体、POST/PUT/PATCH で大きな入力に使う）、④Header（付随情報、身分を示す文字列など）。それぞれ FastAPI の Path, Query, Body, Header で受け取る。
📝 採点ポイント
□ 4つの場所をすべて挙げている
□ それぞれに対応する FastAPI のクラスを書いている
□ 典型的な使い分け（対象／省略可／本体／付随情報）に触れている
第3問GET にボディを使わない理由

なぜ HTTP の GET にはボディを使わないことになっているのですか？「冪等性」というキーワードを使って説明してください。

✅ 解答例
GET は「同じ問い合わせをすれば同じ答えが返る」という冪等性を持つべきとされている。データを取得するための動詞だから、サーバの状態を変えるデータを本体で送るのは目的にそぐわない。代わりにクエリパラメータやパスで条件を指定する。データを送りたい場合は POST（作成）や PUT/PATCH（更新）を使う。
📝 採点ポイント
□ 「冪等性」という言葉を使っている
□ GET はデータ取得用、という役割に触れている
□ データを送るなら POST/PUT/PATCH を使う、という代わりの手段を挙げている
第4問response_model の役割

response_model というパスデコレータの指定は何のためにありますか？ なぜ「内部用モデル」と「出力用モデル」を分けることが重要なのですか？

✅ 解答例
response_model は「外部に返す返事の形」を指定するもの。パス関数が内部用の形（secret などの外に出せない項目入り）を返しても、response_model で出力用を指定しておけば、FastAPI がその項目を自動的に取り除いてくれる。これにより、HIPAA などの要件で個人情報を漏らさない、という実装を仕組みで担保できる。
📝 採点ポイント
□ response_model が返事側の形を指定する役割であることを説明
□ 内部用と出力用を分ける意義（機密情報、法令対応）に触れている
□ FastAPI が自動で絞り込むという動きを述べている
第5問自動ドキュメントの価値

FastAPI の /docs で出てくる自動生成のドキュメントは何ですか？ なぜこの機能が大きな問題を解決すると言えるのですか？

✅ 解答例
/docs には、FastAPI がコードから自動生成した OpenAPI の仕様を基にした、その場で試せる Swagger UI の説明ページが表示される。窓口の一覧、送るデータと返事の形式、試験用の入力欄（Try it out）まで揃う。手で更新する API の説明書は必ずコードとずれて古くなるが、コードから自動生成されるので常に最新の状態が保たれる。窓口が数百に膨れ上がっても、説明が古びない。
📝 採点ポイント
□ OpenAPI / Swagger UI の存在に触れている
□ 「コードから自動生成される」点を強調している
□ 「常に最新であること」「その場で試せること」の価値に触れている
