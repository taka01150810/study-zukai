API Application Programming Interface

プログラムが別のプログラムに用件を伝え、答えを受け取るための窓口。「この形で聞けば、この形で返す」という取り決めのことです。

バックエンド

画面の裏側で動く部分。データを保存したり、計算したり、権限を確認したりします。利用者からは直接見えません。

フロントエンド

利用者が直接見て触る部分。ブラウザの画面やスマホアプリの画面です。

スキーマ schema

データの形の決めごと。「この表には id と name と age という項目があり、age は整数」といった設計図です。

プロトコル protocol

通信のときの手順の取り決め。どんな順番で、どんな形式で送り合うかを決めたものです。

RPC Remote Procedure Call

別のコンピュータにある処理を、自分のプログラムの中の処理と同じ書き方で呼び出す仕組み。裏では通信が起きています。

メッセージング

プログラム同士が小さなデータの塊を送り合う方式。送る側は相手の応答を待たずに次へ進めます。

pub-sub パブリッシュ・サブスクライブ

1つの発信を、それを受け取りたいと登録している複数のプログラムがそれぞれ受け取る方式。全員が同じ内容を受け取ります。

キュー queue

送られたデータを順番に並べておき、待機しているプログラムのうち1つだけが取り出して処理する方式。仕事を分担させたいときに使います。

HTTP

ブラウザとサーバーが会話するときの手順の決まり。「このページをください」「はいどうぞ、状態は200番です」といったやり取りをします。

URL

ウェブ上のどの情報を指しているかを表す住所。https://example.com/users/1 のような文字列です。

REST／RESTful

HTTP をどう使うかの作法。その作法に沿っている状態を RESTful と呼びます。

ステートレス

1回の問い合わせが独立していて、サーバーが前回のやり取りを覚えていない状態。必要な情報は毎回まとめて送ります。

キャッシュ可能

一度取ってきた答えを手元にとっておいて、次に同じものが必要になったときはそれを使える、ということ。

リソース resource

区別して操作できるひとかたまりのデータ。ユーザー、商品、注文などが1つずつリソースです。

エンドポイント／ルート

「どの URL に、どの動詞で送るか」の組み合わせ。URL とプログラムの処理を結びつけるので、ルート（経路）とも呼ばれます。

CRUD

データに対する4つの基本操作、作成（Create）・読み取り（Read）・更新（Update）・削除（Delete）の頭文字です。

クエリパラメータ

URL の後ろに ?key=value の形で付ける追加の指定。並び順や絞り込み条件を伝えるのに使います。

ステータスコード

サーバーが返す3桁の数字。処理がうまくいったか、失敗したか、失敗の原因はどちら側かを表します。

JSON

データを文字列で書き表す形式。{"name": "ハル"} のように、項目名と値を並べて書きます。

JSON:API

「RESTful な API を JSON で書くなら、この構造にそろえよう」という、より細かく決めた仕様のこと。

GraphQL

受け取り側が「この項目だけ欲しい」と指定してデータをもらう方式の API。Meta（旧 Facebook）が作りました。

並行性 concurrency

1つの処理が待たされている間に別の処理を進めて、全体が止まらないようにすること。同時刻に本当に複数動くこととは別です。

並列性 parallelism

複数の処理装置で、本当に同じ瞬間に複数の処理が動いていること。

ビジーウェイト

返事が来るのを待つあいだ、処理装置が何の仕事もせずに待っている状態。この時間が長いほど無駄が大きくなります。

I/Oバウンド

処理時間の大半が、通信やファイル読み書きの返事待ちで占められている処理のこと。

CPUバウンド

処理時間の大半が計算そのものに使われている処理のこと。待ち時間がないので、他の処理に切り替える余地がありません。

イベントループ

「返事が届いたものはないか」を繰り返し確認し、届いたものから処理を進める仕組み。非同期処理の中心にあります。

レイヤー 層

プログラムを役割ごとに分けたまとまり。この本では Web層・サービス層・データ層の3つに分けます。

モデル model

層をまたいでやり取りするデータの形の定義。名前は文字列、年齢は整数、といった決めごとを1か所に書いておきます。

NoSQL／NewSQL

表形式のデータベース以外の保存方式（NoSQL）と、複数台に分散しても表形式のまま扱える新しい方式（NewSQL）です。

ETL

データを取り出し（Extract）、形を整え（Transform）、保存先に入れる（Load）という一連の流れのこと。

サービスとAPI1ファイル時代から、分離とAPIの時代へ

要するに：現代のウェブはバックエンドとフロントエンドに分かれ、その間を API がつなぎます。API の設計はサイトそのものの設計と同じくらい重要です。

ハル
ハル昔の Web サイトって、HTML を書けばできあがり、みたいなイメージなんですけど…今もそうなんですか？
タカ
タカ師匠いい質問だ。昔は PHP と HTML と MySQL の呼び出しを全部1つのファイルに突っ込んで、それで世界に公開できたんだよ。「自分のサイトを友達に自慢する」って遊びだった時代だ。
ハル
ハルえっ、楽しそう。今はもうそういうのは廃れたんですか？
タカ
タカ師匠廃れてはいないけど、サイトが「数百ページ」「数億ページ」と巨大化していくにつれ、1ファイルじゃ管理できなくなった。それで今は、コンテンツ（HTML/JS/画像）と API（プログラム同士をつなぐ仕組み）が別の役割を持つようになったんだ。
ハル
ハルAPI って、よく聞きますけど、結局なんですか？
タカ
タカ師匠API は Application Programming Interface、日本語で言うと「アプリケーション同士が話すための窓口」。たとえば天気アプリが裏で気象庁のサーバーに「東京の今日の天気を教えて」と問い合わせるとき、その問い合わせ口が API だ。
ハル
ハルなるほど、プログラム同士の「話し方の取り決め」みたいな感じですね。
タカ
タカ師匠その通り。そしてもう一つ重要なのが、いまやバックエンド（データベース寄りのサーバー側の処理）とフロントエンド（ブラウザやスマホアプリの画面側）が完全に分かれていることだ。両者の間を埋めるのが API。だから API の設計は、Web サイト本体の設計と同じくらい重要になっている。
ハル
ハル「両方できる人＝フルスタック開発者」って言葉、最近よく聞きます。
タカ
タカ師匠そう、けれど両方の世界が複雑になりすぎて、フルスタックを名乗るのが昔より大変になっているのも事実。ふつうはどちらかに専門化する。だから両者をつなぐ API の「契約」がものすごく大事なんだ。データベースのスキーマと同じく、API も一度決めると変えるのに苦労する。

今：分離してAPIでつなぐ

画面側と裏側を別々に作り、決まった形式のやり取りだけでつなぎます。数億ページ規模でも、担当を分けて開発を進められます。

数億ページ規模

🔎 具体例：天気アプリの中で起きていること

スマホの天気アプリで「東京」を選ぶと、アプリは裏側のサーバーに GET /weather?city=tokyo という問い合わせを送ります。サーバーは {"city":"tokyo","temp":28,"rain":10} のような答えを返します。アプリはこの数字を受け取って、画面に「28℃／降水確率10%」と描きます。画面を描く仕事と気温を調べる仕事が完全に分かれていて、その間の取り決めが city を渡すと temp と rain が返る という API です。

APIの種類ライブラリ呼び出し → RPC → メッセージング

要するに：API は「ライブラリ呼び出し」「RPC」「メッセージング」と歴史的に進化してきました。メッセージングには リクエスト/レスポンス、pub-sub、キューの3パターンがあります。

ハル
ハルAPI っていろんな種類があるって聞きました。
タカ
タカ師匠そうだね。どの API も、次の4つを定義していると思っていい。①プロトコル（通信のルール）、②制御構造（呼び出し方）、③形式（データの並べ方）、④コンテンツの構造（中身のスキーマ）、この4つ。
ハル
ハル種類はどれくらいあるんですか？
タカ
タカ師匠歴史的にいくつかの世代があるんだ。まず昔々、ネットワークが普及する前の API は、ほとんどがライブラリの関数呼び出しだった。「math ライブラリの sqrt 関数を呼んで平方根を求める」みたいな、同じプログラムの中で完結する話。
ハル
ハルネットワークを通らない呼び出しも「API」って呼ぶんですね。
タカ
タカ師匠呼ぶよ。広い意味の API はそういうものも含む。次に、RPC（Remote Procedure Call、リモート手続き呼び出し）が登場した。「別のマシンの関数を、自分のプログラムの中の関数のように呼ぶ」仕組み。今でも gRPC（Google が作った RPC の枠組み）はよく使われる。
ハル
ハル「離れた場所の関数を呼ぶ」って、書き方は同じなのに通信が起きているんですね。
タカ
タカ師匠そう。その仕組みが今のマイクロサービスの土台でもある。さらにメッセージングという方式もあって、これはプロセス間で小さなデータの塊を送り合うやり方だ。
タカ
タカ師匠メッセージには「動詞のような命令（コマンド）」と「名詞のような事実通知（イベント）」がある。よく使われる道具には Apache Kafka、RabbitMQ、NATS、ZeroMQ などがある。

どの API も定義している4要素

📡

① プロトコル

通信のルール。どんな手順でやり取りするか。

🎛️

② 制御構造

呼び出し方。1回きりか、繰り返しか、待つのか待たないのか。

📦

③ 形式

データの並べ方。JSON なのか、別の形式なのか。

🧬

④ コンテンツの構造

中身の決めごと。どんな項目があり、それぞれ何型か。

API の3世代

1

ライブラリの関数呼び出し

同じプログラムの中で完結する呼び出し。ネットワークを通らない。例：平方根を求める sqrt を呼ぶ。

2

RPC（リモート手続き呼び出し）

別のマシンにある処理を、自分の中の関数と同じ書き方で呼ぶ。代表例は gRPC。今のマイクロサービスの土台。

3

メッセージング

プロセス同士で小さなデータの塊を送り合う。命令を表すコマンドと、起きた事実を伝えるイベントがある。代表的な道具：Apache Kafka、RabbitMQ、NATS、ZeroMQ。

通信の3パターン

ハル
ハル通信のパターンにも種類があるんですか？
タカ
タカ師匠あるよ。3つ覚えるといい。①リクエスト/レスポンス：ブラウザがサーバに「ページください」「はいどうぞ」と1対1で会話するスタイル。②パブリッシュ・サブスクライブ（pub-sub）：1つの発信を、受け取りたいと登録している複数のプログラムがそれぞれ受け取って処理する仕組み。③キュー：pub-sub に似ているけど、メッセージを受け取って処理するのは待機している中の1つだけ。仕事を分散して、空いている担当が拾う形だ。
ハル
ハルキューは、届いた仕事が1列に並んでいて、手が空いた人が先頭から取っていく形ですね。
タカ
タカ師匠その理解でいい。実務でよくあるのは、メールの送信や画像の縮小版づくりみたいな「少し時間のかかる裏方処理」をキューに入れておいて、処理担当のプログラムが空いたら取り出す、という使い方だね。
↔️

リクエスト/レスポンス

送った側が答えを待ちます。1つの問いに1つの答え。ブラウザとサーバーの普通のやり取りがこれです。

1対1
📢

pub-sub

1つの発信を、登録している全員がそれぞれ受け取ります。同じ内容が複数の受け手に届きます。

1対多・全員が受け取る
🧾

キュー

並んだ仕事を、待機中のプログラムのうち1つだけが取り出して処理します。同じ仕事が二重に処理されません。

1対多・1つだけが受け取る

🔎 具体例：pub-sub とキューの使い分け

pub-sub が向く場面：「注文が完了した」という事実を、在庫管理・メール送信・売上集計の3つのプログラムに同時に知らせたいとき。3つとも同じ知らせを受け取って、それぞれ別の仕事をします。

キューが向く場面：「この画像の縮小版を作る」という仕事が1日に10万件発生し、処理担当のプログラムを5台動かしているとき。1件の仕事は5台のうち1台だけが取り出します。もし全台が同じ仕事を受け取ってしまうと、同じ画像を5回作ることになり無駄です。

💡 なぜこれが必要か／これを知ったらできること

  • 「すべての API が Web API なわけではない」と知り、設計の幅が広がる
  • 自分のシステムで非同期処理を入れたいとき、キューや pub-sub を選択肢に持てる

✅ この項のまとめ

  • API は4要素（プロトコル／制御／形式／コンテンツ）で定義される
  • 歴史: ライブラリ呼び出し → RPC → メッセージング
  • メッセージングの3パターン: リクエスト/レスポンス、pub-sub、キュー
  • 代表的なメッセージング基盤: Kafka, RabbitMQ, NATS, ZeroMQ

HTTPウェブの3本柱のひとつ

要するに：HTTP はティム・バーナーズ＝リーが提案したウェブの3本柱（HTML, HTTP, URL）の一つで、クライアントとサーバーの通信を担います。

ハル
ハルそれで、Web で使われる API といえば、結局は HTTP ですよね？
タカ

REST（フル）HTTP を「どう使うか」の作法

要するに：REST は HTTP の使い方のスタイルで、ステートレス・キャッシュ可能・リソースベースが特徴です。HTTP の動詞は CRUD に対応します。

ハル
ハル「REST API」って言葉、聞いたことあります。これって HTTP とどう違うんですか？
タカ
タカ師匠REST は HTTP をどう使うかの「スタイル」なんだ。Roy Fielding という人が博士論文で提案した、HTTP の使い方の作法集と思えばいい。
ハル
ハルなんで「REpresentational State Transfer」って呼ぶんですか？
タカ
タカ師匠直訳すると「表現状態転送」。データの状態をある表現形式（たとえば JSON）でやり取りする、という意味合い。よく参照されるけど、誤解されている部分も多い概念だね。
ハル
ハルRESTful っていう言葉も聞きました。それは？
タカ
タカ師匠「REST のお作法に従っている」状態を RESTful と呼ぶ。次の特徴を持つ。①HTTP 上のクライアント／サーバーのやり取りを使う、②ステートレス（各リクエストは独立していて、サーバが過去のやり取りを覚えていない）、③キャッシュ可能（応答を保存して再利用できる）、④リソースベース（操作の対象をリソースとして見る）。
ハル
ハルリソースって何ですか？
タカ
タカ師匠リソースとは「区別して操作できるデータ」のこと。たとえばユーザー、商品、注文。Web サービスは、各リソースに対してエンドポイントを提供する。エンドポイントは「URL と HTTP 動詞の組み合わせ」で、URL が「どのリソースか」を、動詞が「何をしたいか」を表す。
ハル
ハルエンドポイントとルートは同じですか？
タカ
タカ師匠同じものだよ。URL を関数に対応づける（ルーティングする）からルートとも呼ばれる。
ハル
ハルHTTP の動詞って…GET と POST しか知らないです。
タカ
タカ師匠CRUD という言葉を聞いたことはあるかな？ データベースの基本動作 Create/Read/Update/Delete だ。HTTP の動詞はこれにかなり対応している。

RESTful の4つの特徴

🌐

① HTTP を使う

クライアント（呼ぶ側）とサーバー（答える側）が HTTP でやり取りします。

🧊

② ステートレス

1回ごとのやり取りが独立していて、サーバーは前回の続きを覚えていません。必要な情報は毎回まとめて送ります。

💾

③ キャッシュ可能

返ってきた答えを手元にとっておいて、次に同じものが必要になったら再利用できます。

🧱

④ リソースベース

操作の対象（ユーザー、商品、注文）をリソースとして扱い、URL で指し示します。

🔎 具体例：ステートレスだと何が起きるか

ログイン後に「自分の注文一覧」を取りにいくとき、サーバーは「さっきログインしたのは誰か」を覚えていません。そこでクライアントは毎回、身分を示す文字列（トークン）をリクエストに付けて送ります。GET /orders に Authorization: Bearer eyJhbGci... を添える、という形です。おかげでサーバーを10台に増やしても、どの台にリクエストが届いても同じように処理できます。

CRUD と HTTP 動詞の対応

HTTP動詞CRUD意味
POSTCreate作成（書く）
PUTUpdate完全に置き換える
PATCHUpdate部分的に更新
GETRead読み取り／取得
DELETEDelete削除
ハル
ハルPUT と PATCH の違いは？
タカ
タカ師匠PUT は「リソース全部を置き換える」、PATCH は「一部だけ更新」。たとえばユーザー情報の「名前だけ変えたい」なら PATCH、「全項目を新しい値に差し替えたい」なら PUT。

🔎 具体例：PUT と PATCH で結果が変わる場面

今のユーザー情報が {"name":"ハル","age":22,"city":"東京"} だとします。ここに PATCH /users/1 で {"name":"ハル改"} を送ると、結果は {"name":"ハル改","age":22,"city":"東京"} になります。age と city はそのままです。

同じ中身を PUT /users/1 で送ると、全部を置き換える指示なので、結果は {"name":"ハル改"} になり、age と city が消えます。動詞を間違えるとデータが消えるので、ここは区別が重要です。

リクエストとレスポンスの中身

タカ
タカ師匠クライアントが RESTful なエンドポイントに送るリクエストには、データを置く場所が4つある。①ヘッダ（付随情報）、②URL 文字列、③クエリパラメータ（URL の ?key=value の部分）、④ボディ（本体）。
ハル
ハルサーバーが返すレスポンスはどうですか？
タカ
タカ師匠レスポンスは①ステータスコード（整数）、②ヘッダ、③ボディ（空・単一・分割送信）、の組み合わせ。ステータスコードは100番台ずつで分類されている。
📤

リクエストの4か所

①ヘッダ（付随情報。身分証明や希望する形式など）
②URL 文字列（どのリソースか）
③クエリパラメータ（?で始まる絞り込み条件）
④ボディ（送りたいデータ本体）

📥

レスポンスの3要素

①ステータスコード（3桁の整数）
②ヘッダ（付随情報）
③ボディ（空・1つのまとまり・分割して少しずつ送る、のいずれか）

ステータスコードの分類

番号帯意味代表例

200番台成功200 OK, 201 Created
300番台リダイレクション（別の場所へ）301 移動済み, 302 一時移動
400番台クライアント側の誤り404 Not Found, 401 Unauthorized
500番台サーバー側の誤り500 Internal Server Error
ハル
ハル418 ってどこかで見ました…？
タカ
タカ師匠ふふ。418 は「I'm a teapot（私はティーポットです）」という遊び心で入れられた番号。ネットにつながったティーポットがコーヒーを淹れるよう頼まれたときに返す、という冗談の規格だ。
ハル
ハル規格に冗談を入れちゃっていいんですね…
タカ
タカ師匠エンジニアのユーモアだね。RESTful API 設計について書かれた本はたくさんあって、それぞれ役立つ経験則を載せている。本書では、ゆるめの RESTful なやり方を採用する。

🔎 具体例：番号帯を見れば原因の切り分けができる

画面にエラーが出たとき、ステータスコードが 404 なら「送った URL に対応するデータが無い」＝送り先やIDの指定が間違っている可能性が高く、直すのは呼び出し側です。401 なら身分を示す情報が足りていません。一方 500 はサーバー側のプログラムが途中で失敗したという意味なので、呼び出し方を直しても解決しません。番号の百の位を見るだけで、どちらを調べるべきかが決まります。

  • API 設計時に「これは GET か POST か？」と迷ったとき、CRUD の観点で選べる
  • ステータスコードを見て、エラーの原因がクライアント側かサーバー側か即座に判別できる

✅ この項のまとめ

  • REST = HTTP をきれいに使うための設計スタイル
  • 特徴: ステートレス、キャッシュ可能、リソースベース
  • エンドポイント = URL + HTTP動詞
  • HTTP の主要動詞: POST/PUT/PATCH/GET/DELETE は CRUD に対応
  • リクエストはヘッダ、URL、クエリ、ボディの4か所にデータを持てる
  • レスポンスはステータスコード、ヘッダ、ボディから成る

JSONとAPIのデータ形式いまの標準形式

要するに：JSON は JavaScript Object Notation の略で、Web API の標準的なデータ形式です。以前主流だった XML や SOAP に取って代わりました。

ハル
ハルフロントエンドとバックエンドの間でデータをやり取りするって話でしたよね。具体的にはどんな形式で送るんですか？
タカ
タカ師匠いまの標準は JSON（JavaScript Object Notation）。たとえばユーザーのリストはこんなふうに表現する。

下は「ユーザーが2人いる一覧」を JSON で書いたものです。行ごとに何を表しているかを説明しています。

コードを見る（1行ずつ説明つき）
// 角かっこは「複数のものを順番に並べた一覧」を表す。ここから一覧が始まる。
[
  // 波かっこは「1つのまとまり」を表す。ここは1人目のユーザー。
  // id は区別用の番号、name は名前、role は役割。項目名と値をコロンでつなぐ。
  {"id": 1, "name": "ハル", "role": "新人"},
  // カンマで区切って2人目を並べる。項目の並びは1人目とそろえる。
  {"id": 2, "name": "タカ", "role": "師匠"}
// 閉じ角かっこで一覧が終わる。この全体で「2人分のデータ」を表している。
]
// --- このデータの読み方 ---
// 1人目: id=1, name=ハル, role=新人
// 2人目: id=2, name=タカ, role=師匠
ハル
ハルあ、Python の辞書とリストにそっくりですね。
タカ
タカ師匠その通り。JavaScript から生まれた書き方だけど、Python の文法にも似ている。ちょうど「データ構造をやり取りする共通の形式」が必要とされていた時期に登場して、単純さで一気に広まった。
ハル
ハル昔は別の形式だったんですか？
タカ
タカ師匠昔は XML や SOAP という、もっと記述量が多く重い形式が主流だった。JSON はその後継として標準になっていった。本書でも、これ以降はウェブサービスの入出力形式は JSON を前提に話を進めるよ。

🔎 具体例：同じ内容を XML で書くとどれだけ増えるか

上の2人分のデータを XML で書くと、<user><id>1</id><name>ハル</name><role>新人</role></user> のように、項目ごとに開始と終了の2つのタグが必要です。項目名が2回ずつ書かれるので、同じ情報でも文字数が2倍近くになります。通信量が増えるうえ、読み書きの手間も増えます。JSON が広まった理由の1つがこの単純さです。

💡 なぜこれが必要か／これを知ったらできること

  • 普段ブラウザの開発者ツールで「Response」タブを見たときの中身が読める
  • Python の辞書／リストと JSON の対応関係がイメージでき、相互の変換が楽になる

✅ この項のまとめ

  • JSON = データ構造をテキストで表現する標準形式
  • 書き方は Python の辞書／リストに近い
  • 旧来の XML/SOAP に取って代わった

ハル
ハル「JSON:API」って書いてあるのが目に入ったんですけど、これは JSON とは別物？
タカ
タカ師匠いい目のつけどころ。JSON はあくまでデータ形式の話。JSON:API は「RESTful な API の中身を JSON で書くなら、こういう構造にそろえよう」という、より厳しい仕様の提案だ。
ハル
ハルなんで厳しい仕様が必要なんですか？
タカ
タカ師匠ゆるめの REST だと、開発者ごとに「ユーザー一覧の JSON をこう書く／いやこう書く」と揉めることがあるんだ。チームの中でこだわりのぶつかり合いが始まるとき、JSON:API のような厳密な仕様が決着をつけてくれる。
タカ

🔎 具体例：どんな「表記の揺れ」が起きるか

同じ「ユーザー2人の一覧」を返すのに、Aさんは {"users":[...]}、Bさんは {"data":[...]}、Cさんは配列をそのまま [...] と返す、ということが起きます。エラーの返し方も {"error":"not found"}、{"message":"not found"}、{"errors":[{"detail":"not found"}]} と分かれます。受け取る画面側は API ごとに読み取り方を変える必要があり、間違いのもとになります。JSON:API はこの入れ物の形をあらかじめ1つに決めます。

💡 なぜこれが必要か／これを知ったらできること

  • 「API の書き方で揉めている」現場で、厳密な仕様という解決策を提案できる
  • チーム間で標準化が必要になったときの選択肢を持てる

✅ この項のまとめ

  • JSON:API = RESTful API を JSON で書く際の厳密な仕様
  • ゆるめの REST だと表記の揺れが発生する、という問題への解決策
  • 本書はゆるめの RESTful を採用

コンカレンシー（並行処理）待ち時間を無駄にしない

要するに：並行性は「処理装置を空回りさせない」工夫です。通信やファイルの返事を待っている時間に、他の処理を進めます。FastAPI はこれに対応しており、Python の async／await で書けます。

ハル
ハルタカさん、「同時並行性（concurrency）」って言葉、なんかカッコいいけど、いまいち実感がわかなくて…。
タカ
タカ師匠いい疑問。昔の Web サーバーは「同時に何百件の接続をさばけるか」が目標だった。それが10K問題（同時1万接続をどうさばくか）に発展して、今では「同時に何百万接続」が当たり前になっている。
ハル
ハルえええ、何百万…
タカ
タカ師匠そうなると、ただプログラムを書くだけじゃ追いつかない。ここで重要な3つの指標を覚えよう。①遅延（Latency）：1つの応答が返ってくるまでの時間、②待ち時間（Wait time）：何かを待っている時間、③スループット（Throughput）：1秒あたりに処理できるバイト数や件数。遅延と待ち時間は減らしたい、スループットは増やしたい。
ハル
ハル「同時並行性」と「完全な並列性」って、違うんですか？
タカ
タカ師匠違う。これは大事なポイント。並行性 ≠ 並列性。1個の CPU コアで、本当に同時刻に複数の処理が走るわけではない。並行性が目指しているのは、「ビジーウェイト（応答を待って CPU を空回りさせる時間）を減らす」こと。
ハル
ハルビジーウェイト…CPU が何もしないで「まだかな〜」って待ってる状態ですか？
タカ
タカ師匠その通り。CPU は高速だけど、ネットワークやディスクは何千倍〜何百万倍も遅い。だから、ネットワークやディスクに話しかけるたびに、応答が来るまで CPU を何もさせずに置いておくのはもったいない。

3つの指標

⏱️

遅延（Latency）

1つの応答が返ってくるまでの時間。減らしたい

⌛

待ち時間（Wait time）

何かの返事を待っている時間。減らしたい

📈

スループット（Throughput）

1秒あたりに処理できる量や件数。増やしたい

同時接続数の歴史

1

数百接続の時代

「同時に何百件さばけるか」が目標だった。

2

10K問題

同時1万接続をどうさばくかが課題になった。

3

数百万接続が当たり前

順番に書くだけのやり方では追いつかなくなった。

同期と非同期

タカ
タカ師匠ここで同期と非同期の対比を入れよう。通常の Python の実行は同期。コードに書いた順に、一度に1つずつ処理する。一方非同期は、「あることを少しやって、次のことを少しやって、また最初に戻って…」と細切れに進める。
ハル
ハル全部を非同期にすればいいんですか？
タカ
タカ師匠いや、それは違う。CPUバウンド（計算がメインで、ずっと CPU を使う処理）には非同期の余地がない。I/Oバウンド（ネットワークやディスクの応答を待つ処理）のときに、非同期が活きる。
ハル
ハル内部の仕組みはどうなってるんですか？
タカ
タカ師匠非同期の仕組みはイベントループを回している。遅い処理の依頼は「送ったよ、応答が来たら教えてね」と登録するだけで、CPU は別の仕事を進める。ループが一周するたびに応答が来ているか確認して、来ているものから処理する。
ハル
ハル返事待ちの間ずっと止まるんじゃなくて、その間に別の依頼を進めておくんですね。
タカ
タカ師匠そういうこと。10件の問い合わせがそれぞれ1秒の返事待ちをするとき、順番にやれば10秒。返事待ちの間に次を送っておけば、全体は1秒ちょっとで終わる。
タカ
タカ師匠FastAPI は後で見るけど、この非同期処理に対応している。だから一般的な Python の Web フレームワークより、ずっと高速になり得る。ただし、非同期は万能ではない。イベントループの中に重い計算を入れてしまうと、全体が遅くなる。Python の async と await というキーワードや、同期と非同期を混ぜる方法は、後の章で詳しく見るよ。
➡️

同期

書いた順に1つずつ処理します。前の処理が終わるまで次に進みません。返事待ちの間、処理装置は何もしません。

Python の通常の動き
🔄

非同期

返事待ちが発生したら、その間に別の処理を進めます。返事が届いたものから順に続きを処理します。

async / await
🧮

CPUバウンド

処理時間のほとんどが計算そのもの。待ち時間がないので、非同期にしても速くなりません。

非同期は効かない
🌐

I/Oバウンド

処理時間のほとんどが通信やファイルの返事待ち。ここに非同期が効きます。

非同期が活きる

🔎 具体例：10件の外部問い合わせにかかる時間

外部のサービスに10回問い合わせ、それぞれ返事に1秒かかるとします。同期のやり方だと、1件目の返事を1秒待ち、終わってから2件目を送る…を繰り返すので、合計およそ10秒かかります。

非同期のやり方だと、1件目を送った直後に2件目、3件目…と送ってしまい、返事が届いたものから処理します。10件分の待ち時間が重なるので、全体はおよそ1秒強で終わります。ただし、この10件が「外部への問い合わせ」ではなく「10億回の足し算」だった場合、待ち時間が存在しないため、非同期にしても時間は変わりません。

イベントループの動き

1

遅い処理を依頼して、すぐ次へ

「この問い合わせを送った。返事が来たら教えて」と登録するだけで、返事は待たない。

2

別の仕事を進める

登録済みの依頼を放置したまま、次の処理に取りかかる。

3

一周ごとに届いたものを確認

ループが回るたびに「返事が届いた依頼はないか」を確認する。

4

届いたものから続きを処理

届いた順に処理を再開する。

注意：ここに重い計算を入れると、その間ループが止まり、他の依頼の処理も遅れる。

💡 なぜこれが必要か／これを知ったらできること

  • 「FastAPI はなぜ速いのか」を、ループと返事待ちの観点で説明できる
  • async／await を見たとき、「これは何のためのキーワードか」が分かる
  • 同期のコードと非同期のコードを意識的に切り分けられる

✅ この項のまとめ

  • 同時接続数は「数百 → 1万（10K問題）→ 数百万」と進化してきた
  • 並行性 ≠ 並列性。並行性は「ビジーウェイトを減らす」考え方
  • 同期 = 順番に処理、非同期 = イベントループで細切れに処理
  • 非同期が活きるのは I/Oバウンド、CPUバウンドには効かない
  • FastAPI は async/await で非同期処理を扱える

「同時並行性（concurrency）」と「完全な並列性（parallelism）」の違いを、自分の言葉で説明してください。また、非同期処理が活きるのはどんな場面ですか？

✅ 解答例
並列性は本当に複数の処理が同時刻に走ること。並行性は1つの CPU で処理を細切れに切り替えて、結果として「同時に進んでいるように見える」状態を作ること。非同期は CPU が何かを待つ時間（ビジーウェイト）を減らすための仕組みで、ネットワークやディスクなど遅い処理を待つ I/Oバウンドな場面で効果が大きい。計算ばかりの CPUバウンドな処理には効かない。
📝 採点ポイント
□ 並列性と並行性の違いに触れている
□ ビジーウェイトを減らす、という目的を説明している
□ I/Oバウンド と CPUバウンドの区別を意識している
第4問3層アーキテクチャ

Web/サービス/データの3層に分けるのはなぜですか？ 理由を3つ以上、自分の言葉で説明してください。

✅ 解答例
①各層を専門家ごとに分担して書ける、②各層を単独でテストできる、③層を置き換えたり追加したりしやすい（例: gRPC 対応の Web 層を追加できる）、④一度層が混ざると後で分離するのが非常に困難になるから先に分けておく、⑤コードの処理が混ざると、テストを書く人が複数の専門知識を求められてしまうから、などが理由。
📝 採点ポイント
□ 3つ以上の理由を挙げている
□ 「テスト」「置き換え／追加」「専門化」のいずれかに触れている
□ 「一度混ざると分離できない」という保守性の観点に触れている
第5問現代のデータ事情

現代の Web サービスにおいて、データの世界はどう広がっていますか？ 昔のリレーショナルDB一辺倒の時代と比べて、何が変わりましたか？

✅ 解答例
リレーショナルDB だけでなく、NoSQL や NewSQL といった新しいデータの保存先が登場した。さらに機械学習・ディープラーニング・AI が台頭し、Web サービスはモデルへの入出力の窓口としても機能するようになった。データを大規模に扱うための ETL（抽出・変換・ロード）が重要な工程になっている。
📝 採点ポイント
□ NoSQL/NewSQL に触れている
□ 機械学習／AI と Web の関係に触れている
□ ETL という概念に言及している
