デプロイ上に乗せる4つの役割

要するに：本番には「複数の担当 + 見張り + 振り分け + 通信の暗号化」が必要です。

タカ
タカ師匠その上の層の役割は4つ。①動かし続ける：処理が落ちたら起動し直す、②振り分ける：外からの問い合わせをまとめて受け取り、担当に配る、③返事を返す、④暗号化を解く：暗号化された通信を、ここで元に戻す。

🔀

② 振り分ける

問い合わせを、空いている担当に配ります。

📤

③ 返事を返す

担当が作った返事を、外に返します。

🔐

④ 暗号化を解く

暗号化された通信を、ここで元に戻します。

✅ この項のまとめ

複数のワーカーGunicorn + Uvicorn の担当

要するに：gunicorn ... --worker-class uvicorn.workers.UvicornWorker が本番での基本の形です。

タカ
タカ師匠Gunicorn という別の Python のサーバを見たことがあるかもしれない。複数の担当を見張れるけど、これは1件ずつ順に処理する方式のサーバで、FastAPI は非同期の方式が土台だ。
タカ
タカ師匠幸い、Gunicorn から管理できるUvicorn 専用の担当の種類が用意されている。

入れて、4つの担当で起動します。

コードを見る（1行ずつ説明つき）
# 2つのサーバを入れる。角かっこの中は、追加の部品も一緒に入れる指定。
$ pip install "uvicorn[standard]" gunicorn

# main.py の中の app を動かす。
# --workers 4 は、処理の担当を4つ立ち上げる指定。
# --worker-class は、担当の種類を指定する。ここでは非同期に対応した Uvicorn の担当。
# --bind 0.0.0.0:8000 は、外からの接続も受け付ける、という意味。
#   localhost だと同じ機械からしかつながらないが、0.0.0.0 なら外からも届く。
$ gunicorn main:app --workers 4 --worker-class \
    uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000
# --- 実行結果 ---
# [INFO] Starting gunicorn 21.2.0
# [INFO] Listening at: http://0.0.0.0:8000
# [INFO] Booting worker with pid: 12345
# [INFO] Booting worker with pid: 12346
# [INFO] Booting worker with pid: 12347
# [INFO] Booting worker with pid: 12348
# 親が1つ、その下に担当が4つ立ち上がった。担当が落ちても親が起動し直す。
タカ
タカ師匠Gunicorn を動かすと、親の処理が立ち上がり、4つの Uvicorn の担当を管理する。すべてが同じ入口を共有する。main:app は main.py の中の app を指している。
タカ
タカ師匠Gunicorn の説明には「1秒あたり数百〜数千件をさばくには、担当が4〜12あれば十分」とある。

Uvicorn だけでも複数の担当を立てられます。

コードを見る（1行ずつ説明つき）
# --workers 4 で、Uvicorn 自身が担当を4つ立ち上げる。
# ただし、落ちた担当を起動し直す仕組みは持っていない。
$ uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4
# --- 実行結果 ---
# INFO:     Uvicorn running on http://0.0.0.0:8000
# INFO:     Started parent process [12340]
タカ
タカ師匠Uvicorn 自身も複数の担当を立てられるけど、処理の管理ができないので、ふつうは Gunicorn を通す。他にも Uvicorn 用の管理の道具はある。
タカ
タカ師匠これで4つの役割のうち3つ（見張り・振り分け・返事）はまかなえる。通信の暗号化はまだだ。

🔎 具体例：担当を4つにすると何が変わるか

1つの処理単位が同時に扱えるのは、その中の非同期の仕組みが許す範囲までです。計算の重い処理が入ると、その1つが詰まっている間、その担当に届いた問い合わせはすべて待たされます。

担当を4つにすると、1つが詰まっても残り3つが動き続けます。処理装置が4つある機械なら、計算そのものも4か所で同時に進みます。ただし担当ごとにメモリを使うので、増やせば増やすほど良いわけではありません。

✅ この項のまとめ

  • Gunicorn + Uvicorn の担当 が本番での基本
  • 推奨の担当数: 4〜12
  • 通信の暗号化は別に用意する

Dockerひとまとめにして持ち運ぶ

要するに：本番に置くときは、コンテナの形にまとめるのが標準です。短い設定ファイルで済みます。

タカ
タカ師匠Docker は2013年の PyCon で、Solomon Hykes が5分の短い発表で紹介した。それまで Linux のコンテナはほとんど知られていなかった。
タカ
タカ師匠Docker は仮想の機械より速くて軽い。OS 全体を作り直す代わりに、各コンテナはサーバの中心部分を共有し、処理や通信をそれぞれ区切られた範囲に分ける。1台の機械で複数の独立したサービスを動かせて、互いに干渉しない。
タカ
タカ師匠10年経って、Docker は広く知られるようになった。FastAPI のアプリをクラウドに置きたい場合、まずコンテナの型を作る必要があることが多い。FastAPI 公式に詳しい説明がある。
🖥️

仮想の機械

OS をまるごと作り直します。起動に時間がかかり、使うメモリも大きくなります。

📦

コンテナ

OS の中心部分を共有します。起動が速く、使うメモリも小さくて済みます。

今の標準

コンテナの型を作る設定ファイルです。上から順に実行されます。

コードを見る（1行ずつ説明つき）
# 出発点にする型を指定する。Python 3.9 が入った状態から始める。
FROM python:3.9
# この中での作業場所を /code に決める。以降の命令はここを基準にする。
WORKDIR /code
# 必要なパッケージの一覧だけを先にコピーする。
# 先にコピーするのは、コードだけを変えたときに、次の行をやり直さずに済むため。
COPY ./requirements.txt /code/requirements.txt
# 一覧に書かれたパッケージをまとめて入れる。
# --no-cache-dir は、後で使わない一時ファイルを残さない指定。型が小さくなる。
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt
# アプリのコードをコピーする。ここが変わっても、上の pip install はやり直されない。
COPY ./app /code/app
# コンテナが起動したときに実行する命令。
# 0.0.0.0 は外からの接続も受け付ける指定、80 は入口の番号。
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "80"]
タカ
タカ師匠説明すると、①出発点の型、②作業する場所、③必要なものの一覧をコピー、④それらを入れる、⑤アプリのコードをコピー、⑥起動の命令を指定、という順だ。

🔎 具体例：ひとまとめにすると何が解決するか

「自分の機械では動くのに、サーバでは動かない」という状況がよくあります。原因は、Python のバージョンが違う、あるパッケージが入っていない、設定ファイルの場所が違う、などです。

コンテナの型には、Python のバージョンもパッケージも配置も、すべて書かれています。同じ型から作れば、手元でもサーバでも中身は同じです。「動く状態」ごと持ち運べる、というのがこの仕組みの目的です。

✅ この項のまとめ

  • Docker = 軽いコンテナ。OS の中心部分を共有する
  • FastAPI のアプリは、短い設定ファイルで型にできる
  • 公式に詳しい手順がある

パフォーマンス速さの改善の5つの手段

要するに：FastAPI の速さは Python の枠組みの中で最高水準です。さらに改善する手段が5つあります。

タカ
タカ師匠FastAPI の速さは、Python の Web 枠組みの中で最高の水準にある。Go のような速い言語の枠組みと比べても遜色ない。大きな理由は非同期に対応した方式で、返事待ちの時間を無駄にしないことだ。Python 自体は比較的遅い言語なんだけどね。
タカ
タカ師匠全体の速さを上げるための手がかりを順に見ていく。

非同期

タカ
タカ師匠多くの場合、Web サーバはそれほど速くなくていい。問い合わせを受けて結果を返すまでの間に、機能の本体（サービス層）と、データの取得（データ層）が動く。
タカ
タカ師匠コードが返事を待つ必要があるなら、必ず非同期の処理（def ではなく async def）を使う。FastAPI と Starlette が非同期の処理を割り振り、返事待ちの間に他のことを進めてくれる。FastAPI の測定結果が、1件ずつ順に処理する方式の枠組みより優れている理由の1つだ。
タカ
タカ師匠速さには2つの面がある。①1件にかかる時間、②同時に処理できる件数。
⏱️

1件にかかる時間

1つの返事が返るまでの速さ。非同期にしても、これ自体は速くなりません。

📊

同時に処理できる件数

1秒あたり何件さばけるか。非同期はここに効きます。

非同期が効く

キャッシュ

タカ
タカ師匠あまり変わらない元（データベースのめったに変わらない行など）からデータを取る窓口なら、処理の中で結果を手元に置いておくことができる。どの層でもできる。Python 標準の functools に、そのための機能がある。

一度計算した結果を覚えておく書き方です。

コードを見る（1行ずつ説明つき）

# この印を付けると、同じ引数で呼ばれたときに、前の結果をそのまま返す。
# 2回目以降は、中身が実行されない。
@cache
def get_country_name(code: str) -> str:
    # 本来はここでデータベースを調べる。時間がかかる処理だとする。
    return lookup_in_db(code)

# 覚えておく数に上限を付けたい場合は、こちらを使う。
# maxsize=128 なら、直近の128種類まで覚えて、古いものから捨てる。
# 上限がないとメモリを使い続けるので、種類が多い場合はこちらが安全。
@lru_cache(maxsize=128)
def get_area_name(code: str) -> str:

タカ
タカ師匠本書の表では、1件を特定する項目は文字の name だ。表を作るときに指定した。小さな表（本書の規模）では、SQLite は索引を使わず全部の行を見たほうが速いと判断する。けれど100万行の規模になると、索引が無いことは大きな差になる。解決には、どう実行されるかを調べる仕組みを使う。
タカ
タカ師匠小さな表でも、Python のコードや公開されている道具で、データベースに負荷をかけて確かめられる。1件ずつの問い合わせを何度も出しているなら、まとめて出せないか検討する。大きなファイルのやり取りは、一度に全部ではなく、少しずつ送る形を使う。

🔎 具体例：索引の有無で何が変わるか

100万行の表から、条件に合う1行を探すとします。索引が無ければ、先頭から1行ずつ、最大100万回の確認が必要です。1回あたり1マイクロ秒でも、合計1秒かかります。

索引があれば、あらかじめ整理された手がかりをたどって、およそ20回の確認で目的の行に到達できます。100万行でも0.02ミリ秒程度です。表が1000行のうちは差が見えませんが、増えたときに突然現れます。

第1問本番での構成

本番で FastAPI を動かすために、手元の環境（uvicorn 1つ）と比べて追加で必要になる装備を3つ以上挙げて、それぞれの役割を説明してください。

✅ 解答例
①Gunicorn + Uvicorn の担当：複数の担当を動かして並行して処理し、落ちたら自動で起動し直す。②振り分け役（Traefik か nginx）：外からの問い合わせを担当に配り、偏らないようにする。③通信の暗号化（Let's Encrypt の証明書 + Traefik）：暗号化された通信をここで元に戻して、後ろに渡す。④Docker：アプリと必要なものをひとまとめにし、どの環境でも同じ動きにする。⑤クラウド または 自動運用の基盤：実際に動かす場所。増減や立て直しを担当する。
📝 採点ポイント
□ 3つ以上の装備を挙げている
□ それぞれの役割を簡潔に説明している
□ Gunicorn と Uvicorn の組み合わせに触れている
第2問非同期と速さの関係

FastAPI で返事待ちのある処理を async def で書くことが勧められる理由を、速さの観点から説明してください。

✅ 解答例
async def で書くと、FastAPI と Starlette がその処理を非同期に割り振る。返事待ちの間（データベースへのアクセスや外部への問い合わせ）は処理装置を手放し、別の問い合わせを処理できる。これにより、同時に処理できる件数が大きく増える。def のままだと、待っている間ずっと手が空かず、サーバの力を使い切れない。FastAPI が1件ずつ順に処理する方式の枠組みより速い理由の1つがこれ。
📝 採点ポイント
□ 返事待ちの間に他の処理を進められることに触れている
□ 同時にさばける件数が増えることに言及している
□ 1件ずつ順に処理する方式との比較に触れている
第3問問題の調べ方の最初の一手

API で問題が起きたとき、返事の番号から原因をどう切り分けますか？ 404、422、500 それぞれが示す典型的な原因と、最初にすることを説明してください。

✅ 解答例
404：身分の確認の失敗（まだ確認できていない）、権限の不足、または対象が見つからない。身分に関することなら確認の流れを、対象が無いなら住所と指定を確かめる。422：ふつうは形が合っていないという判定。入力の種類、必要な項目、条件への違反が原因。返事の中の detail.loc でどの項目かが分かる。500：サーバ側で失敗が起きている。記録を見て、どこで失敗したかの経路を確かめる。データ層の失敗が受け止められずに上に漏れている場合が多い。
📝 採点ポイント
□ 3つの番号すべてに触れている
□ それぞれの典型的な原因を述べている
□ 最初にすること（記録の確認、detail の確認など）に触れている
第4問速さの手段

FastAPI のアプリを速くするための主な手段を4つ以上挙げて、それぞれどんな詰まりに効くか説明してください。

✅ 解答例
①非同期：返事待ち（データベース、外部への問い合わせ）があるとき、同時にさばける件数が増える。②結果を覚えておく：あまり変わらないデータへの繰り返しのアクセスで、1件の時間が減る。③索引：大きな表への絞り込みの問い合わせが速くなる。④仕事の列：数秒以上かかる処理を後回しにして、返事をすぐ返せる。⑤PyPy / Cython / 別の言語での拡張：計算そのものが重い処理を速くする。⑥Mojo（将来）：Python と同じ書き方のまま、計算の重い処理を大幅に速くする。
📝 採点ポイント
□ 4つ以上の手段を挙げている
□ それぞれが効く詰まりの種類を述べている
□ 非同期／覚えておく／索引／仕事の列 を含んでいる
第5問状況を見る道具

本番の運用で「数値」「見張り」「追跡」を実現する代表的な道具を挙げて、それぞれの役割を説明してください。

✅ 解答例
Prometheus：数値を集める道具。件数、応答時間の分布、失敗の割合などを定期的に取得し、時間の流れとともに保存する。Grafana：集めた数値を、グラフや一覧として表示する道具。異常を知らせる機能もある。OpenTelemetry：1件ごとの内訳の時間を測るための、共通の取り決め。Jaeger などの既存の道具をまとめている。FastAPI 向けの導入の仕組みもある。
📝 採点ポイント
□ Prometheus, Grafana, OpenTelemetry の3つを挙げている
□ それぞれの役割を区別して説明している
□ 数値と追跡の違いに触れている
