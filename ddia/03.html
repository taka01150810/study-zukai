ストレージエンジン storage engine

データベースの中で「保存」と「取り出し」を実際に担う心臓部。倉庫でいう棚入れ・棚出しの仕組みそのもの。

ログ log

追記だけが行われるレコードの並び。倉庫の入庫記録の連番台帳（消さずに足していくノート）。エラーログとは別の広い意味。

インデックス index

欲しいデータの場所を教えてくれる目印。倉庫の所在マップ（どこに何があるかの一覧）。本の巻末索引と同じ。

ハッシュインデックス hash index

「キー→棚番号」を一発で引ける早見表。倉庫の商品番号→棚番号の早見表。

SSTable

キー順に並べて保存したセグメント。倉庫の商品番号順に仕分けした整列棚。

LSMツリー Log-Structured Merge-Tree

メモリに溜めて整列棚に書き出し、裏で統合していく方式。仮置き台→整列棚→棚の合併の流れ。

memtable（メムテーブル）

書き込みを一旦溜めるメモリ上の整列済みの台。倉庫の受付の仮置き台。

Bツリー B-tree

固定サイズのページ（棚板）のツリーをたどってキーを探す方式。ページ式の固定棚。最も広く使われる。

ページ page

Bツリーが読み書きする固定サイズのブロック（通常4KB）。倉庫の1枚の棚板。

コンパクション compaction

同じキーの古い値を捨てて最新だけ残す圧縮整理。倉庫の古い記録を捨てる棚卸し。

マージ merge

複数のセグメント（棚）を1つに統合すること。倉庫の棚の合併。

墓石 tombstone

「このキーは削除した」と示す特別な記録。倉庫の廃棄済みの貼り紙。

WAL write-ahead log

棚を書き換える前に変更内容を先に書いておく追記ログ。倉庫の作業前の予定メモ（事故ったらこれで復元）。

ブルームフィルター bloom filter

「このキーは無い」を高速判定するメモリ効率のよい仕組み。倉庫の「在庫なし」を即答する札。

セカンダリインデックス secondary index

主キー以外でも探せる追加の索引。倉庫の色別・サイズ別の追加マップ。

ヒープファイル heap file

行の実データを置く順序なしの置き場。倉庫の商品本体を置く共通の置き場。

OLTP

ユーザーがキーで少数を低レイテンシで読み書きする使い方。倉庫の1点ずつの出荷・入荷の日常業務。

OLAP

大量レコードをスキャンして集計する分析。倉庫の全在庫を数えて月次レポートを作る棚卸し分析。

データウェアハウス data warehouse

分析専用にデータをコピーした別DB。倉庫の分析専用の別館（読み取り専用の写し）。

ETL Extract-Transform-Load

取り出し→変換→ロードでデータを取り込む流れ。倉庫の各店から在庫を集めて別館に整理して並べる作業。

列指向ストレージ column-oriented

列（品目）ごとにまとめて保存する方式。倉庫の品目ごとにまとめた棚。分析に強い。

マテリアライズドビュー

クエリ結果を実際にディスクへコピーした表。倉庫のよく聞かれる集計を貼り出した掲示板。

あらすじ・要するに・なぜ必要か

この章で何を学ぶのか、最初に地図を持つ

あらすじ

ハルは「保存ボタンを押したらデータはどこにどう置かれているんだろう？」とふと疑問を持ちます。そんな素朴な問いから、カイ先輩との「データベースの中身を覗く冒険」が始まります。たった2行のシェルスクリプトで作る世界一シンプルなデータベースから出発し、なぜ検索が遅くなるのか、どうやって速くするのか、そして「書き込みが得意な仕組み」と「読み取りが得意な仕組み」の違い、さらには「たくさん集計するための特別な置き方」まで、データの保存と取り出しの裏側をじっくりたどっていきます。

🎯 要するに：データベースの仕事は突き詰めると2つだけ。「データを保存すること」と「頼まれたら取り出すこと」。でも速く取り出すには工夫（インデックス）がいる。この章は、その代表である「ログ構造（追記して後で整理）」と「Bツリー（決まった大きさのページで管理）」の2大流派を学び、さらに「ふつうの業務処理（OLTP）」と「大量集計の分析（OLAP）」では最適な保存方法がまるで違うこと、分析には「列ごとにまとめて置く（列指向）」のが効くことを理解する回。

📦 たとえ話：これから「巨大倉庫の棚入れ・棚出し」の話をします

この章を通して、データベース＝巨大倉庫、データ＝商品、書き込み＝棚入れ、読み取り＝棚出し、インデックス＝所在マップに置きかえて読みます。倉庫の仕事も2つだけ。「商品をしまう（棚入れ）」と「頼まれた商品を出す（棚出し）」。そして「どこに何があるか」のマップがなければ、棚出しのたびに倉庫中を端から端まで探すハメになる――この感覚が、この章ぜんぶを貫く合言葉です。

💡 なぜこれが必要か / これを知ったらできること

  • 選べるようになる：自分でストレージエンジンを作ることはなくても、山ほどあるDBから「自分のアプリに合うもの」を選ぶには中身の仕組みを知らないと選べない。
  • 勘で触らない：チューニング設定（パラメータ）を増減すると何が起きるかをイメージできないと、事故る。

3.1

データベースを駆動するデータ構造

世界一シンプルなDBから、なぜインデックスが要るのかを知る
📌 要するに：データベースの仕事は「保存」と「取り出し」。追記だけのログは書き込みが速いが、全件スキャンになるので読み取りが遅い。速く探すにはインデックス（目印）が要る。ただしインデックスは読み取りを速くする代わりに書き込みを遅くするので、必要なものだけ選ぶ。
ハル
新人 ハル先輩、「保存」ボタンを押したデータって、実際どこに、どんな形で置かれてるんですか？ なんとなくDBに入る、としか分かってなくて。
カイ
先輩 カイいい疑問だ。前の章では「アプリ側から見たデータの形」を話したよね。今日は逆。データベースの側に立って、「与えられたデータをどう保存するか」「頼まれたデータをどう見つけるか」を覗いていくよ。
ハル
ハルでも僕、自分でデータベースを作ることなんてないですよ？
カイ
カイ作りはしない。でも選ぶ必要はある。世の中には山ほどストレージエンジンがあって、ワークロードに合わせて選びチューニングしなきゃいけない。特にトランザクション向けと分析向けはまるで別物だからね。
カイ
カイまず、世界で一番単純なデータベースを見せよう。たった2つのBashの関数でできてる。
ハル
ハル2行で……データベースですか？

キーと値を保存する db_set と、取り出す db_get の2つの関数だけ。db_set はファイル末尾に追記し、db_get はそのキーの最後（最新）の行を返します。

世界一シンプルなデータベース（2つのBash関数） 
# 世界一シンプルなデータベース：キーと値を保存し、取り出す2つの関数
#!/bin/bash

# db_set：第1引数(key)と第2引数(value)を「key,value」の形でファイル末尾に追記する
db_set () {
    echo "$1,$2" >> database
}

# db_get：指定キーの行をすべて探し、その中で一番最後（＝最新）の値だけを返す
db_get () {
    grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}
動かしてみる（保存・取り出し・更新） 
# 保存：都市の情報をJSONで保存する
$ db_set 123456 '{"name":"東京","attractions":["東京タワー","スカイツリー"]}'
$ db_set 42 '{"name":"大阪","attractions":["通天閣"]}'

# 取り出し：キー42の最新の値を取得する
$ db_get 42
{"name":"大阪","attractions":["通天閣"]}

# 同じキー42を更新（上書きではなく追記される）
$ db_set 42 '{"name":"大阪","attractions":["海遊館"]}'
$ db_get 42
{"name":"大阪","attractions":["海遊館"]}

# ファイルの中身を見ると、古い値も残ったまま
$ cat database
123456,{"name":"東京",...}
42,{"name":"大阪","attractions":["通天閣"]}
42,{"name":"大阪","attractions":["海遊館"]}
ハル
ハル古いのが残ってるの、無駄じゃないですか？ 上書きすればいいのに。
カイ
カイところがね、これは書き込みがすごく速い。ファイルへの追記はコンピュータにとても効率がいい操作なんだ。この「追記だけが行われるデータファイル」をログ（log）と呼ぶ。
ハル
ハルログって、エラーログのログですか？
カイ
カイ混同しやすいから注意。この本でいうログは「追記だけが行われるレコードの並び」という広い意味。バイナリでプログラムだけが読むものでもログと呼ぶ。
ハル
ハル書き込みは速い。読み取りは？
カイ
カイそこが弱点。db_get はキーを探すたびにファイルの先頭から末尾まで全スキャン。レコード数が n なら検索コストは O(n)。データが増えると目も当てられない。
ハル
ハルじゃあ速く探すには？
カイ
カイそこでインデックス（index, 索引）。本の巻末索引と同じで、目印を横に置いて場所を教えてもらう。インデックスは追加の構造だから、足し引きしてもデータ本体は変わらず、クエリの速さだけ変わる。
ハル
ハルじゃあ全部のキーにインデックスを張ればいいじゃないですか！
カイ
カイそこが大事なトレードオフ。インデックスは読み取りを速くするけど書き込みを遅くする。書くたびにインデックスも更新だからね。だからよくあるクエリパターンを知る人が、必要なところだけ選んで張る。

📦 たとえ話：連番台帳に足すだけの倉庫

このシンプルDBは、商品が来たら入庫記録の連番台帳（ログ）の一番下に行を足すだけの倉庫です。足すだけだから棚入れは超高速。でも所在マップ（インデックス）が無いので、ある商品を出したいときは台帳を上から下まで全部読む（全スキャン）ハメに。商品が2倍になれば探す時間も2倍。だから「どこに何があるか」の所在マップを別に作っておくのです。ただしマップは、棚入れのたびに書き直す手間が増えます。

💡 なぜこれが必要か / これを知ったらできること

  • 「追記は速い」「全スキャンは遅い」という基本感覚が身につき、なぜインデックスが要るかを根本から理解できる。
  • 「インデックス＝読み取り高速化と書き込み低速化のトレードオフ」を知り、無駄なインデックスを張らない判断ができる。

📝 この項のまとめ

  • データベースの最も基本的な仕事は「保存」と「取り出し」。
  • 追記だけのログ（log）は書き込みが効率的。本書のログは「追記のみのレコードの並び」という広い意味。
  • インデックスは元データから導かれる追加構造で、本体は変えずクエリ速度だけ変える。
  • インデックスは読み取りを速くするが書き込みを遅くするので、クエリパターンを知って選ぶ。
3.1.1

ハッシュインデックス

「キー→ファイル内の位置」をメモリの早見表で持つ
📌 要するに：ハッシュインデックスは「キー→ファイル内の位置」をメモリ上の表で持つ方式（Bitcask）。書き込みは追記、ディスクが満杯にならないようセグメント分割＋コンパクション＋マージで整理する。追記設計はシーケンシャル書き込みが速く回復もシンプル。ただし全キーがメモリに収まる必要があり、範囲クエリが苦手。
ハル
ハルインデックスって、具体的にはどう作るんですか？
カイ
カイ一番シンプルなのがハッシュインデックス。多くの言語の「辞書」型は普通ハッシュマップで実装されてる。「このキーはこの場所」と一発で引ける表だ。これをディスク上データの索引に使う。
カイ
カイデータはログに追記していく。それに加えてメモリ上のハッシュマップを持つ。中身は「キー → そのデータがファイルの何バイト目から始まるか（バイトオフセット）」の対応表だ。
ファイルへの追記 + メモリ上のハッシュマップ（イメージ） 
# ファイルへの追記 + メモリ上のハッシュマップ（イメージ）

[データファイル（ログ）]              [メモリ上のハッシュマップ]
0:  123456,{...東京...}              123456 → バイトオフセット 0
64: 42,{...大阪・通天閣...}           42     → バイトオフセット 95（最新の位置）
95: 42,{...大阪・海遊館...}

・書き込み：ファイル末尾に追記し、ハッシュマップのオフセットも更新する
・読み取り：ハッシュマップでオフセットを引き、その場所まで飛んで（シーク）値を読む

📦 たとえ話：商品番号→棚番号の早見表

連番台帳（ログ）に棚入れするのは同じ。でも受付に「商品番号 → 棚の何番地に最新が置いてあるか」の早見表を貼っておきます。棚入れのたびに台帳に足し、早見表の番地も最新に書き換える。棚出しのときは、台帳を全部読まずに早見表を一発で引いて、その棚へ直行するだけ。これがハッシュインデックスです。

ハル
ハルこれって本当に使われてるんですか？
カイ
カイ使われてる。Bitcask（Riakのデフォルトのストレージエンジン）がこの方式。マップを丸ごとメモリに置くから読み書きが速い。ただし全キーがメモリ（RAM）に収まる必要がある。値はディスクにあって1回シークで読めるから、値の総量はメモリより多くてもいい。
ハル
ハルどんなアプリに向いてるんですか？
カイ
カイキーの種類は多くないけど、各キーの値がしょっちゅう更新されるケース。たとえばキーが「猫の動画のURL」、値が「再生回数」。書き込みは大量でも、ユニークなキー（動画の本数）はメモリに収まる。
ハル
ハルでも、追記し続けたらディスクが満杯になりませんか？
カイ
カイいい指摘。だからログをセグメント（区切り）に分ける。ある大きさになったらファイルを閉じて新しいファイルに書く。そして閉じたセグメントにコンパクション（圧縮整理）をかけ、同じキーの古い値を捨てて最新だけ残すんだ。

カイ
カイコンパクションすると重複が消えて小さくなるから、複数のセグメントをマージ（統合）もできる。書き終わったセグメントは変更されない（イミュータブル＝不変）から、マージ結果は新ファイルに書けばいい。しかもバックグラウンドのスレッドでやれて、その間も古いセグメントで読み書きを続けられる。
ハル
ハルセグメントが複数あると、読むときは大変じゃないですか？
カイ
カイ各セグメントがそれぞれ自分のハッシュマップを持つ。探すときは最新のマップから順にたどる。マージのおかげでセグメント数は少なく保たれるから、たどる回数も少ない。

ハルそもそも、なんでわざわざ追記なんですか？ 上書きすればいい気もしますけど。

① 順番に書くから速い

③ 断片化を防ぐ

古いセグメントをマージすることで、ファイルの断片化（フラグメンテーション）を防げる。

ハル
ハルいいことずくめですね。じゃあハッシュインデックスが最強？
カイ
カイいや、制約もある。2つ。①ハッシュテーブルがメモリに収まらないといけない。キーが膨大だとアウト（ディスク上で管理すると大量のランダムI/Oが必要で性能が出にくい）。②範囲クエリが苦手。「kitty00000〜kitty99999まで全部」のような範囲スキャンができず、1キーずつ引くしかない。
ハル
ハルなるほど、キーが多すぎるとダメ、範囲検索もダメ、と。

💡 なぜこれが必要か / これを知ったらできること

  • 「キーが多すぎず、各キーが頻繁に更新される」ワークロードにハッシュインデックス系が向くと判断できる。
  • コンパクション・マージ・墓石・チェックサムといったストレージ実装の定番用語を理解できる。
  • 「範囲検索したいならハッシュインデックスは不向き」と見抜ける。

📝 この項のまとめ

  • ハッシュインデックスは「キー→バイトオフセット」のメモリ上の表。Bitcaskが代表例。
  • セグメント分割＋コンパクション（最新だけ残す）＋マージでディスクを節約。
  • 追記のみ設計の利点：速いシーケンシャル書き込み、シンプルな並行処理・回復、断片化回避。
  • 制約：全キーがメモリに収まる必要、範囲クエリが苦手。
3.1.2

SSTableとLSMツリー

キー順に並べて保存すると、もっと賢くなる
📌 要するに：SSTableは「キー順にソートして保存するセグメント」。マージが簡単・メモリ上のインデックスは疎で済む・圧縮しやすいの3利点。書き込みはメモリ上のmemtableに溜めてソート順でディスクに書き出し（クラッシュ対策に別ログも持つ）、バックグラウンドでマージするのがLSMツリー。LevelDB/RocksDB/Cassandra/HBase/Luceneが代表。存在しないキー検索はブルームフィルターで高速化、コンパクションはsize-tiered/leveledなどの戦略がある。
ハル
ハルさっきのハッシュインデックスの弱点、なんとかなりませんか？
カイ
カイなるんだ。セグメントに条件を1つ足すだけ。「キーでソート（並べ替え）した状態で保存する」というルールを加える。これをソート済み文字列テーブル（Sorted String Table）、略してSSTableと呼ぶ。さらに「1つのマージ済みセグメント内では各キーは一度だけ」も足す（コンパクションが自動で満たす）。
ハル
ハルソートすると、何がうれしいんですか？
カイ
カイ大きな利点が3つある。

利点1：マージが簡単で効率的（マージソート方式）

ファイルがメモリより大きくても平気。複数の入力ファイルの先頭キーを見て、一番小さいキーを出力にコピーするのを繰り返すだけ（マージソートと同じ）。

利点1：ソート済みセグメント同士のマージ 
# 利点1：ソート済みセグメント同士のマージ（マージソート方式）

入力セグメント1: A:1  C:3  E:5
入力セグメント2: B:2  C:9  D:4
                  │
                  ▼ 先頭キーを比べて小さい順に出す
出力セグメント:  A:1  B:2  C:9  D:4  E:5
                          ↑ 同じキーCは「新しいセグメントの値」を優先して残す
ハル
ハル同じキーが両方に出てきたら、どっちを残すんですか？
カイ
カイ各セグメントには「ある期間に書かれた値」だけが入ってる。新しいセグメントの値のほうが最近。マージは隣り合うセグメント同士でやるから、新しいほうを残して古いほうを捨てるだけでいい。

利点2：全キーをメモリに置かなくてよい（疎なインデックス）

handiwork の正確な位置を知らなくても、handbag と handsome の位置を知っていれば、その間にあると分かる。handbag に飛んで読み進めればいい。メモリ上のインデックスは数KBごとに1キーで十分（疎でいい）。

利点2：疎なインメモリインデックス 
# 利点2：疎なインメモリインデックス

[メモリ上の疎なインデックス（数KBごとに1キーだけ）]
  handbag  → オフセット 100
  handsome → オフセット 500

[ディスク上のソート済みセグメント]
  100: handbag,...
       handiwork,...  ← handbag〜handsome の間をスキャンして発見
       handoff,...
  500: handsome,...

（補足）もし全キーと値のサイズが固定なら二分探索ができ、メモリ上のインデックスは不要になる。でも普通はサイズが固定でないので、インデックスがないとレコードの切れ目が分からず難しい。

利点3：圧縮できる

範囲を読むときはどうせ連続した複数レコードを読む。それらをブロックにまとめて圧縮してから書ける。疎なインデックスの各エントリは圧縮ブロックの先頭を指す。ディスク容量もI/O帯域も減る。

📦 たとえ話：商品番号順に並べた整列棚

SSTableは、商品を商品番号順にきっちり並べた整列棚です。①整列棚どうしを合併するのは、両方を端から見比べて小さい番号から並べるだけなので簡単（利点1）。②所在マップは「100番台はこの棚、500番台はあの棚」とざっくり（疎）でOK。間の番号は棚をちょっと歩けば見つかる（利点2）。③隣り合う番号の商品はまとめて梱包・圧縮しておける（利点3）。番号順に並んでいるだけで、いいことが3つも増えるのです。

ハル
ハルいいことだらけですけど……書き込みの順番はバラバラなのに、どうやってキー順に保存するんですか？

SSTableの構築と管理（3.1.2.1）

カイ
カイそこが核心。ディスク上でソートを保つのは大変だけど、メモリ上ならソート済み構造を保つのは簡単。red-blackツリーやAVLツリーといった「バランスのとれたツリー」を使えば、どんな順で入れても読み出しはソート順で取り出せる。
ハル
ハルメモリに溜めて、ソートして、ディスクに書く……？
カイ
カイその通り。流れはこうだ。
1

書き込みは memtable へ

メモリ上のバランスドツリー（red-blackツリーなど）に追加する。このメモリ上のツリーを memtable（メムテーブル） と呼ぶ。

2

閾値を超えたらSSTableに書き出す

memtable が一定サイズ（通常数MB）を超えたらSSTableファイルとしてディスクへ。すでにキー順なので効率よく書ける。これが最新のセグメント。書き出し中の新しい書き込みは別の新しい memtable に受ける。

3

読み取りは memtable → 最新 → 古い…の順

まず memtable、次にディスク上の最新セグメント、その次に古いセグメント…と探す。

4

裏でマージ＆コンパクション

時々バックグラウンドでマージ＆コンパクションを実行し、上書き・削除された値を捨てる。

⚠️ memtableはメモリ上。クラッシュすると、まだ書き出してない分が消える。
ハル
ハルでも memtable はメモリ上ですよね。クラッシュしたら、まだ書き出してない分が消えませんか？
カイ
カイ鋭い。だから保険をかける。ディスク上に別のログを持って、すべての書き込みをそこに即座に追記しておく。このログはソートされてないけど、目的は「クラッシュ後に memtable を復元すること」だけだから問題ない。memtable を無事SSTableに書き出せたら、対応するログは捨てていい。

📦 たとえ話：受付の仮置き台 → 整列棚 → 棚の合併

商品が来たら、まず受付の仮置き台（memtable）に番号順に並べて仮置きします。台がいっぱいになったら、その並びをそのまま整列棚（SSTable）として倉庫に運ぶ。棚出しは、まず仮置き台を見て、無ければ新しい棚→古い棚の順に探す。裏方は空いた時間に古い棚どうしを合併（マージ）して数を減らす。仮置き台が地震（クラッシュ）で崩れても困らないよう、受付の控えノート（別ログ）に来た商品を即メモしておくのです。

SSTableからのLSMツリーの作成（3.1.2.2）

ハル
ハルこの方式、実際の製品で使われてるんですか？
カイ
カイバリバリ使われてる。LevelDB や RocksDB（組み込み用のキー‐バリューライブラリ）がこのアルゴリズム。同じ仕組みは Cassandra や HBase でも使われていて、Googleの Bigtable の論文（SSTable・memtable という言葉はこの論文で登場）から着想を得ている。
ハル
ハルこの仕組み自体に名前はあるんですか？
カイ
カイある。最初に述べたのはPatrick O'Neilらで、以前の log-structuredファイルシステム の上に作られ、Log-Structured Merge-Tree（LSMツリー） と名付けられた。「ソート済みファイルのマージとコンパクション」を土台にするものを LSMストレージエンジン と呼ぶ。
ハル
ハル全文検索とかにも関係しますか？
カイ
カイするよ。ElasticsearchやSolrの全文検索エンジンの Lucene も、語の辞書（term dictionary） を似た方法で保存してる。全文検索ではキーを「語（term）」、値を「その語を含む全ドキュメントIDのリスト（ポスティングリスト）」にして、SSTableに似たソート済みファイルに保存し、必要に応じてバックグラウンドでマージする。

パフォーマンスの最適化（3.1.2.3）

ハル
ハル実用にするには、まだ工夫が要りそうですね。
カイ
カイそう。LSMツリーは「存在しないキーを探すと遅い」弱点がある。無いことを確認するには memtable から一番古いセグメントまで全部調べないといけないからだ。
ハル
ハル「無い」ことを確かめるのに全部見るって、無駄ですね。
カイ
カイだからブルームフィルター（bloom filter）を追加で使う。「このキーはデータベースに存在しない」と高速判定でき、無駄なディスク読み取りを省ける。
ハル
ハルマージのやり方にも種類があるんですか？
カイ
カイコンパクションの順序とタイミングに戦略がある。代表がサイズごと（size-tiered）と階層ごと（leveled）のコンパクションだ。
コンパクション戦略内容採用例
size-tiered（サイズごと）新しく小さいSSTableを、古くて大きいSSTableに次々マージしていく。HBase
leveled（階層ごと）キーの範囲を小さなSSTableに分割し、古いデータを「レベル」へ移す。インクリメンタルにでき、必要ディスク量も少ない。LevelDB・RocksDB（名前の由来）
両方サポート状況に応じて選べる。Cassandra

📦 たとえ話：「在庫なし」を即答する札と、棚の合併ルール

「その商品ありますか？」と聞かれて、無い商品のために全部の棚を歩くのは無駄。だから入口に「うちに無い番号を即答できる札（ブルームフィルター）」を貼り、無ければその場で「ありません」と返します。棚の合併（コンパクション）にもやり方があって、小さい棚を大きい棚へ吸収していく方式（size-tiered）と、番号の範囲ごとに段（レベル）を作って少しずつ整える方式（leveled）があるのです。

カイ
カイ細かい工夫は多いけど、「カスケード（段階的）にSSTableをバックグラウンドでマージしていく」というLSMツリーの基本はシンプルで効率的だ。データがメモリよりずっと大きくても動くし、ソート順だから範囲クエリも効率的、書き込みはシーケンシャルだから書き込みスループットも高い。

💡 なぜこれが必要か / これを知ったらできること

  • CassandraやHBaseなどLSM系DBが「書き込みに強い」理由を、memtable＋シーケンシャル書き込みの観点で説明できる。
  • 「存在しないキーの検索が遅い→ブルームフィルター」という最適化の発想を持てる。
  • size-tiered/leveledコンパクションの違いを理解し、運用チューニングの文脈を読める。

📝 この項のまとめ

  • SSTable＝キー順ソート済みセグメント。マージ容易・疎インデックス可・圧縮可の3利点。
  • memtable（メモリ上のバランスドツリー）に溜め、閾値で SSTable として書き出す。クラッシュ対策に別ログ。
  • この仕組みがLSMツリー。LevelDB/RocksDB/Cassandra/HBase/Lucene などが採用。
  • 存在しないキー検索はブルームフィルターで高速化。コンパクションは size-tiered / leveled 戦略。
  • メモリより大きくても動き、範囲クエリと書き込みスループットに強い。
3.1.3

Bツリー

最も広く使われる「ページ式の固定棚」
📌 要するに：Bツリーは最も広く使われるインデックスで、データを固定サイズのページに分け、ページのツリーをたどってキーを探す（深さは O(log n)、通常3〜4レベル）。挿入で満杯になればページ分割。LSMと違い「その場で上書き」するため、クラッシュ対策にWAL、並行制御にラッチが要る。最適化にはコピーオンライト、キーの短縮（B+ツリー）、リーフの連続配置などがある。
ハル
ハルLSMツリーが一番よく使われてるんですか？
カイ
カイいや、それが意外。log-structuredも広まってきてるけど、最も広く使われているのはBツリー。1970年に登場して10年経たずに「普遍的」と呼ばれた。ほぼすべてのリレーショナルDBの標準実装で、多くの非リレーショナルDBでも使われている。
ハル
ハルSSTableと同じ「キー順ソート」なんですか？
カイ
カイそこは同じ。キー検索も範囲クエリも効率的。でも設計哲学は全然違う。LSMは可変サイズのセグメント（数MB以上）を常にシーケンシャルに書く。Bツリーは固定サイズのブロック（ページ）（通常4KB）に分け、1ページ単位で読み書きする。ディスクも固定サイズのブロックの並びだから、ハードウェアと相性がいい。
カイ
カイ各ページにはアドレス（場所）があって、別のページを参照できる。メモリのポインタに似てるけど、ディスク上の話だ。これでページのツリー（木構造）を作る。
Bツリーでキー251を探す 
# Bツリーでキー251を探す（分岐係数の例）

            [ルートページ：境界 100 / 200 / 300 / 400 / 500]
                              │ 200〜300 を担当する子へ
                              ▼
            [中間ページ：境界 200 / 250 / 270 / 300]
                              │ 250〜270 を担当する子へ
                              ▼
            [リーフページ：251 → 値, 255 → 値, 268 → 値 ...]
                              ↑ ここに値そのもの、または値への参照がある
カイ
カイ出発点がルートページ。各ページに複数のキーと、子ページへの参照が入ってる。子はそれぞれ「キーの連続した範囲」を担当し、参照と参照の間のキーが境界。251なら200と300の境界の間をたどり、細かい範囲へ降りて、最後にリーフページに着く。リーフにはキーの値そのものか、値があるページへの参照が入っている。
ハル
ハル1ページから何個の子に分かれるんですか？
カイ
カイそれを分岐係数（branching factor）と呼ぶ。ページに収まる量しだいで、通常は数百になる。
ハル
ハル新しいキーを追加したいときは？
カイ
カイそのキーの範囲を担当するリーフページを探して追加。空きがなければページを2つに分割して半分ずつ入れ、親ページを新しい範囲に合わせて更新する。既存キーの値更新なら、リーフを探して書き換え、ディスクに書き戻すだけ（場所は変わらず参照そのまま）。
ページ分割でBツリーを大きくする 
# ページ分割でBツリーを大きくする
[満杯のリーフ：333,337,344,...,366]  ← もう入らない！
                │ 350 のあたりで分割
                ▼
[リーフ前半：333,337,344]   [リーフ後半：350,366,...]
        ＼              ／
         [親ページに新しい境界 350 を追加して更新]
カイ
カイこの分割のおかげでツリーは常にバランスが保たれる。だから n 個のキーを持つBツリーの深さは常に O(log n)。実際ほとんどのDBで深さは3〜4レベル。ページ4KB・深さ4・分岐係数500なら最大256TBも保存でき、少ないページ参照で目的に着ける。

（補足）新しいキーの挿入はほぼ直感的だけど、ツリーのバランスを保ちながらキーを削除するのは、少し手の込んだ処理になる。

📦 たとえ話：番号順の「ページ式の固定棚」を案内板でたどる

Bツリーは、棚板1枚を固定サイズ（ページ）にした倉庫です。入口の大案内板（ルート）に「100番台は左、200番台は中央…」。中央へ行くと中案内板「250番台はこっち」。最後に商品棚（リーフ）に着く。案内板を3〜4回たどるだけで目的の商品に着けます。棚が満杯なら、その棚を2つに割って案内板に新しい区切りを足す（ページ分割）。だから倉庫がどれだけ大きくなっても、歩く回数はほぼ変わらないのです。

Bツリーの信頼性を高める（3.1.3.1）

ハル
ハルBツリーは「その場で上書き」するんですよね。LSMの追記と違って。
カイ
カイそう。基本操作は「ディスク上のページを新しいデータで上書き」。場所は変わらず参照もそのまま。追記だけのLSMとは対照的だ。磁気ディスクならヘッドを動かして上書き、SSDなら大きなブロックを消してから書き直すのでもっと込み入る。
ハル
ハル上書き中にクラッシュしたら、どうなるんですか？
カイ
カイ危険。ページ分割が起きると、分割した2ページと親ページの複数を上書きしないといけない。途中でクラッシュすると「どこからも参照されない孤児ページ」ができてインデックスが壊れることがある。
ハル
ハルどう守るんですか？
カイ
カイWAL（write-aheadログ、redoログ）を持たせる。追記のみのファイルで、Bツリー本体を変更する前にすべての変更を先に書く。クラッシュ後はこれでBツリーを整合状態に戻す。
ハル
ハル複数スレッドが同時にアクセスしたら混乱しませんか？
カイ
カイするから、ラッチ（latch, 軽量なロック）でツリーを保護する。この点ではLSMのほうがシンプル。LSMはマージを全部バックグラウンドでやってクエリを邪魔せず、古いセグメントをこっそり差し替えるだけだからね。

📦 たとえ話：棚を書き換える前の「作業予定メモ」と棚ごとの整理券

固定棚は商品をその場で上書きするので、棚の入れ替え中に停電すると棚がぐちゃぐちゃに。だから書き換える前に「これからこう動かす」という予定メモ（WAL）を別ノートに書いておき、停電しても予定メモから元に戻せるようにします。さらに同じ棚を二人が同時にいじらないよう棚ごとに整理券（ラッチ）を配るのです。

Bツリーの最適化（3.1.3.2）

最適化内容
コピーオンライトWALの代わりに、変更ページを別の場所に書き、親の新バージョンを作って新しい場所を指す（LMDBなど）。並行処理制御にも有益。
キーの短縮範囲の境界に十分な情報だけ保存しキー全体を省く。1ページに多くのキーが入る＝分岐係数が大きく、深さが減る。この変種をB+ツリーと呼ぶこともある。
リーフページを連続配置範囲スキャンを速くするためリーフをディスク上で順に並べようとする。ツリーが育つと維持は難しい（LSMはマージ時に書き直すので容易）。
隣接ページへのポインタ各リーフに左右の隣ページへの参照を持たせ、順スキャン時に親に戻らなくて済む。
フラクタルツリーlog-structuredの考えを一部取り入れディスクシークを減らすBツリーの変種（名前に反しフラクタルとは無関係）。

💡 なぜこれが必要か / これを知ったらできること

  • 一般的なRDBのインデックスがBツリーだと理解し、「深さが浅いから少ないディスクアクセスで引ける」感覚を持てる。
  • WALやラッチが「クラッシュ耐性」「並行処理」のために要ることを説明できる。
  • 分岐係数・ページサイズと保存可能量の関係をイメージできる。

📝 この項のまとめ

  • Bツリーは固定サイズページのツリー。キー順・範囲クエリ可、深さ O(log n)（通常3〜4レベル）。
  • 分岐係数は通常数百。満杯時はページ分割でバランス維持。
  • その場で上書きするためWAL（write-aheadログ）でクラッシュ耐性、ラッチで並行制御。
  • 最適化：コピーオンライト、キー短縮（B+ツリー）、リーフ連続配置、隣接ポインタ、フラクタルツリー。
3.1.4

BツリーとLSMツリーの比較

LSMは書き込み、Bツリーは読み取り ― でも実測が大事
📌 要するに：大まかにLSMは書き込みが速く、Bツリーは読み取りが速い。LSMの利点は高い書き込みスループット・小さいファイル・SSDでの有利さ。マイナス面はコンパクションが高パーセンタイルのレスポンスを悪化させ得ること、書き込み帯域をコンパクションと共有し追いつかないと破綻し得ること。Bツリーはキーが1カ所にあり強いトランザクションに向く。結局は自分のワークロードで試して選ぶ。
ハル
ハル結局、BツリーとLSM、どっちがいいんですか？
カイ
カイざっくり「LSMは書き込みが速い、Bツリーは読み取りが速い」と見なされてる。LSMの読み取りが遅くなりがちなのは、いろんなコンパクション段階の複数のデータ構造やSSTableを調べないといけないからだ。
ハル
ハルじゃあLSMは書き込み重視、Bツリーは読み取り重視で決まり？
カイ
カイそう単純じゃない。ベンチマークはワークロード次第でブレるから、結局は自分のワークロードで実際に試すしかない。とはいえ判断材料はあるから整理しよう。

LSMツリーの利点（3.1.4.1）

カイ
カイまずキーワードは書き込みの増幅（write amplification）。Bツリーは最低2回書く（WAL＋ツリー本体）。ページ分割でさらに増え、数バイトの変更でもページ全体を書く。LSMはコンパクションとマージでデータが複数回書き直される。
カイ
カイ書き込みの増幅は、特に「上書き回数に上限があるSSD」で問題になる。書き込みが多いアプリでは、ディスクへの書き込み速度がボトルネックになり、増幅がそのまま性能コストになるんだ。
ハル
ハルで、LSMの利点は？
カイ
カイ3つ。①書き込みスループットが高い、②ファイルが小さくなる、③SSDでも有利だ。
✍️

① 高い書き込みスループット

増幅が低めになる場合があり、複数ページ上書きが不要でコンパクトなSSTableをシーケンシャルに書くだけ。特に磁気HDDで有利。

🗜️

② ファイルが小さい

圧縮率を高められ、Bツリーのような断片化（未使用領域）が少ない。定期的に書き直して断片化を除去（特にleveled）。

💾

③ SSDでも有利

増幅と断片化を抑えると、I/O帯域内で処理できる読み書き数が増える。

カイ
カイSSDの多くはファームウェアが内部的にlog-structuredで、ランダム書き込みでも下層では順番に書く。それでも増幅と断片化を抑えるのはSSDでもメリットがあるんだ。

LSMツリーのマイナス面（3.1.4.2）

ハル
ハル逆にLSMの弱点は？
カイ
カイ大きいのはコンパクションが実行中の読み書きに影響すること。重いコンパクションが終わるまでリクエストがディスク待ちになりやすく、平均は小さくても高いパーセンタイルのレスポンスタイム（1章のp99など）がすごく悪化することがある。その点Bツリーは挙動が予測しやすい。
カイ
カイもう1つ。ディスクの書き込み帯域は「元々の書き込み（ログとmemtableのフラッシュ）」と「バックグラウンドのコンパクション」で共有される。DBが大きくなるほどコンパクションに必要な帯域が増える。
ハル
ハルコンパクションが追いつかなくなったら？
カイ
カイ未マージのセグメントが増え続けてディスクが満杯になり、読み取りも遅くなる。しかも普通SSTable系は「追いついてなくても書き込みを受け付け続ける」から、自分で明示的にモニタリングして検出しないといけない。
ハル
ハルBツリー側の利点も改めて教えてください。
カイ
カイBツリーは各キーがインデックス中の1カ所にしかないのが利点。LSMは同じキーのコピーが複数セグメントに散らばりうる。1カ所だからBツリーは強いトランザクションに向く。多くのRDBはトランザクション分離をキー範囲のロックで実装していて、Bツリーならそのロックを直接ツリーに付けられる（7章）。
ハル
ハル結論、どっちを選べば？
カイ
カイBツリーは深く根づいてて多くのワークロードで安定して速いから当分廃れない。新しいデータストアではlog-structuredが広まりつつある。簡単なルールはないから、実際に試して決めるのが正解だ。

📦 たとえ話：合併中の倉庫は通路が混む／品物は1カ所派と分散派

整列棚の倉庫（LSM）は、商品をどんどん搬入するのは得意。でも裏方が大量の棚を合併（コンパクション）している最中は通路が荷物でふさがり、ときどき棚出しが極端に遅くなる（高パーセンタイルの悪化）。しかも搬入路と合併路が同じなので、合併が追いつかないと倉庫がパンクするから、見張りが要ります。固定棚の倉庫（Bツリー）は、同じ商品が必ず1カ所にあるので、棚に「貸出中の鍵（範囲ロック）」をかけやすく、厳密な貸出管理（トランザクション）に向くのです。

💡 なぜこれが必要か / これを知ったらできること

  • 「書き込みの増幅」という概念で、SSD寿命や書き込み性能の話を理解できる。
  • LSM採用時に「コンパクションが追いついているか」を監視すべきだと判断できる。
  • トランザクション重視ならBツリー系という選定の勘所を持てる。

📝 この項のまとめ

  • 一般にLSM＝書き込み高速、Bツリー＝読み取り高速。ただしワークロード次第なので実測が必要。
  • LSMの利点：高書き込みスループット、小さいファイル（断片化少）、SSDでも有利。
  • LSMのマイナス面：コンパクションが高パーセンタイルのレスポンスを悪化、書き込み帯域の共有で追いつかないと破綻（要監視）。
  • Bツリーはキーが1カ所にあり、強いトランザクション（範囲ロック）に向く。
3.1.5

その他のインデックス構造

セカンダリ・値の置き場・複合・曖昧・インメモリ
📌 要するに：キー‐バリューインデックス（主キー相当）以外にも、セカンダリインデックス（重複キー対応）、値をどこに置くか（ヒープファイル／クラスタ化／カバーリング）、複数列の連結インデックスや地理向けの多次元インデックス、スペルミスに対応する曖昧（全文検索）インデックスがある。さらにRAMが安くなりインメモリDBが発展。速さの本当の理由はエンコード手間の削減。
ハル
ハルここまでのインデックスって、全部「キー→値」でしたよね。
カイ
カイそう、これはリレーショナルモデルのプライマリキー（主キー）のインデックスにあたる。プライマリキーはテーブルの1行・1ドキュメント・1頂点をユニークに特定する。他のレコードはプライマリキーでそれを参照し、インデックスが参照を解決する。
ハル
ハル主キー以外で検索したいときは？
カイ
カイそこでセカンダリインデックス（二次索引）。RDBなら CREATE INDEX で1テーブルに複数張れる。効率的な結合（join）に欠かせない。user_id 列に張れば、同じユーザーの行を全部見つけられる。
ハル
ハルプライマリキーと作り方は違うんですか？
カイ
カイほぼ同じ。主な違いは「キーがユニークじゃない」こと。同じキーの行が大量にあり得る。対処は2通りで、どちらもBツリーでもlog-structuredでも使える。
📋

対処1：リスト化

インデックスの各値を「マッチする行の識別子のリスト」にする（全文検索のポスティングリスト風）。

🔑

対処2：キーをユニーク化

各キーに行の識別子を足して、キー自体をユニークにする。

インデックスへの値の保存（3.1.5.1）

ハル
ハルインデックスで引いた先には、何が入ってるんですか？ 値そのもの？
カイ
カイ2種類ある。①探していた実際の行そのもの、②行が保存されている別の場所への参照。②の置き場をヒープファイル（heap file）と呼ぶ。中身は順序なし。
ハル
ハルなんでわざわざ別の場所（ヒープ）に置くんですか？
カイ
カイセカンダリインデックスが複数あるとき、データが何重にも複製されるのを避けられる。各インデックスはヒープ内の場所を指すだけで、実データは1カ所にまとまる。
ハル
ハル値を更新するときは効率いいんですか？
カイ
カイキーを変えない更新で、新しい値が古い値より大きくなければその場で上書きできて効率的。でも大きくなったら、空きのある場所へ移動が必要で複雑になる（全インデックスを更新するか、元の場所に引っ越し先ポインタを残す）。
ハル
ハル参照を1回挟むのって、遅くなりませんか？
カイ
カイその「インデックス→ヒープ」のホップが負担になりすぎる場合は、行データを直接インデックスの中に入れる。これをクラスタ化インデックス（clustered index）と呼ぶ。MySQLのInnoDBはプライマリキーが必ずクラスタ化で、セカンダリはプライマリキーを参照する。SQL Serverはテーブルごとに1つ指定できる。
ハル
ハル全部入れるか、参照だけか、の中間はないんですか？
カイ
カイある。カバーリングインデックス（covering index）。テーブルの一部の列だけをインデックスに入れ、一部のクエリはインデックスだけで答えられる（クエリを「カバーする」）。
ハル
ハルいいことばかりですか？
カイ
カイデータ複製の常で、読み取りは速いけどストレージは余分に要り、書き込みにオーバーヘッド。複製の不整合を防ぐ必要もあり、トランザクション保証の負担も増える。

📦 たとえ話：所在マップに「番地だけ」書くか「商品も貼る」か

色別・サイズ別の追加マップ（セカンダリインデックス）を作るとき、3つのやり方があります。①マップには番地だけ書いて、商品本体は共通の置き場（ヒープ）に1つだけ置く。②マップに商品そのものを貼り付けてしまう（クラスタ化＝歩かず即取れるが場所を食う）。③よく聞かれる情報だけマップに添える（カバーリング）。便利になるほど、貼り替えの手間と置き場が増えるトレードオフです。

複合インデックス（3.1.5.2）

ハル
ハル複数の列をまとめて検索したいときは？ 1キーのインデックスじゃ足りませんよね。
カイ
カイ最も一般的なのが連結インデックス（concatenated index）。複数フィールドをくっつけて1つのキーにする（順番は定義で指定）。紙の電話帳が (姓, 名) から電話番号への索引なのと同じだ。
ハル
ハル電話帳だと、何ができて何ができないんですか？
カイ
カイ(姓, 名) の順なら「特定の姓を全部」「姓＋名の組み合わせ」は引ける。でも「特定の名を持つ人を全部」は引けない。順番が効くんだ。
ハル
ハル地図でレストランを矩形範囲で探すような検索は？
カイ
カイそれは多次元インデックス（multi-dimensional index）の出番。地理空間データで重要だ。緯度・経度を持つレストランを、地図上の四角の中で探す。
地図上の四角い範囲内のレストランを探す（2次元の範囲クエリ）

SELECT * FROM restaurants
  WHERE latitude  > 51.4946 AND latitude  < 51.5079
    AND longitude > -0.1162 AND longitude < -0.1004;
カイ
カイ普通のBツリーやLSMだと、これは効率的に答えられない。「緯度の範囲だけ」か「経度の範囲だけ」は答えられても、両方同時は無理なんだ。
ハル
ハルどう解決するんですか？
カイ
カイ1つは空間充填曲線で2次元を1つの数値に変換してから普通のBツリーを使う方法。もっと広く使われるのはRツリーのような専用の空間インデックス。PostGISはPostgreSQLのGiST（汎用検索ツリー）を使ってRツリーとして実装している。
ハル
ハル多次元って、地図専用ですか？
カイ
カイいや、面白いことに地理以外にも使える。ECで (赤, 緑, 青) の3次元で特定の色の範囲の製品を探したり、気象に (日付, 気温) を持たせて「2013年で気温25〜30度の日を全部」を探したり。1次元だと2013年を全部スキャンしてから気温でフィルタになるけど、2次元なら同時に範囲指定できる（HyperDexの手法）。

📦 たとえ話：「姓→名」順の名簿と、地図グリッドの所在マップ

連結インデックスは、倉庫の名簿を「メーカー → 型番」の順で作るようなもの。メーカーで全部、メーカー＋型番でピンポイントは引けるが、型番だけでは引けません。多次元インデックスは、倉庫の床に碁盤の目（グリッド）の所在マップを敷くイメージ。「この四角いエリアにある商品ぜんぶ」を縦横同時に絞り込めるのです。

全文検索と曖昧インデックス（3.1.5.3）

ハル
ハルここまでのインデックスは、キーがピッタリ一致しないとダメですよね。スペルミスとかは？
カイ
カイそう、これまでは「厳密な値」か「ソート順の範囲」が前提。スペルミスみたいな「似ているキー」は探せない。そういう曖昧（fuzzy）なクエリには別の手法が要る。
ハル
ハルたとえば？
カイ
カイ全文検索エンジンなら、同義語を含めたり、文法的な語形変化を無視したり、近くの複数語を探したりできる。誤字対応として、Luceneは「編集距離（edit distance）が一定以内の語」を探せる。編集距離1なら、1文字の追加・削除・置換で一致する。
ハル
ハル仕組みは前のSSTableと関係ありますか？
カイ
カイする。Luceneは語の辞書にSSTableに似たソート済みファイルを使う。LevelDBではインデックスが「疎なキーのコレクション」だったけど、Luceneではtrie（トライ）に似た「文字に対する有限状態オートマトン」になっていて、編集距離内の語を効率的に探せるレーベンシュタインオートマトンに変換できる。
ハル
ハルもっと賢い曖昧検索もありますか？
カイ
カイあるよ。ドキュメントの分類や機械学習の方向に進む手法もある。詳しくは情報抽出の教科書を見てくれ。

📦 たとえ話：商品名のスペル違いでも見つける棚案内

普通の所在マップは「商品名がぴったり一致」しないと引けません。でも倉庫の検索係が賢ければ、「1文字違いの似た名前」でも候補を出してくれる（編集距離）。商品名を1文字ずつたどる賢い索引（trie／オートマトン）を持っているから、打ち間違いにも対応できるのです。

全データのメモリでの保持（3.1.5.4）

ハル
ハルここまで全部「ディスクにどう置くか」の話でしたよね。そもそも全部メモリに置けないんですか？
カイ
カイいいところに来た。ここまでは全部「ディスクの限界」への回答だった。でもディスクには2つの利点がある。①永続性（電源を切っても消えない）、②安さ（RAMよりGBあたりが安い）。ところがRAMが安くなって②の優位は薄れ、多くのデータセットは全部メモリに載せられるようになった。これがインメモリデータベースの発展につながった。
ハル
ハルメモリに置いたら、電源が切れたら消えちゃいませんか？
カイ
カイ用途による。Memcachedみたいに「キャッシュ専用で再起動で消えてOK」なものもある。でも耐久性を目指すインメモリDBもあって、バッテリ駆動RAMや、変更ログをディスクに書く、定期スナップショット、他マシンへのレプリケーションで実現する。再起動時はディスクやレプリカから読み直す。
ハル
ハルディスクに書くなら、結局ディスクDBと同じでは？
カイ
カイいや、読み込みはすべてメモリからやる。ディスクは「永続化のための追記ログ」を書くためだけ。だからやっぱりインメモリDBなんだ。製品ではVoltDB、MemSQL、Oracle TimesTenがリレーショナルなインメモリDB。RAMCloudは耐久性を持つキー‐バリュー。RedisやCouchbaseは非同期書き込みで弱い耐久性を提供する。
ハル
ハルインメモリが速いのは、ディスクを読まなくていいからですよね？
カイ
カイ実はそこ、直感に反するけど違う。ディスクベースでもメモリが十分あればOSが最近使ったブロックをキャッシュするから、結局ディスクを読まないこともある。インメモリDBが速い本当の理由は、「メモリ上のデータ構造を、ディスクに書ける形式にエンコードする手間を省ける」ことなんだ。
ハル
ハルなるほど、変換の手間がないから速い、と。ほかに利点は？
カイ
カイディスクベースでは難しいデータモデルを提供できる。Redisはプライオリティキューや集合（set）のインターフェースを出してるけど、全部メモリにあるから実装がシンプルなんだ。あとアンチキャッシング（anti-caching）という方法もある。メモリが足りないとき一番長く使われてないデータをディスクに退避し、再アクセス時にメモリへ戻す（OSのスワップより効率的）。ただしインデックスは全部メモリに収まる必要がある。将来不揮発性メモリ（NVM）が普及すれば設計はまた変わるだろうね。

📦 たとえ話：商品を全部「作業台の上」に出しておく倉庫

インメモリDBは、商品を奥の棚にしまわずぜんぶ作業台の上に広げておく倉庫です。速い本当の理由は「棚から出す時間」ではなく、棚にしまうための梱包（エンコード）をしなくていいこと。ただし停電で台の上が消えないよう、来た商品を控えノート（追記ログ）に書き、ときどき台ごと写真（スナップショット）を撮っておくのです。

💡 なぜこれが必要か / これを知ったらできること

  • プライマリ／セカンダリ、クラスタ化／カバーリングといったインデックス用語を区別して設計できる。
  • 「複数列検索なら連結インデックス、地理検索なら多次元（Rツリー）」と手法を選べる。
  • インメモリDB（Redisなど）が速い理由と耐久性の実現方法を説明できる。

📝 この項のまとめ

  • プライマリキー＝行を一意に特定。セカンダリインデックス＝重複キー可（リスト化またはキーをユニーク化）。
  • 値の保存：ヒープファイル（参照）／クラスタ化インデックス（行を直接格納）／カバーリングインデックス（一部列を格納）。読み取り速度↑だが書き込み・容量・整合性のコスト。
  • 連結インデックスは列の順番が効く。多次元インデックス（空間充填曲線・Rツリー・GiST）は地理や複数範囲に有効。
  • 曖昧検索は全文検索エンジン（編集距離・trie・レーベンシュタインオートマトン）。
  • インメモリDBはエンコード手間の削減で高速。耐久性はログ／スナップショット／レプリケーション等で実現。
3.2

トランザクション処理か、分析処理か？

日常の出荷入荷（OLTP）と、月次棚卸し分析（OLAP）は別物
📌 要するに：OLTP（トランザクション処理）は、ユーザーがキーで少数レコードを低レイテンシで読み書きするインタラクティブな使い方。OLAP（分析処理）は、アナリストが大量レコードをスキャンして要約統計を出す使い方。アクセスパターンが大きく違うため、分析専用のデータウェアハウスへ分けるようになった。トランザクション処理は必ずしもACIDを意味しない。
ハル
ハル「トランザクション向けと分析向けはまるで別」って言ってましたよね。トランザクションって、お金の取引のことですか？
カイ
カイもともとはそう。昔のビジネスデータ処理は販売・発注・給与みたいな商取引にひもづいた書き込みだった。対象がお金以外に広がっても、トランザクションという言葉だけ残って、「論理的なひとまとまりの一連の読み書き」を指すようになった。
ハル
ハルトランザクションって、必ずACIDが要るんですよね？
カイ
カイそこ誤解しやすい。トランザクション処理は必ずしもACID（原子性・一貫性・独立性・永続性）を持たなくていい。ここでは単に「クライアントが低レイテンシで読み書きする」という意味。定期的にまとめてやるバッチ処理と対照的だ（ACIDは7章、バッチは10章）。
ハル
ハルブログのコメントやゲームの操作も商取引と同じ扱い？
カイ
カイアクセスパターンが似てるんだ。普通アプリは何かのキーで少数レコードを引き、ユーザー入力で挿入・更新する。こういう使い方をオンライントランザクション処理（OLTP）と呼ぶ。
ハル
ハル分析だと、何が違うんですか？
カイ
カイ分析はアクセスが全然違う。大量レコードをスキャンして各レコードの少数の列だけを読み、データそのものではなく要約統計（件数・合計・平均）を計算する。こういうクエリだ。
分析的なクエリの例 
# 分析的なクエリの例
- 1月における各店舗の総収入は？
- 直近のプロモーション期間で、通常よりどれだけ多くバナナが売れたか？
- ブランドXのおむつと一緒に最もよく買われた乳児食品のブランドは？
カイ
カイこういうのはビジネスアナリストが書いて、経営判断（ビジネスインテリジェンス）のレポートに使う。OLTPと区別してオンライン分析処理（OLAP）と呼ぶ。両者の典型的な違いはこうだ。
観点OLTP（トランザクション処理）OLAP（分析処理）
主な読み取りキーで少数レコードをフェッチ大量レコードを集計
主な書き込みユーザー入力でランダム・低レイテンシバルクインポート(ETL)／イベントストリーム
主な利用者Webアプリのエンドユーザー／顧客経営判断を支援する社内アナリスト
データの内容最新の状態（現時点）時間経過で生じた出来事の履歴
データセットのサイズギガバイト〜テラバイトテラバイト〜ペタバイト

📦 たとえ話：1点ずつの出荷入荷 vs 全在庫の棚卸し分析

OLTP＝倉庫の日常業務。お客から「商品42を1個出して」と頼まれ、所在マップで一発で見つけてサッと出荷する（少数を低レイテンシ）。OLAP＝月末の棚卸し分析。「先月、店舗ごとに何がどれだけ売れたか」を出すために、倉庫じゅうの記録を端から端まで数えて集計します。日常業務の最中に倉庫中を数え回られたら、出荷が滞って大迷惑。だから分析は別の場所でやるのです。

ハル
ハル最初は同じDBで両方やってたんですか？
カイ
カイそう、SQLは柔軟で両方扱えた。でも1980年代末〜90年代初頭、「OLTPで分析するのはやめて、分析専用の別のDBでやろう」という流れになった。その別のDBがデータウェアハウスだ。

💡 なぜこれが必要か / これを知ったらできること

  • 自分のクエリがOLTP型かOLAP型かを見分け、適したシステムを選べる。
  • 「トランザクション＝ACID」という思い込みを避け、用語を正確に使える。
  • 分析を本番OLTPで回すと負荷で本番が劣化する、という危険を理解できる。

📝 この項のまとめ

  • OLTP＝キーで少数レコードを低レイテンシで読み書き（ユーザー向け、最新状態）。
  • OLAP＝大量レコードをスキャンして集計（アナリスト向け、履歴、巨大）。
  • トランザクション処理は「低レイテンシの読み書き」の意味で、必ずしもACIDではない（バッチ処理と対比）。
  • アクセスパターンが違うため、分析は別個のデータウェアハウスへ分離する流れになった。
3.2.1

データウェアハウス

分析専用の「別館」にETLでコピーする
📌 要するに：データウェアハウスは、各OLTPシステムのデータをETL（取り出し・変換・ロード）で読み取り専用にコピーした分析専用DB。本番OLTPを守りつつ分析できる。OLTPと同じSQLインターフェースでも、最適化対象が違うので内部は大きく異なる。Teradata/Vertica/Redshiftや、オープンソースのSQL-on-Hadoop（Hive、Spark SQL、Impalaなど）がある。
ハル
ハルなんでわざわざ分析用のDBを別に作るんですか？ 既存のでよくないですか？
カイ
カイ大企業は1社で数十のOLTPシステムを持つことがある。顧客向けWeb、店舗のPOS、在庫管理、配送経路、サプライヤー管理、従業員管理……どれも複雑で別チームが独立運用。経営に重要だから高い可用性と低レイテンシが要る。
ハル
ハルその本番DBで分析クエリを流せばいいのでは？
カイ
カイDB管理者は嫌がる。分析クエリは負荷が高くデータの大部分をスキャンするから、同時に動く本番トランザクションの性能を壊しかねない。だから本番OLTPは厳重に守る。
ハル
ハルじゃあデータウェアハウスは……？
カイ
カイデータウェアハウスは独立したDBで、本番OLTPに影響を与えずアナリストがクエリできる場所。社内の各OLTPシステムのデータの読み取り専用のコピーが置かれる。
E

Extract（取り出し）

各OLTPシステム（顧客Web／POS／在庫…）からデータを取り出す。

T

Transform（変換）

分析向けスキーマに変換・クリーンアップする。

L

Load（ロード）

データウェアハウスに読み取り専用コピーとしてロードする（定期ダンプ、または連続的な更新ストリーム）。

✅ この「取り出し→変換→ロード」の流れを ETL（Extract-Transform-Load）と呼ぶ。

📦 たとえ話：各店舗の在庫を「分析専用の別館」に集めて並べ直す

本店・支店（各OLTPシステム）の倉庫はお客対応で大忙し。そこで夜間に各店の在庫記録を取り出し（Extract）、分析しやすい形に並べ直し（Transform）、分析専用の別館（データウェアハウス）に運び込む（Load）。別館は読み取り専用の写しだから、アナリストがいくら数え回っても本店の出荷は止まりません。この一連の搬入作業がETLです。

ハル
ハルどの会社も持ってるんですか？
カイ
カイ大企業はほぼ持ってる。小さい会社はあまり。理由はOLTPシステムが少なくて、普通のSQLやスプレッドシートで分析できる程度のデータしかないから。大企業では、小さい会社なら単純に済むことに多くの困難が伴うんだ。
ハル
ハル分けるメリットの本質は？
カイ
カイデータウェアハウスを分析のアクセスパターンに最適化できること。前半で見たインデックス（ハッシュ、LSM、Bツリー）はOLTPでは強いけど分析にはうまく働かない。だからこの後、分析に最適化された列指向を見ていく。

OLTPデータベースとデータウェアハウスの相違点（3.2.1.1）

ハル
ハルデータウェアハウスもSQLが使えるなら、OLTPと同じものでは？
カイ
カイ表面はね。どちらもSQLインターフェースを持つから似て見える。データモデルも普通リレーショナルで、SQLが分析クエリに向いてるからだ。ドリルダウンやスライスとダイスで探索できるツールも多い。
ハル
ハルじゃあ中身も同じ？
カイ
カイいや、最適化しているクエリのパターンが全然違うから、内部は大きく異なる。今は多くのベンダーがトランザクションか分析のどちらかに集中していて、両方には集中しない。SQL ServerやSAP HANAのように1製品で両対応するものもあるが、徐々に「2つの独立したエンジンを共通のSQLインターフェースでアクセスできるだけ」になってきている。
ハル
ハルデータウェアハウスの製品って、どんなものがありますか？
カイ
カイTeradata、Vertica、SAP HANA、ParAccelなどが高価な商用ライセンス。Amazon RedShiftはParAccelのホステッド版。最近はオープンソースのSQL-on-Hadoopもたくさんあって、Apache Hive、Spark SQL、Cloudera Impala、Facebook Presto、Apache Tajo、Apache Drillなど。いくつかはGoogleのDremelの発想に基づく。

💡 なぜこれが必要か / これを知ったらできること

  • 「分析は本番を巻き込まず別DBで」という分離の理由を説明できる。
  • ETLという定番の取り込みプロセスを理解できる。
  • データウェアハウス製品やSQL-on-Hadoopの全体像を持てる。

📝 この項のまとめ

  • 大企業は多数のOLTPシステムを持ち、本番で重い分析を回すと性能を毀損するため分離する。
  • データウェアハウスは読み取り専用コピーを置く独立DB。ETL（Extract-Transform-Load）で取り込む。
  • 小企業は持たないことが多い（データ量が少なくSQLやスプレッドシートで足りる）。
  • SQL共通でも最適化対象が違い内部は別物。商用（Teradata等）とSQL-on-Hadoop（Hive等）がある。
3.2.2

スターとスノーフレーク：分析のためのスキーマ

巨大なファクトを、ディメンションが星型に囲む
📌 要するに：分析のスキーマは多くがスタースキーマ。中心の巨大なファクトテーブル（イベント1件＝1行、外部キー＋数値）を、人物・対象・日時・場所などを表すディメンションテーブルが星型に囲む。ディメンションをさらに分割して正規化したのがスノーフレークだが、分析にはシンプルなスターが好まれる。テーブルは100列以上になることも珍しくない。
ハル
ハル分析用のデータって、どんな形（スキーマ）で置くんですか？
カイ
カイOLTPはアプリごとに多様だけど、分析はあまり多様じゃない。多くがスタースキーマ（ディメンションモデル）を使う。中心がファクトテーブル（fact table）で、各行は「特定の時点で起きたイベント」。ここでは「顧客が商品を買った」1件だ。
スタースキーマ（図3-9のイメージ）

       [dim_date]      [dim_product]
            ＼            ／
             ＼          ／
   [dim_store]─[fact_sales]─[dim_customer]   ← 中心がファクトテーブル

            ／            ＼
    [dim_promotion]    （周りをディメンションテーブルが囲む＝星型）

                 ＋ 販売価格・仕入価格・数量 などの数値
カイ
カイファクトテーブルは「個別のイベント」を全部そのまま記録するから巨大になる。Apple、Walmart、eBayクラスだと数十ペタバイトに達し、そのほとんどがファクトテーブルだ。
ハル
ハル周りのテーブルは何ですか？
カイ
カイディメンションテーブル（dimension table）。ファクトの列には属性（販売価格・仕入価格など、差で利益率が出る）と、他テーブルを指す外部キーがある。ファクトが「イベント」なら、ディメンションはそのイベントの人物・対象・日時・場所・方法・理由を表す。dim_product の各行は1種類の商品をSKU・説明・ブランド名・分類などとともに表す。
ハル
ハル日付までテーブルにするんですか？
カイ
カイすることがある。日付をディメンションにすると「公休日かどうか」などを持たせられて、「休日と平日で売上がどう違うか」を分析できる。
ハル
ハル「スター」の意味、分かりました。中心のファクトを囲むからですね。スノーフレークは？
カイ
カイその通り、星の輝きみたいだから「スター」。スノーフレークスキーマ（雪の結晶）はその変種で、ディメンションをさらにサブディメンションに分割する。ブランドや分類を別テーブルにして外部キーで参照する。スノーフレークのほうが正規化されてるけど、分析にはスターのほうがシンプルで好まれることが多い。
ハル
ハル列数って多いんですか？
カイ
カイ典型的には1テーブルが100列以上、時に数百列。dim_store には、提供サービス、店内にベーカリーがあるか、店舗面積、開店日、最後の改修日、最寄り高速道路からの距離、なんてのが入りうる。

📦 たとえ話：「出荷記録の山」を中心に、商品台帳・店舗台帳が囲む

分析用の別館は、中心に「いつ・どの商品・どの店・誰に・いくつ売れた」を1件ずつ書いた巨大な出荷記録の山（ファクト）を置きます。記録には商品番号や店番号（外部キー）と、価格・数量（数値）だけが書いてある。商品の詳しい説明は別の商品台帳（ディメンション）、店の詳しい情報は店舗台帳……と周りに置き、番号で引く。中心の記録の山を台帳が星型に囲む形です。台帳をさらに細かく分けると雪の結晶（スノーフレーク）になります。

💡 なぜこれが必要か / これを知ったらできること

  • ファクト／ディメンションの役割を区別し、分析向けスキーマを読める・設計できる。
  • スターとスノーフレークの違い（正規化の度合い）と使い分けを説明できる。
  • 「列数が多くファクトが巨大」という特性が、次の列指向ストレージの動機になると理解できる。

📝 この項のまとめ

  • スタースキーマ＝中心のファクトテーブル＋周囲のディメンションテーブル。
  • ファクト＝個別イベント（外部キー＋数値）で巨大（数十ペタバイトも）。ディメンション＝人物・対象・日時・場所など。
  • スノーフレークはディメンションをさらに分割し正規化。分析にはスターが好まれることが多い。
  • テーブルは100列以上になることも珍しくない。
3.3

列指向ストレージ

品目ごとにまとめた棚 ― 使う列だけ読む
📌 要するに：分析クエリは100列以上あっても数列しか使わない。行指向は1行を丸ごと読むため無駄が多い。列指向は各列をまとめて保存し、使う列だけ読むので効率的。各列ファイルが同じ行順を保つことで行を再構成できる。Parquetのような非リレーショナル向け列フォーマットもある。
ハル
ハルファクトテーブルがペタバイト級って、どうやって効率的にクエリするんですか？
カイ
カイそこが本題。ファクトテーブルは100列以上あっても、典型的な分析クエリが一度に使うのは4〜5列だけ。SELECT * なんて分析ではほぼ使わない。たとえばこのクエリ。
例3-1：曜日ごとに果物とキャンディの売上数を集計する 
-- 例3-1：曜日ごとに果物とキャンディの売上数を集計する分析クエリ
SELECT
  dim_date.weekday, dim_product.category,
  SUM(fact_sales.quantity) AS quantity_sold
FROM fact_sales
  JOIN dim_date    ON fact_sales.date_key   = dim_date.date_key
  JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk
WHERE
  dim_date.year = 2013 AND
  dim_product.category IN ('生鮮果物', 'キャンディ')
GROUP BY
  dim_date.weekday, dim_product.category;
カイ
カイこのクエリは大量の行にアクセスするけど、fact_sales で使う列は date_key、product_sk、quantity の3列だけ。あとは全部無視する。
ハル
ハル普通のDBだと、どう保存されてるんですか？
カイ
カイ多くのOLTPでは行指向（row-oriented）。1行の値が全部隣り合って並んでいる。CSVを思い浮かべればいい。date_key にインデックスを張っても、該当行を丸ごと（100列以上）ロードしてパースし、条件に合わない行をフィルタする。時間がかかる。
ハル
ハル列指向の考え方はシンプルそうですね。
カイ
カイシンプルだ。「1行の全値をまとめる」のではなく「各列の全値をまとめて保存する」。各列が別ファイルなら、クエリが読むのは使う列だけで済む。

行2: 日付A, 商品2, 店3, ..., 数量5

→ 3列だけ欲しくても、行ごと全部（100列以上）を読んでパースして捨てる

[列指向：1列ぶんがまとまって並ぶ]
date_key 列   : 日付A, 日付A, 日付B, ...
product_sk 列 : 商品1, 商品2, 商品1, ...
quantity 列   : 2, 5, 1, ...
→ 欲しい3つの列ファイルだけ読めばよい
📄

行指向

1行の全列が隣り合う。数列しか使わなくても行を丸ごと（100列以上）読む＝無駄が多い。

📊

列指向

各列をまとめて別ファイルに。使う列のファイルだけ読めばよい＝ディスクから読む量が激減。

（補足）列ストレージはリレーショナルで一番理解しやすいけど、非リレーショナルにも使える。たとえばParquetはGoogleのDremelを元にした、ドキュメントデータモデルをサポートする列ストレージフォーマット。

ハル
ハル行を1つにまとめ直すのはどうするんですか？
カイ
カイ各列のファイルが同じ順序で行を保持しているのが大事。23番目の行が欲しければ、各列ファイルの23番目のエントリを取り出して並べれば再構成できる。

📦 たとえ話：品目ごとにまとめた棚

行指向の倉庫は、1件の注文に関するあらゆる項目を1つの箱にまとめて棚に置きます。でも「全注文の数量だけ集計したい」とき、箱を全部開けて数量だけ抜き、残りは捨てるハメに。列指向の倉庫は逆。「日付だけの棚」「商品番号だけの棚」「数量だけの棚」と品目ごとにまとめて置きます。数量を集計したいなら数量の棚だけ見ればいい。どの棚も同じ順番で並んでいるので、23番目の品をどの棚からも取り出せば、元の1件を組み立て直せるのです。

💡 なぜこれが必要か / これを知ったらできること

  • 「分析が遅い→列指向で必要な列だけ読む」という改善の方向を理解できる。
  • 行指向と列指向のデータ配置の違いを説明できる。
  • ParquetなどのカラムナフォーマットがOLAPで使われる理由が分かる。

📝 この項のまとめ

  • 分析クエリは大量行・少数列。行指向は1行丸ごと読むので無駄が多い。
  • 列指向は各列をまとめて保存し、使う列だけ読む。
  • 各列ファイルは同じ行順を保つため、エントリ番号で行を再構成できる。
  • 列ストレージは非リレーショナル（Parquet等）にも適用できる。
3.3.1

列の圧縮

ビットマップで圧縮し、ベクトル化処理でCPUも効率化
📌 要するに：列の中身は繰り返しが多く圧縮しやすい。代表がビットマップエンコーディング（値ごとに0/1の列を作り、疎ならランレングスでさらに圧縮）。IN や AND/OR のクエリをビットごとの論理演算で高速処理できる。Cassandraらの「列ファミリ」は名前に反してほぼ行指向。列指向はディスクI/O削減だけでなく、CPUキャッシュに収めた密ループ＝ベクトル化処理でCPUも効率化する。
ハル
ハル列ごとにまとめると、ほかに得することはありますか？
カイ
カイ圧縮しやすくなる。列の中の値は同じものが何度も繰り返されることが多いから、圧縮にうってつけ。特に効くのがビットマップエンコーディングだ。
ハル
ハルビットマップ？
カイ
カイ1つの列のユニークな値の数は、行数に比べてずっと小さいことが多い（数十億の取引でも商品の種類は10万程度）。そこで、ユニークな値ごとに「その値かどうか」を0/1で表すビットの列を作るんだ。
ビットマップエンコーディング（図3-11のイメージ） 
# ビットマップエンコーディング（図3-11のイメージ）

product_sk 列の値:  68 69 69 68 70 69 69
                     │
                     ▼ 値ごとにビットマップ（その行がその値なら1）
product_sk=68 : 1 0 0 1 0 0 0
product_sk=69 : 0 1 1 0 0 1 1
product_sk=70 : 0 0 0 0 1 0 0

・ユニーク値 n が小さい（例：country は200程度）→ 行ごと1ビットで済む
・n が大きい → ビットマップは大量の0が並ぶ（疎＝sparse）
  → さらに「ランレングスエンコーディング（連続する同じ値をまとめる）」で超コンパクトに
ハル
ハルこのビットマップ、クエリにどう役立つんですか？
カイ
カイデータウェアハウスのよくあるクエリにピッタリだ。例を出そう。
ビットマップによるクエリ処理 
# ビットマップによるクエリ処理
- WHERE product_sk IN (30, 68, 69)
   → 30・68・69 の3つのビットマップをロードし、ビットごとの OR を取る（効率的）
- WHERE product_sk = 31 AND store_sk = 3
   → 2つのビットマップをロードし、ビットごとの AND を取る
   ※ どの列も同じ行順なので、k番目のビットは同じ行に対応する

📦 たとえ話：品目棚に「該当する箱だけ◯」のチェックシート

「商品番号68のものは全部どれ？」と聞かれて毎回棚を見て回るのは大変。そこで、各商品番号ごとに「1番目の箱は該当？ 2番目は？…」を◯×で記したチェックシート（ビットマップ）を用意します。「68か69か70のもの」を探すなら3枚のシートを重ねてどれか◯ならOK（OR）。「68かつ店舗3」なら2枚を重ねて両方◯（AND）。シートの大半が×（疎）なら、「×が10連続」と書いて圧縮（ランレングス）できます。

ハル
ハル列ファミリって聞いたことありますけど、これと同じですか？
カイ
カイ違う、混同注意。CassandraやHBaseには列ファミリ（column family）という概念がBigtable由来であるけど、これを「列指向」と呼ぶのは誤解を招く。列ファミリ内では「行の全列が行キーと一緒にまとめて」保存され、列は圧縮されない。だからBigtableのモデルはやっぱりほぼ行指向なんだ。

メモリの帯域とベクトル化処理（3.3.1.1）

ハル
ハル列指向の速さって、ディスクから読む量が減るからだけですか？
カイ
カイそれも大きいけど、唯一のボトルネックじゃない。数百万行をスキャンする分析クエリでは「ディスク→メモリ」の帯域がまず大きなボトルネック。でも分析DBの開発者は「メモリ→CPUキャッシュ」の帯域や、分岐予測ミス、CPUのパイプラインの空き、現代CPUのSIMD（1命令で複数データを処理）命令の活用まで考える。
ハル
ハル列指向はCPUにも優しいんですか？
カイ
カイそう。圧縮された列のデータの塊（チャンク）をCPUのL1キャッシュにうまく収めて、関数呼び出しのない密なループで一気に処理できる。圧縮すれば同じL1キャッシュに多くの行が収まるし、さっきのビットごとのANDやORは圧縮データを直接処理できる。この手法をベクトル化処理（vectorized processing）と呼ぶ。

💡 なぜこれが必要か / これを知ったらできること

  • 列指向が「読み込み量削減＋圧縮＋CPU効率」の三重で速い理由を説明できる。
  • ビットマップで IN / AND / OR が高速に処理される仕組みを理解できる。
  • 「列ファミリ＝列指向」という誤解を避けられる。

📝 この項のまとめ

  • 列は繰り返しが多く圧縮に向く。ビットマップエンコーディング＋ランレングスでコンパクトに。
  • IN は OR、AND はビットごとのANDで効率処理（全列が同じ行順だから成立）。
  • 列ファミリ（Cassandra/HBase/Bigtable）はほぼ行指向で、列指向ではない。
  • 列指向はディスクI/O削減に加え、ベクトル化処理でCPUキャッシュを活かし高速化する。
3.3.2

列ストレージにおけるソート順序

行ごとまとめて並べ替える ― 圧縮にも効く
📌 要するに：列指向でも行全体をまとめてソートできる（列を独立にソートしてはいけない）。よく使うクエリに合わせて第一・第二のソートキーを選ぶと、範囲スキャンが速くなり、第一ソート列はランレングスで強く圧縮できる。クエリごとに最適なソート順が違うので、Verticaはレプリカを異なるソート順で保存する。これは行指向のセカンダリインデックスに似るが、列指向では列自体が値を持ちポインタはない。
ハル
ハル列指向では、行の順番はどうするんですか？
カイ
カイ必ずしも問題にならない。一番簡単なのは「挿入された順」で、新しい行は各列ファイルに追記するだけ。でも、SSTableで見たように順序を強制してインデックス代わりにもできる。
ハル
ハル列ごとにバラバラにソートすればいいんですか？
カイ
カイダメだ。各列を独立にソートしたら、「どの値とどの値が同じ行か」が分からなくなる。ある列のk番目が他の列のk番目と同じ行だからこそ再構成できる。だからソートするなら行全体をまとめて並べ替える。
ハル
ハル何を基準に並べるんですか？
カイ
カイよく使うクエリを知ってる管理者がソート順の列を選ぶ。クエリが「直近の月」みたいに日付範囲を指定することが多いなら、date_key を第一のソートキーに。するとオプティマイザは直近の月の行だけスキャンすればよく、全行スキャンよりずっと速い。
ハル
ハル2つ目のキーは？
カイ
カイ第一キーが同じ行の中での並び順を決める。date_key が第一なら product_sk を第二のソートキーにして、同じ日・同じ製品の売上をまとめる。「特定期間内で製品ごとにグループ化・フィルタ」するクエリを助けられる。
ハル
ハルソートって圧縮にも関係しますか？
カイ
カイする。第一ソート列のユニーク値が少なければ、ソート後は同じ値が長く連続する。だからランレングスエンコーディングで数キロバイトまで圧縮できることも。行数が数十億でもね。この効果は第一ソートキーで最大。第二・第三キーは並びが混沌として繰り返しが減るので効きにくくなる。それでも最初の数列をソートするのは全体として効率的だ。

📦 たとえ話：「日付順 → 商品順」で品目棚をまとめて並べ替える

品目ごとの棚を並べ替えるとき、日付の棚だけ別の順に並べてはいけません。日付・商品・数量の棚は同じ順番でこそ「23番目どうしが同じ取引」と分かるからです。だから取引まるごとを「まず日付順、同じ日なら商品順」に並べ替えます。すると「先月の取引」を探すとき、先月の区画だけ見ればよく、しかも同じ日付が長く連続するので「日付Aが1000件連続」とまとめて超圧縮できるのです。

複数のソート順序（3.3.2.1）

ハル
ハルでも、クエリによって嬉しいソート順は違いますよね。1つに決められないような……。
カイ
カイいい着眼点。だから「同じデータをいくつかの違うソート順で保存しておく」という手がある。これを列指向に取り入れたのが商用データウェアハウスのVerticaだ。
ハル
ハル同じデータを何個も持つって、無駄じゃないんですか？
カイ
カイ無駄じゃない。どのみち1台の障害でデータが消えないよう、データは複数マシンにレプリケーション（複製）しないといけない。その冗長なコピーをそれぞれ違うソート順にしておけば、クエリごとに最適なバージョンを使える。
ハル
ハルこれって、行指向のセカンダリインデックスと似てますか？
カイ
カイ少し似てる。でも大きく違う。行指向では全行を1カ所（ヒープかクラスタ化）に持ち、セカンダリインデックスは「マッチする行へのポインタ」を持つだけ。一方、列指向では普通「他の場所のデータへのポインタ」は一切なくて、列だけが値を持っているんだ。

💡 なぜこれが必要か / これを知ったらできること

  • ソート順の選び方が「範囲スキャンの速さ」と「圧縮率」の両方に効くと理解できる。
  • 「複数ソート順のレプリカ」（Vertica）という発想で、冗長コピーを性能に活かせると分かる。
  • 列指向と行指向＋セカンダリインデックスの構造的な違いを説明できる。

📝 この項のまとめ

  • 列を独立にソートしてはいけない（行の対応が壊れる）。行全体をまとめてソートする。
  • 第一・第二ソートキーをよく使うクエリに合わせると範囲スキャンが高速化。
  • 第一ソート列はランレングスで強く圧縮できる（後続キーほど効きにくい）。
  • レプリカを異なるソート順で保存（Vertica）。列指向は列自体が値を持ちポインタはない。
3.3.3

列指向ストレージへの書き込み

書き込みが難しい ― 解決はまたLSMツリー
📌 要するに：列指向＋圧縮＋ソートは読み取りに最適だが、その場での更新ができず、1行挿入でも全列ファイルの書き直しになり書き込みが難しい。解決はLSMツリー方式：書き込みをメモリ上のソート済みストアに溜め、十分溜まったらディスクの列ファイルとマージして新ファイルに書く（Verticaの方式）。クエリはメモリとディスクの両方を見るが、その区別はオプティマイザが隠す。
ハル
ハル列指向＋圧縮＋ソートで読み取りは速いんですよね。書き込みはどうなんですか？
カイ
カイそこが欠点。これらの最適化はデータウェアハウスでは理にかなってる（負荷の大半がアナリストの大規模な読み取りだから）。でも書き込みは難しくなる。
ハル
ハルなんで難しいんですか？
カイ
カイBツリーがやる「その場で上書き（インプレース更新）」が、圧縮された列では不可能なんだ。ソート済みテーブルの途中に1行挿入したいと思ったら、おそらくすべての列ファイルを書き直すことになる。行は列内の位置で識別されるから、挿入時に全列を整合させて更新しなきゃいけない。
ハル
ハルそれは大変……。解決策はあるんですか？
カイ
カイもうこの章で見てる。LSMツリーだ。すべての書き込みをまずメモリ上のストアに送ってソート済み構造に溜める。メモリ上が行指向か列指向かは問題にならない。十分溜まったら、ディスク上の列ファイルとマージして一度に新ファイルに書き出す。Verticaが基本的にやっているのがこれだ。
ハル
ハルでもメモリにある分とディスクにある分、別々ですよね。クエリは大丈夫ですか？
カイ
カイクエリは「ディスク上の列データ」と「メモリ内の直近の書き込み」の両方を調べて結果を組み合わせる。でもオプティマイザがこの区別をユーザーから隠してくれる。アナリストから見れば、挿入・更新・削除した変更は次のクエリにすぐ反映されてるように見える。

📦 たとえ話：圧縮梱包した品目棚に1件だけ割り込ませる難しさ

品目棚をぎゅっと圧縮梱包して番号順に並べてあると、途中に1件だけ割り込ませるのは至難。全部の品目棚を解いて並べ直すハメになります。そこで、ここでもLSMの知恵を使う。新しい品は受付の仮置き台（メモリ）に番号順で仮置きし、溜まったらまとめて品目棚と合併して新しい棚にする。棚出しのときは仮置き台と棚の両方を見て答えますが、その手間は受付係（オプティマイザ）がうまく隠してくれるのです。

💡 なぜこれが必要か / これを知ったらできること

  • 「列指向は読み取り最適だが書き込みが重い」というトレードオフを理解できる。
  • その解決にLSMツリー（メモリ蓄積→マージ）が再利用されると分かり、概念のつながりを掴める。
  • 列指向DBへの挿入が即座に反映される仕組み（メモリ＋ディスクの結合）を説明できる。

📝 この項のまとめ

  • 列指向＋圧縮＋ソートは読み取りに最適だが、その場更新ができず書き込みが難しい（全列書き直し）。
  • 解決はLSMツリー方式：メモリ上のソート済みストアに溜め、まとめてディスクの列ファイルにマージ（Vertica）。
  • クエリはメモリとディスクの両方を見て結合するが、その区別はオプティマイザが隠す（変更は即反映に見える）。
3.3.4

集計：データキューブとマテリアライズドビュー

よく使う集計を事前計算して掲示する
📌 要するに：同じ集計を何度も使うなら結果をキャッシュすると速い。マテリアライズドビューはクエリ結果を実際にディスクへコピーしたもの（仮想ビューは展開するだけ）。元データ変更で更新が要り書き込み負荷が増すのでOLTPには不向き、読み取り中心のデータウェアハウス向き。その特殊形がデータキューブ（OLAPキューブ）で、次元ごとの集計を事前計算し特定クエリを超高速化するが、生データほど柔軟ではない。
ハル
ハルデータウェアハウスって全部列ストアなんですか？
カイ
カイいや、必ずしも。旧来の行指向DBや他のアーキテクチャも使われてる。ただアドホックな分析クエリでは列ストアが明らかに速いから急速に広まってる。さて、もう1つ大事な話、実体化された集計（materialized aggregates）を紹介しよう。
ハル
ハル集計を実体化、ですか？
カイ
カイ分析クエリにはよく COUNT、SUM、AVG、MIN、MAX といった集計関数が出る。同じ集計を多くのクエリで使うなら、毎回生データを処理するのは無駄。だからよく使うカウントや合計をキャッシュしておけばいい。
ハル
ハルそのキャッシュって、どう作るんですか？
カイ
カイ1つの方法がマテリアライズドビュー（実体化ビュー）。普通のビュー（仮想ビュー）と違うのは、実際に結果をコピーしてディスクに書くことだ。
👻

仮想ビュー

クエリを書きやすくするショートカット。読むたびに元クエリに展開して実行（実体は持たない）。

📌

マテリアライズドビュー

クエリ結果を実際にコピーしてディスクに保存（実体を持つ）。

ハル
ハル元データが変わったら、コピーは古くなりませんか？
カイ
カイそう。元データが変わったら、その非正規化コピーであるマテリアライズドビューを更新しないといけない。DBが自動でやれるけど、更新は書き込み負荷を高める。だから書き込みの多いOLTPではあまり使われず、読み取りの多いデータウェアハウスのほうが理にかなってる。
ハル
ハルもっと特化したものはありますか？
カイ
カイマテリアライズドビューの特殊ケースで広く使われるのがデータキューブ（OLAPキューブ）。いろんなディメンションでグループ化した集計値のグリッド（格子）だ。
2次元のデータキューブ（図3-12のイメージ） 
# 2次元のデータキューブ（図3-12のイメージ）
            商品1   商品2   商品3   …   ← 各行の合計（日付ごとの売上）
   日付A     149     0      ...        sum
   日付B      0     250     ...        sum
   日付C     ...    ...     ...        sum
    …
  各列の合計  sum    sum    sum
  （日付に関係ない製品ごとの売上）

各セル：その日付×製品の組み合わせのファクト属性（例 net_price）の集計（例 sum）
行や列方向に集計すると、次元を1つ減らしたサマリが得られる
カイ
カイ各ファクトが2つのディメンション（dateとproduct）に外部キーを持つなら、片方を製品、もう片方を日付にした2次元テーブルが描ける。各セルにその組み合わせの集計値が入る。行や列ごとに集計すれば、次元を1つ減らしたサマリ（製品ごと、日付ごとの売上）が得られる。
ハル
ハル次元が2つより多いときは？
カイ
カイ実際はファクトの次元は3以上が普通。図3-9では日付・製品・店舗・プロモーション・顧客の5次元。5次元のハイパーキューブは想像しにくいけど原理は同じで、各セルに「特定の日付−製品−店舗−プロモ−顧客」の売上が入り、各次元に沿って集計できる。
ハル
ハルデータキューブの利点は？
カイ
カイある種のクエリが超高速になる。事前に計算済みだからね。「昨日の店舗ごとの総売上」なら、適切な次元に沿って合計を見るだけで、数百万行をスキャンしなくていい。
ハル
ハル欠点はないんですか？
カイ
カイ柔軟性が低い。生データへのクエリほど自由じゃない。「100ドル以上の商品が生んだ売上の比率」は、次元に価格がなければ計算できない。だからほとんどのデータウェアハウスは、できる限り生データを保持して、データキューブのような集計は特定クエリの高速化のためだけに使う。

📦 たとえ話：よく聞かれる集計を「掲示板」に貼り出す

「店舗ごとの昨日の総売上は？」と毎日聞かれるなら、その都度倉庫じゅうを数えるのは無駄。あらかじめ計算して掲示板（マテリアライズドビュー）に貼り出しておけば一瞬で答えられます。掲示板を「日付×商品×店舗…」の格子にしたのがデータキューブ。事前計算済みなので特定の集計は超高速。ただし格子に無い切り口（価格条件など）は掲示板では答えられないので、生の記録の山も必ず残しておくのです。

💡 なぜこれが必要か / これを知ったらできること

  • 仮想ビューとマテリアライズドビューの違い（実体を持つか）を説明できる。
  • データキューブが「事前集計で高速だが柔軟性が低い」トレードオフを理解できる。
  • 「生データは残し、集計は高速化のために併用する」という実務方針を持てる。

📝 この項のまとめ

  • 必ずしも全データウェアハウスが列ストアではないが、アドホック分析では列ストアが速く広まっている。
  • マテリアライズドビュー＝クエリ結果をディスクにコピー（仮想ビューは展開のみ）。更新負荷ゆえOLTPには不向き、データウェアハウス向き。
  • データキューブ（OLAPキューブ）は次元ごとの集計の事前計算で特定クエリを超高速化。
  • 欠点は柔軟性の低さ。生データは残し、集計は高速化目的で併用する。

シークと帯域、どっちがボトルネックか
📌 要するに：ストレージエンジンはOLTP最適化（ボトルネックはシーク）とOLAP最適化（ボトルネックは帯域）に大別される。OLTPはlog-structured（追記＝LSM系）とインプレース更新（Bツリー）の2流派。log-structuredの鍵はランダム書き込みをシーケンシャルに変換すること。OLAPは列指向で読み込み量を最小化する。これらの語彙が、DB選定・チューニング・ドキュメント理解の土台になる。

🔍

OLTP（ボトルネック：シーク）

ユーザーから莫大なリクエスト。各クエリは少数レコードをキーで引く。インデックスでキーに対応するデータを見つける。ボトルネックはディスクの「シーク」（あちこち探す時間）。

📡

OLAP（ボトルネック：帯域）

アナリストが使う。クエリ数は少ないが1本が重く、短時間に数百万行をスキャン。ボトルネックはディスクの「帯域」（一度に運べる量）。列指向が活躍。

カイ
カイOLTP側のストレージエンジンには、大きく2つの考え方があった。
📜

log-structured

ファイルへの追記と古いファイル削除だけ。一度書いたら更新しない。例：Bitcask、SSTable、LSMツリー、LevelDB、Cassandra、HBase、Lucene。

📚

インプレース更新

ディスクを「更新可能な固定サイズのページの集合」として扱う。代表がBツリー。主要なリレーショナルDBと多くの非リレーショナルDBで使われる。

ハル
ハルlog-structuredの鍵となる発想は？
カイ
カイ「ディスク上のランダムな書き込みを、システマティックにシーケンシャルな書き込みに変換する」こと。HDDやSSDの特性を踏まえて書き込みスループットを高める。OLTPでは少し複雑なインデックス（セカンダリ、多次元、曖昧）や、全データをメモリに置くインメモリDBも見た。
ハル
ハルOLAP（データウェアハウス）側のポイントは？
カイ
カイ大量の行をシーケンシャルにスキャンするクエリでは、インデックスはあまり関係ない。大事なのは「データをすごくコンパクトにエンコードして、ディスクから読む量を最小にする」こと。それを助けるのが列指向ストレージ（＋圧縮、ソート順、ビットマップ、ベクトル化処理、マテリアライズドビュー／データキューブ）だった。
ハル
ハルこれで僕、ストレージエンジンを選べるようになりますか？

📦 たとえ話：日常出荷の倉庫と、棚卸し分析の別館

今日学んだのは、倉庫が大きく2タイプに分かれること。日常の出荷入荷（OLTP）の倉庫は、頼まれた商品を所在マップで一発で見つけるのが命だから、悩みは「目的の棚まで歩く時間（シーク）」。棚卸し分析（OLAP）の別館は、全在庫をまとめて数えるのが命だから、悩みは「一度にどれだけ運べるか（帯域）」。出荷倉庫は「連番台帳に足すだけ（log-structured＝LSM）」派と「ページ式の固定棚（Bツリー）」派の2流派。分析別館は「品目ごとにまとめた棚（列指向）」でぎゅっと圧縮して運ぶ量を減らす。この見取り図が、倉庫（DB）選びとドキュメント読解の土台になります。

📝 この項のまとめ

  • ストレージエンジンはOLTP（シークがボトルネック）とOLAP（帯域がボトルネック）に大別。
  • OLTPの2流派：log-structured（Bitcask/LSM/Cassandra/HBase/Lucene）とインプレース更新（Bツリー）。
  • log-structuredの鍵はランダム書き込み→シーケンシャル書き込みへの変換。
  • OLAPは列指向でデータをコンパクトにし、ディスクから読む量を最小化する。
  • この知識はDB選定・チューニング・ドキュメント理解のための語彙になる。

この章を読み終えたあと、自分の言葉で答えてみてください。スラスラ書ける問題は理解できています。詰まる問題こそが「実は分かっていなかった部分」です。

第1問インデックスのトレードオフ

インデックスを張ると何が速くなり、何が遅くなりますか。データベースが「何にでも自動でインデックスを張る」ことをしない理由とあわせて説明してください。

✅ 解答例を見る
インデックスは「キーから目的のデータの場所を教えてくれる目印」なので、読み取り（検索）のクエリが速くなります。一方で、データを書き込むたびにインデックスも更新しなければならないため、書き込みは遅くなります。さらにインデックスは追加のデータ構造なので保存容量のオーバーヘッドも生じます。何にでも自動で張るとこのオーバーヘッドが無駄に大きくなるので、アプリのよくあるクエリパターンを知っている開発者やDB管理者が、本当に有益なインデックスだけを選んで張ります。
📝 採点ポイント
・インデックスは読み取りを速くする、と説明できている
・書き込みのたびに更新が要るので書き込みは遅くなる、と述べている
・クエリパターンを知る人が必要なものだけ選ぶ（無駄なオーバーヘッドを避ける）と述べている
第2問LSMツリーとBツリー

LSMツリーとBツリーの基本的な仕組みの違いを説明し、それぞれが「書き込み」「読み取り」のどちらに強いとされるかを述べてください。

✅ 解答例を見る
LSMツリーは、書き込みをまずメモリ上のソート済み構造（memtable）に溜め、一定量たまったらキー順のファイル（SSTable）としてディスクに書き出し、バックグラウンドでマージ・コンパクションして整理します。一度書いたファイルは更新せず追記中心です。Bツリーは、データベースを固定サイズのページに分けてツリーを作り、キーを探すときはツリーをたどります。更新はページをその場で上書きします。一般に、LSMツリーは書き込みが速く（シーケンシャルに書ける）、Bツリーは読み取りが速い（キーが1カ所にあり、複数のSSTableを調べなくてよい）とされます。ただしワークロード次第なので実測が必要です。
📝 採点ポイント
・LSM＝memtableに溜めてSSTableに書き出しマージする追記中心、と説明できている
・Bツリー＝固定サイズページのツリーをその場上書きで更新、と説明できている
・LSMは書き込みに強い、Bツリーは読み取りに強い（要実測）と述べている
第3問OLTPとOLAP

OLTPとOLAPの違いを、利用者・アクセスパターン・ボトルネックの観点から説明してください。なぜ分析専用のデータウェアハウスを別に用意するのかも述べてください。

✅ 解答例を見る
OLTP（トランザクション処理）は、Webアプリのエンドユーザーがキーで少数のレコードを低レイテンシで読み書きする使い方で、ボトルネックはディスクのシーク（あちこち探す時間）です。OLAP（分析処理）は、社内アナリストが大量のレコードをスキャンして集計（合計・平均など）する使い方で、ボトルネックはディスクの帯域（一度に運べる量）です。分析クエリは負荷が高くデータの大部分をスキャンするため、本番のOLTPで実行するとトランザクションの性能を毀損します。そこで、各OLTPシステムのデータをETLで読み取り専用にコピーした分析専用のデータウェアハウスを別に用意し、本番に影響を与えず分析できるようにします。
📝 採点ポイント
・OLTP＝ユーザーがキーで少数レコードを低レイテンシ、OLAP＝アナリストが大量スキャンで集計、と区別している
・ボトルネックがOLTPはシーク、OLAPは帯域、と述べている
・本番OLTPを守るためETLでデータウェアハウスにコピーして分離する、と述べている
第4問列指向ストレージ

列指向ストレージが分析クエリで速い理由を、行指向と比較しながら説明してください。圧縮との関係にも触れてください。

✅ 解答例を見る
行指向では1行の全列が隣り合って保存されるため、たとえ数列しか使わないクエリでも、行を丸ごと（100列以上）ディスクから読んでパースする必要があり無駄が多くなります。列指向では各列をまとめて保存するので、クエリで使う列のファイルだけを読めばよく、ディスクから読む量を大きく減らせます。さらに、同じ列の中は同じ値が繰り返されることが多いため圧縮が効きやすく、ビットマップエンコーディングやランレングスエンコーディングでコンパクトにできます。圧縮データはCPUキャッシュに多く収まり、ビットごとのAND/ORで効率処理（ベクトル化処理）できるため、ディスクI/OだけでなくCPUも効率化されて速くなります。
📝 採点ポイント
・行指向は行を丸ごと読むので無駄、列指向は使う列だけ読む、と比較できている
・列は繰り返しが多く圧縮しやすい（ビットマップ/ランレングス）と述べている
・ディスクI/O削減だけでなくCPU効率（ベクトル化処理）にも触れている（あれば加点）
第5問マテリアライズドビューとデータキューブ

マテリアライズドビューとは何か、普通の（仮想）ビューとの違いを説明してください。また、データキューブの利点と欠点を1つずつ挙げてください。

✅ 解答例を見る
仮想ビューはクエリを書きやすくするためのショートカットで、読むたびに元のクエリに展開して実行されるだけで実体を持ちません。マテリアライズドビューは、クエリの結果を実際にコピーしてディスクに書き込んだもの（実体を持つもの）です。元データが変わると更新が必要で書き込み負荷が増すため、読み取り中心のデータウェアハウスに向きます。データキューブは、次元ごとの集計を事前計算したマテリアライズドビューの特殊形です。利点は、事前計算済みなので「店舗ごとの昨日の総売上」のような集計クエリが超高速になること。欠点は、生データほどの柔軟性がなく、たとえば次元に含まれない属性（価格など）の条件では計算できないことです。
📝 採点ポイント
・仮想ビュー＝展開するだけで実体なし、マテリアライズドビュー＝結果をディスクにコピー、と区別している
・マテリアライズドビューは更新負荷があり読み取り中心向き、と述べている
・データキューブの利点（事前集計で高速）と欠点（柔軟性が低い）を挙げている
