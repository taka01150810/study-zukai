分散システム

複数のコンピュータがネットワークで協力して動くしくみ。＝各地に散らばった支店。本部はなく、手紙でやり取りする。

部分障害 partial failure

一部だけが予想外に壊れ、他は元気な状態。＝ある支店との連絡だけ途絶え、他店は通常営業。

決定的／非決定的 deterministic

決定的＝同じことをすれば必ず同じ結果。非決定的＝うまくいくことも失敗することもある（手紙が届くか不明）。

フォールトトレランス fault tolerance

一部が壊れても全体は動き続ける力。＝1店と連絡が切れてもチェーン全体は営業継続。

シェアードナッシング shared-nothing

何も共有せず、各マシンが自分のメモリ・ディスクを持ち、通信は手紙だけ。＝各支店は独立、連絡は郵便のみ。

非同期ネットワーク

手紙がいつ着くか、そもそも着くか保証しないやり取り。遅れも紛失もある。

タイムアウト timeout

返事をどこまで待つかの制限時間。＝返信をいつまで待って「もう来ない」と判断するか。

キューイング queueing

順番待ちの列。遅延の主因。＝郵便局に手紙が溜まって配達が遅れる。

輻輳 congestion

通信が混み合って詰まること。＝郵便が大渋滞。

時刻のクロック time-of-day

カレンダー上の日時を返す時計。巻き戻りうる。＝壁掛け時計（直されて時刻が戻ることがある）。

単調増加クロック monotonic

常に前進し、差が経過時間。＝ストップウォッチ（絶対値に意味はなく差だけ使う）。

NTP

ネットワーク越しに時計を合わせるしくみ。＝標準時の電波で各支店の時計を合わせる。

クロックスキュー

マシン間の時計のズレ。＝各支店の時計がバラバラ。

信頼区間 confidence interval

時刻は一点でなく「この幅のどこか」と考える範囲。TrueTimeは [最早, 最遅] を返す。

プロセスの一時停止

スレッドが急に数秒〜数分止まること。＝担当者が急に席を外す。

GCポーズ stop-the-world

ガベージコレクションで全スレッドが止まる時間。＝長い昼休みで店が一時的に無人になる。

リース lease

期限付きの「自分がリーダー」という権利。＝期限つきの当番札。更新しないと失効する。

クオラム quorum

ノード群の投票・定足数。＝真実は支店の多数決で決める。一般には過半数。

フェンシングトークン fencing token

増える整理番号札。古い番号の書き込みを弾く。＝整理番号札で割り込みを締め出す。

ビザンチン障害 Byzantine fault

ノードが嘘をつく障害。＝嘘の手紙を送る裏切り支店。それに耐えるのがビザンチン耐性。

システムモデル system model

どんなフォールトが起きるかの仮定の枠組み。タイミング3種＋ノード障害3種で記述する。

安全性／ライブ性 safety/liveness

安全性＝何も悪いことが起きない（常に守る）。ライブ性＝最終的に良いことが起きる（条件付きでよい）。

🎬

あらすじ・要するに・なぜ必要か

この章で何を学ぶのか、最初に地図を持つ

あらすじ

新人エンジニアのハルは、ツバサ社で「複数のサーバーが協力して動くシステム（分散システム）」をはじめて任されました。ところが、あるサーバーへのリクエストが返ってこなかったり、ログの時刻がなぜか巻き戻っていたり、生きているはずのサーバーが「死んだ」とみなされて二重処理が起きたり……と、1台のパソコンで動かしていたときには考えられない不気味な現象が次々に起きます。「これ、僕のコードのバグですよね？」と落ち込むハルに、ベテランのカイ先輩はコーヒー片手にこう告げます。「いや、それは分散システムの“当たり前の地獄”なんだよ」。この章は、分散システムで必ず起きるトラブル――壊れるネットワーク・信用できない時計・勝手に止まるプロセス――を、徹底的に悲観的に見ていく回です。

🎯 要するに：1台のコンピュータは「動くか、完全に壊れるか」で分かりやすい。でも複数台をネットワークでつなぐと、一部だけがおかしくなる（部分障害）という新しい地獄が生まれる。しかもネットワークは遅れたりパケットを落としたりするし、各マシンの時計はズレるし、プロセスは突然何秒も止まる。だから「相手のノードが生きているか」すら確実には知ることができない。この章は「何を信じられて、何を信じられないか」を整理し、最後に「システムモデル」という枠組みで現実をどう扱うかを学ぶ。

✉️ たとえ話：これから「支店どうしの手紙連絡」の話をします

この章を通して、分散システム＝遠隔地に散らばった支店、ネットワーク＝支店どうしの手紙のやり取り、ノードの障害＝ある支店との連絡が途絶えることに置きかえて読みます。本部はなく、支店どうしは手紙でしか連絡できません。手紙は届かない・紛失する・遅れて届くし、各支店の時計はバラバラで、担当者は急に席を外す。この「届くか分からない手紙の世界」が、この章ぜんぶを貫くたとえです。

💡 なぜこれが必要か / これを知ったらできること

  • ありえないバグから解放される：分散では「うまくいくことも失敗することもある」非決定的な振る舞いが普通。知らないと延々と悩む。
  • 取り返しのつかない事故を防ぐ：「ノードが落ちた」「時計が正しい」という素朴な思い込みが、データ消失・破壊を招く。先に知れば防げる。
  • 9章への地図になる：合意アルゴリズムなど高度な道具は、すべて「この章の問題をどう乗り越えるか」のためにある。
  • 根拠を持って設計できる：タイムアウト・リトライ・フェンシングトークンを「なんとなく」でなく根拠を持って選べるようになる。

8.1

フォールトと部分障害

一部だけ壊れて、他は元気 ― それが厄介
📌 要するに：1台のコンピュータは「完全に動くか、完全に壊れるか」で予測しやすい（決定的）。だが複数台になると、一部だけが予想外に壊れる部分障害が起きる。しかも結果が決まらない（非決定的）ので、処理が成功したのかどうかさえ知ることができない。これが分散システムの難しさの根源。
ハル
ハルそもそも、1台のコンピュータって、そんなに信頼できるんですか？
カイ
カイかなり信頼できる。1台で動くプログラムは振る舞いが予測しやすい。うまく動くか、まったく動かないかのどちらか。調子が悪いのもたいてい「うまく書けてないソフト」のせいで、再起動で直ることが多い。
ハル
ハル「半分だけ壊れる」中間状態はないんですか？
カイ
カイ基本ないんだ。ハードが正しく動けば同じ処理は常に同じ結果＝決定的（deterministic）。ハードに問題が起きたら、たいていシステム全体がバッタリ倒れる――カーネルパニックや「ブルースクリーン」、起動失敗みたいにね。
ハル
ハル半端に間違うより、いっそ完全にクラッシュする、と。
カイ
カイそれはわざとそう設計してる。間違った答えは混乱を招くから「間違うくらいなら完全に止まれ」という思想。だからコンピュータは雑然とした物理世界を隠して、数学みたいに完璧な「理想的なシステムモデル」を見せてくれる。
ハル
ハルでも複数台になると、その理想が崩れるんですね。
カイ
カイその通り。分散システムは理想モデルじゃなく、ぐちゃぐちゃな物理世界に直面する。ネットワーク分断、配電障害、スイッチ障害、ラック全体の予想外の電源オフ、果ては「低血糖で運転を誤ったトラックが空調設備に突っ込んだ事故」まで起きるんだ。

システムの一部だけが、予想外の形で壊れ、他の部分はピンピンしている――これが部分障害です。

✉️ たとえ話：1店との連絡だけ途絶え、他店は通常営業

1台のコンピュータなら「全店一斉に休業」みたいに分かりやすい。でも支店が増えると、ある支店とだけ手紙が往復しなくなるのに、他の支店とは普通に連絡が取れる、という中途半端な事態が起きます。しかも「その支店に手紙が届いたのか、返事が途中で紛失したのか」さえ分からない。これが部分障害の厄介さです。

ハル
ハル一部だけ壊れて、他は元気……。対処が難しそうですね。
カイ
カイめちゃくちゃ難しい。部分障害の何が厄介かというと、非決定的（non-deterministic）なところ。複数ノードやネットワークが絡む処理は、うまくいくことも、予想外に失敗することもある。
ハル
ハルせめて「成功したか失敗したか」だけでも分かれば……。
カイ
カイそれがね、メッセージがネットワークを渡る時間そのものも非決定的だから、「成功したかどうかを知ることさえできない」ことがある。さっききみが悩んでた「返事が返ってこない」がまさにこれ。この非決定性と部分障害こそが、分散システムを難しくしている正体だよ。

💡 なぜこれが必要か / これを知ったらできること

  • 「成功か失敗か分からない」状態が普通だと理解すると、リトライや冪等性（同じ処理を2回やっても安全）の設計を考えるようになる。
  • 1台の常識（決定的）を分散に持ち込むと事故ると分かり、設計の前提を切り替えられる。

📝 この項のまとめ

  • 1台のコンピュータは決定的で予測しやすく、壊れるときは全体が止まる（わざとそう設計されている）。
  • 分散システムは理想モデルではなく雑然とした物理世界に直面する。
  • 一部だけが壊れる「部分障害」は非決定的で、成否すら知れないことがある。
8.1.1

クラウドコンピューティングとスーパーコンピューティング

「壊れたら全停止」か「壊れても継続」か
📌 要するに：大規模計算にはHPC（スーパーコンピュータ）からクラウドまで幅がある。スーパーコンピュータは「壊れたら全部止める」ので実は1台に近い。一方インターネットサービスはオンライン性・コモディティハード・大規模・地理分散ゆえ、部分障害を前提に耐障害性を組み込む必要がある。小規模でも「いつか壊れる」は必ず来るので、疑念・悲観・偏執で備える。
ハル
ハル大規模なコンピューティングって、どれもだいたい同じ作り方なんですか？
カイ
カイいや、考え方には幅（スペクトラム）がある。両端を見てみよう。

ハルスーパーコンピュータって、分散システムの王様みたいなものですか？

ハル
ハル一部が壊れたら全部止める……。「1台はバッタリ倒れる」と同じですね。
カイ
カイその通り。でも本書が焦点を当てるのはインターネット上のサービスで、これはスーパーコンピュータとは大きく違う。5点に整理しよう。

1. オンライン性: 常に低レイテンシでユーザーに応答が必要。
   「修理のため停止」は許されない。
   （気象シミュレーションのバッチジョブは止めて再開しても影響が小さい）
2. ハードウェア: クラウドはコモディティ（安価で一般的）マシンで構築。
   規模の経済で安いが障害発生率は高い。
   スーパーコンピュータは特化ハードで高信頼、通信は共有メモリやRDMA。
3. ネットワーク: 大規模データセンターはIP/イーサネット基盤、
   高い2分割帯域のためClosトポロジーが多い。
   スーパーコンピュータは多次元メッシュやトーラスなど特化トポロジー。
4. 規模と故障: ノードが多いほど「常に何かが故障している」のが当たり前。
   あきらめるだけの戦略だと、回復ばかりに時間を費やすことになる。
5. 地理的分散: ユーザーの近くにデータを置くとレイテンシを下げられるが、
   通信はインターネット経由になり、ローカルネットより低速で不安定。

✉️ たとえ話：本店集中型のチェーン vs 各店自立型のチェーン

スーパーコンピュータは「巨大な本店1つに全機能を集中」させたチェーン。本店が止まれば全店休業ですが、強固に作ってあります。インターネットサービスは「各地にたくさんの自立した支店」を置くチェーン。1店と連絡が切れても、他店で営業を続けるのが前提です。だからローリングアップグレード（1店ずつ順番に改装）も、調子の悪い店を捨てて新しい店を出すこともできます。

ハル
ハル規模が大きいほど「常に何かが壊れている」って、すごい前提ですね。
カイ
カイ数千ノードあれば妥当な前提だよ。だから、ノードが壊れてもシステム全体が処理を続けられると、運用がすごく楽になる。ローリングアップグレードでノードを1台ずつ再起動しながらサービスは止めない。クラウドなら調子の悪いVMを破棄して新しいのを要求すればいい。
ハル
ハル分散システムをうまく動かすには？
カイ
カイ部分障害を受け入れて、ソフトにフォールトトレランス（耐障害性）を組み込むこと。「信頼できない部品から、信頼できるシステムを作る」。ただし1章でも言ったけど、完全な信頼性は存在しない。「現実的に約束できる限界」を理解しておくのが大事だ。
ハル
ハルうちみたいに数ノードしかない小さいシステムでも、考えないとダメですか？
カイ
カイダメだね。小さいシステムはほとんどの時間は正常に動くけど、「いつか一部がおかしくなる時」は必ず来る。フォールトの処理は設計の一部であるべきだし、運用者は障害時の振る舞いを知っておく必要がある。疑念・悲観・偏執が割に合うのが、この世界。テスト環境でわざと障害を起こして、何が起きるか見ておくといい。

💡 なぜこれが必要か / これを知ったらできること

  • 自分のシステムがHPC型かクラウド型かを意識すると、障害対応の方針（全停止か、耐えて継続か）を選べる。
  • 「数ノードだから大丈夫」という油断を捨て、わざと障害を起こすテストを取り入れられる。

📝 この項のまとめ

  • HPCは「壊れたら全停止＋チェックポイント再開」で単一ノードに近い。
  • インターネットサービスはオンライン性・安価ハード・大規模・地理分散が特徴で、部分障害が前提。
  • 耐障害性で「信頼できない部品から信頼できるシステム」を作る。完全な信頼性はない。
  • 小規模でも障害は必ず来る。疑念・悲観・偏執で、わざと障害を起こしてテストする。
📦

コラム：信頼性のないコンポーネントから信頼性のあるシステムを構築する

「信頼性は最弱リンクで決まる」は誤り
📌 要するに：「信頼性は最弱リンクで決まる」は間違い。エラー訂正コードやTCPのように、信頼できない土台の上に、より信頼できるシステムを築ける。ただし信頼性には常に上限があり（遅延は消せない等）、完璧にはならない。それでも低レベルの面倒を見てくれる点で有益。
ハル
ハルでも先輩、「信頼できない部品から信頼できるシステム」って直感に反します。システムの信頼性って、一番弱い部品（最弱リンク）と同じくらいにしかならないんじゃ？
カイ
カイそれ、よくある誤解なんだけど間違いなんだ。「信頼できない土台の上に、もっと信頼できるシステムを作る」のは、コンピューティングでは古くからある考え方。例を挙げよう。
信頼できない土台から信頼できるシステムを作る例 
信頼できない土台から信頼できるシステムを作る例
- エラー訂正コード（error-correcting code）
    無線通信で電波障害により多少のビットが狂っても、正確にデータを転送できる
- TCP（Transmission Control Protocol）
    土台のIP（Internet Protocol）は信頼できない
    （パケットのドロップ・遅延・重複・順序変化が起きる）
    TCPはその上で「失われたパケットの再送・重複排除・順序の復元」を保証する

✉️ たとえ話：紛失する郵便の上に「確実な連絡網」を築く

郵便（IP）は手紙を落としたり順番を入れ替えたりします。でも各支店が「届いたら受領証を返す。来なければ再送する。番号順に並べ直す」という取り決め（TCP）を上に重ねれば、紛失や順序の乱れを隠した「確実な連絡網」になります。土台が不確実でも、上のルールで信頼性を底上げできるのです。ただし手紙が届くまでの時間（遅延）そのものは魔法のように消せません。信頼性の向上には上限があります。

ハル
ハル信頼できないIPの上に信頼できるTCPが乗ってる、と。じゃあ何でも信頼できるようにできるんですか？
カイ
カイそこには上限がある。エラー訂正コードは少数のビットエラーは直せるけど、信号が完全に洗い流されたら通せるデータ量に限界がある。TCPもパケットのロスや順序変化は隠せるけど、ネットワークの遅延そのものは魔法のように消せない。
ハル
ハル完璧にはできないけど、有益ではある、と。
カイ
カイまさに。完璧じゃなくても、難しい低レベルのフォールトをある程度面倒見てくれる。残ったフォールトは、たいてい理解しやすく対処しやすくなる。これは「エンドツーエンド論」として後の章でもっと深く扱うよ。

💡 なぜこれが必要か / これを知ったらできること

  • 「部品が不安定だから無理」と諦めず、上位レイヤーで信頼性を高める発想が持てる。
  • 信頼性向上には上限があると知り、過度な期待（遅延ゼロなど）をしなくなる。

📝 この項のまとめ

  • 信頼性が最弱リンクで決まるというのは誤り。
  • 信頼できない土台の上に信頼できるシステムを作れる（エラー訂正コード、TCP）。
  • ただし信頼性には上限があり完璧にはならない。それでも有益。
