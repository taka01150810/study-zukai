データモデル data model

データを「どんな形で表すか」の決め方。図書館でいうと本のしまい方・並べ方のルール。

リレーショナルモデル

データを表（テーブル）と行で整理するモデル。＝棚に並べ、背表紙ラベルと索引カードで管理する方式。

ドキュメントモデル

関連する情報を1つの入れ子の書類にまとめるモデル。＝1冊にまとめた書類綴り（ファイル）。

グラフモデル

点（頂点）と線（辺）でつながりを表すモデル。＝人物相関の系図（誰が誰とつながるか）。

クエリ言語 query language

データに問いかける言葉。図書館でいう司書への頼み方。

タプル／行・リレーション／テーブル

タプル＝表の1行（1冊分のカード）、リレーション＝表（同じ種類のカードの束）。

NoSQL

もとはハッシュタグ由来の言葉。今は「Not Only SQL（SQLだけじゃない）」の意。リレーショナル以外のDBの総称。

ポリグロットパーシステンス

複数のモデル（道具）を適材適所で併用すること。＝棚・書類綴り・系図を使い分ける図書館。

インピーダンスミスマッチ

アプリのオブジェクトとDBのテーブルの形が合わずぎくしゃくすること。本の中身と目録カードの様式のズレ。

ORM

オブジェクトとテーブルの変換を肩代わりする道具。＝中身を目録カードに自動転記する助手。

一対多 / 多対一 / 多対多

つながり方。一対多＝1冊に複数の章。多対一＝多くの本が同じジャンルに属す。多対多＝本同士が引用し合う網。

正規化 / 非正規化

正規化＝同じ情報をダブらせずID（請求記号）で1カ所参照。非正規化＝あえて複製して取り出しを速くする。

外部キー／ドキュメント参照

別の場所のデータを指す「請求記号」。図書館の「○○を参照」のクロスリファレンスカード。

結合（ジョイン）

別々の表を、参照（請求記号）でつなげて1つにまとめる操作。カードをたどって関連資料を集める。

ローカリティ locality

関連データが1カ所にまとまっていること。1冊の綴りに全部入っていて一度で取れること。

階層モデル / ネットワークモデル

昔のモデル。階層＝1本の大きなツリー。ネットワーク（CODASYL）＝複数の親を持てる網。

アクセスパス

目的のデータに着くまでの道順。昔は手で道順を指定した。目当ての本までの順路を全部自分で指示。

クエリオプティマイザ

どの索引をどの順で使うか自動で決める仕組み。頼みを聞いて最短の探し方を考えるベテラン司書。

スキーマ schema

データの決められた形・型。図書館の目録カードの記入様式。

スキーマオンライト／オンリード

オンライト＝しまうとき様式を強制。オンリード＝取り出すときに解釈。書く時か読む時か。

宣言的 / 命令的

宣言的＝ほしい結果だけ言う（「○○の本ください」）。命令的＝探し方を全部指示（「棚を1段ずつ見て…」）。

MapReduce

大量データを多数のマシンで分担処理する仕組み。大勢の助手で手分けして数え、最後に合算する。

頂点（vertex）／辺（edge）

グラフの点と線。頂点＝人やモノ、辺＝そのつながり（関係）。系図の人物と続柄線。

プロパティグラフ／トリプルストア

グラフの2つの実装方式。後者は (主語,述語,目的語) の3つ組で表す。

Cypher／SPARQL／Datalog

グラフに問いかける宣言的言語3種。Datalogは最も古く、後の言語の礎。

RDF／セマンティックWeb

RDF＝コンピュータ可読データの記述方式。セマンティックWeb＝それで巨大なデータの網を作る構想。

あらすじ・要するに・なぜ必要か

この章で何を学ぶのか、最初に地図を持つ

「私の言語の限界は、私の世界の限界を意味する。」――ウィトゲンシュタイン『論理哲学論考』（1922）

あらすじ

前回、システムの3つの目標（こわれにくさ・大きくなっても平気・直しやすさ）を学んだハル。今日は「データそのものをどんな形でしまうか」という、もっと土台の話に踏み込みます。データを表（テーブル）にするのか、入れ子の書類（ドキュメント）にするのか、それとも点と線でつなぐ網（グラフ）にするのか――しまい方が変わると、できること・できないことが大きく変わる。カイ先輩は、昔の巨大システムの歴史から最新のNoSQLまでをたどりながら、ハルに「自分のアプリにはどの形が合うのか」を考える目を授けていきます。

🎯 要するに：データを「どんな形で表現するか」を決めるのがデータモデル。代表は3つ――表で整理するリレーショナル、入れ子の書類にするドキュメント、点と線でつなぐグラフ。それぞれ得意・不得意があり、データのつながり方（一対多か、多対多か）で向き不向きが決まる。さらに、その形に問いかける言葉（クエリ言語）にも「やり方を全部指示する命令型」と「ほしい結果だけ言う宣言型」があり、宣言型が主流。この章は、その選び方の地図を手に入れる回。

📚 たとえ話：これから「図書館の蔵書整理」の話をします

この章を通して、データ＝本（蔵書）、データモデル＝本のしまい方・並べ方、クエリ言語＝司書への頼み方に置きかえて読みます。同じ蔵書でも、棚に並べて索引カードで管理するか（リレーショナル）、関連書類を1冊に綴じるか（ドキュメント）、人物相関の系図で結ぶか（グラフ）で、探しやすさも変えやすさも全然違います。この「本のしまい方」選びが、この章ぜんぶを貫く合言葉です。

💡 なぜこれが必要か / これを知ったらできること

  • 問題の考え方が変わる：データモデルは書き方だけでなく「問題そのものの考え方」に影響する。最初に形を間違えると後でずっと苦しむ。
  • 雰囲気選びを卒業：「とりあえずMySQL」「とりあえずMongoDB」をやめ、データのつながり方から論理的に選べる。
  • 流行に振り回されない：リレーショナル vs NoSQL の論争は実は1960年代から繰り返された古い問題。歴史を知ると冷静に判断できる。
  • 使い分けられる：ツリー構造（一対多）か網目構造（多対多）かを見分け、3モデルを使い分けられる。宣言型クエリがなぜ速く並列化しやすいかも説明できる。
2.1

リレーショナルモデルとドキュメントモデル

いちばん有名なデータモデル ― 表と行のSQL
📌 要するに：リレーショナルモデルは1970年にCoddが提唱し、データを表（テーブル）と行（タプル）で整理する。1980年代半ばから30年近く支配的で、ビジネスデータ処理から始まって幅広い用途に広がった。ライバル（ネットワーク・階層・オブジェクト・XML）は現れては消えた。
ハル
新人 ハル先輩、自分のアプリを作ろうとすると最初の一歩で詰まるんです。「データをどうやってしまうか」が分からなくて……。
カイ
先輩 カイいいテーマだ。今日は「データをどんな形で表すか」、つまりデータモデルの話をしよう。これはソフト開発でいちばん大事な部分かもしれない。書き方だけじゃなく、僕らが問題そのものをどう考えるかにまで影響するんだ。
ハル
ハルただの「保存の仕方」じゃないんですね。
カイ
カイ現実の人やモノを、まずアプリのコードでオブジェクトとして表し、保存するときにJSON・テーブル・グラフといった汎用モデルで表し直す。その下ではバイト列、もっと下では電流や光……何層にもなってて、各層がきれいなモデルを提供して下の複雑さを隠してる。だから別々のグループが効率よく協力できるんだ。
ハル
ハルいちばん有名なデータモデルって何ですか？
カイ
カイたぶんSQLのモデルだ。1970年にEdgar Coddが考えたリレーショナルデータモデルが土台。データをリレーション＝テーブルとして整理し、1つのテーブルは順序のないタプル（行）の集まりなんだ。
ハル
ハルふだん見てるあの表ですね。最初から人気だったんですか？
カイ
カイ最初は理論で「効率よく実装できるのか」と疑われた。でも1980年代半ばにはRDBMSとSQLが定番の道具になり、それから25〜30年支配的だった。コンピュータの歴史では永遠とも思える長さだよ。
ハル
ハルもともと何のために？
カイ
カイ起源はビジネスデータの処理。1960〜70年代にメインフレームでやってた。代表は2つ。トランザクション処理（販売・銀行取引・予約・在庫確保みたいな入力処理）とバッチ処理（請求・給与・レポートを溜めてまとめてやる処理）。狙いはきれいなインターフェースで裏側の実装を隠すことだった。
ハル
ハルライバルはいなかったんですか？
カイ
カイたくさん現れては消えた。1970〜80年代初めはネットワークモデルと階層モデル、80年代終わりはオブジェクトDB、2000年代初めはXML DB。みんなブームを作ったが長続きせず、リレーショナルが圧倒した。しかも汎用性が高くて、Web出版・掲示板・SNS・eコマース・ゲーム・SaaSと幅広く使われ続けてる。

📚 たとえ話：背表紙ラベルと索引カードで管理する図書館

リレーショナルモデルは、本を棚にきちんと並べ、1冊ごとに索引カード（行）を作って、同じ様式のカードを引き出し（テーブル）にまとめるやり方です。著者名・出版年・分類…と決まった欄に書く。司書（DB）に「○○の本ください」と頼めば、複雑な探し方を知らなくても出てくる――裏側の手順を隠してくれるのが強み。だからどんなジャンルの蔵書でも回せる万能の整理術として、長く図書館を支配してきました。

💡 なぜこれが必要か / これを知ったらできること

  • 「テーブルと行」というありふれた形が、実は理論から生まれた強力なモデルだと理解できる。
  • リレーショナルDBがなぜ長く主流だったか（汎用性と実装の隠蔽）を説明できる。

📝 この項のまとめ

  • リレーショナルモデル＝データを「リレーション（テーブル）」と「タプル（行）」で表す。1970年Codd提唱。
  • RDBMSとSQLは1980年代半ばから30年近く支配的。
  • 起源はビジネスデータ処理（トランザクション処理とバッチ処理）。
  • 狙いは「きれいなインターフェースで実装の詳細を隠す」こと。
  • ネットワーク・階層・オブジェクト・XMLなどのライバルは長続きしなかった。
2.1.1

NoSQLの誕生

「SQLを使わない」ではなく「SQLだけじゃない」
📌 要するに：NoSQLは特定技術ではなく、もとはハッシュタグ由来の言葉で「Not Only SQL」の意。スケーラビリティ・オープンソース志向・特殊クエリ・スキーマ制約への不満が普及の背景。今後はリレーショナルと非リレーショナルを併用する「ポリグロットパーシステンス」が現実的。
ハル
ハル最近よく聞く「NoSQL」って、SQLを使わないってことですか？
カイ
カイそこが不幸な名前でね。「NoSQL」は特定の技術を指してない。もとは2009年に、リレーショナルじゃない分散DBの集まり（ミートアップ）のために使われた、目を引くTwitterのハッシュタグだっただけなんだ。
ハル
ハルえっ、ただのハッシュタグ！
カイ
カイでも妙に神経を刺激して急速に広まり、後づけでNot Only SQL（SQLだけじゃない）と解釈されるようになった。「使わない」じゃなく「だけじゃない」だ。
ハル
ハルなんでそんなに広まったんですか？
カイ
カイ理由は4つ。①リレーショナルでは出しにくいスケーラビリティ（巨大データ・高い書き込みスループット）が要った。②商用よりフリーでオープンなソフトが好まれた。③リレーショナルが苦手な特殊なクエリ操作があった。④スキーマの制約への不満と、もっと動的で表現力あるモデルへの欲求。
ハル
ハルじゃあこれからはNoSQLが主流に？
カイ
カイどっちかが勝つ話じゃない。アプリごとに要求が違うから、リレーショナルは幅広い非リレーショナルDBと併せて使われていく。この「複数のモデルを組み合わせて保存する」考え方をポリグロットパーシステンスと呼ぶよ。

📚 たとえ話：1つの整理術にこだわらない図書館

NoSQLは「索引カード方式（SQL）をやめる」のではなく、本の性質に合わせて整理術を選ぶという考え方です。ふつうの本は棚と索引カードで、関連書類は1冊に綴じて、人物資料は系図で――。1つの万能整理術にこだわらず、適材適所で混ぜて使う図書館。これがポリグロットパーシステンスです。

💡 なぜこれが必要か / これを知ったらできること

  • 「NoSQL＝SQLを使わない」という誤解を解き、用途に応じた併用という現実的な視点を持てる。
  • NoSQLが選ばれる4つの理由を知り、自分のアプリに当てはまるか判断できる。

📝 この項のまとめ

  • NoSQLはハッシュタグ由来の言葉で、後に「Not Only SQL」と解釈された。
  • 普及の理由：スケーラビリティ、フリー/オープン志向、特殊クエリ、スキーマ制約への不満。
  • 今後はリレーショナルと非リレーショナルを併用する（ポリグロットパーシステンス）。
2.1.2

オブジェクトとリレーショナルのミスマッチ

アプリのオブジェクトとテーブルがかみ合わない
📌 要するに：オブジェクト指向のコードとテーブルの間には変換の層が要り、これをインピーダンスミスマッチと呼ぶ。ORMで定型コードは減るが差は消えない。一対多の関係（履歴書のポジションや学歴）は、正規化テーブル・構造型/JSON型・テキスト列へのドキュメント保存の3通りで表せる。履歴書のような自己完結したツリー構造はJSONが向き、ローカリティ（関連データが1カ所）と木構造の明示という長所がある。
ハル
ハル今のアプリはオブジェクト指向で書きますよね。SQLと相性いいんですか？
カイ
カイそこがSQLへのよくある批判だ。データをテーブルに保存するなら、コードの中のオブジェクトとDBのテーブル・行・列の間に、不格好な変換の層が要る。このズレをインピーダンスミスマッチと呼ぶんだ。
ハル
ハルインピーダンス……？
カイ
カイもとは電子工学で、回路をつなぐとき両方の「電流の流れにくさ」が一致してると電力が最大限伝わり、合わないと信号が反射してトラブルになる。オブジェクトとテーブルの形が合わないとぎくしゃくする、というたとえだ。
ハル
ハルORMを使えば解決するって聞きました。
カイ
カイORM（ActiveRecordやHibernate）は変換の定型コードを減らしてくれる。でも2つのモデルの差を完全には隠せないんだ。
ハル
ハル具体例で見たいです。
カイ
カイLinkedInのプロフィール（履歴書）を考えよう。プロフィール全体はuser_idで指定でき、名・姓は一度しか出ないからusersテーブルの列にできる。でも仕事（ポジション）は複数、学歴も連絡先も数がバラバラ。これが一対多の関係だ。
ハル
ハル1人に複数ぶら下がる、と。どう表すんですか？
カイ
カイ3つある。①伝統的にposition・education・contactを別テーブルにして外部キー参照を張る＝正規化された表現。②SQLの構造データ型やXML型・JSON型を使い、複数値を1行に入れる。③ジョブ・学歴・連絡先をJSONやXMLのドキュメントにしてテキスト列に放り込む（ただし中身にクエリはかけられない）。
ハル
ハル履歴書みたいな「ほぼ自己完結した塊」ならJSONが向いてそうですね。
カイ
カイまさに。履歴書みたいなデータには、こんなJSONがぴったりだ。

一対多を表す3つの方法

🗂️

①別テーブル＋外部キー

position/education/contactを別の引き出しにし、IDで参照。正規化された表現。

正規化
🧩

②構造型/JSON型の列

複数値を1行の中に構造データ型・XML型・JSON型で入れる。

③テキスト列にドキュメント

2.1.3

多対一と多対多の関係

IDで参照する正規化 ― そしてドキュメントの弱点
📌 要するに：人間に意味のある値（地域名・業界名）は、複製せずIDで1カ所に保存するのが正規化の鍵。複製は更新負担と不整合を招く。正規化には多対一の関係が要るが、これはドキュメントモデルに不向きで、結合の弱いドキュメントDBではアプリ側で結合を真似ることになる。アプリが育つと組織のエンティティ化や推薦文のような多対多の関係が生まれ、参照と結合が必要になる。
ハル
ハルさっきのJSONでregion_idやindustry_idが数字のIDでしたよね。なんで「グレーターシアトル地域」みたいな文字列をそのまま入れないんですか？
カイ
カイいい着眼点だ。自由記述ならそのまま保存していい。でも地域や業界の標準化リストを用意してドロップダウンで選ばせる方式には、たくさんメリットがあるんだ。
カイ
カイ①スタイルやスペルを統一できる。②同名都市の曖昧さを排除。③更新が楽（名前は1カ所だから一気に直せる）。④ローカライズ（翻訳）しやすい。⑤検索性が上がる――「神奈川県の慈善家」検索で、リストに「横浜は神奈川県にある」と入れておけばマッチできる。文字列だけじゃどの県か分からないからね。
ハル
ハルIDにすると、いいことだらけ。でもなんでそんなに違うんですか？
カイ
カイ複製（コピー）の問題なんだ。IDを使えば意味のある情報（「慈善活動」って言葉）は1カ所だけに保存され、参照する場所はぜんぶIDを使う。テキストを直接保存すると、その情報を使うレコードすべてに複製される。
ハル
ハル複製すると何が困るんですか？
カイ
カイID自体は人間に意味がないから決して変える必要がない。でも意味のあるものはいつか変わる。そのとき複製されてたらコピー全部を更新しなきゃならず、書き込みの負担と不整合のリスク（一部だけ古いまま）を招く。この複製を取り除くのがDBの正規化の鍵だ。
ハル
ハル正規化って、その「ダブりをなくす」ことなんですね。
カイ
カイそう。正規化と非正規化は議論が尽きないテーマだけど、今は判断を保留する（第Ⅲ部で戻る）。さて、正規化すると多対一の関係が必要になる。1つの地域に多くの人が住み、1つの業界で多くの人が働く、というやつだ。
ハル
ハルその多対一は、ドキュメントモデルでも大丈夫ですか？
カイ
カイそこが弱点。多対一はドキュメントモデルにうまく合わない。リレーショナルは結合が簡単だけど、ドキュメントDBは一対多のツリーには結合が要らない代わりに、結合のサポートが弱いことが多い。
ハル
ハル結合がないと、どうするんですか？
カイ
カイアプリのコードで結合をエミュレート（真似て再現）する。DBに複数回クエリを投げる。この例なら地域・業界のリストは小さくゆっくりしか変わらないからメモリに持てるけど、結合の処理がDBからアプリに移ってきちゃうわけだ。
ハル
ハル最初はドキュメントでうまくいっても、後で困りそうですね。
カイ
カイまさに。機能が増えるとデータ同士がつながる。例えば①組織や学校のエンティティ化――organizationやschool_nameがただの文字列じゃなく「エンティティへの参照」になり、各組織が独自のWebページを持つ。②推薦文――あるユーザーが他のユーザーに推薦文を書け、書いた人の写真と一緒に表示される。推薦者が写真を更新したら表示にも新しい写真が反映されなきゃいけない。
ハル
ハル写真を複製して持ってたら、更新が反映されないですもんね。
カイ
カイその通り。だから推薦文は著者プロフィールへの参照を含む必要がある。こうした新機能は多対多の関係を生み、参照と結合が必要になるんだ。

意味のある情報は1カ所、他はIDで指す。
IDは不変。名前が変わっても1カ所直すだけ。

📚 たとえ話：ジャンル名は「請求記号」で1カ所に

もし全部の本のカードに「慈善活動」とジャンル名を手書きで写したら、ジャンル名が変わったとき何千枚ものカードを書き直す羽目になり、写し間違い（不整合）も起きます。だから図書館は、ジャンルに請求記号（ID）を1つ割り当て、各カードには記号だけ書く（正規化）。多くの本が同じジャンル記号を指す＝多対一です。さらに本同士が「この本はあの本を参照」と引用し合うと、人物相関の系図のような多対多の網になり、クロスリファレンスカード（参照＝結合）でたどる必要が出てきます。これがドキュメント（1冊綴り）方式の苦手な領域です。

  • 多対一・多対多の関係がドキュメントモデルに不向きだと理解し、結合の必要性を見越せる。
  • アプリの成長でデータがつながっていく（多対多が現れる）ことを予測して設計できる。

📝 この項のまとめ

  • 値を直接保存＝複製、IDで参照＝正規化（1カ所に保存）。複製は更新負担と不整合の原因。
  • IDは意味を持たないので変える必要がない。これが正規化の利点。
  • 正規化には多対一の関係が必要だが、ドキュメントモデルには不向き（結合が弱い）。
  • アプリの成長で多対多の関係（組織のエンティティ化、推薦文など）が生まれ、参照と結合が要る。
2.1.4

ドキュメントデータベースは歴史を繰り返すのか？

多対多と結合の悩みは半世紀前からあった
📌 要するに：多対多と結合をめぐる議論はNoSQLよりずっと古く、1970年代のIMS（階層モデル）にさかのぼる。階層モデルはJSON同様のツリー構造で、一対多は得意だが多対多と結合が苦手。これは今のドキュメントDBの悩みとそっくり。当時の解決策がリレーショナルモデルとネットワークモデルで、両者は「大論争」を繰り広げた。
ハル
ハル多対多と結合の弱点、最近の議論ですか？
カイ
カイ実はずっと古い。最初期のコンピュータDBまでさかのぼる。1970年代、ビジネスデータ処理で最も使われたのがIBMのIMS（Information Management System）。もともとアポロ宇宙計画の在庫管理のために作られ、1968年に商用リリースされた。今でもIBMのメインフレームで動いてるんだ。
ハル
ハル50年以上前のDBが現役！ どんな仕組みですか？
カイ
カイIMSは階層モデルというごく単純なモデルを使う。これがドキュメントDBのJSONモデルにそっくりで、すべてのデータをレコードが入れ子になったツリーで表すんだ。
ハル
ハルじゃあIMSも同じ弱点を……？
カイ
カイその通り。IMSは一対多はうまく扱えるけど多対多が苦手で、結合もサポートしてない。開発者はデータを複製（非正規化）するか、レコードからレコードへの参照を自分でたどるか選ぶしかなかった。今のドキュメントDBの悩みとそっくりだろ？ だから「歴史を繰り返すのか？」って問いになる。
ハル
ハル当時、その弱点をどう解決したんですか？
カイ
カイいろんな方法が提案され、中でも傑出したのが2つ。リレーショナルモデル（これがSQLになって世界を制覇）とネットワークモデル（最初は支持を集めたが廃れた）。この2陣営の「大論争」が1970年代を通じて続いた。今でも意味があるから振り返ろう。

📚 たとえ話：「1冊にまとめる綴じ方」は昔も今も同じ壁にぶつかる

IMSの階層モデルは、まさに今のドキュメント（1冊綴り）方式の祖先です。1冊の中に章を入れ子にする一対多は得意。でも「この本とあの本が互いに引用し合う」多対多の網になると、綴じ方では表せず、いちいち別の本を手作業でたどるしかない。半世紀前の図書館員が悩んだのと、今のエンジニアが悩むのは同じ壁なのです。

💡 なぜこれが必要か / これを知ったらできること

  • 今のドキュメントDBの弱点が、半世紀前の階層モデルの問題の再来だと歴史的に理解できる。
  • 流行（NoSQL）に飛びつく前に、過去の教訓から学ぶ姿勢を持てる。

📝 この項のまとめ

  • 1970年代のIMSは階層モデル（ツリー構造）で、JSONに似ている。
  • 階層モデルは一対多が得意、多対多と結合が苦手（今のドキュメントDBと同じ）。
  • 階層モデルの制約への解決策がリレーショナルモデルとネットワークモデル。
  • 両者の大論争が1970年代に続いた。
2.1.4.1

ネットワークモデル（CODASYL）

手で道順をたどる ― 柔軟性に欠ける旧モデル
📌 要するに：ネットワークモデル（CODASYL）は階層モデルを一般化し、レコードが複数の親を持てるので多対一・多対多が表せる。リンクはポインタのようなもので、ルートからアクセスパスをたどってデータに到達する。当時の貧弱なハードには効率的だったが、コードが複雑で柔軟性に欠け、データモデルの変更が困難だった。
ハル
ハルまずネットワークモデルから。どんなものですか？
カイ
カイCODASYLという協議会で標準化されたからCODASYLモデルとも呼ぶ。階層モデルを一般化したものだ。
ハル
ハル一般化、というと？
カイ
カイ階層モデルのツリーではどのレコードも親を必ず1つだけ持つ。でもネットワークモデルではレコードが複数の親を持てる。例えば「グレーターシアトル地域」レコードに、その地域に住む全ユーザーがリンクできる。これで多対一や多対多が表せる。
ハル
ハルリンクって、外部キーみたいなもの？
カイ
カイちょっと違う。外部キーじゃなく、プログラミング言語のポインタみたいなもの（ただしディスク上に保存）。レコードにアクセスする唯一の方法は、ルート（根っこ）から、リンクの連鎖に沿ってパスをたどること。これをアクセスパスと呼ぶ。
ハル
ハル道順をたどっていくんですね。
カイ
カイそう。単純だとリンクリスト（数珠つなぎ）をたどる感じ。でも多対多があると同じレコードへのパスが複数でき、プログラマは複数パスを追跡しなきゃならない。CODASYLのクエリは、リストを繰り返し処理してアクセスパスをたどり、DB内でカーソルを動かす。協議会メンバーすら「n次元のデータ空間を航行してるようだ」と認めてる。
ハル
ハル大変そう……なんでそんな面倒なやり方を？
カイ
カイ1970年代のハードがきわめて限られてたから。テープドライブはシーク（位置移動）が極端に遅く、手動でアクセスパスを選ぶのが限られたハードを最も効率よく使う方法だった。でも代償としてクエリや更新のコードが複雑で柔軟性に欠けるものになった。
ハル
ハル柔軟性がないと、何が困るんですか？
カイ
カイ求めるデータへのパスが分かってない状況がやっかいだ。アクセスパスは変更できるけど、その場合プログラマは大量のクエリを全部調べて書き換えなきゃいけない。つまりデータモデルに変更を加えるのが難しかったんだ。

📚 たとえ話：目当ての本まで「順路を全部自分で指示」する図書館

ネットワークモデルは、「入口から3番目の棚へ行き、左の列の上から5冊目、そこから紐でつながった次の本へ…」と道順（アクセスパス）を司書に逐一指示しないと本が出てこない図書館です。本棚の配置を少しでも変えたら、書き留めた順路メモを全部書き直す羽目に。これが「変更しにくい」という弱点でした。

💡 なぜこれが必要か / これを知ったらできること

  • 「手動でアクセスパスをたどる」古い方式の発想と、その欠点（変更の困難さ）を理解できる。
  • なぜリレーショナルモデルが革命的だったのかを、対比で深く理解できる。

📝 この項のまとめ

  • ネットワークモデル＝CODASYLモデル。階層モデルの一般化でレコードが複数の親を持てる。
  • 多対一・多対多が表せる。リンクはポインタ的で、アクセスパスをたどってアクセスする。
  • 当時のハードには効率的だが、コードが複雑・柔軟性不足でモデル変更が難しかった。
2.1.4.2

リレーショナルモデル

道順は不要 ― オプティマイザが自動で選ぶ
📌 要するに：リレーショナルモデルはデータをオープンに配置し、複雑なアクセスパスを手でたどる必要がない。どのインデックスをどの順で使うかはクエリオプティマイザが自動判断するので、開発者は意識せずに済み、新しいインデックスを宣言するだけで新機能を追加できる。オプティマイザの構築は大変だが、一度作れば全アプリが恩恵を受ける。
ハル
ハル対するリレーショナルモデルは、何が違ったんですか？
カイ
カイ発想が真逆。すべてのデータがオープンに配置される。リレーション（テーブル）は単なるタプル（行）の集まりで、それだけ。込み入った構造もなく、データを見るために複雑なアクセスパスをたどる必要もない。
ハル
ハルアクセスパスがいらない？ じゃあどうやって読むんですか？
カイ
カイ行はどれか1つ読んでも全部読んでもいい。任意の条件にマッチする行を選べるし、いくつかの列をキーに特定の行を読める。外部キー関係を気にせず任意のテーブルに新しい行を追加できる。自由なんだ。
ハル
ハルでも、どのインデックスをどの順で処理するか、誰が決めるんですか？
カイ
カイそこが肝心。クエリオプティマイザが、クエリ各部の実行順序やどのインデックスを使うかを自動判断する。事実上「アクセスパス」を選ぶんだが、違いは開発者じゃなくオプティマイザが自動で決めること。だから開発者はたいてい気にしなくていい。
ハル
ハル新しい検索の仕方をしたくなったら？
カイ
カイ新しいインデックスを宣言するだけ。するとクエリは最適なインデックスを自動で使う。書き直さなくても活用される。だからリレーショナルは新機能を足すのがはるかに楽なんだ。
ハル
ハルオプティマイザを作るの、すごく大変そうですけど。
カイ
カイその通り、複雑な代物で長年研究されてきた。でも肝心なのは一度作れば、そのDBを使う全アプリが恩恵を受けること。特定クエリのためにアクセスパスを手書きするより、長い目で見れば汎用的な解が勝つんだ。

📚 たとえ話：頼めば最短の探し方を考えてくれるベテラン司書

リレーショナルモデルでは、利用者は「○○についての本ください」とほしい結果だけを伝えればいい。順路はベテラン司書（クエリオプティマイザ）が「この索引から引いて、こう棚をたどれば最短」と自動で考えてくれます。新しい探し方が欲しければ新しい索引（インデックス）を1つ作るだけ。利用者は頼み方を変えずに済みます。この優秀な司書を一度育てれば、全利用者がその恩恵を受けるのです。

💡 なぜこれが必要か / これを知ったらできること

  • クエリオプティマイザが「アクセスパスを自動で選ぶ」役割を理解し、宣言的に書ける利点を説明できる。
  • 新しいインデックスを宣言するだけで最適化される、という柔軟性の高さを理解できる。

📝 この項のまとめ

  • リレーショナルモデルはデータをオープンに配置、複雑なアクセスパスは不要。
  • どのインデックス・どの順で実行するかはクエリオプティマイザが自動判断。
  • 新しいインデックスを宣言するだけで活用され、新機能追加が楽。
  • オプティマイザの構築は大変だが、一度作れば全アプリが恩恵を受ける（汎用解が勝つ）。
2.1.4.3

ドキュメントデータベースとの比較

似て非なる ― CODASYLの轍は踏んでいない
📌 要するに：ドキュメントDBは一対多をツリーの中に入れ子にする点で階層モデルに回帰している。しかし多対一・多対多は、リレーショナルもドキュメントも一意の識別子（外部キー／ドキュメント参照）で参照し、読み取り時に解決する点で本質的に同じ。参照を挿入時に固定したCODASYLとは違い、ドキュメントDBはその轍を踏んでいない。
ハル
ハルじゃあ今のドキュメントDBは、昔のネットワークモデルの再来なんですか？
カイ
カイ慎重に見たほうがいい。ドキュメントDBは1つの面では階層モデルに回帰してる。ネストされたレコード（履歴書のpositions・education・contact_infoみたいな一対多）を、独立テーブルじゃなく親のレコードの中に保存してる点だ。
ハル
ハルツリーの中に入れ子にする、という点ですね。
カイ
カイそう。でも多対一・多対多の表現という点では、リレーショナルとドキュメントに基本的な違いはない。どちらも関連アイテムを一意の識別子で参照する。リレーショナルでは外部キー、ドキュメントではドキュメント参照と呼ぶけど、やってることは同じ。その識別子は結合やフォローアップのクエリで読み取り時に解決される。
ハル
ハルあ、じゃあ昔のCODASYLとは違うんですね。
カイ
カイそこが大事。CODASYLは参照を挿入時に解決して固定しちゃってたけど、ドキュメントDBは読み取り時に解決する。だから今のところドキュメントDBは、CODASYLのたどった道（柔軟性のない手動アクセスパス）を繰り返してはいないんだ。

📚 たとえ話：参照は「読むときにたどる」現代の図書館

昔のCODASYLは、本を棚に入れるその瞬間に紐で別の本へ固定的に結びつけて、後から配置を変えにくくしました。今のドキュメントDBやリレーショナルは、カードに「○○を参照」と請求記号を書いておくだけ。実際にたどるのは読みたくなったときです。だから配置換えも自由。同じ「参照」でも、固定するか・読むときたどるかが、柔軟性の決定的な差なのです。

💡 なぜこれが必要か / これを知ったらできること

  • ドキュメントDBと階層/ネットワークモデルの「似て非なる」点を区別できる。
  • 外部キーとドキュメント参照が本質的に同じ仕組み（読み取り時に解決）だと理解できる。

📝 この項のまとめ

  • ドキュメントDBは一対多をツリーに入れ子にする点で階層モデルに回帰。
  • 多対一・多対多はリレーショナル（外部キー）もドキュメント（ドキュメント参照）も識別子で参照、読み取り時に解決。
  • 挿入時に参照を固定したCODASYLとは異なり、ドキュメントDBはその欠点を繰り返していない。

今日のリレーショナルデータベースとドキュメントデータベース

それぞれの強み ― この章はデータモデルに集中

ハル
ハル結局、リレーショナルとドキュメント、どっちを選べばいいんですか？
カイ

ハルデータモデルの観点だと、それぞれの強みは？

2.1.5.1

アプリのコードをシンプルにするモデルは？

データの形しだい ― 関係が強いほどグラフが自然
📌 要するに：コードがシンプルになるモデルはデータの形による。一対多のツリーで全体を一度に読むならドキュメントが向く（リレーショナルだと細分化で複雑化）。ドキュメントはネスト要素を直接参照できず、多対多が必要だと魅力が薄れる（非正規化やエミュレートでコード複雑化・性能低下）。関係性が強いほどグラフモデルが自然。
ハル
ハルどっちのモデルだと、アプリのコードがシンプルになりますか？
カイ
カイデータの形による。アプリのデータがドキュメントのような構造――一対多のツリーで、ふつうツリー全体を一度にロードする――ならドキュメントモデルがいい。これをリレーショナルでやると細分化（shredding）といって、ドキュメント的構造を複数テーブルにバラすことになり、スキーマが込み入ってコードが不必要に複雑になる。
ハル
ハルドキュメントモデルに弱点はないんですか？
カイ
カイあるよ。ドキュメント内にネストされたアイテムは直接参照できない。「ユーザー251のポジションのリストの2番目」みたいに指定しなきゃいけない。階層モデルのアクセスパスに似てる。ただネストが深すぎなければ普通は問題にならない。
ハル
ハル結合が弱いのは、いつも困るんですか？
カイ
カイアプリ次第。例えばイベントと発生時刻を記録する分析アプリなら多対多が要らないかもしれず、問題にならない。でも本当に多対多が必要なら魅力は薄れる。非正規化で結合の必要性を下げられるけど、その分「非正規化データの整合性を保つ処理」が増える。結合をアプリから複数リクエストでエミュレートもできるけど、コードは複雑になりDB内の特化コードより遅くなる。
ハル
ハルじゃあ結局、どっちがシンプルって一概には言えない？
カイ
カイ一般論では言えない。データのアイテム間の関係の種類による。関係性が強い（つながりが多い）と、ドキュメントは扱いにくく、リレーショナルは許容範囲、そしてグラフモデルが最も自然になる。グラフは2.3で扱うよ。
1

一対多のツリー（関係が少ない）

全体を一度に読むならドキュメントが向く。リレーショナルだと細分化で複雑化。

2

多対多が必要（関係が中くらい）

リレーショナルが許容範囲。ドキュメントは非正規化・エミュレートで複雑化・低速化。

3

つながりが複雑（関係が強い）

グラフが最も自然（→ 2.3で）。

📚 たとえ話：資料の「つながり具合」で綴じ方を選ぶ

1人分でまとまる履歴書のような資料は1冊に綴じる（ドキュメント）のが一番シンプル。これを無理に何冊もの薄い冊子にバラす（細分化）と、いちいち集めて回る手間が増えます。でも資料同士が引用し合う多対多なら棚＋索引（リレーショナル）が無難。さらに「誰と誰がどうつながるか」が主役の資料は、もう人物相関の系図（グラフ）で描くのが一番自然です。

💡 なぜこれが必要か / これを知ったらできること

  • データの関係の種類（ツリーか網目か）からモデルを選べる。
  • ドキュメントモデルの制約（直接参照不可、結合の弱さ）を踏まえて判断できる。

📝 この項のまとめ

  • 一対多のツリーで全体を一度に読むならドキュメント向き（リレーショナルは細分化で複雑化）。
  • ドキュメントはネスト要素を直接参照できない（アクセスパス的）。
  • 多対多が必要だとドキュメントの魅力は薄れる（非正規化・エミュレートで複雑化・低速化）。
  • どれがシンプルかは関係の種類次第。関係が強いほどグラフが自然。
2.1.5.2

ドキュメントモデルにおけるスキーマの柔軟性

スキーマオンリード vs スキーマオンライト
📌 要するに：ドキュメントDBはスキーマを強制しないスキーマオンリード（読み取り時に構造を解釈）で、リレーショナルのスキーマオンライト（書き込み時に強制）の逆。動的型/静的型チェックの対比に似て優劣はない。フォーマット変更時に差が出る（アプリ側で補う vs マイグレーション）。スキーマ変更は必ずしも遅くない。構造が不均一なデータにはスキーマオンリードが、均一なデータにはスキーマが有益。
ハル
ハルさっき保留した「スキーマがない」話、ここですね。スキーマって何でしたっけ？
カイ
カイスキーマは「データの決められた形・型」だ。多くのドキュメントDBやリレーショナルのJSONサポートは、ドキュメント内のデータにスキーマを強制しない。任意のキーと値を追加でき、読み取り時にどんなフィールドが入ってるか保証がない。
ハル
ハルドキュメントDBは「スキーマレス」って聞きます。
カイ
カイその言い方は誤解を招く。データを読むコードは普通「何らかの構造があること」を前提にしてる。つまり暗黙にスキーマを想定してるけどDBが強制しないだけ。だから正確にはスキーマオンリードと呼ぶ。逆にリレーショナルの伝統はスキーマオンライトだ。
ハル
ハル読むとき解釈するか、書くとき強制するか、ですね。プログラミングの何かに似てます？
カイ
カイいいところに気づいた。スキーマオンリードは動的（実行時）型チェック、スキーマオンライトは静的（コンパイル時）型チェックに似てる。静的派と動的派が大論争してきたように、これも物議を醸す話題で一般に正しい・間違いはない。
ハル
ハル違いがいちばん出るのは、どんな時ですか？
カイ
カイデータのフォーマットを変更するときだ。例えばフルネーム1フィールドを姓と名に分けたいとする。ドキュメントDBなら、新フィールドで以後のドキュメントを書き始めて、古いのを読んだときの処理をアプリに持たせるだけでいい。こんな感じだ。

このコードは、古い形式（氏名がまとめて1つに入っている）のデータを読んだとき、その場で「名」を取り出して補う処理です。

ドキュメントDB：読み取り時に補う（JavaScript） 
// 古い形式のドキュメント（name に氏名がまとめて入っている）を
// 読んだときに、first_name（名）をその場で補う処理。
// user は1人分のプロフィール、name は「太郎 山田」のような氏名の文字列。
if (user && user.name && !user.first_name) {
    // ① 2013年12月8日より前に書かれたドキュメントには first_name がない
    user.first_name = user.name.split(" ")[0]; // ② name を空白で区切って先頭（名）を取り出す
}
カイ
カイ①のコメント通り、古いデータには新フィールドがない。②で空白区切りの先頭をfirst_nameにする。読み取り時に埋めてるわけだ。一方「静的な型付き」のDBスキーマだと、ふつうマイグレーションをこう実行する。

このSQLは、テーブルに「名」の列を新しく追加し、既存の氏名から名を取り出して埋める移行作業です。

リレーショナル：マイグレーション（SQL） 
-- users テーブルに first_name 列を追加し、既存の name から名を埋めるマイグレーション
ALTER TABLE users ADD COLUMN first_name text;             -- ① 新しい列を追加
UPDATE users SET first_name = split_part(name, ' ', 1);   -- ② PostgreSQL: name を空白で区切り先頭を入れる
UPDATE users SET first_name = substring_index(name, ' ', 1); -- ② MySQL: 同じことを MySQL の関数で
ハル
ハルスキーマ変更って、遅くてダウンタイム（停止時間）が出るって聞きました。
カイ
カイその評判は必ずしも妥当じゃない。多くのリレーショナルDBはALTER TABLEを数ミリ秒で処理する。例外はMySQLで、テーブル全体をコピーするから大きいテーブルだと数分〜数時間のダウンタイムが出ることがある。でも回避ツールもいろいろあるんだ。
ハル
ハルUPDATEのほうは？
カイ
カイ大きいテーブルへのUPDATEは全行を書き直すからどのDBでも遅い。許容できないなら、ドキュメントDBと同じくfirst_nameをデフォルトのNULLのままにして、読み取り時に埋める手もある。
ハル
ハルスキーマオンリードが得なのは、どんな場合ですか？
カイ
カイアイテムの構造がバラバラ（ヘテロジニアス＝不均一）な場合だ。①種類の違うオブジェクトが多くて種類ごとに別テーブルにするのが非現実的、②データ構造が外部システムで決まり制御できずいつ変わるか分からない。こういう時はスキーマがデメリットになりがちで、スキーマレスのほうが自然だ。
ハル
ハル逆に、みんな同じ構造なら？
カイ
カイ全レコードが同じ構造だと期待できるなら、スキーマは「ドキュメント化」と「構造の強制」の点で有益だ。スキーマとその進化は4章で詳しく扱うよ。
観点スキーマオンライト（リレーショナル）スキーマオンリード（ドキュメント）
いつ構造を扱う書き込み時に強制（事前に明示）読み取り時に解釈（強制しない）
似ている型チェック静的（コンパイル時）型チェック動的（実行時）型チェック
フォーマット変更マイグレーション（ALTER/UPDATE）アプリで読み取り時に補完
向くデータ全レコードが均一な構造不均一・外部依存で変わる構造

📚 たとえ話：目録カードの様式を「いつ」そろえるか

スキーマオンライトは、本を受け入れるその場で、決まった様式の目録カードに書かせてはじき出す厳格な受付（書く時にそろえる）。スキーマオンリードは、とりあえずどんなメモでも受け取り、あとで取り出すときに読み手が解釈するゆるい受付（読む時にそろえる）。どんな本でも様式がバラバラに来る（不均一）なら、ゆるい受付が楽。逆にぜんぶ同じ種類なら、最初に様式をそろえたほうが後で混乱しません。

💡 なぜこれが必要か / これを知ったらできること

  • スキーマオンリードとスキーマオンライトの違いを、型チェックの対比で説明できる。
  • データのフォーマット変更時の対応（読み取り時補完 vs マイグレーション）を選べる。
  • 不均一なデータか均一なデータかでスキーマの要否を判断できる。

📝 この項のまとめ

  • スキーマレスは誤解を招く語。正確には「スキーマオンリード」（読み取り時に解釈）。
  • 対するリレーショナルは「スキーマオンライト」（書き込み時に強制）。動的型/静的型に似て優劣なし。
  • フォーマット変更時、ドキュメントはアプリで補完、リレーショナルはマイグレーション。
  • スキーマ変更は必ずしも遅くない（MySQLは例外、回避ツールあり）。
  • 不均一なデータにはスキーマオンリードが、均一なデータにはスキーマが有益。
2.1.5.3

クエリのためのデータローカリティ

全体を一度に取れる利点と、全体を読む弱点
📌 要するに：ドキュメントは連続した文字列やバイナリで保存され、全体を一度に使うならローカリティで性能が上がる。だが一部しか使わなくても全体をロード・書き直すので、ドキュメントは小さく保つべき。ローカリティの着想はドキュメント専用ではなく、Spannerのインターリーブ、Oracleのクラスタテーブル、Bigtableのカラムファミリーでもリレーショナル/その他で実現される。
ハル
ハルローカリティの話、もう少し詳しく聞きたいです。
カイ
カイドキュメントは普通、JSON/XMLとしてエンコードした連続した文字列か、バイナリ型（MongoDBのBSONなど）で保存される。アプリが多くの場合ドキュメント全体にアクセスする（Webページ表示のためなど）なら、このストレージのローカリティに性能上のメリットがあるんだ。
ハル
ハル全体を一気に取れるから速い、ですね。
カイ
カイそう。複数テーブルに分かれてると、全部取るのに複数回のインデックスのルックアップが要り、ディスクのシークも増えて時間がかかる。でもローカリティの恩恵は、一度にドキュメントの大部分が必要になる場合に限られる。
ハル
ハル一部しか要らないときは？
カイ
カイそこが弱点。一部しか使わなくてもDBはドキュメント全体をロードする。大きいドキュメントだと無駄が多い。更新も同じで全体を書き直す（その場で上書きできるのはサイズが変わらない場合だけ）。だからドキュメントは小さく保ち、サイズを大きくする書き込みは避けるのが望ましい。この制約のせいで、ドキュメントDBが有効な状況はかなり減るんだ。
ハル
ハルローカリティって、ドキュメントモデルだけの話ですか？
カイ
カイいや、専用じゃない。GoogleのSpannerはテーブルの行を親テーブルの中にインターリーブ（ネスト）できるとスキーマで指定でき、リレーショナルでも同じローカリティを実現する。Oracleのマルチテーブルインデックスクラスタテーブルも似てるし、Bigtableのカラムファミリー（Cassandra/HBaseで使う）も同じ目的を持つ。ローカリティは3章でもまた見るよ。
⚡

利点

全体を一度に使うなら、複数回のルックアップやシークが要らず速い。

🐢

弱点

一部しか使わなくても全体をロード・書き直す。大きいと無駄。だから小さく保つ。

📚 たとえ話：分厚い綴りは「一冊まるごと出し入れ」になる

1冊にまとめた書類綴り（ドキュメント）は、全部を読みたいときは一度手に取るだけで済んで速い。でもたった1ページの数字を直したいだけでも、分厚い綴りを丸ごと取り出して綴じ直す羽目になります。だから綴りは薄く保つのがコツ。ちなみに「関連資料をまとめて近くに置く」工夫は綴り方式の専売特許ではなく、棚方式（リレーショナル）でも、関連する本を隣同士に並べる（Spannerのインターリーブ等）形で実現できます。

2.2

データのためのクエリ言語

宣言的（ほしい結果だけ）vs 命令的（手順を全部）
📌 要するに：SQLは宣言的（ほしい結果のパターンだけ指定）、IMS/CODASYLは命令的（手順を全部指定）。宣言的の利点は3つ――簡潔で扱いやすい、実装の詳細を隠すのでクエリを変えずに性能改善できる、結果のパターンだけ指定するので並列化しやすい（マルチコア時代に有利）。
ハル
ハルデータの「形」が分かりました。次は、それに「問いかける言葉」ですね。
カイ
カイそう、クエリ言語だ。SQLは宣言的クエリ言語で、対するIMSやCODASYLは命令的コードでクエリしてた。この違い、何を意味すると思う？
ハル
ハル宣言的と命令的……言葉は聞きますけど、はっきりとは。
カイ
カイ例で見よう。動物の種のリストから「サメだけ」返したい。多くのプログラミング言語は命令的で、こう書く。

このコードは、動物のリストを1つずつ見て、「サメ科」のものだけを集めて返す関数です（手順を全部自分で書く＝命令的）。

命令的なやり方（JavaScript） 
// 動物のリスト animals から「サメ科」のものだけ集めて返す関数（命令的なやり方）。
// animals は動物の配列、各動物は family（科）という属性を持つ。
function getSharks() {
    var sharks = [];                              // ① 結果を入れる空の入れ物を用意
    for (var i = 0; i < animals.length; i++) {    // ② 動物を1つずつ順番に見ていく
        if (animals[i].family === "Sharks") {     // ③ 科が「サメ」なら
            sharks.push(animals[i]);              // ④ 結果の入れ物に追加する
        }
    }
    return sharks;                                // ⑤ 集めたサメを返す
}
カイ
カイ「入れ物を用意して、ループを回して、条件を見て、追加して…」と手順を全部指定してるよね。これが命令的。一方、数学の関係代数ではこう書ける。
関係代数（数式） 
# σ（シグマ）は選択演算子。family が "Sharks" の動物だけを返す。
sharks = σ_(family = "Sharks") (animals)
カイ
カイσ（シグマ、selectionのs）は選択演算子で、family = "Sharks"にマッチする動物だけ返す。SQLは定義時、関係代数の構造にきわめて忠実に沿ってた。だから同じことがSQLでこう書ける。

このSQLは、テーブルから「サメ科」の行だけを全部取り出すよう頼むものです（ほしい結果だけ言う＝宣言的）。

宣言的なやり方（SQL） 
-- animals テーブルから family が「サメ」の行だけ全部取り出すSQL（宣言的なやり方）
SELECT * FROM animals WHERE family = 'Sharks';
ハル
ハルSQLのほう、すごく短い！ さっきのループが1行に。
カイ
カイそこが宣言的の特徴。命令型は「指定した操作を指定した順序で行え」と指示する。でも宣言的なSQLや関係代数は、ほしいデータのパターンと、どう変換するか（ソート・グループ化・集計）だけを指定し、どうやって達成するかは指定しない。どのインデックス・どの結合方法・どの順かはDBのクエリオプティマイザに任せる。
ハル
ハルなんで宣言的のほうがいいんですか？
カイ
カイ3つ。1つめ、命令型より簡潔で扱いやすい。2つめ、もっと重要で、DBエンジンの実装の詳細を隠すから、クエリを書き換えなくてもDB側が性能を改善できる。
ハル
ハル性能を改善できる、というのは？
カイ
カイ命令型コードは動物が特定の順序で並んでた。DBが裏で未使用領域を回収しようとレコードを動かして順序を変えたいとする。命令型だと順序に依存してるかDBに分からず勝手に動かせない。でもSQLは順序を保証してないから気にしなくていい。SQLは機能面の制約が強いからこそ、自動最適化の余地が大きいんだ。
ハル
ハル3つめは？
カイ
カイ並列実行に向いてること。今どきのCPU高速化は、クロックを上げるんじゃなくコア数を増やす形で進む。命令型は特定の順序で実行する命令を指定するから並列化がすごく難しい。でも宣言型は「結果のパターン」だけ指定して「アルゴリズム」は指定しないから、DBが自由に並列実装を使えて高速化しやすいんだ。
📜

命令的

手順を順序通り全部指定（forループ）。順序に依存し、並列化が難しく、最適化に書き直しが要る。

🎯

宣言的

ほしい結果のパターンだけ指定（SQL）。簡潔・実装を隠して最適化できる・並列化しやすい。

📚 たとえ話：司書への2通りの頼み方

命令的とは、「入口から3番目の棚へ行って、上から順に背表紙を見て、『サメ』と書いてあったら抜き出して…」と探し方を逐一指示すること。宣言的とは、「サメの本、ぜんぶください」とほしい結果だけ伝えること。後者なら、司書（オプティマイザ）が新しい索引を作って探し方を改善しても、あなたは頼み方を変えずに済むし、何人もの司書が手分けして同時に探す（並列化）こともできます。だから宣言的のほうが賢いのです。

💡 なぜこれが必要か / これを知ったらできること

  • 命令型と宣言型の違いを、コード例で具体的に説明できる。
  • なぜSQLが性能改善・並列化しやすいか（実装の詳細を隠す、順序に依存しない）を理解できる。

📝 この項のまとめ

  • 命令的＝手順を順序通り指定（forループなど）。宣言的＝ほしい結果のパターンだけ指定（SQL、関係代数）。
  • SQLは関係代数（選択演算子σなど）に忠実に沿って作られた。
  • 宣言型の利点：簡潔、実装を隠して性能改善できる、並列化しやすい。
  • 命令型は順序依存で並列化が難しい。宣言型はマルチコア時代に有利。
2.2.1

Web上での宣言的クエリ

CSSは宣言的、JavaScript+DOMは命令的
📌 要するに：宣言的の優位はDB外でも成り立つ。Webでは、要素のスタイル指定をCSS/XSL（宣言的）でやるほうが、JavaScript+DOM API（命令的）よりはるかに優れる。命令的だとコードが長く、状態変化への自動追従ができず（selectedが外れても青が消えない）、新しいAPIへの最適化に書き直しが要る。同じ理屈でDBもSQLが優れる。
ハル
ハル宣言的のよさって、DBだけの話ですか？
カイ
カイいや、まったく別の環境でも同じだ。Webブラウザで比べよう。海の動物のサイトで、ユーザーが今サメのページを見てて、ナビの「Sharks」を「選択中」とマークしたい。HTMLはこうだ。

このコードは、海の動物のメニュー（ナビゲーション）の骨組みです。「selected」が今選ばれている項目を表します。

ナビゲーションのHTML 
<!-- 海の動物のナビゲーション。selected クラスが「今選ばれている項目」を表す。 -->
<ul>
    <li class="selected">                <!-- ① 選択されている項目は selected クラスでマーク -->
        <p>サメ</p>                       <!-- ② これが現在選択されているページ -->
        <ul>
            <li>ホホジロザメ</li>
            <li>イタチザメ</li>
            <li>シュモクザメ</li>
        </ul>
    </li>
    <li>
        <p>クジラ</p>
        <ul>
            <li>シロナガスクジラ</li>
            <li>ザトウクジラ</li>
            <li>ナガスクジラ</li>
        </ul>
    </li>
</ul>
カイ
カイ①で選択中をselectedクラスでマークし、②が選択中のページ。さて、このページのタイトルの背景を青くしたい。CSSならこう書ける。

このコードは「selectedが付いた項目の中のタイトルを青くする」というルールを宣言するものです。

宣言的：CSS 
/* selected クラスを持つ <li> の直接の子である <p> の背景を青くする */
li.selected > p {
    background-color: blue;
}
カイ
カイ青くしたい要素のパターンをCSSのセレクターli.selected > pで宣言してる。意味は「selectedクラスを持つ<li>を直接の親とする全ての<p>」。サメはマッチするが、クジラは親にselectedがないのでマッチしない。
ハル
ハルCSSも宣言的なんですね。XSLとかでも？
カイ
カイできるよ。CSSの代わりにXSLを使ってもいい。

このコードは、CSSと同じ「選択中の項目のタイトルを青くする」指定を、XSLという別の宣言的言語で書いたものです。

宣言的：XSL 
<!-- XSL: class が selected の li の中の p を青い背景にするテンプレート -->
<xsl:template match="li[@class='selected']/p">
    <fo:block background-color="blue">
        <xsl:apply-templates/>
    </fo:block>
</xsl:template>
カイ
カイこのXPathの式li[@class='selected']/pは、さっきのCSSセレクターli.selected > pと同じ意味だ。CSSもXSLも、どちらも宣言的な言語ってこと。
ハル
ハルもし命令的にやったら、どうなるんですか？
カイ
カイJavaScriptでDOM（HTMLをプログラムで操作する仕組み）APIを使うとこうなる。

このコードは、すべての項目を1つずつ調べて「selectedのものの中のタイトル」を探し、見つけたら青くする、という手順を全部書いたものです。

命令的：JavaScript + DOM API 
// すべての <li> を調べ、selected クラスのものの中の <p> を青くする命令的なコード。
// liElements はページ上の <li> 要素の一覧。
var liElements = document.getElementsByTagName("li");        // ① すべての <li> を取得
for (var i = 0; i < liElements.length; i++) {                // ② <li> を1つずつ見る
    if (liElements[i].className === "selected") {            // ③ クラスが selected なら
        var children = liElements[i].childNodes;             // ④ その子要素を取り出す
        for (var j = 0; j < children.length; j++) {          // ⑤ 子を1つずつ見る
            var child = children[j];
            if (child.nodeType === Node.ELEMENT_NODE && child.tagName === "P") { // ⑥ 子が <p> なら
                child.setAttribute("style", "background-color: blue");          // ⑦ 背景を青に設定
            }
        }
    }
}
ハル
ハルうわ、長い……。CSSの3行がこんなに。
カイ
カイ長くて理解しにくいだけじゃない。重大な問題が2つある。1つめ、selectedクラスが取り除かれても（別ページをクリックしても）青色は取り除かれない。再実行しても変わらず、ページ全体がリロードされるまで青いまま。CSSなら、ルールが当てはまらなくなったのをブラウザが自動検出して、selectedが外れたらすぐ青も消える。
ハル
ハル命令的だと、消す処理も自分で書かなきゃいけないんですね。
カイ
カイそう。2つめ、性能改善の新しいAPI（getElementsByClassNameやdocument.evaluate()）を使おうとすると、コードを書き直さなきゃいけない。一方ブラウザのベンダーは、互換性を壊さずにCSSやXPathの性能を改善できる。つまりWebでも宣言的なCSSのほうが優れてる。同じくDBでもSQLみたいな宣言的言語のほうが、命令的なクエリAPIよりはるかに優れてるんだ。

📚 たとえ話：「青いラベルを貼る規則」を決めておく

宣言的（CSS）は、図書館に「『選択中』の札がついた棚の見出しは青くする」という規則を1つ掲示しておくようなもの。札が外れれば青も自動で消えます。命令的（JS）は、司書が手作業で1つずつ見て回り青いシールを貼る方式。札が外れても、誰かがまた回って剥がさない限り青いシールは残ったまま。規則を掲げるほうが、状態の変化にも自動でついてくるし、貼り方の改善も規則を変えずに裏でできるのです。

  • 宣言的の利点がDBだけでなくWeb（CSS）でも成り立つと、身近な例で理解できる。
  • 命令的コードの弱点（状態追従できない、最適化に書き直しが要る）を具体的に説明できる。

📝 この項のまとめ

  • CSS/XSLは宣言的、JavaScript+DOM APIは命令的。
  • 宣言的（CSS）は短く、状態変化に自動追従し（selected除去で青も消える）、ベンダーが裏で最適化できる。
  • 命令的（JS）は長く、状態追従を自分で書く必要があり、新APIへ書き直しが要る。
  • 同じ理屈で、DBでもSQLのような宣言的言語が命令的APIより優れる。

MapReduceでのクエリ

宣言的と命令的の中間 ― やがてSQLを再発明
📌 要するに：MapReduceは大量データを多数マシンで処理するモデルで、宣言的と命令的の中間。mapとreduceの純粋関数を書く（副作用なし、再実行可能）。書きにくいので宣言的なaggregation pipeline（JSONベース、SQLのサブセットに似る）が登場した。教訓は「NoSQLも結局SQLを再発明しがち」。分散クエリ実行はMapReduce専用ではない。
ハル
ハル「MapReduce」って聞いたことあります。あれもクエリ言語ですか？
カイ
カイMapReduceは、大量のデータを多数のマシンにまたがって処理するプログラミングモデルで、Googleが広めた。MongoDBやCouchDBの一部が限定的にサポートしてて、大量ドキュメントへの読み取りのみのクエリに使える。全体像は10章だけど、ここではMongoDBでの使い方を簡単に見よう。
ハル
ハル宣言的ですか、命令的ですか？
カイ
カイどちらでもなく中間だ。クエリのロジックはコードで書くけど、そのコードは処理のフレームワークから繰り返し呼ばれる。多くの関数型言語が持つmap（collectとも）とreduce（fold/injectとも）を基盤にしてる。
ハル
ハル具体例で見たいです。
カイ
カイ海洋生物学者が、動物を見るたびに観測レコードを追加する。毎月のサメの目撃数レポートを作りたい。PostgreSQLならこうだ。

このSQLは、観測記録から「サメ科」だけを月ごとにまとめ、月別の合計目撃数を出すものです。

PostgreSQL（宣言的） 
-- 観測テーブルから「サメ科」だけを月ごとに集計し、月別の合計目撃数を出すSQL
SELECT date_trunc('month', observation_timestamp) AS observation_month,  -- ① 観測日時をその月の初日に丸める
       sum(num_animals) AS total_animals                                  --    月ごとに目撃数を合計
FROM observations
WHERE family = 'Sharks'        -- サメ科だけに絞り込む
GROUP BY observation_month;    -- 月でグループ化
カイ
カイ①のdate_trunc('month', ...)は日時をその月の初日に丸める。「2014年3月17日12時」なら「2014年3月1日0時」。サメに絞り、発生月でグループ化し、月ごとに動物数を合計する。同じことを、MongoDBのMapReduceで書くとこうだ。

このコードは、観測記録から「サメ科」だけを月別に集計するMapReduceです。mapが1件ずつ「年-月」と目撃数を出し、reduceが同じ月の値を合計します。

MongoDB MapReduce（中間） 
// observations コレクションから「サメ科」だけを月別に集計するMapReduce。
// map は1件ずつ呼ばれてキー（年-月）と値（目撃数）を出し、
// reduce は同じキーの値をまとめて合計する。
db.observations.mapReduce(
    function map() {                                    // ② map: query にマッチした各ドキュメントで呼ばれる（this が1件分）
        var year  = this.observationTimestamp.getFullYear();   // 観測年を取り出す
        var month = this.observationTimestamp.getMonth() + 1;  // 観測月を取り出す（0始まりなので+1）
        emit(year + "-" + month, this.numAnimals);      // ③ キー（"2013-12"など）と値（目撃数）を出力
    },
    function reduce(key, values) {                      // ④ 同じキーの値の配列ごとに1回呼ばれる
        return Array.sum(values);                       // ⑤ その月の目撃数を合計
    },
    {
        query: { family: "Sharks" },                    // ① サメだけに絞るフィルタ（MongoDB独自の宣言的拡張）
        out: "monthlySharkReport"                       // ⑥ 最終結果を書き出す先のコレクション名
    }
);
カイ
カイ①でサメだけに絞る（MongoDB独自の宣言的拡張）。②のmapはマッチした各ドキュメントで呼ばれthisにそれが入る。③でキー（"2013-12"など）と値（目撃数）を出力。④で同じキーがグループ化され、グループごとにreduceが一度呼ばれる。⑤で月内の目撃数を合計。⑥で結果がmonthlySharkReportに書き出される。
ハル
ハル実際に2件データがあったら、どう動くんですか？

{
    observationTimestamp: Date.parse("Mon, 25 Dec 1995 12:34:56 GMT"),
    family:     "Sharks",
    species:    "ホホジロザメ",
    numAnimals: 3
}

ハル
ハルmapとreduceの中で、何でもできるんですか？
カイ
カイ制約がある。これらは純粋な（pure）関数でなきゃいけない。入力に使えるのは渡されたデータだけで、追加でDBにクエリを投げられず、副作用も起こせない。だからDBは関数を任意の場所・順序で実行でき、障害があれば再実行もできる。それでも文字列のパースやライブラリ呼び出し、演算はできるから十分強力だ。
ハル
ハルMapReduceって、ちょっと書きにくそうです。
カイ
カイそこが問題。協調する2つのJavaScript関数を慎重に書かなきゃならず、1つのクエリより難しいことが多い。オプティマイザから見ても宣言的な言語のほうが最適化の機会が多い。だからMongoDB 2.2ではaggregation pipelineという宣言的なクエリ言語が追加された。さっきのサメのクエリはこうなる。

このコードは、同じ「月別サメ目撃数の集計」を、より簡潔な宣言的のやり方（aggregation pipeline）で書いたものです。

MongoDB aggregation pipeline（宣言的） 
// aggregation pipeline で書いた、月別サメ目撃数の集計（宣言的）。
// $match で絞り込み、$group で年・月ごとにまとめて合計する。
db.observations.aggregate([
    { $match: { family: "Sharks" } },          // サメ科だけに絞る
    { $group: {
        _id: {
            year:  { $year:  "$observationTimestamp" },   // 観測年でグループ化
            month: { $month: "$observationTimestamp" }    // 観測月でグループ化
        },
        totalAnimals: { $sum: "$numAnimals" }   // グループごとに目撃数を合計
    } }
]);
カイ
カイ表現力で見ると、aggregation pipelineはSQLのサブセット（一部）に似てるけど、構文は英語風のSQLじゃなくJSONベース。この差はたぶん好みの問題。ここから得られる教訓は、装いは違っても、NoSQLシステムがSQLを再発明してしまうかもしれないってことだ。
ハル
ハル結局SQLっぽくなるんですね。
カイ
カイそういうこと。ちなみにクエリ中でJavaScriptが使えるのはMapReduce限定じゃなく、SQLデータベースにもJS関数で拡張できるものがある。それと、MapReduceは複数マシンクラスタ上の分散処理のためのきわめて低レベルなモデルだけど、SQLみたいな高レベル言語はMapReduceのパイプラインとして実装できる（10章）。逆にMapReduceを使わないSQLの分散実装もたくさんある。SQLは単一マシン限定じゃないし、分散クエリ実行はMapReduceの専売特許じゃないんだ。
M

map（手分けして数える）

各データ1件ずつに対し、キー（年-月）と値（目撃数）を出力。純粋関数なので並列・再実行できる。

R

reduce（同じキーで合算）

同じキーの値をまとめて合計。これも純粋関数。

📚 たとえ話：大勢の助手で手分けして数え、最後に合算

MapReduceは、膨大な蔵書数を数えるのに大勢の助手に書架を割り当て、各自が「ジャンルごとに何冊」と紙に書き出し（map）、最後に同じジャンルの紙を集めて足し合わせる（reduce）方式です。各助手は自分の担当だけ見て、他に問い合わせず勝手な書き込みもしない（純粋関数）から、誰がどの順でやっても、途中で1人倒れてやり直しても結果は同じ。ただし「助手への指示書を2枚も書く」のは手間なので、結局「ジャンル別冊数を出して」と一言で頼める方式（aggregation pipeline）に落ち着いた――司書への頼み方（SQL）の再発明ですね。

  • MapReduceのmap/reduceの役割と、純粋関数の制約（再実行可能になる理由）を理解できる。
  • MapReduceが書きにくく、宣言的なaggregation pipelineに進化した流れを説明できる。
  • 「分散＝MapReduce」「単一マシン＝SQL」という誤解を避けられる。

📝 この項のまとめ

  • MapReduceは大量データを多数マシンで処理するモデルで、宣言的と命令的の中間。
  • map/reduceは純粋関数でなければならず（副作用なし）、だから任意の順序・場所で実行・再実行できる。
  • 書きにくいので宣言的なaggregation pipeline（JSONベース、SQLのサブセットに類似）が登場。
  • 教訓：NoSQLも装いを変えてSQLを再発明しがち。
  • 分散クエリ実行はMapReduce専用ではなく、SQLも分散実行できる。

多対多が複雑になったら ― 点と線でつなぐ
📌 要するに：多対多が複雑になるとグラフモデルが自然。グラフは頂点（点）と辺（線）から成り、ソーシャル・Web・交通など多様なデータを表せ、最短パスやPageRankなどのアルゴリズムで操作できる。均一なデータだけでなく異種のオブジェクトも一貫して保存できる（Facebookの例）。実装はプロパティグラフとトリプルストア、クエリ言語はCypher/SPARQL/Datalog。
ハル
ハル一対多と多対多の違いがモデル選びの鍵だと分かりました。多対多が多いと、どうするんですか？
カイ
カイいい質問だ。関係がほとんど一対多（ツリー）か、レコード同士が関係を持たないならドキュメントが向く。でもデータの中で多対多が一般的なら？ リレーショナルも単純な多対多は扱えるけど、つながりが複雑になると、データをグラフとしてモデル化するほうが自然になるんだ。
ハル
ハルグラフって、棒グラフとかのグラフですか？
カイ
カイいや、数学のグラフだ。頂点（vertex＝点）と辺（edge＝点をつなぐ線）の2つから成る。ソーシャルグラフは頂点が人・辺が知人関係、Webグラフは頂点がWebページ・辺がリンク、道路や鉄道は頂点が接続点・辺が路線だ。
ハル
ハルそれで何ができるんですか？
カイ
カイよく知られたアルゴリズムで操作できる。カーナビは道路ネットワークの2点間の最短パスを探すし、PageRankはWebグラフを処理してページの人気を判断し、検索結果のランキングを決める。
ハル
ハルグラフの点って、全部同じ種類じゃなきゃダメですか？
カイ
カイいや、そこが強み。均一なデータだけじゃなく、まったく違う種類のオブジェクトも1つのデータストアに一貫して保存できる。Facebookは単一のグラフで、頂点に人・場所・イベント・チェックイン・コメントを持たせ、辺に友人関係・チェックイン・誰がどの投稿にコメントしたか・誰がどのイベントに出たかを表してる。
ハル
ハルいろんなものを混ぜられるんですね。
カイ
カイそう。この節では例として、アイダホ出身のLucyと、フランスのボーヌ出身のAlainを使う。2人は結婚してロンドンに住んでる設定だ。構築とクエリにはいくつか方法があって、プロパティグラフ（Neo4j、Titan、InfiniteGraph）とトリプルストア（Datomic、AllegroGraph）を取り上げる。クエリ言語は宣言的な3つ――Cypher、SPARQL、Datalog。ほかにGremlinやPregel（10章）もあるよ。

2.3.1

プロパティグラフ

頂点と辺に情報を詰める ― 自由で進化しやすい
📌 要するに：プロパティグラフでは、頂点が一意ID・内外の辺・プロパティを持ち、辺が一意ID・始点・終点・ラベル・プロパティを持つ。リレーショナルの2テーブル（vertices/edges）で表現でき、始点・終点にインデックスを張って探索する。スキーマ制約がなく、どの頂点同士もつなげ、ラベルで種類を区別でき、粒度の違うデータも表せる。機能追加が容易で進化性に優れる。
ハル
ハルプロパティグラフって、頂点と辺に何が入ってるんですか？
カイ
カイ各頂点は、①一意の識別子、②外向きの辺の集合、③内向きの辺の集合、④プロパティ（キーと値のペア）。各辺は、①一意の識別子、②辺の始まりの頂点（始点）、③辺の終わりの頂点（終点）、④関係の種類を示すラベル、⑤プロパティ。
ハル
ハルけっこう情報が詰まってますね。これをリレーショナルDBで表せますか？
カイ
カイ表せるよ。頂点と辺、2つのテーブルで考える。こんなスキーマだ。

このコードは、グラフを「頂点の表」と「辺の表」という2つの表で表すための設計（テーブル定義）です。

プロパティグラフを2テーブルで表す（SQL） 
-- プロパティグラフをリレーショナルなテーブル2つで表現するスキーマ。
-- vertices は頂点、edges は辺。properties は PostgreSQL の json 型で柔軟に持つ。
CREATE TABLE vertices (
    vertex_id   integer PRIMARY KEY,   -- 頂点の一意な番号
    properties  json                   -- 頂点の属性（名前など）をまとめて持つ
);
CREATE TABLE edges (
    edge_id     integer PRIMARY KEY,                       -- 辺の一意な番号
    tail_vertex integer REFERENCES vertices (vertex_id),   -- 始点（辺の出発する頂点）
    head_vertex integer REFERENCES vertices (vertex_id),   -- 終点（辺の到達する頂点）
    label       text,                                      -- 関係の種類（"WITHIN" など）
    properties  json                                       -- 辺の属性
);
CREATE INDEX edges_tails ON edges (tail_vertex);   -- 始点で辺を速く探すためのインデックス
CREATE INDEX edges_heads ON edges (head_vertex);   -- 終点で辺を速く探すためのインデックス
カイ
カイ始点と終点は各辺に保存される。頂点に出入りする辺を取りたいときはedgesテーブルをhead_vertexやtail_vertexで検索するから、両方の列にインデックスを張ってる。このモデルで重要なことが3つある。
ハル
ハル3つ、教えてください。
カイ
カイ①どの頂点も、辺で他のどの頂点とも接続できる（「この種類しかつなげない」みたいなスキーマ制約がない）。②任意の頂点の入出力の辺を効率よく見つけられるのでグラフを探索（traverse＝たどる）でき、パスをどちらの方向にもたどれる。③関係の種類ごとに違うラベルを使えば、きれいに保ちながら1つのグラフに様々な情報を保存できる。
ハル
ハル自由度が高いんですね。これだとどんなデータを表せますか？
カイ
カイすごく柔軟だ。国ごとに違う地域構造――フランスはdépartements（県）やrégions（地方）、アメリカは郡や州――とか、「国の中に国がある」複雑さ、さらに粒度の違うデータ――Lucyの現住所は市レベルだけど生誕地は州レベルでしか分からない、とか。リレーショナルスキーマでは表しにくいことが表せる。
ハル
ハル後から機能を足すのも楽そうですね。
カイ
カイまさに進化性に優れてる。食材のアレルギーを足したいなら、アレルゲンごとに頂点を持たせ、人とアレルゲンの間に辺を張ればいい。食べ物の頂点にアレルゲンからのリンクを張れば含有関係も表せる。「各人が食べても安全なもの」を知るクエリも書ける。機能追加でグラフを拡張するのが容易なんだ。
🔓

制約がない

どの頂点も他のどの頂点へも辺を張れる。種類の縛りなし。

🧭

両方向に探索できる

始点・終点にインデックス。パスをどちら向きにもたどれる。

🏷️

ラベルで区別

関係の種類ごとにラベル。1つのグラフに多様な情報を混在。

📚 たとえ話：何でも書き足せる系図帳

プロパティグラフは、図書館の自由な系図帳。人物カード（頂点）に好きなだけ続柄線（辺）を引け、線には「師弟」「夫婦」「引用」など名前（ラベル）を付けられます。決まった様式に縛られないから、国ごとに違う住所の段階（市・州・国）も、分かる範囲だけで書ける（粒度の違い）。あとから「アレルギー」みたいな新しい欄を足したくなっても、新しいカードと線を描き足すだけ。とても進化させやすい帳面なのです。

  • プロパティグラフの頂点・辺の構成要素を列挙できる。
  • グラフをリレーショナルの2テーブルで表現する方法を理解できる。
  • グラフの柔軟性（制約なし、ラベル、粒度の違い、進化性）を説明できる。

📝 この項のまとめ

  • 頂点＝一意ID＋内外の辺＋プロパティ、辺＝一意ID＋始点＋終点＋ラベル＋プロパティ。
  • リレーショナルの2テーブル（vertices/edges）で表現でき、始点・終点にインデックスを張る。

Cypherクエリ言語

矢印でパターンを描く宣言的言語（Neo4j）
📌 要するに：Cypherはプロパティグラフ用の宣言的クエリ言語（Neo4j用）。CREATEで頂点とラベル付きの辺を作り、MATCHで矢印表記のパターンを探す。:WITHIN*0..は「WITHINの辺を0回以上たどる」。実行方法（全員スキャンか、場所から逆にたどるか）は書かず、オプティマイザが自動で選ぶ。
ハル
ハルCypherって、どんな言語ですか？
カイ
カイCypherはプロパティグラフ用の宣言的クエリ言語で、グラフDBのNeo4j用に作られた。名前は映画「マトリックス」のキャラにちなんでて、暗号文のcipherとは関係ない。まずグラフにデータを入れるところから見よう。

このコードは、地名や人物を頂点として作り、矢印で「アイダホはアメリカの中、Lucyはアイダホ生まれ」というつながり（辺）を作るものです。

Cypher：データの挿入 
// Cypher でグラフにデータを挿入する。各頂点に USA や Idaho といったシンボル名を付け、
// 矢印 -[:ラベル]-> で頂点どうしの辺を作る。
CREATE
  (NAmerica:Location {name:'北アメリカ', type:'continent'}),
  (USA:Location      {name:'アメリカ合衆国', type:'country'  }),
  (Idaho:Location    {name:'アイダホ',       type:'state'    }),
  (Lucy:Person       {name:'Lucy' }),
  (Idaho) -[:WITHIN]->  (USA)  -[:WITHIN]-> (NAmerica),   // アイダホ⊂アメリカ⊂北アメリカ
  (Lucy)  -[:BORN_IN]-> (Idaho)                           // Lucy はアイダホ生まれ
カイ
カイ各頂点にUSAやIdahoというシンボル名を与え、他の部分でその名前を使って辺を作る。(Idaho) -[:WITHIN]-> (USA)は「WITHINというラベルを付けて、Idahoを始点・USAを終点とする辺」を作る。これで「アイダホはアメリカの中、アメリカは北アメリカの中、Lucyはアイダホ生まれ」と表せる。
ハル
ハルデータが入ったら、どんな質問ができるんですか？
カイ
カイ例えば「アメリカで生まれてヨーロッパに移住した人の名前を全部返す」。正確には、アメリカ内の場所へのBORN_INの辺と、ヨーロッパ内の場所へのLIVES_INの辺の両方を持つ頂点を探して名前を返す。Cypherでこう書く。

このコードは、「アメリカ生まれで、かつヨーロッパに住んでいる人」を探して名前を返す問い合わせです。

Cypher：移住者を探すクエリ 
// アメリカで生まれ、かつヨーロッパに住んでいる人の名前を返す Cypher クエリ。
// *0.. は「WITHIN の辺を0回以上たどる」という意味（場所の階層をいくつでもさかのぼる）。
MATCH
  (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (us:Location {name:'アメリカ合衆国'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name:'ヨーロッパ'})
RETURN person.name
カイ
カイ同じ矢印表記が、パターンを探すMATCH節でも使われる。(person) -[:BORN_IN]-> ()は、BORN_INラベルの辺でつながる2頂点の全ての組にマッチ。始点はpersonという変数にバインドされ、終点は名前なし。
ハル
ハル日本語で読み下すと？
カイ
カイ「次の2条件を両方満たす全頂点（personと呼ぶ）を探せ。①personからBORN_INの辺がどこかに出ていて、そこからWITHINの辺の連鎖をたどると最終的にname"アメリカ合衆国"のLocationに着く。②同じpersonからLIVES_INの辺が出ていて、その先WITHINの連鎖をたどると最終的にname"ヨーロッパ"のLocationに着く。これを満たすpersonのnameを返せ」だ。
ハル
ハルこのクエリ、どう実行されるんですか？
カイ
カイいくつかやり方がある。1つは全員をスキャンして各人の生誕地と住所を確認する方法。でも逆もできる。2つのLocation頂点（アメリカとヨーロッパ）から逆にたどる。nameにインデックスがあれば効率よく見つかり、入ってくるWITHINの辺をたどって域内の全場所を見つけ、最後にそこへBORN_INやLIVES_INで入ってくる人を探す。
ハル
ハルでも、どっちで実行するか書かなくていいんですよね？
カイ
カイその通り。宣言的言語では普通のこと。実行の詳細は書かなくていい。クエリオプティマイザが最も効率的と予想した戦略を自動で選ぶから、開発者はアプリの他の部分に集中できるんだ。

📚 たとえ話：系図に「こういう線でつながる人を探して」と頼む

Cypherは系図帳に対し、矢印の絵で「『生まれ』の線でアメリカ圏に、『住む』の線でヨーロッパ圏につながっている人」というパターンを描いて頼む頼み方です。:WITHIN*0..は「『○○の中』の線を何段でもさかのぼってよい」の意味。利用者は探す順番（全員見るか、地名から逆にたどるか）を指定しません。司書（オプティマイザ）が一番速い手順を選んでくれます。

💡 なぜこれが必要か / これを知ったらできること

  • Cypherで頂点・辺を作り、パターンマッチでグラフを問い合わせる書き方を理解できる。
  • 可変長パス（*0..）の意味を理解し、階層をさかのぼる検索を表現できる。
  • 宣言的なので実行戦略をオプティマイザに任せられると理解できる。

📝 この項のまとめ

  • Cypherはプロパティグラフ用の宣言的言語（Neo4j用）。
  • CREATEで頂点とラベル付き辺を作成、MATCHで矢印パターンを検索。
  • :WITHIN*0..＝WITHINの辺を0回以上たどる（正規表現の*に類似）。
  • 実行戦略（全員スキャン or 場所から逆探索）は書かず、オプティマイザが自動選択。
2.3.3

SQLでのグラフクエリ

同じ問いがCypher4行→SQL29行
📌 要するに：グラフクエリは結合の数が事前に決まらない（可変長パス）。SQLではSQL:1999の再帰共通テーブル式（WITH RECURSIVE）で表せるが、Cypherの4行が29行になるほど扱いづらい。同じクエリでも言語によって長さが激変することは、ユースケースに合ったデータモデル選びの重要性を示す。
ハル
ハルさっきグラフをリレーショナルの2テーブルで表せましたよね。じゃあSQLでも同じクエリが書けますか？
カイ
カイ書ける。けど困難が伴う。リレーショナルでは普通、必要な結合が事前に分かってる。でもグラフクエリでは、目的の頂点に着くまでにたどる辺の数が変動するかもしれない。つまり結合の数が事前に決まらないんだ。
ハル
ハル結合の数が決まらない、というのは？
カイ
カイさっきのCypherの() -[:WITHIN*0..]-> ()の部分だ。ある人のLIVES_INの辺は、通り・市・地域・地方・州……どんな場所も指しうる。市が地方の中、地方が州の中、と階層を何段もたどるかもしれないし、直接指してるかも。Cypherは:WITHIN*0..と簡潔に書ける。正規表現の*に似てる。
ハル
ハルSQLでこの「0回以上」をどう書くんですか？
カイ
カイSQL:1999から、可変長のパスを再帰共通テーブル式（WITH RECURSIVE）で書ける。同じ「アメリカ生まれでヨーロッパ在住の人」を返すクエリをSQLで書くとこうだ（PostgreSQL、DB2、Oracle、SQL Serverで動く）。ただしCypherよりずっと扱いづらい。

このコードは、Cypherの4行と同じ「アメリカ生まれでヨーロッパ在住の人」を、SQLで書いたものです。場所の階層を1段ずつ広げながらたどります。

SQL：再帰共通テーブル式（29行） 
-- アメリカで生まれ、かつヨーロッパに住む人の名前を返すSQL（再帰共通テーブル式を使う）。
-- in_usa はアメリカ内の全場所、in_europe はヨーロッパ内の全場所を再帰的に集める。
WITH RECURSIVE

  -- in_usa はアメリカ国内のすべての場所の頂点IDの集合
  in_usa(vertex_id) AS (
      SELECT vertex_id FROM vertices WHERE properties->>'name' = 'アメリカ合衆国'  -- ① まず「アメリカ合衆国」の頂点を起点にする
    UNION
      SELECT edges.tail_vertex FROM edges                                          -- ② そこへ within で入ってくる場所を次々に加える
        JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
        WHERE edges.label = 'within'
  ),

  -- in_europe はヨーロッパ内のすべての場所の頂点IDの集合
  in_europe(vertex_id) AS (
      SELECT vertex_id FROM vertices WHERE properties->>'name' = 'ヨーロッパ'        -- ③ 「ヨーロッパ」の頂点から同じことをする
    UNION
      SELECT edges.tail_vertex FROM edges
        JOIN in_europe ON edges.head_vertex = in_europe.vertex_id
        WHERE edges.label = 'within'
  ),

  -- born_in_usa はアメリカ国内で生まれたすべての人の頂点IDの集合
  born_in_usa(vertex_id) AS (                                                       -- ④ in_usa の各場所へ born_in で入ってくる人を集める
    SELECT edges.tail_vertex FROM edges
      JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
      WHERE edges.label = 'born_in'
  ),

  -- lives_in_europe は、ヨーロッパに住んでいるすべての人の頂点IDの集合
  lives_in_europe(vertex_id) AS (                                                   -- ⑤ in_europe の各場所へ lives_in で入ってくる人を集める
    SELECT edges.tail_vertex FROM edges
      JOIN in_europe ON edges.head_vertex = in_europe.vertex_id
      WHERE edges.label = 'lives_in'
  )

SELECT vertices.properties->>'name'
FROM vertices
-- アメリカで生まれ、かつヨーロッパに住む人を見つけるために結合する
JOIN born_in_usa     ON vertices.vertex_id = born_in_usa.vertex_id      -- ⑥ 両方の集合の積（重なり）を取る
JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;
カイ
カイ①でname"アメリカ合衆国"の頂点を探しin_usaの最初の要素にする。②でin_usa内の頂点に入ってくるwithinの辺をたどってin_usaに加える、を辺がなくなるまで繰り返す。③で同じことを"ヨーロッパ"からやってin_europeを作る。④でin_usaの各頂点に入ってくるborn_inの辺をたどってアメリカ生まれの人を見つける。⑤で同様にin_europeからヨーロッパ在住の人を。⑥で両者を結合して積集合（両方に当てはまる人）を得る。
ハル
ハルCypherだと4行なのに、SQLだと……これ、すごく長いですね。
カイ
カイ29行だ。同じクエリが、ある言語では4行、別の言語では29行。これが意味するのは、ユースケースが違えば適切なデータモデルも違うってこと。アプリに合ったデータモデルを選ぶのは、本当に重要なんだよ。

📚 たとえ話：系図帳なら一言、台帳なら長い手順書

「アメリカ圏で生まれヨーロッパ圏に住む人」を、系図帳（グラフ）に頼めば短い一言で済みます。でも同じことを棚＋索引カードの台帳（リレーショナル）でやろうとすると、「アメリカ圏の場所を1段ずつ集めて、ヨーロッパ圏も集めて、生まれの人を集めて、住む人を集めて、重ねて…」と長い手順書（29行）が必要に。やりたいことに合った帳面を選ぶことが、いかに大事かが分かります。

💡 なぜこれが必要か / これを知ったらできること

  • グラフクエリの「結合数が事前に決まらない」性質と、可変長パスの難しさを理解できる。
  • SQLの再帰共通テーブル式でグラフをたどる方法を知る。
  • 同じクエリの行数差から、データモデル選択の重要性を実感できる。

📝 この項のまとめ

  • グラフクエリは結合数が事前に決まらない（たどる辺の数が変動）。
  • Cypherの:WITHIN*0..はSQL:1999の再帰共通テーブル式（WITH RECURSIVE）で表せる。
  • だがCypherの4行がSQLでは29行になるほど扱いづらい。
  • 行数の差は「ユースケースに合うデータモデルを選ぶ重要性」を示す。

トリプルストアとSPARQL

(主語, 述語, 目的語) の3つ組で表す
📌 要するに：トリプルストアはプロパティグラフと同等の内容を (主語, 述語, 目的語) の3つ組で表す。主語は頂点、目的語はプリミティブ値（＝プロパティ）か別の頂点（＝辺）。Turtle形式（N3のサブセット）で書け、_:名前で頂点を表し、セミコロンで同じ主語の複数の述語をまとめて簡潔にできる。
ハル
ハルもう1つのグラフの実装、トリプルストアって何ですか？
カイ
カイトリプルストアモデルは、だいたいプロパティグラフと同じことを違う用語で表す。すべての情報を(主語, 述語, 目的語)の形で保存する。例えば(Jim, likes, bananas)なら、Jimが主語、likesが述語（動詞）、bananasが目的語だ。
ハル
ハル主語・述語・目的語。英語の文みたいですね。目的語って何が入るんですか？
カイ
カイ主語はグラフの頂点に相当。目的語は2つのどちらか。①文字列や数値みたいなプリミティブな型の値。この場合、述語と目的語は主語の頂点のプロパティのキーと値に相当する（(lucy, age, 33)は{"age":33}のlucy頂点みたい）。②グラフ中の別の頂点。この場合、述語はグラフの辺で、主語が始点・目的語が終点（(lucy, marriedTo, alain)なら述語marriedToが辺のラベル）。
ハル
ハル値か、別の頂点か。書き方の例を見たいです。
カイ
カイ同じデータをTurtleというフォーマット（Notation3＝N3のサブセット）で書くとこうだ。

このコードは、これまでのグラフ（Lucyや地名）を、トリプル（3つ組）の形で1行ずつ書き出したものです。

Turtle形式（1行ずつ） 
# Turtle 形式でグラフをトリプルとして書いたもの。
# _:名前 は頂点を表す（このファイル内でだけ意味を持つ名前）。a は「型は」という述語。
@prefix : <urn:example:>.
_:lucy     a       :Person.
_:lucy     :name   "Lucy".
_:lucy     :bornIn _:idaho.
_:idaho    a       :Location.
_:idaho    :name   "アイダホ".
_:idaho    :type   "state".
_:idaho    :within _:usa.
_:usa      a       :Location.
_:usa      :name   "アメリカ合衆国".
_:usa      :type   "country".
_:usa      :within _:namerica.
_:namerica a       :Location.
_:namerica :name   "北アメリカ".
_:namerica :type   "continent".
カイ
カイ頂点は_:someNameと書く。この名前はファイルの外では意味を持たない。なぜ要るかというと、これがないと「同じ頂点を参照してるトリプルがどれか」分からなくなるから。_:idaho :within _:usaのように述語が辺を表すときは目的語が頂点になり、_:usa :name "アメリカ合衆国"のように述語がプロパティのときは目的語が文字列リテラルになる。
ハル
ハル同じ_:lucyを何度も書くの、無駄じゃないですか？
カイ
カイいいところに気づいた。同じ主語について複数のことを述べるときはセミコロンが使える。こうするとTurtleはぐっと読みやすくなる。

このコードは、同じ内容を「同じ主語は1回だけ書いてセミコロンでまとめる」より簡潔な書き方にしたものです。

Turtle形式（セミコロンで簡潔に） 
# セミコロン（;）で同じ主語を1回だけ書いて複数の述語をまとめた、より簡潔な Turtle。
@prefix : <urn:example:>.
_:lucy     a :Person;   :name "Lucy";          :bornIn _:idaho.
_:idaho    a :Location; :name "アイダホ";        :type "state";   :within _:usa.
_:usa      a :Location; :name "アメリカ合衆国";  :type "country"; :within _:namerica.
_:namerica a :Location; :name "北アメリカ";      :type "continent".
ハル
ハルだいぶスッキリしました。

📚 たとえ話：すべてを「主語・述語・目的語」の一言カードに

トリプルストアは、図書館のあらゆる事実を「○○は △△ が ××」という3語の付箋カード1枚ずつに分解して箱に入れる方式です。「ルーシーは 名前が ルーシー」「ルーシーは 生まれが アイダホ」…。目的語が文字なら属性（プロパティ）、目的語が別の人物カードを指せばつながり（辺）。同じ人物を何枚にも書くのは大変なので、「ルーシーは…」を1回書いて続柄を並べる略記（セミコロン）も用意されています。

💡 なぜこれが必要か / これを知ったらできること

  • トリプル（主語・述語・目的語）でグラフを表す発想を理解できる。
  • 目的語が「値か頂点か」でプロパティか辺かが決まると説明できる。
  • Turtle形式の読み書き（_:名前、セミコロン省略）の基本を理解できる。

📝 この項のまとめ

  • トリプルストアは (主語, 述語, 目的語) の3つ組で情報を保存（プロパティグラフと同等）。
  • 主語＝頂点。目的語が値なら述語＝プロパティのキー、目的語が頂点なら述語＝辺のラベル。
  • Turtle（N3のサブセット）で記述。_:名前は頂点を表す（ファイル内限定の名前）。
  • セミコロンで同じ主語の複数の述語をまとめると読みやすい。

セマンティックWeb

トリプルストアとは独立 ― 構想は壮大だが未実現
📌 要するに：トリプルストアのデータモデルはセマンティックWebとは独立。セマンティックWebは「コンピュータが読めるデータをWebで公開し、RDFで一貫フォーマット化して巨大なweb of dataを作る」構想だが、過剰宣伝のわりに実現せず懐疑的に見られる。ただしトリプルはアプリ内部のデータモデルとして優れている。
ハル
ハルトリプルストアを調べると「セマンティックWeb」がよく出てきます。関係あるんですか？
カイ
カイ実は、トリプルストアのデータモデルはセマンティックWebとは完全に独立してる。DatomicというトリプルストアはセマンティックWebとの関係を一切主張してない。ただ多くの人の頭で2つが密接にリンクしてるから、説明しておこう。
ハル
ハルセマンティックWebって何ですか？
カイ
カイ基本はシンプルな考え。Webは今、人間が読めるテキストや画像で情報を公開してる。それならコンピュータが読めるデータとしても公開すればいい、と。その仕組みがRDF。いろんなサイトが一貫フォーマットでデータを公開し、自動で組み合わせて"web of data"――インターネット規模の「あらゆる情報のDB」を作ろうとした。
ハル
ハルすごく壮大ですね。実現したんですか？
カイ
カイ残念ながら、2000年代初めに過剰に語られたわりに実現する兆しはほとんどなく、多くの人が懐疑的だ。短縮形の用語があふれ、複雑すぎる標準が提唱され、傲慢さも見られた、という問題もあった。
ハル
ハルじゃあ無駄だったんですか？
カイ
カイいや、欠点の裏に優れた成果もたくさん生まれた。セマンティックWebにRDFデータを公開するつもりがなくても、トリプルはアプリの内部的なデータモデルとして優れてる。そこは分けて考えるといい。

📚 たとえ話：世界中の図書館を1つの目録でつなぐ夢

セマンティックWebは、世界中の図書館が同じ様式の付箋カード（RDF）で蔵書情報を公開し、それを全部つなげて「人類の全知識の巨大目録」を作ろうという壮大な夢でした。理想は美しかったものの、様式が複雑すぎて広く実現はしませんでした。ただし、その付箋カード方式（トリプル）自体は、1つの図書館の中の整理術としては十分に優秀です。夢と道具は切り離して考えましょう。

💡 なぜこれが必要か / これを知ったらできること

  • トリプルストアとセマンティックWebを混同せず区別できる。
  • セマンティックWeb構想（RDFによるweb of data）の狙いと現状を理解できる。

📝 この項のまとめ

  • トリプルストアのデータモデルはセマンティックWebと独立（Datomicは関係を主張しない）。
  • セマンティックWeb＝コンピュータ可読データをWeb公開し、RDFで巨大なweb of dataを作る構想。
  • 過剰宣伝のわりに実現せず懐疑的に見られるが、トリプル自体はアプリ内部のモデルとして優秀。
2.3.4.2

RDFデータモデル

URIで名前の衝突を防ぐ ― データ交換のための設計
📌 要するに：TurtleはRDFの人間に優しいフォーマットで、RDF/XMLは同内容でも冗長（ツールで相互変換可能）。RDFはインターネット上のデータ交換用に設計され、主語・述語・目的語をURIにすることで、他人のデータと組み合わせても名前の衝突を防ぐ。URIは必ずしもアクセス可能である必要はなく、単なる名前空間でよい。
ハル
ハルさっきのTurtleはRDFのフォーマットの1つなんですか？
カイ
カイそう、Turtleは人間が読めるRDFデータのフォーマットだ。RDFはXMLでも書けるけど、同じ内容でもはるかに冗長になる。見てごらん。

このコードは、さっきと同じデータ（Lucyや地名）を、RDF/XMLという別の書き方で書いたものです。Turtleよりずっと長くなります。

RDF/XML（冗長） 
<!-- 同じデータを RDF/XML 構文で書いたもの。Turtle よりずっと冗長。 -->
<rdf:RDF xmlns="urn:example:"
    xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">

  <Location rdf:nodeID="idaho">
    <name>アイダホ</name>
    <type>state</type>
    <within>

      <Location rdf:nodeID="usa">
        <name>アメリカ合衆国</name>
        <type>country</type>
        <within>
          <Location rdf:nodeID="namerica">
            <name>北アメリカ</name>
            <type>continent</type>
          </Location>
        </within>
      </Location>
    </within>
  </Location>

  <Person rdf:nodeID="lucy">
    <name>Lucy</name>
    <bornIn rdf:nodeID="idaho"/>
  </Person>
</rdf:RDF>
カイ
カイTurtle/N3のほうがずっと目に優しいよね。Apache Jenaみたいなツールが、必要に応じてRDFのフォーマット間を自動変換してくれる。
ハル
ハルRDFって、なんか独特な癖がありますね。urn:example:とか。
カイ
カイRDFがインターネット上でのデータ交換のために設計されたからだ。トリプルの主語・述語・目的語は、しばしばURIになる。述語が単にWITHINじゃなく<http://my-company.com/namespace#within>みたいになる。
ハル
ハルなんでわざわざURLにするんですか？
カイ
カイ自分のデータを他人のデータと組み合わせられるようにするため。仮に他人がWITHINに違う意味を与えてても、<http://other.org/foo#within>なら衝突しない。名前空間で区別するわけ。ただしこのURLは、必ずしも何かに解決できる（アクセスできる）必要はなく、RDFから見れば単なる名前空間だ。だから例では混乱を避けるためurn:example:withinみたいな解決できないURIを使ってる。このプレフィックスはファイル先頭で一度指定すればいい。

📚 たとえ話：世界共通の請求記号で「同名違い」を防ぐ

図書館どうしが目録を持ち寄ると、同じ「内」という言葉でも館ごとに意味が違うかもしれません。そこでRDFは、言葉に世界で一意の長い住所（URI）を付けて「これはA館の『内』」「これはB館の『内』」と区別します。住所といっても、実際にそこへ手紙が届く必要はなく、名札として一意であればいい。だから他館のカードと混ぜても取り違えが起きないのです。

💡 なぜこれが必要か / これを知ったらできること

  • TurtleとRDF/XMLの関係（同内容・冗長さの違い・相互変換）を理解できる。
  • RDFがURIを使う理由（データ交換時の名前衝突回避）を説明できる。

📝 この項のまとめ

  • TurtleはRDFの読みやすいフォーマット、RDF/XMLは冗長（Apache Jenaなどで相互変換）。
  • RDFはデータ交換用設計で、主語・述語・目的語をURIにする。
  • URIで名前空間を区別し、他人のデータと組み合わせても衝突を防ぐ。
  • URIはアクセス可能である必要はなく、単なる名前空間でよい（例ではurn:example:）。

SPARQLクエリ言語

CypherのルーツでCypherより簡潔
📌 要するに：SPARQLはRDFトリプルストア用の宣言的クエリ言語（「スパークル」）。CypherはSPARQLのパターンマッチングを取り入れたので両者は酷似する。SPARQLは変数を?で始め、/でパスをつなぎ*で可変長パスを表し、Cypherより簡潔。RDFはプロパティと辺を区別せず述語を使うため、両方に同じ構文が使える。
ハル
ハルRDFをクエリする言語が、SPARQLですか？
カイ
カイそう。SPARQL（"SPARQL Protocol and RDF Query Language"の略、「スパークル」と発音）は、RDFモデルを使うトリプルストア用のクエリ言語だ。SPARQLはCypherより前からあって、Cypherのパターンマッチングは実はSPARQLから取られてる。だから2つはよく似てる。
ハル
ハルさっきの「アメリカ生まれでヨーロッパ移住」のクエリ、SPARQLだとどうなりますか？
カイ
カイCypher以上に簡潔になる。

このコードは、「アメリカ生まれでヨーロッパ在住の人」を探す問い合わせを、SPARQLで書いたものです。Cypherよりさらに短くなります。

SPARQL：移住者を探すクエリ 
# アメリカで生まれ、かつヨーロッパに住む人の名前を返す SPARQL クエリ。
# 変数は ? で始まる。/ はパスをつなぎ、:within* は within を0回以上たどる。
PREFIX : <urn:example:>

SELECT ?personName WHERE {
  ?person :name ?personName.
  ?person :bornIn  / :within* / :name "アメリカ合衆国".
  ?person :livesIn / :within* / :name "ヨーロッパ".
}
カイ
カイ構造はCypherにそっくりだ。SPARQLの変数は疑問符?で始まる。次の2つの式は等価だよ。

このコードは、Cypherの矢印表記とSPARQLのパス表記が同じ意味になることを並べて示したものです。

Cypher と SPARQL の対応（辺） 
(person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location)   # Cypher
?person :bornIn / :within* ?location.                   # SPARQL
ハル
ハルほんとに似てますね。プロパティのマッチも同じですか？
カイ
カイそこがRDFの面白いところ。RDFはプロパティと辺を区別せず、どちらにも述語を使うから、プロパティのマッチにも同じ構文が使える。次の2つも等価だ。

このコードは、プロパティ（名前）のマッチも、CypherとSPARQLで同じ意味になることを示したものです。

Cypher と SPARQL の対応（プロパティ） 
(usa {name:'アメリカ合衆国'})   # Cypher
?usa :name "アメリカ合衆国".    # SPARQL
カイ
カイSPARQLは優れたクエリ言語でね。たとえセマンティックWebが普及しなくても、SPARQLはアプリ内部で使える強力なツールになり得るんだ。

📚 たとえ話：付箋カードの箱への、より短い頼み方

SPARQLは、トリプルの付箋カードの箱（RDF）に対する頼み方で、Cypherの兄貴分（先にできた）です。だからCypherとそっくり。?で「探したい人」を表し、/で「カードをたどる順路」をつなぎ、*で「何段でもさかのぼってよい」を表す。しかも付箋カードは属性も続柄も同じ「述語」で書くので、名前を調べるのも、つながりをたどるのも、まったく同じ書き方で頼めるのが楽なところです。

💡 なぜこれが必要か / これを知ったらできること

  • SPARQLとCypherの類似（パターンマッチング、可変長パス）を理解できる。
  • RDFがプロパティと辺を区別しない（どちらも述語）という特徴を説明できる。

📝 この項のまとめ

  • SPARQLはRDFトリプルストア用の宣言的クエリ言語。CypherはSPARQL由来で酷似。
  • 変数は?始まり、/でパス連結、*で可変長パス。Cypherより簡潔。
  • RDFはプロパティと辺を区別せず述語を使うので、両方に同じ構文が使える。
  • セマンティックWebが普及しなくてもSPARQLは強力なツール。

グラフDBのネットワークモデルとの比較

CODASYLの再来ではない ― 4つの違い
📌 要するに：グラフDBはCODASYLの再来ではない。違いは4つ――①スキーマ制約がない（どの頂点も自由につなげる）、②一意IDやインデックスで頂点に直接アクセスできる（パスをたどる必要がない）、③頂点・辺は順序づけされない、④宣言的クエリ言語（Cypher/SPARQL）をサポートする。
ハル
ハルグラフDBって、さっきの古いCODASYL（ネットワークモデル）の再登場じゃないんですか？ 似てる気がします。
カイ
カイ一見そう思えるよね。でも答えはNo。重要な違いがいくつかある。
カイ
カイ①CODASYLは「どのレコード型がどれとネストできるか」を決めるスキーマを持つ。グラフDBには制約がなく、どの頂点も他のどの頂点へも辺をいくつでも持てる。だから要求変化に柔軟。②CODASYLは特定レコードに着くにはパスをたどるしかなかった。グラフDBは任意の頂点を一意のIDで直接参照でき、インデックスで特定の値を持つ頂点も見つけられる。③CODASYLではレコードの子が順序づけられた集合でDBが順序を保つ必要があった。グラフDBでは頂点も辺も順序づけされない（クエリ時にソートできるだけ）。④CODASYLは全クエリが命令的で書きにくくスキーマ変更ですぐ動かなくなった。グラフDBは命令的に辺をたどるコードも書けるが、たいていCypherやSPARQLみたいな高級な宣言的言語もサポートする。
ハル
ハルなるほど、見た目は似てても中身は全然違うんですね。
観点CODASYL（ネットワークモデル）現代のグラフDB
スキーマ制約どの型がどれとネストできるか固定制約なし。どの頂点同士も自由に接続
アクセス方法パスをたどるしかない一意IDやインデックスで直接アクセス
順序子は順序づけられた集合（順序を保つ必要）頂点・辺は順序づけなし（クエリ時にソート）
クエリ言語命令的のみ。変更に弱い宣言的（Cypher/SPARQL）もサポート

📚 たとえ話：見た目は同じ「系図」でも、扱いやすさが段違い

昔のCODASYLも今のグラフDBも、どちらも「系図のように線でつなぐ」点は同じに見えます。でも昔の系図帳は、つなげる相手の種類が決まっていて、目当ての人には決まった順路をたどるしかなく、並び順も守らねばならず、頼み方も逐一手順指示でした。今の系図帳は、誰とでも自由につなげ、名前から直接めくれ、並び順は自由、しかも「こういう人を探して」と一言で頼める。見た目は系図でも、使い勝手はまるで別物なのです。

💡 なぜこれが必要か / これを知ったらできること

  • グラフDBと古いネットワークモデルの本質的な違い（柔軟性・直接アクセス・宣言的クエリ）を説明できる。
  • 「昔の技術の焼き直し」という誤解を避けられる。

📝 この項のまとめ

  • グラフDBはCODASYL（ネットワークモデル）の再来ではない。違いは4つ。
  • ①スキーマ制約なし（自由に接続）、②一意IDやインデックスで直接アクセス可能。
  • ③頂点・辺は順序づけされない、④宣言的クエリ言語（Cypher/SPARQL）をサポート。
2.3.5

礎となったもの：Datalog

ファクト＋ルールで組み立てる ― 後の言語の祖先
📌 要するに：DatalogはSPARQL/Cypherより古く、後のクエリ言語の礎（Prologのサブセット）。predicate(subject, object)でファクトを書き、:-でルールを定義する。ルールは右辺の全述語がマッチすると左辺を導出し、他のルールや自分を再帰参照できる。within_recursiveを繰り返し適用して階層を広げ、migratedで答えを出す。ルールの再利用が強力で、複雑なデータに向く。
ハル
ハル最後のグラフクエリ言語、Datalogですね。
カイ
カイDatalogは、SPARQLやCypherよりずっと古く、1980年代からアカデミックな分野で研究されてきた。あまり知られてないけど、その後のクエリ言語の礎になったから重要。実際DatomicはDatalogをクエリ言語に使い、CascalogはHadoop内の巨大データへのDatalog実装だ。
ハル
ハルデータの書き方はどうなるんですか？
カイ
カイデータモデルはトリプルストアに似てて、もう少し汎用的だ。(subject, predicate, object)じゃなくpredicate(subject, object)と書く。これまでのデータをDatalogで書くとこうだ。

このコードは、これまでのグラフを「○○の△△は××」という事実（ファクト）の並びとして書いたものです。

Datalog：ファクト（事実） 
% これまでのグラフを Datalog の「ファクト（事実）」として書いたもの。
% predicate(subject, object) の形。name(usa, 'アメリカ合衆国') は「usa の名前はアメリカ合衆国」。
name(namerica, '北アメリカ').
type(namerica, continent).

name(usa, 'アメリカ合衆国').
type(usa, country).

within(usa, namerica).
name(idaho, 'アイダホ').

type(idaho, state).
within(idaho, usa).

name(lucy, 'Lucy').
born_in(lucy, idaho).
カイ
カイこれでデータが定義できた。同じ「アメリカ生まれでヨーロッパ移住」のクエリはこう書く。CypherやSPARQLとは見かけが違うけど、気にしなくていい。DatalogはPrologのサブセットなんだ。

このコードは、まず「○○は××の中にある」という関係を再帰的にたどるルールを定義し、それを使って「アメリカ生まれでヨーロッパ在住の人」を探すものです。

Datalog：ルールとクエリ 
% Datalog で「アメリカ生まれでヨーロッパ在住の人」を探すクエリ。
% :- の右がすべて成り立つとき左が導かれる。大文字始まりは変数。
within_recursive(Location, Name) :- name(Location, Name).     /* ルール 1: 場所そのものは within_recursive */

within_recursive(Location, Name) :- within(Location, Via),    /* ルール 2: Location が Via の中にあり、 */
                                    within_recursive(Via, Name). /*           Via が Name の中にあるなら成立（再帰） */

migrated(Name, BornIn, LivingIn) :- name(Person, Name),       /* ルール 3: 人の名前・生誕地・居住地を組み合わせる */
                                    born_in(Person, BornLoc),
                                    within_recursive(BornLoc, BornIn),
                                    lives_in(Person, LivingLoc),
                                    within_recursive(LivingLoc, LivingIn).

?- migrated(Who, 'アメリカ合衆国', 'ヨーロッパ').
/* Who = 'Lucy'. */
ハル
ハルCypherはすぐSELECTが出るのに、Datalogは細かくステップを踏みますね。
カイ
カイその通り。Datalogはまず、DBに新しい述語を伝えるルールを定義する。ここではwithin_recursiveとmigratedの2つ。これらはDBに保存されたトリプルじゃなく、データや他のルールから導出される。関数が他の関数や自分自身を呼べるように、ルールは他のルールを参照できる。だから複雑なクエリを小さな部品から組み上げられる。
ハル
ハル大文字で始まるLocationとかNameは何ですか？
カイ
カイそれが変数だ。述語はCypherやSPARQL同様にマッチする。name(Location, Name)にLocation = namerica、Name = '北アメリカ'とバインドすれば、name(namerica, '北アメリカ')というトリプルにマッチする。ルールは、:- の右辺の全部の述語にマッチが見つかったときに適用される。適用されると左辺がDBに追加されたかのようになる（変数はマッチした値で置き換わる）。
ハル
ハル実際にどう動くのか、追ってみたいです。
カイ
カイいいね。①name(namerica, '北アメリカ')があるのでルール1が適用され、within_recursive(namerica, '北アメリカ')が生成される。②within(usa, namerica)があり、①ができたのでルール2が適用され、within_recursive(usa, '北アメリカ')が生成される。③within(idaho, usa)があり、②ができたのでルール2が適用され、within_recursive(idaho, '北アメリカ')が生成される。
ハル
ハルルール1と2を繰り返すと、だんだん範囲が広がっていくんですね。
カイ
カイそう。これを繰り返すと、within_recursiveから北アメリカにある全場所が分かる。そのうえでルール3で、BornInの場所で生まれLivingInの場所に住む人を探す。BornIn = 'アメリカ合衆国'、LivingIn = 'ヨーロッパ'でクエリし、見つかった人をWhoに残せば、当てはまる値（Lucy）が見つかる。最終的にCypherやSPARQLと同じ答えが出るんだ。
ハル
ハルちょっと考え方が違いますね。これって便利なんですか？
カイ
カイ他のクエリ言語とは違う考え方が要るけど、ルールを組み合わせて様々なクエリで再利用できるから強力なんだ。一度きりの単純なクエリにはそれほど便利じゃないけど、データが複雑ならうまく使える。
1

ルール1：場所そのもの

name(namerica,'北アメリカ') → within_recursive(namerica,'北アメリカ') を生成。

2

ルール2：1段さかのぼる（再帰）

within(usa,namerica) と①から within_recursive(usa,'北アメリカ')。さらに idaho まで広がる。

3

ルール3：人を組み合わせる

生誕地と居住地を within_recursive でたどり、条件に合う人（Lucy）を見つける。

📚 たとえ話：「事実カード」と「導き出すルール」で推理する

Datalogは、図書館に「○○の△△は××」という事実カードを並べ、別に「もしAでBなら、Cと言える」という推論ルールを貼っておく方式です。「アイダホはアメリカの中、アメリカは北アメリカの中 → だからアイダホは北アメリカの中」とルールを繰り返し当てはめて、隠れた事実をどんどん導きます。一度作ったルールは別の調べ物にも使い回せるので、込み入った蔵書の関係をたどるのに向いています。

💡 なぜこれが必要か / これを知ったらできること

  • Datalogの「ファクト＋ルール」という独特の発想を理解できる。
  • ルールの再帰適用で階層をたどる仕組みを追える。
  • ルールを部品として再利用する強力さを理解できる。

📝 この項のまとめ

  • DatalogはSPARQL/Cypherより古く、後のクエリ言語の礎（Prologのサブセット）。
  • predicate(subject, object)でファクトを、:-でルールを定義（大文字は変数）。
  • ルールは右辺の全述語がマッチすると左辺を導出し、再帰や他ルール参照ができる。
  • within_recursiveの繰り返しで階層を広げ、migratedで答えを得る。
  • ルールを再利用できるので、複雑なデータに強い。

第1問一対多とドキュメントモデル

履歴書（プロフィール）のようなデータがJSONドキュメントに向いている理由を、「一対多」「ローカリティ」という言葉を使って説明してください。

✅ 解答例
履歴書は、1人のユーザーに複数のポジションや学歴がぶら下がる「一対多」のツリー構造になっています。JSONドキュメントはこのツリー構造をそのまま入れ子で表現でき、構造が見た目にも明示的になります。さらに、関連する情報がすべて1カ所にまとまる「ローカリティ」に優れているため、プロフィール全体を取り出すのに一度のクエリで済みます。リレーショナルで複数テーブルに分けると、複数回のクエリや込み入った結合が必要になります。
📝 採点ポイント
□ 履歴書が一対多のツリー構造であると説明している ／ □ JSONがツリー構造を入れ子で明示的に表せると述べている ／ □ ローカリティ（関連情報が1カ所、一度のクエリで済む）に触れている
第2問スキーマオンリードとスキーマオンライト

「スキーマオンリード」と「スキーマオンライト」の違いを説明し、それぞれがプログラミング言語のどんな型チェックに似ているかも述べてください。

✅ 解答例
スキーマオンライトは、スキーマ（データの決められた形）を事前に明示し、データを書き込む時にDBがその形に従っているか保証する方式です（リレーショナルの伝統的なやり方）。スキーマオンリードは、データの構造を強制せず、データを読み取る時にだけ構造を解釈する方式です（多くのドキュメントDB）。スキーマオンライトは静的（コンパイル時）型チェックに、スキーマオンリードは動的（実行時）型チェックに似ています。どちらが正しいという答えはなく、用途によります。
📝 採点ポイント
□ スキーマオンライト＝書き込み時に強制、スキーマオンリード＝読み取り時に解釈、と説明している ／ □ それぞれが静的型チェック・動的型チェックに似ていると述べている ／ □ 一般的な優劣はなく用途次第、と触れている
第3問宣言的クエリと命令的クエリ

SQLのような宣言的クエリ言語が、forループで書くような命令的コードより優れている点を、2つ以上挙げて説明してください。

✅ 解答例
①宣言的クエリは「ほしい結果のパターン」だけを指定し「どう達成するか」は指定しないため、簡潔で扱いやすいです。②DBエンジンの実装の詳細が隠れるので、クエリを書き換えなくてもDB側が裏で性能を改善できます（命令的だと順序に依存しているか分からず、勝手に最適化できません）。③結果のパターンだけを指定しアルゴリズムを指定しないため、複数のコアやマシンに並列化しやすく、マルチコア時代に有利です。
📝 採点ポイント
□ 宣言的＝結果のパターンだけ指定、命令的＝手順を順序通り指定、と区別している ／ □ 「実装を隠すので書き換えなしに最適化できる」を挙げている ／ □ 「並列化しやすい」または「簡潔」を挙げている
第4問グラフモデルが向くデータ

ドキュメントモデルが向くデータと、グラフモデルが向くデータの違いを、「一対多」「多対多」という言葉を使って説明してください。

✅ 解答例
ドキュメントモデルは、データの関係がほとんど「一対多」（ツリー構造）で、レコード同士のつながりが少なく、ふつうツリー全体を一度に読むような用途に向いています。一方グラフモデルは、データの中で「多対多」の関係が一般的で、つながりが複雑な場合に自然です。たとえばソーシャルネットワークや、人・場所・イベントなどあらゆるものが関係しうるデータに向きます。関係性が強いほど、ドキュメントは扱いにくく、リレーショナルは許容範囲、グラフが最も自然になります。
📝 採点ポイント
□ ドキュメント＝一対多（ツリー）・関係が少ない用途、と説明している ／ □ グラフ＝多対多・つながりが複雑な用途、と説明している ／ □ 関係性が強いほどグラフが自然、と述べている（具体例があるとなお良い）
第5問グラフDBはネットワークモデルの再来か

現代のグラフデータベースが、1970年代のネットワークモデル（CODASYL）の単なる再登場ではない理由を、2つ以上挙げてください。

✅ 解答例
①CODASYLは「どのレコード型がどれとネストできるか」のスキーマ制約がありましたが、グラフDBには制約がなく、どの頂点も他のどの頂点へも自由に辺を張れます。②CODASYLは特定のレコードに着くにはパスをたどるしかありませんでしたが、グラフDBは一意のIDやインデックスで頂点に直接アクセスできます。③CODASYLのクエリは命令的で書きにくく変更に弱かったのに対し、グラフDBはCypherやSPARQLのような宣言的クエリ言語をサポートします（頂点・辺が順序づけされない点も違いです）。
📝 採点ポイント
□ スキーマ制約の有無（グラフは自由に接続できる）に触れている ／ □ アクセス方法の違い（パスをたどる vs 一意IDやインデックスで直接）に触れている ／ □ クエリ言語の違い（命令的 vs 宣言的なCypher/SPARQL）に触れている
