ストリーム処理 ― 出来事を、起きるそばから次々さばく

バッチ処理は「サイズが決まったデータ」をまとめて処理する。でも現実のデータは止まらず流れ続ける。終わりのないデータ（イベントの流れ）を生まれた瞬間に少しずつ処理する――それがストリーム処理。新人ハルとベテラン カイ先輩の対話で、流れの運び方・DBとの関係・流れの処理の仕方を、ひとつずつ網羅して学びます。

この章に出てくる専門用語を、ニュース速報の配信室のたとえ＋やさしい言葉でまとめました。困ったらここに戻ってきてください。

ストリーム処理 stream processing

終わりのないデータの流れを、生まれた端から少しずつ処理すること。＝出来事を起きるそばから次々さばく配信室。

イベント event

「ある時点で起きたこと」を表す、小さく自己完結した変わらない記録。＝1本の速報原稿。時刻印が付く。

プロデューサ producer

イベントを生み出す側（発行者・送信者）。＝速報を出す記者。

コンシューマ consumer

イベントを受け取って処理する側（購読者・受信者）。＝速報を受け取る部署。

トピック topic

関連するイベントをまとめたグループ。＝ジャンル別の配信チャンネル（スポーツ速報・経済速報など）。

メッセージブローカー message broker

イベントの流れを預かって仲介する専用システム。＝速報の中継デスク。

パブリッシュ/サブスクライブ pub/sub

発行する側と購読する側を多対多でつなぐモデル。＝記者が出した速報を、複数の部署が好きに購読する。

ログベースのブローカー log-based

速報を消さずに連番付きで台帳に残す中継デスク。＝連番付きの速報台帳（Kafka等）。

パーティション partition

1本の台帳を複数に分けて別マシンに置いたもの。＝チャンネルを複数の窓口に分けて並行にさばく。

オフセット offset

パーティション内で各速報に振られる連番。＝台帳の行番号。「どこまで読んだか」を表す。

承認 ack

「処理し終えた」という確認の合図。＝部署が「対応完了」と中継デスクに返事する。

リプレイ replay

過去の速報を巻き戻してもう一度処理すること。＝台帳をさかのぼって読み直す。

変更データキャプチャ CDC

DBの変更を観察して流れとして取り出す仕組み。＝元帳の書き換えをそのまま速報化する。

イベントソーシング event sourcing

出来事の履歴そのものを正本として残す設計。＝起きた出来事の台帳を「真実」にする。

changelog 変更履歴

状態へのすべての変更を時系列に並べた追記ログ。＝配信室がつけ続ける変更の台帳。

コマンド／イベント

コマンド＝まだ失敗しうる要求、イベント＝検証後の確定した事実。＝「速報を出したい申請」と「確定して流れた速報」。

ウィンドウ window

集計の対象にする時間の区切り。＝「直近◯分のまとめ」を出すための時間の窓。

イベントの時刻／処理の時刻

イベントの時刻＝出来事が起きた時刻、処理の時刻＝速報を受け取った時刻。＝事件発生時刻 vs デスクに届いた時刻。

ストリーム結合 stream join

2つの流れを突き合わせて関連づけること。＝2つの速報を照合する。

マテリアライズドビュー materialized view

元データから導出して保存しておく、読みやすい結果。＝速報から作る「まとめ表」。

冪等（べきとう） idempotence

何回やっても1回と同じ結果になる操作。＝同じ速報を二度さばいても結果が変わらない。

exactly-once 厳密に1回

障害があっても「ちょうど1回処理したかのよう」な結果になること（実態はeffectively-once＝事実上1回）。

バックプレッシャー backpressure

受け手が追いつかないとき送り手を止めて流量を抑える仕組み。＝デスクが詰まったら記者の投稿を待たせる。

🎬

あらすじ・要するに・なぜ必要か

この章で何を学ぶのか、最初に地図を持つ

あらすじ

ツバサ社のハルは、前の章で「バッチ処理（まとめて一括処理）」を学んだばかり。ところが運用チームから「ユーザーの行動を1日後じゃなくて、もっとすぐ分析に反映できないか」という要望が来てしまった。1日ぶんを夜にまとめて処理する仕組みでは、どうしても結果が出るのが遅い。困ったハルは、夜のオフィスでカイ先輩に相談する。そこから始まるのは、データを「終わりのない流れ（ストリーム）」として、生まれた端から処理していくという新しい考え方――ストリーム処理の世界をめぐる長い対話だ。

🎯 要するに：バッチ処理は「サイズが決まった有限のデータ」をまとめて処理する。でも現実のデータは止まらず流れ続けるので、「終わりのないデータ（イベントの流れ）」を生まれた瞬間に少しずつ処理したい。それがストリーム処理。この章では、(1) イベントの流れをどう運ぶか（メッセージング、ログベースのブローカー）、(2) データベースの変更そのものを流れとして扱う考え方（CDC、イベントソーシング）、(3) その流れをどう処理するか（時刻の扱い、ウィンドウ、結合、耐障害性）を、ひとつずつ網羅していく。

📡 たとえ話：これから「ニュース速報の配信室」の話をします

この章を通して、ストリーム処理＝出来事を起きた順に流し続けるニュース速報の配信室に置きかえて読みます。イベント＝1本の速報原稿、プロデューサ＝速報を出す記者、コンシューマ＝速報を受け取る部署、メッセージブローカー＝速報の中継デスク、トピック＝ジャンル別の配信チャンネルです。バッチ処理が「夕刊を1日1回まとめて刷る」なら、ストリーム処理は「出来事が起きるたびに速報を流し続ける」配信室です。

💡 なぜこれが必要か / これを知ったらできること

  • 現実のデータは「昨日も今日も明日も増え続ける」もので、本当の意味で「完成」しない。バッチだけでは結果が遅すぎて、せっかちなユーザーやリアルタイム分析の要求に応えられない。
  • DB・キャッシュ・検索インデックスなど複数のシステムを「ずれなく同期させ続ける」には、流れとしての変更（ストリーム）を扱う技術が要る。これは現代のデータ基盤の中核。
  • 用途（ロスを許すか、順序が大事か、再読み込みしたいか）に応じてメッセージの運び方を正しく選べるようになる。
  • 「直近5分の平均」のような時間集計を、遅れて届くイベントまで考えて正しく計算でき、障害時も「ちょうど1回処理したかのよう」な結果（exactly-once）を保てるようになる。
ハル
新人 ハル先輩、こないだ習ったバッチ処理、けっこう気に入ってたんですけど……運用チームから「1日待つのは遅い、もっと早く結果がほしい」って言われちゃって。
カイ
先輩 カイ王道の悩みだね。バッチって、入力のサイズが「ここまで」って決まってるのが大前提だったろ？ MapReduceの中心はソートだけど、入力を全部読み終わるまで出力を始められない。「入力が有限で、いつ読み終わったか分かる」ことに頼ってる。
ハル
ハルでも現実のデータって、終わらないですよね。ユーザーは昨日も今日も明日もデータを作り続けるし……。
カイ
カイまさにそこ。だからバッチは「1日ぶん」「1時間ぶん」って人工的に区切る。でもその区切りが遅延の原因になる。究極は「区切らず、イベントが起きるたびに連続的に処理する」こと。それがストリーム処理の発想なんだ。

ここでカイ先輩は「ストリーム（流れ）」という言葉を整理した。「時間とともに少しずつ使えるようになっていくデータ」のことで、Unixの標準入出力、遅延リスト、TCP接続、ネット経由の音声・ビデオ配信など、身近なところにたくさんある。この章で扱うのは特にイベントストリーム（出来事の流れ）だ。

「ストリーム」が登場する身近な例（メモ） 
# ストリーム（stream, 流れ）とは
# 「時間とともに少しずつ使えるようになっていくデータ」
- Unix の標準入力 stdin / 標準出力 stdout
- プログラミング言語の遅延リスト（必要になったら計算される列）
- ファイルシステムの API（例: Java の FileInputStream）
- TCP 接続
- インターネット経由の音声・ビデオ配信

流れの章立てはこうだ。まず「流れをどうやって運ぶか（11.1 転送）」。次に「データベースと流れの関係（11.2）」。最後に「流れをどう処理するか（11.3）」。じっくりいこう。

11.1

イベントストリームの転送

流れを「どう運ぶか」 ― 速報をどう中継するか
📌 要するに：ストリームではレコードを「イベント（＝1本の速報）」と呼ぶ。プロデューサ（記者）が生成し、コンシューマ（部署）が消費する。関連イベントは「トピック（チャンネル）」でまとめる。DBをポーリング（繰り返し問い合わせ）する手もあるが、遅延を減らそうとすると空振りが増えて無駄になる。新着を「通知」する専用ツール（メッセージングシステム）が必要。
ハル
ハルバッチでは入出力が「ファイル」でした。ストリームだと何になるんですか？
カイ
カイバッチでは入力がファイル（バイトの並び）で、それをレコードの並びにパースした。ストリームでは、そのレコードのことをイベントと呼ぶ。中身はほぼ同じ。小さくて、自己完結してて、イミュータブル（変わらない）なオブジェクトで、たいてい起きた時刻のタイムスタンプを持ってる。
ハル
ハルバッチでは1つのファイルを複数のジョブが読みました。ストリームでも誰かが作って誰かが読むんですか？
カイ
カイそう。生み出す側をプロデューサ、消費する側をコンシューマと呼ぶ。1つのイベントは一度生成され、複数のコンシューマに読まれうる。関連するイベント群はトピックやストリームとしてグループ化される。
ハル
ハルじゃあ単純に、プロデューサがDBに書いて、コンシューマがDBを定期的に見に行けばいいんじゃ？
カイ
カイ原理的にはできる。コンシューマが定期的にポーリングして「前回以降に新しいイベントある？」と聞く。でも遅延を減らそうとポーリングの頻度を上げると、「新しいイベントなし」の空振りが増えて無駄が大きくなる。だったら新着を通知するほうがいい。DBはこの通知が昔から苦手でね。だから通知に特化した専用ツール＝メッセージングシステムが発展してきたんだ。

📡 たとえ話：掲示板を見に行く vs 速報を流してもらう

各部署が「新しい情報ないかな」と何度も掲示板を見に行くのがポーリング。頻繁に見に行くほど「何もなかった」の空振りが増えて、足が疲れるだけ。それより、出来事が起きたら配信室から速報を流して通知してもらうほうがずっと効率的。これがメッセージングシステムの発想です。

イベントの例（メモ） 
# イベントの例
- ユーザーが起こしたこと  : ページの閲覧、商品の購入
- マシンが発生源のこと    : 温度センサーの計測値、CPU 利用率の定期計測
- Web サーバーのログの各行（バッチの章で出てきた例）
※ JSON やバイナリ形式などにエンコードして、ファイル追記・DB 挿入・ネットワーク送信ができる

💡 なぜこれが必要か / これを知ったらできること

  • 「ポーリングは頻度を上げると無駄が増える」と理解すれば、低遅延が必要な場面で通知型を選べる。
  • イベントが「イミュータブルで自己完結」だと知れば、後で何度でも読み直せる設計の土台になる。

📝 この項のまとめ

  • ストリーム処理ではレコードを「イベント」と呼ぶ（小さく・自己完結・イミュータブル・タイムスタンプ付き）。
  • プロデューサが生成、コンシューマが消費。関連イベントはトピック／ストリームでまとめる。
  • ポーリングは低遅延化すると空振りが増えて非効率。新着の「通知」が望ましい。
11.1.1

メッセージングシステム

速報を部署たちに届ける仕組み
📌 要するに：メッセージングシステムはイベントをコンシューマにプッシュ（押し出して届ける）する。複数対複数の発行/購読（pub/sub）モデル。区別の鍵は「送信が速すぎたらどうする（ドロップ／バッファ／バックプレッシャー）」と「クラッシュ時にメッセージを失うか」の2点。ロスを許せるか否かはアプリ次第。
ハル
ハルメッセージングシステムって、何をしてくれるんですか？
カイ
カイプロデューサがメッセージを送ると、それがコンシューマたちにプッシュされる仕組みだ。Unixのパイプやネットワークのコネクションみたいな「直接つなぐ」やり方でも作れるけど、たいていはその上に拡張を加えてる。パイプやTCPは送信者と受信者がきっかり1対1だろ？ メッセージングシステムでは、複数のプロデューサが同じトピックに送れて、複数のコンシューマが1つのトピックを受信できる。この「発行する／購読する」モデルをパブリッシュ／サブスクライブモデルと呼ぶ。
ハル
ハル仕組みはいろいろある感じですか？
カイ
カイ唯一の正解はない。システムを見分けるには、2つの質問をするといい。「送信が速すぎたら？」と「クラッシュしたら失う？」だ。

📡 たとえ話：記者が速報を出しすぎたら、中継デスクはどうする？

記者（プロデューサ）が速報を投げる速さに、受け取る部署（コンシューマ）がついていけないとき、配信室の取れる手は3つ。(a) 捨てる（ドロップ）、(b) いったん溜める（バッファ）、(c) 記者に「ちょっと待って」と止めてもらう（バックプレッシャー）。さらに「中継デスクが落ちたら溜めてた速報は消えるのか」も大事な質問です。

メッセージングシステムを見分ける2つの質問 
# 質問1: プロデューサがコンシューマの処理速度より速く送ったら？
  (a) ドロップ          : メッセージを捨てる
  (b) バッファリング    : キューにためる（あふれたら? クラッシュ? ディスクに書く?）
  (c) バックプレッシャー : 送信側をブロックして送らせない（フロー制御とも）
  # 例) Unix のパイプや TCP は (c)。小さな固定バッファが一杯になると送信側が止まる

# 質問2: ノードがクラッシュ／一時オフラインになったら? メッセージは失われる?
  → 永続性が必要ならディスク書き出し＋レプリケーションが要る（その分コスト増）
  → ロストを許せるなら、同じハードでも高スループット・低レイテンシにできる
ハル
ハルメッセージって、失われても大丈夫なものなんですか？
カイ
カイアプリ次第だ。定期的に送られるセンサーの測定値なら、たまに1個落ちても次がすぐ来るから問題ないことが多い。でもイベントの個数を数えてるなら、ロスはカウンタが不正確になることに直結する。バッチは失敗したタスクを自動リトライして失敗した部分出力は捨てるから「障害が起きなかったのと同じ出力」になる。同じ保証をストリームでどう実現するか――それが章の後半のテーマだ。

💡 なぜこれが必要か / これを知ったらできること

  • 自分のアプリで「メッセージロスが致命的か」を判断でき、永続性のコストをかけるか決められる。
  • バックプレッシャーという概念を知ると、速い送信側に引きずられてシステムが崩れるのを防げる。

📝 この項のまとめ

  • パブリッシュ／サブスクライブモデルは複数プロデューサ・複数コンシューマを許す。
  • 送信過多への対処は3択：ドロップ／バッファリング／バックプレッシャー。
  • 失われるかどうかはアプリ依存。カウント用途などは信頼性が重要。
11.1.1.1

プロデューサからコンシューマへの直接のメッセージング

中継デスクを通さず、記者が部署へ直接届ける
📌 要するに：中間ノードを挟まない直接メッセージング（UDPマルチキャスト、ZeroMQ、webhooksなど）はシンプルで低遅延だが、メッセージロスをアプリが意識せねばならず、送受信が常にオンラインである前提に弱い。
ハル
ハル間に何も挟まず、直接届けるやり方もあるんですか？
カイ
カイあるよ。中間ノードを通さず、プロデューサとコンシューマが直接ネットワーク通信する。UDPマルチキャスト、ZeroMQのようなブローカーなしライブラリ、HTTP/RPCリクエスト（webhooksの発想）などだ。
ハル
ハルシンプルで良さそうですけど、弱点は？
カイ
カイメッセージが失われる可能性をアプリのコードが意識しないといけない。基本「プロデューサもコンシューマもずっとオンライン」が前提だ。コンシューマが落ちてたら、その間のメッセージを見落とすかもしれない。プロデューサが再送できるプロトコルもあるけど、プロデューサ自身がクラッシュしたら、再送するはずだったバッファごと失われる。

📡 たとえ話：記者が部署へ直接電話する

中継デスクを通さず、記者が担当部署へ直接電話で速報を伝えるやり方です。速くてシンプルですが、部署が席を外していたら（オフライン）その速報は聞き逃される。記者が「もう一度かけ直す」つもりでメモを持っていても、記者自身が倒れたらメモごと消えてしまう。「相手が席にいる前提」に弱いのです。

直接メッセージングの例 
- UDP マルチキャスト : 株式市場のフィードなど、低レイテンシ最重視の金融業界で広く使う
                       UDP 自体は信頼できないが、ロスのリカバリはアプリ側で（プロデューサが再送）
- ブローカーなしライブラリ : ZeroMQ や nanomsg。TCP や IP マルチキャスト上で pub/sub を実装
- StatsD / Brubeck   : 信頼できない UDP でメトリクス収集。全メッセージ受信時のみ正確（＝近似になりがち）
- HTTP / RPC リクエスト : コンシューマがサービスを公開していれば、プロデューサが直接プッシュ
                         これが webhooks の発想（コールバック URL を登録し、イベント時にそこへ投げる）

💡 なぜこれが必要か / これを知ったらできること

  • 低遅延が命の金融などでは直接方式が有効だと判断できる。
  • 「相手が落ちると見落とす」弱点を理解し、信頼性が要る場面ではブローカーを選べる。

📝 この項のまとめ

  • 直接メッセージングは中間ノードなしで通信（UDPマルチキャスト、ZeroMQ/nanomsg、HTTP/RPC、webhooks）。
  • ロスをアプリが意識する必要があり、耐えられる故障は限定的。
  • 送受信のどちらかが落ちるとメッセージを失いやすい。
11.1.1.2

メッセージブローカー

「相手が落ちても大丈夫」にする中継デスク
📌 要するに：メッセージブローカーは「メッセージ専用DB」のような仲介役。プロデューサが書き込み、コンシューマが読み取る。クライアントの出入りやクラッシュに強く、永続性の責任はブローカーが負う。配送は非同期（待たずに別タイミングで進む）。
ハル
ハル「相手が落ちても大丈夫」にする方法は？
カイ
カイメッセージブローカーを間に挟むんだ。要するに「メッセージの流れの扱いに特化した一種のデータベース」だ。サーバーとして動いて、プロデューサとコンシューマがクライアントとして接続する。データをブローカーに集中させることで、クライアントの出入り（接続・切断・クラッシュ）に楽に耐えられる。永続性の心配はブローカーに移る。
ハル
ハルプロデューサは送ったら、どこまで待つんですか？
カイ
カイふつうは「ブローカーがバッファした」ところまでしか待たない。コンシューマが処理し終えるのは待たない。つまりコンシューマへの配送は非同期。たいてい1秒未満で届くけど、たまってると遅れることもある。

📡 たとえ話：中継デスクが速報を預かる

記者が部署へ直接電話するのをやめ、いったん中継デスク（ブローカー）に速報を預ける方式です。部署が席を外していても、デスクが速報を保管しておいてくれる。記者は「デスクに渡した」時点で次の取材へ進める（非同期）。速報を失わない責任は、記者でも部署でもなく中継デスクが負います。

メッセージブローカーを介したやり取り（スケッチ） 
[プロデューサ] ──書き込み──▶ [メッセージブローカー] ──読み取り──▶ [コンシューマ]
                              （メッセージを保持）
- プロデューサ: ブローカーにメッセージを書き込む
- コンシューマ: ブローカーからメッセージを読み取って受信する
# 低速なコンシューマがいても、ふつうブローカーは無制限にキューイング（設定次第）

💡 なぜこれが必要か / これを知ったらできること

  • ブローカーを挟めば、コンシューマが落ちてもメッセージが保持され、復帰後に処理できる。
  • 「プロデューサはバッファされた時点で先に進める」非同期性を理解し、レスポンスを速く保てる。

📝 この項のまとめ

  • メッセージブローカー＝メッセージ流に特化したDB的な仲介役。
  • 永続性はブローカー側に集約され、クライアントの出入りに強い。
  • 配送は非同期で、通常は速いがバックログがあると遅れる。
11.1.1.3

メッセージブローカーとデータベースの比較

「聞かれたら答える」DB vs 「変化を教える」ブローカー
📌 要するに：ブローカーはDBに似るが、(1)配信成功で自動削除（長期保存に不向き）、(2)キューは短い前提、(3)検索はトピックのサブスクライブ、(4)クエリではなく変化の通知、という違いがある。旧来型はJMS/AMQP標準（RabbitMQ等）。
ハル
ハルブローカーが「メッセージ専用DB」なら、ふつうのDBと何が違うんですか？
カイ
カイ似てる部分もあって、XAやJTA（分散トランザクションの標準）で2相コミットに参加できるブローカーすらある。でも重要な違いが4つある。表で見よう。
ハル
ハルなるほど、DBは「聞かれたら答える」、ブローカーは「変化があったら教える」んですね。
カイ
カイいい要約だ。ここまで説明したのは旧来のメッセージブローカーの姿で、JMSやAMQPという標準にまとまってる。実装としてはRabbitMQ、ActiveMQ、HornetQ、IBM MQ、Azure Service Bus、Google Cloud Pub/Subなどがある。
観点データベースメッセージブローカー
(1) 保持の仕方明示的に削除するまで保持配信成功したら自動削除 → 長期保存に不向き
(2) 前提するデータ量大量保存が前提すぐ消す前提なので「キューは短い」想定。たまると遅い
(3) データの選び方セカンダリインデックス等で多様に検索パターンに合うトピックの部分集合をサブスクライブ
(4) 結果の鮮度クエリ結果はある時点のスナップショット（再クエリが必要）任意クエリ不可。だが新着が来たら通知する

📡 たとえ話：資料室 vs 速報の中継デスク

DBは資料室。聞きに行けば答えてくれるが、後で誰かが書き換えても教えてはくれない（自分で見に行く）。中継デスク（ブローカー）は速報を流す係。過去の資料は長く置かないが、新しい出来事が起きたらすぐ「変化があった」と教えてくれる。役割が逆なのです。

💡 なぜこれが必要か / これを知ったらできること

  • 「ブローカーは長期保存に向かない」と知れば、保存が要る用途で誤用しない。
  • DBの「聞かれたら答える」とブローカーの「変化を通知する」の役割分担を設計に活かせる。

📝 この項のまとめ

  • ブローカーはDBに似るが、配信成功で自動削除し、キューが短い前提。
  • 検索はトピックのサブスクライブ、結果は「変化の通知」型。
  • 旧来型はJMS/AMQP標準（RabbitMQ、ActiveMQ等）。
11.1.1.4

複数のコンシューマ

速報を複数の部署で分担 or 全員に配る
📌 要するに：複数コンシューマには (a) ロードバランシング（各メッセージを1つのコンシューマへ＝並列化）と (b) ファンアウト（各メッセージを全コンシューマへ＝ブロードキャスト）の2パターンがあり、組み合わせも可能。
ハル
ハル1つのトピックを複数のコンシューマで読むとき、どう配るんですか？
カイ
カイ主に2つのパターンがある。ロードバランシング（負荷分散）は各メッセージを「どれか1つ」のコンシューマへ。処理を分担して並列化できる（重い処理向き）。ファンアウト（拡散配信）は各メッセージを「すべての」コンシューマへ。独立した複数のコンシューマが同じ放送を別々に聴ける。
ハル
ハル同じ入力ファイルを複数のバッチジョブが読むのが (b) のファンアウトに近い感じですね。
カイ
カイその通り。そして2つは組み合わせられる。独立した2つのコンシューマグループが同じトピックを購読し、各グループは集団として全メッセージを受け取りつつ、グループ内では1メッセージを1ノードだけが受け取る、という具合に。

📡 たとえ話：手分け処理 vs 全部署に同報

大量の速報を3つの部署で手分けして、1本ずつ別々の部署が担当するのがロードバランシング（早くさばける）。一方、同じ速報を全部署に同時に配るのがファンアウト（経済部も社会部も同じ速報を別々の目的で見る）。組み合わせれば「速報を全グループに配りつつ、各グループ内では手分け」もできます。

🔀

(a) ロードバランシング

各メッセージはどれか1つのコンシューマへ。処理を分担し並列化（重い処理向き）。例：AMQPの同一キューを複数で消費、JMSの共有サブスクリプション。

📣

(b) ファンアウト

各メッセージは全コンシューマへ。独立に同じ放送を聴ける。例：JMSのトピックサブスクリプション、AMQPのExchange対応付け。

💡 なぜこれが必要か / これを知ったらできること

  • 「重い処理は分担したい」ならロードバランシング、「全員に同じ通知を配りたい」ならファンアウトと選べる。
  • 2つを組み合わせて「グループ単位の配信＋グループ内の分担」を設計できる。

📝 この項のまとめ

  • ロードバランシング：各メッセージを1コンシューマへ。処理を分担し並列化。
  • ファンアウト：各メッセージを全コンシューマへ。独立に同じ放送を聴ける。
  • 2パターンは組み合わせ可能。
11.1.1.5

承認と再配信

「対応完了」の返事と、来なかったときの再送
📌 要するに：承認は「処理し終えた確認」。承認が来ないとブローカーは再配信する。ロードバランシングと再配信が組み合わさると、メッセージの順序が入れ替わりうる。順序が大事なら、コンシューマごとに別キューにする。
ハル
ハルコンシューマが処理途中でクラッシュしたら、そのメッセージはどうなるんですか？
カイ
カイそこで承認（ack）を使う。クライアントは処理を終えたら明示的にブローカーに「終わった」と伝え、ブローカーはそのメッセージをキューから消す。承認が来なかったら（コネクション切れやタイムアウト）、ブローカーは「処理されなかった」とみなして別のコンシューマに再配信する。ただし、実際は処理済みなのに承認だけネットワークで失われることもある。
ハル
ハル再配信って、何か副作用があるんですか？
カイ
カイロードバランシングと組み合わさると、メッセージの順序が変わるんだ。順序を守ろうとしても（JMSもAMQPも順序保持を要求してる）、ロードバランシング＋再配信が組み合わさると順序変化は避けられない。回避するにはコンシューマごとに別キューを使う（＝ロードバランシングを使わない）しかない。

📡 たとえ話：返事が来ないと別の部署へ回す

中継デスクは、速報を渡した部署から「対応完了」の返事（承認）が来て初めて控えを消します。返事が来ないと「あの部署、倒れたかな」と判断して別の部署へ回す（再配信）。すると、手分け処理しているせいで、速報3が再配信で別の部署に回り、速報4より後に処理される――送った順と処理した順がずれるのです。順番が命の速報は、1部署が専任（別キュー）で順に処理するしかありません。

再配信で順序が入れ替わる例（プロデューサが m1〜m5 を送信） 
時間 ──────────────────────────────▶
コンシューマ1: m1 ........ m4   m3(再)  m5
コンシューマ2: ... m2   m3(処理中にクラッシュ!) ✗

- コンシューマ2 が m3 を処理中にクラッシュ（承認なし）
- 同じころコンシューマ1 は m4 を処理していた
- 承認されなかった m3 は後からコンシューマ1 へ再配信
- 結果、コンシューマ1 の処理順は m4 → m3 → m5
- → m3 と m4 がプロデューサの送信順とは違う順序で処理された

💡 なぜこれが必要か / これを知ったらできること

  • 承認の仕組みを理解すれば、コンシューマのクラッシュでメッセージを失わない設計ができる。
  • 「ロードバランシング＋再配信で順序が崩れる」と知り、因果関係のあるメッセージでは別キューを選べる。

📝 この項のまとめ

  • 承認：処理完了を伝え、ブローカーがメッセージを削除できるようにする。
  • 承認が届かないと再配信。ただし「処理済みなのに承認だけロスト」もありうる。
  • ロードバランシング＋再配信は順序を入れ替える。順序が重要なら別キュー。
11.1.2

パーティション化されたログ

速報を消さずに「連番付きの台帳」に残す
📌 要するに：旧来のブローカーは「メッセージは一時的」が前提で、配信後すぐ消す。受信が破壊的で再実行に弱く、後から来たコンシューマは過去を読めない。これに対し、DBの永続性とメッセージングの通知を合体させたのがログベースのブローカー。
ハル
ハルここまでのブローカーって、配信したらメッセージを消しちゃうんですよね。なんだか「使い捨て」っぽい。
カイ
カイいいところに気づいた。旧来のブローカーは、ディスクに書く永続型でさえ、配信したらすぐ消す。「メッセージングは一時的」という考えが中心にあるんだ。でもDBやファイルは逆で、消すまでずっと残る。AMQP/JMSは承認でメッセージが消える＝受信が破壊的だから、同じコンシューマを再実行しても同じ結果にならない。後から新しいコンシューマを足しても、登録時点以降しか受け取れない。
ハル
ハルだったら「DBの永続性」と「メッセージングの低遅延な通知」を合体できないんですか？
カイ
カイそれこそがログベースのメッセージブローカーの発想なんだよ。

📡 たとえ話：その場で破り捨てる速報 vs 連番付きの速報台帳

旧来の中継デスクは、部署に渡した速報の控えをその場で破り捨てる。後から来た新人部署は、昨日の速報を読めません。ログベースのブローカーは、すべての速報を連番を振って台帳に書き残す方式。読んでも消えないので、誰でも好きな番号からさかのぼって読み直せます。

💡 なぜこれが必要か / これを知ったらできること

  • 「受信が破壊的だと再実行できない」問題を理解し、再処理したい用途でログ型を選べる。
  • 永続性と通知を両立させる発想（ログベース）の必要性が分かる。

📝 この項のまとめ

  • 旧来ブローカーはメッセージを一時的に扱い、配信後に削除（破壊的・再実行に弱い）。
  • 後から来たコンシューマは過去のメッセージを読めない。
  • DBの永続性＋メッセージングの通知＝ログベースブローカーという発想。
11.1.2.1

メッセージストレージへのログの利用

追記専用の台帳と、台帳を分ける「パーティション」
📌 要するに：ログは「追記専用のレコードの並び」。プロデューサは末尾に追記、コンシューマは順に読む。スループットのためにログをパーティション化し、各メッセージにオフセット（パーティション内の連番）を振る。パーティション内は全順序だが、またぐ順序は保証なし。Kafka等が代表。
ハル
ハル「ログ」ってここでは何のことですか？
カイ
カイ単純に「追記だけができる、ディスク上のレコードの並び」だ。プロデューサがメッセージをログの末尾に追記して送り、コンシューマがログを先頭から順番（シーケンシャル）に読む。末尾まで読んだら、新しい追記の通知を待つ。Unixの「tail -f」（ファイル末尾の追記を監視）と基本的に同じ動きだよ。
ハル
ハル1本のログだと、ディスク1台ぶんしか速度が出ない気がします。
カイ
カイそこでパーティション化する。ログを複数のパーティションに分けて、別々のマシンに置く。各パーティションは独立に読み書きできるから、全体のスループットが上がる。トピックは「同じ種類のメッセージを扱うパーティションのグループ」と定義できる。各メッセージには単調増加する連番オフセットが振られる。
ハル
ハル実際の製品だと何がありますか？
カイ
カイApache Kafka、Amazon Kinesis Streams、TwitterのDistributedLogがこの方式だ。GoogleのCloud Pub/Subもアーキテクチャは似てる。全メッセージをディスクに書きつつ、パーティショニングで毎秒数百万メッセージ、レプリケーションで耐障害性を実現する。パーティション内は全順序だけど、複数パーティションをまたぐ順序は保証されない。

📡 たとえ話：窓口を増やして並行に台帳をさばく

1冊の速報台帳に全員が書き込むと、1人の書記の手の速さが上限になります。そこで台帳を窓口ごとに分冊（パーティション）し、別の書記が並行に書く。各分冊の行には行番号（オフセット）が振られ、その分冊の中では順番がはっきり分かる。ただし「窓口Aの3行目と窓口Bの3行目、どちらが先か」はわからない――またぐ順序は保証されないのです。

パーティション化されたログ（トピック = パーティションの集まり） 
プロデューサ ──追記──▶ [ ... | e1 | e2 | e3 | e4 | (末尾) ] ◀──順に読む── コンシューマ
                       追記だけのレコードの並び（ログ）

トピック「クリックイベント」
  パーティション0: [ 0 | 1 | 2 | 3 | 4 ... ]  ← マシンA
  パーティション1: [ 0 | 1 | 2 | 3 ... ]      ← マシンB
  パーティション2: [ 0 | 1 | 2 | 3 | 4 | 5 ]  ← マシンC
              ↑ 箱の中の番号 = オフセット（そのパーティション内の連番）

💡 なぜこれが必要か / これを知ったらできること

  • パーティション化で「1台のディスク」の限界を超えてスケールできると分かる。
  • オフセットの概念を理解し、「どこまで読んだか」を管理する設計につなげられる。

📝 この項のまとめ

  • ログ＝追記専用のレコードの並び。コンシューマはシーケンシャルに読む。
  • パーティション化で複数マシンに分散し、スループットを上げる。
  • 各メッセージにオフセット。パーティション内は全順序、またぐ順序は保証なし。
  • 代表例：Kafka、Kinesis、DistributedLog。
11.1.2.2

従来のメッセージングとログの比較

ログ型の長所と、粗い分担の弱点
📌 要するに：ログ方式はファンアウトが容易。ロードバランシングはパーティション単位の粗い割り当てで、(1)並列度がパーティション数で頭打ち、(2)重いメッセージで後続が詰まる、という欠点がある。重い処理・順序不問なら旧来型、高スループット・順序重視ならログ型。
ハル
ハルログ方式は、ファンアウトもロードバランシングもできるんですか？
カイ
カイファンアウトは簡単だ。複数コンシューマが互いに影響せず独立にログを読めて、読んでも消えないからね。ロードバランシングはちょっと粗い。個々のメッセージじゃなく、パーティション全体をコンシューマグループのノードに割り当てる。各ノードは割り当てられたパーティション内の全メッセージを、ふつう単一スレッドで順に読む。これには2つの欠点がある。
ハル
ハルじゃあ、どっちを使えばいいんですか？
カイ
カイ使い分けだ。1メッセージの処理が重くてメッセージ単位で並列化したい、順序はそこまで重要でないならJMS/AMQPスタイル（旧来型）。スループットが高く、1メッセージは高速に処理でき、順序が重要ならログベースだ。

📡 たとえ話：チャンネルごと丸ごと1部署に任せる

ログ型の分担は、速報を1本ずつ配るのではなく、「スポーツチャンネルは丸ごとA部署、経済チャンネルは丸ごとB部署」とチャンネル単位で任せます。だから手分けできる部署の数はチャンネルの数が上限。しかも、1本だけ処理に時間のかかる速報があると、同じチャンネルの後続の速報がぜんぶ詰まって待たされます（先頭の詰まりが後続を止める）。

パーティション単位ロードバランシングの欠点と使い分け 
# 欠点
(1) 並列度の上限 = パーティション数
    同じパーティションのメッセージは同じノードに行くので、
    分担できるノード数はパーティション数までしか増やせない
(2) ヘッドオブラインブロッキング
    処理に時間がかかるメッセージが1つあると、
    同じパーティション内のそれ以降のメッセージが滞る

# 使い分けの目安
- JMS/AMQP（旧来型）: 1メッセージの処理が重く並列化したい / 順序はそこまで重要でない
- ログベース        : スループットが高く、1メッセージは高速 / 順序が重要

💡 なぜこれが必要か / これを知ったらできること

  • 並列度がパーティション数に縛られると知り、最初に十分なパーティション数を設計できる。
  • 用途（順序重視か並列重視か）でブローカー方式を選べる。

📝 この項のまとめ

  • ログ方式はファンアウトが容易（読んでも消えない）。
  • ロードバランシングはパーティション単位＝並列度の上限はパーティション数。
  • 重い1メッセージが後続を詰まらせる（ヘッドオブラインブロッキング）。
  • 旧来型＝重い処理・順序不問、ログ型＝高スループット・順序重視。
11.1.2.3

コンシューマのオフセット

「どこまで読んだか」を行番号で記録するだけ
📌 要するに：ログ方式ではコンシューマのオフセットを記録するだけで「どこまで処理したか」が分かる（個別承認が不要）。これはDBレプリケーションのログシーケンス番号と同じ原理。ノード障害時は別ノードが最後のオフセットから再開し、記録漏れぶんは再処理される。
ハル
ハルログ方式だと、どこまで処理したか管理しやすそうですね。
カイ
カイその通り。パーティションを順に処理するから、「現在のオフセットより小さいものは処理済み、大きいものは未処理」と一目で分かる。だからブローカーは個々のメッセージの承認を追跡しなくていい。定期的にコンシューマのオフセットを記録するだけ。管理のオーバーヘッドが減って、スループットを上げやすい。これは5章のシングルリーダーDBのログシーケンス番号にそっくりだ。ブローカーがリーダーDB、コンシューマがフォロワーみたいに振る舞う。
ハル
ハルコンシューマのノードが落ちたら？
カイ
カイそのパーティションはグループ内の別ノードに割り当てられて、最後に記録されたオフセットから処理を再開する。もし落ちたノードがもっと先まで処理してたのにオフセットを記録してなかったら、そのぶんは再開後にもう一度処理される。この「二重処理」の対処は章の後半でやる。

📡 たとえ話：しおりを挟んでおくだけ

部署は速報台帳を読み進めながら、「ここまで対応済み」というしおり（オフセット）を挟むだけ。中継デスクは1本ずつの「対応完了の返事」を管理しなくていい。担当部署が倒れても、別の部署がしおりの位置から読み再開できます。ただし、倒れる直前にしおりを更新し忘れていたら、その間の速報はもう一度処理されます。

💡 なぜこれが必要か / これを知ったらできること

  • 「オフセット記録だけで進捗管理できる」ためスループットを上げやすいと理解できる。
  • 障害復帰時に「記録漏れぶんが再処理される」と知り、後述の冪等性対策の必要性が見える。

📝 この項のまとめ

  • コンシューマのオフセットで進捗が分かり、個別の承認が不要。
  • DBレプリケーションのログシーケンス番号と同じ原理（ブローカー＝リーダー、コンシューマ＝フォロワー）。
  • ノード障害時は別ノードが最後のオフセットから再開。記録漏れぶんは再処理されうる。
11.1.2.4

ディスク領域の利用

台帳は「巨大な循環バッファ」、古いものから上書き
📌 要するに：ログはセグメントに分けて古いものを削除・アーカイブする「巨大な循環バッファ」。HDD 6TB・150MB/秒なら約11時間、実際は数日〜数週間ぶん残せる。全部ディスクに書くのでスループットはほぼ一定（メモリ優先型は履歴量に依存して遅くなる）。
ハル
ハルでも追記し続けたら、いつかディスクが一杯になりますよね？
カイ
カイなる。だからログをセグメント（区間）に分けて、古いセグメントは削除するかアーカイブに移す。実質、ログは「固定サイズで、一杯になったら古いものから消える循環バッファ（リングバッファ）」なんだ。ただしディスク上だから、すごく大きくできる。
ハル
ハル普通のメッセージングシステムと、何か違いがあるんですか？
カイ
カイ大きく違う。ログは「どれだけ履歴を残すか」に関係なく全部ディスクに書くから、スループットがほぼ一定だ。一方、デフォルトでメモリに持ち、あふれたらディスクに書くタイプは、キューが短いうちは速いけど、ディスク書き込みが始まると一気に遅くなる。スループットが「どれだけ履歴を残すか」に依存しちゃうんだ。

📡 たとえ話：壁一面の速報ボード、古い紙からはがす

速報台帳は壁一面の巨大なボード。新しい速報を貼り続け、一杯になったら一番古い紙からはがして捨てます（循環バッファ）。ボードがとても大きいので、たいてい数日〜数週間ぶんの速報が貼ったまま残せる。しかも貼る作業の速さは「どれだけ古い紙を残しているか」に左右されず、いつも一定なのです。

ログのバッファ容量の概算（本書執筆時点の典型値） 
- 大容量 HDD の容量          : 6 TB
- シーケンシャル書き込み速度 : 150 MB/秒
- 上限速度で書き続けて一杯にするまで : 約 11 時間
→ つまり「約 11 時間ぶん」をバッファできる（超えたら古いメッセージを上書き）
※ 実際はディスク帯域を使い切ることは稀なので、ふつうは数日〜数週間ぶん残せる
※ HDD やマシンを増やしてもこの「比率」は変わらない

💡 なぜこれが必要か / これを知ったらできること

  • 「数日〜数週間ぶん残せる」と分かれば、コンシューマの遅れにどれだけ猶予があるか見積もれる。
  • ログ型のスループットが一定という性質を、性能予測に使える。

📝 この項のまとめ

  • ログはセグメント分割＋古いもの削除で、実質「巨大な循環（リング）バッファ」。
  • HDD 6TB・150MB/秒で約11時間、実用上は数日〜数週間ぶん保持できる。
  • 全部ディスクに書くのでスループットはほぼ一定。
11.1.2.5

プロデューサにコンシューマがついて行けない場合

遅れすぎると読めないが、他には影響しない
📌 要するに：ログ方式は「巨大だが固定サイズのバッファ」。コンシューマが遅れすぎると古いメッセージは読めなくなるが、遅れを監視して警告できるし猶予も大きい。1つのコンシューマが遅れても他に影響しないので、本番ログを実験用に消費しても安全。
ハル
ハルコンシューマが遅れて、ログの古い部分が消されちゃったら？
カイ
カイ3択（ドロップ／バッファリング／バックプレッシャー）で言えば、ログ方式は「巨大だが固定サイズのバッファを使うバッファリング」だ。コンシューマが大きく遅れて、必要なメッセージが保持期間より古くなると読めなくなる。事実上、バッファに収まらない古いメッセージをドロップするわけだ。対策は、コンシューマが先頭からどれだけ遅れてるかを監視して、遅れが大きくなったら警告を出すこと。バッファが大きいから、運用担当者が直す時間は十分にある。
ハル
ハルもし1つのコンシューマが落ちたら、他に影響しますか？
カイ
カイここがログ方式の大きな利点でね。あるコンシューマが大きく遅れてメッセージを見落とし始めても、影響を受けるのはそのコンシューマだけ。他のコンシューマへのサービスは損なわれない。だから本番のログを、実験・開発・テスト・デバッグのために消費しても、本番サービスをあまり心配しなくていい。旧来型では、止めたコンシューマのキューにメッセージがたまって、動いてるコンシューマのメモリを奪っちゃうから対照的だ。

📡 たとえ話：ボードからはがれる前に読みに来て

遅れがちな部署が、速報ボードの古い紙がはがされる前に読みに来られなかったら、その速報は読めません。でもボードはとても大きいので猶予は十分。配信室は「あの部署、ずいぶん遅れてるぞ」と監視して警告を出せます。しかも、その部署が遅れても他の部署はまったく困らない。だから新しい実験部署が本番ボードを自由に読んで練習しても安全なのです。

💡 なぜこれが必要か / これを知ったらできること

  • コンシューマの遅れを監視・警告する運用設計ができる。
  • 「コンシューマ同士が独立」と知り、本番ログを実験・開発に安全に使い回せる。

📝 この項のまとめ

  • ログ方式は巨大固定サイズのバッファ。遅れすぎると古いメッセージはドロップされる。
  • 遅れを監視して警告でき、修正の猶予は大きい。
  • コンシューマ同士は独立で、1つが遅れても他に影響しない（実験消費が安全）。
11.1.2.6

古いメッセージのリプレイ

台帳をさかのぼって、何度でも読み直す
📌 要するに：ログ方式の消費はリードオンリーで、副作用はオフセットの前進だけ。オフセットを巻き戻せば古いメッセージをリプレイ（再処理）でき、コードを直しながら何度でも繰り返せる。バッチ処理同様、実験やバグ回復が容易になる。
ハル
ハルAMQP/JMSは受信が破壊的でしたよね。ログ方式は違うんですか？
カイ
カイ全然違う。ログ方式の消費は「ファイルの読み取り」に近くて、ログを書き換えないリードオンリーの操作だ。メッセージを処理して生じる唯一の副作用は、コンシューマのオフセットが前進することだけ。しかもそのオフセットはコンシューマが制御してるから、自由にいじれる。だからリプレイ（再処理）ができる。昨日のオフセットから処理を始めて出力を別の場所に書けば、昨日ぶんを再処理できる。コードを書き換えながら何度でも繰り返せる。
ハル
ハルそれ、バッチ処理に似てますね。入力を壊さずに何度も実験できる感じ。
カイ
カイまさに。リプレイができるおかげで、導出データが入力データと明確に分離される。実験を増やせるし、エラーやバグからの回復もしやすい。だからログベースのメッセージングは、組織内のいろんなデータフローをつなぐ道具としても優秀なんだ。

📡 たとえ話：しおりを昨日のページに戻して読み直す

速報台帳は読んでも消えないので、部署は自分のしおり（オフセット）を昨日のページまで戻して、もう一度読み直すことができます。集計の計算式を直してから昨日の速報を全部やり直し、正しいまとめ表を作り直す、なんてことが何度でもできる。元の台帳（入力）は無傷のまま。だから安心して実験できるのです。

💡 なぜこれが必要か / これを知ったらできること

  • バグを直してから過去のイベントを再処理し、正しい結果に作り直せる。
  • 新しい導出ビューを「過去のログを最初から再生して」ゼロから構築できる。

📝 この項のまとめ

  • ログ消費はリードオンリー。副作用はオフセット前進のみ。
  • オフセットを巻き戻してリプレイ（再処理）でき、コード修正と再実行を繰り返せる。
  • 導出データと入力が分離され、実験・バグ回復が容易（組織のデータフロー結合に有用）。
